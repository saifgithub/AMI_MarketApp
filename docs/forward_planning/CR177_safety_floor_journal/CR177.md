# CR177 — the app never records that it stopped you

**Filed** 2026-08-13, from Saiful's directive during the CR133 discussion:
*"The safety-floor issue — create a CR."*

**Status:** proposed. Surfaced by CR133's schema audit of what INSIGHTS could actually
compute, then measured directly against `backend/app/api/sim.py`.

---

## 1. Why

AMI's product claim is that it makes you a better decision-maker. The safety floor is the
sharpest teaching instrument in the app: it is the moment the product refuses to let you
break a rule **you wrote yourself**.

That moment is not recorded anywhere.

Measured at `backend/app/api/sim.py:362`:

```python
    if not result.accepted:
        return {
            "ok": False,
            "compliance": {
                "passed": result.compliance.passed,
                "violations": result.compliance.violations,
                "blocked_by": result.compliance.blocked_by,
                ...
            },
        }

    trade = result.trade
    assert trade is not None
    ...
    # Journal capture — sim_trade entry          <- line 390, unreachable when blocked
```

The blocked path returns **before** the journal write. The violation reaches the UI in the
response, the ticket shows it, and then it is gone. Nothing durable is written.

**What that costs, concretely.** AMI stops you from breaching your own position-size cap on
Tuesday. On Friday you open the Journal to review your week. The block is not there. You
cannot see that you attempted the same breach four times, and neither can anything else:

- **The Decision Journal is incomplete in the one place it claims authority.** It is the
  record of your decisions, and an attempted trade that was refused *is* a decision.
- **CR133's INSIGHTS card "how your mandate has moved" is weaker than it looks.** It can show
  that a limit was loosened; it cannot show that you were repeatedly hitting that limit
  first. The loosening-after-a-loss pattern the card exists to surface is exactly the one
  that needs the blocks to be legible.
- **It is invisible to us as well as to the user.** We cannot answer "is the safety floor
  firing at all, and on what?" from data. For a control whose entire justification is that
  it is *structural rather than prompt-level* (CLAUDE.md: *"prompt instructions are not
  controls"*), having no record of it firing is a gap in our own assurance.

This is the CR040 family seen from the other side. The usual failure is a silent fallback
that makes a broken thing look fine. Here a control works **correctly** and leaves no trace,
so a working safety floor and an absent one produce the same history.

---

## 2. Scope

**In:** the training path only — `POST /v1/sim/trade`'s blocked branch.

**Out, and why:**

- **The game path.** `sim_engine.py:1006` has a structurally similar early return, but games
  deliberately do not run the safety floor (implementation_plan §7.1 keeps two public entry
  points precisely so the game never calls it). That rejection is a cash/limit refusal, not a
  mandate block, and folding the two would blur the boundary that CR109's fence exists to
  hold.
- **`POST /v1/sim/preview`.** A preview is a question, not a decision. Journaling every
  keystroke-level dry run would bury the real events — the reminder-rule logic of CR176
  applies here too.
- **The PM's own verdict.** `check_mandate_compliance` also wraps the Room's verdict; whether
  that deserves an entry is a separate question and is not claimed here.

---

## 3. It must NOT be a `SIM_TRADE`

The tempting cheap version — reuse `EntryType.SIM_TRADE` with a `blocked` tag — is wrong, and
CR133 is what makes it obviously wrong.

INSIGHTS card 1, *"how your trades ended"*, buckets `SIM_TRADE` rows on `won`/`lost`/`manual`.
A blocked attempt is **not a trade**: nothing filled, no position existed, there is no
outcome. Putting it in `SIM_TRADE` would silently inflate the denominator of the card CR133
calls its strongest, and every ratio in it would quietly become wrong.

**Proposed: a new `EntryType.COMPLIANCE_BLOCK = "compliance_block"`.**

Rejected alternative: **reuse the dead `EntryType.DRIFT_ALERT`.** It has no writer anywhere
(CR133 found this), so it is superficially free. But it names a different event — *your
mandate has drifted* — and CR133 already identifies it as the natural home for "your mandate
loosened right after a loss". Spending it here would cost that, and would leave a type whose
name does not describe its rows.

---

## 4. What the entry records

Everything already present on the blocked response, so no new computation:

| Field | Source |
|---|---|
| `blocked_by` | `result.compliance.blocked_by` — **which rule stopped you**, the load-bearing field |
| `violations` | `result.compliance.violations` |
| ticker · side · quantity · order type | the request |
| `sharia_verdict` / `classification_verdicts` | when present |

`Outcome` stays `PENDING`-equivalent or absent — a block has no win/loss and must never be
rendered as either.

---

## 5. Two hazards this CR has to design against

**5.1 — The client will not know the type for days.** Backend ships by rsync same-day; the
Flutter client ships through store review. `mobile/lib/models/journal.dart::fromWire` returns
**`JournalEntryType?`** — `null` for an unrecognised wire value. So the moment the backend
starts writing `compliance_block`, every installed build receives entries it cannot name.

This is the same topology as CR109 Amendment M's 404-tolerance, and it is an acceptance
condition rather than a footnote: **the entry must be inert on a client that does not know
it — verified before the backend ships, not after.** If the null path crashes or renders a
blank card, the client-side tolerance lands first and the backend write waits for it to reach
devices.

**5.2 — Frequency is the signal, but a hammered button is not.** A user who taps submit
twenty times against the same cap produces twenty identical blocks. That the attempt repeated
*is* the teaching signal and must not be deduped away; twenty rows in the Journal for one
frustrated minute is noise. Proposal: write every block (the data stays honest) and let the
reader aggregate — but state a measured position on rapid identical repeats before shipping,
rather than discovering it in the Journal.

---

## 6. Acceptance

1. A trade blocked by the safety floor writes **exactly one** journal entry naming the rule
   that blocked it (`blocked_by` present and non-empty).
2. That entry is **not** an `EntryType.SIM_TRADE`, asserted by a test — so CR133's
   "how your trades ended" denominator is provably unchanged.
3. An accepted trade writes exactly the entries it writes today. No double-write, no
   behaviour change on the happy path.
4. The game path writes no compliance-block entry, asserted — the §7.1 fence holds.
5. A client that does not know the type renders it inertly and never as a result (CR040).
6. Mutation proof: removing the new write turns a test red.

---

## 7. What this unlocks

Once the rows exist, INSIGHTS gains a card CR133 could not specify because the data did not
exist: **how often AMI stopped you, and which rule.** That is arguably the single most
educational number the app could show — it is the product's core claim, measured. It is
**not** claimed in this CR; this CR only makes it computable.

---

## 8. Effort

Small. One journal write on an existing branch, one enum value on each side, one client
render case, plus the tolerance check of §5.1. No migration — `journal_entries` already
stores `payload` as JSON.
