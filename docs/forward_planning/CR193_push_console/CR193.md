# CR193 — a founder-triggerable push console (`/send-test-push`)

**Status:** in_progress · **Filed:** 2026-08-18 (AT:R70)

## What

A new ops slash-command, `.claude/commands/send-test-push.md`, that lets Saiful trigger a
real OneSignal push from the Mac without needing to remember SSH/docker syntax: it resolves
a user by email via the admin API (LAN-direct), lists their registered devices, confirms
with him, then sends via `backend/scripts/send_notification.py` running inside the
`api-alpha` container on melehost.

## Why

Asked whether push notifications work, the honest answer was: infra is proven green
(DEF209, closed 2026-08-06 — key auth, send-endpoint auth, both platform credentials, device
registration all measured directly against the live OneSignal API), but nobody has ever
confirmed a push landing on a real handset. DEF209's own closing note named that as the one
remaining step, deferred to Saiful because it's user-visible — and it's sat undone since
2026-08-07. Offered a one-off test send to close it, Saiful's answer was: *"we have not yet
build the capability for me to send push messages from a console. maybe from this mac."* The
gap isn't the one test — it's not having a repeatable way to trigger one himself, for this
and for every future push-shaped feature (CR176's game push, CR187's resting-order push,
CR095's daily reminder, CR135's eventual notification list).

## Scope

**In:**

1. `.claude/commands/send-test-push.md` — an instruction doc Claude Code follows, not new
   backend code, following the existing `/promote-to-alpha` / `/rollback-alpha` ops-command
   pattern.
2. User resolution via `GET /v1/admin/users?email=...` against `http://192.168.20.59:8000`
   directly (LAN-direct per the standing route preference — melehost is on the LAN, no need
   to go through the Cloudflare tunnel), bearer-authed with `ADMIN_SECRET` (already present
   in `infra/alpha.env`). No SSH needed for lookup.
3. Device listing via `GET /v1/admin/users/{user_id}` (`AdminUserDetail.devices`:
   `device_model`, `os_version`, `last_seen_at`) so Saiful sees which handset(s) will buzz
   before confirming.
4. A confirm-before-send gate (target, title, body) — this is a real, user-visible action.
5. The actual send stays SSH + exec, since no HTTP route triggers `notify()` today:
   ```
   ssh melehost "cd ~/ami_trade && docker compose exec -T api-alpha \
       python -m scripts.send_notification --user-id <uuid> --title '...' --body '...' --type test_push"
   ```
6. Reporting `push_status` / `push_detail` back, plus two caveats every run should carry:
   OneSignal targets `external_user_id` = the whole account, fanning out to *every* device
   on it (no single-device targeting exists); and the send shares `notify()`'s per-user rate
   limit (1/minute, 3/hour) with real notifications.

**Out:**

- An HTTP admin route to trigger a send — would need its own auth/audit design for a
  since-real-user-visible action; SSH+exec is enough for founder-only, occasional use.
- Per-device targeting. A single-device test needs a dedicated test account signed into only
  that one phone.
- Anything on the notification-history/bell UI — that's CR135.

## Acceptance

1. Saiful can run `/send-test-push <email>` from the Mac and get back a real device list
   without SSHing anywhere himself.
2. The command refuses to send without an explicit confirm.
3. A real send against Saiful's own account returns `push_status=sent` and the push is
   observed arriving on the phone — closing the last open thread on DEF209.
4. If it does **not** arrive, that's a new finding (DEF209's diagnosis found no fault
   upstream of delivery) — file a new DEF rather than reopening DEF209.
