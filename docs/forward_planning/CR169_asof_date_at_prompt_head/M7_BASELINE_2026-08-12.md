# CR169 — M7 built, baseline run, and what it says about this CR

**Run:** 2026-08-12 · **Corpus:** `corpus/llm_audit_2026-08-07-epoch.json`, 198 prose turns, one epoch
· **Result:** **0 / 30 mismatched date claims = 0.0%** · **Verdict per the CR's own fork table:
`dropped`. M7 stays.**

---

## 1. M7 exists

`backend/scripts/prompt_quality_sweep.py::m7_date_accuracy`. Deterministic, no LLM judge, so unlike
M1–M6 it can gate a commit — the CR143 §7 gap the CR names.

It scores exactly one construct, the self-checking one the CR quotes: a reply that states **both** a
date and a distance to it (*"$608.23 by 2026-11-03 (88 days)"*). The fact sheet's `as of` line decides
whether they agree; no interpretation is needed. Tolerance ±1 day absorbs the inclusive/exclusive
convention.

**Getting to a trustworthy 0% took three corrections, all found by hand-reading rather than by
trusting the first number** — recorded because each is a way this metric could have lied:

| Draft | Reported | What was actually wrong |
|---|---|---|
| 1 | 1/29 = **3.4%** | The one "mismatch" was **the instrument's error**: it paired an earnings *date* with an FOMC *day-count* 60 chars later. The prompt itself says "FOMC decision in 40 days" and the reply restated it correctly. |
| 2 | 0/**3** | The clause-break guard added to fix that used `\*\s` for bullets, which matched the trailing asterisk of every markdown `**bold**` span and cut the scored population from 29 to 3 — a guard that looked like precision and was blindness. |
| 3 (final) | 0/**30** | Emphasis markers now stripped before matching. `**88** days` and `**20-day** average` were defeating both the day-count matcher **and** the indicator-window mask, suppressing real pairs while leaking `20-day average` into the unscored pile. |

| | |
|---|---|

Unscored and hand-read (P16 — the metric prints what it did *not* match): **51 lone dates**, all
`2026-11-03`, the real earnings date, restated without a paired count — nothing to check, nothing
wrong. **107 lone day-counts**, dominated by `88d` (earnings), `40d` (FOMC — both correct against the
prompt's own figures) and `7d` (the Reddit mention window, a data window rather than a date offset).
`20-day`/`50-day` indicator windows are masked by construction and are not date claims.

**What 0/30 does and does not license.** It excludes a true mismatch rate above **9.5%** at 95%
confidence. It does not exclude a small one. n is bounded by how often the agents volunteer both
halves of a checkable claim, and that is 30 pairs across 198 turns.

## 3. Verdict

The CR pre-registered its own decision rule:

> | ~Zero | Close as `dropped`, recording the measurement. The position fix solves a problem we do not have, and the existing clause is doing its job. |

0/30 is that case. **CR169 → `dropped`.**

The corollary is worth stating plainly, because it runs against the CR's own reasoning: CR169 argued
that our anchoring clause — *"do not estimate how far away a date is from your own sense of the current
date"* — was "the weaker answer" because CLAUDE.md says instructions are not controls. On this epoch
the clause is at 0% error. **That does not vindicate instructions-as-controls in general** (DEF243:
rewording moved displacement 28.9% → 33.3%, i.e. nothing). It says this particular instruction sits
next to the datum it governs, and the model is not being asked to compute the day-count itself — the
fact sheet already did, and the agents are restating a supplied figure rather than deriving one. The
structural fix upstream needed is the one we already have: **the number is in the context, not behind a
tool call** (CR167 §5).

## 4. What survives

**M7 stays**, per the CR's own line — *"it is a CR143 §7 gap and it outlives this CR."* It is now the
only deterministic scorer in the sweep that can gate a commit, and it costs nothing to keep running.

Re-open CR169 only if M7's rate moves off zero on a later epoch. The position change is byte-neutral
and stays cheap, so the option is not lost by dropping it now.
