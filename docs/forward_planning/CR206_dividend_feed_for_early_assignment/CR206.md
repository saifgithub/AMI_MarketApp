# CR206 — the dividend feed for D9 early assignment

Authoritative summary: this CR's row in [`cr_list.md`](../cr_list.md)
(`_registry/CR206.row.md`).

Split out of CR172 §11 on 2026-08-24 (AT:R74).

The rule is written. The feed is not, and the reason it is not is worth keeping:
`dividend_rate` on `EarningsInfo` is an **annual** figure, and the rule needs the
**next payment**. Annual ÷ 4 is an assumption about payment frequency dressed as
a measurement, on a rule whose output takes a position away from a user early.
The fix is to read the actual last payment, which means a new provider-protocol
method across the whole fallback chain — a real surface, and the reason this is
its own CR.

Not urgent: `derivatives_allowed` is set on 0 of 42 current mandates.

## The distinction the whole CR turns on

`None` and `[]` are different answers and the code keeps them apart at every
layer. `None` = *this provider could not tell you* → the leg keeps reporting
`not_evaluated`. `[]` = *this company pays no dividend* → a measurement, and
the rule can conclude safely. Collapsing them would turn a feed outage into a
confident "your short call is safe", which is DEF059 pointed at a position
that can be taken away from a user.

Three places enforce it, each with a test: `FallbackProvider` falls through on
`None` but **not** on `[]` (or a secondary that knows nothing would overwrite
a primary that knows something); `CachingProvider` caches `[]` but **never**
`None` (caching a failure for six hours turns one bad request into six hours
of `not_evaluated`); and `next_dividend_for` routes them to `events` vs
`unresolved`.

## Deliberately not done

`DIVIDEND_HISTORY_TTL_SECONDS` is 6h against the chain's 300s. Not tuned
against production behaviour — a dividend is declared once a quarter with its
ex-date known weeks ahead, so the number is chosen from the shape of the fact
rather than measured. If it proves wrong it is one constant.

## Live verification on `alpha-2026-08-25-2`, and a coverage limit it exposed

Run inside the promoted container against real yfinance data:

```
dividend feed = {'GOOG': DividendEvent(ex_date=2026-09-04, amount_per_share=0.22)}  unresolved=()
```

GOOG resolves to a real upcoming ex-date and a **measured** $0.22 payment — the feed works end to
end. **AAPL does not appear, and that is correct rather than a bug:** `unresolved` is empty, so both
tickers were answerable; AAPL simply has no *upcoming* ex-date published right now.
`_upcoming_ex_date` rejects a past date because yfinance's `exDividendDate` is frequently the LAST
one, and assigning a short call against a dividend already paid would call shares away for a payment
nobody is about to capture.

**The limit to be honest about:** this means the D9 early-assignment rule is inert for any
underlying whose next ex-date is not yet declared — which, between quarters, is most of them. That
is the conservative direction (we never assign off an assumed date), and it is *not* the same as the
pre-CR206 state, where the rule could not run at all for anyone. But it is a real coverage gap, and
if it matters later the fix is a declared-dividend calendar, not an inference from the payment
series — the series is historical by construction and cannot name a future date.
