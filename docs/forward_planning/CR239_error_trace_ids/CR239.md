# CR239 — Trace ID on every error, surfaced to the user

**Status:** Leg A built. Leg B not started. **Filed by:** Architect (AT:R85), from
Saiful's suggestion while diagnosing a live "can't reach the backend" report (DEF446)
and a Room content-quality report (DEF445) in the same session.

**Leg A build note:** `HTTPAuditMiddleware` mints the id (`uuid4()`, before
`call_next`), `bind_contextvars(request_id=...)` so it rides every structlog line for
the request for free (including agent `llm_call_start` during a Room — no extra code,
`merge_contextvars` was already the first processor), echoes `X-Request-Id` on every
response, and passes it into `record_http` as `HTTPAuditRow.id` explicitly rather than
letting the ORM default it — the row's own primary key IS the trace id, not a second
number. `app.main` gained two global exception handlers (`HTTPException` and the
catch-all) that put the same value in the JSON body's `request_id` field. Mobile reads
`X-Request-Id` off `DioException.response.headers` (no interceptor plumbing needed —
the header is already sitting on the error) and `friendlyError()` appends a short
"Error ref: `xxxxxxxx`" footnote, never the headline. Room (scope item 5) shows its own
`run_id` instead via a separate `withRoomRunReference()` helper, since a broken Room
stream runs over raw `http.Client`, not Dio, so the HTTP-level id is rarely reachable
there anyway. The one-command lookup is `docs/tools/room_investigation/trace_lookup.py`.
Tests: `backend/tests/unit/test_cr239_request_id.py` (backend), the new `CR239 Leg A`
group in `mobile/test/friendly_error_test.dart` (mobile). Leg B (Sentry capture for
errors that never reach the server) is unbuilt — everything in that section below is
still the plan, not the state.

## Why

Today, tracing a user's error report back to its cause means guessing: match the
screenshot's timestamp to the user's rough platform/build, grep `docker logs` across a
multi-minute window, cross-reference `http_audit`/`room_runs` by `user_id`, and hope
nothing else with the same shape happened in that window. This session did exactly that
twice in one hour — once for a connectivity complaint, once for a Room quality complaint
— and both took several minutes of log archaeology that a single identifier would have
made instant.

Saiful: "We should be able to tell what errors we are getting from a screenshot. Some
uniq number that can be used to trace the errors."

The infrastructure already half-exists: `HTTPAuditMiddleware`
(`backend/app/middleware/http_audit.py`) writes one `http_audit` row per request, keyed
by its own UUID `id`, with `method`, `path`, `user_id`, `status_code`, `latency_ms`, and
scrubbed request/response bodies. `core/logging.py` already configures `structlog` with
`contextvars.merge_contextvars`, so binding one value once makes it appear on every log
line for that request with no per-call-site changes. **Nothing generates this ID before
the response, and nothing shows it to the user.**

**A server-minted ID only answers half of Saiful's question, though.** Asked directly —
"does it tell us what the problem was on the user's phone?" — no, not for the class of
error that never reaches the server at all: DNS failure, no network, TLS/cert error, a
timeout before the request sends, a client-side crash, a stale build pointed at a dead
URL. For those, `docker logs` has nothing to grep for, because the server never saw the
request. And today the app has no capture path for that class either:
`SentryFlutter.init` is wired in `main.dart` (A10) and catches uncaught
Flutter/Dart errors, but `friendlyError()`'s entire job is to CATCH the `DioException`
and turn it into copy — by design, that catch means it never becomes an uncaught error
Sentry sees. `grep -rn "Sentry\.\(captureException\|captureMessage\)" mobile/lib`
(excluding `generated/`) returns nothing: nowhere in the app is a caught error ever
explicitly reported. The diagnostic detail — the real `DioException` type, the OS-level
socket error, current connectivity state — is thrown away the moment `friendlyError()`
runs, which is exactly the class of report (DEF446) that started this conversation.

So this CR has two legs, not one: **(A)** plumb the request ID that already half-exists
through to the error screen, for errors that DO reach the server — this closes the gap
this session hit twice today (DEF446, DEF445); **(B)** give the app a client-side
capture path for errors that DON'T reach the server, so a report like "can't reach the
backend" carries enough to diagnose even when there is no server-side request to find.
Leg B needs its own local reference number too (Sentry's `event_id`, most naturally),
shown the same way, so the user-facing copy never has to explain which kind of failure
it was — one reference format, two different backing stores depending on where the
failure actually happened.

## Scope

### Leg A — the request reached the server (grep-the-logs case)

1. **Backend — generate + propagate.** A `RequestIDMiddleware` (or an addition to
   `HTTPAuditMiddleware`, whichever avoids double middleware ordering headaches) generates
   a UUID per request *before* `call_next`, binds it via
   `structlog.contextvars.bind_contextvars(request_id=...)` so every log line for that
   request — including agent `llm_call_start`/error lines during a Room — carries it, and
   passes it to `record_http` so `http_audit.id` (or a new `request_id` column, if reusing
   `id` collides with existing callers) is the same value a support session would grep for.
   Echoed back on every response via an `X-Request-Id` header, on the error path
   (exception handler, non-2xx responses) and on success — a user should be able to
   report "it was slow" or "it looked wrong" with a number too, not just "it broke".
2. **Backend — error bodies.** Every `HTTPException`/error JSON body gains a `request_id`
   field alongside `detail`, so a client that only inspects the parsed body (not headers)
   still gets it. One shared error-response shape, not one per route — same reasoning
   `friendly_error.dart`'s single-implementation fix (DEF148) already established
   client-side; this is its backend mirror.
3. **Mobile — carry and show.** `ApiClient`'s Dio interceptor reads `X-Request-Id` (or the
   body field) off every response/exception and attaches it to the thrown
   `DioException`/typed exception. `friendlyError()` appends a short, tappable/selectable
   trace line to error copy — e.g. "Error ref: `a1b2c3d4`" — truncated to a short prefix
   for on-screen legibility (mirrors how git/Sentry surfaces short SHAs; the full UUID
   stays in `http_audit` for the actual lookup). Never blocks or clutters the primary
   message — DEF148's "what failed, in the user's words" stays the headline; the ref is a
   footnote. DEF446's fresh `_ErrorView` (onboarding) and any other error-surface widget
   picks it up through the shared `friendlyError` path, not a second implementation.
4. **Support tooling.** A one-line lookup path — `grep <request_id> ` against
   `docker logs ami_api_alpha`, or a small admin endpoint
   (`GET /v1/admin/trace/{request_id}` behind the existing admin auth) that joins
   `http_audit` + `room_runs`/`onboarding_sessions`/whatever table the path touched — so
   "paste the number, get the whole story" is one command, not a bespoke query per
   incident. Exact shape TBD at build time; the acceptance bar is "one paste, one
   command", not a specific implementation.
5. **Room runs specifically.** `room_runs.id` already serves this role for Room — a Room
   error screen should show ITS OWN run id (already minted, already logged against by
   `run_id` in every `llm_call_start`/`room_completed` line) rather than inventing a
   second number for the same incident. The new HTTP-level `request_id` and the existing
   `room_runs.id` are related-but-distinct (a Room convene is one HTTP request that spans
   a `run_id` that outlives it via polling) — scope includes deciding which one the Room
   error screen shows, not necessarily minting a third ID.

### Leg B — the request never reached the server (the phone-side case)

1. **Report, don't just catch.** Every catch site that currently produces
   `friendlyError()` copy for a `DioException` whose `isConnectivityFailure()` is true
   (the new classifier DEF446 added — `connectionTimeout`, `sendTimeout`,
   `connectionError`, `unknown`, and an unmarked `receiveTimeout`) also calls
   `Sentry.captureException(error, hint: ...)` before the string is built, tagged with
   the same action/route context `friendlyError` already takes. This is additive to
   DEF148's guard, not a change to it — the user-facing string is unchanged; a second,
   separate report goes to Sentry alongside it. Gated the same way A10 already gates all
   Sentry activity: no DSN, no capture, no network, exactly today's opt-out.
2. **Capture what actually matters for this class.** At minimum: the Dio exception
   type, the request path (action, not full URL with params), current connectivity
   status (`connectivity_plus` or platform equivalent — was there a network interface up
   at all?), app build number, and backend-mode (Alpha/Beta/Prod toggle) — the single
   most likely explanation for "can't reach the backend" on a dev/QA device is the toggle
   pointed at a backend that isn't running. `sendDefaultPii = false` stays as configured;
   none of this is user content.
3. **Surface Sentry's own event_id.** `captureException` returns a `SentryId`; thread it
   back to the same `friendlyError()` trace-reference line Leg A uses, so the on-screen
   copy is uniform regardless of which leg actually fired — the user never needs to know
   or say which kind of failure it was, they just read off the one reference shown.
4. **Lookup.** Sentry's own dashboard is the tool here, keyed by that event_id — no new
   storage or query surface needed for this leg, unlike Leg A's `http_audit` join.

## Non-goals

- Not a new observability platform beyond what's already provisioned — Leg A is a manual
  grep/join workflow made fast, not automated alerting; Leg B uses Sentry, already wired
  in `main.dart` (A10), not a new vendor.
- Not a change to what `http_audit` retains or scrubs — DEF181/DEF430's redaction rules
  apply unchanged; the trace ID is metadata, not a body field.
- Not a change to what Sentry is configured to send — `sendDefaultPii = false` and the
  existing `beforeSend` Authorization/cookie scrub stay exactly as they are; Leg B adds
  call sites, not a new PII posture.

## Acceptance

- Every backend error response (4xx/5xx, from any route) carries the same `request_id` in
  both `X-Request-Id` and the JSON body, and that value appears verbatim in
  `docker logs ami_api_alpha` and the `http_audit` row for that request.
- Every mobile error screen that goes through `friendlyError()` shows a short trace
  reference, without changing DEF148's guard (no raw exception ever reaches the string).
- A support session can go from "user's screenshot" to "the exact log lines and DB rows
  for that request" in one grep/query, without needing the user's timestamp, platform, or
  account guessed at — **for an error that reached the server.**
- For an error that never reached the server (real repro: airplane mode, or a
  backend-mode toggle pointed at a dead host), the same screen still shows a trace
  reference, and that reference resolves in Sentry to an event carrying the Dio exception
  type, connectivity state, build number, and backend-mode — enough to tell "no network"
  from "wrong host" from "TLS failure" without the user describing anything beyond the
  reference number.
- Independent audit not required (additive, no safety-floor/verdict-path change) — normal
  review is enough.
