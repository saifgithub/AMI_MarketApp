## 1. Convene the Room: Token Size Estimation

"Convene the Room" is a multi-agent orchestrator that runs **12 agents sequentially** across 6 distinct phases to produce a single trading `Verdict` on a ticker.

Because the orchestrator runs the agents in a sequential loop (see [room_runner.py](file:///Volumes/Extreme%20Pro/AMI_MarketApp/backend/app/services/room_runner.py#L1031-L1108)), each subsequent agent's prompt includes the running transcript of all prior agent outputs (the "snowball" effect).

### 1.1. Prompt Structure & Component Token Counts

At each agent's turn, the runtime prompt is constructed as:
`system_prompt = base_prompt + mandate_overlay + user_overlay + alpaca_snapshot + safety_floor (PM only) + room_addition`

Here are the typical token counts for each prompt component:

1. **Base Agent Prompts (loaded from [content/agents/](file:///Volumes/Extreme%20Pro/AMI_MarketApp/content/agents/)):**
   - Stripped of YAML frontmatter. Varies from ~410 to ~760 tokens.
   - *Average across non-PM agents:* **~450 tokens**
   - *Portfolio Manager (PM) base prompt:* **~760 tokens**
2. **User Mandate Overlay:**
   - Generated by [overlay_generator.py](file:///Volumes/Extreme%20Pro/AMI_MarketApp/backend/app/agents/overlay_generator.py#L21) based on user's primary goal, risk score, and compliance rules.
   - *Estimated size:* **~220 tokens**
3. **User Briefing Overlay:**
   - Appended from the `OverlayStore` if the user has customized instructions for that agent ("Brief Your Agent").
   - *Estimated size:* **~50 tokens** (default or average size; 0 if empty)
4. **Alpaca Portfolio Snapshot:**
   - Formatted text block showing cash, equity, and positions (loaded once per run).
   - *Estimated size:* **~80 tokens** (varies slightly with position counts; 0 if unlinked)
5. **Safety Floor (Portfolio Manager Only):**
   - Mandate-enforcement instructions appended last to the PM's prompt.
   - *Estimated size:* **~240 tokens** (see [safety_floor.py](file:///Volumes/Extreme%20Pro/AMI_MarketApp/backend/app/agents/safety_floor.py#L43))
6. **Room Addition (Ticker Metadata & Instructions):**
   - Contains ticker name, compact fundamental fact-sheet, user mandate parameters, and turn instructions.
   - *Estimated size:* **~200 tokens**

### 1.2. Agent Output Length Budgets
Each agent's output is governed by short budgets defined in `_LENGTH_GUIDE` (see [room_prompts.py](file:///Volumes/Extreme%20Pro/AMI_MarketApp/backend/app/services/room_prompts.py#L50-L63)):
- **Analysts (x4):** 2–4 sentences (average **~60 tokens** output)
- **Researchers (x2):** 3–5 sentences (average **~90 tokens** output)
- **Research Manager (x1):** 4–6 sentences (average **~110 tokens** output)
- **Trader (x1):** 3–4 sentences (average **~85 tokens** output)
- **Risk Debators (x3):** 2 sentences (average **~50 tokens** output)
- **Portfolio Manager (x1):** 3–4 sentences (average **~85 tokens** output)

### 1.4. Multi-Round Debate Footprint (Floor Manager Tier)

For Floor Manager subscribers, the system supports up to **3 rounds** of debates. Although the current codebase hardcodes `rounds=1`, a 3-round implementation would increase the number of LLM calls to **~25 calls** (Round 1: 12, Round 2: 7, Round 3: 6).

Since later rounds run over a much larger cumulative transcript (exceeding 2,500 tokens in Round 3), the input tokens will balloon.
- **Estimated Total Input Tokens (3-Rounds):** **~45,000 to 55,000 tokens**
- **Estimated Total Output Tokens (3-Rounds):** **~2,200 tokens**
- **Cost (without caching, Claude 3.5 Sonnet):** **~$0.18 per 3-Round run**

### 1.5. Monthly Token Consumption Scenario (500 Users, 60 Convenes/Month)

To evaluate the operational impact, we model a baseline where **500 users** execute **60 standard (1-Round) Convenes per month** (totaling **30,000 runs/month**).

#### A. Without Caching
Every single run costs the full input and output token count.
* **Monthly Input Tokens:** 30,000 runs × 17,580 input tokens = **527,400,000 tokens** (527.4M)
* **Monthly Output Tokens:** 30,000 runs × 840 output tokens = **25,200,000 tokens** (25.2M)
* **Estimated Cost (Claude 3.5 Sonnet):** $1,582.20 (input) + $378.00 (output) = **$1,960.20 / month**
* **Estimated Cost (Claude 3.5 Haiku):** $421.92 (input) + $100.80 (output) = **$522.72 / month**

#### B. With Caching (Assuming 70% Cache Hit Rate)
*Why 70%?* A cache entry on Claude has a **5-minute TTL**. If users space their 60 Convenes hours apart, the cache hit rate drops to 0% (and misses incur a 25% write surcharge). However, trading apps are used in sessions where a user researches several tickers back-to-back. We assume that on average, 70% of runs hit the active cache for the static prefix.
* **Cached Portion (Static prefix):** 12,000 tokens per run (360M tokens total/month).
  - *Hits (70%):* 252M tokens billed at 10% = **25.2M billing-equivalent tokens**
  - *Misses/Writes (30%):* 108M tokens billed at 125% = **135.0M billing-equivalent tokens**
* **Dynamic Portion (Never cached):** 5,580 tokens per run = **167,400,000 tokens** (167.4M)
* **Monthly Input Tokens (Billing-Equivalent):** 25.2M + 135.0M + 167.4M = **327,600,000 tokens** (327.6M)
* **Monthly Output Tokens (Unchanged):** **25,200,000 tokens** (25.2M)
* **Estimated Cost (Claude 3.5 Sonnet):** $982.80 (input) + $378.00 (output) = **$1,360.80 / month** (~30.6% total cost reduction)
* **Estimated Cost (Claude 3.5 Haiku):** $262.08 (input) + $100.80 (output) = **$362.88 / month** (~30.6% total cost reduction)

#### C. With Caching (Theoretical Max - 100% Cache Hit Rate)
If the cache is kept perpetually active (e.g. constant overlapping requests or longer TTL support).
* **Monthly Input Tokens (Billing-Equivalent):** 360M static tokens × 10% + 167.4M dynamic = **203,400,000 tokens** (203.4M)
* **Estimated Cost (Claude 3.5 Sonnet):** $610.20 (input) + $378.00 (output) = **$988.20 / month** (~49.6% total cost reduction)
* **Estimated Cost (Claude 3.5 Haiku):** $162.72 (input) + $100.80 (output) = **$263.52 / month** (~49.6% total cost reduction)

## 2. Prompt Caching Opportunities & Analysis

Prompt Caching allows LLM providers to cache identical prefixes of system prompts or message histories. 
- **Anthropic Claude (Sonnet 3.5 / Haiku 3.5):** Requires a minimum prefix size of **1,024 tokens**. Cached reads are **90% cheaper**; cached writes are **25% more expensive**. Cache TTL is **5 minutes** of inactivity.
- **Google Gemini (1.5 Pro / Flash, 2.0 / 3.0):** Requires a minimum prefix size of **32,768 tokens (32k)**. In AMI MarketApp, the individual prompts are 1k-2k tokens. Thus, Gemini's 32k minimum cache threshold is too high to be useful for standard individual agent runs or single-round Convene the Room sessions.
- **Therefore, our caching strategy focus is entirely on Anthropic Claude.**

Let's analyze where caching can be applied:

### Opportunity A: Across Separate Convene the Room Runs (Same User)
- **Mechanism:** When a user runs Convene on Ticker A and then immediately on Ticker B, the agent-specific system prompts share a massive identical prefix:
  `base_prompt + mandate_overlay + user_overlay + alpaca_snapshot`
- **Cacheability:** For any specific agent (e.g., Fundamentals Analyst), this prefix is **100% identical** across separate runs for that user, provided their mandate and Alpaca positions didn't change.
- **Token Size Check:** The static prefix is **~1,005 tokens** (non-PM agents) and **~1,555 tokens** (PM agent). 
  - Standard agents hover right at the 1,024-token boundary. If the user has custom brief overlays or multiple compliance constraints, it easily exceeds 1,024. If they have none, it might fall slightly short.
  - PM always exceeds the threshold (~1,555 tokens).
- **Strategy:** Restructure `room_runner` to place a cache breakpoint exactly at the end of the `base` prompt (pre-convene ticker block). Ensure we hit the 1,024 threshold by padding the mandate metadata block if necessary.

### Opportunity B: 1-on-1 Chats (Analyst Chat & Concierge)
- **Mechanism:** In 1-on-1 chat sessions (handled by `agent_runner.py`), a user has a back-and-forth conversation with a single agent. The history grows with each turn, but the system prompt and early history remain identical.
- **Cacheability:** **Highly cacheable.** We can place a cache breakpoint at the end of the system prompt and on the second-to-last user message.
- **Token Size Check:** System prompt for 1-on-1 is ~1,000+ tokens, and history adds to it, easily clearing the 1,024 threshold on the very first assistant turn.
- **Savings:** Reduces input cost by **up to 85%** on long chat sessions.

### Opportunity C: Within a Single Convene Run (Self-caching transcript)
- **Mechanism:** Can Agent 2 (Market Analyst) reuse the cache from Agent 1 (Fundamentals Analyst)?
- **Analysis:** No. Since Claude caches prefixes starting from the very first token, and each agent has a unique `base_prompt` at the start of the prompt, Agent 2's prompt prefix differs immediately from Agent 1's.
- **Can we restructure?** If we put the shared context first (`mandate + alpaca + ticker_profile`) and the agent-specific instructions last, the prefix `mandate + alpaca + ticker_profile` (~450 tokens) is shared. However, it is too small to clear the 1,024 token minimum.
- **Transcript growth caching:** Caching the transcript at each step is not useful because the transcript is modified at every single step, resulting in a cache write (25% extra cost) but zero cache hits.

## 4. Implementation Recommendations

To implement prompt caching, we propose the following changes:

### 4.1. Restructure & Cache Base Prompts in Convene the Room
In [room_runner.py](file:///Volumes/Extreme%20Pro/AMI_MarketApp/backend/app/services/room_runner.py), modify `_speak_one_agent` and `_stream_pm_narration` to mark the `system_prompt` prefix as cacheable.

1. **Alpaca Snapshot Cache:**
   To prevent minor portfolio fluctuations from breaking the prompt cache between consecutive runs, cache the formatted Alpaca snapshot string in memory/Redis for **5 minutes**.
2. **Add Cache Breakpoint:**
   When invoking `stream_chat`, pass the cache breakpoint block. In Anthropic SDK, cache control is set on the system prompt block:
   ```python
   # In room_runner.py _speak_one_agent
   # system_prompt is divided into a cached system instructions block and a dynamic room_addition.
   ```

### 4.2. Enable Caching in 1-on-1 & Concierge Chats
In [agent_runner.py](file:///Volumes/Extreme%20Pro/AMI_MarketApp/backend/app/services/agent_runner.py), modify `stream_one_on_one_message` and `_stream_concierge` to:
1. Place a cache breakpoint on the `system_prompt` (which contains the agent prompt, mandate, and live ticker data).
2. Place a cache breakpoint on the last message in `history` to cache the conversation history.
