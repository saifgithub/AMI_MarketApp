# CR209 — The onboarding walk addresses its answers instead of deducing them

**Filed:** 2026-08-25 (AT:R74) · **Owner:** architect · **Parent:** [CR162](../CR162_two_platform_ui_automation/)

## Why

DEF362 — "the iOS onboarding walk cannot reach Floor" — survived two point fixes
(DEF347, DEF348) and one observability fix (DEF366). Re-running it on 2026-08-25
established the root cause, which is neither the app nor connectivity nor the
semantics tree:

`helpers/onboarding.py::_live_chip` selects the answer for the current interview
turn as **the bottom-most labelled control**. On iOS the bottom of the screen
never belongs to the chips. Measured across three consecutive runs, each control
exposed by excluding the last:

| Run | Control occupying the slot | Taps |
|---|---|---|
| 1 | `Next keyboard` — the keyboard's globe key | 186 |
| 2 | `Type your answer…` — the composer text field | 180 |
| 3 | `Send answer` — the send arrow | 579 |

Each count is read back from the Appium log by element id, not inferred. The
harness was never blind: the accessibility tree is fully populated in the wedged
state (25 buttons, all four chips labelled), and a single chip click driven by
hand advances the interview normally. The walk could see the answer and tapped
something else.

**A denylist cannot converge here.** The candidate pool is the platform's, not
ours; every exclusion promotes the next non-chip control into the same slot.

**DEF346 is the sharp edge and the reason this is a framing fix, not a fourth
exclusion.** Giving the send button a VoiceOver label — a correct accessibility
fix — is what made `labelled_only=True` stop excluding it. `_live_chip`'s
docstring still asserts the arrow *"has none"*. An accessibility improvement
silently invalidated a test heuristic, and nothing failed locally to say so.

## What changed

The app already ships an identifier contract for exactly this
(`mobile/lib/qa/semantics_ids.dart` ↔ `qa/appium/config/semantics_ids.py`, kept
honest by `mobile/test/qa/semantics_ids_test.dart`). The Concierge interview —
the one surface the walk must drive — was not in it. It is now.

- **`OnboardingIds.answerChip`** on every chip (`widgets/chat/chip_row.dart`).
  Deliberately **not** unique per chip: the harness needs *an answer for the
  current turn*, `onboarding_screen.dart` renders only the live turn's chips
  (`state.currentChips`), and numbering them would invent an ordering the
  backend-authored interview does not have.
- **`OnboardingIds.composer`** and **`OnboardingIds.send`** so those two are
  nameable rather than guessed at geometrically.
- The walk asks for chips by identifier first; the geometric heuristic remains
  only as a fallback for turns that are not chip questions, so it can no longer
  be the reason a chip question wedges.

`identifier` is not a label and is never spoken, so DEF249's `button: true`
announcement is untouched — asserted.

## Acceptance

1. Every chip carries the identifier, and the identifier does not vary with the
   rendered label (AR fixture) — `mobile/test/qa/onboarding_ids_test.dart`.
2. The chip is still announced as a button (DEF249 holds) — same file.
3. The three interview ids are distinct and namespaced `ami.onboarding.`.
4. `flutter analyze` clean; `mobile/test/qa/semantics_ids_test.dart` still green.
5. The iOS smoke gate reaches Floor — `pytest -m smoke` against the simulator.
6. **Not accepted on one green run.** DEF362 produced a pass and two failures in
   the same afternoon, so the gate must hold across repeated runs before CR162
   closes.

## Deliberately not in scope

Deleting the geometric fallback. It still serves non-chip turns, and removing it
in the same change would mean the run that proves the identifier path also
removes the thing that would have covered its gaps.
