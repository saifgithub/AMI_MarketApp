# CR243 — Room: Malay-language prompt reliability (translate + respond-only-in-Malay)

**Status: research substantially done, build not started.** Filed by
investigator session (AT:R85), from Saiful, 2026-09-27: "Mint one CR for
Arabic, and another for Malay [for Room LLM prompt language support]" —
following a language-reliability investigation
([`docs/Research/RES009_room_llm_consistency/`](../../Research/RES009_room_llm_consistency/README.md),
docs 14–20). Sibling of [CR242](../CR242_room_arabic_prompt_language_reliability/CR242.md)
(Arabic) — same research, same structure, split by language since the two
are independently buildable and were measured with somewhat different
results. Saiful's explicit framing: **the remaining translation/testing
work for this build is the responsibility of whoever builds this CR, not
something to keep iterating on in the research phase.**

## This is NOT app localization — that's already built

**Read this before scoping any work here.** AMI already has substantial,
shipped Malay support, unrelated to this CR:

- **CR083** (closed, 2026-08-20) — Flutter UI strings (445/445 ARB keys),
  glossary (208/208 terms), daily challenges (193/193), AI Coach (280/295,
  15 deliberately excluded Sharia-sensitive keys), and lesson content
  (341/342 `.ms.mdx` files, 1 lesson — Sharia unit lesson 355 — staged but
  unresolved) are ALL already translated to Malay, via an in-house on-prem
  LLM pipeline (`content/i18n/`, `scripts/translate_*.py`).
- **CR087** (closed) — made those translated lessons actually servable
  (backend locale-aware loading, mobile locale-aware requests). Unlike
  Arabic, Malay stayed at the original v1.0 timeline (D-007) rather than
  getting an early public-store push — CR087's own record notes MS was at
  3/342 when CR083 caught it fully up afterward.
- **DEF144** (open) — a known, unresolved quality defect in that existing
  pipeline: foreign-script code-switching (Chinese/Cyrillic/Japanese
  fragments gluing into AR/MS output) — affects Malay too, not just
  Arabic. Native QA is still an acknowledged non-blocking gap per
  `content/i18n/qa_spotcheck_log.md`.
- **CR241** (proposed) — `users.locale` is effectively stuck at "en" for
  almost every user; a real per-user locale signal doesn't exist in
  production yet, which matters for any locale-aware Room routing this CR
  might eventually want.

**This CR is narrower and different: it's about the Room's own LLM-agent
prompts** (fact sheets, mandate, upstream transcript, verdict format) —
content that is generated fresh per convene, per ticker, per user, and has
never gone through CR083's translation pipeline (which only translates
STATIC content: lessons, glossary, UI strings). The Room's prompts don't
exist as files to pre-translate; they're assembled live from a mandate +
market data + a 12-agent transcript. This CR is about whether/how to make
THAT dynamic content produce reliable Malay output.

## What RES009 already found (the starting point for this CR's build)

Full detail in the RES009 docs; summary for this CR's purposes:

1. **Two mechanisms exist for getting non-English Room output; neither
   alone is reliable.** "English prompt + append a reply-in-Malay
   instruction" (RES009 14/15) and "translate the whole prompt into Malay"
   (RES009 16) were both tested on real captured Room prompts
   (`portfolio_manager`, full 12-agent convenes) against both vLLM/ami-llm
   and DeepInfra/GLM-5.3-Flash. English-revert rates ran up to 40% (vLLM +
   fully-translated-Malay prompt) even with a whole-prompt translation —
   a smaller worst case than Arabic's 100%, but still unreliable on its
   own.
2. **A working recipe was found: translate the prompt AND append one
   short, final, standalone instruction.** RES009 20 ("Test B") — "IMPORTANT
   — respond only in Bahasa Malaysia (Malay). Do not use English anywhere
   in your response," placed as the LAST line of an already-translated
   prompt — got **0% English-revert across every combo tested (vLLM and
   DeepInfra, 20/20 draws)**. This is the strongest, cheapest mitigation
   found, and should be this CR's starting point, not a chat-only
   instruction (docs 14/15's approach) or full translation alone (doc 16).
3. **The trading decision itself is robust to language.** Every
   language/provider combination tested landed the same vote (APPROVE,
   matching the English baseline) regardless of which language it answered
   in — this is not a decision-quality risk, purely an output-language
   reliability question.
4. **One Malay-specific defect found and worth re-checking under this
   CR's own broader testing**: RES009 doc 14's narrower single-agent test
   found a single stray Chinese character leaked into 1 of 3 Malay draws
   (plausible base-model artifact — ami-llm is Qwen-derived,
   Chinese-lab-trained); the larger 20-draw doc 15 batch found zero such
   leaks. Sample sizes throughout are small (3–5 draws); this CR's own
   broader testing should re-establish whether this is a real, sizeable
   risk or noise.
5. **A real, unrelated production gap was found and is NOT this CR's
   scope**: `research_manager`'s scripted fallback renders a fixed,
   context-blind template unconnected to the live convene's actual
   debate — documented in
   [RES009 doc 19](../../Research/RES009_room_llm_consistency/19_app_findings_for_def_cr_triage.md)
   as a candidate DEF, independent of language, and the specific incident
   that surfaced it was on DeepInfra + Malay (doc 15: 2/5 scripted-fallback
   rate on that combo, zero on every other combo/language tested) — worth
   this CR's build track knowing about even though the fix belongs
   elsewhere.

## What this CR's research explicitly did NOT cover (now this CR's job)

Per Saiful's framing, expanding this coverage is this CR's own
responsibility, not something the research phase needs to close first:

- **Only one ticker (JPM), one agent role (`portfolio_manager`) tested**
  for the translate + instruction-last recipe specifically (docs 16/18/20).
  Doc 15's broader 5-ticker/full-Room test used the simpler append-only
  approach, not the full recipe — all 12 agent roles need the WINNING
  recipe (translate + instruction-last) verified, not just the earlier,
  weaker mechanism. `research_manager`'s tag-based output format (not
  JSON) in particular was never tested with the winning recipe.
- **No native Malay speaker has reviewed any output.** Every fluency
  judgment in RES009 14–20 is the investigating session's own read,
  explicitly flagged throughout as unverified. This CR needs real
  native-speaker QA before any Malay Room output reaches a real user —
  same standard `content/i18n/qa_spotcheck_log.md` already holds itself to
  for lesson content (there: automated-only today, native QA acknowledged
  as a gap; don't repeat that gap here without at least flagging it the
  same way).
- **Only tested on a ticker/role already known stable in English.** JPM
  was deliberately picked because doc 13 showed it unanimous in English —
  isolating language effects from the ticker-level instability RES009
  found elsewhere (CR228). Whether this recipe holds on an
  already-marginal ticker (SO, T, BAC, MO, SLB — all found unstable even in
  English) is untested.
- **The DeepInfra+Malay scripted-fallback rate (doc 15: 2/5, 40%) is
  higher than any other combo/language tested** — worth this CR's own
  investigation into whether that's Malay-specific, provider-specific, or
  both, at a larger sample than doc 15's n=5.
- **No production integration exists.** `mandate.locale` today
  (`room_prompts.py`) is inert metadata inside the English prompt, never
  an instruction, and there's no code path that assembles a translated
  prompt or appends the instruction-last suffix. This CR needs to design
  and build that path: where the translation happens (per-call live
  translation of the assembled prompt? a translated prompt-template layer
  parallel to the English one?), and how `mandate.locale`/`users.locale`
  (pending CR241) actually triggers it.
- **Provider choice still open.** CR240 (hosted LLM provider evaluation)
  is itself still "research done, no build yet" — this CR's provider
  choice should track whatever CR240 lands on, not assume DeepInfra or
  vLLM unilaterally.
- **Cost/latency of the translate + instruction-last approach at
  production scale** — not measured against a real per-convene budget for
  a fully-Malay-served Room, only against the small research sample.

## Non-goals

- Does not touch CR083/CR087's already-shipped static content translation
  pipeline — that system stays as-is.
- Does not fix DEF144 (foreign-script code-switching in the static
  content pipeline) — a separate, already-tracked defect on a different
  code path (though this CR's own testing should watch for the same
  failure mode in Room prompt output, per finding 4 above).
- Does not fix CR241 (`users.locale` tracking) — a prerequisite this CR
  depends on for real per-user routing, but not this CR's own scope to
  build.
- Does not decide CR240's provider question — this CR's build should be
  provider-agnostic where possible (the recipe worked on both vLLM and
  DeepInfra) and adapt once CR240 lands.
- Does not fix RES009 doc 19's scripted-fallback finding — flagged
  separately, applies to English convenes too, even though the incident
  that surfaced it happened on this CR's language.

## Acceptance (draft — refine at build time)

- The translate + instruction-last recipe (or whatever the build track
  determines works best after its own broader testing) verified across
  all 12 agent roles, not just `portfolio_manager`.
- At least one ticker already known unstable in English tested, to confirm
  the recipe doesn't interact badly with an already-marginal decision.
- The DeepInfra+Malay scripted-fallback rate re-measured at a larger
  sample to establish whether doc 15's 40% is real or small-sample noise.
- A real native Malay speaker has reviewed a representative sample of
  Room output before this ships to any real user.
- A concrete design for where translation happens in the live request
  path, wired to `mandate.locale`/`users.locale`.
