| CR177 | 2026-08-13 | **The app never records that it stopped you.** Saiful, during the CR133 discussion: *"The safety-floor issue — create a CR."* Measured at `backend/app/api/sim.py:362`: when the safety floor blocks a trade, `if not result.accepted: return {...}` fires **before** the journal write at `:390`, so the violation reaches the UI in the response, the ticket shows it, and then it is gone. Nothing durable is written. **Concretely:** AMI stops you breaching your own position-size cap on Tuesday; on Friday the Journal shows no trace, so you cannot see you attempted the same breach four times — and neither can anything else. **Three costs.** (1) The Decision Journal is incomplete in the one place it claims authority — an attempted trade that was *refused* is a decision. (2) CR133's INSIGHTS card *"how your mandate has moved"* can show that a limit loosened but not that you were repeatedly hitting it first, which is precisely the loosening-after-a-loss pattern the card exists to surface. (3) It is invisible to **us** too: we cannot answer *"is the safety floor firing at all, and on what?"* from data — a gap in our own assurance for a control whose whole justification is that it is structural rather than prompt-level. **This is CR040 seen from the other side:** the usual failure is a silent fallback making a broken thing look fine; here a control works **correctly** and leaves no trace, so a working safety floor and an absent one produce identical history. **Scope: the training path only.** The game's similar early return at `sim_engine.py:1006` is explicitly OUT — games deliberately never run the safety floor (implementation_plan §7.1 keeps two public entry points for exactly that reason), and that rejection is a cash/limit refusal, not a mandate block; folding them would blur the fence. `POST /v1/sim/preview` is out too — a preview is a question, not a decision, and journaling every dry run buries the real events. **It must NOT be a `SIM_TRADE`, and CR133 is what makes that obvious:** INSIGHTS card 1 buckets `SIM_TRADE` rows on won/lost/manual, and a blocked attempt is not a trade — nothing filled, no position, no outcome — so reusing the type would silently inflate the denominator of the card CR133 calls its strongest and quietly corrupt every ratio in it. Proposed `EntryType.COMPLIANCE_BLOCK`. **Rejected: reusing the dead `EntryType.DRIFT_ALERT`** (CR133 found it has no writer anywhere, so it looks free) — it names a different event and CR133 already identifies it as the natural home for *"your mandate loosened right after a loss"*; spending it here would cost that. The entry carries `blocked_by` (the load-bearing field — **which rule stopped you**), `violations`, ticker/side/quantity, and any sharia/classification verdicts; all already on the blocked response, so no new computation and no migration. **Two hazards designed against rather than discovered.** (1) `mobile/lib/models/journal.dart::fromWire` returns `JournalEntryType?` — **null** on an unknown wire value — and the backend ships by rsync same-day while the client ships through store review, so every installed build will receive entries it cannot name. Same topology as CR109 Amendment M's 404-tolerance; it is an acceptance condition, not a footnote: the entry must be inert on an unknowing client, **verified before the backend ships, not after**. (2) Frequency is the signal but a hammered button is not — twenty taps against one cap must stay honest in the data without becoming twenty Journal rows for one frustrated minute; a measured position on rapid identical repeats is required before shipping. **Acceptance:** one entry per block naming the rule; asserted **not** a `SIM_TRADE` so CR133's denominator is provably unchanged; the happy path unchanged; the game path writes nothing, asserted; an unknowing client never renders it as a result (CR040); and removing the write turns a test red. **What it unlocks, not claimed here:** once the rows exist, INSIGHTS can show *how often AMI stopped you, and which rule* — the product's core claim, measured. Effort: small; no migration (`journal_entries.payload` is already JSON).
