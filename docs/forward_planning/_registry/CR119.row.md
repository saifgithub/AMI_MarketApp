A user the app has succeeded with is a user whose portfolio screen is unusable. Today's reporter sits at 89.3% cash with 4 sector rows and a short list, so nothing is broken yet; this is a scaling ceiling, filed before it is hit. **Interactions the design has to absorb, all decided today and all in this file:** **CR116** moves holdings above the watchlist, **CR118** caps and scrolls the sector legend, and CR116's row flags that the holdings block is a conditional (`if (p.holdings.isEmpty)` renders `_NewTraderHint`), so the empty state is a distinct layout, not a degenerate case of the populated one. A redesign that ignores the empty state will regress the new-trader experience DEF060 exists to protect. Also live in this screen: `_watchlistKey`, a `GlobalKey` used as a scroll/coach-mark target, which any restructure must keep attached. **Open questions for the design, not for this row:** whether the three lists become tabs, sections with independent scroll, or separate screens; what the summary state of a collapsed list shows (count? top holding? total value?); and whether trades — the least-referenced and fastest-growing of the three — belongs on this screen at all rather than behind the Journal, which is already the durable record surface. **Sequencing:** CR116 and CR118 are small, ruled and land first; they are not blocked on this and should not wait for it.
