Both were measured false LAN-direct on 2026-08-16: `vllm:prefix_cache_queries_total` 59,681,175 and `vllm:prefix_cache_hits_total` 24,623,808 → a **41.3%** prefix-cache hit rate on `ami-llm`, readable today. The per-call field stays dead and is not this CR's business — `usage.prompt_tokens_details` is present in the shape and `None` in value, an upstream V1-engine bug (issues 44961 / 16162 / 18062), and CR141's NULL is the honest answer for it (CR040: never a fake zero). **What remains is build work, not a defect:** a `/metrics` reader, storage for `(sampled_at, queries_total, hits_total)`, a lifespan tick, and a windowed `Δhits / Δqueries` surfaced beside CR141's `llm_audit` rows. **The counters must be stored raw**, not as a rate — they are lifetime-cumulative, so a stored rate can never be windowed afterwards and a stored pair can. Acceptance is measured against the live host, not a fixture: a written sample matches a manual `curl` in the same minute; two samples spanning real Room traffic produce a rate that is *not* the lifetime rate (proving the window works rather than re-deriving 41.3% forever); an unreachable host leaves a **gap**, never a zero and never a repeated last value; and a unit test pins the parser against a captured body including the no-counters case. Baseline for whoever picks it up: 41.3% is lifetime-cumulative and CR017 §2.4's original 18.5% was too — neither is like-for-like, so re-read on a window rather than treating it as a trend.
