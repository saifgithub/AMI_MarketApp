| CR239 | 2026-09-26 | **Trace ID on every error, surfaced to the user — two legs, not one.** Filed from Saiful's suggestion while diagnosing a live "can't reach the backend" report (DEF446) and a Room content-quality report (DEF445) in the same session — both took several minutes of log/DB archaeology that a single identifier would have made instant. Saiful's own follow-up caught the gap in the first draft: "does it tell us what the problem was on the user's phone?" No — a server-minted ID only covers requests that reach the server. **Leg A** (the grep-the-logs case): `HTTPAuditMiddleware` already writes one `http_audit` row per request keyed by its own UUID, and `core/logging.py` already configures `structlog.contextvars`, so binding a request id once makes it appear on every log line for that request for free — backend generates it, echoes it in `X-Request-Id` + every error body's `request_id` field; mobile's Dio interceptor reads it and `friendlyError()` appends a short trace reference (never the headline); a one-command lookup joins `http_audit` with whatever table the route touched; Room shows its own already-existing `room_runs.id` rather than a second number. **Leg B** (the phone-side case, for a request that never reached the server at all — DNS, no network, TLS, a stale build's dead URL): today `SentryFlutter.init` (A10, `main.dart`) catches only uncaught errors, and `friendlyError()`'s whole job is to CATCH the `DioException` first — so nothing is ever explicitly reported (`grep -rn "Sentry\.\(captureException\|captureMessage\)" mobile/lib` returns nothing outside `generated/`). Leg B adds an explicit `Sentry.captureException` at every catch site DEF446's new `isConnectivityFailure()` classifies as true, tagged with Dio exception type, connectivity state, build number, and backend-mode toggle; the returned `SentryId` feeds the same on-screen trace-reference line Leg A uses, so the user reads one reference regardless of which leg fired. Non-goals: no new observability vendor (Leg A is grep/join, Leg B is already-wired Sentry), no change to DEF181/DEF430 scrubbing or Sentry's existing PII posture. **Leg A built** (`HTTPAuditMiddleware` mints + binds + echoes the id, `app.main` exception handlers put it in every error body, mobile reads `X-Request-Id` off the Dio response and `friendlyError()` appends the footnote, Room shows its own `run_id` instead via `withRoomRunReference()`, one-command lookup at `docs/tools/room_investigation/trace_lookup.py`) — **Leg B not started.** | proposed | [CR239_error_trace_ids/](CR239_error_trace_ids/CR239.md) | AT:R85 |
