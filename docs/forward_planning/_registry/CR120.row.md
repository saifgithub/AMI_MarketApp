| CR120 | 2026-07-29 | **Portfolio: structure for three growing lists, and a cap on trade history.** Saiful: *"The portfolio screen has watchlist, holdings and trade history. They will all grow. We need a better way than simple scrolling one after another. We also need to limit the trades to either a number of items… or of a period… Users can still check trades in the Journal instead."* **Measured, from the DOM of a built prototype at 390×844, not estimated:** `portfolio_screen.dart:137` is a `ListView(children:)` — **not `.builder`** — so every row is constructed on every rebuild, and since `TradeRow`/`_WatchlistRow` are `ConsumerWidget`s under a `ref.watch(simNotifierProvider)`, a price tick rebuilds all of them: **3.6 screens / 31 rows** at a modest account, **8.9 / 84** at six months, **25.4 / 252** at heavy use. Growth is linear and unbounded because nothing is capped server-side either — `sim_engine.py:447 list_trades` selects every trade the user has ever made, `opened_at DESC`, no `limit`, no `offset`. **Three structural findings shaped the fix.** (1) **Open and closed trades are interleaved by open date** — there is no status split in the render path (`:170`), so a live position opened in April sits below forty closed trades from May; **open trades are money at risk, not history, and are never capped in any option**. (2) **The watchlist is not user-curated — it auto-grows**: `sim.py:302` silently adds every traded ticker and `watchlist_store.add` has no cap, so the same ticker can appear in all three sections without the user ever touching it. (3) The sector donut renders above the watchlist today and reads as unrelated to anything; it belongs inside Holdings. **The premise needed correcting, and the correction is binding.** *"Users can still check trades in the Journal"* is **half true**: every trade does write a journal entry carrying the full trade JSON (`sim.py:314`, `:393`, `:446`) and the Journal already ships a TRADE filter chip plus search — **but Floor Pass gets 30-day retention** (`journal_store.py:42-47`, `FLOOR_PASS_RETENTION_DAYS = 30`) while `sim_trades` has none. For a free user the relationship is **inverted — the Portfolio is the durable record and the Journal is the lossy one** — so a fetch-limit cap pointing at the Journal would silently delete their own trade history from every surface (CR040, degrade loudly, with the user's data as the thing lost). Hence: the cap is a **view default with an in-place escape hatch, never a fetch limit** (`SHOW ALL 57` reads the Portfolio's own durable data), and the Journal pointer is **plan-aware** — *"Journal keeps 30 days on Floor Pass — 47 of these 57 are older. They stay here."* **The cap, decided by Saiful: last 25, with the span they cover stated** (`LAST 25 CLOSED · 17 MAY – 28 JUL`) — the period is **described, never used to filter**, because a pure period filter shows an empty history to a user who took a break and shows all 200 to a day-trader who did not, while a combination must choose union (unbounded) or intersection (empty). Above it sits a summary computed over **all** closed trades, not the visible 25 (a hit rate over an arbitrary display window is a wrong number wearing the authority of a statistic): win/loss bar, `WON 41 · LOST 16 · 72% · NET +$39,330`. **Four structures built and measured on identical data before the call** — landing screens at modest / six-month / heavy, plus the worst state a user can reach: **today 3.6 / 8.9 / 25.4** (no other state exists); **bounded dashboard 2.5 / 3.0 / 3.2** (3.2, bounded by construction); **segmented tabs 1.0 / 1.4 / 2.3** as first built, before open trades moved to the landing tab; **collapsible sections 1.0 / 1.5 / 2.4** (**9.7 with everything expanded** — a number the user can undo with two taps). I recommended the bounded dashboard and flagged the tab risk — a horizontal switcher nested inside the bottom-nav tab the user is already in, with **no tab pattern anywhere in the app** outside `alpaca_connect_screen.dart`. Saiful chose tabs; the mitigations are below. **STRUCTURE DECIDED 2026-07-29 — segmented tabs.** Saiful chose tabs after reviewing all four in the prototype. Three hex-clipped segments (`cornerCut: 8`, matching `ticker_chart.dart:185` and CR106's BOARD|TRANSCRIPT toggle) under a pinned compact value card; fill flip only, no sliding indicator and **no swipe-between-tabs** (the DS rules out motion on text, and a horizontal swipe inside a bottom-nav tab fights the OS back gesture). **POSITIONS carries holdings AND open trades, so HISTORY is closed trades only and its count says `195`, not `200`** — this is the one thing the structure could get wrong, since an open trade is money at risk with a stop that can fire and a tab the user does not land on makes it invisible; it also dissolves the interleave defect, because no list contains both any more. The sector donut moves inside Positions where it describes the list beneath it. **Tab state is `TabController` state, not a persisted preference** — it survives in-app navigation and resets to Positions on cold start, because persisting it means a user who checked History once opens the app a week later to a screen that does not show what they own; no prefs key, so none of CR106's T-MODESIDE trap surface either. **A list over 12 items gets search + sort inside its own tab** (what a full viewport per list buys, and what the rejected dashboard could not offer without a navigation), with per-list defaults rather than one generic sort: holdings by value, watchlist A–Z (a watchlist is scanned to *find* a name, and movers-first moves the name every day), closed newest. **Measured per tab** — Positions 1.1 / 1.7 / 2.9, Watchlist 1.0 / 2.0 / 4.2, History 2.8 / 3.7 / 3.7 screens across modest / six-month / heavy: **History stops growing at six months**, which is the 25-cap doing its job, while **Watchlist is the one unbounded tab** and is unbounded for a reason nobody chose (the auto-add above) — search and sort make 40 rows navigable, not 200, so that needs its own conversation if the auto-add stays. The summary strip is captioned `ACROSS ALL 195 CLOSED` so it cannot be read as a statistic about the visible 25. Tab labels are the tightest strings on the screen (~117pt each); `POSITIONS 12` fits at 1.0 and 1.15 in EN, and **AR/MS need re-checking once translated** — a `FittedBox` shrinking a tab label is CR108 over again. Rejected: the bounded dashboard (flattest at 3.2 and nothing behind a mode, but no list ever gets a full viewport) and collapsible sections (2.4 screens is a state the user can undo with two taps → 9.7); both kept live in the prototype so the comparison stays auditable. **RTL verification caught a live instance of CR106's T-BIDI trap**: `+$5,423.69 (+5.33%)` reordered to `(5.33%+` — every run mixing sign, digits and parens is now bidi-isolated (the layout mirrors, the numbers do not). **Phase 1 needs nothing from the backend** — structure + section split + the 25-cap + the summary + the plan-aware pointer are all view concerns over data already fetched, plus `ListView.builder`; pagination (`limit`/`offset`/`total` on `GET /v1/sim/trades`, and honouring the existing unused `status=` filter) is Phase 3, wanted by the pushed all-trades route which today fetches the whole ledger to render a 25-row tab. **Six defects spotted, flagged to the Architect to mint, not filed here:** open trades buried in history; the eager `ListView(children:)` itself; the trade→journal write wrapped in `except Exception: pass` (`sim.py:328` and two more — silent, and much more expensive once the Portfolio points at the Journal); the Journal list endpoint at `limit=100` with no pagination despite returning `total`; the undisclosed auto-growing watchlist; and `_WatchlistRow` setting the price at 24px `statMid` against a 12px ticker, so the price shouts and the identity whispers. `retranslate:[ar,ms]` — 16 proposed ARB ids in the spec.
