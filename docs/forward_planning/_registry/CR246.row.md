| CR246 | 2026-09-28 | **Backend concurrency: verify the Room (and the API generally) handles multiple simultaneous users correctly** — to be assigned to another agent. Filed after a live incident: the CR228 research toolkit was extended (2026-09-28) to run several Room convenes concurrently, and the FIRST real concurrent run hit `room_sim_holdings_failed`/`room_sector_context_holdings_failed` (`"Multiple rows were found when one or none was required"`) — a get-or-create race on a brand-new synthetic user's portfolio row when N concurrent convenes all called it at once. The app's own `except Exception`/degrade-loudly handler (CR040) caught it and fell back to an honest "Portfolio unavailable this run" line rather than serving wrong data — **the fallback working is not the same as the underlying race being safe**; duplicate rows left behind by the race are real state corruption a different, less-defended read path could hit later. Scope: (1) root-cause and properly fix this exact get-or-create race (DB unique constraint/upsert/lock, not just a wider try/except); (2) verify two DIFFERENT real users convening simultaneously don't leak data into each other (portfolio, mandate, risk-budget, credit balance, rate-limit counters); (3) check shared-mutable-resource races under concurrent write — credit-balance double-spend, risk-budget bookkeeping, `RoomRunner`'s `_active_queues`/`_active_by_key` dedup dicts (touched by the REAL production `start_run()` entry point, unlike the toolkit's direct `run()` calls the 2026-09-28 toolkit-safety check reasoned about); (4) DB connection-pool behavior under real concurrent load vs. Supabase's ~490-500 connection ceiling (CR245 flagged the ceiling as a capacity number, never load-tested against it); (5) provider-side rate-limit/graceful-degradation behavior under concurrent LLM traffic across multiple users. Suggested method: reproduce the exact bug minimally first, fix properly, then build a repeatable N-concurrent-distinct-users load test with a numeric pass/fail bar (e.g. zero cross-user leakage, zero duplicate rows, mathematically correct credit balances after concurrent deductions, bounded p99 latency).
