# CR192 — record vLLM's prefix-cache rate from `/metrics`, since it will never arrive per-call

**Status:** proposed · **Filed:** 2026-08-17 (AT:R70) · **Split from:** DEF226

## What

Scrape `vllm:prefix_cache_queries_total` / `vllm:prefix_cache_hits_total` from the vLLM host's
`/metrics` endpoint on a periodic tick, store the counter pair with a timestamp, and derive a
**windowed** cache-hit rate from consecutive samples. Surface it beside CR141's per-call
`llm_audit` rows so a prompt change can be judged against it.

## Why this exists as a CR and not as the rest of DEF226

DEF226 was filed on the claim that the cache-hit rate is *"still unobtainable on the provider we
actually use"*, and that CR017 §5 step 0 (prompt-prefix reordering) *"would be a blind change judged
on nothing"*. Both sentences were measured false on 2026-08-16, LAN-direct against the live host:

| Fact | Measured 2026-08-16, `192.168.20.74:8000` |
|---|---|
| Per-call `usage.prompt_tokens_details` | present in the shape, **`None`** in value — the server emits the field, the V1 engine nulls it (upstream issues 44961 / 16162 / 18062) |
| `vllm:prefix_cache_queries_total` | 59,681,175 |
| `vllm:prefix_cache_hits_total` | 24,623,808 |
| **Prefix-cache hit rate** | **41.3%** |

So the *blocking* half of DEF226 is gone — the number is readable and CR017 §5 step 0 is unblocked.
What survives is not a defect at all: nothing is broken, nothing degrades silently, and CR141's code
is correct as written (`cache_read_tokens` NULL is the honest answer for a provider that does not
report it — CR040's never-a-fake-zero contract). What survives is **work we have not built**: a
scraper, a tick, and a place to put the numbers. That is CR-shaped, and leaving it inside a defect
row would keep an `open` defect standing for a feature request.

## Scope

**In:**

1. A reader for the vLLM host's `/metrics`, parsing the two counters. LAN-direct
   (`VLLM_BASE_URL`'s host), not via the public hostname.
2. Storage for `(sampled_at, queries_total, hits_total)`. A new small table, or the existing
   telemetry path — whichever the implementer measures as less machinery. **The counters must be
   stored raw, not as a rate**: they are lifetime-cumulative, so a stored rate cannot be windowed
   afterwards and a stored pair can.
3. A periodic tick to sample it — `main.py` lifespan, same shape as CR109 slice 1's daily NAV
   snapshot.
4. A derived windowed rate (`Δhits / Δqueries` between two samples) exposed wherever CR141's usage
   numbers are read.

**Out:**

- Prompt-prefix reordering itself. That is CR017 §5 step 0, which this unblocks and does not do.
- Any attempt to make `prompt_tokens_details.cached_tokens` work per-call. It is an upstream V1
  engine bug; pinning an engine version to chase it is a bigger decision than this CR.
- Anthropic's cache accounting, which already arrives per-call and needs nothing.

## Acceptance

1. A sample is written on the tick, and the two counters in it match a manual `curl` of `/metrics`
   taken in the same minute — **measured against the live host, not a fixture.**
2. Two samples spanning a period of real Room traffic produce a windowed rate that is not the
   lifetime rate, proving the windowing works rather than re-deriving 41.3% forever.
3. The vLLM host being unreachable leaves a **gap** in the series — not a zero, and not a repeated
   last value. Same reasoning as CR141's NULL: an absent sample means "we did not measure", and a
   fabricated one would be read as a cache collapse.
4. A unit test pins the parser against a captured `/metrics` body, including the case where the two
   counters are absent (a vLLM build without prefix caching).

## Baseline for whoever picks this up

41.3% on `ami-llm`, 2026-08-16, **lifetime-cumulative**. CR017 §2.4's original figure was 18.5%,
also from `/metrics`. Neither is a like-for-like window, so treat 41.3% as a number to re-read on a
window, not as a trend to extrapolate from.

## The counters reset, and acceptance 2 does not survive that (measured 2026-08-19)

Re-read LAN-direct while triaging this CR:

```
vllm:prefix_cache_queries_total{engine="0",model_name="ami-llm"}  1,064,911
vllm:prefix_cache_hits_total{engine="0",model_name="ami-llm"}       612,032
```

That is **fewer** queries than the 59,681,175 recorded three days earlier, so the counter did not
advance — it went back to zero, because the vLLM process restarted. Δqueries across that boundary
is −58,616,264.

This is not a footnote on the baseline; it is a hole in the design above. A windowed
`Δhits / Δqueries` computed across a restart yields a negative or nonsensical rate, and the reader
has no way to tell that from a genuine collapse in cache performance. So the sampler needs one more
rule, and it belongs in acceptance rather than in the implementer's head:

> **A sample whose counters are lower than the previous sample's is a reset boundary, not a
> window.** Record it as a new series (or mark the gap), never as a delta. The honest read across a
> restart is "no measurement", the same answer CR040 requires when the host is unreachable — the
> failure mode here is identical, only harder to see, because a reset still returns a well-formed
> 200 with plausible numbers.

Storing the counters raw is what makes this detectable at all; a stored rate would have hidden it
completely. That decision is now load-bearing for a second, unanticipated reason.

The current lifetime rate is **57.5%** (612,032 / 1,064,911) — quoted only as a fresh reading on a
short-lived counter, not as an improvement on 41.3%. The two numbers cover different processes and
are not comparable, which is the whole point.
