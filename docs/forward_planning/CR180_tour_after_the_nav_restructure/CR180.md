# CR180 — the app tour after the nav restructure

**Filed 2026-08-13, at Saiful's direction, immediately after CR133/CR178 landed:**
*"this is a significant change. we should update the App tour."*

---

## 1. Why

CR133 moved the furniture. The tour still describes the old room.

| | Before CR133 | After |
|---|---|---|
| Bar | FLOOR · PORTFOLIO · JOURNAL · LESSONS · SETTINGS | FLOOR · PORTFOLIO · **GAME** · LESSONS · **YOU** |
| Journal | a tab | a segment of `YOU` |
| Settings | a tab | a segment of `YOU` |
| The mandate | Settings → My Mandate | `YOU` → SETTINGS → My Mandate |
| INSIGHTS | did not exist | a segment of `YOU` (CR178) |

`TourSection` is `{floor, portfolio, journal, lessons}`. Two of those four
sections are no longer tabs, one whole tab (`YOU`) has no tour at all, and
`INSIGHTS` — the only genuinely new *surface* in the app — is untaught.

**The part that does not fix itself.** A new user gets the Floor tour, then each
section's tour as they arrive, and `YOU` would simply be added to that list. But
**every existing user already has `tour_floor_seen = true`**, so nothing fires
for them ever again. Their mental model says the Journal is in slot 3 and
Settings is in slot 5, and the app now silently disagrees. Nothing in the
current design tells them what moved — they have to find out by tapping a
GAME tab where the Journal used to be.

That is the CR040 shape pointed at the user's memory rather than at a config
value: the change is real, it is invisible, and the failure mode is a user
concluding a feature was removed.

## 2. Scope

1. **A one-time "what moved" notice**, shown **only** to users who learned the
   old bar. The rule is derivable, not guessed: they have at least one
   `tour_*_seen` flag from before the restructure *and* no `tour_nav_v2_seen`
   flag. A brand-new user has neither and gets the ordinary tour instead — a
   migration notice about a layout they never saw is noise.
2. **A `YOU` tour** — three steps: the segmented control, where the mandate
   lives now, and what INSIGHTS is. `TourSection` gains `you`, so
   *Restart app tour* covers it.
3. **`TourSection.journal` keeps its flag and its steps.** The Journal did not
   change; only its address did, and CR133 already re-triggered it on
   `journalVisibleProvider`. Renaming or resetting the flag would re-run a tour
   the user has already completed.
4. **`GamesHomeScreen` gets `AmiScreenHeader`.** It was a *pushed* route and
   used an `AppBar`; as a tab it is the only one of five wearing different
   chrome — an inconsistency CR133 introduced by promoting it, and one that
   belongs with the tour work because both are "the GAME tab does not look like
   it belongs yet".

## 3. Deliberately NOT in scope, with the reason

**No coach-mark tour for GAME.** The games home is already a self-explaining
screen: heading, a body stating the rules (*"A fresh 10,000 AMI Cash book, five
trading days, no mandate"*), a live entrant count, the `NO MANDATE · NO HALAL
SCREEN` disclosure chip and its body, and two labelled CTAs. A coach-mark tour
would be the **fourth** explanatory layer on one screen, and the design's own
fence (§13.3) is that the first-entry screen stays *"the single uncluttered
choice"*. If play data later shows people bouncing off it, that is a defect with
evidence, not a tour we should add pre-emptively.

## 4. Acceptance

1. A user with `tour_floor_seen` and no `tour_nav_v2_seen` sees the notice
   **once**; a second launch does not show it.
2. A user with **no** tour flags at all never sees the notice — they get the
   ordinary Floor tour.
3. The notice names what moved in terms of what the user is looking for (the
   Journal, Settings, the mandate), not in terms of slot numbers.
4. The `YOU` tour fires the first time `YOU` is opened and not again.
5. *Restart app tour* resets `you` and the nav notice along with everything
   else — a "restart" that leaves a section un-restartable is the same
   half-truth as a stale path.
6. The GAME tab's header is the same component as the other four.
