# CR241 — Fix `users.locale`: currently write-once and effectively always "en"

**Status:** Proposed, not built. **Filed by:** Architect (AT:R85), from Saiful asking
"are we able to tell what language the user is using the app in?"

## Why

Investigation (2026-09-26) found the locale-tracking infrastructure exists but is
broken in practice — a silent-degradation case per CLAUDE.md's "degrade loudly" rule
(CR040): nothing errors, the durable field is just wrong for almost everyone, with no
visible signal that it's wrong.

- `users.locale` (`backend/app/db/models.py:170`, default `"en"`) is written **once**,
  at account creation, from `POST /v1/auth/anon`'s `req.locale`
  (`backend/app/api/auth.py:166`, `backend/app/services/auth_service.py` ~406-452).
- The mobile client's `bootstrapAnon()` call (`mobile/lib/state/auth_providers.dart:149`)
  never passes a `locale:` argument, so it silently falls through to the client-side
  default `String locale = 'en'` (`mobile/lib/api/api_client.dart:1488`). In practice
  `users.locale` is pinned to `"en"` for virtually every user regardless of device
  locale or in-app language choice.
- Settings → Language (`mobile/lib/i18n/locale_provider.dart`, `LocaleNotifier.setLocale()`,
  line ~47) only persists to local `SharedPreferences`. It never calls the backend, so a
  later language change never reaches `users.locale` either — there is no write path at
  all after signup.
- Settings shows `users.locale` as a **read-only** row (`settings_screen.dart:429`)
  labelled as if it reflects the Language section below it — it doesn't; it reflects
  whatever was sent (or defaulted) once, at signup, possibly weeks earlier.

**The one reliable signal today** is CR181 persona-telemetry
(`backend/app/services/persona_telemetry.py`), which logs the live device/Settings
locale on every telemetry event (`mobile/lib/state/telemetry_providers.dart:19-29`,
reading `localeNotifierProvider ?? PlatformDispatcher.instance.locale`) and aggregates
per user. That's an event-log derivation, not a queryable "current locale" field on the
user row — every other consumer that reads `users.locale` directly (or would want to)
is reading a stale/default value.

This matters ahead of the AR/MS v1.0 push (CLAUDE.md: "EN at alpha, AR + MS at v1.0")
— locale-keyed backend content services (lessons, glossary, AI coach, daily challenges,
client-release-floor) already accept an explicit `locale` param per request, but
anything that instead wants to *default* to "the user's language" by reading
`users.locale` is defaulting to English almost always, silently.

## Scope (proposed, not built)

1. `bootstrapAnon()` sends the real resolved locale (`contentLocaleFor()` / device
   locale via `PlatformDispatcher.instance.locale`) on every call, instead of omitting
   the argument.
2. Add a write path (e.g. `PATCH /v1/users/{id}` or equivalent) so
   `LocaleNotifier.setLocale()` pushes the change to the backend when the user picks a
   language in Settings, keeping `users.locale` in sync going forward.
3. Settings' read-only locale row should then genuinely reflect the synced value (or be
   removed if redundant with the Language picker once synced).

**Non-goals:** no change to CR181 telemetry (it already works correctly), no change to
per-request `locale` params on content endpoints, no new AR/MS translation work.

## Acceptance

`users.locale` reflects the user's actual current app language — set correctly at
signup from device locale, and updated whenever the user changes it in Settings — not
just frozen at `"en"` from a bootstrap call that never sent the real value.
