## CR235 — CI trimmed to a clean-checkout check; Flutter tests + harness self-tests move into the local release gate

## What

`.github/workflows/tests.yml`'s backend unit-test job is removed. The Flutter suite
(`flutter test`) and the `qa/appium` harness offline self-tests (`tests_offline/`) move
out of CI and into a new local release gate, `scripts/promotion/preflight_local_gate.sh`,
run bare inside `/promote-to-alpha` with the same VERDICT-line + exit-code + JSON-record
discipline `preflight_suite.sh` already uses. CI shrinks to what remains: Flutter
(analyze + test) and the harness offline guards, both of which already ran on
`ubuntu-latest` in minutes. `/promote-to-alpha` gains a new step,
`scripts/promotion/ci_status.py`, that looks up GitHub Actions' result for the exact
commit being promoted and prints it as one clear WARNING line — GREEN / RED (naming
failing jobs) / PENDING / CANCELLED / NOT RUN / UNAVAILABLE — that never blocks the
promotion.

## Why

Saiful, 2026-09-25, on the CI review: **"On the CI. go with your recommendation."** The
recommendation, verbatim: *"move the Flutter tests and harness self-tests into the local
release gate, where results are actually read. Cut CI down to a quick clean-checkout check
(Flutter plus harness, a few minutes), drop the 5-hour backend job, and have
/promote-to-alpha show the result as a warning."*

Background, measured by the Architect the same day:

- GitHub Actions on `main` last went green **2026-08-10**.
- The harness job (`qa-harness`) was red every run since 08-11 — first a stale
  `MANIFEST.sha256`, then 8 stale containment tests. Both fixed the same day this CR was
  filed (DEF431).
- The backend and Flutter jobs flapped 08-14→08-25.
- The backend job alone took **5h13m** on a single 09-17 run.
- Every push cancels the previous run's jobs — **11 consecutive cancels** the day this was
  measured — so most runs never finished at all.
- **Nothing in `/promote-to-alpha` or `promotion_protocol.md` ever read the CI result.**
  The workflow existed, ran, and reported, entirely disconnected from the one process that
  ships code.

This is the same failure shape as DEF326 (a gate whose failing state is invisible in the
summary a human reads) and DEF405 (that gate's own exit code swallowed by a wrapper before
a human sees it), one layer further out: a gate that correctly ran and correctly reported,
with **no wrapper and no consumer at all** — the promotion process simply never asked. See
`docs/initial_specs/08_tech/failure_patterns.md` P38, added by this CR, for the general
class.

## Scope

### 1. Local release gate

`scripts/promotion/preflight_local_gate.sh` (new) — runs `flutter test` (mobile/) and
`qa/appium`'s `tests_offline/` (no device needed: locator dispatch, locale-vs-ARB, crawler
logic, harness manifest reasoning). Same discipline as `preflight_suite.sh`:

- Runs bare, ends in one `VERDICT: PASS|FAIL` line and an exit code (0 both green, 1
  either red, 2 could not run).
- Writes `.deliveryos/local_gate_verdict.json` (sha, verdict, flutter/harness sub-verdicts,
  timestamp) so a wrapper that swallows the exit code (DEF405) still cannot swallow the
  record.
- Degrades loudly (CR040) on a missing `qa/appium/.venv` — fails with the exact bootstrap
  command from `qa/appium/README.md` (`cd qa/appium && python3 -m venv .venv &&
  .venv/bin/pip install -r requirements.txt`) rather than skipping silently.

Wired into `/promote-to-alpha` step 1, immediately after the existing suite gate and
`flutter analyze`, with the same "run bare, never through a pipe" instruction DEF405 put on
the suite gate.

`scripts/promotion/postflight.py` gains `check_local_gate_verdict` (mirrors
`check_suite_verdict`'s reasoning, kept as a separate function because the local gate's
record has no single `target`/pass-fail-error counts — it runs two independent suites) and
a `local_gate` check in the driver, second after `suite`. `--local-gate-verdict` CLI flag
added, same pattern as `--suite-verdict`.

### 2. CI workflow trim

`.github/workflows/tests.yml`: the `backend` job (`pytest tests/unit/ -q` on
`ubuntu-latest`, `uv pip install -e ".[dev]"`) is removed. The `mobile` (Flutter
analyze + test) and `qa-harness` (offline guards including the manifest and register-drift
checks) jobs are unchanged — they already ran in minutes and stay green. `concurrency:
cancel-in-progress` stays (harmless now the jobs are short); the workflow still triggers on
push to `main`, on PRs, and via `workflow_dispatch`.

### 3. CI status as a promotion-time warning

`scripts/promotion/ci_status.py` (new) — `gh run list --commit <sha> --workflow tests.yml
--json status,conclusion,headSha,databaseId,url,createdAt`, filtered to the exact commit
being promoted (confirmed live against the repo: `gh run list --commit` filters
server-side by `headSha` on `gh` 2.92.0). On a RED result, `gh api
repos/{owner}/{repo}/actions/runs/<id>/jobs` names the specific failing job(s). Prints
exactly one line:

```
CI: GREEN — all jobs passed (<url>)
CI: RED — <job1>, <job2> failed (<url>)
CI: PENDING — still running (<url>)
CI: CANCELLED — superseded by a later push (<url>)
CI: NOT RUN — no workflow run found for this commit
CI: UNAVAILABLE — gh CLI not installed / not authenticated (<detail>)
```

`main()` always exits 0 on a successful lookup (including RED/PENDING/CANCELLED/NOT
RUN — none of those are a script failure, they are facts about CI); the only non-zero exit
is an internal error preventing the lookup itself, on the same COULD-NOT-RUN-vs-failure
distinction `postflight.py` already draws. Wired into `/promote-to-alpha` step 1 as the
final line before the manual smoke question — printed, never read for an abort decision,
per Saiful's explicit ruling that this warns and never blocks.

## Non-goals

- The backend unit suite is not dropped — it still gates at promotion time via
  `preflight_suite.sh`, unchanged. Only its CI copy is removed.
- No change to what `preflight_suite.sh` itself runs or how it records its verdict.
- No attempt to make CI itself block the promotion — Saiful's explicit choice is warning,
  not gate, for the CI result specifically (the tests that must gate now do, locally, in
  step 1).
- No self-hosted runner or device farm for `qa/appium`'s device suites — those stay on
  melehost and the Mac, as CR162 already decided; only the *offline* self-tests move.
