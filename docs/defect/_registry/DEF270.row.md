| DEF270 | 2026-08-12 | prompt | sim | **The anonymous→claimed merge dropped the whole career: a player's career-point total silently became ZERO at the moment they signed up.** `merge_service.execute` re-keys 24 tables and missed three, all of which the game depends on. **`career_events` is the severe one.** `career_ledger.career_points_total` is `SUM(delta)` over that table for a `user_id`, so leaving the rows on the dead orphan account does not merely lose a history — the adopted account's career score, and every title and rung derived from it, reads as 0. A player who played a week anonymously and then claimed their account would watch their score vanish at the exact moment the product asks them to commit, and the runs themselves DID move (`game_entries`, `game_portfolios`, `game_trades`, `portfolio_nav_daily` are all handled), so every surface anyone looks at would have appeared to work. **`game_duels` is the subtle one — THREE user columns, not two.** `_rekey_all` only knows a `user_id` column, so it cannot reach a table that names a user on each side; and beyond `user_a_id`/`user_b_id`, `winner_user_id` is a separate pointer. Moving the sides while leaving the winner behind is WORSE than losing the row: the adopted account ends up in a settled duel it did not win, i.e. a fabricated loss on its record. (That half-fix was written, then caught by its own mutation check before it shipped.) Leaving duels behind entirely also breaks `games_duels.opponent_of()`, which decides which side is "you" by comparing `user_a_id == user_id` — against a stale id it falls through and returns side A, so a claimed account's duel card would show the player **their own book as the opponent**. **`game_short_positions` is the quiet one:** every read is by `portfolio_id` and the portfolio does move, so the position keeps working and the row simply carries a dead owner until some future user-scoped query needs it — exactly why it would not have been noticed. **A trap in the obvious fix, recorded because it would have looked like success:** reusing the existing `_rekey_skipping_conflicts(conflict_col=period_key)` for `career_events` is silently wrong — `period_key` is NULL on every non-stipend row and `NULL NOT IN (...)` evaluates to NULL (falsy), so every `run_close` and every `duel_result` row would have been left behind while the merge reported a non-zero count. Hence a dedicated `_rekey_career_events` that moves everything and drops only a `finish_stipend` row whose `period_key` the adopter has already claimed (`uq_career_event_stipend_period` is the one genuine conflict; adopter wins, matching every other conflict on this path). **Verification:** `backend/tests/unit/test_games_merge_career_and_duels.py`, 9 tests, incl. the orphan-on-side-B case, the winner-pointer case (mutation-checked: removing that one `update` turns 2 red), the stipend conflict AND its mutation guard that a DIFFERENT period still moves, and a closing test written as an INVARIANT — *nothing the player earned stays on the dead account* — rather than as a list of tables, because two of the three tables here were added the same day the gap was found and a table-by-table test goes stale the next time the game grows one.
