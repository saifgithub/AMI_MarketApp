| DEF132 | 2026-07-28 | process | orchestration | **`orchestration/audit/watcher.sh state` exits 1 on a *successful* board read, so any caller gating on its exit code reads a healthy handshake as a failure.** Found while measuring DEF131, unrelated to it, and deliberately **not** folded into that lane. `print_state`'s final statement is `[ "$n" -eq 0 ] && echo "(no lanes yet under $CR_DIR)"` — a bare `&&` with no `else`, whose exit status becomes the function's and therefore the script's. When lanes exist (`n > 0`) the test is false, the `&&` short-circuits, and the script exits **1** despite having printed a correct table; the only way to get exit 0 is the degenerate case of **no lanes at all**, which is precisely the state a caller would least want to treat as success. Measured side by side: `watcher.sh state` → **exit 1**, sibling `dispatch.sh state` → **exit 0**, on the same repo at the same moment. **Not currently exploited** — nothing in the repo gates on `watcher.sh state`'s exit code today, and its documented contract for the blocking modes (`0` work found, `2` bad usage, `3` timed out) is unaffected — but the script's own header advertises "**0** work found (**or table printed**)", so the code contradicts its stated contract, and the failure is silent in the direction that matters: a future `if sh watcher.sh state; then …` would take the wrong branch on every healthy repo. Same shape as the wider DEF131 lesson (a documented claim that nothing enforces), and the same class as this project's standing `set -e`/exit-code hazards. Fix shape: give the trailing test an explicit `else`/`true`, or end `print_state` with an explicit `return 0`, and — because the whole point is that nobody noticed — pin it with a check that asserts both watchers exit 0 on a populated `state` read, rather than only fixing the one line.
