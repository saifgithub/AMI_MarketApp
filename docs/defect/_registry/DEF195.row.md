| DEF195 | 2026-07-30 | audit | infra | **Nothing stops a client release shipping keys the live backend does not accept, and `extra='ignore'` guarantees that failure is silent rather than loud.** Near-missed on this very release and confirmed by the REL61 bundle auditor. `0.1.0+61` was uploading to TestFlight with a settings screen that PATCHes seven new Mandate fields while Alpha's live `Mandate` schema contained **none of them** — verified against Alpha's own OpenAPI, all seven `ABSENT`. Had a user opened that build before the backend promotion, the screen would have loaded, they would have set a post-loss cooldown, the PATCH would have returned **200**, and Pydantic's `extra='ignore'` would have dropped every unknown key. A control that looks authoritative and writes nothing is **DEF129** exactly — the defect CR101 exists to abolish — reintroduced not by any code but by **deployment order**. Caught only because the Architect happened to write "nothing promoted yet" into the audit brief and then checked the claim; there was no gate, no test, and no alarm. **The asymmetry that makes this structural:** `infra/PROMOTION_HOLD.md` already guards the *other* direction — backend ready on `main`, client half not yet on any device — because that case was painful enough to earn a mechanism. The reverse (client shipped, backend behind) has no equivalent, even though it is the more dangerous of the two: a client ahead of its backend fails *silently* with a success response, whereas a backend ahead of its client is merely inert. **Fix must be mechanical, not procedural** — a checklist item would be the "prompt instructions are not controls" mistake in release form (CR038). Concrete shape: before a store upload, diff the set of keys the client can PATCH against the live backend's OpenAPI schema for the same model, and fail the build on any key the deployed backend would not accept. The client's PATCH key set is statically derivable from its request model; the backend's is a live OpenAPI read, which this session already did ad hoc in a five-line script. Ordering rule to encode alongside it: **backend promotes first, client ships second** — on this release it went the other way round. Auditor's own words: *"Agree it wants minting — a promotion-order gate with the check mechanical (OpenAPI diff vs the client's PATCH key set), not procedural."* Relates to **CR101** (the near-miss), **DEF129** (the failure it would have reproduced), **DEF038** / **DEF063** (features dark for months because config never reached the container — same silent-gap family), **CR040**, **CR038**. | open | — | AT:R65 |
