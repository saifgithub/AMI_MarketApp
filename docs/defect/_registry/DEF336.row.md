| DEF336 | 2026-08-20 | claude | room | **A dead LLM provider produced a full 450-run backtest batch that reported "450 completed, 0 failed" — because the DEF059 outage fail-safe is a completed run carrying a PASS verdict, and nothing could tell it from a decision.** The CR164 outcome sweep `r70-outcome-1` ran 2026-08-19 20:05 → 2026-08-20 04:57 UTC against an on-prem vLLM that had died in the eleven minutes after the previous batch finished. **Every one of the 450 verdicts** was `action=PASS, overridden_from_llm=True, reason="AMI's analyst room lost its model connection before the Portfolio Manager could rule…"`. The sweep counted each as `completed`, wrote 450 records to the batch JSONL, and printed a clean summary; `backtest_report.py` would have scored them as a 0%-approval Room and the number would have looked like conservatism. The giveaway was arithmetic, not instrumentation: the paired batch on identical code approved 9 of 126 (7.1%), so 0 of 450 has probability ≈1e-15 — the result was impossible before it was suspicious. Wall-clock said the same thing more cheaply: 450 runs in 8.9 h is 71 s each against a measured 155 s, because a failing convene fails fast. **Root cause is a sentinel with no name.** The fail-safe's text was an inline literal inside `room_runner`'s PM branch, so the only way for any consumer to recognise an outage verdict was to match a prose fragment — and no consumer did. `overridden_from_llm` alone cannot serve: the safety floor sets it too, on verdicts that ARE decisions. **This is DEF059's own lesson recurring one layer out.** DEF059 stopped an outage minting a confident APPROVE for a user; nothing stopped an outage minting 450 confident PASSes for an experiment, where the cost is not one bad verdict but a whole dataset that looks like evidence. `failure_patterns` P-class: a fail-safe is only safe if its output is distinguishable downstream. **Fix, in three parts.** (1) `PM_LLM_UNAVAILABLE_REASON` is now a named constant and `is_llm_outage_verdict(verdict)` is the recogniser, pinned by a test to the `Verdict` the runner actually builds so a reword of one without the other cannot silently un-detect it, and asserted NOT to fire on a safety-floor override. (2) `backtest_sweep.py` aborts after `--max-consecutive-outages` (default 3) consecutive outage verdicts, prints how many of the completed runs are outage fail-safes, and exits 3 — rather than spending a night manufacturing a dataset whose only content is the provider's downtime. (3) `backtest_report.py` refuses to score any batch whose verdicts are >5% outage fail-safes (exit 4), an independent guard at the layer that turns records into claims. **`r70-outcome-1` is void** — 450 records, zero scoreable, recorded in the CR164 findings so nobody scores it later; its pairs are re-run under a fresh batch-id. **Still open and NOT ours:** the vLLM host `192.168.20.74` is unreachable (100% packet loss, port 8000 closed) and needs Saiful — no backtest can run until it returns.
