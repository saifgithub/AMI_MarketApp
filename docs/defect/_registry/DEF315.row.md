| DEF315 | 2026-08-15 | user | mobile | **After placing an order the app looked like it had gone back to the state just before it — and the submit button was live again the whole time.** Reported by Saiful from a device: *"There is a 'delay' between placing an order and getting the confirmation that the order was accepted. The app looked like it was back to the state just before the order was made, confusing the user."* **Cause:** `SimNotifier.submit` set `submitting: false` the instant `POST /v1/sim/submit` returned, and then made four more sequential round trips before any of the state reflected the trade — `simEvaluate` (the **entire** resting-order sweep plus bracket evaluation, with a per-ticker quote fan-out), `simPortfolio`, `simListTrades`, `simRestingOrders` — followed by the journal and watchlist refreshes. For every one of them the spinner had stopped and the portfolio behind the sheet was still the pre-trade one. **One flag was carrying two meanings** — *"the POST is in flight"* and *"this order is being placed"* — which are the same thing to the user and diverge by four round trips in the code (P10's shape on a money-moving control). **The confusion is the symptom; the defect is the live button.** The trade ticket's CTA gates on `state.submitting` and **never on `state.loading`**, so through the whole reconciliation window the button was enabled over a form still holding the order that had just been accepted. A second tap places a second order, and the server's duplicate guard covers only trades carrying a `verdict_ref` (`sim_engine.submit`'s `_existing_trade_for_verdict`) — **a manual trade has no such guard at all.** The window is as long as a cold-cache sweep takes, which is exactly the case where the user is most likely to tap again. **Fix:** `submitting` now spans the whole operation — the POST *and* the reconciliation — because from the user's side that is one action, and it is cleared in a **`finally`**, one place covering both paths (the error path previously cleared it only by an explicit assignment in the `catch`, so a throw between the two assignments would have wedged the button off). `refresh()` is still awaited, because the screen the user returns to must be correct before the control comes back; the **journal and watchlist refreshes are deliberately no longer awaited** (`unawaited`) — they feed the Journal tab and the ticker tape, neither of which is on screen when the sheet closes, so holding the button hostage to them bought nothing but latency. **Guarded:** `mobile/test/state/def315_submit_window_test.dart`, 2 tests. The first samples `submitting` **on every state emission** through a `container.listen`, against a fake API whose reconciliation calls are deliberately slow, and asserts that no emission shows an idle button while the portfolio is still pre-trade — a before/after assertion cannot see this defect at all, because `submitting` ends false either way and what changed is whether it was ever false *during*. The second pins the `finally` by throwing from `simSubmit`. **Mutation-proved:** restoring `submitting: false` to the line after the POST turns the window test red. **Full suite: Flutter 1,103 passed, `flutter analyze` 0 errors.** Not on any device — ships in `+97` with CR188 slices 2–3. | fixed | [mobile/lib/state/sim_providers.dart](../../mobile/lib/state/sim_providers.dart) · [mobile/test/state/def315_submit_window_test.dart](../../mobile/test/state/def315_submit_window_test.dart) | AT:R70 |
