It runs on BOTH CR136 routes — the tiles GET and the Finding POST — because both call `evaluate_gate`. There is no `COUNT`, and the trial leg has no date bound at all, unlike the daily leg which at least filters after the fetch. The row count is bounded today only by `daily_cap × days`, i.e. by the cap working correctly — and the audit's own BLOCKER B1 (fixed at round 2) was a live demonstration that "bounded by the cap" is an assumption rather than a property: with the cap defeated, an ordinary user reached ~7,200 generations a day, every one of them a row this query would then fetch in full on every subsequent request. **Fix, not yet made:** replace the fetch-and-count with two `SELECT COUNT(*)` queries plus a `SELECT MIN(created_at)`, and give the trial leg the same date bound the daily leg has. Roughly ten lines. **Deliberately deferred rather than folded into M07's round 2**, and the reason is the coupling, not the size: this is the read that produces both spend counters, B1 had just proved that subsystem was silently broken, and a rewrite of the counting SQL shipped in the same commit as a blocker fix would put two changes with completely different failure modes behind one verdict — a wrong `COUNT` predicate does not fail loudly, it just changes the cap. It also lands in `journal_store.py`, which M08 has under audit. Wants its own round: the COUNT rewrite, a test that the three numbers are unchanged for a seeded book, and one that the trial leg's new date bound does not move a boundary any existing test asserts.
