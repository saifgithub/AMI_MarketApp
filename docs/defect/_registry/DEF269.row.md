| DEF269 | 2026-08-11 | bug:tester-report | sim | **Game fills leaked into every TRAINING read of `sim_trades` — and `evaluate_outcomes` sold them out of the training portfolio.** Reported by a tester on the shipped build: *"game trades are appearing in portfolio open trades."* `sim_trades` was a per-USER table long before it was a per-portfolio one. CR109 slice 2 gave a user MANY portfolios (one `kind="training"` + one per game run) and routed game fills through the same `_execute_fill`, so a game row lands in `sim_trades` carrying the same `user_id` and a different `portfolio_id` — and six readers still filtering on `SimTradeRow.user_id == user_id` alone silently widened from "this user's training trades" to "this user's trades anywhere". **The reported symptom is the mild half.** The severe one is `sim_engine.evaluate_outcomes`, which selected those same rows and then sold each against `p_row = self._load_portfolio_row(s, user_id)` — which defaults to `kind="training"`. `submit_game_trade` passes `stop`/`target` straight through, so a GAME position hitting its stop would liquidate shares the TRAINING account had bought for its own reasons, credit the proceeds to training cash, and leave the game position open: a cross-portfolio sale with no user action and no surface that would show it. `manual_close` is the same sale by another door. Two quieter halves: `_risk_limit_context` reads `list_trades`, so game fills consumed the training account's over-trading brake, post-loss cooldown and open-risk cap — the safety floor refusing a training trade on activity that never happened in the account it protects; and `holding_lots` blended game fills into a training holding's FIFO cost basis, producing a wrong average cost on a screen the user reads as fact. `day_trader_outcomes._load_all_trades` had the same shape (a lesson about the user's own practice account, counting their contest fills). **Fix:** one `training_trade_scope(user_id)` clause — `SimTradeRow.portfolio_id.in_(select(SimPortfolioRow.id).where(user_id, kind == "training"))` — applied at all six sites. Scoping by `portfolio_id` rather than by a new `kind` column on the trade is deliberate: the portfolio row already knows its lane, so there is nothing to keep in sync and no way to write a trade whose own label disagrees with the portfolio it belongs to. It returns no rows when the user has no training portfolio, which is the correct answer rather than a crash or a fall-through to everything. **Verification:** `backend/tests/unit/test_def269_game_trades_leak_into_training.py`, 8 tests written against the observable guarantee ("the training lane cannot see or act on a game fill") rather than against the query text, incl. the cross-portfolio liquidation, a mutation guard that a genuine TRAINING stop still fires (so scoping to nothing would not pass), and the cost-basis and open-risk halves. Mutation-checked: reverting `training_trade_scope` to `user_id ==` turns 6 of the 8 red.
