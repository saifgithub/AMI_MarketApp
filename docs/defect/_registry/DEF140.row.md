The W3C server-sent-events line-splitting rule terminates a line on **CRLF, LF, *or* a lone CR** — so a bare `\r` inside a `data:` field ends that field for a compliant reader, and `\r\r` produces the blank line that ends the *event*. That is byte-for-byte the forgery vector DEF127 closed for `\n`, still open for `\r`. **Why it is not live today, measured:** our only consumer is the shipped Flutter client, whose decoder (`mobile/lib/services/api/api_client.dart:113-135`) splits on `\n` alone and has no `\r` arm, so a raw CR reaches it as an ordinary character. The exposure is latent, not current — it opens the moment anything else reads these streams (a browser `EventSource`, a proxy that normalises line endings, a curl-based debug script, a future web client). **Why DEF127 deliberately did not fix it:** escaping `\r` to a literal `\\r` would be *rendered* by the shipped `0.1.0+56` decoder, which only inverts `\\n` and `\\\\` — a visible regression in the field to close a hole no live client has. The asymmetry was forced by the wire format, and correctly, but it is now an undocumented sharp edge inside the choke point that exists precisely so nobody has to think about framing. **Fix shape (not yet chosen):** either `sse_text` rejects `\r` the way `sse_json` already rejects both control characters — turning a silent reframe into a loud `SseFramingError`, per CLAUDE.md's degrade-loudly rule — or it normalises CR to LF before escaping. Rejecting is the stronger read: no producer has a legitimate reason to put a carriage return in streamed prose, and a raised error surfaces at the source instead of corrupting a transcript. Either way the whole-tree invariant in `test_def127_sse_framing_invariant.py` extends to cover it, and the escape decision gets a comment saying *why* the two framers differ.
