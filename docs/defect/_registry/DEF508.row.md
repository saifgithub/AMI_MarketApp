Only the last limit wrapped to two lines and showed its value. **Second attempt: DEF502 set `maxLines: 2` and it still clipped on the device.** | fixed | **Cause (reproduced in a widget test):** Flutter's `_RenderChip` sizes the label's height with a dry layout at the chip's FULL max width, then lays the label out at the real, narrower width (minus the check mark, label padding and chip padding) with that one-line height as `maxHeight`. A label that fits on one line at full width but wraps at the real width is clamped to one line's height, so its second line, holding the value, is cut. DEF502's `maxLines: 2` cannot help: the line count was fine, the height was clamped. The last limit only showed its value because its longer "— 10.5%" already wrapped in the first measurement. **Fix:** the chip is a small private widget, `_WrappingChoiceChip` (same outline, selected tint, check, 48 dp tap target, button + selected semantics, same `riskLimitOff_<key>` key), built on a plain `Row` so its height follows the text over any number of lines; the label has no `maxLines`, so the value shows at any locale length and text scale. The number is still the server-resolved one passed in as the label (CR129/CR046): nothing is computed client-side. **Tests:** `def508_risk_limit_chip_wrap_test.dart` (5 cases: all seven chips at 360 dp, DPR 2, scales 1.0 and 1.3; a 300-600 dp sweep at both scales; a fine 330-560 dp sweep that checks only the line clamp; ar and ms at 360 dp, 1.3x; semantics and tap). On the old code the line-clamp sweep fails at 402 dp (text bottom 29.6 vs box 16.5, one line) and the other three layout cases fail on `didExceedMaxLines`; the test env has no IBM Plex Mono (Ahem is wider), so the sweep, not one font's metrics, carries the proof. **Verify** on the next device run: E5-MAND-01 shows the value on all seven chips.
