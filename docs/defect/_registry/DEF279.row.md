| DEF279 | 2026-08-13 | prompt | infra | **Both store build scripts bumped and COMMITTED the build number before running the checks that can refuse the build, so every refusal spent a number that was never uploaded.** In `build_testflight.sh` and `build_playstore.sh` the pubspec bump sat at line ~117-131 and the two refusal gates — GAMES+PRODUCTION, and the RevenueCat Test-Store-key check — at ~142-180, *after* it. Apple and Google both reject a re-upload at the same `+N`, so a burned number is genuinely spent: the next real build skips it, and the version history acquires gaps that mean nothing. **Observed twice, the second time live.** First: the `0.1.0+85`/`+86` double-burn from two refused builds, reverted by hand in `b27a08e4` (*"un-burn 0.1.0+85/+86 — two bumps from refused builds"*) — treated as a one-off at the time. Second: cutting `+86` for CR109 slice 4, `scripts/build_testflight.sh` printed *"▶ bumping pubspec: 0.1.0+85 → 0.1.0+86"* and *"▶ committed bump"*, then refused one screen later because `REVENUECAT_IOS_SDK_KEY` is a `test_…` key and `--internal-only` was not passed. The bump commit `2dc02793` was already on `main`. Recovered only because the burned number happened to be the one wanted anyway, so the rebuild could pass `--no-bump`; had the operator re-run without it, `+86` would have been abandoned for `+87`. **Fix:** move both gate blocks ABOVE the bump in both scripts — a pure relocation, no logic change, with an `ORDER IS LOAD-BEARING` comment naming this defect so the next edit does not undo it. **Why it matters beyond the wasted integer:** a gate that costs something when it fires teaches the operator to route around it, and these two gates are the ones that stop a hidden game route reaching App Review (guideline 2.3.1) and stop a Test-Store key granting free paid entitlements to real users. Those must be cheap to trip. This is the CR040 family seen from an unusual angle — not a control that fails silently, but a control whose *cost* creates pressure to disable it. **A process note worth keeping:** the fix was first written while a build was still executing the very script being edited. Bash reads a script incrementally, so rewriting ~60 lines under a running interpreter can send it to a garbage offset; the edit was reverted within the minute and re-applied after the build finished. Never edit a shell script that is currently running — the correct sequence is park the patch, wait, apply.
