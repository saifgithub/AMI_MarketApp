| DEF419 | 2026-09-24 | founder | backend | **`/v1/sim/preview` checked the mandate against the AMI sim account even when the trade's destination was Alpaca paper.** Saiful, from a TestFlight screenshot (ASML buy 10 @ $1731, destination Alpaca paper): *"When placing an order either for both or for alpaca paper only, the mandate is checked against the local AMI SIM account. The mandate should check limits based on the account in use. It does mean that it may reject for ami and approve for alpaca. Or vice versa. This is an expected condition."* Root cause: `SimEngine.preview()` always sized the single-name cap, sector cap and cash-sufficiency check against the caller's `$10k` AMI sim portfolio (`ensure_portfolio`/`_compliance_context`), so an Alpaca-only preview measured a trade against the WRONG account's equity — "position size 137.2% exceeds single-name cap 100.0%" on a screenshot where the actual (larger) Alpaca account could easily have accommodated it. Fix (backend half; mobile follow-up not yet filed as its own CR): `SubmitTradeRequest.account` (new, optional `AccountSnapshotIn` — `kind`, `equity`, `cash`, `positions[]`) on `POST /v1/sim/preview` only; when present, `SimEngine.preview()` builds `Holding`/`quotes`/`portfolio_value`/`cash` from THAT snapshot and runs the SAME `check_mandate_compliance` against it instead of the AMI portfolio — same mandate, same function, different denominator; response echoes `account_kind` so the client can label which account the verdict is about. Per-USER limits (post-loss cooldown, over-trading brake, total open-risk) still read AMI's own trade history regardless of which account is named — those are about how often/how hard the user trades, not one account's balance sheet, and AMI is the only place that history exists; halal/long-only/blocklist are also mandate-level and fire identically on both paths. Client-attested input (CR202 custody: the backend never holds the Alpaca credential) is bounded the same way `AlpacaSnapshotIn`/`AlpacaOrderLogIn` already are (`extra="forbid"`, finite floats, symbol pattern, `equity>0`) — malformed input is a 422, never a silent fallback to the AMI account (degrade loudly — falling back IS the bug this DEF fixes). Known limitation, disclosed in the design doc: an externally-custodied account has no AMI-tracked NAV history, so its drawdown check reads `0.0` (this codebase's established "no data, never a false breach" convention — see `price_alert_evaluator.py`'s identical zero-context call), not a claim the account never drew down. `preview()` still never persists (guarded by a dedicated test). 20 new tests (`test_def419_per_account_mandate_check.py`): no-account unchanged, same order rejected/accepted per account in both directions (incl. cash sufficiency), 8 malformed-snapshot 422 cases + a schema-level non-finite (NaN/inf) case, existing snapshot holdings counted into the sector cap and the CR171 gross-exposure short path, a documented single-name-cap-ignores-same-ticker-BUY-holding negative control (pre-existing, deliberate design, unchanged by this DEF), long-only short-detection reading snapshot holdings, over-trading brake and post-loss cooldown proven per-user across both accounts, halal identical on both paths, and the never-persists invariant.
