| DEF388 | 2026-08-31 | claude | backend | **CR214's primary estimator ranked on the raw vote count, so a degrading provider silently reorders the cross-section it measures.** The rank-IC arm scored each convene by `approve_votes` alone. But `samples` records how many independent CIO draws *actually returned*, not how many were configured — a loaded provider returns fewer, and the first convenes of the CR214 sweep produced **1-of-1 and 3-of-5 in the same batch**. On a count-based score the 1-of-1 (score 1) ranks **below** the 3-of-5 (score 3) while meaning the opposite, so provider load — not the Room's judgement — determines part of the ranking the entire edge test rests on. Demonstrated: on three rows whose returns line up perfectly with the approval fraction, the count-based IC is **−0.5** and the fraction-based IC is **+1.0** — a sign flip, not a dilution. **Fix:** score on the approval fraction via a module-level `graded_score()` helper (extracted so it is directly testable rather than pinned by an AST guard), returning `None` — not `0.0` — when there is no usable denominator, since a run that never reached the vote path expresses no view and folding it in as the weakest score asserts a rejection the Room never made. The report now also prints the achieved-draws distribution, so a batch whose provider was degrading is visible rather than quietly diluted (CLAUDE.md, *degrade loudly*). **Caught before the estimator had ever run against real data** — Phase B predates `approve_votes`, so this arm had only ever been unit-tested on synthetic full-sample rows where the bug is invisible. Found by reading the first live sweep verdicts out of Postgres rather than assuming the config value was what landed.
