| DEF395 | 2026-09-01 | claude | mobile | **The new tour overlay stopped watching its target once the target settled, so a target that vanished MID-STEP left a full-screen dim, and a tour nobody saw fired its completion toast.** Three defects in `ami_tour_overlay.dart` as first landed under [DEF382](../DEF382), all raised by the CR215 foreign auditor (`kimi-code/k3`) and all verified at file:line before filing. **(a) The watcher stopped.** `_scheduleRectRefresh` re-armed itself only `if (waiting)` — i.e. only while still hunting a first rect — so the post-frame chain ENDED the moment a target settled. `_focus`'s skip-a-dead-target logic therefore ran only at step TRANSITIONS; a target leaving the tree while its step was on screen was never observed at all, and the barrier kept painting with `_rect == null`, which is a full-screen dim over a step pointing at nothing. Escapable via Skip/Next, so a soft lock rather than a hard one. Fixed by re-arming for as long as the tour is open — this forces no frames (`addPostFrameCallback` runs after a frame the app produces anyway, and a vanishing target always produces one) — and by handing a confirmed-dead target back to `_focus`, which already knows how to step over it and close when none remain. **(b) `onFinish` fired for a tour that was never displayed.** `_focus` walks past unmounted targets with `index++` and falls off the end into the same `_close(finished: true)` the last "Got it" tap reaches, so an all-unmounted tour showed the completion toast and marked itself seen. Now `_close(finished: _shownAny)` — *finished* means the user reached the end, not that the loop did. **(c) A comment asserted behaviour the code did not have,** claiming the rect refresh re-ran on "an orientation change"; nothing rescheduled it, so a rotation would leave the cutout at stale coordinates. Left unreachable rather than engineered around: `main.dart:69` locks the alpha to `portraitUp`. The comment now says so, and says what to add if that lock is ever lifted. **Provenance — this is the second correlated-error catch in one round.** The same-family gate (`auditor.core`, opus-4-8) returned `VERDICT: COMPLETE (round 1)` and asserted the entry was *"removed on every exit path (skip / last-step finish / vanished target), via an idempotent `_close()`"*. That is false for the mid-display case. See [DEF394](../DEF394) for the first catch in the same round.
