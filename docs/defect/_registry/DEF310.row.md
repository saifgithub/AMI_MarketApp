| DEF310 | 2026-08-15 | prompt | backend | **A triggered stop-limit fills against its TRIGGER on the next sweep, ignoring the limit price the user set.** `_fill_triggered` read `order.named_price` unconditionally, which returns the **trigger** for a stop-limit. Correct on the first sweep, while the order is `working` and the trigger is what it waits for — and wrong on every sweep after, because the phase-1 block that re-evaluates against `limit_price` runs only `if order.state == "working"`. A `triggered` stop-limit therefore fell straight through to a trigger comparison, matched, claimed, and **filled with its limit price never consulted at all.** **The case it breaks is CR170's own worked example and the second half of acceptance 6** — *"a stop-limit that triggers into an unmarketable limit rests and does not fill."* Sell stop-limit, trigger $90, limit $88, price gaps to $85: sweep one triggers and correctly declines; sweep two, five minutes later, fills at **$85 — three dollars below the floor the user named.** That gapped-through-the-limit outcome is, in CR170's words, *"the classic stop-limit failure and the reason the type exists in the curriculum"*, so filling it is not a rounding error — it is the simulator teaching the inverse of its own lesson, on a money-moving path, live on Alpha since `alpha-2026-08-14-3`. **Why three layers of testing missed it.** The two-phase rule had exactly one test, `test_cr170_order_pricing.py::test_stop_limit_that_gaps_through_its_limit_never_fills`, which exercises the **pure function**. `test_cr170_resting_orders.py` opens by naming this precise gap — *"that file proves the arithmetic; this one proves the arithmetic is the one that runs… a guard nothing exercises is not a guard"* — and then never gave acceptance 6's stop-limit clause a sweep-level test. Every existing sweep test also sweeps **once**, which is the only cadence under which the defect looks correct. **Found while writing CR187's push tests**, by a test that swept three times to prove a trigger notification fires only once. **Fix:** the phase is in `state`, not in `order_type`. `_fill_triggered` now derives `(eval_type, named)` before the trigger comparison — `LIMIT`/`limit_price` for a `triggered` stop-limit, the order's own type and named price otherwise — so phase 2 is evaluated by the same `is_triggered` call that phase 1 is, rather than by a block that only runs in one state. `fill_resting_order` already priced the fill off `limit_price` correctly; only the trigger decision was wrong, so the fix is four lines and no pricing change. **Guarded:** `test_def310_stop_limit_phase2.py`, 4 tests, every one sweeping at least twice.
