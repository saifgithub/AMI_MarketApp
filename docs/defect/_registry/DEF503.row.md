| DEF503 | 2026-11-19 | AMI-DL-3 real-device E5 run (Android, store build 0.1.0+118 against Alpha) | mobile / Journal | **Three Journal bugs (E5-JRNL-01):** (a) tapping ALL fetched the full list but the highlight and check stayed on the previous chip (1-ON-1); (b) with a chip selected, a search listed TRADE and BLOCKED entries under 1-ON-1; (c) the "Entry removed - UNDO" snackbar never auto-dismissed, stayed 30+ s and followed the user across screens. | fixed | **Cause:** (a) `JournalNotifier.refresh` wrote `copyWith(filterType: filterType)` and `copyWith` treats null as unchanged, so ALL could never clear a chip. (b) the same coupling in reverse: bare `refresh()` calls from `MandateNotifier`, the Room and trade fills fetched unfiltered while the lit chip stayed, so the list and the chip disagreed and a search sat on top of that; with no request ordering, a slower older response could also overwrite a newer one. (c) Flutter does not start the auto-dismiss timer for a SnackBar that has an action when `MediaQuery.accessibleNavigation` is on (TalkBack, and the UI-automation service a device lab drives the phone with), and the root `ScaffoldMessenger` keeps it across screens. **Fix:** `refresh()` with no arguments re-fetches the chip and search in view; one private `_fetch` is the only writer and always records the filter the rows were fetched with (`clearFilter` for ALL); a request token drops stale responses; the undo bar closes on an explicit timer (8 s under accessible navigation, 4 s otherwise) and when the user leaves the Journal segment. (b) was reproduced as logic, not on the device: the exact sequence the tester used could not be replayed here, the ordering and bare-refresh defects above are the ones found in code. Tests: `def503_journal_filter_and_undo_test.dart` (9 cases: ALL clears chip in state and on screen, search sends both filters, bare refresh keeps them, stale response dropped, bar closes normally, closes under accessible navigation, closes on leaving the segment); 7 of 9 fail on the old code.
