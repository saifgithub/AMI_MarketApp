| DEF119 | 2026-07-27 | backend | api | **`freeze()`'s 2-per-year streak-freeze cap is an unprotected COUNT-then-INSERT — two concurrent requests can both pass the check.** Found by the CR091-STREAKS auditor (track U, independent) as its single MINOR finding; the lane was still voted **COMPLETE round 1** because the blast radius is narrow. `reputation_service.freeze()` enforces the Floor Manager perk's 2/year cap with a `SELECT COUNT(*)` immediately followed by an `INSERT`, with **no `SELECT ... FOR UPDATE` and no constraint spanning "count of rows per user per year."** The only DB constraint is `UniqueConstraint(user_id, frozen_date)` on `StreakFreezeRow`, which prevents re-freezing the *same* date and does nothing for two *different* dates requested concurrently. **The auditor's reproduction was inconclusive and says so:** it seeded one legitimate freeze, opened two uncommitted sessions and called `freeze()` on each for different new dates — both calls got past the stale COUNT before either committed (so the race window is real at the code level), but SQLite's coarse file-level write lock threw `database is locked` on the second insert. That lock is an artifact of the **test engine**, not the application; Postgres's default READ COMMITTED — the actual production engine — does not serialise this. Evidence is therefore structurally reasoned, not mutation-confirmed, and cannot be settled without a live Postgres instance (unavailable: the Mac is a pure editor). Worst case is a paid-tier user obtaining a few extra streak-freeze days per calendar year — **no credits, no money, no security/safety/compliance surface** — which is why this is MINOR rather than a blocker on the lane. Recommended fix: `SELECT ... FOR UPDATE` on the count query, or an equivalent serialising constraint. Note the cap's period is the **calendar year** (`period_key = str(target_date.year)`), confirmed from code during the audit.
