| DEF157 | 2026-07-29 | prompt | mobile | **A release can ship one store and silently skip the other — `+57` went to TestFlight and never went to Play at all, and nothing anywhere noticed for a week.** Surfaced by Saiful 2026-07-29 as *"we have a drift in the build number for IOS and Android. they should both be 58. android is showing 56"* — reported as a drift in the artifacts, but **measured, the artifacts are not drifted**: `pubspec.yaml` and `android/local.properties` both read `0.1.0+58`, the built APK carries `versionCode 58` (read out of the binary manifest), the AAB is the same build, the melehost tester rig's APK is **byte-identical to the local one by sha256**, TestFlight has `58`, and `google_play_track_version_codes` reports **`internal → [58]`**. The `56` is what was **installed on the device** — Play had not yet propagated the release uploaded minutes earlier. **The real defect is why the gap is TWO builds instead of one:** `+57` was built and uploaded to TestFlight on 2026-07-28 and **was never published to Play**, so Android's last delivered build stayed at `56` while iOS moved to `57` and then `58`. **Mechanism — two independent bump paths with no parity check.** `scripts/build_testflight.sh` and `scripts/build_playstore.sh` each own a `DO_BUMP=1` and each bumps `pubspec.yaml` themselves (`build_testflight.sh:47,86`, `build_playstore.sh:55,87`). Running one without the other advances the shared version for **both** platforms while shipping only one, and nothing in either script, in the promotion protocol, or in any test compares what the two stores actually carry. This is the **P11 shape** — one rule ("both stores ship the same build number") implemented in two places with nothing tying them together — and the **CR040 shape** on top of it: the failure is completely silent, so the only signal is a human noticing a number in the app days later, which is exactly what happened. **Consequence beyond the number:** every Android tester was two builds behind for a week, so any bug report from an Android device in that window was filed against code that was not the code we thought was running — which corrupts triage, not just tidiness. **Second observation from the same measurement, and it is INERT — the first version of this row overstated it and is corrected here.** The Play **closed testing track** (API name `alpha`) holds `versionCode 43` under a release named `ami_trade_release`, against internal's `58`. I initially recorded that as fifteen builds of live staleness and warned that any tester enrolled in closed testing had been running a weeks-old build. **That was wrong, and querying the Play Developer API directly rather than only `google_play_track_version_codes` is what showed it: the release's `status` is `draft`, not `completed`.** A draft release is never served to anyone, whatever the enrolment. So nothing is stale in the field and no tester is stranded — it is an abandoned half-finished release, created around 2026-07-21 when `+43` was current, and left in the console. Consistent with `mobile/android/fastlane/Fastfile`, which has only ever targeted `track: "internal"` (CR048) — our automation has never written to the closed track, so this is a manual console leftover. `beta` and `production` are empty. **Disposition: cosmetic cleanup, not a defect** — discard the draft in the Play Console or leave it; it changes nothing either way. Recorded rather than deleted because the *method* matters: a track-version query alone reports a version code with no indication of whether it is live, which is precisely the kind of number that reads as alarming and is not. **Fix shape (not yet built):** a release must be a single act that either ships both stores or fails loudly. Options in preference order — (1) one `scripts/release.sh` that bumps ONCE and drives both store scripts with `--no-bump`, so the version can only advance when both uploads are attempted, which is how `+58` was in fact shipped by hand today; (2) a parity check that queries `google_play_track_version_codes` and the App Store Connect API for the latest build on each and fails when they differ, runnable standalone so drift is detectable without a release; (3) at minimum, a loud warning in each single-store script that it is advancing a version the other store will not receive. **The guard is the part that matters** and must not be a comment in a runbook: a check that runs, since the whole failure mode here is that a silent skip looks identical to a successful release. **`--no-commit` remains mandatory on `build_testflight.sh`** whenever it is invoked (its `--commit` path does a bare `git commit`, which sweeps a concurrent track's staged work — a separate known trap, not this defect).
