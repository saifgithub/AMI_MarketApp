| DEF158 | 2026-07-29 | audit | mobile | **The restart-onboarding confirm dialog promised to clear the user's mandate, and nothing clears it.** REL58 MAJOR M2. DEF152 added a confirm gate in front of the Floor footer's "restart onboarding" link — the gate itself is mechanically correct and well tested — but its body read *"This clears the mandate your interview produced — goal, risk score, drawdown cap and constraints…"*. **Traced end to end, no code path does that:** `reset()` ([`onboarding_providers.dart:123-128`](../../mobile/lib/state/onboarding_providers.dart)) removes a `SharedPreferences` flag and resets in-memory state, with no API call; the only interview→mandate persist path, `_bind_onboarding_session` ([`auth.py:82-84`](../../backend/app/api/auth.py)), is guarded by `get_mandate_store().get(user_id) is None` and its own docstring says it must *"never clobber a mandate that may have been edited since claim"*; and `/onboarding/readback/confirm` builds a mandate preview the client never PATCHes back. **The population split, measured rather than assumed:** `get_or_default()` ([`mandate_store.py:51-56`](../../backend/app/services/mandate_store.py)) returns a hydrated default **without persisting**, so a `mandates` row exists only after claim-binding or a Settings edit. A user with no row (anonymous, pre-claim) restarts fine — their new answers form the mandate at claim. A user **with** a row keeps it: the retaken interview changes nothing, and the old answers keep governing the safety floor and every Room run. That is exactly the user the dialog was speaking to, so the copy was false precisely where it mattered and true only where it was redundant. **Class:** promise-vs-mechanism — the same shape as **DEF129**, which was fixed *in the same batch* this copy shipped in, and the **CR040** question ("if this fires silently, what does the user end up believing?") answered badly: they believe they have reset their strategy and they have not. **Fix (copy, not mechanism):** the body now states the one thing true for both populations — the interview re-runs, an existing mandate is *not* replaced, and Settings → My Mandate is where it changes — reusing the exact "Settings → My Mandate" phrasing already established by `tradeTicketChangeMandate`. Making restart genuinely replace the mandate is a product decision touching DEF060's deliberate anti-replay guard; minted separately as **DEF160** rather than self-ruled here (see the REL58 routing finding). **AR and MS carry the EN string as placeholders, flagged `retranslate:[ar,ms]`** — both already held fluent translations of the false claim, and a visibly-English placeholder is loud where a fluent lie is silent. **Guard:** a widget test that refuses six phrasings of the old promise and requires the body to name the control that does work; its `reason` line instructs a future editor to change the mechanism first, the test second, the copy last. The invariant the new copy rests on is already pinned backend-side by `test_def060_onboarding_claim_mandate.py::test_claim_does_not_clobber_an_existing_mandate`. **Mutation measured:** restoring the original sentence turns the file 1 RED of 7.
