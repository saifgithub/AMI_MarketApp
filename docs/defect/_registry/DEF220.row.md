| DEF220 | 2026-08-06 | audit | backend | **Six check-then-INSERT sites under a real uniqueness constraint have no `IntegrityError` handler — surfaced by widening the P15 guard, none of them reviewed.** `failure_patterns.md` P15 says a function that SELECTs what exists and INSERTs the rest is correct in one process and raises in two. The guard written for it initially matched call sites **by name** (`upsert_*`), which CR136-M01's round-2 auditor showed enforces a naming convention rather than the pattern: their `AUD-M4` added an unguarded check-then-`session.add` that simply was not called `upsert_*`, and the guard passed. **Widened to the shape** — any function that both reads a model and `session.add`s that same model, where the model carries a `UniqueConstraint`, a unique `Index`, a `unique=True` column, or a **primary key with no default** (the natural-key case, which collides exactly like an explicit constraint; a uuid4-defaulted PK cannot collide and is excluded, which is what keeps the rule from flagging every append-only insert). **What it found, first run:** 21 collidable models, 9 matching sites. One guarded in place (`portfolio_snapshot.py`, M03's original), two guarded at the caller (`price_history.upsert_daily_bars` and `ticker_reference.upsert_reference`, both fixed under CR136-M01 A2 — the handler wraps the call because the commit happens in the caller's `get_session().__exit__`, which is precisely the frame this AST rule cannot see from inside the callee). **The remaining six are unreviewed and are this defect:** `auth_service._upsert_user_device` → `UserDeviceRow`; `lessons_service._check_agent_unlocks` → `AgentActivationRow`; `mandate_store.upsert` → `MandateRow`; `overlay_store.save_new_version` → `OverlayEditCounter`; `reputation_service._award_badge` → `BadgeRow`; `social_context._cache_write` → `SocialSentimentCacheRow`. **Not fixed blind, deliberately.** Each needs its own reachability question answered before a handler is added, and the answers will differ: `_award_badge` and `_check_agent_unlocks` are idempotent-by-intent (a badge awarded twice is a skip), `_cache_write` is a cache whose loser can simply drop the write, and `mandate_store.upsert` writes user-authored state where silently swallowing a lost race could hide a real conflict. Wrapping all six in the same `except IntegrityError: pass` would satisfy the guard and answer none of those questions — the CR040 shape, and the reason P15 asks the handler to **say which outcome it chose**. **Severity is deliberately not higher.** No live failure is known; the same in-process accident that hid CR136-M01's instance (one uvicorn, no `--workers`) covers these too, and CR136-M01's auditor measured **0 races in 60 trials** on this stack. That protection is a deployment fact, not a guard, and CLAUDE.md's Beta stack is **GCP Cloud Run** — instances share no state, so every one of these becomes reachable the day a second instance exists. **Held from regressing meanwhile:** the six are pinned in `_UNREVIEWED` inside `backend/tests/unit/test_p15_check_then_insert_guard.py`, so a **seventh** site fails the build immediately, and a pin left behind after a fix also fails (a stale entry hides the next real one).
