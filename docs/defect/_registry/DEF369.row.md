| DEF369 | 2026-08-25 | claude | backend | **`credit_service.spend()` was a read-modify-write with no row lock — double-spend.** Security review M3, minted and fixed as part of CR123's Medium backlog. `spend()` reads `credit_balance`, compares it to the cost and writes the difference; two concurrent calls that both read the same starting balance both pass the check, and the second write clobbers the first — a user with one credit buys two Rooms. **The review recorded it as latent, masked by a single worker plus await-free callers. DEF205 removed that mask on the same day**: 1-on-1 and Brief now spend through this same function, both are SSE streams, both are reachable 12x/minute per user, and they share a concurrency cap greater than one. The window is real now. **Fix:** `s.get(User, user_id, with_for_update=True)` — `SELECT … FOR UPDATE`, taken BEFORE the balance is read (a lock acquired after the read protects nothing). **Guard:** `backend/tests/unit/test_def369_spend_takes_a_row_lock.py` (5 tests). It asserts the **compiled Postgres SQL** rather than racing two sessions, because the unit suite runs on SQLite where `FOR UPDATE` is silently a no-op — a race test there would pass for the wrong reason or be flaky. Also pins the lock-before-read ORDER, and keeps a negative control so the assertion is known to discriminate. 1/1 mutation killed (removing the lock). | fixed | `backend/app/services/credit_service.py` | AT:R74 |
