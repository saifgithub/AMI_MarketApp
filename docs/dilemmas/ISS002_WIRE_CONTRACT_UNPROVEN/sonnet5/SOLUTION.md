# ISS002 — solution (sonnet5)

Everything referenced below is runnable in this folder:

- `discover_pairs.py` — auto-discovers (endpoint, Dart class) pairs from `mobile/lib/services/api/api_client.dart`. No pair is hand-declared.
- `dart_keys.py` — generalizes `test_wire_contract_parity.py`'s own key-extractor across every file in `mobile/lib/models/`, adds `??`-alternation grouping and one level of nested-list detection.
- `wire_capture_plugin.py` — a pytest plugin that captures every real JSON response any `TestClient` receives during a normal run of `backend/tests/unit/`.
- `compare.py` — the check itself: diffs Dart-read keys against the real captured wire, per discovered pair, recursing one level into nested classes.
- `discovered_pairs.json`, `captured_responses.jsonl`, `compare_report.json` — the actual measured output of a real run against this repository (see §4 for how it was produced and its numbers).

---

## 1. Reading of the problem

The shipped guard (`test_wire_contract_parity.py`) diagnoses its own limit correctly but understates it: it says growing coverage "requires a human to declare each pair," as if the obstacle were labor. It is not. `PortfolioSnapshot.holdings` is `list[dict]` and its keys are written as string literals inside the route body — there is no Pydantic field for `mark`, `value`, `unrealised_pnl` to compare against, ever, no matter how many pairs a human declares by hand. The same is true of every bare-`dict`-returning route (`get_close_payload` and the whole games Close surface). **A schema-based check cannot see a surface that has no schema, and roughly a third of this codebase's response shape is exactly that kind of surface.** So the real defect isn't "nobody declared the pair" — it's that the guard asks Pydantic what crossed the wire, and Pydantic doesn't know, because for these routes it was never asked to type it. The fix has to stop consulting the type system as the source of truth for "what did the server actually send" and consult the wire itself, at the moment code that already runs — the existing test suite — sends and receives it. That reframe is what the rest of this document implements: not a bigger allowlist, not a smarter schema diff, but a shift from *static* to *observed* ground truth, discovered automatically from the one file every wire call already has to pass through.

## 2. The mechanism

**A. Auto-discover the pairs, from the code that has to exist anyway.**
Every mobile network call funnels through `mobile/lib/services/api/api_client.dart` — confirmed by reading it: `simPortfolio`, `simSubmit`, `gamesRunDetail`, all ~85 wire-consuming methods call `_dio.<verb>(...)` and hand the response to some `X.fromJson(...)`. `discover_pairs.py` slices the file into brace-matched method bodies, extracts the URL literal from the `_dio` call and every `X.fromJson(` reachable in that body, and writes `(verb, url_template, dart_class)` triples — **85 of them, on this repository, today, with zero hand-declaration.** This can't go stale by omission the way the old `_PAIRS` list could: a new endpoint call *is* a new entry in this exact file, so discovery and the feature's own existence happen in the same commit.

**B. Capture the real wire, not the type.**
`wire_capture_plugin.py` monkeypatches `starlette.testclient.TestClient.request` — the one method every `.get/.post/...` call in all 92 files that use `TestClient` funnels through — to record `(method, path, status, json_body)` for every request made during a normal `pytest backend/tests/unit/` run. No new tests are written. This captures the *actual* runtime JSON, including everything assembled via `list[dict]` literals and bare `dict` returns, because it operates on real response bytes, not a Python type annotation.

**C. Diff, per discovered pair, unioned across the whole suite.**
`compare.py` matches captured `(method, path)` rows to a discovered pair's URL-template regex, unions every real body observed for that endpoint (different tests reach different branches — an empty portfolio, one with shorts, a resting order, a rejected trade — so the union approximates every shape the endpoint can actually produce), and diffs it against the keys `dart_keys.py` says the paired class's `fromJson` reads. Three refinements over a naive diff:

- **`??`-alternation groups.** `j['run_id'] ?? j['id']` is grouped and satisfied by *either* spelling appearing on the real wire — the deliberate two-lane pattern is never a false positive, but if the server emits **neither**, it still fails.
- **One level of nested-list recursion.** `SimPortfolio.holdings` → `.map((h) => SimHolding.fromJson(...))`: the extractor finds the wire key controlling the list (`holdings`) and the class it feeds, then re-runs the same diff against the *real, captured* list elements — this is the literal DEF365 shape, closed without any schema.
- **Degrade loudly.** A pair with zero real 2xx observations reports `UNVERIFIED`, not `PASS`. The CI step treats `UNVERIFIED` as a build failure exactly like `FAIL` — a surface the mechanism cannot evaluate must not pass silently, which is the brief's own explicit constraint.

**D. Wire it into `/promote-to-alpha`, once, after the suite it reuses.**
This is not a new test file inside `backend/tests/unit/` (that would double the suite's runtime for every local `pytest -q`, which is the wrong place to pay this cost — see §4). It is a separate script invoked once by the promotion gate, immediately after that gate's own mandatory full-suite run, reusing that run's captured responses rather than paying for a second one. Exit non-zero on any `FAIL`/`UNVERIFIED`.

**A complementary, cheaper check the same discovery data makes almost free.** `discover_pairs.py`'s raw `_dio` call inventory (109 call sites, before filtering to the 85 that parse a response) can be matched the other direction — against every registered FastAPI route (`app.router.routes`) — to find backend routes with **no client call site at all**. Run against this repository today, this finds `POST /v1/sim/options/propose` (`ProposeResponse`, in `backend/app/api/options.py`): a fully implemented, documented endpoint with no occurrence anywhere in `api_client.dart`. That is instance #1's exact shape (`OptionProposalTicket` — "shipped with exactly one referencing file: its own test"), and it appears to still be live in this codebase, not merely historical. (The same scan also finds `/v1/coach/*`, which *is* a deliberate, correctly-labeled deprecation shim per its own docstring — proof this check needs the same kind of reasoned-exemption discipline as the main one, not that it's wrong.) I did not fix or file either finding — out of scope for this exercise — but I verified both by reading the source, not by inference.

## 3. The six inventory items

**1. `list[dict]` / `dict` with route-body literal keys (`PortfolioSnapshot.holdings`).**
Solved directly, not worked around: the check never asks Pydantic what `holdings` contains. It reads the real captured JSON, finds the real keys (`ticker`, `quantity`, `avg_cost`, `mark`, `value`, `unrealised_pnl`, `opened_at`, `stop`, `target` — confirmed by reading the actual route body at `backend/app/api/sim.py:491-505`), and diffs those against what `SimHolding.fromJson` reads. This is the one item the shipped guard structurally cannot do at any amount of manual effort, and it is the one this mechanism does by default.

**2. Dart fallback spellings (`j['run_id'] ?? j['id']`).**
Handled by alt-grouping (§2). Measured on this repo: `GameCloseResult` alone has 9 such groups (`run_id`/`id`, `final_rank`/`rank`, `career_points_delta`/`career_point_delta`, three-way groups on the counterfactual fields, etc. — see `dart_keys.py`'s own printed output). Each is satisfied by any one spelling being observed; the check only fires if the server emits none of them.

**3. `?? <default>` masking a missing key as a plausible value.**
The mechanism does not touch, and does not need to touch, Dart's runtime fallback behavior — the app still shows `'draw'` or `'Unnamed'` gracefully, and that's fine. What it changes is that the **key's presence on the real wire is verified independently of whether the client would visibly break on its absence.** `GameCloseDuel.outcome` (`j['outcome'] as String? ?? 'draw'`) is tracked as a required key regardless of the graceful default; if the server stopped emitting `outcome`, the build fails even though no screenshot or manual QA pass would ever show a crash. This is precisely why a presence-diff on the wire, not a behavior check on the running app, is the right lever for this item — a QA pass is structurally blind to a silently-substituted default.

**4. Bare-`dict` routes (`get_close_payload`, the whole games Close surface).**
Solved the same way as item 1, and demonstrated: `GET /v1/games/runs/$runId/close -> GameCloseResult` was auto-discovered (§2A) with zero hand-declaration, and its 16 required keys + 9 alt-groups were extracted purely from Dart source (§3 item 2's numbers are this endpoint). No Pydantic model is consulted anywhere in this path — `get_close_payload`'s return type is `dict`, and the check never looks at it.

**5. Fields that legitimately exist on only one side.**
Handled two ways. **Direction:** only "Dart reads a key the server never emits" is flagged; the reverse (server sends a field Dart never reads) is not checked at all — an unused field is not the silent-breakage class this brief is about. **Within one side, "sometimes present":** handled by unioning real observations across the *entire* suite run rather than one fixture, so a field gated behind a resting-order or short-position branch is only flagged if **no test anywhere** reaches that branch. This surfaced a live, honest example during measurement: a partial 175-test run (sim/games tests only) reported `SimSubmitResult.order`/`.short` as missing, because that subset didn't include the CR170/CR171 resting-order and short-position test files. §4 reports whether the full suite resolves this — the point either way is that the signal is accurate to the branch coverage it was given, not noise.

**6. Newly added fields — "when the class actually strikes."**
This is what `UNVERIFIED` exists for. A field added to a Dart model has zero real observations the moment it's written, and reports loudly, in CI, before merge — not three defects later, found by a human reading code. No one has to remember to declare anything: adding the `_dio` call and the `fromJson` read *is* the act of enrolling the surface (§2A), because that's the only way the feature can exist on the client at all.

## 4. What it costs

**Runtime.** `discover_pairs.py` + `dart_keys.py` + `compare.py` together run in well under a second (measured: `dart_keys.py` indexes 129 Dart model classes, `discover_pairs.py` finds 85 pairs from 109 raw call sites, both sub-second on this machine). The capture hook's overhead on the real suite, and the full-suite `PASS`/`FAIL`/`UNVERIFIED` breakdown, are reported in the addendum below — I ran the actual 5,176-test suite with the plugin attached rather than assert a number, and recorded what happened, including a confounded early measurement I'm not hiding (see the addendum for why one number is flagged unreliable rather than quietly dropped).

**Maintenance.** The per-surface hand-declaration this replaces goes to zero. What remains is: (a) the two lexical extractors staying in sync with the Dart codebase's *style*, not its content — a risk, not a chore, discussed in §5/§6; (b) an `_EXEMPT`-shaped allowlist for the rare case where a real gap can't be closed by writing a covering test (same discipline the shipped guard already uses, kept as the fallback, not the primary path).

**Dependencies.** Zero new ones. `re`, `pathlib`, `json`, `starlette.testclient` (already a transitive test dependency via FastAPI), and the pytest hook API are all already in the stack.

**False-positive rate.** The brief's bar is the ~250-orphan naive sweep. This mechanism cannot reproduce that failure mode by construction: it never pools "every Dart key" against "every Pydantic field." Every comparison is anchored to one specific (endpoint, class) pair from one real call site, diffed only against the exact JSON object that call site's own navigation path produced. Measured on the partial run: 85 pairs, 6 `PASS`, 1 `FAIL` (a real branch-coverage gap, not noise — see item 5), 78 `UNVERIFIED`, 0 spurious `SKIP`s. The full-suite numbers are in the addendum.

## 5. How it fails

- **No value-semantic check.** Two sides agreeing on a key name but disagreeing on meaning (inverted booleans, cents vs. dollars, a sign convention) is invisible — this is a presence check, not a contract-type check.
- **Response direction only.** Client → server payload shape is out of scope. This matches the brief's actual symptom class (all three named instances are server → client), but it's a real boundary, not an oversight.
- **Non-JSON surfaces stay permanently `UNVERIFIED`.** `/v1/room/stream` (SSE) was observed in the capture with `body=None` — the plugin only parses `application/json`. This degrades loudly (never a false `PASS`) but also never resolves; a differently-shaped check is needed for streaming surfaces, out of scope here.
- **Recursion is one level deep, and only for `.map(...)`-shaped lists.** A doubly-nested structure, or a single nested object reached through an intermediate local variable (`final tradeJson = (j['trade'] as Map?)?.cast<...>(); ... SimTrade.fromJson(tradeJson)` — this exact pattern exists in `SimSubmitResult.fromJson`) is not walked by the current code. Extending it is mechanical — trace local-variable assignments the same way `nested_lists` traces `.map()` sources — but I did not build it; I'm naming the gap rather than claiming coverage I don't have.
- **Lexical, not a real Dart parser — and I found a live instance of exactly this failure mode while building it.** An early version of `discover_pairs.py`'s call-site regex required `_dio.get` as one token and silently missed `simPortfolioHistory` and `simHoldingLots`, because those two methods break the line between `_dio` and `.get<...>` (`_dio\n    .get<...>(...)`). It undercounted by 7 of 109 real call sites until I compared its output against a manual `grep` and found the gap. I fixed it (the diff is in `discover_pairs.py`'s own comment), but it demonstrates the class of risk: a lexical extractor is only as good as the style variance it's been shown, and this codebase will keep introducing style variance it hasn't seen. Separately, `dart_keys.py`'s factory-slicing (inherited unchanged from the shipped guard's own accepted tradeoff) misattributed a key read by a free function sitting between two factories (`_duelVerdictFrom`'s `j['beats']`) to the wrong class — a spurious extra requirement, not a missed one, so it only makes the check *stricter* than correct, never looser, but it's still a tax a human has to recognize as an artifact.
- **Degrading loudly means `UNVERIFIED`, not "confirmed correct."** A pair that's `UNVERIFIED` because literally no test reaches the branch that populates it stays `UNVERIFIED` until someone writes that test — correct behavior, but it means the mechanism's first real run against this codebase will likely show a wall of `UNVERIFIED` rather than a clean `PASS` board, and that wall is the honest state of test coverage, not a bug in the check. The addendum reports what that wall actually looks like after the full suite.

## 6. What would have to be true for this to be the wrong choice

- **If the mobile client moves to codegen'd models** (OpenAPI-generated Dart, or `json_serializable`/`@JsonKey` reflection-based parsing) instead of hand-written `j['key']` indexing — the regex extractor stops matching and, worse, **fails silently into an empty key-set rather than an error**, which under the current design reads as "nothing to check" rather than "the check just broke." That's a real regression risk I'm flagging, not dismissing: it needs its own canary (mirroring the shipped guard's `test_the_extractor_is_not_silently_matching_nothing`) before this could be trusted long-term. Generated bindings would also be the *strictly better* fix if the "no serialization-strategy rewrites" constraint is ever lifted — this whole approach is a lexical workaround for a codebase that hand-writes what could be generated, and the brief rules the better fix out of scope, not out of existence.
- **If the `UNVERIFIED` wall stays large permanently** rather than shrinking as tests get written — a standing wall of red that nobody clears trains people to route around it, which is the same "control gets ignored" failure CLAUDE.md already warns about, just relocated from a prompt instruction to a CI check. The addendum's real numbers are the evidence for whether this is a live risk here or not.
- **If promotion-gate latency is a harder constraint than assumed.** `/promote-to-alpha` already blocks on the full unit suite; this rides that run rather than adding a second one, but any capture overhead compounds at exactly the gate a solo founder needs to stay fast. The addendum reports the measured overhead rather than asserting it's negligible.
- **If the actual failure mode was never "no check," but "the check that existed wasn't run before shipping."** All three named instances were found by a human reading code, and the shipped guard already existed before at least one of them — I don't have evidence this is what happened here (CR172's instances read as genuine coverage gaps, not skipped runs), but if it turns out CI wasn't gating merges at all, no smarter test fixes a process that isn't enforced; the fix would be a promotion-gate hook, not a better diff.

## Addendum: full-suite measurement

*(Filled in after the full `backend/tests/unit/` run — 5,176 tests — completed with the capture plugin attached. See `captured_responses.jsonl` and `compare_report.json` in this folder for the raw data.)*

**The run.** `backend/.venv/bin/python -m pytest backend/tests/unit/ -q -p wire_capture_plugin` (via `PYTHONPATH` pointing at this folder — no file inside `backend/` was touched): **5,171 passed, 5 skipped, in 1088.63s (18m08s)** — a clean pass, no test broke by having the plugin attached. It captured **1,280 real JSON responses** across the whole run.

**The check.** `compare.py` against those 1,280 responses and the 85 auto-discovered pairs:

```
85 discovered pairs | 44 PASS   1 FAIL   40 UNVERIFIED   0 SKIP
```

- **0 false positives.** Every `PASS`/`FAIL` is traceable to a real captured object, and the one `FAIL` is a true positive (below) — not the ~250-orphan noise the naive sweep produced. This is the direct, measured answer to the brief's false-positive bar, not an estimate.
- **The one `FAIL` is real, and it's a genuine gap.** `SimSubmitResult.order` — read by the Dart client, defined on the wire only when a submit rests instead of filling — was never observed once in 21 real `/v1/sim/submit` responses across the *entire* 5,176-test suite (confirmed by re-querying the capture directly: 22 total responses, 0 with `resting: true`, 0 with a non-null `order`). CR170 shipped the resting-order feature; nothing in this suite currently drives `POST /v1/sim/submit` through `TestClient` far enough to rest an order and observe the field the client depends on. That is a live, currently-open version of exactly the class this Dilemma is about, found by running the mechanism, not asserted from reading code.
- **The DEF365 field is still HTTP-untested, one recursion level down.** `SimPortfolio.options` (nested via `.map()` into `SimOptionLeg`, §2C) reports `UNVERIFIED`: across 25 real `GET /v1/sim/portfolio/{id}` responses, `holdings` was populated once, `shorts` 8 times, `closed_shorts` 4 times — and `options` **zero** times. CR172 fixed the defect (the field exists and is populated by `sim_engine`, confirmed by reading `backend/app/api/sim.py`), but no test in this suite drives an actual HTTP portfolio fetch against a portfolio holding an open option structure. The mechanism can't tell "fixed but untested at the wire" from "still broken" — correctly, because from the wire's perspective they look identical — and reports the honest state instead of a false `PASS`: this is `degrade loudly` doing its job on the exact surface DEF365 was about.
- **40 `UNVERIFIED` overall, not 0.** That's the real shape of this codebase's HTTP-level (not service-level) test coverage today, not a flaw in the check — most of `backend/tests/unit/` calls service functions directly rather than routing through `TestClient`, so many discovered endpoints (`AgentUnlockRequirement`, `LessonStatus`, `MergeResult`, several `games` surfaces, etc.) simply were never hit as HTTP requests in this run. Wiring this into `/promote-to-alpha` would turn this into a hard gate the first day, and would require either exercising these endpoints via `TestClient` in existing tests (many already do, just not through the client-consuming shape) or explicit, reasoned `_EXEMPT` entries — real, visible, up-front work, not a silent gap.

**Overhead, measured cleanly (not the earlier CPU-contended number).** Re-run in isolation, with nothing else competing for CPU: the `sim`/`games` subset (175 tests) ran in **15.46s without the plugin, 14.79s with it** — no measurable overhead, the difference is within ordinary run-to-run noise. An earlier same-subset comparison (26.6s → 34.4s, ~29%) was confounded by the full 5,176-test capture run competing for CPU on the same machine at the same time; I'm reporting both numbers rather than deleting the bad one, and trusting the clean, uncontended pair. I did not re-run the full 5,176-test suite a second time *without* the plugin to get an exact full-suite delta (that's another ~18 minutes) — the honest gap in this measurement is that the full-suite marginal cost is inferred from the clean subset result, not independently confirmed at full scale.

**Reproducing this.** `python3 discover_pairs.py`, then from `backend/`: `PYTHONPATH=<this folder> backend/.venv/bin/python -m pytest tests/unit/ -q -p wire_capture_plugin`, then `python3 compare.py` from this folder. `python3 find_orphan_routes.py` (run the same way from `backend/`) reproduces the complementary orphan-route finding in §2D — 34 routes with no client call site, including the live `POST /v1/sim/options/propose`.
