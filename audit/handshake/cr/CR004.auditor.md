## Findings

### F1 — MAJOR (reproduced) · streak-milestone credits re-granted under the daily cap
`backend/app/services/reputation_service.py:155-167` + `:262-285`

`_grant_milestone()` grants credits **unconditionally** once its
`_already_awarded` guard passes, but that guard relies on a `reputation_events`
row that `award()` **declines to write** when the daily cap is already exhausted
(`remaining <= 0` returns at line 156-157, *before* the INSERT at line 160). So
when a milestone award is clipped to a zero-write, its guard row never persists,
and its credit grant re-fires on **every subsequent `streak()` call** —
`GET /v1/league/me` runs `rep.streak()` on every league-screen load
(`api/league.py:69`), inside a `get_session()` that commits.

**Reproduced** by `audit/handshake/regression/test_streak_milestone_cap_pin.py`:
two league-screen loads for a 100-day-streak user →
`credit_balance 130 -> 230 (+100)`; the captured log shows
`streak_milestone_granted credits=100 milestone=100` **twice** while
`reputation_awarded event_type=streak_100` **never** appears. Unbounded: each
refresh grants another 100 credits until a day the award finally writes.

- **Guaranteed case:** `streak_7(10)+streak_30(25)+streak_100(50) = 85 > 25`/day
  cap, so streak_100 is always clipped to zero-write on the day all three fire.
- **Reachable-in-alpha generalization:** the bug hits **any** crossed milestone
  (incl. streak_7) whenever the day's 25-pt cap is already consumed by normal
  activity (2 lessons + a few challenges) *before* `streak()` runs — that is
  reachable now, not only at a 100-day streak. Economic exploit on a **monetized
  currency** (credit packs are sold). Trends BLOCKER on impact; classified MAJOR
  because no current alpha user is known to have triggered it and streak_7's
  per-refresh amount is small — but it must be fixed before any user reaches a
  milestone under a capped day.
- **Fix direction (architect's call):** decouple the once-ever milestone grant
  from the point-cap write — e.g. write the `streak-{milestone}` guard row
  unconditionally (even at 0 points when capped), or gate the credit grant on
  `award()` having actually recorded the ref. The pin will pass once fixed.

### F2 — MINOR · `reputation_events` has no DB unique constraint on its dedup anchor
`backend/alembic/versions/c3d4e5f60014_reputation_league.py:37-54`

The `(user_id, event_type, ref_id)` dedup is enforced **only** in app code
(`_already_awarded` SELECT, `reputation_service.py:222-231`). No partial unique
index → two concurrent same-`ref` awards can both pass the SELECT and double-
insert, and there is no defense-in-depth behind the app check. Recommend a
partial unique index `(user_id, event_type, ref_id) WHERE ref_id IS NOT NULL`.
(Would not by itself fix F1 — F1's row is never written at all — but hardens the
dedup contract the whole engine leans on.)

### F4 — MINOR · challenge-attempt check-then-insert is not atomic; IntegrityError uncaught
`backend/app/api/daily_challenge.py:159-176`

`existing is None → s.add(DailyChallengeAttemptRow(...))` is not atomic across
concurrent requests. Data is safe (the `UNIQUE(user_id, challenge_id)` backstop
prevents a double attempt), but a concurrent double-submit of the same challenge
raises `IntegrityError` on the second commit, which is **uncaught** → 500 rather
than the intended graceful `already_attempted=True`. Narrow race; UX-only.

### F5 — OBSERVATION · merge mid-week doesn't re-sum orphan's in-week league points
`backend/app/services/merge_service.py:221-250`

The merge re-keys `reputation_events` and sums the orphan's **lifetime**
`reputation` into the adopter, but does **not** recompute the adopter's current
`league_members.points` (the in-week passthrough is only updated at `award()`
time). A mid-week account claim could undercount the adopter's current-week
league standing. Lifetime reputation is correct; edge case.

### F6 — OBSERVATION · weekly_roll concurrent-call duplicate cohorts (theoretical)
`backend/app/services/league_service.py:126-144`

Two concurrent `weekly_roll()` calls could both pass the `exists is None` check
and both assemble (no unique constraint on `leagues.week+tier`). Very low risk
given the single-container hourly lifespan tick; noted for completeness.
