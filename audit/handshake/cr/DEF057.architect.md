# DEF057 — audit lane (architect)

**Item:** DEF057 — `room_runner.py::_profile_for_ticker()`'s docstring promises a
"deterministic synthetic baseline," but seeded its rng off Python's builtin
`hash(ticker.upper())` — `str` hashing is randomized per process
(`PYTHONHASHSEED`) unless explicitly pinned, so the same ticker produced a
different synthetic profile on every process restart, contradicting the
function's own documented intent. Found by track U auditing DEF056
(`DEF056.auditor.md` observation O2) — pre-existing from the CR024 era, unrelated
to DEF056 itself. Surfaced as `test_social_media_mention_trend_varies_by_ticker`
flaking under an unlucky randomized default test-process hash seed (6 tickers
coincidentally collided on the same `rng.choice` outcome for that seed; passed
reliably at seeds 0-5). Register:
[`docs/defect/def_list.md`](../../../docs/defect/def_list.md) DEF057. Full spec:
[`DEF057_room_profile_rng_not_actually_deterministic.md`](../../../docs/defect/DEF057_room_profile_rng_not_actually_deterministic/DEF057_room_profile_rng_not_actually_deterministic.md).

**depends-on:** none. Same file DEF052/053/CR034/DEF056 touched this session
(`room_runner.py`) but an independent, unrelated code path (`_profile_for_ticker`'s
rng seed, not the technicals/fundamentals overlays or the PM verdict flow).

**Head SHA:** `b0c85a2`.

## What was done

One-line fix: `rng = random.Random(hash(ticker.upper()))` →
`rng = random.Random(zlib.crc32(ticker.upper().encode()))`. `zlib.crc32` is a
stable, non-randomized 32-bit hash — same ticker, same seed, in any process,
forever. `zlib` is stdlib, no new dependency. Single call site in the module;
grepped to confirm no other code seeds off `hash(ticker)`.

Not a production correctness bug in the sense of user-facing harm — the
profile's narrative fields (`sentiment_score`, `mention_trend`, etc.) are
already explicitly synthetic/illustrative, so no contract depends on a
*specific* per-ticker value surviving a restart. The bug is real, though: the
code's own docstring claims determinism it didn't have, and the practical
symptom (test flakiness under an unpinned hash seed) is a genuine CI-hygiene
issue that would otherwise resurface unpredictably in future sessions/audits.

## Why this is safe / minimal

- **Single call site, single-line change** — no other logic in
  `_profile_for_ticker` or elsewhere depends on the specific seed source, only
  on it being *a* deterministic function of the ticker string (which it now
  actually is).
- **No existing test asserted an exact value derived from the old `hash()`-seeded
  output** — checked directly: every existing `_profile_for_ticker` test either
  compares two calls for the same ticker (still equal under the new seed,
  since `crc32` is deterministic per-ticker too) or asserts a field's shape/
  range, never a hardcoded literal tied to the old seed. Nothing broke.
- **Zero behavioral change to what the LLM sees in production** beyond which
  specific illustrative value it's given — the fields were already disclosed
  as synthetic/illustrative in the prompt; this doesn't change what's
  disclosed, only makes the underlying value stream actually stable across
  restarts as documented.

## Tests run (self-test)

- **Adversarial confirmation, 9 explicit `PYTHONHASHSEED` values**
  (`0,1,2,3,4,5,42,1337,999999`): `test_social_media_mention_trend_varies_by_ticker`
  passes at every one — previously seed-dependent (per the auditor's own
  report, failed at the default randomized seed, passed at 0-5), now
  seed-independent by construction.
- **New `test_profile_for_ticker_rng_seed_is_hash_seed_independent`**: pins the
  exact expected `base_price` (`408.14`) and `pe` (`"53.3"`) for `"AAPL"` under
  the `crc32`-seeded implementation. A `hash()`-seeded implementation would
  need a specific, unlikely `PYTHONHASHSEED` to reproduce these values by
  chance, so this pins the fix rather than merely re-asserting same-process
  consistency (which would have passed before the fix too, since `hash()` is
  stable *within* one process).
- **Adversarial self-check against the reverted code**: temporarily restored
  the pre-fix `hash()`-based seeding (kept the new test in place), re-ran —
  **failed** (`assert 271.74 == 408.14`, confirming the test actually exercises
  the fixed code path, not a vacuous assertion). Restored the fix, re-ran green.
- `pytest backend/tests/unit/ -q` → **742 passed** (741 → 742, +1 exactly).
