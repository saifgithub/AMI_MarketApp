# DEF049 — audit lane (architect)

**Item:** DEF049 — **monetized-currency credit double-grant under concurrency**. Minted from the
DEF039 round-1 audit's OUT-OF-SCOPE finding **O1**. `reputation_service._grant_milestone` granted
streak-milestone credits **unconditionally**, without checking whether *its* `award()` call actually
wrote the guard row. After DEF039 added the partial-unique index + `IntegrityError`→rollback→return-0
to `award()`, a concurrent same-milestone race-loser rolls its guard-row insert back yet still ran
`user.credit_balance += credits` → a one-time double credit. Register:
[`docs/defect/def_list.md`](../../../docs/defect/def_list.md) DEF049.

**depends-on:** DEF039 (this bug only manifests *because* DEF039's rollback landed; the fix is on top
of it).

**Head SHA:** `58bf138`

## Why the obvious fix is wrong (and what was done instead)

The DEF039 auditor suggested "gate the credit grant on `award()` returning > 0." **That reopens F1.**
A legitimately cap-clipped milestone (`always_record=True`, daily cap exhausted) returns **0 with the
guard row written and credits owed** — the exact scenario `always_record` exists for. Gating on
`> 0` would skip credits there. The only correct signal is "did *this* call write the row, or roll
back?", which is distinct from the points value.

| Piece | Change |
|---|---|
| service | `app/services/reputation_service.py` — new private `_AwardRaceLost` exception + opt-in `_raise_on_race: bool = False` param on `award()`. On the `IntegrityError` path, if `_raise_on_race` is set, `award()` rolls back then **raises** instead of returning 0. `_grant_milestone` passes `_raise_on_race=True` and wraps the call in `try/except _AwardRaceLost: return` — so a race-loss skips the credit grant. Every other caller keeps the default (return 0 on race), behaviour identical. |

## Why this is safe / minimal

- **F1 stays fixed:** a cap-clipped milestone raises **no** `IntegrityError` (the guard row is a
  genuinely-new `(user, event_type, ref_id)` — unique index not violated), so `award()` returns 0
  normally, no exception, credits granted. Only a true concurrent duplicate raises.
- **Blast radius bounded:** `_raise_on_race` defaults False; the 8 other `award()` call sites are
  untouched. Only `_grant_milestone` opts in.
- **No schema change**, backend-only.
