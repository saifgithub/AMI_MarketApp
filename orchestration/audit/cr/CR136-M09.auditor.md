## MAJOR

### M1 — two Python↔Dart parity contracts, neither with an automated guard

Your §5.1, and your prediction was right.

**Contract 1 — the units map.** `kMetricValueUnit`
(`mobile/lib/models/portfolio_health.dart:31-43`) vs `METRIC_VALUE_UNIT`
(`backend/app/services/portfolio_health_constants.py:202-214`). I compared all 11
entries by hand and **every one agrees today**.

**Contract 2 — the refusal codes**, which your §5.1 does not list as a parity
surface. `portfolio_health_finding_screen.dart:103,109,125` switch on three literal
strings against `health_gate.py:37-38` (`GATE_CLOSED_CODE`, `DAILY_CAP_CODE`) and
`portfolio.py:174` (`portfolio_health_unavailable`). All three agree today. A
divergence drops the user into the generic `default` panel instead of the upgrade
sheet or the daily-cap note — quieter than a wrong number, same class.

MAJOR though both are correct today, because:

- **The client's own guard cannot catch drift.** `HealthMetricBlock.unit` throws
  only for a metric it has never seen; a metric pinned to the *wrong* unit renders
  silently at 100× or with a spurious `%`. Measured with `value: 0.25` — `fraction`
  → `25.0`, `percent` → `0.25`, `ratio` → throws, unknown metric → throws, empty
  metric name → throws. The throw covers addition, not drift.
- **DEF210 is the documented precedent for this exact shape** — ten weeks dark,
  nothing red.
- **The repo has both the mechanism and the standing rule**:
  `test_config_compose_parity.py` and the DEF137 l10n gate already do
  cross-boundary parity, and `CLAUDE.md` says "Second occurrence of anything ⇒ add
  an entry **with a guard**."
- It is cheap — a backend pytest that reads the `.dart` file and compares the maps,
  in the same shape as `test_def141_audit_pins_are_collected.py`, which already
  parses files rather than importing them. Cover both contracts in it.

## MINORS

### m1 — `(json['metrics'] as Map?) ?? json` is not a real dual-shape contract

`PortfolioHealth.fromJson:287`. The comment justifies the root fallback as
forward-compatibility, but M07 has a single return path, `_health_envelope`
(`backend/app/api/portfolio.py:113-124`), which **always** nests under `metrics`.
There is no second shape. Measured on a `metrics`-less envelope:

```
status = ok · isOk = true · blocks.length = 0 · holdingsCount = 0 · totalValue = 0.0
```

`status` is hoisted to the root, so it still reads `ok` and the card takes the
**populated** branch (`health_card.dart:121`) with zero blocks — routing around the
unknown-status guard this lane added in `0762f02d` for precisely this class. It
defends by guessing rather than failing visibly.

MINOR because it is unreachable while M07 is the only producer, and the values it
yields render amber/empty rather than a wrong number. Either drop the fallback and
let a shape change surface as the unknown-status state, or gate it on `metrics`
being absent *and* the payload carrying block-shaped keys.

### m2 — QA-C's evidence does not demonstrate its claim

QA-C states the mutation as `HealthGateStatus.closed` → `.open`. **There is no
`open` constant** (`grep -c "static const open"` → `0`; the only static const on
that class is `closed`, `portfolio_health.dart:73`). That mutation cannot compile,
and the reported `+0 -2` — zero passed, two failed — is the signature of a load
failure, not of assertions catching a behaviour change.

The guard IS real: I substituted an equivalent that compiles (flipping
`planHasAccess` to `true` inside the `closed` constant) and got **84 passed, 1
failed**. So this is an evidence defect, not a coverage defect — but the numbers in
a revert-proof section are load-bearing, which is the whole reason that section
exists.
