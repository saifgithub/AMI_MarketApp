# DEF094 — audit lane (coder.api submission)

SUBMITTED: round 1

**Item:** DEF094 — the Sharia verdict is computed, enforced, and never sent to the client.
`ComplianceResult.sharia_verdict` (`backend/app/schemas/trade.py:91`) existed and was populated by
the safety-floor resolver, but `sim.py`'s hand-built response dicts dropped it on every trade —
including the **accepted** path, which carried no compliance block at all. Acceptance:
`docs/defect/DEF094_sharia_verdict_never_reaches_the_client/DEF094_sharia_verdict_never_reaches_the_client.md`.
Assign: `orchestration/dispatch/lanes/DEF094.assign.md`.

**Code branch:** `lane/DEF094.coder.api` @ **`b02c5dc`** (based on `main` @ `6b24833`).

**GATE: independent** — the wire that carries a religious observance disclosure to a user, D-5;
DEF084's exact surface one layer out.

## Fix shape (1 prod file + 1 test file, `backend/app/api/sim.py`)

1. **`preview_trade`** — added `response_model=PreviewTradeResponse` (new `PreviewTradeResponse` /
   `ComplianceBlock` Pydantic models). `ComplianceBlock.sharia_verdict: ShariaVerdict | None`
   registers `ShariaVerdict` in the generated OpenAPI (the assign's test 3) — previously the route
   returned a bare `dict`, which FastAPI cannot type into a response schema at all.
2. **`submit_trade` rejected path** (`return {"ok": False, "compliance": {...}}`) — added
   `sharia_verdict` to the hand-built dict, `model_dump(mode="json")` or `None`.
3. **`submit_trade` accepted path** (`return {"ok": True, "trade": ...}`) — this is the defect's
   headline case: previously **no compliance block at all**. Now returns
   `{"ok": True, "trade": ..., "compliance": {passed, violations, blocked_by, sharia_verdict}}`.

Kept `submit_trade`'s existing two-shape dict return (no response_model — `ok:True` vs `ok:False`
have different keys; a Union response_model was scoped out as unnecessary surface for a ~2-line fix
per the assign). `preview_trade` alone carries the typed model since its shape never branches.

**Key names match CR069-MOBILE's fixture exactly** (verified against
`mobile/lib/models/sim.dart:228-248` and `mobile/lib/models/sharia.dart:86-95`, not assumed):
`compliance.sharia_verdict.{status, ticker, standard, source, as_of}`. No `mobile/**` touched.

## Adversarial angles worth probing

- **The accepted path is the one that was dark.** Confirm a PASS *and* an UNKNOWN ticker both
  submit successfully (`ok: True`) and their `compliance.sharia_verdict.status` differ — the
  regression the defect names explicitly (AAPL vs ASML byte-identical bodies).
- **UNKNOWN must never block.** `test_submit_accepted_unknown_ticker_is_permitted_and_discloses`
  asserts `ok: True` + `status: "unknown"` together — if either flips, G3 is broken from either
  direction (silent pass vs. false rejection).
- **UNAVAILABLE (paused source) still discloses on the block.** Covered on `preview` only
  (`test_preview_unavailable_pauses_and_carries_the_verdict`) — the assign only requires "each of
  the four states" once, not on every route; SCREENED_OUT and PASS are each covered on both routes.
- **`classification_verdicts` (DEF061's parallel field) was NOT touched** — out of this defect's
  scope (assign names `sharia_verdict` only); worth confirming it isn't a second dark field the
  auditor expects fixed here versus tracked separately.
- **OpenAPI claim is checked structurally, not just described:** the hand-off's evidence section
  below shows the actual schema ref, not just "should work."
