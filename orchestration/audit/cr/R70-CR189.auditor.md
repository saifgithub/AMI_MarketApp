## The blend — arithmetic checked by hand, not read off the docstring

`blended_bracket` (`trading_math/order_pricing.py:272`), all three documented
cases recomputed independently:

| book | rule says | I compute |
|---|---|---|
| 10 @$100 stop $95 + 10 @$110 stop $99 | $97.00 | (95·10 + 99·10)/20 = **97.00** ✓ |
| 10 @$100 stop $95 + 10 @$110 **no stop** | $95.00 | (95·10)/10 = **95.00** ✓ |
| no stop + no stop | none | `stop_den = 0` → **None** ✓ |
| *(the rejected alternative)* zeroing the unbracketed lot | $47.50 | (95·10 + 0·10)/20 = **47.50** ✓ |

The $47.50 counterfactual is exact, which makes the excluded-not-zeroed
argument land: zeroing protects nothing, dropping deletes a control the user
set by hand, excluding carries it. Stop and target accumulating over
independent denominators is right and is tested
(`test_stop_and_target_are_averaged_over_their_own_contributors`).

work and was worth flagging as the one to attack first.**

## The thing you asked me to look at

*"a $110 lot and a $95 lot exiting together at $97 record a loss and a gain
respectively, and `_apply_sell_row`'s clamp still holds when the second lot
draws against a holding the first already reduced."*

`test_each_lot_realises_against_its_own_entry_on_a_shared_trigger` covers
exactly this and its arithmetic is right:

- lot 1: 10 @$100, 6 sold earlier → **4** left; exit $94 → (94−100)·4 = **−24.00** ✓
- lot 2: 10 @$110, unprotected on its own; exit $94 → (94−110)·10 = **−160.00** ✓
- position stop = $95.00 — only lot 1 carries one, so this *is* the
  "protection carried across the whole position" case doing its job ✓

And it is load-bearing rather than decorative: it went red under one of the
LEDGER-lane mutations I ran (`_open_quantity_by_lot` returning the ticker
total), so it genuinely pins per-lot attribution rather than restating the
blend.

## One thing this lane got right that the LEDGER lane got wrong

Your line here — *"weighted by `quantity_open` … makes a sold-out lot weigh
nothing — **DEF318 restated as arithmetic rather than enforced as a second
gate**"* — is exactly correct, and it is the mechanism I ended up proving
from the other direction. Reverting DEF318's per-lot gate leaves the
dead-lot scenario safe *because of this weighting*, which is why that lane's
QA table names a test that never fires. The design is right here; the
attribution is wrong there. Worth noting so the LEDGER fix does not
"correct" this lane by adding a gate it does not need.
