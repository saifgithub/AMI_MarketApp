### The question this lane has to answer

Saiful's rule: "an outage never costs the user. The user sees 'desks unreachable — not
charged'." So the acceptance question is not just "is `refund()` called". It is whether the
user's balance nets back to what it was before the charge, on every path a Room can take to
the outage verdict, and whether "wasn't charged" is only ever said when that is true.

### What holds

- **Scope.** The refund is keyed on the sentinels, not on `action`. CR098's withheld-analyst
  NO_VERDICT and a normal verdict stay charged, and the lane's tests cover both.
- **One predicate.** `run_was_refunded` decides both the refund and the `done` event's
  `refunded`. I read `api/room.py:367`.
- **No double refund with DEF425.** The refund sits after `status = COMPLETED` is persisted,
  and `_sweep_stuck_runs` selects only `running`, so the two paths cannot both fire.
- **The DEF059 PASS follow-up.** The prefix match still requires `overridden_from_llm`.

### MAJOR-1 — a respawned Room refunds the plan's base price, not what it charged, then says "wasn't charged"

`start_run` charges `base + surcharge` when the live-data bundle is entitled
(`room_runner.py:5034`) and passes that as `credit_cost=charged_total`. DEF425's startup
respawn re-enters `self.run()` at `room_runner.py:4796` **without** `credit_cost`. `run()` then
falls back to `room_cost_for_plan(plan)` (`:5397`), and `_persist_run` overwrites
`row.credit_cost` with that base price (`:4324`). DEF432's refund uses `run.credit_cost`, so on
that path it gives back the base price only.

The probe charged 12 (a Trader live bundle), then ran an outage Room through `run()` in the
respawn shape, with no `credit_cost`:

```
PROBE plan_base=8 charged=12 before=150 after=146 net_cost=4 incomplete=True
      reason_tail="... This Room wasn't charged."
```

The user is 4 credits down and is told the Room wasn't charged. The same fallback would
over-refund if the plan's price rose between the charge and the respawn, for example when a
trial ends. The root is older than this lane: the respawn has never carried the charge, and
CR039's failure refund reads the same field. But DEF432 is the lane that puts "wasn't charged"
in front of the user on this path. Respawns happen on every deploy that restarts
`ami_api_alpha` mid-convene, which is DEF425's own scenario.

**Fix direction:** pass `credit_cost=row.credit_cost` from the persisted row into the respawn's
`self.run(...)`. The row already holds the real charge until `_persist_run` overwrites it. Add
a test: a respawned outage Room with a charge above the base price nets to zero.

### MINOR-1 — a failed refund still tells the user they weren't charged

The "This Room wasn't charged." suffix is written into the verdict reason when the verdict is
assembled, before `refund()` runs. `run_was_refunded` reads that verdict, not the ledger. I made
`refund` raise:

```
room_outage_refund_failed credits=8 error='db down'
PROBE2 net_cost=8 says_not_charged=True
```

So the user is charged 8. The verdict, and the Journal entry built from it, say "wasn't
charged", and `done` reports `refunded: true`. The failure is logged, which is loud to us but
silent to the user. It needs a DB fault at exactly that point, so it's minor. It is still the
"report drifts from what happened" class that `run_was_refunded` was built to close; the
predicate only closed the drift between decision and report. Either attach the suffix only
after `refund()` returns, or record the refund outcome on the run and have the predicate read
that. CR039's failed-run refund has the same shape, and that's pre-existing.

### On the attack surface

4. Banking the outage verdict in the calibration ledger is the right call: count it, don't
