# DEF131 — audit lane (auditor)

`AWAITING_AUDIT` on the architect's board and does not exist on an auditor's separate checkout.

**Gate:** independent — and the Architect is right that I should be suspicious on principle: this
changes **my own instrument**. I have treated it accordingly.

**Audited SHA:** `821f54f` on `main` (Architect-executed, no coder lane). Isolated worktree
`.claude/worktrees/audit-DEF131/`, created detached at that SHA. Scope reproduced: **6 files,

## MAJOR 1 — the fix does not guard the submission side on the board the architect actually reads

This is the finding, and it is measured, not read. I rebuilt the DEF131 incident in **two clones**:
the architect commits `SUBMITTED: round 1` and does not push.

| Where | Board | Shows |
|---|---|---|
| **Architect's clone** | **`dispatch.sh state`** — the board they read | **`ASSIGNED`. No `UNPUSHED`.** `inbox` exits **0** ("nothing to integrate") |
| Architect's clone | `watcher.sh state` | `UNPUSHED` ✅ |
| **Auditor's clone** | `watcher.sh state` | **`(no lanes yet)`** — the item does not exist |
| Auditor's clone, after the push | `watcher.sh state` | `AWAITING_AUDIT` ✅ |

`watcher.sh`'s new check on the **architect** file (`$a`) can only fire in the clone where the file
is unpushed — the architect's. And `watcher.sh` is the **auditor's** instrument; the architect polls
`dispatch.sh inbox`, which is what Saiful told them to use and what the bridge says they were
diligently polling. In `dispatch.sh`, `$s` (`<ITEM>.architect.md`) is opened **only** to read
`sub_round` — `grep -n 'unpushed \|undelivered ' dispatch.sh` shows both are called on `$u` alone.

**So the exact scenario that produced DEF131 still shows a clean board to the person who caused it,
and still shows nothing at all to the person waiting for it.** What the fix *does* close is the
mirror image — an auditor who commits a verdict and fails to push — which is real and worth having,
but it is not this defect.

Fail-open, on the item's own acceptance. **MAJOR** by calibration and by "doubt resolves toward
MAJOR"; there is no doubt here.

**The remedy is small** and symmetric with what is already there — in `dispatch.sh`'s `lane_state`,
run `undelivered "$s"` / `unpushed "$s"` alongside the existing `$u` checks and surface the result as
its own loud state, so `needs_architect` and `inbox`'s exit-1 set catch an undelivered *submission*
the same way they now catch an undelivered *verdict*.

## MAJOR 2 — the root cause does not survive checking, and the real cause is unfiled

The bridge and the commit message both state as observed fact that two lanes waited hours **because**
12 commits stayed local, that the auditor "truthfully reported nothing to audit", and that "pushing
produced a `DEF120` `COMPLETE` within minutes". I am the auditor in that account, and the timestamps
do not support it:

| Evidence | Time |
|---|---|
| `b696ef9` DEF120 r4 submit — **committed locally** | 02:07 |
| `7982e36` CR098-MOBILE-LIVE submit — committed locally | 02:11 |
| I read `git log`, found **both**, and opened the queue | **09:52** |
| I created the DEF120 audit worktree and began | **09:53** |
| `refs/remotes/origin/main` reflog — the backlog **push** | **09:57** |
| My `DEF120` `COMPLETE` committed | 10:02 |

**I started auditing four minutes before the push, from the same physical checkout
`/Volumes/Extreme Pro/AMI_MarketApp`.** The correlation in the bridge is real; the causation is
inverted. The lanes were visible to me in `git log` from 02:07 onward and unpushed-ness never
prevented me from seeing them.

The actual reason they sat is in my own run-76 report, written before I saw this lane: **my
background watcher died at 00:11** with the previous process teardown. Its output file stops at the
startup line — no lane, no exit-3 timeout, no error. A dead watcher is **indistinguishable from an
empty queue**, which is why my checkpoint memo said "queue is EMPTY" (true at 00:11, wrong by 02:07)
and why I reported nothing pending. `watcher.sh state` reported both lanes correctly the entire time;
nothing was polling it.

**Why this is MAJOR and not a note.** The registers are this project's memory. A defect closed
against the wrong cause means the outage class reads as handled when it is not — the DEF038/DEF063
shape in the orchestration layer, which is precisely the class this lane invokes. Concretely: the
next time the watcher dies silently, both boards will be green, `UNPUSHED` will be absent, and the
queue will sit again exactly as it did today.

**To be scrupulous about what I have and have not shown.** I have not shown that the unpushed window
harmed nobody — if Saiful was relaying a *different* auditor instance on a separate clone, the push
gap genuinely blinded it and the fix is exactly right for that topology. What I have shown is that
the confirmation the bridge offers ("pushing produced a `COMPLETE` within minutes") is not evidence
for the causal claim, and that for the auditor working this repository the cause was elsewhere.

**What closes this:** correct the causal record in the bridge and the register row, and file the
liveness gap — a watcher that exits without a verdict, a timeout, or a trace, and a queue-check that
therefore cannot distinguish "nothing waiting" from "nobody looking". I am not asking for that fix in
this lane; I am asking for it to exist as an item, because right now it does not.

## MINOR — "staleness can only over-report" is false in one constructible case

The Architect invited exactly this: *"If you think a stale ref can produce a false GREEN, that is a
MAJOR and I want it."* I constructed one, so the unqualified claim in the comment is wrong — but the
construction is narrow enough that I am grading it MINOR, not MAJOR, and saying why.

**T7c**: after a genuine push, a second clone rewrites remote history so the file's commit no longer
exists on the remote (`git reset --hard` + `push --force`). The local tracking ref still contains the
sha, `merge-base --is-ancestor` passes, and the board reads **`AWAITING_AUDIT` for a submission that
is not on the remote at all** — measured, `file commit on remote? 0`.

MINOR rather than MAJOR because the trigger is a force-push that rewrites shared history, which this
project explicitly forbids (`CLAUDE.md`: "Don't proactively run destructive commands (force push,
reset hard…)"), a single `git fetch` corrects it, and I could construct **no other** false GREEN —
ordinary staleness (T7b) behaves exactly as claimed. The fix is to the sentence, not the code:
*staleness from someone else's push can only over-report; a rewritten remote can under-report until
the next fetch.*

## Recorded, not scored

- **T8**: with a relative `HANDSHAKE_CR_DIR` the absolute-path assumption breaks and `git log -1 --
  <file>` returns nothing, which `unpushed()` treats as silence — fail-open. It never surfaces
  because `undelivered()` runs first and its `ls-files --error-unmatch` fails **closed** to
  `UNCOMMITTED`. Correct by ordering rather than by construction; worth knowing if that order ever
  changes.
- **The `git log -1 --format=%H -- <file>` choice is right**, and I tried to break it: amended
  commits, reverts and later unpushed edits all move the sha off the remote ref and report
  `UNPUSHED`. The commit-identity check is stricter than a content diff would have been, in the safe
  direction.
- **No-fetch-on-poll is the correct call** and I am not arguing with it. A board read that does
  network I/O every 30s would be a worse defect than the one being fixed.
