# DEF062 — audit lane (coder.api)

**Item:** DEF062 — `PATCH /v1/mandate/{user_id}` took `updates: dict[str, Any]` with no
request schema, and `MandateStore.patch()` merged it via `current.model_copy(update=updates)`,
which Pydantic v2 explicitly skips validation for. `max_drawdown_pct` (declared
`Literal[10, 20, 30, 50, 100]`) and `risk_score` (declared 1-5), plus every enum field, could
be persisted out of range/type with no error. `max_drawdown_pct` specifically feeds a raw
numeric comparison inside the safety floor's deterministic `check_mandate_compliance()`.
Register: [`docs/defect/def_list.md`](../../../docs/defect/def_list.md) DEF062 row.

**depends-on:** none. `safety_floor.py` NOT touched — DEF084-BE landed on main before this
lane branched (rebased on `4a87312`); confirmed no conflict, frozen surface untouched.

**Head SHA (this branch):** see `git log -1` on `coder.api-DEF062` at push time.

## What was done

- `backend/app/services/mandate_store.py::MandateStore.patch()` — after building the
  shallow-merged `Mandate` via `model_copy(update=updates)` (which skips validation), the
  result is now re-validated through the full schema:
  `Mandate.model_validate(merged.model_dump(mode="json"))`. Any update that would produce a
  schema-invalid `Mandate` (bad `max_drawdown_pct`, bad `risk_score`, wrong enum, wrong type,
  etc.) now raises `pydantic.ValidationError` before the row is ever persisted.
- `backend/app/api/mandate.py::patch_mandate()` — catches `ValidationError` from
  `store.patch()` and turns it into `HTTPException(422)`, matching the existing 422
  convention used elsewhere in the API (`app/api/sim.py:440`). Without this the route would
  have surfaced a raw 500.
- `backend/tests/unit/test_def062_mandate_patch_validation.py` (new) — guard tests:
  - `test_patch_rejects_out_of_range_max_drawdown_pct` / `..._risk_score`: `MandateStore.patch`
    raises `ValidationError` and does not persist the corrupt value. **Verified RED against
    current main first** (see below).
  - `test_patch_still_accepts_valid_updates`: valid updates still round-trip.
  - `test_patch_endpoint_returns_422_for_out_of_range_max_drawdown_pct`: HTTP-level — the
    route returns 422, not 500 or 200.
- `backend/tests/unit/test_auth_dependency.py::test_correct_user_patch_returns_200` — this
  pre-existing happy-path test patched `max_drawdown_pct: 8.0`, which is **not** a member of
  the schema's `Literal[10, 20, 30, 50, 100]` — it was unknowingly exercising the exact
  defect (only ever "passed" because nothing validated the write). Changed to a valid value
  (`20`) so the test now exercises real happy-path behavior instead of the bug.

## Why this is safe / minimal

- **Two-file diff**, no schema/migration change, no new dependency (`pydantic.ValidationError`
  already imported transitively via `pydantic`).
- **`safety_floor.py` untouched** — the fix is entirely upstream of it, in the write path.
  Its consumers (`coder.room` etc.) see no interface change; a `Mandate` reaching them is now
  guaranteed schema-valid, strictly narrowing the input space it already assumed.
- **Existing merge semantics unchanged for valid input** — `compliance` still merges by key
  first, then the whole thing round-trips through `Mandate.model_validate`, which is a no-op
  for anything that was already going to be schema-valid. Every existing mandate test
  (`test_mandate_store.py`, `test_mandate_history.py`, `test_mandate_audit.py`,
  `test_def060_onboarding_claim_mandate.py`) still passes unmodified.
- **Not reachable from the shipped mobile UI today** (per the defect's own note — the picker
  only sends the 5 valid values), so this closes a public-contract gap with no behavior
  change for any real client.
