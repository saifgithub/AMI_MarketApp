## 1. What was broken

Security review 2026-07-30, proven live from an ordinary LAN device (the dev Mac):
Postgres answered as superuser `postgres`/`postgres` and all 30 tables were readable;
Redis answered `PING` with no auth. Cause: compose published 5434/6379/8001 on
`0.0.0.0`+`[::]`, and **Docker bypasses ufw**, so the host firewall was never in the
path. Rolls up C3 + N6 + N7 + M8 + M13 + M14.

## 2. What shipped

1. **C3 binds** — `127.0.0.1` on 5434/6379/8001.
2. **Credentials** — `${POSTGRES_PASSWORD:?}`, `${REDIS_PASSWORD:?}`,
   `${WEBSITE_DB_PASSWORD:?}`. `:?` not `:-` deliberately (CR040: a default is a
   silent fallback to a known credential).
3. **Redis** `--requirepass`, healthcheck authenticating via `REDISCLI_AUTH` so the
   secret stays out of process args.
4. **M8** — `api-website` moves off the superuser to `ami_website`, plus
   `REVOKE CONNECT ON DATABASE ami_trade FROM PUBLIC` (without that revoke a second
   role is decorative, since PUBLIC may connect to any database by default).
5. **N6** — explicit `ami_internal` network.
6. **N7** — non-root `USER` in both Dockerfiles (uid 1001 / 1002).
7. **M13** — `mem_limit` on all five services; backups gpg-AES256, `chmod 600`,
   `chmod 700` on the dir, `PGPASSWORD` default removed.
8. **M14** — `uv sync --locked --no-dev --no-install-project`; all five images
   digest-pinned.

## 5. Real measurement — NOT AVAILABLE, and why

**This is the weakest part of the submission and I am not dressing it up.** Every
acceptance criterion in the CR doc is a live probe against melehost, and **SSH to
melehost is down** (DEF224 — `~/.ssh/id_ed25519` is passphrase-protected, the macOS
Keychain stopped supplying it; Saiful must run `ssh-add --apple-use-keychain`). There
is also no Docker daemon on the Mac (`CLAUDE.md`: pure editor), so I could not even
`docker compose config`.

So the C3 exposure this CR closes **is still open on the host right now.** What I could
verify: the compose YAML parses under `yaml.safe_load` and the three ports carry
`127.0.0.1`; `uv lock --check`; the parity test; the full suite. Image digests were
fetched from the Docker Hub registry API by manifest-list digest (not from a local
daemon), so they are arch-independent and correct for melehost's amd64.

**Two failure modes the tests cannot catch, both documented in the runbook:**

- `POSTGRES_PASSWORD` is read by Postgres **only at first initdb**. melehost's volume
  exists, so the env var alone changes nothing and the API would authenticate with a
  password the DB does not have. Needs a live `ALTER USER` in the same window.
- The API now runs as uid 1001 and the `bug_attachments` named volume is root-owned, so
  **bug-report uploads break silently** until it is chown'd. That is the alpha feedback
  channel.
