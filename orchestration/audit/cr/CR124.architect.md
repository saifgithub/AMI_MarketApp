## 1. What was broken

Security review 2026-07-30, proven live from an ordinary LAN device (the dev Mac):
Postgres answered as superuser `postgres`/`postgres` and all 30 tables were readable;
Redis answered `PING` with no auth. Cause: compose published 5434/6379/8001 on
`0.0.0.0`+`[::]`, and **Docker bypasses ufw**, so the host firewall was never in the
path. Rolls up C3 + N6 + N7 + M8 + M13 + M14.

## 2. What shipped

1. **C3 binds** — `127.0.0.1` on 5434/6379/8001.
2. **Credentials** — `${POSTGRES_PASSWORD:?}`, `${REDIS_PASSWORD:?}`,
   `${WEBSITE_DB_PASSWORD:?}`. `:?` not `:-` deliberately (CR040: a default is a
   silent fallback to a known credential).
3. **Redis** `--requirepass`, healthcheck authenticating via `REDISCLI_AUTH` so the
   secret stays out of process args.
4. **M8** — `api-website` moves off the superuser to `ami_website`, plus
   `REVOKE CONNECT ON DATABASE ami_trade FROM PUBLIC` (without that revoke a second
   role is decorative, since PUBLIC may connect to any database by default).
5. **N6** — explicit `ami_internal` network.
6. **N7** — non-root `USER` in both Dockerfiles (uid 1001 / 1002).
7. **M13** — `mem_limit` on all five services; backups gpg-AES256, `chmod 600`,
   `chmod 700` on the dir, `PGPASSWORD` default removed.
8. **M14** — `uv sync --locked --no-dev --no-install-project`; all five images
   digest-pinned.

## The auditor's sharper point, which is the part worth keeping

> *"the §4 mutation-proof table's 'unpinned postgres digest' entry is real … but it only
> demonstrates the compose-level check works; it was never evidence for the
> Dockerfile-FROM class of image at all, so 'all five' was not actually exercised by the

That is the real defect and it is a defect in **my method**, not just in one line. I ran
five mutations, all five were killed, and I read that as the claim being proven. But a
mutation can only be evidence about a surface it can reach, and `unpin the postgres

was ever going to unpin, and both application images — including the one N7 hardens —
were unchecked. **Five green mutations across the wrong surface is not four-fifths of a
proof; it is zero proof for the fifth.**

## New guard: `test_every_dockerfile_base_image_is_pinned_by_digest`

- **Discovers Dockerfiles from compose's own `build:` context**, not a hardcoded list,
  so a service added later is covered without anyone remembering. Handles both the short
  (`build: ./dir`) and long (`build: {context, dockerfile}`) forms.
- Checks **every** `FROM` (multi-stage safe), stripping `AS <stage>`.
- Asserts `checked >= 2` so it cannot pass vacuously if a service is renamed — the
  failure mode that produced this MAJOR was a guard silently covering nothing.
- Reuses `_code_only()` so a commented-out `FROM` in a doc block cannot satisfy or break
  it.
- Its docstring records why the split exists, so the next person does not re-merge the
  two tests and re-open the hole.

**Mutation-proven against the audit's own finding**: reverting the pin to bare
`FROM python:3.13-slim` fails exactly `test_every_dockerfile_base_image_is_pinned_by_digest`
(`1 failed, 17 passed`). Restored, green at 18.

## Round-2 addendum — the second pass found 3 MAJOR, not 1. All taken.

The verdict on origin lists **MAJOR 1 (Dockerfile digest), MAJOR 2 (runbook safety
claim), MAJOR 3 (yfinance cache), MINOR 1 (REDISCLI_AUTH untested), MINOR 2 (role SQL
untested)**. MAJOR 1 is fixed above. The rest:

### MAJOR 3 — the one that matters, and I introduced it

The non-root switch silently broke yfinance's on-disk cache. `--no-create-home` still
records `/home/ami` in passwd, Docker sets no `HOME` on a `USER` switch, so
`expanduser("~")` landed under root-owned `/home`. yfinance **does not crash**: it
catches the `OSError`, logs through its own plain `logging` logger — a different stream
from our structlog JSON — and sets `dummy = True`. It also never memoises the failure,
so it retried the failing `makedirs` on **every call** while permanently losing the
cookie/crumb cache that `pyproject.toml`'s own comment says exists to survive Yahoo's
rate-limit dance.

That is a textbook CR040 violation shipped *by the change meant to harden the container*
— a silent fallback whose steady-state answer is "market data quietly got more
fragile". The auditor traced it through the installed `yfinance==1.3.0` at file:line
rather than reasoning by analogy, which is why it is actionable rather than a worry.

Fixed: `ENV HOME=/data` plus `/data/.cache` created and chown'd (`/data` was already
chown'd). Guarded by `test_the_backend_image_gives_the_non_root_user_a_writable_home`,
which asserts the *precondition* — a HOME under a path the image chowns to the runtime
uid — rather than trying to simulate yfinance.

### MAJOR 2 — the runbook told Saiful something false about a live system

I wrote "everything before step 4 is additive and safe to run against the live system."
It is not. The running `api-alpha` carries `postgres:postgres` as a hardcoded literal in
its container env, so it cannot pick up the new password before the step-4 recreate.
`session.py` sets no `pool_size`/`pool_pre_ping`, so SQLAlchemy defaults apply and any
burst past 5 concurrent DB operations in the step-3→step-4 window opens a fresh
connection with the stale password and fails.

This is the worst of the three because of who executes it: Saiful, by hand, reading
"safe". Fixed — the claim is replaced with an explicit correction block stating the
overflow-connection risk and instructing that steps 3 and 4 run back-to-back at a quiet
hour, with the note that the SQL *ordering* was never the problem.

### MINOR 1 + MINOR 2 — both had zero coverage, both now guarded

`test_the_redis_healthcheck_can_actually_authenticate` (requirepass without a matching
healthcheck credential leaves the container permanently unhealthy, which blocks
`depends_on: service_healthy` and takes the stack down) and
`test_the_website_role_sql_actually_restricts_the_app_database` (M8 is only a boundary
if PUBLIC's default CONNECT is revoked; a file that creates a role and stops there looks
like privilege separation and is not).

### A recurrence worth recording

`_code_only()` stripped `#` comments only, so the new SQL guard failed against
`01_website_role.sql`'s own header explaining that the website API *used to be* the
SUPERUSER. **Third instance this session of a "must not contain" assertion matching its
own documentation.** Fixed at the helper — it now defaults to `("#", "--")` — rather than
at the call site, so the next file type does not make it four.
