## 2. Design decisions worth checking

- **One new nullable column** (`users.daily_reminder_hour`) combined with the **existing**
  `users.timezone`. No second timezone column, and **no separate enabled flag** — NULL is
  the off switch, precisely so an hour and an enabled-bit cannot drift apart.
- **Channel by `effective_plan_for_user`**, never raw `users.plan`, so an expired trial
  correctly drops to the email channel.
- **`notify()` gained an additive keyword-only `attempt_push`.** The free-tier path still
  writes CR027's durable `notifications` row (that table's docstring says `notify()` is
  its only writer) without pinging OneSignal for a user whose channel, by product rule,
  was never push. **Please check this did not weaken CR027's own guarantee** — it is a
  change to an already-audited module and it is the most invasive thing in this CR.

## 3. The CR040 properties — attack these

**(a) Once per day, surviving a restart.** "Already reminded" is a query against the
durable `notifications` row (`source_ref` = the user's local ISO date), never process
memory. Pinned by a test that `importlib.reload()`s the module mid-run. **Try to make it
double-send**: two ticks in one local day, a tick spanning local midnight, a user whose
timezone puts them on a different date than UTC.

**(b) A user reachable on no channel is counted and logged at ERROR**, with four distinct
reasons that deliberately separate *"no email on file"* from *"the email transport is not
configured"*. `send_daily_reminder()`'s return value is used precisely so a reminder that
never left the process cannot be counted as sent. **This is the common case, not the
edge** — anonymous-first onboarding means most users have `email IS NULL`. Check that no
path lets a user silently receive nothing while the tick reports success.

**(c) Timezone.** `zoneinfo`, validated at the write boundary. A garbage zone must not
crash the tick nor silently become UTC. Check what happens to a row that already holds a
bad zone (possible: the column predates the validation).

## 4. The gap I found and closed, which is the interesting part

The build came back complete and **entirely unreachable**: `daily_reminder_hour` was NULL
for every user, NULL means off, and **nothing in the API wrote it**. The tick would have
run every 15 minutes forever and correctly sent nothing — a feature that is on, green,
and does nothing, with no error and no user complaint. CR095's own acceptance says the
reminder fires *"at their configured local time"* and there was no way to configure it.

Added `PUT /v1/daily_challenge/reminder` (hour + timezone in one call, because an hour
without a timezone is a reminder at the wrong time). 8 tests including an **IDOR pin** —
there is no `user_id` in the path, the row comes from the authenticated caller, and the
pin exists so nobody later "helpfully" adds a path parameter.

## 6. Known gaps

- **No mobile settings control**, so no real user can set an hour yet. The API is
  reachable; the app is not wired. Backend-only slice by choice — a mobile change needs a
  build and a device pass.
- **5 new user-facing strings are English-only** (push title/body, email subject/body).
  This matches the existing magic-link and CR027 price-alert pattern — OneSignal's payload
  only ever carries an `"en"` key today — so it is not a regression, but it is new copy
  and carries `retranslate:[ar,ms]` per the standing rule. I flag; I do not translate.
- `sent_email` means a transport call was made, not delivery confirmed — same
  fire-and-forget contract as `send_magic_link`.
- `deep_link = {"route": "open_daily_challenge"}` follows CR027's naming convention but
  **the mobile dispatcher was not touched or verified**, so that route may not resolve.
- The reminder does not consult quiet hours; none are defined anywhere in the repo
  (CR109 would define real ones). Inventing them would be undocumented scope creep.
