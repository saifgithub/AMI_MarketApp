## The three MAJOR, and what each fix actually changes

### 1. A timezone-only PUT silently cleared the reminder hour

`row.daily_reminder_hour = req.daily_reminder_hour` ran unconditionally, and
Pydantic cannot distinguish an omitted field from an explicit `null` on a plain
`Optional[int] = None`. `timezone` had the correct guard; the hour did not.

**Fix:** `if "daily_reminder_hour" in req.model_fields_set:` in
`app/api/daily_challenge.py`. `model_fields_set` carries exactly the
distinction Pydantic drops on the value itself.

**The trap in this fix, and the test that covers it:** the lazy version is `if
req.daily_reminder_hour is not None`, which passes the auditor's pin and
silently removes the only way to turn reminders off — `null` is the column's
own "off" value. `test_an_explicit_null_hour_still_turns_reminders_off` is
there specifically to fail that shortcut.

### 2. A same-day timezone change produced a second reminder

`source_ref` is the user's local date, recomputed from `users.timezone` on
every tick. Change timezone far enough forward mid-day and today's local date
points at a row that doesn't exist yet.

**Fix:** `_already_reminded_today` now OR's the `source_ref` match with a
trailing 20h window on `created_at`. `source_ref` moves when the timezone
column moves; `created_at` does not.

**This fix had a real bug that my own non-vacuity test caught, and I want it
attacked.** The row's `created_at` came from the column default (wall clock)
while the sweep compares against its caller-supplied `now`. In production those
are the same clock so it worked; under any simulated `now` — every test, any
replay or backfill — it compared two different clocks and suppressed
everything. The window looked like it worked while actually being unfalsifiable.
Fixed by threading the sweep's own `now` into `notify(created_at=...)` so the
row is stamped with the same clock the dedupe reads back.
`test_the_next_days_reminder_still_fires` is the leg that caught it and is the
leg I'd attack: **a 20h window that also swallowed the legitimate next-day
reminder would satisfy the auditor's pin perfectly.**

Please also sanity-check the 20h constant itself. My reasoning: it must sit
below the 24h separating two legitimate consecutive reminders, and above the
largest re-trigger a timezone jump can produce (UTC-12 → UTC+14 is 26h of
apparent local movement, but it re-triggers within *minutes*, not hours, so the
binding constraint is the 24h ceiling, not the 26h). I believe any value in
roughly 2h–23h works and 20h is a middle choice. Tell me if that reasoning is
wrong.

### 3. Concurrent ticks double-sent; nothing at the DB level stopped it

`NotificationRow` had no unique constraint, `_already_reminded_today` is a
plain SELECT and `notify()` a plain INSERT. The only thing preventing a
double-send was that exactly one process runs the sweep today.

**Fix, three parts:**

- `uq_notifications_dedupe` on `(user_id, type, source_ref)`, migration
  `8c5b1a70f4d2`. NULLs are distinct in SQL unique constraints, so the majority
  of `notify()` callers — the ones passing no `source_ref` — are deliberately
  unaffected; passing one is what opts a caller into dedupe.
- `notify()` catches the resulting `IntegrityError` and returns
  `push_status="duplicate"` (plus a `was_duplicate` property) with the winner's
  notification id, so the losing racer sees a describable skip rather than an
  unhandled 500.
- **The free-tier path now writes its row BEFORE sending the email.** This is
  the part I most want checked, because the constraint alone does not fix
  anything here: the old order sent the email first and wrote the row second,
  so both racers delivered and only the loser failed to write. A claim made
  after delivery guards nothing.

There is also a fourth place this could have gone wrong and did not, worth
verifying: the **paid** path calls `notify()` (which pushes) and then falls
through to an email fallback on any non-`"sent"` status. Without an explicit
`was_duplicate` early-return, a suppressed duplicate would read as "push didn't
deliver" and send an email — turning the fix into a different double-send.

## Mutation proof of the one guarantee that could silently not exist

The constraint is a DB-level property, so "the test passes" is not evidence it
exists. Removed `UniqueConstraint` from the model and re-ran:


Restored, passes. The three auditor pins each failed before their own fix and
pass after, and the fixes are disjoint: the tz pin's tick 2 writes a *different*
`source_ref`, so the constraint cannot be what saves it; the concurrent pin's
two threads share one `now`, so the window cannot be what saves it.

## Docstrings that were false and are now corrected

`main.py::_daily_reminder_tick` claimed the interval carried "no risk of a
double-send" without qualification. That was true only under today's
single-process topology, which is exactly the "operational assumption stated as
a control" this repo's own doctrine flags. Both that docstring and
`daily_reminder`'s now name all three legs and say which one does the work.
