# DEF375 — audit lane (QA-only tour skip so the iOS UAT gate never meets a modal tour)

**SCOPE:** def

**TIER: B.** Mobile-only, dart-define-gated app behaviour change plus one QA build script
edit. No auth, billing, migration or compliance-perimeter change. The channel-refusal branch
(can a production build ever skip a tour) is the one path with real blast radius if wrong — a
MAJOR finding there raises it to Tier A.

**SHA:** `5e1b2ae6` on `worktree-agent-abd8df8e6ac555811`, parent `abd76ee8` (current `main`
tip at start of work). Review with `git diff abd76ee8..5e1b2ae6`.

**depends-on:** none. **Promoted:** no (mobile QA-path change; nothing here ships in a store
build — see "Attack surface" below for why).

## What and why

DEF375's row (`docs/defect/_registry/DEF375.row.md`) carries five prior rounds (AT:R74,
2026-08-25 → 2026-08-29) of trying to make the Appium UAT harness dismiss the five first-run
coach-mark tours (floor, portfolio, lessons, journal, you) mid-run, so the iOS gate's 19
`pytest -m phase1` tests could reach the screens they test instead of 7 of them failing
behind a modal tour. Every wiring attempt — after every tab tap, on first visit only, walking
with Next instead of Skip — either made the gate worse or reproduced the same failure:
DEF382 measured that touching the coach-mark overlay's own dismiss controls collapses the iOS
accessibility tree, so the next test module's onboarding check reads an empty tree and burns
its full 480s timeout. `ami.tour.skip`/`ami.tour.next` are addressable (DEF382 fixed that with
`MergeSemantics`) but using them from the harness is a dead end regardless of addressability.

This round's brief (from the task description, referencing CLAUDE.md's CR225 precedent):
don't fight the tour from the harness side — give the QA build a deterministic, structural way
to start with every tour already marked seen, gated the same way `AdMobConfig` gates real ad
units on `AMI_RELEASE_CHANNEL`, so a production build can never carry the skip regardless of
what dart-define an operator's shell happens to have set.

## Changes

- **`mobile/lib/qa/tour_qa_config.dart` (new).** `TourQaConfig`, a pure resolver in the same
  shape as `AdMobConfig.resolve` (CR225): `skipToursForQa` reads `AMI_QA_SKIP_TOURS` (flexible
  truthy string — `1`/`true`/`yes`/`on`, the same lesson `AMI_QA_SEMANTICS` paid for in
  `main.dart`, since `bool.fromEnvironment` reads `=1` as `false` silently) and
  `AMI_RELEASE_CHANNEL`, and resolves `true` only when the flag is set AND the channel is not
  `production`. `unknown` (no channel forwarded at all) and `internal` both count as
  skippable — the conservative-default rule is inverted from `AdMobConfig`'s on purpose: AdMob
  treats an unset channel as "not permitted to serve real ads" (conservative = off); this
  treats an unset channel as "permitted to skip tours" (conservative = the QA build works with
  no extra wiring), because the risk being guarded against is the opposite direction — a real
  user seeing no tour, not a real user seeing a live ad unit. `resolve`/`parseChannel` take
  their inputs as parameters (`@visibleForTesting`), same as `AdMobConfig.resolve`, so the
  fixed compile-time constants can still be varied from a test.
- **`mobile/lib/features/tour/tour_service.dart`.** `TourService` gained an optional
  `skipToursForQa` constructor parameter (defaults to the real `TourQaConfig.skipToursForQa`
  getter — a test cannot flip a compile-time `String.fromEnvironment` constant, so this is the
  injectable seam). `hasSeen(TourSection)` checks it **before** touching `SharedPreferences` at
  all and returns `true` unconditionally if set. Every one of the five tour screens
  (`floor_screen.dart`, `portfolio_screen.dart`, `journal_screen.dart`, `lessons_screen.dart`,
  `you_screen.dart`) already gates its tour on `hasSeen` before building the overlay — grep-
  confirmed, no screen file touched — so this one choke point covers all five. The CR180
  nav-change notice (`shouldShowNavChange`) is a documented side effect, not a separate fix: it
  triggers off a pre-restructure `tour_*_seen` flag having been set, and under the QA flag no
  screen ever calls `markSeen` (short-circuited before that point), so the notice's own
  precondition stays false.
- **`scripts/build_qa_ios_sim.sh`.** Forwards `AMI_QA_SKIP_TOURS=true` by default (overridable
  via env like every other var in the script) alongside the existing `AMI_QA_SEMANTICS=true`.
  Deliberately still forwards no `AMI_RELEASE_CHANNEL` — matching `install_iphone.sh`'s
  existing choice not to forward it — so the QA Simulator build lands on the unset/
  non-production default that `TourQaConfig` treats as skippable.
- **Tests:** `mobile/test/qa/tour_qa_config_test.dart` (the resolver in isolation) and
  `mobile/test/features/tour/tour_service_qa_skip_test.dart` (the wiring through
  `TourService.hasSeen`, including the never-writes-prefs and CR180-notice-doesn't-fire
  claims).
- **Governance:** `docs/defect/_registry/DEF375.row.md` → `fixed`, registers regenerated
  (`docs/defect/def_list.md`), a short doc note at
  `docs/defect/DEF375_coach_mark_tours_block_ios_gate/`.

## Attack surface (please probe)

1. **Can a production build ever skip tours?** Two independent gates: (a)
   `build_testflight.sh`/`build_playstore.sh` never pass `AMI_QA_SKIP_TOURS` in their
   dart-define list at all — grepped, confirmed absent; (b) even if hand-added,
   `TourQaConfig.resolve` refuses it once `channel == production`, and that channel is derived
   structurally by those scripts from `--production`/`--internal-only`, never hand-typed
   (CR225's existing mechanism, reused not re-implemented). Proven in
   `tour_qa_config_test.dart`'s `flag set, channel production => tours show (skip refused)`.
   Worth independently confirming the channel derivation in both store scripts still matches
   what CR225 documented — this round did not touch that derivation, only consumed its output.
2. **`install_iphone.sh` (cable-installed tester devices)** forwards neither
   `AMI_QA_SKIP_TOURS` nor `AMI_RELEASE_CHANNEL` — confirmed by grep, zero occurrences of
   either in that script. So a cable-installed device build is on the unset/non-production
   channel AND has no skip flag, meaning `skipToursForQa` resolves false (flag absent) and
   tours show normally, same as today. Flagging for a second look because "unset channel
   counts as skippable" is the more permissive of the two branches, and this is the one real
   script where that branch is reachable outside the QA path — it stays safe only because the
   flag itself is never forwarded there either.
3. **Semantics IDs stability.** `ami.tour.skip`/`ami.tour.next` (`TourIds` in
   `mobile/lib/qa/semantics_ids.dart`) are untouched by this change — `tour_ids_test.dart`
   (DEF382's guard) still passes unmodified. Confirm the reviewer agrees these should stay:
   they are now not load-bearing for the *gate* (the gate no longer taps them), but they remain
   the way a real user or a future on-device harness dismisses a tour by hand, so removing them
   would be a regression this round did not intend.
4. **`TourService`'s injectable constructor.** `skipToursForQa` is an optional named param
   defaulting to the real getter; `tourServiceProvider` (the only production wiring site,
   `tour_providers.dart`) still constructs with `TourService()` — no override — so production
   Riverpod wiring is unchanged. Confirm no other call site was missed (grep found exactly two:
   the provider and the pre-existing `nav_change_test.dart`).
5. **`shouldShowNavChange` side effect.** Verify the reasoning that no screen calls `markSeen`
   under the QA flag (each screen's `hasSeen` check returns before reaching its own `markSeen`
   call) actually holds for all five call sites, not just the ones read closely
   (`floor_screen.dart` has two call sites — `initState` and a `ref.listen` — both were checked;
   worth a second pass on `journal_screen.dart`'s `journalVisibleProvider`-driven listener,
   which has slightly different gating prose in its own comment).
6. **Guard evasion / scope creep.** This round did not add a guard the way CR225 added
   `test_config_compose_parity.py`-style enforcement for `AMI_RELEASE_CHANNEL` forwarding,
   because there is no docker-compose or CI surface for a Flutter dart-define — the enforcement
   here is the widget tests plus the one script that matters (`build_qa_ios_sim.sh`) being
   hand-verified. Confirm that's an acceptable enforcement level for a QA-only, never-shipped
   flag, or whether a `failure_patterns.md` guard entry is warranted for "a QA dart-define
   accidentally reaching a shipping script."
