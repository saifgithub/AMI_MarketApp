## MINOR m1 — §5.1, the lane's own headline defect, no longer exists

§5.1 reports a delete-then-replay hole: the route's idempotency read returns the
tombstone, `append_unique` collides with it, the client gets a dead
`journal_entry_id`, and the gate counters freeze. I re-ran its probe verbatim
against the real store at `c0f1ac86`:

```text
                                  submission §5.1        measured at c0f1ac86
1. first write                    created=True           created=True
2. user swipes it away            —                      get -> None
3. route's idempotency read       returns the tombstone   find_by_dedupe_key -> None
4. re-write, same dedupe_key      created=False, same id  created=True, NEW id
   returned row deleted_at        set                     None
5. client opens journal_entry_id  store.get -> None       a live entry
6. gate counters                  used=1 daily_used=1     used=2 daily_used=2
```

Every line inverts. The partial predicate means there is no collision with a
tombstone at all, and the idempotency read excludes them. §5.5 is stale the same
way — it says `portfolio_health_stats` filters `daily` on `reference_id` while
`len(rows)` does not; `46bf51ae` made both per-user and the current docstring
says so.

MINOR, not higher, because **the code is right** — this is a provenance defect,
not a behaviour one. It is recorded because an auditor who trusted §5.1 would
have opened a defect against working code, and because the submission presents
it as the lane's most important finding.

## What I probed beyond the submission — the partial index's new freedoms

The old analysis could not have asked these, so I did:

```text
5x (create, delete) on ONE dedupe_key    5 distinct rows created
                                         portfolio_health_stats: used=5 daily_used=5

restore a tombstone whose key a LIVE row now holds
                                         restore_with_reason -> RestoreOutcome.SUPERSEDED
                                         find_by_dedupe_key   -> the live row
                                         latest_portfolio_health_entry -> the live row, deleted_at=None
```

Both land correctly. Delete-to-replay is *possible* but **costs** budget rather
than resetting it — the counter is the row, so it fails in the safe direction —
and `DAILY_CAP_DEFAULT = 2` binds after two. The tombstone/live collision the
partial index newly permits is resolved by M07 r4's `RestoreOutcome`, which is
the guard I graded as a good change one lane over doing exactly its job here.
