### Versioning-convention note (documented per instruction)

`legal/VERSIONING.md` states archiving happens "if this is a major bump" (semver: 1.0→2.0). The
**actual, most recent precedent** (`e1f2bd92`, this same morning) archived v4.0→`/terms/v4/` for
what its own commit message calls a label-only, non-substantive change — i.e. NOT a major bump by
the doc's own semver table. I followed the precedent (archive on every published point bump,
overwriting the single per-major slot with the latest superseded text) rather than the doc's
literal "major only" text, since the precedent is what the repo actually does today and the task
named it explicitly ("exactly the v4.1 pattern"). Privacy's `/privacy/v2/` is a first-time archive
(no prior slot existed to overwrite), created the same way. Saiful/legal (A22) should reconcile
`VERSIONING.md`'s stated rule against the practice if the drift matters to them.

## Attack surface — the two questions this DEF exists to answer

**Is any Alpaca data still sent for a live account?** No, by construction at three
independent points, all covered by tests:
1. `AlpacaSnapshotCache.current()` — the Room-convene/1-on-1 upload path. Gated;
   `test/state/def430_alpaca_snapshot_paper_only_test.dart`.
2. `trade_ticket_sheet.dart`'s `_fetchAlpacaSnapshot()` — the DEF419 mandate-preview
   path. Gated (this lane's own fix, not merely verified);
   `test/screens/sim/def419_per_account_test.dart`'s new "DEF430 — a live-linked
   account never reaches the preview" group.
3. `AlpacaClient.submitOrder`/`cancelOrder` — the only two writes this client ever
   makes. Pre-existing `isAlpacaPaperHost` gate, unchanged by this lane, still pinned
   by `alpaca_client_paper_only_test.dart`.

No other call site reads `AlpacaCredentialStore`/`AlpacaClient.account()`/`.positions()`
outside these three (grepped `alpaca_providers.dart`, `trade_ticket_sheet.dart`, and
`api_client.dart` for every `alpaca`/`account` reference before starting).

**Is the notice exactly-once?** Yes, structurally, not just empirically: `notify()`'s
`uq_notifications_dedupe` unique constraint on `(user_id, type, source_ref)` is a DB
constraint, not app-level bookkeeping — the mutation test above proves a re-run with
the guard removed WOULD double-notify, and the real code's fixed, never-recomputed
`source_ref` is what the constraint keys on. Delivery is via the FastAPI lifespan
(every container boot), so a user who links after one boot but before the next is
correctly picked up by the following boot; a user who links after ALL boots that will
ever run again is deliberately never notified (they get the point-of-collection
link-screen disclosure instead — see the versioning note above for why this is
intentional, not a gap).

### MAJOR-1 — the preview-path Alpaca snapshot was stored verbatim in `http_audit` for 90 days

`HTTPAuditMiddleware` (`backend/app/middleware/http_audit.py`) redacted secret-shaped keys and
the literal key `alpaca`. The DEF419 preview snapshot on `POST /v1/sim/preview` rides the key
**`account`**, not `alpaca` (confirmed by grepping `mobile/lib/services/api/api_client.dart` for
every `toMandateSnapshotJson`/`toWireJson` call site — Room convene and 1-on-1 both send the
snapshot under `alpaca`, already redacted; order submit/cancel never send it at all — `/v1/sim/preview`
is the only route affected). So equity, cash and positions landed unredacted in `http_audit` for
90 days, which made Privacy v2.1's "we do not store the summary as its own record" false for that
one path.

**Fix, as ruled:** the policy text is unchanged — the code was wrong, not the wording. Added
`_PATH_SCOPED_PRIVATE_FIELDS: dict[str, re.Pattern]`, keyed by request path, applied in
`_scrub_secret_fields(body, path=...)` in addition to the existing blanket `_SECRET_FIELD_RE` /
`_PRIVATE_FIELD_RE`. Only `/v1/sim/preview` → `account` is registered today. Scoped by path
deliberately: `account` is a generic key name used elsewhere for unrelated payloads, so a blanket
match would over-redact.

New test file `backend/tests/unit/test_http_audit_scrub.py` (13 tests) posts the real
`toMandateSnapshotJson` wire shape through the real app with `TestClient` on `/v1/sim/preview`,

becomes `[REDACTED]`. Also checked: a Room body's `alpaca` key still redacts; a non-Alpaca route

### MAJOR-2 — the "one-time" notice would repeat after the 90-day notifications trim

`notify_policy_update_v2_1`'s exactly-once guarantee rests entirely on `uq_notifications_dedupe`
— i.e. the earlier `notifications` row still existing. `trim_audit_tables()` (`backend/app/services/audit.py`)
deleted `notifications` rows older than 90 days on every boot's sweep, with no exemption by type.
So ~90 days after the first send, the row is gone and the next boot tells every linked user again
that "Privacy Policy updated (v2.1)" — repeating forever, once per retention window.

**Fix, as ruled:** exempt `policy_update` notifications from the trim rather than changing the
sweep's cadence or moving the row elsewhere. `_NOTIFICATION_TYPES_EXEMPT_FROM_TRIM = {"policy_update"}`,
applied as an `and_(created_at < cutoff, type.notin_(...))` filter — every other notification type
(price_alert, daily_challenge, ...) still trims normally.

New tests in `test_audit.py`: `test_trim_audit_tables_exempts_policy_update_but_not_other_types`
and `test_policy_update_notice_survives_trim_and_re_sweep_stays_a_no_op` — notify → age the row 91
days → trim → re-sweep → still exactly one row, `notified == 0` on the re-sweep.

### MAJOR-A — the preview RESPONSE stores the paper account's cash and a position's quantity

`preview_trade` (`backend/app/api/sim.py:719-736`) returns `cash_available` and
`held_quantity` on the snapshot path — the Alpaca paper account's own figures —
plus the same numbers folded into free-text `violations` strings (insufficient-cash
and concentration refusals). `HTTPAuditMiddleware` stored the response body
verbatim; only the request key `account` was redacted (round 2's MAJOR-1 fix).

**Fix, as ruled:** reused the existing `SCRUB_PATHS` whole-body mechanism rather
than building a parallel per-key response scrubber (per-key redaction can't reach
text embedded inside a string value, which is exactly how the violation strings
leak the numbers). New table
`_PATH_SCOPED_RESPONSE_SCRUB_ON_REQUEST_FIELD: dict[str, str]` in
`http_audit.py`, keyed by path → the request-body key whose PRESENCE (not value)
triggers a response blackout. `/v1/sim/preview` → `"account"` is the only entry
today. Computed from the raw request bytes BEFORE request-side scrubbing runs
(presence, not the scrubbed value). When present, the response follows the exact
same `scrub` branch `SCRUB_PATHS` already uses (`captured_response =
b"[REDACTED]"`, response object returned unconsumed) — not a new code path, an
additional trigger for the existing one. A preview with no `account` (AMI's own
sim) is untouched and keeps its normal response.

New tests in `backend/tests/unit/test_http_audit_scrub.py`: a snapshot buy, a
snapshot sell of an already-held ticker, a snapshot buy sized past the account's
cash (the insufficient-cash refusal path, which is the one MAJOR-A's own
discovery was about — the violation TEXT carries the number, not just a
structured field), and a control case with no `account` key that asserts the
response is NOT redacted (proves this is a conditional fix, not a blanket
blackout of every preview). Each of the three snapshot cases first asserts the
real, unredacted `TestClient` response text DOES contain the leak (`"50000"`,
`"cash_available"`, `"held_quantity"`) before checking the stored row is clean —
so a test that passed vacuously (e.g. because the route never actually returned
those fields) would have been caught by its own setup.

### MINOR-A — the scoped redaction matches the exact path only

`_PATH_SCOPED_PRIVATE_FIELDS.get(path)` and the new response-scrub table above
were both exact dict lookups. A POST to `/v1/sim/preview/` (trailing slash)
307-redirects at the route layer, but the middleware sees the pre-redirect path,
so an exact lookup missed it and stored the full snapshot on both request and
response.

**Fix:** `_normalize_scrub_path(path)` strips exactly one trailing slash (never
the bare root `/`), applied before every scoped lookup — the pre-existing
`_scrub_secret_fields`'s own `_PATH_SCOPED_PRIVATE_FIELDS` lookup, the new
response-scrub table lookup, and the `scrub = path in SCRUB_PATHS` check itself
(so a trailing-slash auth route also stays covered, not just the DEF430 route).

New test `test_sim_preview_trailing_slash_request_is_still_redacted`: POSTs to

### Attack surface

1. **Response redaction is additive and conditional**, not a second global
   `scrub`-everything switch: `_PATH_SCOPED_RESPONSE_SCRUB_ON_REQUEST_FIELD` is
   path-keyed, and even for its one entry (`/v1/sim/preview`) it only fires when
   the specific request actually carried the named key — proven by
   `test_sim_preview_without_account_keeps_normal_response`, which is a control,
   not an incidental pass.
2. **Path normalization is scoped to exactly one trailing slash on a non-root
   path** (`len(path) > 1 and path.endswith("/")`), so it cannot collapse an
   unrelated multi-slash or empty path into something that accidentally matches
   a scoped entry.
3. **The merge re-key is unconditional and symmetric** with every other
   `_rekey_all()` table in the file — no new conflict rule, no UNIQUE
   constraint to resolve, so it can't introduce a new collision class the other
   free-form tables don't already handle.

   surface" is just whether the sentence is now true of the code, which the
