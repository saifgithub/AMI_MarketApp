The argument:

1. **M07 is the only module that decides who pays and how often.** Every other
   lane can be wrong about a *number*. M07 can be wrong about *entitlement*,

   paying user refused, discovered only if they complain. Neither turns anything

4. **Nothing here has ever run outside my own pytest.** Measured against Alpha
   this session (§3): both M07 routes return **404** on

5. **Every semantic in the module is pinned by tests I wrote myself** — the

## 2. What the module is, and the decisions worth challenging

### 2.1 Two routes, one gate object; the free surface is structurally free

`GET /v1/portfolio/health/{user_id}` — tiles, FREE in every mode. It calls
`evaluate_gate` and **never** `enforce_gate`, so the free surface is incapable of
gating rather than merely observed not to. The guard is an AST test
(`test_the_tiles_route_never_calls_enforce_gate`) that walks every `ast.Name` in
the handler, not call nodes — both gate functions reach the thread pool as
`asyncio.to_thread(fn, …)` *arguments*, so the first draft of that test passed
vacuously by checking calls.

Worth challenging: the tiles route does the whole expensive computation
(`build_health_context` → EWMA covariance over the book) with **no rate limiter**,
by deliberate parity with the sector-allocation route in the same file.

### 2.2 The gate is three independent facts

`mode ∈ {open, trial, plan}` as a `Literal` (a typo fails boot loudly, never
falls open); `trial_active = used < budget AND days_elapsed < trial_days` (window
OR budget, whichever exhausts sooner); `plan_has_access = effective_plan value ∈
normalised env list`. Access: `open` ⇒ always; `trial` ⇒ `trial_active OR
plan_has_access`; `plan` ⇒ `plan_has_access`. **The daily cap applies in every
mode, `open` included.**

### 2.3 The counters are journal rows the user can delete

No new table — which means both counting reads deliberately **include
soft-deleted rows** (`portfolio_health_stats`, journal_store.py:364-381, no
`deleted_at` filter). Delete yesterday's Finding must not mint today's budget.
`list_for_user` is unusable here: it filters soft-deletes *and* applies the Floor
Pass 30-day retention window, either of which hands out free Findings or resets a
rule's hysteresis band because the row holding its state aged out of a plan's
view.

Trial counters are per **user** across every `reference_id`, because
`reset_portfolio` destroys the row and `ensure_portfolio` mints a fresh `uuid4()`
(sim_engine.py:387-388, :399-417) — a per-portfolio trial would reset on every
book reset. The daily counter is per **portfolio**, per Rev 4. That asymmetry has
a consequence: §5.3.

### 2.4 Two steps sit before the gate, deliberately

`_own` (403 before anything is spent), then the same-day idempotency replay (200,
`created:false`, no LLM, no write, **not gated** — the entry is already in the
user's journal and re-reading it must not cost budget or be refusable). The
replay additionally requires `deleted_at IS NULL`: returning a deleted row
answers "regenerate" with a journal id pointing at a row the user cannot open.

§5.1 is that guard failing anyway.

### 2.5 The write is the serialisation point, not the read

`uq_journal_dedupe (user_id, entry_type, dedupe_key)` with `dedupe_key =
"<portfolio_id>:<as_of>"`, NULL for every other entry type — NULLs do not collide
in a unique index on either Postgres or SQLite, so the eight other journal
writers are untouched and there is no backfill. `append_unique` returns the
winner's row as `created:false`, the same answer a same-day replay gets.

Deliberately **not** a partial index on `payload->>'as_of'`: that expression is
spelled differently on Postgres and SQLite, so it would be enforced in production
and silently absent under test — the one arrangement guaranteed to let the defect
come back unnoticed.

### 2.6 Where the CODE and the module DOC disagree — code is the truth

- **Doc §3.2 sketches `health_gate` owning its own `JournalEntryRow` SELECTs and
  declaring `PORTFOLIO_HEALTH_ENTRY_TYPE` locally.** Shipped: both counter reads
  are `JournalStore.portfolio_health_stats` (the seam register overrides the doc,
  and the doc carries that note itself), and the constant is imported from
  `portfolio_health_constants` with `# noqa: F401` — **`health_gate` has no
  reader for it at all**. The acceptance item `grep -n "EntryType"
  health_gate.py → no matches` still passes (measured, §3), but the
  build-order-independence property it encodes is now hollow: `health_gate`
  imports `journal_store` (health_gate.py:35), and `journal_store` imports
  `EntryType`. The grep tests a spelling, not the property. I did not weaken the
  test; I am flagging that it stopped meaning what it says.
- **Doc §3.4 justifies hoisting `status`/`as_of`/`generated_at`/`engine_version`
  to the envelope root with "M09's `fromJson` reads `json['metrics'] ?? json`".**
  Shipped M09 (round-2 `m1`) deleted that fallback; it reads `metrics` only and

- **Doc §5 case 13** specifies the entry-type/enum equality assert as

- **Doc §3.5 step 6's REFINED note** (replay requires `deleted_at IS NULL`) and

## 5. What I would attack if I were the auditor

> §4 is deliberately the last section in this file: the serial measurement pass
> rewrites its fenced block in place.

### 5.1 THE ONE — the deleted-prior guard and the uniqueness constraint cancel each other. Measured this session.

Both guards landed in `043995b0`. They contradict.

- The route refuses to replay a soft-deleted prior (`portfolio.py:190-196`,
  `prior.deleted_at is None`) — so a user who deleted today's Finding falls
  through to real generation.
- Generation ends at `store.append_unique(draft)`
  (`portfolio_finding.py:1256`) with `dedupe_key = "<portfolio_id>:<as_of>"`.
  **The soft-deleted row still holds that key** — `uq_journal_dedupe` has no
  `deleted_at` predicate, and `find_by_dedupe_key`
  (`journal_store.py:150-158`) has no `deleted_at` filter either.

So the INSERT collides with the row the guard just refused to replay, and
`append_unique` hands it straight back. Measured, driving the real POST route
with the real M06 persistence path (probe script lives outside the repo, in the
session scratchpad; no repo file was written or modified):

```text
POST 1: 200 {'journal_entry_id': 'bdb44d1f-…-d473fdf6706f', 'created': True}
soft_delete -> True
[info] portfolio_finding_lost_write_race as_of=2026-08-02 portfolio_id=6f1d9df8-…
POST 2: 200 {'journal_entry_id': 'bdb44d1f-…-d473fdf6706f', 'created': False}
same id as the deleted row? True
store.get(returned id) -> None
stats (trial_used, daily_used): 1 1
```

`store.get(...) -> None` is the whole finding: **the client is handed a
`journal_entry_id` that does not resolve** — exactly the dead link
`prior.deleted_at is None` exists to prevent, plus a full render (and, on the
LLM-enabled path, a billed LLM call — `llm_render_sections` runs *before*
`append_unique`) spent to produce it. The user's only visible outcome is a
Finding screen that cannot open its own journal entry, and the log line is
`portfolio_finding_lost_write_race`, which reads like a benign concurrency
event.

Reachable by an ordinary user, not an attacker: `journal_screen.dart:170-186`
soft-deletes any entry with an undo snackbar; the Finding screen regenerates.

**Why the suite is green over it.** `test_a_deleted_prior_entry_is_not_replayed_to_the_client`
asserts `created is True` — but it runs under the `wired` fixture, whose
`_fake_generate` seeds the row directly with `dedupe_key=None`, so the real
constraint is never reached. The one test that does exercise real persistence
(`test_the_route_composes_the_real_engine_rules_and_renderer`) never deletes.
The guard and the constraint are each tested; **their composition is not.**

I did not fix it: the shared checkout has concurrent lanes reading this tree, and
a source edit mid-round would corrupt their runs. Grade it; I will take it in
round 2. It is **not** DEF211 or DEF212 and I have not filed it — the ID mint is
a separate act and this is the first place the finding is written down.

### 5.2 §3.4's CR040 guarantee depends on every upstream module never raising

The tiles route's stated contract is "GET stays 200; a 5xx would hide the amber
state from the card". But `build_health_context` is called with **no `try`**
(`portfolio.py:149`), so any raise anywhere in M02/M04 becomes a 500 on the free
surface. **DEF211** (zero-variance benchmark leg → unguarded `ValueError` from
`beta_r2`) is a known live instance whose stated end-to-end impact is *a 500 on
this exact route*. It is **deliberately deferred and I am not re-filing it** —
what I want graded is the design question it exposes: is "the tiles never 5xx" a
guarantee at all when it is a property of code M07 does not own, or does the
CR040 answer require M07 to convert an engine raise into a rendered amber state
here? A blanket `except` is the wrong answer (silent degrade is the disease, not
the cure); the right one is probably a narrow, named contract with M04.

### 5.3 The daily cap resets with the portfolio

`daily_used` filters on `reference_id == portfolio_id`; `reset_portfolio` deletes
the row and `ensure_portfolio` mints a fresh `uuid4()`. Trial counters survive by
design (per-user, §2.3) — but **in `plan` mode the daily cap is the only limiter
on an entitled user**, so reset-the-book restores it, bounded only by the 5/min
rate limiter. `test_the_daily_counter_is_per_portfolio_the_trial_is_per_user`
pins the mechanism as intended. The question is whether Rev 4's "per portfolio
per day" is the right denominator for what is actually an LLM *cost* control.
Cost to the user is their whole simulated book, so this is not a likely abuse —
it is a question about the denominator, not an exploit report.

### 5.4 `portfolio_health_stats` counts in Python over an unbounded fetch

`journal_store.py:364-381` selects **every** Portfolio Health row the user has
ever had — no SQL `COUNT`, no date bound on the trial leg — and counts in
Python. Bounded today by cap × days. Ask whether it stays bounded in `open` mode
over a year of daily use, and whether a `COUNT`/`min()` pair is owed here.

### 5.5 The five Settings and their compose forwarding — the DEF038/DEF063 class

`test_config_compose_parity.py` passes, but it asserts a *key appears* in the
api-alpha env block; it does not assert the substitution default is right. The
defaults are mirrored into the `${…:-…}` substitutions deliberately, because an
**empty** env var still overrides a Settings default — a bare `:-` would blank
`PORTFOLIO_HEALTH_PLANS` and hard-close `plan` mode. Verify that reasoning for
`GATE_MODE` too: an empty value there should fail the `Literal` at boot, which is
the loud direction — confirm it is actually loud (a boot failure an operator
sees) and not a restart loop nobody reads.

### 5.6 The idempotency replay is ungated on purpose

A fully refused user (402-worthy) still gets 200 with the stored sections. My
read: not an entitlement leak, because the entry is already in their journal and
`sections` come from the stored payload. I would like that read checked, because
it is the one place a "before the gate" step returns paid content.

### 5.7 Lifecycle of the rate limiter (the protocol's stateful-construct clause)

`portfolio_health_finding_rate_limit` is a module-level singleton with in-process
`OrderedDict` state, LRU-bounded at `MAX_TRACKED_KEYS`, user-keyed
(`f"user:{current_user.id}"`). Correct on call one is a different claim from
correct on call ten-thousand, and from correct across two replicas. Alpha runs
one container today; confirm what the limiter means when it does not.

### 5.8 The 402-before-429 precedence

Until `043995b0` it was asserted only by the function's own docstring — no test
made both conditions true at once. It matters: a 429 tells a user who can *never*
generate to come back tomorrow, which will be just as false tomorrow. One test
now covers it. Confirm the ordering is right for the CTA M09 renders off the gate
dict, and that `enforce_gate` is the only producer of 402/429 in the module.
