## 2. What the module is, and the decisions worth challenging

### 2.1 Two routes, one gate object; the free surface is structurally free

`GET /v1/portfolio/health/{user_id}` — tiles, FREE in every mode. It calls
`evaluate_gate` and **never** `enforce_gate`, so the free surface is incapable of
gating rather than merely observed not to. The guard is an AST test
(`test_the_tiles_route_never_calls_enforce_gate`) that walks every `ast.Name` in
the handler, not call nodes — both gate functions reach the thread pool as
`asyncio.to_thread(fn, …)` *arguments*, so the first draft of that test passed
vacuously by checking calls.

Worth challenging: the tiles route does the whole expensive computation
(`build_health_context` → EWMA covariance over the book) with **no rate limiter**,
by deliberate parity with the sector-allocation route in the same file.

### 2.2 The gate is three independent facts

`mode ∈ {open, trial, plan}` as a `Literal` (a typo fails boot loudly, never
falls open); `trial_active = used < budget AND days_elapsed < trial_days` (window
OR budget, whichever exhausts sooner); `plan_has_access = effective_plan value ∈
normalised env list`. Access: `open` ⇒ always; `trial` ⇒ `trial_active OR
plan_has_access`; `plan` ⇒ `plan_has_access`. **The daily cap applies in every
mode, `open` included.**

### 2.3 The counters are journal rows the user can delete

No new table — which means both counting reads deliberately **include
soft-deleted rows** (`portfolio_health_stats`, journal_store.py:364-381, no
`deleted_at` filter). Delete yesterday's Finding must not mint today's budget.
`list_for_user` is unusable here: it filters soft-deletes *and* applies the Floor
Pass 30-day retention window, either of which hands out free Findings or resets a
rule's hysteresis band because the row holding its state aged out of a plan's
view.

Trial counters are per **user** across every `reference_id`, because
`reset_portfolio` destroys the row and `ensure_portfolio` mints a fresh `uuid4()`
(sim_engine.py:387-388, :399-417) — a per-portfolio trial would reset on every
book reset. The daily counter is per **portfolio**, per Rev 4. That asymmetry has
a consequence: §5.3.

### 2.4 Two steps sit before the gate, deliberately

`_own` (403 before anything is spent), then the same-day idempotency replay (200,
`created:false`, no LLM, no write, **not gated** — the entry is already in the
user's journal and re-reading it must not cost budget or be refusable). The
replay additionally requires `deleted_at IS NULL`: returning a deleted row
answers "regenerate" with a journal id pointing at a row the user cannot open.

§5.1 is that guard failing anyway.

### 2.5 The write is the serialisation point, not the read

`uq_journal_dedupe (user_id, entry_type, dedupe_key)` with `dedupe_key =
"<portfolio_id>:<as_of>"`, NULL for every other entry type — NULLs do not collide
in a unique index on either Postgres or SQLite, so the eight other journal
writers are untouched and there is no backfill. `append_unique` returns the
winner's row as `created:false`, the same answer a same-day replay gets.

Deliberately **not** a partial index on `payload->>'as_of'`: that expression is
spelled differently on Postgres and SQLite, so it would be enforced in production
and silently absent under test — the one arrangement guaranteed to let the defect
come back unnoticed.

### 5.1 THE ONE — the deleted-prior guard and the uniqueness constraint cancel each other. Measured this session.

## 6. Round 2 — B1 closed, m3 taken, m2 deferred to DEF214, m1 routed to Saiful

Submitted at ``0b385dc2``. B1 was the round; the rest is bookkeeping.

### B1 — the fix is the constraint, not the lookup

The audit's MUT-E ("the fix": add `deleted_at IS NULL` to `find_by_dedupe_key`)
is **not** the fix, and running it is what showed why. That filter changes which
row the loser of a race is handed; it does not stop the collision, so the write
still never happens, no row is ever created, and both counters stay frozen. It
converts a silently wrong id into an `IntegrityError` out of the route — louder,
still broken, and a user who deletes today's Finding still cannot regenerate it.

The invariant that was wanted all along is **"at most one LIVE Finding per user
per entry type per day"**. A tombstone is not live. So `uq_journal_dedupe`
becomes a **partial unique index on `deleted_at IS NULL`** (migration
`d3e4f5a60029`), which keeps `c2d3e4f50028`'s whole argument — only a database
constraint can serialise two concurrent writers — and applies it to the set it
should always have covered.

`WHERE deleted_at IS NULL` is spelled identically on both dialects, so this
carries none of the risk that made an expression index on `payload->>'as_of'`
unacceptable in the original migration. Rendered both, rather than asserting it:

```sql
-- alembic upgrade --sql, postgresql dialect
ALTER TABLE journal_entries DROP CONSTRAINT uq_journal_dedupe;
CREATE UNIQUE INDEX uq_journal_dedupe ON journal_entries (user_id, entry_type, dedupe_key) WHERE deleted_at IS NULL;

-- CreateIndex from the model metadata, sqlite AND postgresql dialects, identical:
CREATE UNIQUE INDEX uq_journal_dedupe ON journal_entries (user_id, entry_type, dedupe_key) WHERE deleted_at IS NULL
```

Two consequences the constraint change creates, both handled:

1. **`find_by_dedupe_key` still needs the filter, for a different reason than the
   auditor gave.** Once a day has been deleted and regenerated, a tombstone and a
   live row hold the *same* key — and that lookup is `LIMIT 1` with no
   `ORDER BY`. Under a genuine race (two POSTs after a delete both clear the
   idempotency read, one inserts, the other loses) the loser could be handed the
   tombstone: B1 exactly, through the door the partial index deliberately leaves
   open. Pinned by a store-level test rather than by a race, so it is a statement
   about the contract and not about scheduling luck.
2. **`restore` refuses when a live row holds the key.** `deleted_at` is now a
   predicate, which makes undo the one operation that can turn a legal state into
   an illegal one — delete, regenerate, undo, and two live rows claim one day.
   Returning `False` refuses the undo; the alternative is an `IntegrityError`
   raised out of a route whose contract is a boolean.

### 6.1 The regression test is the deliverable, as the auditor said

`test_deleting_todays_finding_and_regenerating_writes_a_live_row_and_spends_budget`
drives the real route through the real persistence path — the `wired` fixture
genuinely cannot see this, because `_fake_generate` seeds `dedupe_key=None` and
never reaches the constraint. It asserts the counter, not only the id:
`daily_used == 2` and `trial_findings_used == 2`.

**One correction to my own first draft, recorded because the auditor will
otherwise wonder why the cap is not asserted:** I wrote a third POST expecting

third POST is a same-day **idempotent replay** of the now-live row (§5.6, which

The cap can only bite across days or books, and is covered by the existing
`daily_used` tests. The assertion now says what is actually true and load-bearing:
the replay returns the live id and charges nothing.

### m4 — the store distinguishes the outcomes; the route stops guessing

`restore()` answered `False` for four different facts and `journal.py` turned all
four into `404 "entry not found"`. Three of them really are "not found". The
fourth — refused because a newer live row holds the key — is an entry that
**exists, is the caller's, and is not restorable**, which is a 409.

`RestoreOutcome` (`RESTORED` / `NOT_FOUND` / `SUPERSEDED`) is returned by a new
`restore_with_reason`; `restore()` keeps its boolean contract and delegates, so
all seven existing call sites are untouched. The route branches on the enum and
returns `409 journal_restore_superseded` with a message a user can act on.

The regression test asserts the 409 **and** that both reachable 404 paths are
still 404 — an unknown id and a live (never-deleted) entry. Without that half the
change could have turned every failed undo into a conflict, which is the
mirror-image defect.

**Not done, deliberately:** no Dart-side handling. The client already surfaces
`friendlyError(e, action: 'undo that delete')` for any failure, so the user is
told something went wrong either way; what changes here is that the API now tells
the *truth*, which is what a log or a support question will read. Wiring
`journal_restore_superseded` to specific copy is a UI change for the CR that
gives the undo path more than a 4-second snackbar.
