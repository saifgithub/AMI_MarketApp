## 1. Why this lane exists — and the case for returning it

Rev 4's named audit scope is **M02 and M05 only**: *"Independent audit remains
warranted for the estimator module (M02) and rule engine (M05) specifically"*
(governing pin, § Risk class). Every other CR136 lane, including this one, is a
risk-based extension raised by Saiful. So the honest position first: **if the
argument below does not hold, return this lane as misallocated effort.** I would
rather be told that than have a chunk waved through on momentum.

The argument is that Rev 4 drew the audit boundary around *arithmetic* and
*judgement* and left out **adjudication** — and adjudication is where this
project's defects actually live.

1. **M04 is the only layer that decides what is TRUE versus what is UNKNOWN,
   and nothing downstream re-derives it.** M02 proves the numbers are computed
   correctly given inputs. M05 proves the thresholds fire correctly given
   metrics. Neither answers *should this number have been published at all*.
   That is `sufficient`, and `sufficient` is set in exactly one place —
   `portfolio_health.py`. M06 strips insufficient blocks before prompt assembly
   (`portfolio_finding.py:214`, `kept = [b for b in metric_blocks if
   b.get("sufficient")]`), M09 renders the insufficient card state off the same
   flag, and M06's allow-list registers every numeric leaf of every *surviving*
   block as citable. A block wrongly marked sufficient is therefore not merely
   displayed — it becomes a number the LLM is *licensed* to narrate. There is no
   second opinion anywhere in the chain.
2. **Every failure mode in this module is dark, not red — this project's
   recurring class.** There is no path here that 500s on a bad decision; each
   gate fails toward a plausible number. Remove the T/N gate and 50-name Euler
   risk shares off a 126-day window still sum to exactly 1.0 and read as an
   answer. Remove the dropped-weight ceiling and a book with 80% of its money
   unmeasured still gets a complete Tier-1 report — `partial: true` is even
   still set, so the honesty flag is present and the numbers simply describe a
   fifth of the money. DEF210 stayed dark ~10 weeks. DEF038 and DEF063 each
   shipped dark for months for want of one `docker-compose.yml` line. This
   module has more silent-failure surface than the two Rev 4 named, because the
   two Rev 4 named both *produce* numbers whereas this one *authorises* them.
3. **M04 widened a machine-readable enum after its consumers were written, and
   nothing guards it.** The module doc pins four `insufficient_cause` values;
   the code emits **six** — `feed_unavailable` and `zero_variance` were added
   later, the first out of CR040 reasoning at the M01 seam, the second from a
   degenerate-covariance find. M09's audit produced
   `backend/tests/unit/test_cr136_dart_parity.py` precisely because a
   backend↔Dart enum that drifts is DEF210's exact shape — but that guard covers
   `METRIC_VALUE_UNIT` and the three refusal codes, **not this enum**. And one
   consumer is already an exact-equality branch on the old set:
   `mobile/lib/widgets/portfolio_health/health_card.dart:430-434` shows the
   benchmark explanation only when `insufficientCause == 'benchmark_misaligned'`,
   so a benchmark **feed outage** (`feed_unavailable`) removes the beta tile with
   no note at all, while the card stays in its populated state because
   `portfolio_volatility` is still sufficient. Read from source at that line; I
   did **not** execute it in a widget test, and it is M09's file, not mine — but
   M04 is the layer that minted the sixth value.
4. **Three of this file's five commits were written under another module's
   acceptance criteria.** `71cf6b7f` and `2a653673` are *M05 lane* commits that
   modify `portfolio_health.py`; `e40d441b` is an *M07 lane* commit that added
   the root `holdings` rows. The M05 auditor found the R2b weight-basis

5. **This module has never run outside pytest.** Measured this session:

## 2. What the module is, and the decisions worth challenging

### 2.1 `sufficient: false ⇒ value AND standard_error null` is enforced centrally, not per call site

`_block()` (`portfolio_health.py:149-152`) nulls `value`, `standard_error` and
`t_eff` whenever `sufficient` is false, **regardless of what the caller
computed**. The reason it is one place rather than nine is that `null` has to
have exactly one meaning downstream, and a second meaning would make the
contract unenforceable. Worth challenging: today most call sites already pass
`None`, so the observable thing the central guard still catches is a leaked
`t_eff` on an insufficient block. That is a real leak (it is a payload leaf, and
M06 registers leaves of surviving blocks) but it is *not* the leak the guard was
written for. Ask whether the guard is now load-bearing or merely belt-and-braces
— and if the latter, whether that is a reason to keep it or a reason to notice
that the call sites are doing the work.

### 2.2 There are TWO refusals, and the module doc pins only one

The doc's pipeline step 1 is the mock-**history** refusal
(`use_real_market_data=false`). The code adds a second, in `_gather_inputs`
(`:742`): if `portfolio_marks_snapshot` reports a mock price source, refuse with
`reason="marks_source=mock_walk"` and load nothing further. The reasoning is in
the docstring: marks resolve through `FallbackProvider(cache(yfinance) →
mock_walk)`, so a Yahoo rate-limit puts random-walk prices into **every weight
in the payload** — risk shares, HHI, cash fraction, the LEVEL denominator — while
the report still says `status: "ok"`. Verified by reading
`sim_engine.py:307-314`: `_aggregate_source_from_quotes` returns `"mock_walk"`
on an empty quote set *and* on any mixed set, so a partially-mock fan-out is
caught too. This guard exists in no spec document. Challenge whether it belongs
here or at M01/M07, and whether one test is enough for a guard whose absence
publishes a confident risk analysis of a book that does not exist.

### 2.3 Three denominators coexist on purpose — this is the M06-round-0 failure class

- `full_invested` — every risky holding, dropped ones included. Denominator for
  `weight_concentration` (HHI), for the root `holdings[].invested_weight_pct`,
  and for the correlation-pair weight floor.
- `covered_invested + cash` — survivors plus cash. Denominator for the **LEVEL**
  weights that σₚ and beta are computed on (`:370-373`). σₚ describes the sleeve
  the engine actually measured.
- `full_invested + cash` — the root `total_value` and the root `cash_fraction`
  (R4's input, accounting).

All three are in the module doc §3.3 and all three are deliberate. The exposure
is that a block whose `basis` field reads `"total_value"` is computed over
`covered_total`, while the root key literally named `total_value` is the *full*
figure. In a partial book those differ, and a consumer that multiplies a
`total_value`-basis σₚ by the root `total_value` to get a dollar figure
overstates it. I checked the two consumers I can see — nothing in
`mobile/lib/widgets/portfolio_health/` reads `.totalValue` (it is parsed at
`models/portfolio_health.dart:323` and read nowhere), and `portfolio_rules.py`
computes its own total-value percentages from `invested_weight_pct` and the cash
fraction rather than from this key. So it is latent, not live. M06's round-0
blocker was a units mismatch of the same family that rendered "1969.00%".

### 2.4 The benchmark is a LEG of one Σ, and it is never re-gridded

SPY enters the same `ewma_covariance` call as the holdings (`:344-347`), so beta
and σₚ can never come from different windows — and `cov_risky` is a **slice** of
the joint matrix (`:348`), never a second estimate, which is valid because
`cov[i][j]` depends only on rows `i` and `j`. Usability requires the benchmark to
survive the bad-print screen **and** to contribute ≥ `T_MIN` returns to the
**inner join** (`:314-317`). Rev 4 estimator pin 5 exists because the
pre-existing `portfolio_stats.beta()` validates *length*, not *dates* — a
benchmark of the right length on the wrong grid is the silent wrong beta. No
forward-fill, no calendar padding, no positional alignment.

### 2.5 `weight_concentration` is UNCONDITIONALLY sufficient — and that has a downstream consequence

`sufficient=True` is hardcoded (`:559`), because counting weights needs no price
history. It also never goes `partial`, and it counts dropped holdings, so a book
the engine could not measure is not flattered by having its unmeasurable names
excluded from its own concentration figure. The consequence I want challenged:
since M04 always emits this block in an `ok` payload, M06's
`InsufficientContextError("no sufficient metric block survived the strip")`
(`portfolio_finding.py:216`) appears **unreachable from any `ok` payload with
holdings**. Which means a Finding can be generated on a book where the only
measurable fact is HHI. Whether that Finding reads honestly is M06/M09's
problem, but M04 is the layer that made it possible. I read this call path; I
did not execute it.

### 2.6 The estimator-definition constants are deliberately NOT in the constants module

`EWMA_LAMBDA`, `TRADING_DAYS_PER_YEAR`, `TRADING_DAYS_PER_MONTH` and
`BAD_MONTH_Z` live in `app/trading_math/portfolio_risk.py:35-38`, next to the
estimator that uses them, and `portfolio_health.py` imports them from there —
even though the module doc §3.1 lists all four as belonging here. One definition,
no drift, and M02's hand-off forbids duplicating them. This is a doc-vs-code
disagreement resolved in the code's favour and documented in the constants
module's own docstring.

### 2.7 The `_PCT` suffix on rule thresholds is load-bearing

M04's payload is in decimal fractions; M05's rule API works in percentage
points. The constants module names every percentage-point threshold with a
`_PCT` suffix (`RULE_R1_FIRE_TOP_RISK_SHARE_PCT = 41.5`, not the doc's
`R1_FIRE_RISK_SHARE = 0.415`) and says why in a comment: *"an unlabelled
0.415-vs-41.5 mix-up is not a visible error — it is a rule that silently never
fires."* The one place M04 itself crosses the boundary is the correlation-pair
floor (`:625`, `RULE_R2B_MIN_PAIR_WEIGHT_PCT / 100.0`) — worth checking that
this is the only crossing.

## What I would attack if I were the auditor

Ordered by what I think is most likely to be real.

1. **The `insufficient_cause` enum widened from 4 to 6 with no parity guard, and
   one consumer branch is already exact-equality on the old set.** `feed_unavailable`
   and `zero_variance` have no copy key anywhere (`grep` over `app_en.arb` finds
   keys for `short_window`, `dropped_weight_exceeded`, `t_over_n`,
   `benchmark_misaligned` and no others). M09's card handles the top-level case
   with a documented generic fallback (`health_card.dart:250-256` — good), but
   the *notes* list does not: `health_card.dart:430-434` gates the benchmark
   explanation on `== 'benchmark_misaligned'`, so a benchmark feed outage
   removes the beta tile silently while the card stays populated. **If you find
   one thing in this lane, I expect it to be this.** The fix shape already
   exists — extend `test_cr136_dart_parity.py` to a third contract over the
   `INSUFFICIENT_*` constants.
2. **The inner join does not require a CONTIGUOUS grid, and the annualisation
   assumes one trading day per observation.** `_join` (`:302-307`) intersects
   dates; `_returns_on` (`:186-190`) then takes consecutive ratios *on the joined
   grid*. A thinly-traded holding whose series has gaps yields multi-trading-day
   returns treated as daily, and `annualize_vol` multiplies by √252
   unconditionally (`trading_math/portfolio_risk.py:36` even comments that
   calendar-day padding understates σ, which is the same assumption from the
   other side). Nothing checks the ratio of `window_days` to `n_observations`,
   though the engine already computes both. **I did not quantify the effect and
   am not going to state a number I have not measured** — but the direction is
   an overstated σ, and it is silent. Boundary to probe: two survivors whose
   intersection is every other trading day, ≥126 joined returns.
3. **`_gather_inputs`'s mock-marks refusal has exactly one test, and I could not
   revert-proof it cleanly** (§4 explains why: reverting it drives the test into
   a live `price_history.get_daily_series` fetch, so the mutation is
   network-dependent rather than a clean assertion kill). It is the highest-value
   guard in the module and the least protected. Mutate it yourself in an isolated
   worktree with `get_daily_series` monkeypatched.
4. **`predicted_vol_for_snapshot` runs the entire engine per user.** It calls
   `build_health_context(user_id)` (`:822`) with no `sim`, so it resolves the sim
   engine, re-fetches marks, re-fetches 2y of daily history for every holding
   plus SPY, and rebuilds Σ — once per user, from M03's daily snapshot job
   (`portfolio_snapshot.py:80-82`). Correct, and side-effect-free as specified.
   Ask what it costs at N users and whether the daily-history store's TTL
   actually amortises across users within one job run. I did not measure this.
5. **`weight_concentration` is always `sufficient: true`, which appears to make
   M06's `InsufficientContextError` unreachable** from any `ok` payload with
   holdings (§2.5). Confirm or refute from the M06 side; if I am right, a Finding
   can be generated on a book whose only measurable fact is HHI.
6. **The `basis: "total_value"` label vs the root `total_value` key** (§2.3).
   Latent today because nothing multiplies them. Ask whether "latent" is good
   enough for a payload that is explicitly an LLM input, given that M06 registers
   every numeric leaf of every surviving block as citable.
7. **The bad-print screen runs BEFORE the short-history rule** (`:270-284`), so a
   holding with 40 closes and a phantom print is recorded as `data_quality`, not
   `short_history`. The module doc pins that order and I believe it is right (a
   spike-and-reversal is a data fault whatever the series length), but the
   recorded `reason` is what M09 shows the user, so it is a copy decision wearing
   a pipeline-order costume.
8. **`_prepare` silently dedupes by date, last-wins** (`:177-183`,
   `by_date[iso] = float(close)`). If M01 ever serves two rows for one date (an
   adjusted and an unadjusted close, say), one is chosen with no record. Check
   whether M01's store can produce that.

## 7. Round 4 — DEF213's guard, and a false-fire test that was vacuous

Round 3 came back COMPLETE with zero findings. This round is not a fix to a
finding; it is the deferred half of §5.4 / §6's "still owed" line. Attack 2 was
raised in this lane at round 1, confirmed by the auditor as "real and correctly
reasoned", graded by neither of us, and filed as **DEF213** with a full
measurement once M04's tree was free. Saiful decided the shape on 2026-08-03:
**"guard now, correct later"** — ship the loud-degradation half, make the
re-annualisation its own CR. The re-annualisation is now **CR139**.

Submitted at `b335bfb4`. Delta: engine + constants +
engine tests (backend), cause const + card branch + one ARB key + card test
(mobile), plus the M07 comment correction below.

### What the guard is

`_returns_on` takes close-to-close ratios on the grid `_join` produces, and
`annualize_vol` multiplies by √252 unconditionally, so a return spanning k
trading days is annualised as though it spanned one. The engine already computed
both numbers that expose this and published them in every block; it simply never
compared them:

```python
elif window_days / t_obs > GRID_DENSITY_MAX:
    estimator_cause = INSUFFICIENT_SPARSE_GRID
```

Ordering is deliberate. `short_window` is checked first and wins, so a young book
is never told its feed has holes — pinned by
`test_a_short_grid_reads_short_not_sparse`, which needed a fixture change of its
own: a thinned holding with fewer than 126 of its own closes is **dropped**, and
the join then quietly reverts to the full grid, so the first version of that test
asserted `499 < 126` and failed. `_book_thinned(..., private=…)` gives every name
a disjoint private tail so the intersection can be short while nobody is dropped.

### Where 1.65 comes from, and the part I got wrong first

The gappy side was already measured when DEF213 was filed. The clean side was
not, and it is **not 7/5 = 1.40** on a real calendar, because market holidays
remove trading days without removing calendar days. `def213_guard_threshold.py`
(new, in `verification_fleet/`): 10y of daily bars, 8 instruments across both
venues and four asset classes. All 8 share **one** calendar — 2513 of 2513 dates,
so a clean book's join loses nothing for calendar reasons — and over 11,038
rolling windows at every length the engine consumes the ratio is mean 1.4535,
**max 1.4921**.

The tail that actually threatens a false fire is a multi-day closure, and it is
**constructed, not observed**: Yahoo's free endpoint caps that ticker at ~10y
today (`period="20y"`, `period="30y"` and any explicit pre-2016 `start` all
answer with an EMPTY frame rather than an error), so 9/11 and Sandy are outside
the fetchable window. Deleting L consecutive sessions from the real calendar
reproduces the shape: worst **1.5556 at L=5**, longer than any US closure since
1933. 1.65 clears that by 6.1% and the observed max by 10.6%.

What it catches: above **11.9%** of one holding's days missing. That is not a
round number either — it is just past where the bias overtakes the estimator's
own error bar (F17: 6.29–6.37% relative at T=126, against a measured bias of
+6.1% at 5% missing and +7.9% at 10%). Below that line a gap costs less than the
sampling noise the metric already carries; above it the bias dominates.
