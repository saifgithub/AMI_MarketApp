## 1. What this is and why it exists

CR129 ships a Day Trader preset that sets every risk limit permissive, on Saiful's
reasoning that *"if we do not let them fail in a safe environment, they will fail with
real money."* CR131's argument is that **a preset which only removes limits is a faster
way to lose with nothing learned** — a user who switches it on, loses steadily and draws
no conclusion has had exactly the real-money experience this product exists to replace.

So: compute the user's own before/after record across the preset boundary, and place it
beside the published research baselines.

## 2. THE AUDIT DIMENSION IS THE HONESTY RULES, not the arithmetic

The arithmetic is ordinary. What can go wrong here is the product telling a user
something it has not earned. CR131's spec makes four demands and they are the acceptance:

**(a) Never fabricate a comparison from a thin sample.** A user three days in has no
annualisable return and must be told *"too early"* — carrying **no figure at all**, not
a zero, not an extrapolation. Thresholds are `MIN_TRADES_FOR_COMPARISON = 10` and
`MIN_ELAPSED_DAYS_FOR_COMPARISON = 14`, required on **both** sides of the boundary.
Mutation-proven: forcing `_meets_threshold` to `return True` turns 2 tests red.

**(b) Do not moralise.** No grade, no warning, no copy telling the user they are doing
badly. The 11.4-vs-18.5 gap is more persuasive than any sentence we could write, and a
lecture invites the reader to dismiss the data with it.

**(c) It must work honestly for the user who is WINNING.** No special-casing. A winning
user gets the same shape, beside the plain fact that <1% sustain it and that a short
winning window is Barber & Odean's own proposed mechanism for the overconfidence that
drives excess trading.

**(d) Baselines carry provenance.** US 1991–1996 and Taiwan 1992–2006 retail equity, so
nothing implies the baseline describes this user's market.

**Please attack (a) and (c) hardest.** (a) is where a plausible-looking number gets
invented; (c) is where a "helpful" special case would quietly turn a measurement into a
judgement.

## 3. Cohort detection

Boundary is the **earliest** `MANDATE_EDIT` journal entry whose summary marks the preset
applied (`mandate.py:154` writes it). No such entry ⇒ not in the cohort, nothing
computed. Mutation-proven: stubbing that lookup to `None` turns 7 tests red.

Worth checking: the summary string is the coupling between `mandate.py` and this
service, and **nothing structurally enforces that they agree** — if CR129's copy is
reworded, cohort detection silently returns empty and every user looks like a
non-participant. I judged a shared constant the better fix but did not make it, because
`mandate.py` is CR129's file and CR129 is still `in_progress`. **If you think that is
the wrong call, say so — it is the weakest seam in this CR.**

# Round 2 — the MAJOR was mine to have fixed, and I argued my way out of it

`VERDICT: AWAITING_FIXES (round 1)` — 1 MAJOR, 2 MINOR.

**I flagged this seam myself in §3, said a shared constant was the better fix, and then
did not make it** — reasoning that `mandate.py` is CR129's file and CR129 is
`in_progress`. A first audit pass agreed with me and returned COMPLETE. **A second pass
declined to take my word, ran the adversarial test, and it changed the answer.**

The exploit, reproduced: rewording `mandate.py`'s summary to *"…preset now active — …"*
— still containing `"Day Trader preset"`, the only substring CR129's own adjacent test
checks — left the **entire 2589-test suite green** while `compute_day_trader_outcomes()`
silently returned `not_in_cohort` for a user who had just switched. That failure is
indistinguishable from "nobody has tried the preset", which is the shape you never
investigate because it looks like an honest zero.

**Why none of my tests could have caught it, which is the part worth keeping:** every
CR131 test drives the marker through a helper built *from the constant itself*. They all
agree with each other by construction. A test that sources its input from the thing
under test cannot detect drift in that thing — it is the vacuity failure in a shape that
looks like coverage.

And "CR129 owns that file" was the wrong reason to stop. There is an active
`coder.api-CR129-BE` worktree editing that exact copy right now, which makes the drift
*more* likely, not a reason to leave it.

## Fix — structural, not detective

`DAY_TRADER_JOURNAL_MARKER` and `DAY_TRADER_JOURNAL_SUMMARY` now live **once**, in
`day_trader_preset.py` — the preset's own module, because the preset is the thing both
sides are describing. `mandate.py` imports the summary; `day_trader_outcomes.py`
re-exports the marker. **No literal copy survives anywhere** (`grep` for the string
outside that module returns nothing).

Re-running the auditor's exact mutation now leaves cohort detection working, because
both sides move together. That is the intended outcome: the drift is no longer
*detected*, it is *impossible*.

The auditor's `test_cr131_cohort_marker_coupling_pin.py` is kept and registered in
DEF141's `MIGRATED_PINS` — the constant makes drift impossible today, but the pin is
what fails loudly if someone re-introduces a second copy.

## MINOR 1 (fixed) — my register row contradicted the code

`CR131.row.md` said the elapsed-days floor was **14**; the shipped code says **7.0**. I
wrote 14 from my own build brief and never checked it against the implementation. A
