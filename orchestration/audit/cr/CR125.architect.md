## 1. What shipped

**Token format.** `scaffold:<hex>:<exp>:<ver>:<sig>`, HMAC over all three
fields so `exp` and `ver` cannot be rewritten offline. The pre-CR125 3-part
signed format is **rejected outright**, not silently downgraded (CR040). New
`auth_token_ttl_days`, default 30, forwarded in compose.

**Revocation.** `users.token_version` (migration `2851822570ac`) is the
counter. `DELETE /v1/auth/session` bumps it, so sign-out genuinely revokes every
outstanding token — it was a documented no-op before. The check lives **only**
in `api/dependencies.py::get_current_user(_optional)`, deliberately out of
`parse_scaffold_token`, so that function stays a pure session-free parse and the
Supabase-JWT swap point `dependencies.py` calls out stays a one-function change.

**Mobile.** Bearer moved to `flutter_secure_storage` (iOS Keychain
`first_unlock_this_device`, Android Keystore `encryptedSharedPreferences`) with
an inline first-launch migration off `SharedPreferences`;
`android:allowBackup="false"` + `fullBackupContent="false"`; a 401-recovery
guard that fires at most once per distinct rejected bearer and skips
`/v1/auth/*`.

**A gap found while wiring it:** `/v1/auth/anon`'s bearer-trust check verified
only the HMAC, so a token just revoked by sign-out could still prove device
ownership and get a **fresh valid token re-minted** — silently undoing the
sign-out. Now routed through a dependency that enforces `token_version`.

## 2. The one I want attacked hardest — and why the build's own framing of it
   was wrong

The build flagged this as *"known, not a regression"*: a device recovering from
an expired token with no claimed credential re-bootstraps under a **fresh
anonymous user_id**, per the pre-existing A2 anti-spoofing policy.

That framing is wrong, and I think dangerously so. **This product is
anonymous-first** — most users hold no Apple/Google/email credential — and
CR125 is what gives every token a 30-day TTL. So the shape as built was: an
anonymous user opens the app on day 31, their token no longer proves
possession, `ensure_anonymous` mints a brand-new user, and their portfolio,
journal, streaks, credits and lesson progress are orphaned. No error. No
warning. The app simply looks new. It would have hit the entire alpha cohort at
once, on a timer, and "A2 policy" is a true description of the mechanism and no
defence of the outcome. Nothing about it is a security property being enforced.

**Fix:** `/v1/auth/anon` — and only that route — resolves identity through a new
`get_rebootstrap_identity_optional`, which skips the `exp` check **and nothing
else**. Signature still required, row must exist and not be suspended,
`token_version` still checked against the live row.

Each preserved property has its own test, and I want each one attacked
independently:

- **a revoked token proves nothing here, expired or not** — sign-out still
  genuinely revokes and cannot be undone by re-bootstrapping;
- **a forged token proves nothing** — `allow_expired` skips only `exp`, never
  the HMAC, so nobody can hand-write a token for a user_id they do not own;
- **an expired token still authenticates no ordinary request** —
  `/v1/mandate/*` and `/v1/auth/me` both still 401, so expiry keeps full force
  everywhere it was actually doing work.

Mutations, each reverted before the next:

```text
strict exp restored     -> only test_an_expired_token_still_proves_ownership_on_anon
version check dropped   -> only the two revocation tests
```

**The residual risk I am accepting, say if you disagree:** someone holding a
stolen *expired* token can re-establish that session indefinitely. I judged
this acceptable because a stolen *unexpired* token already grants full access,
and revocation kills both — so expiry's real security value here is bounding
API access, which is fully preserved. If you think the right answer is instead
a bounded grace window (accept expired only within, say, exp + 180 days), say
so; that is a small change and I would rather be told than assume.

This commit also **replaced** `test_expired_token_also_does_not_prove_ownership_on_anon`,
which asserted the destructive behaviour as though it were correct. A test can
pin a bug in place exactly as well as it pins a fix, and that one would have
defended the data loss against anyone who tried to fix it.

## 3. Other things worth attacking

- **The SharedPreferences → secure-storage migration.** It must be idempotent
  and safe if interrupted between the write and the plaintext-removal half.
  Tested both halves, but this is device state and I cannot run it on a device
  from here.
- **`parse_scaffold_token_user_id`** is used by `feedback.py` and
  `http_audit.py` for best-effort attribution and does NOT check
  `token_version` — those call sites attribute, they do not authenticate.
  Please confirm neither can be reached in a way that authorizes anything.
- **The 401-recovery guard** fires at most once per distinct rejected bearer.
  Check it cannot loop, and that a genuine revocation during an active session
  lands somewhere the user understands rather than in a silent re-bootstrap.
- **`allow_expired` has exactly one caller.** If it acquires a second, the
  whole argument above collapses. Worth a guard, and I have not written one —
  tell me if you think it needs one.

## 5. Sequencing — load-bearing, and the reason CR121 went first

This is **BREAKING**: the token format changes, so every installed build must
re-authenticate on update. Saiful accepted that explicitly. CR121's version gate
must reach devices **first** — an orphaned client that cannot authenticate and
has no forcing function to update has no way out at all.
