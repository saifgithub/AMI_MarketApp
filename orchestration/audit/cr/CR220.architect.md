## What and why

The Concierge interview asks seven questions and derives a full `Mandate`. Settings exposed the
**risk half** of the result as editable and rendered the **identity/goal half** as `_ReadOnlyRow`
(`settings_screen.dart:329-337`), with `display_name`, `learning_style`, `risk_quotes` and both
ticker lists not surfaced at all.

**The backend was never the obstacle.** `PATCH /v1/mandate/{user_id}` already accepted every one of
these fields — none is in `CLIENT_UNWRITABLE_MANDATE_FIELDS` — so they validated, versioned and
journalled fine and nothing in the client offered the control. That makes the feature half of this CR
mostly client work, and it means the entitlement boundary Saiful asked about ("settings set by
payment status are not a user self-change") already existed as DEF179's set and is reused verbatim
rather than reinvented.

Four latent defects sat in the same fields and were folded in on Saiful's ruling rather than filed
separately:

- **(a) the compliance-default inversion.** `_parse_constraints` returned `long_only` /
  `liquid_only` as bare keyword hits, so "No hard rules" stored `False` for both while
  `Compliance` defaults them `True`. **An onboarded user came out strictly LESS constrained than one
  who never onboarded**, and the `or Compliance().model_dump()` guard at the call site could never
  fire because the dict is never falsy.
- (b) `timezone` is an abbreviation ("GMT+8"), not the IANA id the spec requires.
- (c) `users.locale`/`timezone` are always `en`/`UTC` (`bootstrapAnon` omits both).
- (d) `display_name` is always the literal `"Trader"` — `detected_display_name` is never assigned
  anywhere in the codebase.

Per Saiful's ruling the **capture side is untouched**: (b), (c) and (d) are addressed by making the
values user-correctable, not by changing the interview.

## The judgement calls I most want a second opinion on

**1. The backfill tightens a live safety control, and I argued against it before implementing it.**
I recommended fix-forward-only; Saiful ruled backfill-everyone ("one population, one meaning").
I implemented the ruling. What I want attacked: the *blast radius*. Every affected user gets
`long_only=True` and `liquid_only=True` written, which can refuse a trade they expect to work. My
mitigations are a per-user journal entry naming the change and the remedy, a real version bump so it
appears in history, dry-run-by-default, and an `--only-untouched` flag that restricts to v1
mandates. **I have not run it against real data** — Alpha has a live experiment and I did not touch
it. The affected count is therefore UNMEASURED, and the CR doc says so. If the auditor thinks a
tightening backfill must not ship without that count measured first, I would take that as a MAJOR
and I would not argue.

**2. My opt-out parser is a keyword heuristic and I widened the failure toward "stay restricted".**
`"want to short" / "allow short" / "allow me to short"` sets `long_only=False`; anything else leaves
the schema default. I explicitly do NOT infer the opt-out from the bare word "short", because the Q7
chip itself reads *"ONLY long positions (no shorting)"* and freeform *"I don't want shorting"* is a
request FOR the restriction. So an unrecognised phrasing means the user stays restricted and has to
change it in Settings. That is the safe direction, but it IS a behaviour regression for someone who
would previously have been unrestricted by accident — attack whether the phrase list is too narrow.

**3. `Path.BOTH`'s three new prompt branches are agent-behaviour text riding a settings CR.**
Saiful ruled "wire it" over "omit it". The News/Macro branch was the risky one: CR147 Tier A.5
deliberately softened the LONG_HORIZON text because the agent has **no macro feed**, and asking it to
weigh the cycle invites it to supply one from training memory. My BOTH branch asks for structural
reads too, so I carried that warning into it verbatim in substance. **I have not run a live Room with
`path=both`** — no promotion, and the vLLM box is in use. The wording is reasoned, not measured.

**4. `toPatchJson` now ALWAYS sends `ticker_allowlist`, including null.** It had to, or a cleared
allowlist could never reach the server (the backend deep-merges, so an absent key means "keep what
was stored"). That change is what surfaced the regression below, and it is the widest-blast-radius
line in the mobile diff.

## The regression my own tests caught, which review did not

`_save()` sent `compliance` on **every** save — the condition was `_localCompliance != null`, and
`_initFrom` always populates it. Harmless while the payload was six bools the server merged back to
themselves. It stopped being harmless the moment `toPatchJson` started always carrying
`ticker_allowlist`: **an untouched save would have PATCHed `null` over a real allowlist and silently
deleted a safety rule.** The fix compares against the server's object, which then required real value
equality on `ComplianceFlags` (`==` was identity, so every `copyWith` looked like a change).

I am flagging this rather than burying it because it is the exact class this repo keeps filing —
a control that degrades silently — and because it means my first version of this CR shipped a bug
that only an integration-level test would find.

## Four things I found by attacking my own code after writing the lane file

Both are committed as separate fixes rather than folded silently into the feature commit.

1. **Ticker lists were neither deduped nor bounded.** `['AAPL','AAPL','aapl']` cost three DB lookups
   and produced the error text `unknown ticker(s): AAPL, AAPL, AAPL`. And nothing capped the list,
   so an arbitrarily long array meant an arbitrarily long lookup loop on every PATCH. Now deduped
   order-preservingly and capped at 200 (far above any hand-curated list; the cap bounds the work,
   it does not shape the feature). Two new guards.
2. **The backfill was only ever tested through its helpers.** `flags_to_repair` and
   `disclosure_summary` had guards; `main()` — the thing that actually WRITES to every affected
   user's mandate — had none, so the script as a script had never been executed. Now driven end to
   end on the fixture DB: dry-run writes nothing, `--apply` repairs and bumps the mandate to v2
   (a real, visible version), and a re-run reports `affected users : 0` (idempotent). **Mutation:
   dropping the `if args.apply:` guard so the dry run writes turns
   `test_dry_run_reports_but_writes_nothing` red** — without that test, a broken preview flag would
   have silently written to every user on what the operator believed was a rehearsal.
3. **The full suite went RED on my i18n change, and I nearly submitted without running it.**
   I hand-copied the 38 EN strings into `app_ar.arb` / `app_ms.arb` as placeholders and reasoned —
   in this very lane file — that visibly-English is louder than a fluent wrong translation. That
   reasoning is right and the method was wrong: **DEF295 exists precisely to catch it.** Its guard
   (`test_def295_seeded_translations_are_marked.py`) failed on both locales, because an English
   string hand-copied into a target ARB is indistinguishable from a hand translation, so
   `translate_arb.py` skips it **forever** — the key is present, DEF137's parity guard is green, and
   the Arabic screen renders English permanently. The supported path is
   `scripts/translate_arb.py --seed-missing`, which writes the same English but records each key in
   the `@@x-ami-seeds` map so the translator picks it up later. Re-seeded that way: 20 i18n guards
   green, 825 seed entries in `app_ar.arb` including all 38 of mine.

   **What this cost and what it proves.** The backend count I first had in hand was
   `2 failed, 5655 passed … exit=1`. Both failures were mine. If I had read the pass count instead
   of the exit code I would have submitted a red suite as green — which is DEF326's exact history,
   the reason the promotion gate now reads the exit code for the operator. I am recording it rather
   than quietly re-running, because "the architect self-tested" is only worth anything if the times
   it caught something are visible too.

4. **`flutter analyze` flagged an unused optional parameter in my own test file** — the stand-in API
   client took a `known` set nothing ever passed. Now a const. This is why the analyze number below
   is quoted from a clean re-run: my first reading of it was against a machine running three heavy
   jobs and the output was truncated by buffering, so I re-ran it rather than quote a partial.

## Backward compatibility with installed builds (the DEF294 question)

`infra/PROMOTION_HOLD.md` exists for the case where a backend change breaks the clients already in
the field, because the backend ships by rsync and the client ships through a store days later. I
checked CR220 against that shape rather than assuming it was fine, and I claim **no hold is owed**:

- **The old client's `toPatchJson` omits a null `ticker_allowlist`** (`if (tickerAllowlist != null)`).
  The backend deep-merges, so an absent key preserves the stored value — an old client can neither
  clear nor corrupt an allowlist it does not know about.
- **The old client always sends `ticker_blocklist: []`**, since nothing ever populated it. Run
  against the new validator, that exact payload is **accepted** (verified in-process, not reasoned:
  the full six-bool + empty-blocklist body an old build sends returns clean and normalises to `[]`).
  The empty-list refusal is scoped to the ALLOWLIST only, where `[]` would mean "nothing tradable".
- **The new read-path fields are additive.** An old client parses `primary_goal` / `horizon` / `path`
  / `learning_style` as opaque strings it renders in a read-only row, so a value it has never seen
  (`both`, `story`) displays as itself rather than crashing or inverting — the DEF294 failure was an
  old client *misinterpreting* a changed payload, and there is no equivalent here.
- **The backfill only tightens `long_only`/`liquid_only`**, which the old client both reads and
  displays correctly; it is a value change, not a shape change.

The one thing an old client cannot do is *use* the new controls, which is the normal state of any
backend-first ship. **Worth attacking:** whether any installed build round-trips a GET body straight
back through PATCH — that would now carry `ticker_allowlist` and could trip the empty-list refusal.
I did not find such a call site (the only PATCH builder is `_save()`'s sparse map), but I searched
rather than proved.

## Known limits, stated rather than left to be found

- **The timezone picker is 16 regional zones, not the full IANA database.** The value is narration
  only today — every day/week boundary in the safety floor is pinned to UTC by design
  (`risk_limits.py`) — so a searchable 600-row picker is a lot of surface for a field nothing
  enforces. The user's current value is always offered even if absent from the list, so a picker
  change can never silently drop what they had. If the auditor thinks a mandate field that the
  overlay narrates should carry a real IANA value for every user, that is a fair MINOR.
- **`risk_quotes` are editable and remain INERT** (Saiful's ruling). The section says so in its own
  copy rather than letting the user assume the analysts read them.
- **AR/MS carry the EN string as a MARKED seed** for all 38 new keys, written by
  `scripts/translate_arb.py --seed-missing` so each is recorded in the `@@x-ami-seeds` map and the
  translator will pick it up. `retranslate:[ar,ms]`. Visibly-English is louder than a fluent wrong
  translation (DEF158's reasoning) — but the marker is what stops "visible placeholder" from
  becoming "permanently English", which is the DEF295 trap I fell into first (see above).
- **No device pass.** `NEEDS-DEVICE-CHECK` for the pickers, the ticker chips' delete affordance and
  the allowlist warning banner — the widget harness is not a device.
- **`custom_constraints` stays dead.** Q7 invites freeform text and `_parse_constraints` still
  hard-codes `[]`. Out of scope by ruling; the field remains a dead capture.
- **The `.arb` diff was 6300 lines in my first commit** because my rewrite reformatted AR/MS from
  4-space to 2-space indent. Amended to preserve the original formatting; the parsed content is
  byte-identical between the two commits (verified by json.loads comparison) and the diff is now 40
  lines per file. Mentioned because the auditor is reading a diff.
