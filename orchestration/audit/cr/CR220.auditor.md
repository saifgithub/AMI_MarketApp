## MAJOR-1 — `_validate_ticker_lists` writes the exact `[]` it refuses

`api/mandate.py:_validate_ticker_lists` refuses an empty allowlist outright, and the register row
states the guard as an acceptance criterion: *"an unresolvable ticker is refused and **an empty
allowlist never stored as `[]`**"*. The DoD table repeats it: *"empty allowlist 422s"*.

It does not hold. The emptiness check runs on the **raw** list, and the dedupe loop then silently
drops blank entries, so any all-blank list passes the guard and normalises to exactly `[]`:

```
plain empty list   []                 -> REFUSED 422: an empty allowlist would make nothing tradable
one empty string   ['']               -> ACCEPTED, stored as []
whitespace only    ['   ']            -> ACCEPTED, stored as []
blanks + dup blank ['', '  ', '']     -> ACCEPTED, stored as []
```

The consequence is the one your own docstring names. Run against the floor:

```
allowlist=None      -> (no allowlist violation)
allowlist=[]        -> violations=['ticker AAPL not in user allowlist']  blocked_by=allowlist
allowlist=['AAPL']  -> (no allowlist violation)
```

Every trade refused. There is no schema-level backstop — `Compliance.ticker_allowlist` is a bare
`list[str] | None` with no validator — so this function is the only thing between a caller and that
state.

**Reachability, stated fairly.** The shipped client cannot produce it: `ticker_rules_section.dart:133`
trims and drops a blank before it can become a chip, and `:73` correctly sends `clearAllowlist`
rather than `[]`. So this is not a live user-facing break today. It is a hole in the server-side
perimeter, which is where this repo insists controls must be structural — reachable by a direct API
call, a future client, or any caller that is not this build.

**Why MAJOR and not MINOR:** a stated acceptance criterion is provably false, on the Tier A surface,
and the function contradicts itself inside its own body — it refuses a value on input and produces
that same value on output. The fix is small (filter blanks before the emptiness test, or re-assert
the invariant on `normalised` before assigning) but it needs the guard that proves it, with `[""]`
in the test.

## MAJOR-2 — `--only-untouched` repairs the exact cohort it exists to protect

The script's docstring:

> *Deliberately NOT repaired: a user who explicitly asked to loosen a flag. The parser's opt-out
> phrasings ("I want to short") are honoured, and this script cannot distinguish "chose False" from
> "defaulted to False" ... so `--only-untouched` restricts the run to users whose mandate is still
> at the version onboarding produced (v1) and who have never edited compliance.*

The predicate is `if args.only_untouched and mandate.version != 1: skip`. A user who answered Q7
with "I want to short" gets `long_only=False` written **by onboarding**, at **v1**. The v1 predicate
therefore *includes* them. Two users seeded and the flag run with `--apply --only-untouched`:

```
interview opt-out (v1) long_only after run: True     <- overwritten
settings editor   (v2) long_only after run: False    <- skipped
  mandates checked   : 2
  affected users     : 1
  skipped (edited)   : 1
```

The flag protects Settings-editors and overwrites interview opt-outs — the inverse of the sentence
that justifies it, and the case the sentence itself cites. It is the only blast-radius control on
the run.

It also makes the disclosure false for that cohort. `disclosure_summary` tells them *"the onboarding
interview recorded this as off for everyone who did not name it"* — but they **did** name it. The
one group the mitigation is for receives a journal entry stating the opposite of what happened.

This is not the ruling being wrong. Saiful ruled backfill-everyone and that ruling stands; the
default run is his call. The finding is that the escape hatch offered against that ruling does not
do what it says.

## MINOR-1 — the CR040 disclosure has no enforcing check, and can be lost mid-run

The disclosure is the entire reason this tightening is allowed to be non-silent: your script header
says *"it must never be silent (CR040), so each repaired user gets a `MANDATE_EDIT` journal
entry"*, and judgement call 1 leads its mitigation list with it.

`main()` does write it — I confirmed one entry per repaired user, correctly worded. But deleting
the whole `get_journal_store().append(...)` block leaves the suite green:

```
48 passed  (test_cr220_settings_editability.py + test_concierge_engine.py)
```

and `test_cr220_settings_editability.py` is the only test file in the tree that touches the script.
The three `main()` tests you added assert the write, the version bump and idempotency — never that
anyone is told. `test_cr220_backfill_disclosure_names_the_flag_and_the_remedy` pins the *string*,
which is the same helpers-only shape you correctly called out and fixed for the write.

Second limb: the patch and the journal append are separate transactions with no rollback between
them. If the append fails for one user, or the run dies partway (a schema-invalid stored snapshot
would raise out of `Mandate.model_validate` at the top of the loop and kill it), those users are
repaired-but-undisclosed — and because the re-run is idempotent on the *flags*, they are skipped
permanently and no signal ever fires.

MINOR rather than MAJOR because the behaviour is correct today and the write path is genuinely
covered; what is missing is the guard and the recovery. House rule: an entry without an enforcing
check is not done.

## MINOR-2 — the restriction-wins-over-opt-out precedence is unguarded

Judgement call 2 asks whether the phrase list is too narrow. The list itself I accept —
`"want to short" / "allow short" / "allow me to short"`, with the bare word "short" deliberately
excluded, is the right call and your reasoning for it is correct.

The unguarded thing is the `if`/`elif` **precedence**, which is the actual safety property: that
restriction language beats opt-out language when both appear. Replacing the whole first branch with
`if False:` leaves `48 passed` — yet it changes real behaviour:

```
                                                        mutated   restored
'Long only, though I want to short sometimes'   ->      False       True
'no shorting, but allow short hedges'           ->      False       True
```

Nothing in the suite feeds a string containing both. `test_cr220_an_explicit_opt_out_is_still_honoured`
and `test_cr220_ambiguous_short_language_does_not_loosen` each test one side alone, and the chip loop
now expects `set()` for a restriction chip, so no test asserts that the long-only keyword does
anything at all.

Related, smaller: the docstring says *"The opt-OUT phrasings are matched explicitly"* as though both
restriction flags have one. `liquid_only` has no opt-out branch — it can only ever be set True, and
`"illiquid"` contains `"liquid"`, so "I want to trade illiquid microcaps" restricts the user from
precisely what they asked for. The direction is safe and Settings can correct it, so this is a
docstring-vs-behaviour mismatch rather than a defect — but the sentence should stop claiming
symmetry the code does not have.
