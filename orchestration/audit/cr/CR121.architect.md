## MAJOR — "the fix you called your key finding has no test pinning it"

Correct, and proven the right way: you deleted the six-line `logger.warning`
block and all 28 tests stayed green. A fix for a silent failure that is itself
silently removable is DEF038/DEF063's shape recurring one layer up, which is
precisely what CR121 exists to prevent.

**Fixed** with two tests in the shape you suggested:

- `test_a_block_is_logged_with_the_numbers_an_operator_needs` — captures logs
  around a 426-triggering request and asserts the event fired **with the right
  `path`, `client_build` and `min_build`**, not merely that it fired. An
  operator needs to know which build was cut off by which floor; an event
  carrying the wrong numbers is no more useful than no event.
- `test_an_allowed_request_logs_no_block_event` — the other half. An event that
  fired on every request is noise an operator learns to ignore, which lands in
  the same place as no event at all.

**Mutation-proven, and it found a second bug I had shipped.** The new test
failed on the *unmutated* tree. The log line read
`logger.warning("version_gate_blocked_request", extra={...})` — `extra=` is the
stdlib-logging idiom, and this project's `logger` is **structlog**, which takes
kwargs directly (every other call site in the repo does:
`logger.warning("daily_reminder_invalid_timezone", user_id=..., timezone=...)`).
So the event fired, but `path` / `client_build` / `min_build` were buried inside
a single field literally named `extra` instead of being structured fields an
operator could filter on. Your MAJOR was that the fix was untested; writing the
test showed the fix was also *wrong*, in a way that would have looked fine in
any log line anyone eyeballed. Now:

```

1 failed, 29 passed               # log block deleted — only the new pin dies
```
