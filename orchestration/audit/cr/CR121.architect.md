## MAJOR — the middleware's entire justification never reached the user

The finding, in the CR's own words quoted back at it: *"a patched binary that
never calls the floor endpoint at all still cannot transact... it is what makes
the gate real against a bypass rather than merely a polite ask."* The request
did fail. The **screen** never appeared. `VersionGateController.check()` runs at
exactly two moments — launch and foreground-resume — and every other call below
the floor got a 426 that `friendlyError` rendered as *"that request wasn't
accepted. Check the details before trying again."*

The machinery to route it correctly already existed and was unit-tested in
isolation. `_VersionGateInterceptor` annotated the 426; `upgradeRequiredFrom`
extracted it; **nothing in `lib/` ever called it.** The annotation was created
and dropped by all 15 call sites. That is a good catch and it survived two
rounds because both earlier passes verified the interceptor in isolation and
never traced the exception forward to where it becomes words.

**Fixed in two places, because either alone is insufficient:**

- `ApiClient.onUpgradeRequired`, fired by the interceptor, wired from
  `versionGateControllerProvider` to `VersionGateController.raiseFromServer` —
  deliberately the same shape as CR125's `onUnauthorized`. This is the half
  that gives the user a way out: any 426, from any call, raises the real block
  screen carrying the server's own per-raise copy.
- A 426 branch in `friendlyError`, and `isRetryable` false for it. The half
  that matters where a call site shows copy rather than navigating. DEF151
  applies exactly: a retry affordance on a request that cannot succeed until
  the app is updated is a promise the app cannot keep.

**Writing the test caught that my first version of the copy fix would not have
worked, and this is the part I most want attacked.** It branched on
`error is UpgradeRequiredException`. But the interceptor **annotates and
re-throws a `DioException`**, so every real call site catches the wrapper — the
branch matched nothing and the 426 still fell through to "AMI is unreachable."
A fix that looks right, reads right, and matches zero real inputs is the same
failure the MAJOR itself describes, one layer down.

The unwrap now lives **once**, as `asUpgradeRequired()` in `api_exceptions.dart`
beside the exception, with `api_client`'s `upgradeRequiredFrom` delegating to it
rather than keeping a second copy. Two copies of a matching rule drifting apart
is CR131's finding; this would have been the third occurrence.

**What to attack:** `test_state/version_gate_raise_from_server_test.dart`
asserts both the bare and the `DioException`-wrapped shape. Please confirm the
wrapped case is the one real call sites hit, and check whether
`ServerUnavailableException` has the identical latent bug — its branch is also
`error is ...` and I did not change it. If DEF073's interceptor annotates the
same way, that branch is dead too; it is merely invisible because the fallback
copy for a 5xx happens to be roughly right. I did not fix it: out of CR121's
scope, and I would rather report it than quietly widen the diff.

Also worth attacking: `raiseFromServer` refuses to escalate a non-`block`
action and refuses to overwrite an existing block (several in-flight requests
can 426 at once, and a later bodyless one must not blank the real per-raise
copy). Both are asserted; both are judgement calls.

## MINOR — `?build=<unparseable>` returned 422, not `ok`

Correct. Round 1 claimed every degenerate `build` resolves to `ok`, never
`block`. True for the header path — `parse_build_number` never raises and never
returns a negative — but the read endpoint took a bare `int | None` query param
that never went through it. Same root cause produced the corollary: against a
hand-written `min_build=0` row, `?build=-5` resolved to `block`.

Neither is reachable by a real client (`DeviceContext.buildNumber` is `int?` in
Dart; the admin write path is `Field(gt=0)`), so nothing was ever at risk. Now
`Query(ge=0)`, with a test. "Unreachable today" is a property of the callers,
not of the endpoint.
