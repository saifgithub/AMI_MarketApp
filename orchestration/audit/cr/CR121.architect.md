## 1. What shipped

The client already computed its version, shipped it on bootstrap, and let the server
store it in `users.last_app_version` / `user_devices.app_version` — and nothing ever
acted on it. This closes that loop.

**(a) `client_release_floors` — append-only, one row per raise.** Saiful's requirement
was *"message will be added for each time we move the bar,"* so the answer to "what did
we tell users when we killed build N?" has to be a row, not a memory. Active floor =
highest `min_build` among `active=true`. A bad raise is retracted by flipping `active`
false, which lets the previous-highest row govern again without losing history. Migration
`1d3f04e6d806` on `4aad7942bba0`; `alembic heads` is a single head.

**(b) Unauthenticated `GET /v1/client/release-floor`,** sibling of `/v1/health`. It must
answer *before* a session exists, because a blocked client may be too old to
authenticate at all. The server returns `action: block|nag|ok` — the decision is
server-side, so raising or retracting the floor takes effect with no client release.

**(c) `VersionGateMiddleware` → 426** off a new `X-App-Version` header, added at the
single existing choke point (`api_client.dart`'s `_AuthInterceptor.onRequest`). Exempt:
`/v1/health`, the floor endpoint itself (an already-blocked client must be able to
re-check after updating), `/v1/feedback/bug` (a stuck user must be able to say so).

**(d) `POST /v1/admin/release-floor`** behind the existing `ADMIN_SECRET` bearer, with
the footgun guard: refuses a `min_build` above the highest build ever observed across
both version columns unless `force=true`.

**(e) Mobile:** `_VersionGateInterceptor`, launch + foreground-resume check,
non-dismissible block screen, dismissible nag (at most once per app session).

## 2. The properties I most want attacked

**Acceptance — fails OPEN, on both sides, and that is deliberate.** This is an explicit
exception to CLAUDE.md's degrade-loudly rule and the CR spec says so. A fail-*closed*
gate turns any melehost outage into a simultaneous brick of every installed client,
which is strictly worse than briefly serving a stale build. Both sides wrap the lookup
in try/except. **Please attack this from the other direction than I did:** I checked
that a lookup *failure* fails open. What I want tested is whether any *successful* but
degenerate response can wedge a user — an empty table, every row retracted, a
`min_build` of 0, a malformed/absent `X-App-Version`, a `build` that fails to parse. My
claim is every one of those resolves to `ok`, never `block`. `resolve_action` returns
`ok` when either `floor` or `build` is None; `parse_build_number` never raises.

**Acceptance — the footgun guard actually guards.** `highest_observed_build` scans
`users.last_app_version` AND `user_devices.app_version` and takes the max, returning 0
when nothing parseable exists. Raising the floor above what TestFlight has approved
bricks every iOS tester with nowhere to go, so this refuses with a 409 naming both
numbers. **Worth attacking:** 0 is the "no evidence any build exists" floor, so on a
virgin DB *every* raise trips the guard and needs `force` — I believe that is correct
(you should have to say so explicitly) but it is a judgement call, not a proof.

**Acceptance — the middleware cannot 5xx the whole app.** A DB failure inside
`dispatch` is caught, logged, and falls through to `call_next`. The failure mode I care
about is the one where a bad floor lookup turns into a 500 on *every* request in the
app, which would be worse than no gate at all.

## 3. What I found reviewing the build before committing, and fixed

**A 426 reached no log anywhere.** `VersionGateMiddleware` is added *after*
`HTTPAuditMiddleware`, so it is the outer of the two and a blocked request
short-circuits before the audit log ever sees it. Raise the floor and there would have
been zero signal about how many clients you just cut off — the CR040 shape exactly. Now
logs `version_gate_blocked_request` with path, client build and floor. **Please check my
middleware-ordering reasoning independently** — Starlette's `add_middleware` builds the
stack in reverse, so I am claiming the order is CORS → VersionGate → Audit → route, and
the whole "never reaches the audit log" argument depends on that being right.

**The build reported 2655 tests; the real number is 2654.** Baseline at `70e38eea` is
2617 collected, measured in a scratch worktree per DEF159. The +37 decomposes as 35 new
CR121 tests + 2 new `test_config_compose_parity` cases for `IOS_TESTFLIGHT_JOIN_URL`.

## 4. Known gaps, declared rather than discovered

- **No numeric App Store ID exists** (the DEF100/CR084 provisioning gap), so the iOS
  store link is `settings.ios_testflight_join_url`, unset today. Unset falls back to the
  generic `https://testflight.apple.com/` page and logs
  `release_floor_ios_store_url_unconfigured`. Forwarded in compose as
  `IOS_TESTFLIGHT_JOIN_URL`.
- **No retraction HTTP endpoint and no admin.html row.** `active=false` is the
  documented retraction mechanism but today it takes a SQL statement. Not in the CR's
  explicit scope; flagging because "retract a bad raise" is the emergency path and it is
  currently manual.
- **5 new ARB keys carry English in ar/ms** with a retranslate note. Per project rule,
  this commit flags AR/MS re-translation for those 5 ids.
- **The version-gate middleware adds one indexed single-row SELECT per request.** I
  consider this acceptable because `HTTPAuditMiddleware` already does a synchronous
  `get_session()` write per request on the same event loop, so this is consistent with
  existing architecture rather than a new class of cost — the session closes before
  `call_next`, so concurrent pool pressure is unchanged. **This is reasoning, not a
  measurement.** If you think it warrants a short-TTL cache, say so; the service
  docstring argues explicitly against caching, and that argument may not survive contact
  with the per-request path.
- **Device-only behaviours are unprovable by widget test:** system back-gesture against
  the block screen, real backgrounding/resume, actual store hand-off.

## 5. Sequencing — this is load-bearing

A gate only binds builds that already contain it, so `0.1.0+57` and everything before it
is permanently ungateable. CR121 must reach devices **before** CR125's breaking token
change, or an orphaned client has no forcing function to update and no way to
re-authenticate. If you find anything that would delay CR121 shipping, say so loudly —
the cost is not CR121's, it is CR125's.
