# DEF182 — audit lane (Alpaca credential crypto: dedicated key + fail-closed + versioned rollover)

**SCOPE:** chunk — one defect with three named parts. Not a CR, so the Definition-of-Done table is
not owed here.

**SHA:** `f858a9c5` on `main`, pushed to `origin/main`. Single commit, self-contained.

**depends-on:** none.

**Already promoted.** `alpha-2026-08-19-1` (`5d2fe388`) is live on melehost and carries this code.
That is deliberate context, not a request to go easy: if the audit finds a BLOCKER, the fix ships
by re-promotion, and I would rather know.

## What and why

`app/core/secret_crypto.py` protects `users.alpaca_access_token` / `alpaca_refresh_token` at rest
(DEF044). The CR123 security review graded it a CR040 violation on two counts:

1. **One secret did two jobs.** With `ALPACA_ENCRYPTION_KEY` empty — the default, and the state
   Alpha actually ran in — the Fernet key was derived from `SECRET_KEY`, which also signs bearer
   tokens. Three other findings (H2/DEF185, H7/DEF178, M15) all call for rotating `SECRET_KEY`;
   doing so would have silently orphaned every Alpaca ciphertext row.
2. **The crypto failed OPEN.** `decrypt_secret` returned the raw stored value on `InvalidToken` or a
   missing key, so post-rotation the Alpaca client would have sent `gAAAAA…` — the ciphertext — as
   an API key, with nothing saying so.

Fix, three parts: a dedicated key required outside `env=local`; `decrypt_secret` raises instead of
returning ciphertext; an `enc::v2::` marker naming the key that wrote each row, plus
`ALPACA_ENCRYPTION_KEY_PREVIOUS` for a dual-key rollover.

## The judgement call I most want a second opinion on

**Where the loudness stops.** `decrypt_secret` raises, but
`EncryptedString.process_result_value` catches `SecretDecryptionError`, logs
`encrypted_column_unreadable` at ERROR, and returns **`None`**.

Reasoning: these columns hang off `User`, which `get_current_user` loads on **every** authenticated
request. A raise propagating to the caller would turn one unreadable credential into a total account
lockout — the user could not use the app at all. `None` is exactly "not linked", which every call
site already handles (`_require_linked` → 409 `alpaca_not_linked`; `agent_runner.py:144` and
`room_runner.py:3858` both guard on `if row.alpaca_access_token` and omit the Alpaca overlay).

**What to attack:** that this is not just the fail-open bug wearing a hat. My claim is that the
difference is real — the old code handed the *ciphertext* to the Alpaca client as if it were a
credential, whereas this hands back *nothing* and says so at ERROR — but I built both halves and
would not necessarily see it if I were wrong.

## Known limits, stated rather than left to be found

- **The rollover procedure is documented and unit-tested, never rehearsed on real data.** No
  ciphertext exists to rehearse against.
- **Legacy plaintext passthrough is retained.** A stored value with no marker is returned unchanged
  (with a warning outside `env=local`). That value genuinely *is* the secret, so refusing it would
  break a working link for no confidentiality gain — but it is a deliberate hole in "everything is
  encrypted" and belongs in the audit's view.
- **Parens-in-strings / key-shape validation:** none. Any non-empty `ALPACA_ENCRYPTION_KEY` is
  accepted and SHA-256'd into a Fernet key, so a one-character key is silently as valid as a
  32-byte one. I judged an entropy check out of scope; disagree if you think otherwise.

# Round 2 — response to the round-1 verdict

**Verdict answered:** AWAITING_FIXES (round 1) — 1 MAJOR, 3 MINOR, 0 BLOCKER.

## MAJOR-1 — fixed

You were right, and the framing that made it land was yours: the configured case is not the same
bug as the automatic one, it is **worse**. Round 1 removed the path where an *empty* key silently
fell back to `SECRET_KEY`. Setting the two equal by hand produced a row stamped `enc::v2::` — a
marker this module's own docstring defines as *"rotating SECRET_KEY no longer touches this
ciphertext"* — that the `SECRET_KEY`-derived key opens. The pre-DEF182 state at least labelled such
rows `v1` honestly. I had shipped a marker that vouches for a property nothing checked.

`_reuses_secret_key(raw)` now vets every configured value, at **both** ends:

- **Write** (`encrypt_secret`): refuses with a message that names *this* mistake. That mattered
  more than it looks — the pre-existing refusal says "ALPACA_ENCRYPTION_KEY is not set", which
  would send an operator to set it, plausibly to the same value again. The new message says
  `"...configured to the same value as SECRET_KEY..."` and tells them to generate one.
- **Read** (`_dedicated_keys`): drops the value and logs `secret_crypto_key_reuses_secret_key` at
  ERROR. A row already written that way degrades the documented way — raise → `None` → 409
  `alpaca_not_linked` — rather than opening and reassuring everybody. I considered letting reads
  through on the "don't break a working link" argument and rejected it: "it opens" is precisely the
  false reassurance, and the read path is where the false independence would be believed.

**The register-row claim you graded is retracted and rewritten.** *"H2/DEF185, H7/DEF178 and M15
can now rotate SECRET_KEY freely"* was an unconditional green light resting on an unchecked
property. It is now conditional on a check that exists, and the row says so.

## MINOR-1 — fixed, same site

With `ALPACA_ENCRYPTION_KEY` empty and `_PREVIOUS` set, `encrypt_secret` used `dedicated[0]` — the
**retired** key — stamped `v2`, no warning. Reachable from step 3 of this module's own rotation
instructions applied to the wrong variable, and the promotion that finished the rollover would then
orphan exactly the rows written in between. `encrypt_secret` now refuses that combination outright,
before the `_strict()` branch, so it refuses on a dev box too.
