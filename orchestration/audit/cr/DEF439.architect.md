## The key-format research, and why the fix is NOT a key-prefix check

Alpaca does not document key-ID prefixes. The convention — paper keys start `PK`, live keys
start `AK` — is community/observed, not a contract Alpaca promises to keep. A generation change
on Alpaca's side could invalidate a prefix rule silently, and a prefix rule alone cannot do
anything about the OAuth path at all, where the mobile app never sees a key ID.

**Measured, not assumed:** a real Alpaca paper key ID is 26 characters, its secret 44 (Architect
data point, 2026-09-25, pinned by commit `7cf861cd`,
`def439_alpaca_paper_only_link_test.dart:165-176`). No length rule exists in
`alpaca_connect_screen.dart` today, and the commit message is explicit that none should be
added — lengths vary between key generations, so a length check would be exactly the kind of
undocumented-convention trap the prefix check itself is designed around.

**The real, structural boundary is the endpoint, not the key shape**: a paper key pair gets a
401 from the live host and vice versa (Alpaca enforces this key↔host pairing server-side). The
fix's own docstring (`alpaca_connect_screen.dart:8-20`) states the reasoning directly: an
unrecognised key prefix is never refused on that basis alone; the endpoint is what actually
decides.

## The design — three independent gates, not one

1. **API-key path — recognisable-live-prefix refusal, client-side, before any network call.**
   `_isLiveKeyId` (`alpaca_connect_screen.dart:279-280`) refuses a case-insensitive `AK...` key
   ID immediately, with copy naming the reason ("That's a live-account key... paper keys start
   with PK"). This is a courtesy fast-path, explicitly NOT the structural gate — an unrecognised
   prefix is not refused here, by design (see above).
2. **API-key path — the endpoint field is restricted to a confirmed paper host.** The CR224
   free-text endpoint override field's own form validator now calls `isAlpacaPaperHost(trimmed)`
   (`alpaca_connect_screen.dart:419`) and refuses anything that doesn't resolve as paper. This
   is a UI-layer check (bypassable in principle by a modified client), backed by:
3. **API-key path — the structural gate: `validate()` calls the real endpoint, `isLinkedToPaperAccount()`
   gates what happens after.** `AlpacaClient.validate()` calls `GET /v2/account` against
   whatever `baseUrl` was submitted — a genuinely live pair against a (hypothetically bypassed)
   live-looking-but-not-actually-live host would 401 if it doesn't match, because Alpaca itself
   enforces key↔host pairing. And even if a credential is stored, `alpacaLinkedProvider` /
   `isLinkedToPaperAccount()` re-derives "linked" from `isAlpacaPaperHost(creds.baseUrl)` at
   every read — never from a stored label — so nothing downstream (Portfolio badge, trade-ticket
   destination picker, Room/1-on-1 snapshot upload) can be fooled by a credential that slipped
   past the connect screen's own gates.
4. **OAuth path — the token itself is what's checked, because Alpaca gives no other hook.**
   `AlpacaClient.validateOAuthToken()` (`alpaca_client.dart:368-383`) hits the paper host's `GET
   /v2/account` with the freshly-exchanged bearer token BEFORE `AlpacaCredentialStore.save()` is
   ever called (`alpaca_connect_screen.dart:599-623`). Alpaca's `/oauth/authorize` documents no
   `env=paper` selector — which Alpaca account (paper or live) a token resolves to is decided by
   whichever account the user was logged into in the browser when they approved the app, not by
   anything the authorize-request URL can pass. A token minted against a live account gets a 401
   from the paper host, same signal `AlpacaException.isAuthFailure` already carries for the
   API-key path.
5. **Pre-fix stored live credentials never render as an ordinary paper link.** `alpacaLinkedProvider`
   changed meaning (was "is *a* credential stored", now "is a credential stored AND does it
   resolve to a confirmed paper host") — a credential saved before this fix that resolves to a
   non-paper host now reads as **not linked**, with `alpacaStoredNonPaperProvider` driving an
   explicit "AMI now links Alpaca paper accounts only — relink" prompt in both Settings
   (`settings_screen.dart:1691-1721`) and Portfolio (`portfolio_screen.dart:2019-2063`), instead
   of silently rendering the stale live credential as though it were paper — DEF439's own root
   complaint, closed structurally rather than patched at each display site.

**D-075** (`docs/initial_specs/11_decisions/decision_log.md:689-715`, on the branch) records this
as a narrow amendment of D-071: a live/production Alpaca account can no longer be **linked** at
all, not merely refused a write. What did NOT change: D-071's core boundary (AMI never routes an
order to a live execution venue) is untouched — `submitOrder`/`cancelOrder`'s own paper-host
re-check stays as a structural backstop even though a live link should now be unreachable by
construction; CR202's device-local credential custody is unchanged; the CR224 endpoint override
still exists for a paper account Alpaca resolves to a different host, restricted to paper hosts,
not removed.

## Attack surface (please probe)

1. **No live-host reachability anywhere in `mobile/lib`.** Grepped the whole tree for
   `api.alpaca.markets` (the live host, no `paper-` segment) and for every `alpaca.markets`
   occurrence:
   ```
   $ grep -rn "api\.alpaca\.markets" mobile/lib --include="*.dart" | grep -v "paper-api\.alpaca\.markets"
   alpaca_client.dart:64:/// endpoints are `api.alpaca.markets`, no `paper-` segment. Checking by
   ```
   The only hit is a docstring comment explaining the naming convention, not a URL the client
   ever calls. Every other `alpaca.markets` occurrence is either `paper-api.alpaca.markets` (the
   default, `alpaca_credential_store.dart:35`) or `app.alpaca.markets`
   (`alpaca_connect_screen.dart:105,352` — Alpaca's own OAuth **login/authorize** gateway, which
   is correct: `/oauth/authorize` is a browser-facing login page, not the API host, and the
   resulting token is validated against the paper API host afterward via
   `validateOAuthToken()` before ever being stored — see gate 4 above). No path in this diff can
   still reach `api.alpaca.markets` for account data or writes.

2. **`isAlpacaPaperHost`'s pattern match is looser than the default host, but not exploitably
   so.** It accepts any host ending `.alpaca.markets` that also contains "paper" anywhere in the
   hostname — e.g. a hypothetical `evil-paper-api.alpaca.markets` would read as paper. This is
   still constrained to genuine subdomains of `alpaca.markets` (an attacker would need to control
   DNS under Alpaca's own domain, which is out of AMI's threat model and Alpaca's own problem if
   it happened), and it's the same predicate CR224 relies on to admit legitimate region/account
   host variants — a stricter exact-match would break that feature. Not a finding, just flagging
   the boundary for the record: this check trusts "operates under alpaca.markets and names
   itself paper," not a fixed host list.

3. **The AK-prefix refusal (gate 1) is a courtesy, not the control — confirmed by M1.** Mutating
   it out only failed 3 narrowly-scoped tests (the prefix-refusal tests themselves), not the
   broader paper-only guarantee — because gates 2–5 don't depend on it. This is by design per the
   fix's own docstring, not an oversight, but worth the auditor independently confirming that no
   downstream code silently assumes the AK-prefix check already filtered out live keys.

4. **The endpoint-field validator (gate 2) is client-side UI only** — `TextFormField.validator`
   runs on `Form.validate()`, which a modified/patched client could skip entirely while still
   calling `AlpacaCredentialStore.save()` directly. The actual backstop against that is gate 5:
   `alpacaLinkedProvider` re-derives paper-ness from the stored credential's host at every read,
   never trusting that the connect screen's own gates ran. Worth the auditor confirming there is
   no code path that reads `AlpacaCredentialStore` directly for a "linked" decision without going
   through `isLinkedToPaperAccount()` — I did not find one, but did not exhaustively grep every
   call site of `AlpacaCredentialStore.read()`/`isLinked()` outside the files this diff touches.

5. **OAuth validation order** — confirmed by reading `_exchangeCode`
   (`alpaca_connect_screen.dart:599-623`): `validateOAuthToken()` is called and awaited BEFORE
   `AlpacaCredentialStore.save()`. An exception from the validate call propagates to the
   `on AlpacaException catch` block, which sets `_error` and returns without ever reaching the
   `save()` call — a live OAuth token cannot be stored even transiently. No test explicitly
   pins the ORDER (validate-then-save, not save-then-validate-then-maybe-rollback) via a
   mutation that swaps them — worth the auditor adding one if it isn't already covered by
   `def439_alpaca_oauth_paper_validate_test.dart` (I read the diff stat, not every assertion in
   that file's 99 new lines).
