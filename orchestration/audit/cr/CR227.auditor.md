## MAJOR-1 — a LIMIT/STOP ticket silently becomes an immediate market order on the Alpaca leg

**The non-goal is written down three times and enforced nowhere.**

- CR doc Non-goals: *"No resting/limit/stop orders on the Alpaca leg. Market orders (immediate
  fill) only, for both 'Alpaca only' and 'Both.' AMI's LIMIT/STOP/STOP_LIMIT tickets remain
  AMI-sim-only."*
- CR doc design note (`:109-113`): *"mixing 'AMI's resting order triggers three days later' with
  'Alpaca fills immediately today' for the same ticket is a correctness problem this CR does not
  attempt to solve."*
- `CR227.row.md`: *"Market orders only in v1; no resting/limit/stop."*

`_destinationLocked` (`trade_ticket_sheet.dart:302-303`) is `coverTicker != null || sellTicker
!= null`. It is **blind to `_orderType`**. `grep -n "_orderType"` over the whole file shows it
never gates the destination selector, `_submitAlpacaOnly`, or `_placeAlpacaOrder`.
`AlpacaClient.submitOrder()` takes only `{symbol, side, qty}` — there is no parameter through
which an order type or limit price *could* travel — and hard-codes `type: 'market'`
(`alpaca_client.dart:175`). The user's chosen type and limit price are discarded without a word.

The submission half-caught this and then argued itself out of it:

> "the destination selector is hidden entirely whenever the ticket is in a non-market-order state
> via `_destinationLocked`'s cover/sell gating — actually, to be precise: the selector's own
> gating is on cover/sell only; a non-market AMI order type simply never reaches
> `_submitAlpacaOnly`/`both` with an Alpaca call since `submitOrder()` itself is hard-coded
> `type: market`."

The correction is right about the mechanism and wrong about the consequence. `submitOrder()` being
hard-coded `type: market` is not a guard — it is *precisely the bug*. It does not prevent the
non-market ticket from reaching Alpaca; it is what **converts** it on arrival.

**Run, not reasoned (P24).** Driving the real `TradeTicketSheet` through its own test harness
(the lane's `_RecordingAlpacaClient`/`_FixedSim`, with `restingOrdersSupported: true` so the
order-type selector renders — the lane's `_portfolio()` leaves it false, which is why no existing
test could have caught this):

| ticket | destination | what Alpaca received |
|---|---|---|
| **LIMIT @ $1.00** AAPL | Alpaca only | `buy 1.0 AAPL` — market |
| **LIMIT @ $1.00** AAPL | Both | `buy 1.0 AAPL` — market |
| **STOP** AAPL | Alpaca only | `buy 1.0 AAPL` — market |

**Consequence, and why this is MAJOR rather than MINOR.** On the "Both" path with a LIMIT ticket
the two legs diverge into states the user is not told apart:

- AMI sim: `resting: true` — a resting limit order. Nothing has executed.
- Alpaca: a **market order, filled now**, at whatever the market price is.

The outcome list renders `AMI SIM — BUY AAPL — resting order placed.` beside `ALPACA PAPER —
BUY 1 AAPL — accepted.` (`_placeAlpacaOrder`, `:698-702`; `_simOutcomeMessage`, `:724-726`).
Neither message names an order type. A user who set a limit of $1.00 on a $250 stock, precisely
to *not* buy at the market, reads two green lines and believes both legs are waiting at their
limit. One of them already bought.

This is CR040 "degrade loudly" inverted: a silent fallback whose failure mode is the user holding
a false belief about a position they now own. It is also the house rule — *an entry without an
enforcing check is not done*. The non-goal was stated, and the enforcing check was never written.

**Not reachable only in theory.** Nothing gates the order-type selector against a linked Alpaca
account: `restingOrdersSupported` is server-driven (`sim_providers.dart:146`, `book.supported`),
and on Alpha it is on. Any linked user who picks LIMIT and Alpaca in the same ticket hits this.

**What would close it.** Any one of these, plus a test that fails without it:
1. Force `TradeDestination.amiSim` whenever `_orderType != SimOrderType.market` — i.e. widen
   `_destinationLocked` to `|| _orderType != SimOrderType.market`, which also hides the selector
   and matches what the CR doc says already happens; or
2. Refuse in `submitOrder()` — give it the order type and throw `AlpacaOrderRejected` on anything
   non-market, mirroring how the paper-host rule is enforced structurally rather than by UI; or
3. Ship the Alpaca leg as a genuine limit order (out of scope for v1 per the CR's own reasoning).

(1) or (2) is a small change. (2) is the stronger one and matches this CR's own best instinct —
`submitOrder()` already re-enforces the paper-host rule itself rather than trusting the UI. The
same argument applies here verbatim.

## What I attacked that held

**1. The paper-only boundary holds — including against attacks not in the submission.**
`isAlpacaPaperHost` (`alpaca_client.dart:42-45`) is `host.endsWith('.alpaca.markets') &&
host.contains('paper')`. I probed 20 URL shapes. **No live-reaching URL is admitted**, across ten
attack shapes: the suffix check defeats `paper-api.alpaca.markets.evil.com`; `Uri.host` strips
userinfo, so `https://paper@api.alpaca.markets` → `api.alpaca.markets` → refused; query
(`?paper=1`), fragment (`#paper`), backslash-userinfo, trailing-dot (`api.alpaca.markets.`) and
explicit-port forms all refuse. `paper-api.alpaca.markets` and CR224 account-prefixed overrides
are admitted. Uppercase is normalised.

The lane nominated this heuristic as its weakest point and asked whether `GET /v2/account` should
have been read instead. My answer: **the current check is adequate and the fail direction is
safe.** Its permissive cases (`notpaper.alpaca.markets`, `paperclip.alpaca.markets`) all require a
host Alpaca itself controls — not attacker-reachable. It fails unsafe only if Alpaca issues a
paper host without "paper" in it, which is their documented convention and not a silent change.
And `submitOrder()` enforces it itself, independent of the UI (`:162-167`) — the right instinct.

**2. The mandate floor is not bypassable by destination.** `_submitAlpacaOnly` calls `preview()`
first and returns on `preview == null || !preview.accepted` (`:649-668`), so `_placeAlpacaOrder`
is unreached. The "Both" path's Alpaca call sits inside `if (result != null && result.ok)`
(`:604-618`) — structurally unreachable on a mandate rejection, not merely guarded. A null preview
(network failure) refuses rather than proceeding, which is the correct fail-closed direction.

**3. Backend genuinely stays order-free, and the DEF145 guard still bites.** The range touches
exactly one backend file, the DEF145 test; zero backend production code. `grep -rn
"v2/orders\|v2/positions/" backend/app/` → nothing. I checked the guard was not weakened: diffing
assertion-bearing lines over the range yields **one** changed line, and it is inside a message
string. No `assert`, no `_ALLOWED_CALLS`, no matcher changed — prose only.

I then confirmed it still catches what it exists to catch: appending an
`await client.post(f"{creds}/v2/orders")` to `alpaca_service.py` fails **two** independent
assertions (`test_no_public_function_reads_as_a_write`,
`test_nothing_in_the_backend_calls_an_alpaca_order_endpoint`); 3 passed on revert. Rewriting the
rationale rather than deleting the guard was the right call and the pins are intact.

**4. D-071 is a genuine narrowing, not an erosion.** D-071 (`decision_log.md:513+`) permits an
order only to a confirmed paper account, checked by endpoint and explicitly "never by trusting a
stored label" — which is what the code does. D-004 is marked *partially amended* with a
cross-reference, not superseded, and restates that live remains strictly forbidden. `CLAUDE.md`'s

## MAJOR-1 — CLOSED, at both layers, both proven independently

The fix is the two-layer shape I recommended, and the lane took the stronger option rather than
the cheaper one:

1. **UI layer** — `_destinationLocked` (`trade_ticket_sheet.dart:315-317`) now also fires on
   `_orderType != SimOrderType.market`. The destination selector disappears for a non-market
   ticket, same treatment as cover/sell, and `destination` is forced to `amiSim`.
2. **Client layer** — `submitOrder()` takes a `required SimOrderType orderType` and throws
   `AlpacaOrderRejected` on anything non-market **before reading the credential store**
   (`alpaca_client.dart:169-176`), so it fires independent of link state and host.

**I re-drove my exact round-1 attack table against the fix, and widened it.** Six cells —
`{LIMIT, STOP, STOP_LIMIT} × {Alpaca only, Both}`, including STOP_LIMIT which I did not test in
round 1 — each driving the real `TradeTicketSheet`. I used the **worst-case ordering**: pick the
Alpaca destination *first*, then change the order type, so `_destination` is already non-`amiSim`
when the lock engages. That is the ordering a UI-level hide is most likely to miss.

| ticket | destination | selector after type switch | Alpaca received |
|---|---|---|---|
| LIMIT | Alpaca only | hidden | *(nothing)* |
| LIMIT | Both | hidden | *(nothing)* |
| STOP | Alpaca only | hidden | *(nothing)* |
| STOP | Both | hidden | *(nothing)* |
| STOP_LIMIT | Alpaca only | hidden | *(nothing)* |
| STOP_LIMIT | Both | hidden | *(nothing)* |

All six: the Alpaca call is entirely unmade. Round 1's table produced a market order in every
cell; round 2 produces none.

**The client layer verified separately, because no widget test can reach it.** The lane's
`_RecordingAlpacaClient` *overrides* `submitOrder` wholesale, so every widget test bypasses the
real guard — the UI hide is the only thing those tests can prove. I therefore exercised the real
`AlpacaClient` directly with a **genuinely linked account on a valid paper host**
(`paper-api.alpaca.markets`, asserted to pass `isAlpacaPaperHost` in-test), so neither the link
check nor the host check could be what refused. All three non-market types still threw
`AlpacaOrderRejected`. The second layer does real work; it is not riding on the first.

**Both layers proven load-bearing by single-guard mutation:**

```
mutation: client `if (orderType != SimOrderType.market)` -> `if (false)`
  -> kills the lane's own order-type test AND my independent linked-paper-host test
  -> reverted, green

mutation: `_destinationLocked`'s order-type clause removed (back to cover/sell only)
  -> reopens the round-1 defect in ALL SIX cells of my table
  -> "MAJOR-1 regression: STOP LIMIT reached Alpaca via BOTH", etc.
  -> reverted, green
```

Removing either clause alone reopens a hole the other does not cover — which is the definition of
two independent guards rather than one guard written twice.

**`orderType` is `required` with no default.** That matters: a default of `market` would have
reproduced the original defect's exact shape for any future caller who forgot the parameter.
Only one call site exists (`trade_ticket_sheet.dart:707`) and it passes the live `_orderType`.

**The harness gap from round 1 is closed too.** `_pump` now takes
`restingOrdersSupported` (default `false`) with a comment naming why: the order-type picker is
gated on it, so no round-1 test *could* have rendered a LIMIT chip. That was the reason the
original defect was invisible to a green suite, and the lane fixed the cause, not just the
symptom.
