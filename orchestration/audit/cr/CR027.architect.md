## Adversarial focus — what to try to break

**(a) Degrade-loudly: the row survives every push failure mode.**
`backend/app/services/notification_service.py::notify()` (L51-79) writes the
`NotificationRow` (L62-71) UNCONDITIONALLY, before `_attempt_push()` (L73) is even called
— push outcome cannot roll back the row (separate `get_session()` context, no shared
transaction). Try: empty `onesignal_rest_key` → `_attempt_push` returns `"not_configured"`
after a `logger.warning("notification_push_not_configured", ...)` (L93-100) — never a
silent no-op (CR040). Rate-limited (2nd call within 60s, or 4th within an hour) →
`"rate_limited"` (L86-91), row still exists. `httpx.RequestError` → `"failed"` + warning
(L118-123). OneSignal `>=400` → `"failed"` + warning with truncated body (L125-131). Test
file: `backend/tests/unit/test_notification_service.py` (8 tests) — confirm each of these
4 branches has its own test and that each asserts the row exists via a DB read, not just
the returned `push_status`.

**(b) Mandate-check reuse is narrowed correctly — not spuriously blocking, not spuriously
permissive.** `price_alert_evaluator.py::_alert_mandate_check()` (L83-101) calls
`check_mandate_compliance()` framed `side=Side.SELL, quantity=1, order_type=MARKET,
portfolio_value=0.0, current_drawdown_pct=0.0, last_loss_closed_at=None,
trade_open_timestamps=[], existing_open_risk_pct=0.0` (L100). Verify: (i) this framing
exercises allowlist/blocklist/halal/classification checks (the ones that matter for a
`price_alert`, which never submits an order) but never engages cooldown/sizing/
over-trading/open-risk branches — read `safety_floor.py`'s full function body
side-by-side against this call and confirm every non-allowlist branch is gated on a
condition this framing can't trigger (e.g. cooldown checks `is_buy`/timestamps present).
(ii) `_implies_short_entry()` (L67-81) is a disclosed heuristic, not a discovered existing
check — confirm it's applied ONLY to `manual_below` alerts with no `trade_ref` under a
`long_only` mandate, matching the one case the CR doc names, and that a blocklisted/haram
ticker's alert is correctly blocked regardless of this heuristic. Test file:
`backend/tests/unit/test_price_alert_evaluator.py` (19 tests) — try deleting the L100 call
entirely and confirm a blocklisted-ticker test goes RED (structural wiring proof, not just
the pure function in isolation — same class of gap CR026's round-2 MAJOR caught).

**(c) No duplicate fire across evaluation cycles.** `_fire_alert()` (L151-176) is an
atomic conditional `UPDATE ... WHERE id=? AND status='active'` (L154-156) — the real guard
against a race, not merely "the loop only reads active rows." Test: run
`evaluate_price_alerts()` twice in a row against the same breaching alert (mocked quote
unchanged) and confirm the second cycle does not re-fire / re-notify (row is `fired` after
cycle 1, excluded from cycle 2's `WHERE status='active'` scan at L166).

**(d) One quote fetch per ticker, off the event loop.** `evaluate_price_alerts()` (L178+)
groups active alerts by ticker and calls `await asyncio.to_thread(provider.quote, ticker)`
once per ticker (L197) — confirm no per-alert redundant fetch, and that a fetch failure
for one ticker skips only that ticker's alerts (never fires on missing/stale data) without
aborting the whole tick. The `httpx.post` inside `_attempt_push` is also `to_thread`-wrapped
at the evaluator's only async call site (L228-230) — confirm `notify()` itself is NOT
async (it's a sync function; the CLI calls it directly, unwrapped, by design — only the
evaluator's async context needs the wrapper) and that
`test_no_blocking_io_in_async_routes.py`'s pinned-count entry for
`notification_service.py: 1` still matches (grep the file for `httpx\.` call sites).

**(e) Migration is single-head, sqlite+postgres portable.**
`backend/alembic/versions/8a4ce4f8abc3_notifications_price_alerts.py`, `down_revision =
e5f6a7b80025` (verified via `alembic heads` during build — NOT the `d4e5f6a70024` an
earlier stale Plan assumption had guessed). Confirm `alembic heads` still returns a single
line at `8a4ce4f8abc3` and both new tables use the portable `Uuid`/`JsonB` TypeDecorators
from `app/db/base.py`, not raw Postgres types.

**(f) Schema-owner boundary.** `backend/app/db/models.py` and
`backend/alembic/versions/` are `coder.api`'s exclusive `schema_owner: true` domain per
`orchestration/dispatch/roster/coder.api.md` — this CR edits both directly as the
architect (single-session build, no coder.api lane spawned for it). Checked for collision
before submitting: `git diff main...lane/<X>.coder.api -- backend/app/db/models.py
backend/app/agents/safety_floor.py backend/alembic` returns EMPTY for all 9 currently
active `coder.api` worktrees (`BE-AGENTS`, `BE-GUARD191`, `BE-MANDATE`, `BE-MINOR`,
`CR129-BE`, `DEF062`, `DEF098`, `SEC-BATCH1`, `SIM-DEF166`) — none touch these paths, so no
live lane will have a rebase conflict against this schema addition. `safety_floor.py`

**(g) OneSignal SDK wiring — login/logout at every identity-change call site.**
`mobile/lib/state/auth_providers.dart`'s `_pushLogin`/`_pushLogout` are called after every
`_commitUserChange` (bootstrap, `verifyMagicLink`, `signInWithApple`, `signInWithGoogle`)

**(i) `RadioGroup<T>` migration is a genuine API fix, not cosmetic.**
