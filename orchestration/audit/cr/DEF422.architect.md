# DEF422 — audit lane (Portfolio tab counts: combine AMI + Alpaca)

**SCOPE:** def

**TIER: B.** Mobile-only. Changes what number a tab bar displays and adds two small
inline glyphs (spinner/warning); no auth, billing, migration, or compliance-perimeter
change. Every existing provider read, l10n key set beyond the two additions, and every
pre-existing rule/test (§4.1 open-trade placement, DEF146's per-segment-clip geometry
rule, DEF170's fade cue, CR188 slice 3's holdings/transaction-log split) is untouched
and still covered by its original tests. A MAJOR finding raises it to Tier A.

**SHA:** `e820cb6c` on branch `worktree-agent-ae74dbcc7cbccb0a4`, worktree of `main` at
merge-base `5308b1b5`. Review with `git diff 5308b1b5..e820cb6c -- mobile/ docs/defect/
docs/forward_planning/CR234_alpaca_orders_view/`.

**depends-on:** none. **Promoted:** no (mobile; ships in the next TestFlight/Play build
after this verdict).

## What and why

Saiful, from a TestFlight +111 screenshot of the Portfolio screen: *"The 'order' header
was showing '0' orders. But I still have one order open in alpaca."* The screenshot shows
the tab bar reading `POSITIONS 4 •` / `ORDERS 0` / `HISTORY 28` while the Orders tab's
own body, under the purple ALPACA PAPER badge CR234 added, lists an open `BUY 10 ASML
LMT $1700.00 GTC ACCEPTED` — the tab's own count and its own rendered list disagreed.

**Root cause:** CR234 shipped this AMI-only **on purpose**, documented at the
`_PortfolioTabBar` call site and in `docs/forward_planning/CR234_alpaca_orders_view/`:
Alpaca's counts come from async `FutureProvider`s, and a combined badge would either
show a number that changes shape mid-load or silently drop Alpaca's contribution on
every loading/error frame — the exact "quietly wrong count" CR040 forbids. **Saiful's
report overrides that call**: an AMI-only count that reads "0" while a real Alpaca order
sits open is the worse lie. CR040 exists to prevent exactly this class of quietly-wrong
number, and the honest-but-partial count fired that same guard from the other direction.

## Changes

- **`_TabCount`** (new, `portfolio_screen.dart`) — holds an AMI int and an optional
  `AsyncValue<int>` for the matching Alpaca provider. `displayCount` is `ami +
  (alpaca?.valueOrNull ?? 0)` — the loading/error state is carried separately by
  `marker`, never folded into the number, so the printed count is never a
  combined-looking figure that is actually partial.
- **`_PortfolioTabBar`** converted `StatelessWidget` → `ConsumerWidget`. Gates on
  `alpacaLinkedProvider` first (unlinked/still-resolving → AMI-only, unchanged from
  pre-DEF422); once linked, watches `alpacaPositionsProvider` (POSITIONS),
  `alpacaOpenOrdersProvider` (ORDERS), `alpacaClosedOrdersProvider` (HISTORY) — the same
  three providers `_AlpacaPortfolioSection`/`AlpacaOpenOrdersSection`/
  `AlpacaHistorySection` already read for each tab's own body, so the badge can never
  disagree with what's rendered below it. HISTORY's Alpaca side is deliberately
  uncapped (matches `AlpacaHistorySection` — every closed order) rather than mirroring
  AMI's own 25-cap view default (`_closedTradeCap`), which is a display convenience with
  its own SHOW ALL escape hatch, not a fetch limit, and counting to it would make the
  badge disagree with "how many Alpaca orders actually closed."
- **`_TabCountMarker`/`_TabCountMarkerIcon`** (new) — `null` (nothing to show),
  `loading` (an 8×8 `CircularProgressIndicator`, `strokeWidth: 1.5`), or `error` (a 10px
  `Icons.warning_amber_rounded`, `hexAmber`). Deliberately not `HexPulseLoader` (the
  app's usual motif) — that widget is sized for a card body (28px+) and would itself
  overflow this 32px-tall segment. Each carries a `Semantics(label: …)` from two new
  l10n keys (`portfolioTabCountLoading`/`portfolioTabCountError`) so a screen reader
  gets the honest state too, not just the visual.
- **`_TabSegment`** gained a `marker` param, rendered between the label and the existing
  `trailing` (the live pip) — both can render at once; they are separate facts (fetch
  state vs. live risk).
- **Label overflow fix:** `_TabSegment`'s `Text` gained a
  `FittedBox(fit: BoxFit.scaleDown)`. §9 acceptance 7b's pre-existing overflow test only
  ever measured 1–2 digit AMI-only counts; a 3-digit combined count is newly reachable
  under DEF422 and the fixed-width assumption broke at 320dp/1.3x. **This does not touch
  DEF146's rule** (no per-segment `ClipPath`/border — the parent still clips the whole
  bar as one shape); it only scales the label's own text, which DEF146's docstring never
  addressed.
- **Second, unrelated overflow found and fixed:** the new 320/375/430dp × 1.0x/1.3x
  sweep also tripped a pre-existing `RenderFlex` overflow in
  `PortfolioEquityChart`'s "WINDOW RETURN +x.xx%" inner `Row` (`portfolio_equity_chart.
  dart:183`) — a file this DEF does not otherwise touch, whose own doc comment only
  ever measured 1.0–1.15 scale at 390dp. Fixed with the same `Flexible`+ellipsis pattern
  already used elsewhere in that file (the label wraps in `Flexible`, the numeric run
  does not, matching the file's existing convention), rather than left live or dodged
  around in the test.
- **CR234's own doc** (`CR234_alpaca_orders_view.md`) updated: the "Tab-count decision"
  section renamed to record the reversal, quoting Saiful's report and stating how
  DEF422 resolves CR040's original objection (a marker, not a silently-partial number)
  rather than ignoring it.
- **New l10n keys**, both `retranslate:[ar,ms]`, seeded via `scripts/translate_arb.py
  --seed-missing` (never hand-copied) then `flutter gen-l10n`.

## What the existing "•" means (Saiful's screenshot: "POSITIONS 4 •")

Not a literal bullet character — it's `_LivePip`, a 6px flat-top hex dot rendered as
`trailing` on the Positions segment whenever `hasOpenTrade` is true (a holding, short,
working order, or resting order — "money at risk right now", CR188 slice 3). It is
**unrelated to and unaffected by this fix**: a separate boolean computed in `_body`
from `SimState`/`SimPortfolio`, unchanged by DEF422. Both it and a new count `marker`
can render on the same segment at once (label → marker → live pip, in that order,
matching "count, then is that count still settling, then is there live risk").

- **6 no-overflow tests**: 320/375/430dp × 1.0x/1.3x, heavy AMI profile (12 held/5

  `flutter analyze`'s existing DEF146 hex-bar geometry untouched, checked directly on
  the Positions landing tab as pumped (not dodged to another tab) plus again after
  switching to Orders.

**How the two overflow bugs were actually found:** the new sweep initially failed at
320dp/1.3x with a `RenderFlex overflowed by 22 pixels` error whose `debugCreator`-style
trace (captured via a temporary `FlutterError.onError` override during triage, removed
before finalizing — not in the diff) named `portfolio_equity_chart.dart:183` — the
"WINDOW RETURN" `Row` — not the tab bar. Fixed there, re-ran, confirmed the tab bar's
own label was the second, separate cause at the same viewport/scale via the same
technique, fixed with `FittedBox`.

**Mutation-check (manual, no automated Dart mutation tool in this repo):** three
mutations against `_TabCount`/`_PortfolioTabBar`, each applied, run, and reverted in
turn:

1. `displayCount => ami` (drop Alpaca's contribution) — killed: all 3 combine tests
   fail (`HISTORY 2` not found, etc.).
2. `displayCount => alpaca?.valueOrNull ?? 0` (drop AMI's contribution) — killed: 19 of
   28 tests fail (nearly the whole DEF422 suite, including the unlinked baseline).
3. `final linked = true;` (ignore `alpacaLinkedProvider`, always treat as linked) —
   killed: the unlinked-stays-AMI-only test fails (marker icons appear where none
   should).
4. `marker` getter returns `null` unconditionally (drop the loading/error branches) —
   killed: all 4 loading/error tests fail (spinner/warning icon not found).

All four restored to the correct implementation before the final `flutter analyze` /
`flutter test` run quoted above (i.e. those runs are against the real code, not a
mutant).

## Attack surface (please probe)

1. **The three Alpaca providers this DEF newly reads on `_PortfolioTabBar`
   (`alpacaPositionsProvider`/`alpacaOpenOrdersProvider`/`alpacaClosedOrdersProvider`)
   are `autoDispose`.** `_PortfolioTabBar` is always mounted (not behind the
   `IndexedStack`), so it watches all three continuously regardless of which tab is
   selected — confirm this doesn't create redundant network traffic beyond what
   `_AlpacaPortfolioSection`/`AlpacaOpenOrdersSection`/`AlpacaHistorySection` already
   trigger for their own tab bodies (Riverpod should dedupe identical provider watches
   within one `ProviderScope`, but worth an independent check given the tab bar watches
   unconditionally while the corresponding body only renders when its tab is selected).
2. **Count vs. rendered-list parity** — the core guarantee this DEF exists to restore.
   Confirm on a real linked paper account that the ORDERS badge number always equals
   the count of rows `AlpacaOpenOrdersSection` actually renders (not just in the test
   fixtures here), including edge cases: an order that fills between the count read and
   the list read (a real race, not simulated in these widget tests), and a
   `pending_cancel` order (counted as open per `AlpacaOrder.isClosed`'s own exclusion
   list — confirm that's still the right side of the line for a *count*, not just for
   the cancel-button gating it was written for).
3. **Loading/error honesty under a real slow/flaky network** — the widget tests
   simulate "still loading" with an unresolved `Completer` and "failed" with a
   synchronous throw; neither reproduces a slow-then-succeeds real request. Worth a
   manual pass on melehost or a throttled connection to confirm the spinner actually
   appears and clears rather than the combined number popping in with no transition a
   user would notice as "it just changed."
4. **Unlinked-account posture** — confirm a user who unlinks an Alpaca account
   mid-session (not covered by these tests, which only start unlinked or start linked)
   correctly drops back to AMI-only counts rather than freezing on a stale combined
   number; `alpacaLinkedProvider` is `autoDispose`, so this likely self-resolves via
   normal invalidation, but worth confirming against the actual unlink flow.
5. **Overflow guard's real bound** — the 6 no-overflow tests use 120 Alpaca items per
   tab (a 3-digit combined count), not an arbitrarily large number. Confirm there's no
   realistic account size (Alpaca paper accounts aren't capped) where a 4+ digit count
   could reappear the same class of overflow `FittedBox` can't rescue past some point
   (it can shrink indefinitely, so this is a soft concern, more "does it become
   illegibly tiny" than "does it overflow").
6. **`PortfolioEquityChart` fix is genuinely out-of-scope-but-fixed** — confirm the
   `Flexible` addition on `l.portfolioEquityCurveWindowReturn` doesn't change that
   label's truncation behavior on a real long-translated string in AR/MS (ellipsis was
   added, previously absent; the English string is short enough this is unlikely to
   ever trigger, but AR/MS wording is out of this session's control).
