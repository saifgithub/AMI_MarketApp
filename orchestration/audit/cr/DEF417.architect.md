# DEF417 — audit lane (deterministic `liquid_only` enforcement)

**SCOPE:** chunk (backend only — `liquid_only` has no mobile-side representation to change; the flag is already rendered read-only in Settings)

**TIER: A.** This adds a new branch to `check_mandate_compliance`, the uncoachable safety-floor function every trade (SimEngine submit/preview/short-open, the Room's scripted path, the Room's live-PM override) is checked against. `liquid_only` defaults `True` on `Compliance`, so this branch is live for essentially every existing mandate the moment it ships — the widest blast radius of any DEF417-adjacent change.

**SHA:** `6205dcd2` on `worktree-agent-ac80fb31f19dd7500`, parent `abd76ee8` (this worktree's tip, itself already ahead of `main`). Review with `git show 6205dcd2` or `git diff abd76ee8..6205dcd2` — 14 files, 1451 insertions / 13 deletions.

**depends-on:** none. **Promoted:** no — needs `/promote-to-alpha` plus a live classification refresh (see "What ships dark until the next refresh" below).

## What and why

DEF417 row (`docs/defect/_registry/DEF417.row.md`): the mandate's `liquid_only`
flag ("ONLY liquid names (no microcaps)", default `True`) was rendered into
every PM/Trader prompt (`overlay_generator.py:268`,
`concierge_engine.py:592`) but `safety_floor.check_mandate_compliance` — which
DOES deterministically enforce `halal`/`esg_lite`/`no_fossil_fuels`/
`no_tobacco_alcohol_gambling`/`long_only` — had no corresponding branch.
Prompt instructions are not controls (CLAUDE.md, CR038); the alpha LLM is a
refusal-stripped build, so the gap was worse than the general case.

**The fix**, full detail in `docs/defect/DEF417_liquid_only_enforcement.md`:

- New `app/schemas/liquidity.py` — `LiquidityVerdict`/`LiquidityStatus`, a
  four-state resolver mirroring `ClassificationVerdict` (DEF061). Two
  thresholds: `MICROCAP_FLOOR_USD_M = 500` (the SAME number
  `overlay_generator.py` already narrated — now IMPORTED from this module
  rather than duplicated, so shown == enforced) and
  `ILLIQUID_AVG_DOLLAR_VOLUME_USD = 1_000_000`.
- `ClassificationUniverse` (the DEF061 sourced sector/industry snapshot)
  gains `market_caps`/`avg_volumes` maps and a `resolve_liquidity(ticker,
  price=...)` method, populated in the SAME daily classify pass
  (`_network_classify`'s new `market_caps_out`/`avg_volumes_out`
  side-channels read `info["marketCap"]`/`info["averageVolume"]` from the
  SAME `yf.Ticker(t).info` call already open for sector/industry — zero new
  sockets). Persisted on two new nullable JSON columns on
  `ClassificationUniverseSnapshotRow` (migration `def417a0b0c0d1`, chained
  after the actual current head `cr230a0order0log` — verified by scanning
  every `down_revision` in `alembic/versions/` for one with no referrer).
- `check_mandate_compliance` gets one new branch (4e, right after the
  DEF061 fossil/sin/esg_lite loop): `liquid_only` + `proposed.is_buy` →
  resolve against `classification_universe.resolve_liquidity(t, price=...)`,
  where `price = proposed.limit_price or quotes.get(t)` — the SAME fallback
  the existing single-name-cap pricing (step 6) already uses.
  `ComplianceResult.liquidity_verdict` carries the verdict on the wire
  (`ComplianceBlock`, `_compliance_json`), same shape as
  `sharia_verdict`/`classification_verdicts`.
- **One deliberate divergence from the DEF061 pattern, and the main thing to
  probe:** `LiquidityVerdict.is_blocking` returns `True` only for `EXCLUDED`
  — NOT for `UNAVAILABLE`. The three DEF061 flags block on UNAVAILABLE (the
  screen "pauses" by refusing every trade), and they can afford to because
  they default `False` — an outage only silences the minority who opted in.
  `liquid_only` defaults `True`, so the same blocking-on-outage rule would
  refuse a BUY for nearly every mandate in the app the moment the daily
  refresh lags or `CLASSIFICATION_SCREEN_ENABLED` is off. DEF417 routes
  UNAVAILABLE to `ComplianceResult.advisories` instead — disclosed loudly,
  never silently, never blocking.

## Attack surface (please probe)

1. **Threshold choice.** $500M market cap / $1M average daily dollar volume
   — both are the SAME numbers already narrated in the PM/Trader prompt
   overlay pre-DEF417 (the $500M literal existed in
   `overlay_generator.py::_MICROCAP_FLOOR_USD_M` before this DEF; DEF417 only
   made it enforced and imported). The $1M/day figure is new — I did not
   find an existing narrated number for it to inherit, so I picked it from
   general retail-illiquidity-screen convention (cited in the DEF doc) rather
   than a sourced regulatory figure. Judge whether that's tight enough, or
   whether it should be sourced/reviewed before Alpha, given it's a NEW
   enforced number with no prior user-facing commitment to match.
2. **Unknown data — the DEF059 direction.** UNKNOWN (ticker outside the
   ~503-name classified universe) is PERMITTED + disclosed, never blocked.
   Verify this can't be flipped by a partial-data ticker: a name with a
   market cap reading but no volume reading is judged on the cap ALONE
   (`test_resolver_judges_on_market_cap_alone_when_volume_unpriceable`) — is
   that the right call, or should a genuinely-partial reading also count as
   "insufficiently measured" and defer to UNKNOWN? I judged "a real reading
   below the floor is a real exclusion regardless of what else is missing"
   as the more defensible of the two, since the alternative (requiring BOTH
   figures) would let a real microcap through whenever only volume happened
   to be missing.
3. **UNAVAILABLE-does-not-block — the core judgment call of this DEF.** I
   made this call unilaterally (not escalated to Saiful, unlike DEF419's
   drawdown/open-risk questions) because it seemed to follow directly from
   CR040's own logic applied to the blast-radius difference, but it IS a
   product decision about how hard `liquid_only` should be enforced under
   degraded conditions, and I did not get a ruling on it. Please judge
   whether this needed escalation before shipping, and whether "advisory,
   never block" is the right resolution versus, say, blocking only once the
   classification universe has been enabled+healthy for N days (a softer
   rollout gate) or leaving it blocking-on-outage but accepting the wider
   blast radius as the honest cost of enforcement.
4. **Call-site wiring — the CR026-BE lesson.** Verify the 5 wiring tests
   actually prove what they claim: each removes/mutates the call site's
   `classification_universe=` argument (or, for room_runner, the `ctx.`
   attribute) and confirms the test goes red. I did this for one site
   (mutation evidence #4 above) as a spot-check, not all five individually —
   worth independently confirming the other four aren't passing by
   coincidence (e.g., a stale cached provider serving a non-paused universe
   despite the removed kwarg).
5. **Existing users whose holdings now violate liquid_only — does it block
   sells?** No — the check gates on `proposed.is_buy` only; verified by
   `test_sell_never_blocked_by_liquid_only`. `check_holdings_against_mandate`
   (the BL12 post-PATCH audit) was NOT extended with a liquidity check in
   this DEF — an existing microcap holding under a newly-set `liquid_only`
   mandate will not surface in that audit's `violations` list at all. Is
   that an acceptable scope cut for a DEF (vs. requiring a follow-up CR), or
   should BL12 parity have been in scope here alongside the trade-path
   check? I judged it out of scope because the DEF417 row names
   `check_mandate_compliance` specifically, not the holdings-audit sibling,
   but flagging since "does it block sells" was an explicit acceptance
   question in the brief and BL12 is the surface that would notice a
   retroactive breach.
6. **The classification screen being OFF by default in most environments.**
   `classification_screen_enabled` defaults `False`
   (`app/core/config.py:664`); melehost has it `true` (verified live via
   SSH). If a future deploy or a fresh environment forgets that env var,
   `liquid_only` silently degrades to advisory-only for 100% of mandates —
   which is DELIBERATE per point 3 above, but worth confirming this doesn't
   read as "DEF417 didn't actually fix anything" if probed against a
   mis-configured environment. `test_config_compose_parity.py` passed
   (I added no new env-driven setting — this DEF reuses
   `classification_screen_enabled`, already forwarded in
   `docker-compose.yml`), so the setting itself isn't newly at risk of the
   DEF038/DEF063 dark-feature class; the RISK here is behavioral (advisory
   vs block), not wiring.
7. **What ships dark until the next refresh.** The migration back-fills
   `market_caps`/`avg_volumes` to `{}` on existing rows. Until the next
   daily `_classification_universe_refresh()` tick runs post-promotion,
   EVERY ticker resolves liquidity to UNKNOWN (permitted + disclosed) even
   for a real microcap — not a false EXCLUDED, but also not yet actually
   filtering anything. This is the same gap DEF061/CR026 shipped with for
   their own first day. Worth confirming the promotion runbook doesn't
   silently assume enforcement is live before the first post-deploy refresh
   completes.
