## 2. What the module is, and the decisions worth challenging

### 2.1 The table IS the calendar

`price_history_daily` is `(ticker, date)`-unique; a trading day is a day a bar
exists. CR136 imports no trading calendar anywhere, deliberately. `Candle.t` →
`datetime.fromtimestamp(t, timezone.utc).date()` is the *entire* derivation
(`_candles_to_bars`, :282). `latest_trading_day()` (:485) reads the newest SPY
row and is M03's only source of "what day is it" — the seam register's
`M01 → M03` pin. Calendar padding would understate σ by √(252/365) ≈ 15%, which
is why no arithmetic is allowed to creep in.

### 2.2 The leaf provider is resolved locally — never the fallback stack

`_leaf_provider()` (:99) returns `YfinanceProvider()` in real mode,
`MockWalkProvider()` otherwise, and **`None`** when yfinance is missing —
explicitly not the keyless Yahoo path and above all not the mock walk. Reading
history through `get_market_data_provider()` (which is
`FallbackProvider(cache(yfinance) → mock_walk)`) would let one transient Yahoo
failure persist fabricated bars into the analytic history permanently, with
nothing to show it happened. Every row is stamped with the leaf that produced
it, and real-mode reads exclude `source == "mock_walk"` in **two** places
(`_load_rows:174-175` and `latest_trading_day:498-499`).

### 2.3 The bad-print gate is volatility-scaled and REPORT-ONLY

`bound = max(15 · σ̂_MAD, 0.10)`; flag on `|r| > 1.00` unconditionally, on any
non-finite/non-positive price, or on `|r| > bound` with a next-day **price**
retrace ≥ 0.60 of the move. MAD rather than a plain sd because the observation
being hunted is the one that would inflate a plain sd and hide behind the
widened bound. M01 never repairs, drops or edits — M04 decides
(`DATA_QUALITY_DROP_REASON`, `partial: true`).

### 2.4 The fetch throttle has two stamps, and one is in-process mutable state

`_should_fetch` (:313) is *stale AND not throttled*. "Stale" = newest bar older
than yesterday UTC, or fewer rows than `min_days`. "Throttled" = last **attempt**
within 6h, where the attempt stamp is `max(row.fetched_at …, _last_fetch_attempt[ticker])`.
The module-level `_last_fetch_attempt` dict exists because the stored
`fetched_at` is written only by a *successful* upsert, so a dead feed would
never arm the throttle and would be re-hit on every evaluation for every
holding, forever. That fix is real; the state it introduces is the thing I want
challenged (attack 2).

### 2.5 `fetch_failed` — the CR040 answer to "feed down" vs "young security"

`DailySeries.fetch_failed` (:148) says a fetch was attempted this call and
produced nothing. Without it, an outage and a genuinely young security are the
same empty series and the engine tells the user *"this holding does not have
enough price history"* when the truth is *"our data feed is down"*. M04 maps it
to `FEED_UNAVAILABLE_DROP_REASON`, which exists solely for this distinction.

### 2.6 `replace_foreign_rows` — a mock run must not overwrite real history

`upsert_daily_bars(..., replace_foreign_rows=False)` makes a row written by a
different provider untouchable. A local dev run in mock mode would otherwise
walk over accumulated real bars *in place* — value and provenance both — and
the damage would be invisible afterwards, because the rows still look like
ordinary history.

### 2.7 Units and basis: M01 sits below both pins

M01 stores **prices**, not metrics, so the Tier-1 fraction / Tier-2 percent /
dimensionless-ratio pin does not bind here — nothing in this module is ever
rendered. The only ratios it touches are the bad-print bounds, all decimal
fractions (`0.10`, `0.60`, `1.00`), never percent. SHARE-vs-LEVEL is M04's
question; M01 has no weights. **DEF211** (`portfolio_health.py:353/436`, M04's
call site) and **DEF212** (`portfolio_rules.py` / `portfolio_finding.py`,
M05/M06) do not live in this module; both are deliberately deferred per their
register rows and nothing is owed here.

## What I would attack if I were the auditor

**1. The write path is a check-then-insert against a unique constraint, entered
concurrently, and the module handles no `IntegrityError` at all. If you read one
item, read this one.**

`get_daily_series` (`price_history.py:382-452`) loads rows, decides to fetch,
performs the network round-trip *outside* any transaction (deliberately, :414),
then opens a second session and calls `upsert_daily_bars`, which SELECTs the
affected dates into a dict and inserts what is missing. The table carries
`uq_price_history_ticker_date`. Five things make this worth your round rather
than my assertion:

- `build_health_context` is invoked via `asyncio.to_thread`
  (`api/portfolio.py:149` and `:173`), so two concurrent card opens run this in
  two threads of one process.
- **Every** evaluation fetches SPY — `_gather_inputs` appends `BENCHMARK_TICKER`
  to the ticker list (`portfolio_health.py:752-754`). On a cold table, which is
  exactly the promote-day state, two simultaneous requests both see zero SPY
  rows, both fetch, both insert the same ~504 dates. `get_session` commits on
  exit and re-raises on error (`db/session.py:76-81`); nothing in
  `price_history.py`, `portfolio_health.py` or `api/portfolio.py` catches it.
- `price_history.py` imports no `sqlalchemy.exc` whatsoever — grep it.
- **M03, same CR, same session, DOES catch it.** `portfolio_snapshot.py:192`:
  `except IntegrityError:` with the comment *"the unique constraint is the
  backstop behind the check above; a concurrent tick losing this race is a skip,
  not a failure."* The pattern was known and applied one module over.
- **You have already found a concurrency hole in this CR** — `043995b0
  fix(CR136-M07): audit findings — concurrent POSTs bypassed the gate entirely`.
  Second occurrence of a class ⇒ `failure_patterns.md` entry *with a guard*, per
  CLAUDE.md.

The throttle does not close it: `_last_fetch_attempt` is a plain dict mutated
without a lock, and check-then-set across two threads is not atomic. sqlite +
single-threaded pytest cannot observe any of this, so if you agree it is real it
needs a threaded or live reproduction, not a unit test.

**2. `_last_fetch_attempt` is unbounded in-process state that never expires.**
PROTOCOL.md's trust-critical contract names this exact shape — *"a cache,
singleton, connection pool, background task, or anything that persists across
more than one call … does it ever refresh/expire/invalidate in the deployed
process (not only in a test that resets it)"*. It is cleared **only** by
`set_history_provider`, a test hook. Every ticker any user ever holds acquires a
permanent entry. Two questions: is unbounded-and-never-reclaimed acceptable for
a long-lived container, and does a restart releasing the throttle for every
ticker at once re-open the Yahoo rate-limit exposure the throttle was added to
close?

**3. A partially-garbage fetch is reported to the user as a young security.**
`_candles_to_bars` (:259-291) drops non-finite/non-positive closes and logs a
count — but the count never reaches `DailySeries`, and `fetch_failed` is set
only when the fetch produced *nothing*. So a provider serving 504 bars of which
400 are NaN persists 104, reports `fetch_failed=False`, and M04's short-history
rule drops the holding with `reason: "short_history"`. `FEED_UNAVAILABLE_DROP_REASON`
exists precisely because that distinction matters
(`portfolio_health_constants.py:53-56`) and this path defeats it. Is a rejection
count owed on `DailySeries`?

**4. The `replace_foreign_rows` call-site expression has no test.**
`get_daily_series:446` passes `replace_foreign_rows=source != _MOCK_SOURCE`. The
only test of that guard — `test_a_mock_run_never_overwrites_real_history`
(test:674) — calls `upsert_daily_bars` **directly** with the flag hard-coded to
`False`. `grep -rn replace_foreign_rows backend/tests` returns exactly that one
line. So on my reading the expression at :446 could be inverted or deleted with
no test going red, and the defect it guards is *silent destruction of
accumulated real history by a mock-mode dev run* — invisible afterwards, because
the rows still look like ordinary history. **I did not run this mutation**: hard
rule for this submission is no source edits while other lanes test the same
tree. Please run it; it is the mutation I most expect to survive.

**5. Trading-day derivation is only ever tested at 04:00 UTC.** Every fixture
stamps `_epoch(day)` = 04:00 UTC (test:53-55). The claim is that yfinance stamps
a daily bar at midnight exchange-tz, so the UTC date equals the trading date —
true for any exchange at or west of UTC. For an exchange **east** of UTC
stamping local midnight (Tadawul +03, Bursa +08 — both on CLAUDE.md's Markets
roadmap) the epoch lands on the *previous* UTC day and every date shifts by one,
for those tickers only. M04 then inner-joins against SPY, gets a near-empty
intersection, and reports `benchmark_misaligned` — the wrong cause, silently.
Not live today (US equities at MVP). The question is whether an invariant this
load-bearing should be asserted rather than documented (CR038).

**6. `robust_daily_sigma` returns 0.0 whenever MAD is exactly 0, and that is
reachable on real data.** Not only on the alternating fixture the tests warn
about: any holding unchanged on >50% of days (thin small-cap, a carried-forward
NAV) has MAD = 0, so σ̂ = 0 and the bound collapses to the 10% floor. A genuine
12% move with a ≥60% next-day price retrace — routine on a wide-spread illiquid
name — is then flagged and the holding is dropped for `data_quality`. The
false-positive rate was measured on 12 liquid US large-caps and ETFs (§2.8) and
is asserted for the whole holdable universe.

**7. `detect_bad_print_days` never flags index 0** — the loop starts at 1. A
garbage `adj_closes[0]` is caught only *transitively*, because index 1's `prev`
is unusable. I believe that holds and the holding still drops, but no fixture
injects at day 0; every one injects at index 90, 100, or the last bar. Confirm
the reasoning rather than the tests here.

**8. The one end-to-end "2y" test runs on a series containing Saturdays.**
`test_two_year_period_serves_daily_bars` asserts `MockWalkProvider` returns 504
bars at consecutive 86400s deltas — i.e. calendar-daily, weekends included,
which is the exact thing the rest of the module says must never exist. Harmless
as long as mock mode is refused at M04 (it is, `build_health_context:` first
branch), but confirm nothing else keys off that shape.

**9. Where I think this lane is genuinely strong**, so you can spend your time
elsewhere: the CR040 provenance story (2.2) is guarded in real mode with a
vacuity guard on the stack it excludes, both halves of `_leaf_provider`'s
real-mode branch are tested, and the bad-print detector's four bounds are each
exercised on the side that changes the verdict. Those were the previous pass's
findings and they came back closed.

All four guards are real: each mutation is killed by a named assertion
(`test_real_mode_never_serves_a_fabricated_row`,
`test_non_positive_and_non_finite_prints_are_flagged`,
`test_a_failing_provider_is_throttled_like_a_succeeding_one`,
`test_latest_trading_day_ignores_fabricated_rows_in_real_mode`) rather than by a
load or collection error, and the suite returns to baseline on restore. The two
mock-source filters are guarded **independently** — QA-A and QA-D are separate
code paths, and a single test covering only the read filter would have left
`latest_trading_day` unprotected.

**Coverage finding, stated out loud:** the kill radius is exactly one test for
every one of the four. Each of this module's guards rests on a single assertion,
so weakening or deleting that one test silently re-opens the hole — which is the
same shape as the failure the guards defend against.
