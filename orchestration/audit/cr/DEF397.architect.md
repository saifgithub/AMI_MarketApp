## What and why

When the LLM provider is merely **slow** (not down), an agent blows `room_agent_timeout_s` (180 s)
and `_compute_agent_text` substitutes `_scripted_for()` — not silence, but a complete, confident
template sentence populated with real computed figures, carrying no `[AMI …]` mark. The run reached
`COMPLETED` with `error_message=None`, a full 12-entry transcript and a **genuine, reasoned PM
verdict**, because the PM itself happened to answer. Nothing anywhere recorded that the Room was
thin.

Measured on batch `cr217-glm-1` (CAT @ 2025-08-08, provider `glm`): **6 of 10 agent calls returned
0 chars** with `latency_ms` pinned at 180000/180003/180006 and `error IS NULL`, while
`portfolio_manager` completed in 82.8 s and emitted a real verdict.

`is_llm_outage_verdict` could not catch it: it requires `reason == PM_LLM_UNAVAILABLE_REASON`, set at
one site reached only when the PM's **own** stream is empty. It is a **PM-liveness test, not a
Room-liveness test**.

The fix, in one line: **record which degradation fired, at the five sites where it is known; read it
once, where records become claims.**

- `_RoomContext.degraded_agents` — a per-run dict `AgentId.value → cause`, written by the five live
  fallback branches in `_compute_agent_text`. Five, **not six**: the scripted demo path
  (`room_runner.py`, the `else` of `if live:`) deliberately records nothing.
- `_mark_degraded` prefixes each substituted turn with an `[AMI: the <agent> did not answer this
  convene (<reason>)…]` mark, in the DEF125 / CR201 idiom.
- `Verdict.agents_degraded` stamped at the CR098 insertion point.
- `degraded_agent_count()` + `is_thin_room_verdict()` — a **sibling** of `is_llm_outage_verdict`.
- Five scorers exclude it; `backtest_report` gains exit **6** and a corrected denominator;
  `backtest_sweep`'s breaker no longer resets.
- `llm_gateway` catches `CancelledError`/`GeneratorExit` before `except Exception`.

## The judgement calls I most want a second opinion on

**1. The stamp's position is load-bearing and I chose it from reading, not from a failure.**
`enforce_safety_floor` builds a **fresh** `Verdict` on override and drops every field it does not
name (the CR214 trap, documented at `safety_floor.py:845-851`). My stamp sits at the CR098 point
(`room_runner.py:4892`), which I traced as running *after* the floor call (`:4703`), so the field
survives. `test_the_record_survives_a_safety_floor_override` asserts the shape — **but I wrote that
test, and it constructs the verdict rather than driving a real floor-override run.** If the ordering
is not what I read, or if some path reaches `_persist_run` without passing `:4892`, that test would
not tell me. **Attack this first.**

**2. `is_thin_room_verdict` returns `False` on an absent record — is that the right polarity?**
T-BACKFILL says an absent value is never inferred, so "we do not know whether this Room was thin"
must not be reported as "it was thin". The consequence is that **every pre-fix run is permanently
unclassifiable and silently scoreable**. I believe that is correct (the alternative retro-classifies
2,555+ historical verdicts from a field they never carried), but it is a decision that quietly favours
scoring over refusing, and it is the opposite of how the outage guard behaves.

**3. Threshold 3-of-12 is asserted, not derived.** I have no data calibrating it. The observed
incident was 6 of 10. One or two silent analysts is a Room that still debated — that is reasoning,
not measurement. Mitigation: the dict stores **which** seats, so recalibrating is consumer-side with
no schema change. If the auditor thinks the number should be different, or that seat identity should
weight it (the Trader vs one analyst), that is a real finding and I would take it as MINOR.

**4. The gateway change is the widest blast radius in this defect.** `except (asyncio.CancelledError,
GeneratorExit)` fires on **every cancelled LLM call backend-wide**, not just the Room's — Concierge,
brief_engine, agent_runner, price_alert_evaluator. It re-raises immediately and only sets
`error_str`, so I claim it cannot change control flow. The thing to attack: whether any caller
depended on a cancelled call recording `error=NULL`, and whether the `finally` block's
`record_llm_call` can now be reached in a state it previously never saw.

## Known limits, stated rather than left to be found

- **The `cr217-glm-1` evidence is inherited from the brief, not re-measured by me.** I did not query
  `llm_audit` — the numbers in "What and why" are the investigation's, and I could not verify them
  without touching the live stack.
- **`Verdict.agents_degraded` is `None` for any run that dies before the VERDICT phase**, because the
  stamp sits inside `if phase.label == "VERDICT"`. Those runs are already excluded everywhere by the
  `null_verdict` rung, so I judged this acceptable — but it means the field is not a record for
  non-completing runs. The transcript marks and the gateway `error` column cover those instead.
- **Pre-fix batches are unclassifiable and I did not attempt to reconstruct them.** T-BACKFILL
  forbids writing an inferred value, and the only available reconstruction (the `llm_audit`
  fingerprint joined by wall-clock proximity — `llm_audit` has no `run_id`) is an estimate. If a
  CR217 conclusion turns out to depend on knowing, that is a read-only forensic query reported as an
  estimate, never a write.
- **No mobile change and no device pass.** The mark reaches the client through the existing
  `hasAmiAnnotation` test (`room_transcript_rows.dart:40`) and the verdict is serialised wholesale on
  both SSE paths, so I claim zero client work is owed — **that claim is worth attacking**, and the
  Flutter suite was not run because no Dart file changed (`git show --stat` confirms).
- **Deliberately out of scope**, each noted in the DEF row: the timeout guard itself (this defect is
  about *recording*, not *preventing*; DEF389-394 own that space); the PM self-consistency hole

  `llm_audit`; and the PM's `trade_proposal`, built from `base_price` and therefore surviving the
