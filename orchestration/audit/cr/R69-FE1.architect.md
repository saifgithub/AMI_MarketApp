## What was built

### CR174-FE — interactive lesson mode

A second way to read a lesson: the same blocks, re-cut into a swipeable deck of beats with a
draggable parameter play in the middle. Book mode is unchanged and is still the default for a
`story` learning style.

- `models/lesson_beats.dart` — the pure fold from `Lesson` + `LessonInteractive` to `List<LessonCard>`.
- `widgets/lessons/interactive_registry.dart` — six pilot lessons (013, 014, 015, 016, 017, 018),
  each with a frame builder reproducing that lesson's own published figures.
- `widgets/lessons/lesson_parameter_play.dart` — the slider + `CustomPaint` canvas.
- `screens/lessons/lesson_beat_deck.dart` — `PageView.builder`, no auto-advance.
- `state/lesson_view_mode_provider.dart` — the CR106 `RoomViewMode` shape: nullable state so "never
  chose" is distinguishable from "chose book", `setMode()` the only writer.

**The registry is the gate, not a config flag.** A lesson with no registry entry gets no toggle at
all — never a placeholder, never an empty deck (CR040). `_offersInteractive` reads
`InteractiveRegistry.has(lessonId)` directly.

### CR170-FE — resting-order controls

Order-type + TIF pickers, conditional price fields, the live intent hint, the resting-orders section
on the portfolio screen, cancel with a server-verdict toast.

**The one decision this slice had to make: a capability probe, not an open control.** A front end for
resting orders is **not inert** against a backend without the book. `POST /v1/sim/submit` accepted
`order_type=limit` long before CR170, and `sim_engine.py:658` shows what it did with it —
`fill_price = mark if order_type == MARKET else (limit_price or mark)`. It rests nothing. **It fills,
instantly, at whatever price the user typed.** Shipping the picker open would not have been an
unfinished feature; it would have been a money-moving control that silently does something else.

So the controls are gated on `SimState.restingOrdersSupported`, raised **only** by a successful
`GET /v1/sim/orders/{user_id}`. A compile-time flag (CR109's `AMI_GAMES` shape) was the obvious
alternative and was rejected: it needs someone to remember to rebuild and re-ship on the day the
backend lands, whereas the probe flips itself on the next refresh.

Two properties are deliberate and tested:

- **It fails closed on *any* error, not only a 404.** "No route" and "route present but unwell" are
  genuinely different facts, but the cost of guessing wrong in the permissive direction is the
  instant-fill above. There is no reading of that trade-off where the optimistic default wins.
- **It never fails the refresh.** Losing the portfolio, holdings and trades because an optional book
  is unreachable would be the worse outcome.

### CR171-FE — short-sell refusals

`features/sim/short_rules.dart`: a sell never crosses zero (§1), and a short's bracket inverts (§5).
Both produce a *refusal at the tap* rather than a server round trip, because a refusal three seconds
later out of the network reads as the app being broken.

Deliberately **not** modelled client-side: borrow cost, margin thresholds, forced buy-in, gross
concentration. Those need position state and a rate the client does not have, and a client-side
approximation of a margin call is the CR040/DEF252 sin — a number that looks authoritative and is
invented.

## Corrections to the CR docs found while building

Recorded because each was a claim in the spec that turned out false, not a preference:

- **CR170 §9 locates the resting-response crash at `trade_ticket_sheet.dart:247` (`result.trade!`).
  It is one layer earlier.** `SimSubmitResult.fromJson` cast `j['trade'] as Map<String, dynamic>`
  unconditionally and throws on null *first*, so `:247` never runs. The user-visible symptom is
  therefore **not** a crash but a generic *"couldn't place that trade"* over an order the server
  **accepted** — worse, because it invites a second tap. Both layers fixed.
- **The ticket had no rebuild on the fields its hint reads.** The quantity field carries no
  `onChanged`, so the live hint and CR171's refusals were computed once and never again — a sell of
  ten against a holding of four typed cleanly and no refusal ever appeared. **Found by a failing
  test, not by inspection.** Fixed with listeners on all six inputs, chosen over per-field
  `onChanged` because the set will grow and the one that gets forgotten is the one that matters.
- **CR174's acceptance 3 has a false premise.** It assumes the client has no scored answer before an
  attempt. Lessons serve `answer_index` + `explanation` in the pre-attempt payload today — the DEF042
  shape, which was fixed for daily challenges and never swept to lessons. Filed as **DEF294**
  (backend, open, not started) rather than papered over; the deck is deliberately built *not* to
  deepen the reliance.

## The revert-proof QA (builder's own; the auditor's blind pass is separate)

Eight mutations, each confirmed red then reverted:

| # | Mutation | Test that bit |
|---|---|---|
| 1 | Probe fails **open** (`supported: true` in the catch) | `cr170_resting_orders_test.dart` |
| 2 | `resting` inferred from `trade == null` instead of read | `cr170_resting_orders_test.dart` |
| 3 | Cross-zero sell **split** into close+short instead of refused | `order_rules_test.dart` |
| 4 | A `filling` order becomes cancellable | `cr170_resting_orders_test.dart` |
| 5 | `_Ltr` wrapper removed from the play's slider (RTL) | `cr174_reader_mode_test.dart` |
| 6 | Registry gate ignored — toggle offered for any lesson | `cr174_reader_mode_test.dart` |
| 7 | Unknown view-mode string resolves to `book` not unset | `cr174_models_test.dart` |
| 8 | `insertPlayIfDue` drops the play on a mis-authored anchor | `lesson_beats_test.dart` |

**Two of these initially SURVIVED, and that is the part worth reading.**

**Mutation 5 (RTL).** Removing `_Ltr` still passed *"the same drag does the same thing in ar"* —
because a Material `Slider` **jumps to the touch point** on drag-start, and from the card's opening
$459 that jump alone raised the value. The test was measuring the jump, not the drag. Rewritten to
measure the delta *from the touch point* (`startGesture` → `moveBy` → compare), after which the
mutation produces 2 red instead of 1.

**Mutation 1 (the probe).** Flipping fail-closed to fail-open broke **nothing**, because every widget
test constructed `SimState` by hand and **none ran the probe** — the single most load-bearing decision
in the slice had no test at all. Fixed by driving `SimNotifier.refresh()` through a `ProviderContainer`
against a fake `ApiClient` that 404s the book.

Both are the **DEF190 shape** — *a check that keeps passing through the very change it exists to
catch* — and this lineage has now hit it three times (CR173's autoplay guard, then these two). I am
flagging it rather than filing it because I do not think it is a defect in any one test; it is what
this codebase's guards fail like, and the auditor's blind pass is the right place to test whether the
fixes actually hold.

### What the SHA-pinned run caught that the shared tree hid

Two things, and both are the reason the bindings demand this rather than a number typed from the
working directory.

**1. An unused import of mine (fixed, and it is why the SHA moved).** The clean-tree analyze flagged
`unused_import` on `features/sim/order_pricing.dart` in `test/screens/sim/cr170_resting_orders_test.dart`
— no symbol from that library appears in the file. It is a warning in a test file, not an error, and
`--no-fatal-infos` still exits 0, so nothing in my own loop had surfaced it. Removed in `c79d873c`,
which is **why this lane submits at `c79d873c` rather than `9f5858b1`**. The change is test-file-only,
so the shipped `0.1.0+90` binary is byte-identical to the audited code path. Analyze went 8 → 7.

**2. My own first extraction was wrong, and I am recording it rather than quietly re-running.**
`git archive <sha> mobile/` produced **1026 passed, 8 failed**. The failures were real and my fault:
`cr174_models_test.dart:224` reads `Directory('../content/lessons')` — the lesson corpus lives
*outside* `mobile/`, so a mobile-only extraction has no corpus to check the registry against.
Re-extracting the full tree gives **1034 passed**, matching the shared tree exactly. Worth the
auditor knowing for two reasons: the corpus-parity tests are load-bearing for CR174's Tier A
question (they are what pins the six registry anchors to lessons that actually ship in all three
locales), and any audit worktree scoped to `mobile/` alone will reproduce my 8 failures and they
will not mean what they appear to mean.
