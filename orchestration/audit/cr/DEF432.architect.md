## What and why

Found by auditor U68 auditing DEF424, recorded but not scored there ("Recorded, not scored" —
out of that lane's scope): a Room convened while the LLM is down ends `completed | NO_VERDICT`
with the copy "Too much of your analyst room was unreachable … reconvene when the desks are
back," and keeps its credits (measured: `room:MSFT 150->142`). Brief and 1-on-1 already refund
an outage turn (DEF424); the Room did not.

**Saiful's ruling, 2026-09-25, verbatim:** **"Refund it."** — "Same rule as Brief and 1-on-1: an
outage never costs the user. The user sees 'desks unreachable — not charged'."

**Starting point:** an earlier worker on this defect was stopped mid-task. Its uncommitted diff
was saved as a patch and applied cleanly to this worktree's `main` base, then reviewed critically
rather than accepted as done — see "What was in the draft patch, and what changed" below.

**Two candidate outage causes were distinguished before implementing, not assumed:**

`room_runner.py` has TWO NO_VERDICT-shaped constructs and one PASS-shaped one:

1. `PM_LLM_UNAVAILABLE_REASON` (DEF059) — the CIO's OWN stream is empty. Produces a fail-safe
   **PASS**, not NO_VERDICT, with `overridden_from_llm=True`. Recognised by
   `is_llm_outage_verdict`. This is a delivered (conservative) decision, not an abstention, and
   is NOT in DEF432's row or the auditor's measured evidence — both name only the NO_VERDICT
   case. Left untouched; out of scope for this defect. (Flagged below as a follow-up question,
   not silently fixed here.)
2. `PM_ROOM_INCOMPLETE_REASON` (CR219 R51) — too many of the OTHER eleven desks were scripted
   fallbacks (`room_max_scripted_turns` cap reached). Produces **NO_VERDICT**, recognised by
   `room_verdict_is_incomplete`. This is DEF432's measured case (`room:MSFT 150->142`,
   `completed | NO_VERDICT`) and the one Saiful's ruling addresses.
3. `_assemble_no_verdict` (CR098 Amendment 2) — Market analyst withheld by tenure pull-back, a
   deliberate professional-discipline refusal argued from a full fundamentals case. Also
   NO_VERDICT, but not an outage at all — the roster answered, the PM chose not to price a
   trade. Must stay charged and distinguishable from (2).

Fix targets exactly (2), keyed on `room_verdict_is_incomplete` (the `PM_ROOM_INCOMPLETE_REASON`
sentinel string), never on `action == NO_VERDICT` alone — that would also catch (3) and
over-refund a deliberate refusal.

## The fix

1. **Refund**, `room_runner.py`'s `run()`, the single `COMPLETED` persistence point (right after
   the status-flip `_persist_run(run)` call, before `bank_verdict_outcome`): when
   `run_was_refunded(run)` is true (see predicate below), calls `refund(user_id, run.credit_cost,
   reason=f"room_outage_no_verdict:{run_id}")` — best-effort, same shape as the CR039 failed-run
   refund a few lines down in the `except Exception` branch: a refund failure logs
   `room_outage_refund_failed` and must not turn a delivered (if outage-abstained) verdict into a
   hard error.
2. **Scope**, enforced by keying on `room_verdict_is_incomplete`, never on the action alone —
   see the three-way distinction above. `_assemble_no_verdict`'s NO_VERDICT and a normal
   APPROVE/PASS/REJECT both stay charged.
3. **User-visible copy**: `PM_ROOM_INCOMPLETE_REASON`'s one construction site now appends a new
   `_ROOM_OUTAGE_NOT_CHARGED_SUFFIX = "This Room wasn't charged."` — AMI named in the surrounding
   sentence, no bare "the AI"/"the LLM". The mobile client renders `verdict.reason` verbatim with
   no ARB mapping (confirmed by reading `mobile/lib/screens/room/room_screen.dart:1346` and
   `mobile/lib/models/room_consensus.dart` — the ONLY ARB-mapped field off a verdict is the
   `action` enum via `_actionLabel`, and it explicitly passes through unrecognised/free-text
   values), so no mobile change is needed for this string to reach the user.
4. **Decision Journal**: `build_journal_entry_for_run` (unedited) already reads
   `verdict.reason` verbatim into the journal `summary` whenever `run.verdict is not None` — the
   outage NO_VERDICT always has a verdict object, so the journal entry inherits the "wasn't
   charged" sentence for free. No separate journal fix needed; verified by reading the function,
   not assumed.
5. **CR236's `done` event alignment** — the actual new-since-first-brief item. CR236 (merged,
   `5eb0a620`) added `credit_cost`/`refunded` to the Room stream's final `done` SSE event
   (`api/room.py`), with `refunded = _final.status == "failed"`. An outage NO_VERDICT leaves the
   row `COMPLETED`, so that boolean would read `false` for a Room DEF432 just refunded — the app
   would say "used 8 credits" for a Room that cost nothing (a DEF437-class fabrication-by-report).
   Fixed by introducing **one shared predicate**, `run_was_refunded(run: RoomRun | None) -> bool`
   in `room_runner.py`, called by BOTH:
   - the refund decision in `run()` (`if run_was_refunded(run): refund(...)`), and
   - `api/room.py`'s `done` event (`'refunded': run_was_refunded(_final)`).

   `run_was_refunded` returns `True` for exactly two shapes: `status == "failed"` (CR039's
   existing refund, unconditional) or `status == "completed"` AND
   `room_verdict_is_incomplete(verdict)` (this defect's new case). `False` for
   CANCELLED/QUEUED/RUNNING and for `None`. The two call sites can now never disagree about
   whether a given run was refunded, because there is exactly one function that decides it.

## What was in the draft patch, and what changed

The stopped worker's patch got the core mechanism right — the refund call, its placement on the
single COMPLETED path, the scoping via `room_verdict_is_incomplete`, the reason-string suffix, and
a first-draft test file. Reviewed critically rather than accepted, three real problems were found
and fixed:

1. **Missing entirely: the CR236 `done`-event alignment** (item 5 above) — the draft patch did not
   touch `api/room.py` at all, so `refunded` would have stayed `false` for every DEF432-refunded
   Room. This is explicitly flagged as new-since-first-brief in the task and was not optional.
   Added the shared `run_was_refunded` predicate and wired both call sites to it.
2. **Two tests in the draft had inverted balance assertions.** `_run_room()` drives
   `RoomRunner.run()` directly (the low-level generator), which — per DEF425's own documented
   finding — never spends credits on its own; only `start_run()` does. The draft's
   `test_llm_down_room_no_verdict_is_refunded_net_zero` and
   `test_refund_fires_exactly_once_even_if_swept_or_retried_later` captured `before` AFTER the
   test's own manual `spend()` call, then asserted the POST-refund balance equalled that
   post-charge number — which is only true if the refund does NOT fire. Running the suite before
   any fix to the test caught this immediately: `assert 150 == 138` with the refund demonstrably
   firing (`room_outage_refunded credits=12` in the log). Fixed by capturing `before` BEFORE the
   test's `spend()` call, so the assertion correctly expects the refund to restore the pre-charge
   balance.
3. **No test coverage for `run_was_refunded` itself, or for the CR236 alignment** — added 6 unit
   tests directly against the predicate (failed/outage-completed/normal-completed/cr098-withheld/
   cancelled+running+queued/None) and 2 new cases to `test_cr236_room_done_credit_cost.py`
   (outage NO_VERDICT → `refunded: true`; normal completed verdict → `refunded: false`) per the
   task's explicit instruction.

Everything else in the draft (refund placement, best-effort error handling, the outage-vs-CR098
scoping, the suffix string, the module-level comments explaining why the two refund paths — this
one and DEF425's shutdown/sweep path — cannot double-fire) was correct on inspection and kept.

## Double-refund risk — verified, not assumed

Confirmed by reading, not inferred from the draft's comment: `_sweep_stuck_runs`
(`room_runner.py`) selects `.where(RoomRunRow.status == "running")`. This defect's refund only
fires AFTER `run.status = RoomStatus.COMPLETED` is set and persisted (`_persist_run(run)` a few
lines above the refund call). A `COMPLETED` row is therefore never `"running"` and can never be
selected by the sweep — the two refund paths (this one, and DEF425's shutdown-mark → sweep →
retry-exhausted refund) operate on disjoint status transitions for a single `run_id` and cannot
both fire.

## Attack surface (please probe)

1. **The DEF059 full-CIO-outage PASS (`is_llm_outage_verdict`) is charged and was left untouched.**
   This is a genuine open product question, not an oversight: it is a delivered fail-safe verdict
   (PASS, not an abstention), and neither DEF432's row nor the auditor's "Recorded, not scored"
   note mentions it — only the NO_VERDICT case was measured and ruled on. If Saiful's "an outage
   never costs the user" principle is meant to extend to it too, that is a fresh scope decision,
   not something this fix should have silently absorbed. Worth asking explicitly.
2. **Re-verify the mobile rendering claim live**, not just by reading the client source: confirm
   a real Alpha Room hitting this NO_VERDICT path shows the "This Room wasn't charged." sentence
   and the credits chip / post-Room line via `roomResultRefunded` ("Not charged — this Room
   didn't reach a verdict") once promoted — this round's evidence for the mobile side is
   read-only source inspection (via a research subagent), not a live client run.
3. **`refund()`'s own idempotency** — `credit_service.refund()` has no dedup/idempotency key of
   its own (a straight `credit_balance += amount` under a row lock); the "exactly once" guarantee
   here is entirely structural (this call site is reached at most once per run_id, on a status
   transition no other code path also takes), not enforced by the ledger itself. If a future
   change ever calls `run()`'s COMPLETED branch twice for the same `run_id` (e.g. a hypothetical
   replay/backfill tool), this refund would double-fire with no ledger-side guard. Worth flagging
   as a class, per DEF432's own three-way outage-cause distinction being the kind of "second
   occurrence" the guards register (`docs/initial_specs/08_tech/failure_patterns.md`) tracks.
4. **`bank_verdict_outcome`'s calibration ledger** still banks the outage NO_VERDICT row
   (unedited by this fix, and correctly so — CR219 R55 wants to know how often the Room decides
   with no live price, which an outage NO_VERDICT is a real instance of); confirm the auditor
   agrees this is a "count it, don't hide it" case distinct from the credits question.
