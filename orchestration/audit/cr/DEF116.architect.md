# DEF116 — audit lane (blocking I/O stalls the backend for every concurrent user)

SUBMITTED: round 1

**Item:** synchronous, network-bound calls (yfinance / `SimEngine.current_*` / the `build_*_block`
family / `_profile_for_ticker`) made inline from `async def` handlers on a **single-process,
single-event-loop** uvicorn. Each 1–3s call parks the whole loop — every other user's SSE stream,
LLM token relay and unrelated API call queues behind it. Fires on **every Room convene** and **every
1-on-1 turn mentioning a ticker**. Saiful graded it an **MVP show-stopper**: near-harmless at
Stealth Alpha (10–20 invite testers rarely overlap), total at public launch.

## Audit this hardest

### 1. The waiver is where the risk lives, not the fix

`_WAIVED_CALL_CHAIN_NAMES` (9 entries) prunes the walk past `current_marks` /
`_marks_with_quotes` / `current_price` / `preview` / `submit` / `evaluate_outcomes` /
`manual_close` / `current_marks_with_source` / `_build_room_sector_context`.

The Architect emptied that set and re-ran the guard: **9 further blocking route handlers** appear —
`get_portfolio`, `submit_trade`, `preview_trade`, `reset_portfolio`, `close_trade`,
`evaluate_trades`, `audit_holdings`, `sector_allocation`, `stream_room`. Spot-checked one to
confirm it is not a name-collision artifact: `sim_engine.py:271`
`return {t.upper(): self.current_quote(t) for t in tickers}` — a sync fetch **per ticker in a
loop**, so `get_portfolio` stalls the loop for `N × (1–3s)`. Hotter route, bigger stall than
anything this lane fixed. **Minted as DEF120.**

Two things to test, not read:

- **Does the waiver still fail loudly if a waived site is "fixed" wrongly?** The docstring claims
  *"removing a name here without fixing its call site should turn this guard red again."* Verify
  that claim — it is the only thing keeping the waiver honest rather than decorative.
- **The prune is by bare function name across every module**, so `preview` / `submit` /
  `current_price` disable traversal through *any* same-named function anywhere under `backend/app`,
  not only `SimEngine`'s. Does that mask a path unrelated to the 9 known sites? A guard that goes
  green on a genuinely new regression is worse than no guard — this project's own DEF038/DEF063
  lesson in a different costume.

### 2. Is the guard sound where it claims coverage?

Probe it with shapes the Architect did not use — a blocking leaf reached through a class method, a
module-level alias, a conditional branch, a comprehension. The CR049 auditor found value doing
exactly this (it deliberately avoided the coder's suggested recipe and used two independent probes).
Also confirm the `_to_thread_wrapped_call_ids` exemption cannot be abused to launder a real
violation.

### 3. D2 — leaves untouched, and the ~15 `monkeypatch.setattr` tests still real

The Architect's check was structural: the diff contains only call sites plus one `import asyncio`,
and no `def`/`async def` line. Confirm no leaf signature moved, and — more usefully — confirm the
existing `monkeypatch.setattr` tests still actually exercise the patched path now that the call runs
inside a `to_thread` worker, rather than passing vacuously.

### 4. `room_runner.py` — CR090's kwargs survived the hoist

`_profile_for_ticker` was moved out of the `_RoomContext(...)` kwargs into a preceding statement.
CR090-ROOM had just rewritten this call to thread `news_feed=` / `social_feed=` through it. The
kwargs appear carried through in the diff — verify they are, and that `profile = ctx.profile`
immediately after still refers to the same object. CR090's D4 lesson was that moving this exact seam
silently voided existing patch-based tests.

### 5. The Alpaca gap — is prose enough?

`alpaca_service.py:77,113` (via `alpaca_snapshot_text`, called from `room_runner.py` and
`agent_runner.py`) is the **identical live bug**, correctly out of scope per D4, and the guard
**deliberately does not detect it**. The docstring's reasoning was checked and is sound (name-based
`.get`/`.post` resolution collides with `Session.get`, `*_store.get`, producing bogus chains). But
the net result is that a known-live instance of the exact class this guard exists for is held only
by a comment. Judge whether that is acceptable or whether it needs a narrowly-targeted structural
check.
