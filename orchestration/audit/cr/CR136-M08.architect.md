## 1. Why this lane exists — and when to return it

Rev 4's named audit scope is **M02 and M05 only** (the two math-critical
modules). Every other CR136 lane, this one included, is a **risk-based
extension raised by Saiful**, not something the CR asked for. The honest
argument for M08:

**1. This is the module where the Finding stops being a computation and becomes
a record.** M02–M07 can all be re-run: a wrong number today is a right number
tomorrow once the estimator is fixed. A journal row cannot be re-run. Rev 4's
F19 makes the archived artefact carry its own disclosures *forever* precisely
because it is the thing a user reopens in a year and screenshots. A mapper
defect is written into the permanent record, not into a rendering.

**2. Every guard in this module fails by NOT REFUSING — the project's exact
recurring failure class.** Three of them:

- soft-deleted rows must still count against the trial budget (else
  delete-to-reset-trial mints free Findings),
- soft-deleted rows must still carry rule hysteresis state (else a journal tidy
  silently re-arms every cleared rule and the bands flap),
- `uq_journal_dedupe` must exist (else a double-tap writes two Findings and
  bills two LLM calls against a cap of two).

None of the three raises, logs, or reddens anything when it breaks. The user
sees a slightly generous product; we see nothing at all. That is DEF210's shape
(~10 weeks dark), DEF038's and DEF063's (months dark for want of one
docker-compose line).

**3. The largest unaudited surface in CR136 is here.** At `c56e2c41`,
`orchestration/audit/cr/` holds lanes for CR136-M02, -M05, -M06, -M09 and the
CR136 doc itself. **No lane exists for M07 and none for M08** (other module
lanes are being submitted alongside this one in the same round — this counts the
committed state). Yet `journal_store.py`'s two CR136 reads,
the whole dedupe/idempotency layer, and the entry mapper were all built inside
M06's and M07's build passes — reviewed by the builder, by nobody else. The
irreversible half of CR136 is the half nothing independent has looked at.

**4. Probing it produced a live finding in one sitting.** §5.1 is a measured,
reachable path where "regenerate after deleting today's Finding" hands the
client a `journal_entry_id` for a row the API will 404, after spending the LLM
call. Probe output pasted. That is not a hypothetical, and its existence is the
strongest form of this lane's argument.

**When to return it as misallocated effort.** The counter-argument is real and I
want it taken seriously: M08's own two commits are ~120 lines of pure mapper plus
a 135-line payload-pure Dart widget, both of which are as close to trivially
reviewable as CR136 gets. If §5.1 turns out to be the whole of it, and if you
judge the register-pinned seams to have been adequately covered inside M06's and
M07's own passes, **say so and take the time back for M06 round 3** — that lane
has an open BLOCKER history and is where the model still touches user-facing
prose. I would rather be told this lane was cheap insurance than have M06 rushed.

## 2. What the module is, and the decisions worth challenging

### 2.1 The artefact has exactly one constructor, and the validation is the point

`build_finding_entry` (`portfolio_health_journal.py:39`) is pure — no DB, no
clock, no LLM. It was not *added* as a second construction path: M06's inline
dict literal was **extracted** into it (`portfolio_finding.py:1223-1248` now
calls it), so there is one place that builds the artefact and one place that
validates it.

The validator raises `ValueError` on four things, and each maps to a specific
silent failure rather than to tidiness:

| Rejected | What it would otherwise become |
|---|---|
| a missing section key | a permanent report with a hole in it |
| an **unexpected** section key | content stored forever and rendered by nothing — the Dart renderer walks a fixed order |
| a blank/non-`str` section (incl. `head`) | an F19 violation: an archived Finding that outlives every caveat that was true when it was written |
| a `rule_states` value outside `{fired, cleared}` | read as `cleared` on the next run — a fired rule's hysteresis memory silently dropped |

**Worth challenging:** the "unexpected key" half only landed in `d26dd4f4`. For
one commit the doc's *EQUAL* pin was enforced as a *superset* pin.

### 2.2 This module touches no numbers — deliberately, and it is worth confirming

The units pin (Tier-1 decimal fractions ×100 to display; Tier-2 `realised_*`
already percent; `beta`/`effective_bets`/`weight_concentration` dimensionless
ratios) and the SHARE-vs-LEVEL basis rule are **M04/M06/M09 surfaces, not this
one**. M08 stores strings M06 already rendered and validated;
`finding_sections.dart` renders those strings through `MarkdownBody` and
reformats nothing. The one number-adjacent decision is `summary`, which the doc
originally pinned to `None` and which now carries the first §F1 headline — plain
prose with no markup, so DEF150's clipped-markdown-fragment concern does not
bind. If you disagree that this module is number-free, that disagreement is more
valuable than anything else in §5.

### 2.3 Both journal reads deliberately break the store's own invariant

`journal_store.py:17-21` states it in the module docstring: every read in the
file filters `deleted_at IS NULL` **except** the two CR136 reads at the bottom.
That is not an oversight; `list_for_user` was unusable for either job because it
applies *both* the soft-delete filter and Floor Pass's 30-day retention window —
either of which silently hands a user free Findings or resets a rule's band.

**Doc-vs-code, and the code is right:** M08 §3.4 pins the portfolio filter as
"payload filter in Python — no JSONB operator dependence". The shipped code
filters on the `reference_id` **column** (`journal_store.py:340`), which is
possible only because the seam register overrode the doc's `reference_id=None`
pin. Better than the doc. But see §5.3 — that column has no index.

### 2.4 Idempotency is two layers answering two different questions

- **Read layer** (`portfolio.py:187-198`, mirrored in
  `portfolio_finding.py:1181-1195`): *"has today already been answered?"* —
  returns the existing entry, spends no LLM call, no budget, and is deliberately
  **not gated**, because re-reading something already in your journal must not
  be refusable.
- **Constraint layer** (`uq_journal_dedupe` + `append_unique`): *"two writers
  arrived, which one wins?"* — the read cannot serialise anything, because the
  competing INSERT may land immediately after it.

The measurement behind the constraint (five concurrent POSTs → five Findings
against a daily cap of two, five LLM calls billed) is **M07's, recorded in the
migration docstring. I did not re-measure it in this session** and it is not
offered here as my evidence.

### 2.5 The Dart renderer degrades to a raw dump on purpose

`FindingSections.isRenderable` false ⇒ the branch at
`journal_detail_screen.dart:343` does not fire and the entry falls through to
the generic key/value dump. Ugly, but visible and honestly labelled — never a
blank screen and never a disclosure-less report. The renderer also accepts a
top-level `disclosure` key as a fallback so an entry written by an older build
still renders its caveats instead of dropping to the dump.

## 5. What I would attack if I were the auditor

*(§4 is last because the serial measurement pass rewrites it in place.)*

### 5.1 MEASURED — regenerate-after-delete hands the client a dead journal id

**Attack this first; it is the one I found and did not fix.** The route refuses
to *replay* a soft-deleted prior (`portfolio.py:190`, `prior.deleted_at is
None`), so it falls through to generate. `append_unique` then collides on
`uq_journal_dedupe` and returns the row that already holds that key — **which is
the very soft-deleted row the route just declined to replay**
(`journal_store.py:144-148` has no `deleted_at` check). Measured with a
read-only probe against the real store on the conftest's sqlite fixture (script
in scratchpad, no repo file touched):

```text
1. first write                     created=True id=71ff8e29-c0ae-4ef6-94d1-2566740c4a08
2. user swipes it away             GET entry -> None
3. route's idempotency read        deleted_at=datetime.datetime(2026, 8, 3, 12, 16, 43, 782435)
   -> deleted_at is not None, so the route FALLS THROUGH: gate enforced,
      LLM path run, build_finding_entry called, append_unique attempted.
4. re-write, same dedupe_key       created=False id=71ff8e29-c0ae-4ef6-94d1-2566740c4a08
   returned row is the same one?   True
   returned row deleted_at         datetime.datetime(2026, 8, 3, 12, 16, 43, 782435)
5. client opens journal_entry_id   store.get -> None
6. gate counters after both calls  used=1 daily_used=1
```

Reachable at shipped defaults: `portfolio_health_daily_cap: int = 2`
(`config.py:286`), so after one Finding + a delete, `daily_used` is 1 and
`enforce_gate` passes. What the user gets: the report they just deleted,
returned as the answer to "regenerate", with `created: false`, and a
`journal_entry_id` that `GET /v1/journal/{user}/entry/{id}` 404s
(`journal_store.get` filters `deleted_at IS NULL`). What we get: an LLM call and
a full render, both discarded, and an INFO line reading
`portfolio_finding_lost_write_race` when nothing raced — a diagnostic that would
send the next person looking at concurrency.

Today the mobile client parses `journal_entry_id` (`portfolio_health.dart:368`)
but never navigates on it, so the visible face is only the stale report. It
becomes a dead link the moment M09 or CR137 wires "open in journal".

Three candidate fixes, and I want your call on which: (a) treat a collision with
a soft-deleted row as a `restore` + overwrite; (b) refuse it and return 409 so
the client can say "restore it from Trash"; (c) fold `deleted_at` into the
dedupe key — which I think is wrong, because it re-opens the duplicate-write
hole the constraint exists to close. **Not DEF211 or DEF212**, both of which are
deferred on purpose and neither of which lives in this module. Not yet filed as
a defect either — this round I am permitted exactly one file.

### 5.2 `portfolio_health_stats` loads every Finding the user has ever written

`journal_store.py:364-381` issues `select(JournalEntryRow)` with no column
projection and no limit, then `.scalars().all()` and counts in Python. Each row
carries the full Finding payload — stripped context plus all six sections.
`evaluate_gate` calls it once on the tiles path (`portfolio.py:150`) and twice
per generating POST (`:198`, `:217`). Not silent-wrong; it is the class of thing
that only ever shows up on the account with the most history, which is the
account you least want it to show up on. Is there a bound I have missed?

### 5.3 `reference_id` is not indexed

Both CR136 reads filter on it (`journal_store.py:340`, `:378`), and the seam
register's stated reason for pinning `reference_id = portfolio_id` was to avoid
"a payload scan". `models.py:282` declares it
`mapped_column(Uuid(), nullable=True)` — no `index=True`, and the dedupe
migration added none. Did the pin actually buy what it claimed?

### 5.4 `SECTION_KEYS` ↔ the Dart renderer has no guard, and one drift is silent

M09's `test_cr136_dart_parity.py` guards the units map and the three refusal
codes. Nothing guards this seam: `finding_sections.dart` hardcodes `'sections'`,
`'head'` and `'f1'…'f5'`; `portfolio_health_journal.py` owns `SECTION_KEYS`.
Worse, the backend pin is **derived from the constant it is meant to pin** —
`test_portfolio_health_journal.py:87` asserts
`set(draft.payload["sections"]) == set(SECTION_KEYS)`, which survives any rename
of `SECTION_KEYS`. Most renames degrade loudly (`isRenderable` goes false, raw
dump appears), but **one does not**: rename `f1…f5` and keep `head`, and
`isRenderable` stays true (a disclosure exists, `sections` is a Map) while the
loop finds nothing — the screen renders a caveat box and **no report body at
all**. Confirm whether that is reachable, and whether the fix belongs in
`test_cr136_dart_parity.py` as a third contract.

### 5.5 The trial counter is per-user, the daily counter per-portfolio

`journal_store.py:373-380`: `len(rows)` ignores `reference_id`, `daily` filters
on it. The docstring's reason is that `reset_portfolio` destroys and recreates
the portfolio, so a per-portfolio trial would reset itself. Check that against
Rev 4's own pin, and check the trial-window boundary in `health_gate.py:107` —
`days_elapsed = (now - first_at).days` truncates, so day 14.9 still reads 14.

### 5.6 The migration has never been executed, and carries no backfill

`backend/tests/conftest.py` builds the schema with `create_all` and then
*stamps* the revision — so `c2d3e4f50028` runs for the first time on melehost,
not in any test. It also adds `dedupe_key` as nullable with no backfill, which is
safe **only** because no Finding row exists anywhere yet: the newest Alpha tag is
`alpha-2026-08-01-1` at `a7cfd7eb` (2026-08-01), which predates every CR136
M06–M11 commit. A Finding written on a live host between `88797409` and
`043995b0` would carry `dedupe_key IS NULL` and sit outside the constraint
permanently. I could not check melehost from this session; treat this as an
M11 pre-promotion item, not as something I verified.

### 5.7 The `deleted_at` two-use split has no structural enforcement

`load_latest_finding` returns a soft-deleted row on purpose, and its two current
consumers read it differently — hysteresis unconditionally, replay only when
`deleted_at is None`. That contract lives in prose in two docstrings. CR137 is
the next consumer. Is there a shape that makes forgetting it impossible, or is
this the CR038 problem again (an instruction where a control is needed)?

### 5.8 Old-client degradation (doc §3.9) is claimed, not tested

The doc asserts a pre-M08 client renders the slate `UNKNOWN` card plus the
generic dump. `test_journal_entry_type_parity.py` enforces that `fromWire`
returns `null` rather than coercing, which is the mechanism — but no test pumps
a `portfolio_health_analysis` payload with `entryType == null` through the card
and the detail screen. `NEEDS-DEVICE-CHECK`, or a widget test.

## 4. Revert-proof QA — measured, not asserted

**Specified at authoring time, run later by the serial measurement pass.** Other
agents were reading this same checkout concurrently and a source edit would have
corrupted their test runs, so the mutations were written as a specification and
executed afterwards on an exclusive tree. Every number above §4 was measured in

confirmed clean afterwards.

assertion being weakened later.
