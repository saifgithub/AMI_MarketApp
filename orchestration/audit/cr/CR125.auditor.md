## BLOCKER — CR125's own Acceptance criterion is violated: the `user_id` does NOT survive
upgrade. Reproduced live, two independent root causes, both orphan the account.

`CR125_mobile_secure_session.md:46-47` / `CR125_implementation_plan.md:123-124`, verbatim
acceptance: *"a device on the old build re-authenticates cleanly on update; the `user_id`
survives, only the credential is reissued — no silent lockout of legitimate data."* This is
false as built. Both mechanisms below reproduce **exactly** the orphaning shape a0f122f0's own
commit message describes and says it prevents — just via two triggers a0f122f0 doesn't cover.

**(1) The token-format migration itself, day zero, 100% of the alpha cohort.**
`get_rebootstrap_identity_optional`'s `allow_expired=True` only relaxes the `exp` check *inside*
`parse_scaffold_token`'s 4-part branch. The pre-CR125 2-part signed format matches neither the
4-part nor the 1-part branch and is rejected outright — correct for ordinary auth, but this is
also the ONLY path `/v1/auth/anon` has to recognize a returning caller. Every existing installed
token is pre-CR125 format, so `current_user=None` for every existing user on their very first
bootstrap after this ships → A2's `trust_device_id=False` → fresh user minted. Reproduced
(`repro_format_migration.py`): a real anon user's actual pre-CR125-shaped token, replayed at
`/v1/auth/anon` with the matching `device_user_id`, returns `200` with a **different** `user.id`,
`is_new: true`. This is not probabilistic — it is the default outcome for every install, not a
30-day-timer edge case.

**(2) `AuthNotifier._handleUnauthorized` (mobile) wipes the token BEFORE re-bootstrapping,
defeating the backend leniency a0f122f0 built.** It calls `DeviceUser.clearTokenOnly()` then
`bootstrap()`; `bootstrap()`'s own `persistedToken` read is now `null`, so `POST /v1/auth/anon`
goes out with **no Authorization header** — same `current_user=None` path as (1), even for a
token that a0f122f0 explicitly designed to still be honoured (plain expiry, no revocation).
`device_user_test.dart`'s `'wipes the token but preserves device_user_id'` proves only that the
*local* id string survives — it never asserts the server treats that survivor as the same user,
and it doesn't, once `authenticated_user_id` is `None`. `test_fresh_token_after_reauth_works_again`
(backend) dodges the real case by POSTing `device_user_id: None` instead of the real id — it never
exercises what `_handleUnauthorized` actually sends. Any ordinary mid-session 401 post-CR125 (app
backgrounded past 30 days, not killed; or sign-out from another claimed session) reaches this path.

Doubt bounces toward MAJOR per protocol — this isn't in doubt; it's a reproduced, written-spec
violation on the single most consequential axis for an anonymous-first product. **BLOCKER.**

**Direction, not mandated code:** (1) — extend `get_rebootstrap_identity_optional`, and only it,
to also accept the legacy 2-part format as ownership proof (its own HMAC-over-hex_id check),
minting a fresh current-format token in response; keep `get_current_user`/`_optional` rejecting
it outright everywhere else. (2) — `_handleUnauthorized` should attempt the re-bootstrap WITH the
dying bearer attached (like a normal cold start does) and only accept "this is a new identity" if
the backend actually returns a different `user.id`, rather than deciding client-side, pre-ask,
that the token is worthless.

## MAJOR — the three SSE routes never reach the 401-recovery guard

`streamBriefMessage` / `streamOneOnOneMessage` / `streamRoom` send via raw `_httpClient.send()`
(`_sseRequest`), bypassing every Dio interceptor including `_AuthInterceptor` — pre-existing
(AT:R33 finding A8), but CR125 is what makes 401 on these three routes routine rather than
attacker-only. A 401 there throws a generic `Exception`, caught by callers (`room_providers.dart`
confirmed — routes to `friendlyError`, no crash), but `onUnauthorized` never fires: no token
clear, no re-bootstrap. Retrying the same action (Convene the Room / continue a Brief / 1-on-1)
keeps 401ing until an unrelated Dio call happens to trigger recovery or the user force-quits.
Squarely inside CR125's own stated concern for 3 of the app's flagship interactive surfaces.

## MAJOR — residual-risk framing is understated

Architect's framing: unexpired-token theft already grants full access and revocation kills both,
so relaxing `exp` "costs nothing the revocation story depends on." For an anonymous-first app with
no session timeout and no organic reason to ever call `DELETE /v1/auth/session`, that equivalence
doesn't hold: an unexpired stolen token is naturally time-bounded (the legit holder's copy moves
past it); an **expired** stolen token under the current design is not bounded at all —
`allow_expired` ignores `exp` entirely, so a token leaked once (old backup, a scrub miss, a
disposed device) can be replayed against `/v1/auth/anon` forever, re-minting a fresh valid
current-format token every time, no time pressure on the attacker. That undercuts one of CR125's
two stated goals ("closes the 'tokens never expire' item") for exactly the leak vector TTL is
supposed to bound. Recommend the bounded grace window the architect already proposed
(e.g. `exp + 180 days`) rather than fully open-ended `allow_expired`.

## Both BLOCKERs — reproduced fixed, not merely read as fixed

**(1) Format migration.** Re-ran the round-1 repro against `92d3bd23` with a real pre-CR125-shaped
token: `/v1/auth/anon` now returns the **same** `user.id`, `is_new: false` — was a different id in
round 1. Widening confirmed confined to the one route: the same legacy token still `401`s on
`/v1/mandate/*` and `/v1/auth/me`; a forged legacy token (garbage signature) for a victim
`user_id` still proves nothing. One property worth naming, not a finding: a legacy token for a
user who has since signed out under the NEW scheme still resurrects ownership on `/v1/auth/anon`
(legacy tokens carry no `token_version`, and `_version_matches` treats `None` as skip) — disclosed
verbatim in the architect's own docstring, not a regression (nothing could revoke a legacy token
before CR125 either), and bounded by the same wall-clock cutoff as the rest of the leniency.

**(2) Mobile recovery path.** `AuthNotifier._handleUnauthorized` no longer wipes the token before
`bootstrap()` — confirmed by direct diff read (the 2 wiping lines are gone; `bootstrap()`'s own
`DeviceUser.getToken()` read is now the first thing that happens, so the dying bearer rides the
recovery `POST /v1/auth/anon` exactly like a normal cold start). No shipped test exercises this
end-to-end (backend-side coverage of what it now correctly triggers is adequate; the mobile change
itself is a clean 2-line deletion, fully determined by inspection). Retry-loop guard
(`_lastUnauthorizedToken`) is untouched by this fix, so no new loop risk; a genuinely revoked
token still ends in one clean re-bootstrap under a fresh identity, not a loop, because the
recovery POST still passes through the server's own `token_version` check.

## MAJOR (round 1) — SSE routes — proven fixed with a throwaway test, not just read

`_notifyIfUnauthorized` wired into all 3 streams, gated to `== 401` internally; `streamRoom`'s

## MAJOR (round 1) — residual risk — proven fixed, plus one new edge the bound itself has

`AUTH_REBOOTSTRAP_GRACE_DAYS` (default 180) now bounds `allow_expired`. Swept both new config
knobs at their edges. `AUTH_LEGACY_REBOOTSTRAP_UNTIL` (date): empty/whitespace/malformed/past all
correctly refuse (malformed logs `auth_legacy_rebootstrap_until_unparseable`), boundary `<=`
today accepts, far future accepts — exactly the "unparseable refuses" intent, no gaps found.

**New MINOR** — `AUTH_REBOOTSTRAP_GRACE_DAYS` has no lower-bound validation. `_within_rebootstrap_grace`
runs unconditionally on every 4-part token (expired or not) and is a no-op only for `grace >= 0`.
A negative value (e.g. `-10`) moves `cutoff` *before* `exp`, so it can reject a token's ownership
proof on `/v1/auth/anon` even when that token **has not expired yet** — reproduced directly
(`ttl_days=+5`, `grace=-10` → refused). Contradicts the field's own docstring ("how long **past**
`exp`..."). Not a security hole — the same token still authenticates every ordinary route fine,
this only affects the one ownership decision — but it is a misconfiguration foot-gun in the exact
"silently causes the thing this CR exists to prevent" class this project has hit twice before
(DEF038/063). Recommend `Field(ge=0)` on `auth_rebootstrap_grace_days`, matching the discipline
already applied to the date field.

## MINOR (round 1) — flag guard — confirmed evadable, two concrete techniques, not escalated

The architect's own submission names this hole before I could. Confirmed it's real, not
hypothetical: fed two synthetic "attack" snippets through the pin's own `_truthy_flag_calls()`.
Variable indirection (`_ALWAYS = True; ...allow_expired=_ALWAYS`) and a `**{"allow_expired": True}`
dict-splat both evade detection (`[]` offenders both times); the direct-literal shape the real
code actually uses is correctly caught as a sanity check. Both evasions require a deliberate
second step to dodge the guard, not an accidental trigger — matches the architect's own
"contrived" framing, kept at MINOR. Recommend: flag any keyword literally named
`allow_expired`/`allow_legacy` regardless of value shape (a legitimate call never needs to pass
`False` explicitly — it's the default), which closes the variable-indirection case for free; the
`**kwargs`-splat case needs one more AST pass matching the call target, a known bounded technique
if it's ever worth the effort.
