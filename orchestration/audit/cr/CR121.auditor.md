### MAJOR — the mobile "belt-and-braces" 426 is undetectable to the user for every call except the two dedicated check sites

The CR's own words for why `VersionGateMiddleware` exists: *"a patched
binary that never calls the [floor] endpoint at all still cannot
transact... it is what makes the gate real against a bypass rather than
merely a polite ask."* True narrowly (the request does fail, 426 not 200)
but the promised UX — a screen, a headline, a CTA to the store — never
appears for this path. It only appears via `VersionGateController.check()`,
called from exactly two places: app launch, and
`AppLifecycleState.resumed`. Any *other* call while a user is below the
floor (place a trade, load a lesson, anything) hits
`VersionGateMiddleware`'s 426 and shows the user nothing recognizable.

**The machinery to route it correctly already exists and is unit-tested in
isolation — it just has no caller:**

```
$ grep -rn "upgradeRequiredFrom\|UpgradeRequiredException" mobile/lib/ | grep -v "api_client.dart\|api_exceptions.dart"
(no output)
```

`_VersionGateInterceptor` (api_client.dart) correctly annotates a 426's
`DioException.error` with `UpgradeRequiredException`
(`version_gate_interceptor_test.dart` proves this in isolation), and
`upgradeRequiredFrom(e)` exists to extract it — mirroring
`serverUnavailableFrom(e)`, DEF073's equivalent for 5xx, which
`room_providers.dart` IS wired to (`on ServerUnavailableException catch`).
Nothing in `lib/` calls `upgradeRequiredFrom`. The annotation is created and
then dropped on the floor by every one of the 15 call sites that route
errors through `friendlyError(e, ...)` (the DEF148 single-funnel — its own
docstring: "the one place an exception is turned into something a user
reads").

**Reproduced — the actual copy a user sees, both un-annotated and
interceptor-annotated give the identical wrong message:**

```dart
// raw 426 DioException, and separately the interceptor-wrapped version
// (.error = UpgradeRequiredException(minBuild: 58, action: 'block'))
friendlyError(err, action: 'place that trade')
// => "Couldn't place that trade — that request wasn't accepted.
//     Check the details before trying again."
```

`friendly_error.dart` has no `error is UpgradeRequiredException` branch (it
has one for `ServerUnavailableException`, at the top) and `_forStatus` has
no `426` case, so it falls through the same path as an ordinary 422 —
`_statusRetryable(426)` is `false` (426 is neither `429` nor `>=500`) —
producing copy indistinguishable from a rejected form submission. No
headline, no "update" language, no store link, no route to
`VersionGateBlockScreen`. `test/friendly_error_test.dart` — the DEF148
completeness guard, whose own docstring says "the guard... fails if any
[call site] interpolates a caught object into user-facing text again" —
doesn't catch this either: its job is "did you call `friendlyError`", not
"does `friendlyError` know what a 426 means", and its status table
(`test/friendly_error_test.dart:58-89`) never includes 426.

**Why this survived two rounds of audit on this lane:** both passes
correctly read `_VersionGateInterceptor`'s unit tests in isolation ("fires
on 426 only... tested against every other status") and correctly concluded
the *interceptor* works. Neither traced the annotated exception forward to
where the 15 call sites actually turn it into words, which is the only
place the gap is visible.

**Why MAJOR not BLOCKER:** the server-side refusal itself is sound — no
data is at risk, nothing transacts on a stale build, and the primary path
(launch + foreground-resume, which covers the overwhelming majority of real
sessions) correctly shows the real block screen. This is scoped to the
window between a floor being raised mid-session and the user's next
backgrounding — real, and exactly the case the middleware's own docstring
names as its reason to exist, but not an open safety/data hole.

**Suggested fix (not prescriptive):** either (a) a top-level catch in
`_VersionGateGateState`/`ApiClient` that calls `upgradeRequiredFrom(e)` on
any REST failure and routes to `versionGateControllerProvider`'s block
state, or (b) minimally, an `error is UpgradeRequiredException` branch in
`friendlyError` so the copy at least says "update required" instead of
"wasn't accepted" — (a) is the one that actually shows the CTA/store link.

### MINOR — `GET /v1/client/release-floor?build=<unparseable>` returns 422, not `action: "ok"` as claimed

The submission's exact claim: *"a `build` that fails to parse... My claim is
every one of those resolves to `ok`, never `block`."* True for the
**header** path (`parse_build_number` never raises — confirmed) but the read
endpoint's `build: int | None` is a bare Pydantic query param, not routed
through `parse_build_number` at all:

```
GET /v1/client/release-floor?build=not-a-number
→ 422 {"detail": [{"type": "int_parsing", "loc": ["query", "build"], ...}]}
```

Neither `ok` nor `block` — a validation error, a third outcome the claim
didn't name. **Not reachable by the real client**: `DeviceContext.buildNumber`
is `int?` in Dart, so the app can only ever send a real int or omit the
param; this requires a hand-crafted request to the unauthenticated endpoint.
No real device can be bricked by it. Corollary, same root cause: with
`min_build=0` (only reachable by writing the DB directly — the admin write
path's own schema is `Field(gt=0)`, confirmed, so it can't happen through
the API) a **negative** `build` value (`?build=-5`, again only reachable by
hand — `parse_build_number` never returns negative, and no legitimate
client ever sends one) resolves to `block`, contradicting "min_build=0 never
blocks a real build." Both are real, both require bypassing the actual
client and the actual write API to reach — worth a `ge=0` on the query
param for defense in depth, not a functional risk to any user.

### Item 3b — refuses to overwrite an existing block: correct in the tested direction, MISSES the reverse race

**New MINOR.** The shipped test only proves one ordering (real detail first,
bodyless second — correctly ignored). The reverse ordering is unguarded:
if a bodyless 426 (unparseable/missing response body — e.g. a truncated
response during a connectivity blip, not a normal well-formed 426) wins the
race and arrives FIRST, `raiseFromServer`'s `if (state.isBlocked) return;`
then silently drops every SUBSEQUENT 426, including one carrying the real
per-raise `headline`/`body`/`storeUrl`. Reproduced:

```dart
c.raiseFromServer(const UpgradeRequiredException());               // bodyless, arrives first
// state: blocked=true, headline=null, storeUrl=null
c.raiseFromServer(const UpgradeRequiredException(
  minBuild: 58, action: 'block', headline: 'Update required',
  body: '...', storeUrl: 'https://testflight.apple.com/join/ABC123',
));                                                                  // real detail, arrives second
// state UNCHANGED: headline=null, storeUrl=null — the real copy never displaces the blank one
```

Bounded, not urgent: (a) requires a normal 426's body to fail to parse
client-side, a narrower trigger than the ordinary "several requests 426 at
once" case the guard is built for; (b) the block screen's own always-visible
"check again" button calls `VersionGateController.check()` — an
UNCONDITIONAL overwrite (no `isBlocked` guard there) — so one tap against
the real `GET /v1/client/release-floor` self-heals it immediately; (c) the
safety property CR121 exists for (a stale build cannot transact) still
holds throughout — the user is blocked, just with less-helpful copy than
they're owed until they tap the button that's already on the screen.
MINOR, not MAJOR: real, reproducible, but a one-tap-away UX gap, not a
functional or safety defect. Suggested fix (not prescriptive): key the
refusal on "does the incoming exception carry more information than the
