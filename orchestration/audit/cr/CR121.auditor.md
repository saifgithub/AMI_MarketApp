## What I verified and confirms your claims exactly

**Fail-open — all five degenerate-but-successful shapes resolve `ok`,
never `block`, and I tried to break it.** Read `resolve_action`: `if floor
is None or build is None: return "ok"` covers empty table (`get_active_floor`
returns `None`), every row retracted (same — the `active.is_(True)` filter
means an all-retracted table is indistinguishable from empty), and a
malformed/absent `X-App-Version` (`parse_build_number` never raises, always
`None` on garbage). `min_build=0` is additionally blocked at the schema
layer — `AdminReleaseFloorRequest.min_build: int = Field(gt=0)` — so it's
unreachable through the only write path, and even if a row existed with it
(no DB `CHECK` constraint), `build < 0` can never be true since
`parse_build_number` never returns a negative int. **Mutation-proof:**
replaced the `if floor is None or build is None` guard with `if False`
→ 4 of 28 tests failed with `AttributeError: 'NoneType' object has no
attribute 'min_build'` (the exact class of bug the guard exists to
prevent). Reverted.

**Footgun guard — mutation-proof.** `highest_observed_build` scans both
columns, returns 0 on a virgin DB; `create_floor_raise` refuses
`min_build > highest` unless `force`. Deleted the `if not force and
min_build > highest` check → `test_footgun_refuses_min_build_above_highest_observed`
failed (200 instead of 409). Reverted. Your judgement call on 0-as-floor
tripping every raise on a virgin DB is correct and matches the "no evidence
any build exists" framing.

**Middleware ordering — independently verified against Starlette's actual
source, not your reasoning alone.** You asked me to check this
independently since the whole "426 never reaches the audit log" argument
depends on it. Read `Starlette.add_middleware`
(`self.user_middleware.insert(0, ...)` — prepends) and
`build_middleware_stack` (`for cls,... in reversed([ServerError] +
user_middleware + [ExceptionMiddleware]): app = cls(app, ...)`) directly
from the installed `starlette==1.0.0` package. Traced the registration
order in `main.py` (`HTTPAudit` → `VersionGate` → `CORS`) through both
functions by hand: final nesting outer→inner is
`ServerError → CORS → VersionGate → HTTPAudit → ExceptionMiddleware →
router`. **Your claim is correct**: `VersionGateMiddleware` wraps
`HTTPAuditMiddleware`, so a 426 short-circuit before `call_next` never
reaches it — the logging fix (MAJOR above notwithstanding) is necessary,
not redundant.

**Middleware can't 5xx the app.** The DB lookup is wrapped in
`try/except Exception: logger.exception(...)`, falls through to
`call_next`. Matches `test_middleware_fails_open_when_the_floor_lookup_raises`.

**Exempt paths, locale/store-url resolution, admin auth, duplicate-`min_build`
409, per-raise message roundtrip** — read directly, all match the 35
`test_cr121_*` tests, all reproduced green (`35 passed in 2.47s`, targeted
run).

**Mobile** — `_VersionGateInterceptor`'s `upgradeRequiredExceptionFor`
