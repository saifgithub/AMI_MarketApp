## What slice C does (from the module's own docstring and the commit message, cross-read)

Saiful's Option-B ruling (2026-09-11): the training lane charges a flat transaction-cost proxy
(10 bps/side + $1 minimum, deliberately matching `games_scoring.FEE_BPS`/`FEE_MIN` — the two
lanes should not silently disagree about what a round trip costs). Rides the game lane's existing
fee mechanism: computed OUTSIDE `_execute_fill` and passed through as a parameter, not resolved
inside it — same "every caller obliged to supply one" discipline CR194 used for `price_source`.
Shorts and options each charge in their own single cash statement (not double-charged against the
equity toll). Forced closes and game fills pay nothing — the toll is a training-lane, user-chosen-
trade concept, not a penalty on the sweep's own forced liquidations.

**No backfill, and NULL is the mechanism, not just a stated intent.** A trade row written before
the flag flips carries `toll = NULL`, never `0.0` — the module's own docstring states why: a
column of zeros WOULD be a backfill by another name (every historical row would read "this trade
paid $0 in toll", which is a fact nobody measured, the exact CR040 shape CLAUDE.md names).
Cumulative toll is DERIVED by summing per-row amounts at read time, never a running counter on the
portfolio — the docstring states this is deliberate specifically so a `reset_portfolio()` (which
destroys and recreates the `sim_portfolios` row) needs no seeding and no reset code: a fresh
portfolio's own rows sum to 0 by construction, with nothing to forget.

**§F3 disclosure swaps with the flag.** `portfolio_finding.py:519` carries the standing sentence
"this simulation charges no commissions, spreads, or taxes" — confirmed present in the file at
that line. The commit's claim is that this sentence becomes conditionally false and is replaced
when `training_toll_enabled` is on; I read the surrounding `_f3_toll`-adjacent functions
(`portfolio_finding.py:633`, `:690`) which append toll content into §F3 by the same route as the
passive-twin content, but did not this round independently drive both flag states end-to-end
against a running server to watch the sentence actually swap — see Attack surface.

**`TOLL_NO_CHARGES_YET` sentinel.** `training_toll.py:55` — a distinct machine state from
"not measured", used when the flag is on but the book has not yet been charged anything (a fresh
portfolio, flag just flipped). Confirmed present and referenced in both the service
(`training_toll.py:168`) and the test file (`test_cr222_training_toll.py:684,686`).

## Attack surface (named for the auditor, not defended here)

- **The D-5 byte-identical flag-off guard is the single load-bearing claim in this slice, and I
  did not independently re-attack it beyond running it green.** "Flag off changes nothing at
  all" is exactly the CR040 property this whole CR family cares about (§F3's disclosure staying
  literally true when the toll isn't charged) — the auditor should mutate the guard itself (e.g.
  temporarily force `toll_enabled()` to `True` inside the "off" fixture, confirm the guard catches
  it) rather than trust that a passing test named `_byte_identical` actually diffs byte-for-byte
  rather than comparing a looser structural equality. I did not read the guard's own assertion
  body closely enough this round to state which comparison it performs — flagging the gap rather
  than the answer.
- **The NULL-vs-zero distinction is asserted by the docstring; the auditor should confirm no
  code path anywhere defaults a missing toll to `0.0`** (e.g. an aggregate/sum operation that
  coerces NULL to 0 without the caller intending that) — a SQL `SUM()` over a NULL column already
  returns NULL-safe aggregation in Postgres, but the read-time cumulative computation in
  `cumulative_toll_for` is Python-side per the module's own docstring ("nothing here reaches the
  network"), so I'd want the auditor to check its NULL-handling explicitly rather than assume the
  DB layer protects it.
- **§F3 disclosure swap not driven live.** Named above under "What slice C does" — I read the code
  but did not start a server, flip the flag, and diff the actual rendered §F3 block against the
  flag-off baseline. This is the exact thing CR040 exists to catch (a disclosure that's supposed
  to become false and silently doesn't).
- **Shorts/options single-cash-statement claim.** The commit message states shorts and options
  "charge in their own single cash statement" specifically to avoid double-charging against the
  equity toll. I ran the full test file (31/31 green) but did not isolate and re-derive this
  specific non-double-charge property by hand against `sim_shorts.py`/`sim_options.py`'s diffs
  (28 and 14 lines respectively) — those two files' changes are the ones I read least closely this
  round relative to `training_toll.py` and `portfolio_finding.py`.
- **Forced-close / game-fill "pays nothing" claim.** Asserted by the commit message; I found no
  toll-specific carve-out named directly at the game-fill or forced-close call sites in
  `sim_engine.py` during a quick grep (searched for "forced close"/"game fill"/"pays nothing" —
  no direct hits, meaning the carve-out is implemented some other way, e.g. simply never passing a
  toll rate into those call sites rather than an explicit skip check). Worth the auditor tracing
  the actual call graph from `_execute_fill`'s toll parameter back to confirm forced-close and
  game-fill code paths genuinely never compute or pass a nonzero toll, rather than trusting the
  claim.
- **Passive twin symmetry.** The row states "twin deposit-buys charge symmetrically" —
  `passive_twin.py` changed by 78 lines in this commit. Not independently re-derived this round;
  the `test_twin_output_is_byte_identical_to_slice_b_with_the_toll_off` test (in the 31 passing)
  is the builder's own evidence for the flag-off half of this claim only, not the flag-on
  symmetric-charging half.
