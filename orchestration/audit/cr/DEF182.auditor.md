## MAJOR-1 — nothing stops the dedicated key from *being* `SECRET_KEY`

The defect is titled "one secret doing two jobs". The fix closes the path
where that happened *automatically*. It leaves open the path where it happens
*by configuration*, and it is not detected:

```
encrypt with ALPACA_ENCRYPTION_KEY == SECRET_KEY -> enc::v2::gAAAA   (accepted, no complaint)
the SECRET_KEY-derived legacy key opens that v2 row: True
```

That is worse than the v1 state it replaced, in one specific way: the row is
**marked `v2`**, and `v2` is defined in your own docstring as "keyed
independently … rotating `SECRET_KEY` no longer touches Alpaca ciphertext at
all." A row written under this configuration carries a marker that asserts the
exact property it does not have.

This is load-bearing right now, not hypothetically. The register row you
committed says:

> *"So H2/DEF185, H7/DEF178 and M15 can now rotate `SECRET_KEY` freely; the
> 'must land BEFORE any rotation' bar is met."*

That is an unconditional green light, written into the defect register for a
future session to act on, resting on a property nothing checks. If the two
values are ever equal — a first-time `alpha.env` written under time pressure,
a second environment stood up by copy-paste, a key "rotation" that pastes the
wrong line — the rotation silently destroys every ciphertext row, and the `v2`
marker means nobody thinks to look.

You *did* treat the property as load-bearing: your live check printed
`distinct from secret_key : True`. That is the tell. A one-off `python -c` is
how you verify a guard, not how you have one — and this project's own house
rule is that an entry without an enforcing check is not done, with CR040's
corollary that if it must hold, make it structural.

**Cost to close is about three lines**, and there is idiomatic precedent in
the same file: `config.py:341` uses a `field_validator` to fail boot rather
than guess, with a comment saying exactly why. Refusing at the `_dedicated_keys()`
/ `encrypt_secret` site works equally well and keeps it beside the raise it
belongs with. Add the test that pins it — a mutation that removes the check
should red something.

**On key shape, where you invited disagreement:** I agree an entropy check is
out of scope and I am not asking for one. `ALPACA_ENCRYPTION_KEY=x` is
accepted and SHA-256'd, and I measured that too — but a weak key is a weak
key, whereas key-equals-`SECRET_KEY` is *the defect returning under its own
fix's marker*. They are not the same finding. They do share a check site, so
if you want to reject a key below some length while you are there, it is free;
I will not hold the lane on it.

## MINOR-1 — `_PREVIOUS` set with the current key empty writes under the retired key

```
wrote with ALPACA_ENCRYPTION_KEY="" and _PREVIOUS=A, then read with A: True
```

`_dedicated_keys()` returns `[current, previous]` filtered for truthiness, and
`encrypt_secret` writes with `dedicated[0]`. With only `_PREVIOUS` set, that
index is the *previous* key — so new secrets are encrypted under the key the
operator believes is retired, tagged `v2`, with no warning. It is loud later
(clearing `_PREVIOUS` makes those rows raise), but silent at the moment of the
mistake, which is the wrong end.

It is reachable from your own documented procedure: step 3 says "clear
`ALPACA_ENCRYPTION_KEY_PREVIOUS`", and clearing the other one instead lands
here. Same check site as MAJOR-1 — a write must use the *current* key or
refuse.
