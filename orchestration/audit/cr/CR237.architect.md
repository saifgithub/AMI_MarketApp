## Why (unchanged from CR237.md)

When every analyst desk answers but the CIO is unreachable, the Room ends in the DEF059
fail-safe PASS ("AMI's analyst room lost its model connection before the Chief Investment
Officer could rule…"), refunded since DEF432. The analysts' work is still on the run; this lets
the user retry ONLY the CIO's own turn against that saved work, free, without reconvening the
whole Room. Saiful: "we could also retry the CIO run. maybe offer the option to the customer."

## The design

1. **One shared CIO-step function**, `_run_cio_step`, extracted from what used to be inline in
   `run()`'s VERDICT phase — builds the PM prompt (or the CR098 no-parse NO_VERDICT), samples/
   votes, parses, runs `enforce_safety_floor`/compliance/sizing, and assembles the final
   verdict. Called from both `run()` (line ~6581) and `retry_cio_step` (line ~7056) — no second
   copy of the floor, the compliance check, the sizing math, or either annotation pass. This is
   the structural guarantee the floor-still-applies test below verifies.
2. **`cio_retry_eligible(...)`** — the one predicate for "can this run be retried", read by both
   the route (to decide whether to actually retry) and the `cio_retry_available` flag on every
   run payload. True only when: own run; `status == completed` AND the verdict is the DEF059
   outage PASS (`is_llm_outage_verdict`) — never the R51 partial-outage NO_VERDICT and never a
   reasoned verdict; a `cio_context_snapshot` was persisted; `mandate_version` matches the
   CURRENT stored mandate; within `settings.room_cio_retry_max_age_minutes` (default 240,
   forwarded in `docker-compose.yml` — `test_config_compose_parity` passes). The in-flight guard
   (`RoomRunner._retrying_runs`, an in-memory set) is separate and stateful, checked inside
   `retry_cio_step` itself.
3. **Three new `room_runs` columns**, migration `cr237a0cio0retry1` (single head off
   `def425a0interrupt1` — re-verified: `alembic heads` reports exactly one head after this
   worktree's merge with `main`, `cr237a0cio0retry1`):
   - `refund_recorded` — set True exactly once, at the instant a refund actually SUCCEEDS
     (DEF432 outage or CR039 failed-run), never cleared. `run_was_refunded` reads this FIRST so
     a later successful retry can't un-flip a genuinely-refunded run to "charged".
   - `cio_context_snapshot` — nullable JSONB, the pre-CIO desk-phase products (trader levels/
     sizing, withheld/scripted rosters, the fundamentals `profile`) a retry needs to replay just
     the CIO step. Written only on the DEF059 outage PASS.
   - `cio_retried` — set True once a retry SUCCEEDS on a run. Drives the mobile cost line's
     third branch.
4. **Retry rebuilds safety context FRESH** — mandate, portfolio value/drawdown, sector/risk-
   limit context, halal/classification universes are all re-resolved at retry time via the same
   builders `run()` itself calls, off the CURRENT user/ticker state — never carried from the
   original run's snapshot. Only the desk-phase PRODUCTS (arguments, trader levels, the option
   menu's inputs) come from the snapshot; the option menu itself is re-priced against the
   current chain. Verified by `test_retry_reads_current_portfolio_value_not_original_runs` and
   `test_mandate_change_between_outage_and_retry_is_caught_by_eligibility`.
5. **Free** — `retry_cio_step` never calls `spend()` or `refund()`. A successful retry leaves
   `refund_recorded` True (the original outage refund stands) and sets `cio_retried` True.
   Verified by `test_successful_retry_makes_no_spend_or_refund_call_at_all` (a real monkeypatch
   count, not an absence-of-evidence read).
6. **Journal updated in place** — `journal_store.update_by_reference` overwrites the LIVE entry
   for `(user_id, ROOM_RUN, run_id)` rather than appending a second one; `retry_cio_step` calls
   `append` only as a defensive fallback if no prior entry exists (should not happen — every
   terminal run journals on `on_complete` — but a missing entry must not fail an otherwise-
   successful retry).

## The route (added by me — not in the applied draft)

`POST /v1/room/runs/{run_id}/cio-retry` in `api/room.py`, SSE, mirroring `stream_room`'s own
event translation (`phase`/`agent_token`/`agent_done`/`verdict`/`error`, plus a `done` terminal
event carrying `credit_cost`/`refunded`/`cio_retried`/`cio_retry_available`). Ownership and
existence (404/403) are checked SYNCHRONOUSLY before any SSE body is sent — same discipline as
`stream_room`'s pre-stream 402: a refusal the caller can know up front must be a real HTTP
status, never an in-band `error` event the client has to sniff for. Every OTHER refusal (wrong
verdict shape, stale mandate, aged out, in-flight) surfaces as an in-band `error` event, mirroring
`retry_cio_step`'s own refusal shape.

**DEF200 ratchet caught a real mistake of mine**: I first wrote the handler as `async def`
(matching `stream_room`), which `test_no_new_handler_blocks_the_event_loop` flagged — the
handler's only work before returning `StreamingResponse` is the sync `runner.get_run(run_id)`
ownership check, which `async def` would run ON the event loop rather than in Starlette's
threadpool. Fixed by making it a plain `def` (matching `get_room`/`list_user_rooms`, the other
two handlers whose only pre-stream work is a sync DB read) — the retry's own I/O runs later,
inside the `StreamingResponse` body, off this call stack entirely. Ratchet passed clean after
the fix; no baseline entry added.

## Attack surface (please probe)

1. **Can the retry bypass the floor?** No — verified above, both by the test and by an external
   mutation of the real production call site.
2. **Can the retry charge or double-refund?** No — `retry_cio_step` never calls `spend()`/
   `refund()` (verified by a real monkeypatch call-count assertion,
   `test_successful_retry_makes_no_spend_or_refund_call_at_all`); `refund_recorded` is left
   True (never re-set) on a successful retry, so `run_was_refunded` stays truthful
   (`test_successful_retry_keeps_refund_recorded_true_ledger_nets_zero` drives a real ledger
   balance check, not just a flag read).
3. **Can the retry run on a non-outage run?** No — `cio_retry_eligible` requires
   `is_llm_outage_verdict`, re-checked inside `retry_cio_step` itself even if a caller's earlier
   check somehow passed (`test_retry_refuses_a_non_outage_verdict`).
4. **Can the retry run on someone else's run?** No — the route checks `run.user_id ==
   current_user.id` before streaming anything (404/403, real HTTP status, not an in-band
   event); `retry_cio_step` itself re-checks via `cio_retry_eligible`'s own ownership clause
   (`test_retry_refuses_someone_elses_run` drives the runner method directly, bypassing the
   route, to prove the SERVICE layer's own check holds independent of the route's).
5. **Can two retries run concurrently on the same run?** No — `RoomRunner._retrying_runs` (an
   in-memory set) blocks a second attempt while the first is genuinely in flight. Verified with a
   REAL concurrency probe (`test_second_concurrent_retry_on_same_run_is_refused_in_flight`): a
   gateway that blocks on an `asyncio.Event` inside the CIO call, a first retry task started and
   confirmed via `runner.is_retrying(run_id) is True` BEFORE the second attempt is made — not a
   sequential-call assertion that could pass by accident.
6. **Does a retry survive a restart cleanly?** Yes —
   `test_restart_mid_retry_leaves_outage_pass_untouched_no_credit_movement`: starts a retry
   against a gateway whose CIO call hangs forever, cancels the wrapping task mid-flight
   (simulating a process death), then reads the row back through a FRESH `RoomRunner` instance
   (fresh in-memory `_retrying_runs`, matching what a real process restart would present) and
   confirms `status` is still `completed` (never left at `running`, so DEF425's sweep — which
   only claims `status == "running"` rows — cannot touch it), the outage verdict is unchanged,
   `cio_retried` is False, and no credits moved.
7. **Does a retried run's cost line stay truthful?** Yes — `RoomResultCostLine`'s `cioRetried`
   branch takes priority over both `refunded` and the normal cost line, rendering
   `roomResultCioRetried` ("Not charged — the CIO's retry was free, and the original Room was
   refunded") — the one shape that is simultaneously "finished" (so `roomResultRefunded`'s
   "didn't reach a verdict" text would be false) and "never net-charged" (so the normal cost
   line would be false too). Covered by a mobile widget test rendering the real widget tree, not
   a unit test of the string logic alone.
