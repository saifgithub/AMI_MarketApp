# DEF425 — auditor verdicts (container restart mid-Room charges full price, no verdict, no refund)

## Round 1 — auditor U68

**SHA audited:** fix `18e1c0a3`, merged `b5de455c`, at `main` `16990d51`. Not live: Alpha still runs
`685dbdd0`. Scratch worktree `audit-U68-Q` per DEF159.

**The drill, re-run for real.** I built a throwaway stack on melehost: an API container on the HEAD
tree (confirmed `RoomRunner.mark_shutting_down` present in the loaded module), with its own
Postgres, Redis and network. The LLM is the mock provider, and a full Room takes about 24s for 8
credits (baseline: `completed`, 13 → 5). A driver convenes a Room over the real `/v1/room/stream`
SSE route, reads for 6s and disconnects. About 8s into the run I send a real SIGTERM
(`docker stop -t 10`). Everything was removed afterwards.

### What holds

- **The shutdown is now told apart from anything else, and the row is left RUNNING.** The stop
  took 1s and logged `room_cancelled_shutdown`, and the row stayed `running`. `mark_shutting_down()`
  ran before the cancellation reached `run()` on the real uvicorn shutdown sequence (attack surface
  §2, measured).
- **Retry-exhausted rows are refunded, exactly once.** Row at `retry_count=1`, aged past the cutoff:

```
D3 AFTER BOOT 1: failed | abandoned: auto-retried 1 time(s), gave up | balance 13 | credits_spent 13->5, credits_refunded 5->13
D3 AFTER BOOT 2: failed | balance 13 | (no second refund)
```

- **A retried run is not charged twice.** Drill 2 below completed with one `credits_spent`.
- **A client disconnect does not cancel the run.** Dropping the SSE at 5s with no restart gives
  `completed`, one charge, one journal entry. There is no user-cancel feature to regress.
  The inert CANCELLED branch (§4) is reachable only by a direct `.cancel()`, and nothing calls
  one.

### MAJOR-1 — after an ordinary restart the credits stay taken: the sweep only claims rows older than 30 minutes

`_sweep_stuck_runs` runs once, at `RoomRunner.__init__`. It selects `status == "running" AND
started_at < now - room_dedup_running_minutes`, which is 30 minutes (`room_runner.py:4528-4537`,
`config.py:491`). A restart brings the process back in seconds, so the row DEF425 now leaves
RUNNING is too young for that one sweep, and nothing looks at it again. Measured, with a restart
immediately after the SIGTERM:

```
AFTER STOP:         running | retry 0 | cost 8 | balance 5 | journal: "Room on AAPL — running"
AFTER BOOT +20s:    running | retry 0 | cost 8 | balance 5
AFTER BOOT +80s:    running | retry 0 | cost 8 | balance 5
same user re-convenes AAPL -> X-Room-Run-Id = the SAME dead run; stream replays 4 agent_done then `done`, no verdict
```

- **The credits.** They come back only at the next boot that happens at least 30 minutes after
  the run started. Drill 2 aged the same row by 31 minutes and restarted: `completed | retry 1 |
  REJECT`, charged once. On Alpha the next boot is the next promotion, hours or days later. If it
  never happens, the 8 credits never return.
- **The user is also locked out.** `_find_active_run` (`:4764-4783`) treats the dead row as live
  for the same 30 minutes, so re-convening that ticker attaches to a run no process is executing
  and ends with no verdict. Before the fix, the user could at least re-run it by paying again.
- **Why the tests passed.** The lane's test `test_shutdown_cancelled_row_is_claimed_by_the_sweep_on_next_boot`
  backdates `started_at` by an hour (`test_def425_shutdown_cancel_no_refund_gap.py:188`), which
  covers up exactly this gap.

The acceptance question was whether a restart mid-Room eats credits. For the restart that
actually happens (a promote, a `docker restart`), it still does. They are now held rather than
lost outright, and the ticker is blocked for 30 minutes on top.

**Fix:** at boot, claim every `running` row the new process is not executing. Uvicorn runs a single
worker here, so at `__init__` nothing is executing. That means `started_at < process_start` (or
no cutoff at all), not `< now - 30min`. If the cutoff must stay for a multi-instance future, mark
the interrupted row (for example `interrupted_at` on the shutdown branch) and let the sweep claim
marked rows at once. Add a test with a fresh `started_at`.

### MINOR-1 — the shutdown path writes a Decision Journal entry for a run that has not finished

`_pump`'s `finally` still calls `on_complete` (`_finalise_to_journal`) when `run()` re-raises on
shutdown (`room_runner.py:5150-5184`, the call at `:5177`). `_finalise_to_journal` then journals the RUNNING row as
*"Room on AAPL — running … without reaching a verdict"*. ROOM_RUN entries carry no dedupe key, so:

- **after a retry**, the journal holds both entries. Drill 2: `Room on AAPL — running || Room on
  AAPL — REJECT`.
- **after exhaustion**, the only entry says "running" for a run that is failed and refunded
  (drill 3).

It is user-facing and wrong, but no money moves, so it is MINOR. **Fix:** skip `on_complete` in
`_pump` when `self._shutting_down` is set. The retry or the sweep writes the real entry.

### Evidence

```
pytest test_def425_shutdown_cancel_no_refund_gap.py test_def424_llm_down_branded_fallback.py -q -p no:cacheprovider   13 passed  EXIT=0
Drills (throwaway stack, real SIGTERM): D1 immediate restart, D2 aged retry, D3 exhausted + double boot, D4 client disconnect: as above
```

The builder's two mutations are recorded. My drills probe the guarantee directly.

FOREIGN: not run — no `foreign/DEF425.r1` branch exists. Not a clean bill.

### Verdict

The mechanism is right. The shutdown is recognised, the row is kept for the sweep, a retry does
not double-charge, and an exhausted row is refunded once. But on a real restart the sweep cannot
see the row for 30 minutes and never looks again. So the Room is not retried and not refunded,
and the user cannot re-run that ticker in the meantime. The goal is not yet met.

### MAJOR-1 (round 2) — while any response is still streaming, the shutdown never reaches the mark: the row is left exactly as in round 1

**The cause.** The mark is written in `run()`'s shutdown branch. That branch only runs once the
lifespan `finally` has called `mark_shutting_down()` and the loop is torn down. Uvicorn 0.47 runs
the lifespan shutdown only *after* in-flight responses finish ("Waiting for connections to
close"). Nothing bounds that wait: no `--timeout-graceful-shutdown`. So when a user is watching
their Room at SIGTERM, uvicorn waits on that SSE stream until Docker SIGKILLs it at 10s. The
lifespan never runs, and the row is never marked. The same happens with any other open stream on
the process, such as a Brief or 1-on-1 reply, and then it applies to *every* running Room, not
only the watched one.

**Drill A, measured: the client stays connected through the SIGTERM.**

```
stopped after 11s   "Shutting down" / "Waiting for connections to close" — then SIGKILL; no room_cancelled_shutdown
AFTER STOP:       running | retry 0 | marked=f | balance 5
AFTER BOOT +45s:  running | retry 0 | marked=f | balance 5        <- round 1's MAJOR-1, unchanged
```

A user watching the Room during a promotion is the ordinary case. It is exactly the restart
DEF425 was filed for.

**The fix is proven.** I re-ran drill A with only one change: the API started with uvicorn
`--timeout-graceful-shutdown 5`.

```
room_cancelled_shutdown logged, "Waiting for application shutdown" -> "Finished server process"
AFTER STOP:       running | retry 0 | marked=t | balance 5
AFTER BOOT +45s:  completed | retry 1 | REJECT | balance 5 | spent once | journal: "Room on AAPL — REJECT"
```

**Fix:** add `--timeout-graceful-shutdown 5` to the API's uvicorn command (the Dockerfile `CMD`, or
a compose `command:` for `api-alpha`). It must stay below the container's stop grace, which is
Docker's default 10s today unless `stop_grace_period` is raised. Pin both in a parity test, in the
style of `test_config_compose_parity`, so the timeout cannot drift above the grace. Unmarked rows
from a real SIGKILL or OOM still fall back to the 30-minute age rule, as the Architect states.
That is accepted.

### MINOR-1 (round 2) — the retry's own pump still journals a run that is still RUNNING at shutdown

AFTER STOP 2:  running | retry 1 | journal: "Room on MSFT — running"
BOOT 2:        failed + refunded | journal: "Room on MSFT — running"   <- the only record of a failed, refunded run

Add a test that shuts down a respawned run.

  cancel-and-await of its own tasks, which takes milliseconds. I did not reproduce it.
- **The mark stays on failed rows.** A `failed` row keeps `interrupted_at` set. That is harmless:
  the sweep selects only `running`.

### MAJOR-1 (round 3) — a respawned Room's row is rewritten to the base price, so the refund DEF425 guarantees gives back less than was charged

**Where.** `_respawn_run_from_row` calls `self.run(...)` without `credit_cost`
(`room_runner.py:4796`). `_PendingRetry` has no field to carry it (`:4258`). So `run()` falls back
to `room_cost_for_plan(plan)` (`:5397`), and `_persist_run` overwrites `row.credit_cost` with that
base price (`:4324`). The charge `start_run` actually made included the CR090 live-data surcharge,
which is up to 4 credits (`credit_service.py:112`, `start_run` `:5033`). That amount is lost from
the row before any refund reads it. Every refund path on a respawned run reads the row's figure:

- the retry-exhausted sweep refund, which is DEF425's own code (`:4644-4658`);
- the CR039 failed-run refund (`:6447`);
- DEF432's outage refund (`:6292`). DEF432's audit carries that one, so it is cited here and not
  scored twice.

The same row also streams `live_data_notice.surcharge_charged = 0` for a run that was charged the
surcharge (`:5455`).

**Measured.** This is the same probe as above, with a trader-plan user charged `8 + 4 = 12`:

```
base=8 charged=12 bal0=150 after_spend=138
after respawn: row.credit_cost=8
boot 3: failed + refunded -> balance=146 (net loss 4)
```

A Room that produced nothing kept 4 of the user's 12 credits, which is 33% of the charge. That is
the exact wrong DEF425 exists to prevent: credits taken for a restart. The fallback itself is
older (CR090 left the respawn at base pricing). But DEF425 is what now routes every
deploy-interrupted Room through the respawn, and the retry-exhausted refund that reads the
overwritten figure is DEF425's own code. So it is in scope.

**Fix direction:** in `_sweep_stuck_runs`, add `credit_cost: int` to `_PendingRetry` and fill it
from `row.credit_cost`. Pass `credit_cost=p.credit_cost` to `self.run()` in the respawn. Add a
test that seeds a surcharged row, respawns it, and asserts two things: the row keeps its charged
figure, and a retry-exhausted refund returns the full amount.

### MINOR-1 (round 3) — the interrupted-at mark depends on uvicorn being PID 1, and nothing pins that

**The chain.** Round 3 made `mark_shutting_down()` reachable. But the stamp itself is written in
`run()`'s cancellation branch, and only after something cancels the Room's `_pump`. The lifespan
cancels only its own tracked tasks (`main.py:535-541`). The pumps are bare `create_task`s
(`room_runner.py:4858`, `:5309`), so what cancels them is `asyncio.run`'s teardown. The
`mark_shutting_down` docstring relies on that (`:4536-4541`). The catch is in uvicorn 0.47's
`capture_signals`: after `serve()` returns, it re-raises the captured SIGTERM **inside the event
loop** (`server.py:338-339`). A normal process dies right there, before any teardown.

**Measured.** This is the same probe app and client, with the flag set:

```
as an ordinary process:              LIFESPAN_SHUTDOWN at +5.16s, then process dies by SIGTERM; PUMP_CANCELLED never logged
SIGTERM inherited as SIG_IGN
(emulates PID-1 semantics):          LIFESPAN_SHUTDOWN at +5.17s, then PUMP_CANCELLED shutting_down=True
```

It works in the container today only because the exec-form `CMD` makes uvicorn PID 1. The kernel
drops a re-raised SIGTERM that has no handler, so teardown runs. U68's drill A2 is consistent
with that. Two changes that look harmless would silently remove the mark on every Room while all
tests stay green: compose `init: true` (mutation 7 survives), or a shell-form or wrapper
entrypoint. The unit tests call `mark_shutting_down()` and `task.cancel()` by hand, so the real
teardown never runs under test.

**Fix direction:** make it structural. Have `RoomRunner` keep a set of its `_pump` tasks. In the
lifespan `finally`, after `mark_shutting_down()`, cancel and await those tasks (bounded well
inside the remaining 10s of grace). The shutdown branch then runs before uvicorn's re-raise,
whatever the PID. The minimum alternative is a parity check that pins an exec-form `CMD` and no
`init:` on `api-alpha`. It is graded MINOR because it holds on the deployed shape today.

### Recorded, not scored

- **A comment claim is false.** The comments at `room_runner.py:4826-4829` and `:5296` say the
  sweep's retry-exhausted `failed` branch "writes the real, terminal entry". It writes none: the
  probe shows 0 journal entries for a failed-and-refunded run. No entry is better than round 2's
  false "running" one, but a refunded Room now leaves no journal record at all. Either write a
  `failed` entry from the sweep or correct the comments.
- **The parity test reads only the Dockerfile.** A future compose `command:` on `api-alpha` would

- **`return` inside `finally` swallows the pump's CancelledError** (`:4829`, the same shape as

- **Carried from round 2:** the shutdown flag is process-wide, and a live re-drill on Alpha after
