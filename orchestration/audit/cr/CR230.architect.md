## What and why

Saiful, on CR227's own privacy-review thread, after I reported two things I'd framed as privacy
gaps (`llm_audit` capturing unredacted Alpaca portfolio snapshots, potential Sentry
local-variable exposure) and asked whether to file a Defect: *"on the contarary. we need to keep
a log of every interection we have with alpaca. there is no privacy issue at the moment since
these are paper trading."* — an explicit reversal of my framing. He does not want those two things
scrubbed; he wants Alpaca interaction logging kept, and by extension, more complete.

Taking "every interaction" literally surfaced a real asymmetry: the backend's only Alpaca
visibility was incidental — a portfolio snapshot upload that happens to ride along on a Room/chat
turn. **Order placement itself — the actual `POST /v2/orders` call CR227 added — left zero
backend trace**, because CR227's design is mobile-direct (CR202 custody: the backend never holds
the credential). I filed CR230 to close that gap with a purpose-built log of order *attempts*,
then Saiful said *"Build CR230, and remmeber to send it to nthe auditor"* — this submission.

## Scope: order attempts only, not a general Alpaca-call proxy

`account()`/`positions()` reads are deliberately NOT logged — they're not state-changing, and
logging every poll would be high-volume noise (the Portfolio screen refreshes on-demand) for no
decision-relevant benefit. Order placement is the interaction that matters: it's the one action
this app takes against a real (paper) brokerage account. If you think this scope call is wrong —
that "every interaction" should include reads — that's a fair thing to attack; I judged it a scope
decision within what Saiful asked for, not a gap in it, but I'm not certain of that reading.

## Design

### Backend: `AlpacaOrderLogIn` schema

`backend/app/schemas/alpaca.py` — `extra="forbid"`, reuses the existing `_SYMBOL_PATTERN` (even
though this data never reaches an LLM prompt, so the prompt-injection rationale that pattern
exists for doesn't strictly apply — I judged a DB column still isn't the place for a client to
write arbitrary strings, so kept the bound rather than dropping it). `side` and `destination` and
`outcome` are each a closed enum via regex (`^(buy|sell)$`, `^(alpaca_only|both)$`,
`^(submitted|rejected_by_alpaca|refused_client_side)$`). `detail` capped at 500 chars,
`alpaca_order_id`/`alpaca_status` at 64/32.

### Backend: `AlpacaOrderAuditRow` + migration

`backend/app/db/models.py` — new table `alpaca_order_audit`. `user_id` NOT NULL (unlike
`LLMAuditRow`'s nullable `user_id` — every row here comes from an authenticated, claimed user via
`_require_claimed`, there is no anonymous/system path that would need NULL). Migration
`cr230a0order0log_alpaca_order_audit.py`, single head off `e221i000009c`, `create_table` +
two explicit indexes (`created_at`, `user_id`) — not `index=True` inline, matching the DEF337
class convention `admin_audit`'s own migration set.

**Retention posture — decided during implementation, diverges from the CR doc's original
assumption.** The CR doc as filed assumed `llm_audit`/`http_audit`'s 90-day
`trim_audit_tables()` sweep. While implementing, I judged that wrong: Saiful's instruction was
"keep a log of every interaction," and `admin_audit`'s own docstring already states the exact
reasoning that applies here — "volume is human-scale [per-trade, not per-HTTP-request] and
forensic value is permanent." A 90-day auto-delete works against "keep a log of every
interaction." I followed `admin_audit`'s pattern instead: excluded from `trim_audit_tables()`
entirely, and pinned that by a test (`TestRetentionPosture::test_a_row_older_than_the_audit_retention_window_survives_the_trim`
— stamps a row 200 days old, runs `trim_audit_tables()`, asserts the row survives). **This is the
one design decision in this submission I'd most want checked**: did I read Saiful's instruction
correctly, or should this have stayed on the 90-day track like every other audit table? I have no
way to ask him before this round closes, so I'm flagging the judgment call explicitly rather than
letting it pass as if the CR doc's original text still applied.

### Backend: route

`POST /v1/alpaca/order_log` in `backend/app/api/alpaca.py` — `get_current_user` +
`_require_claimed` (same gate as `link`/`link_state`), writes one row via a new
`record_alpaca_order()` helper in `backend/app/services/audit.py` (added alongside
`record_llm_call`/`record_http`/`record_one_on_one_message`, same best-effort
try/except-logged-never-raises shape as its siblings), returns 204. Write-only — no read endpoint
in v1.

**Deliberately not touched:** `backend/app/services/alpaca_service.py` — DEF145's guard test
AST-parses that exact file for its `httpx` call allow-list, and this CR adds no Alpaca HTTP call
anywhere (it's a logging write against AMI's own DB, not a call to Alpaca). Confirmed below.

### Mobile: call site

`trade_ticket_sheet.dart`'s `_placeAlpacaOrder()` (existing, from CR227) now takes a
`TradeDestination` parameter and calls a new `_reportOrderLog()` helper on every resolution
branch:
- success → `outcome: submitted`, carrying the returned `AlpacaOrder.id`/`status`
- `AlpacaOrderRejected` (CR227's client-side refusal — non-market order type or non-paper host,
  never reached Alpaca) → `outcome: refused_client_side`
- `AlpacaException` or any other throw (an Alpaca-side HTTP rejection) → `outcome:
  rejected_by_alpaca`

`_reportOrderLog()` wraps the call in `try { } catch (_) { }` — the exact same swallow-on-failure
idiom `alpaca_connect_screen.dart`'s `_reportLinked` already uses for CR203's link-state report,
not `unawaited()` (I said `unawaited` in the CR doc's original design section before writing the
code; the doc has been corrected to match what I actually built — try/catch, awaited, still
fire-and-forget in effect since nothing branches on its result).

`ApiClient.alpacaReportOrderLog()` (`api_client.dart`) is the new client method, sibling to the
existing `alpacaReportLinkState()`.

## The load-bearing guarantee: a failed log call must never change the trade outcome

This is the finding I most want attacked. The log call runs AFTER the trade outcome is already
decided (`_placeAlpacaOrder` builds its return value first in each branch's logic, the report
call is a side effect alongside it) — but "runs after" in source order isn't proof it can't still
break something (an unhandled exception from a fire-and-forget call can still crash the isolate
or corrupt widget state if not actually swallowed).

**Proven by mutation, not just asserted.** In the clean verification worktree, I removed the
`try { } catch (_) { }` around the `alpacaReportOrderLog` call in `_reportOrderLog()` (left the
bare `await` call). Re-ran `cr230_alpaca_order_log_test.dart`:

```
Expected: <null>
  Actual: <Instance of 'Exception'>
the report was still attempted despite failing
  [failed on t.takeException() no longer returning null — the throw surfaced into the widget tree]
```

3 passed / 1 failed — exactly the test named for this guarantee ("a throwing order_log call still
shows the same success banner as a working one"). Reverted; 4/4 again; `git status --short`
clean.
