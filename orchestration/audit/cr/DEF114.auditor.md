# DEF114 — audit lane (auditor)

**Item:** every streamed text surface — Room `agent_token`, Brief Your Agent, 1-on-1 chat — decoded
the backend's escape with two sequential `replaceAll`s that cannot invert it **in either order**,
silently corrupting any text containing a backslash immediately followed by `n`.

**Gate:** independent — corrupts text the user reads, on three shipped paths.

**Audited SHA:** `2895970`, off `main` @ `98c6a07`. Isolated worktree
`.claude/worktrees/audit-DEF114/`. **Provenance:** filed from the CR090-MOBILE auditor's mutation
set as a *coverage gap*; the Architect re-ran the round-trip in real Dart before laning and
**upgraded it to live corruption** — both decode orders are wrong, so pinning the current order
would have enshrined the bug.

### Correctness — a property test, not another corpus

The Architect verified 18 hand-picked cases. I did something independent and stronger: transcribed
the backend escape into Dart and **exhaustively enumerated every string up to length 5 over the
alphabet that can actually break this codec** (`\`, `n`, newline, `a`, tab) plus a 20,000-case
randomised sweep over a wider alphabet including `"`, `'`, `é` and an emoji.

```
cases checked            : 23906
SHIPPED helper failures  : 0
old order A failures     : 3772   (non-vacuity check)
old order B failures     : 3772   (non-vacuity check)
   e.g. both break on [92, 92, 92, 92, 110]   ->  \\\\n
```

`unescape(encode(s)) == s` holds for **all 23,906**. The test is provably non-vacuous — both
previously-shipped orders fail 3,772 cases each — which also confirms the Architect's "both orders
are wrong" re-grade exhaustively rather than on three examples.

That subsumes the unrecognised-escape divergence they flagged (shipped writes both chars and
advances 2; their reference advances 1). It cannot diverge: the only character that can *start* an
escape is `\`, and `\\` is handled explicitly — so the char at `i+1` can never itself begin one. The
property sweep covers it empirically.

### D3 — the judgement call the Architect asked for

They offered it rather than asserting: *"is an untested cross-file invariant acceptable here, or does
it want a guard on the backend side?"*

I verified the invariant myself rather than accept it. All four sender sites apply the escape to a
**complete value**, not a stream: `room.py:214` (`msg.content`), `:237` (`ev.text`),
`one_on_one.py:115` and `brief.py:115` (`chunk`). No escape sequence can span a chunk boundary,
by construction, at every site today.

**My judgement: acceptable, but worth a new item — MINOR, not blocking.** It is not fail-open in
current code; it is a correct invariant that no test pins, so a future switch to a streaming escape
would silently reintroduce the corruption on all three surfaces. The cheap guard belongs on the
backend (assert each SSE sender escapes a complete value), and D2 deliberately scoped the backend
out — so I agree with the Architect that this is a **new item, not a round-2 fix**, and it does not
hold up this verdict.
