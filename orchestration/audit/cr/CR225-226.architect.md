# CR225 + CR226 — audit lane (AdMob re-link + global adaptive banner + text-scale clamp)

**SCOPE:** cr

**TIER: A.** CR225 re-links `google_mobile_ads`, which is the first point at which this
build can ACTUALLY reach a third-party ad network in production — CR122 (2026-07-29)
built the full consent/ATT/CCPA flow, but DEF351 (2026-08-21) unlinked the SDK before it
ever shipped live, so nothing built on it has been exercised end-to-end against a real
platform channel. That crosses the consent/privacy perimeter (UMP gather, App Tracking
Transparency, GDPR/CCPA `rdp` extra) from inert code to reachable code, which is the
condition CLAUDE.md's audit protocol treats as Tier A regardless of how contained the
diff looks. CR225 also touches the store-build compile path directly (a broken link here
is a shipped-build-breaking regression, DEF351's own failure mode). CR226 rides the same
tier because it depends on CR225 and adds the one placement visible on every screen — the
widest blast radius any placement in `ads.md` has. Neither CR touches auth, money
movement or the mandate/compliance-floor logic itself.

**SHA:** `bb74e85b` (both CRs, one commit — see "Why one commit" below). On my worktree
branch, not merged to `main`. Review with
`git show bb74e85b --stat` then `git diff 61817c70..bb74e85b -- mobile/ docs/ scripts/`.

**depends-on:** none (CR225 is itself the base CR226 depends on). **Promoted:** no
(mobile; ships in the next TestFlight/Play build after this verdict, per the standing
mobile-lane practice).

## What and why

**CR225.** DEF351 (2026-08-21) unlinked `google_mobile_ads` after `^9.1.0` broke every
`flutter build ios --release` archive (`-Wnon-modular-include-in-framework-module` on a
header the plugin's own `FLTAd_Internal.h` imports out of its vendored framework). The fix
this CR lands: pin to `9.0.0` **exact** (not a caret range — `^9.0.0` could resolve back
into the broken 9.1.x range on a future `pub upgrade`), restore the deleted
`admob_real_sdk.dart` adapter unchanged in shape, re-wire `ads_providers.dart`'s
`adsServiceProvider`/`adMobUmpConsentProvider` to their pre-DEF351 form. One functional
wrinkle: 9.0.0 predates the `AgeRestrictedTreatment` enum 9.1.0 introduced, so
`configureAndInitialize` now maps `AdAgeTreatment` onto 9.0.0's older
`tagForChildDirectedTreatment`/`tagForUnderAgeOfConsent` int-coded fields instead — same
policy contract (`ad_content_policy.dart`'s "age treatment NONE, never silently dropped"),
different wire shape. Flagged for the auditor's own read, not just mine, in Attack surface
2 below.

**CR226.** All six existing placements (`ads.md`) are screen- or empty-state-specific, so
Floor Pass ad revenue depends on a user reaching particular screens. Saiful asked
(2026-09-22) for one placement visible everywhere; CR232 (already on `main`) reserved a
`ShellBannerSlot` in `HomeShell`'s persistent chrome (nav / ad slot / ticker tape) for
this CR to fill. Saiful's rulings this session (2026-09-24, verbatim from the dispatch):
banner on every post-onboarding page in that order; internal builds serve Google's
official AdMob TEST unit IDs structurally, real IDs only on production builds; a visible
separator between the nav and the banner (accidental-click risk); paid tiers see no
banner. The adaptive-sizing and text-scale-clamp halves of CR226's scope come from a
design-research pass under CR231 (`ad_adaptive_research.md`, `ad_placements_research.md`)
that measured real chrome heights against real form factors and found two pre-existing,
ads-adjacent gaps: no text-scale clamp anywhere in the app (`app.dart` sets no `builder:`),
and the header title had no overflow guard (only its subtitle did).

## Changes

**CR225 — SDK re-link:**
- `pubspec.yaml` — `google_mobile_ads: 9.0.0` exact pin, re-added.
- `admob_real_sdk.dart` — restored (was deleted by DEF351); `_tagFor` remaps age
  treatment onto 9.0.0's API (see above).
- `ads_providers.dart` — `adsServiceProvider`/`adMobUmpConsentProvider` restored to serve
  the real adapter when `AdMobConfig.setup` resolves non-null; unchanged (house-only) when
  it doesn't.
- `test/ads_structural_test.dart` — `_adSdkAdapterExpected` flipped back to `true`.

**CR225/CR226 shared — the internal/production ad-unit gate (Saiful's ruling, landed once
since both CRs' surface needs it):**
- `admob_config.dart` — new `AdMobReleaseChannel` enum (`unknown`/`internal_`/`production`)
  and `AMI_RELEASE_CHANNEL` dart-define. `AdMobConfig.resolve` now takes a `channel`
  parameter; `mode=live` is honoured **only** when `channel == production` — every other
  channel, including the unset/dev default, downgrades to Google's reserved test unit ids,
  loudly logged, rather than either serving real units or refusing to house fill.
- `build_testflight.sh`/`build_playstore.sh` — derive `AMI_RELEASE_CHANNEL` structurally
  from the SAME `--internal-only`/`--production` flags that already gate the RevenueCat
  Test-Store-key and CR109 games checks (never an independently-settable env var).
- `install_iphone.sh` — deliberately does NOT forward the channel define at all, so a
  cable install always resolves `unknown` (the conservative downgrade) even if
  `ADMOB_MODE=live` is set locally.

**CR226 — the banner itself:**
- `ads_models.dart` — `AdFormat.banner`, `AdPlacement.globalBanner` (7th entry in
  `AdPlacement.approved`).
- `admob_sdk.dart` — `AdMobBannerRequestSpec` (carries `widthDp`), `AdMobBannerHandle`,
  `AdMobSdk.loadBanner`, `AdMobBannerFill`.
- `admob_real_sdk.dart` — `loadBanner` via `AdSize.getLargeAnchoredAdaptiveBannerAdSize`
  (9.0.0's non-deprecated resolver for the adaptive-size call).
- `ads_service.dart`/`admob_ads_service.dart`/`house_ads_service.dart` —
  `AdsService.requestFill` gains optional `widthDp` (ignored by non-banner placements).
  `AdMobAdsService` reuses the NATIVE unit id for banner requests (no 4th build-time
  ad-unit-id define) — flagged for Saiful's console setup, see Attack surface 5.
- `ads_providers.dart` — `AdGate.request` gains `widthDp`; `AdFormat.banner` is EXEMPT
  from the `ads.md:59-60` frequency caps and from `recordShown`'s impression counter (a
  persistent, once-mounted slot is not a discrete per-screen impression — running it
  through the 8/day cap would hide it after 8 re-renders, not 8 actual showings). Still
  goes through the SAME plan gate as the other six.
- `widgets/ads/anchored_ad_banner.dart` (new) — `LayoutBuilder`-measured width (not
  `MediaQuery.size`), dispose + re-request on width change, draws the AdMob policy
  separator around its OWN content so it collapses to zero height with the banner.
- `widgets/ads/house_ad_banner_strip.dart` (new) — compact single-row house fallback,
  reusing `HouseAdCard.copyFor`'s existing targeting table.
- `widgets/ads/shell_banner_slot.dart` — now renders `AnchoredAdBanner` (was
  `SizedBox.shrink()`).
- `docs/initial_specs/06_monetization/ads.md` — 7th placement row.

**CR226 — text-scale clamp:**
- `theme/ami_text_scale.dart` (new) — `kChromeMaxTextScaleFactor = 1.3`,
  `clampChromeTextScale` wrapping `MediaQuery.withClampedTextScaling`.
- `ami_screen_header.dart` — clamp applied; title gains `maxLines: 1` + ellipsis (only the
  subtitle had this before).
- `hex_bottom_nav.dart` — clamp applied, AND a genuine layout bug found and fixed: the
  label's `FittedBox(scaleDown)` was sizing to its own natural height as the last child of
  a `mainAxisSize: min` Column (not being squeezed by a bounded constraint), so at 3.1×
  scale even the 1.3×-clamped label still overflowed the 15dp left in the 64dp cell after
  the fixed 33dp icon zone. Fixed with an explicit `SizedBox(height: 15)` around the label
  so `FittedBox` has a real box to scale into. This was NOT theoretical — the widget test
  caught it on a real `pump()` before the fix; see Tests below.
- `ticker_tape.dart` — clamp applied around `TickerTape.build`'s return (not the
  `bottomInset` read above it, which correctly stays on the ambient unclamped
  `MediaQuery`).
- `app.dart` — `builder:` added on `MaterialApp` (the entry point the CR doc names);
  deliberately a pass-through, not a global clamp — clamping app-wide would defeat OS
  accessibility scaling for lesson/agent body content.

**Why one commit, one architect brief for both CRs:** `ads_providers.dart` and
`admob_config.dart` are each touched by both CRs in the same regions (the facade provider,
the mode-resolution function), and CR226 cannot exist without CR225's re-link underneath
it — a caller reading a CR226-only diff would see `AdMobAdsService`/`RealAdMobSdk`
referenced without their re-link landing first. Splitting the commit would have meant
either committing CR226 on top of dead code (CR225 unmerged) or replaying the same hunks
twice. Governance rows/docs are still per-CR and both are tagged in the commit trailer.

## Attack surface (please probe)

1. **The consent/privacy perimeter is now reachable for the first time.** CR122 built
   `RealAdMobUmpConsent.gatherConsent` months ago, but with the SDK unlinked nothing ever
   called it against a real UMP endpoint. Re-linking means the ATT prompt, the GDPR form,
   and the CCPA `rdp` extra can now actually fire in a shipped build. Check that
   `AdMobConfig.isConfigured` (which gates whether the Settings re-consent row even
   appears) still tracks `AdMobConfig.setup` exactly, and that nothing in this diff
   changed WHEN `gatherConsent` runs relative to the first ad request.
2. **The 9.0.0 age-treatment remap** (`admob_real_sdk.dart::_tagFor`) is the one place
   this CR changed BEHAVIOR, not just restored it — verify the mapping is actually
   equivalent under 9.0.0's older API (`tagForChildDirectedTreatment`/
   `tagForUnderAgeOfConsent`, both set to the SAME derived tag) and that
   `AdAgeTreatment.none` really does reach `TagForChildDirectedTreatment.unspecified`,
   not a false "yes" that would misdeclare the app as child-directed to the ad network.
3. **The internal/production channel gate is the load-bearing new control** (Saiful's
   2026-09-24 ruling). Verify: (a) `AdMobConfig.resolve`'s `channel` parameter actually
   reaches every `mode=live` code path, not just the happy one; (b) the two build
   scripts' `AMI_RELEASE_CHANNEL` derivation can't be bypassed by a flag combination
   neither script's existing gates already forbid; (c) `install_iphone.sh` truly never
   forwards the define (a grep, not a read of the comment); (d) whether a THIRD build
   path exists anywhere (CI, a doc'd manual `flutter build` invocation) that sets
   `ADMOB_MODE=live` without setting `AMI_RELEASE_CHANNEL` at all — that already resolves
   to `unknown` → downgrade, which is correct, but confirm no path sets `channel=production`
   without going through `--production`.
4. **Banner reuses the native ad unit id**, a deliberate scope-narrowing decision (see
   Changes) rather than adding a 4th build-time id define. If Saiful's AdMob console setup
   assumes separate banner inventory, this under-serves rather than over-serves — probe
   whether that's the right default or should have been flagged louder than a code comment.
5. **Frequency-cap exemption for `AdFormat.banner`** is a new carve-out in `AdGate.request`
   — verify it cannot be used to exempt a FUTURE non-banner placement from caps by mistake
   (the check is `placement.format != AdFormat.banner`, not an allowlist of placements),
   and that `recordShown`'s early-return for banner doesn't accidentally suppress a cap
   record for a placement that should have one.
6. **The `hex_bottom_nav.dart` layout fix** was discovered mid-task by the new test, not
   pre-planned — worth an independent check that `SizedBox(height: 15)` doesn't itself
   clip a legitimately-sized label at 1.0× scale on a real device (the test asserts no
   `RenderFlex` overflow and the box stays 64dp tall, but does not screenshot render).
7. **AdMob policy separator correctness** — Saiful's ruling is about avoiding accidental
   taps near the nav; confirm the border-only (no full gap/padding row) treatment actually
   reads as a visible separator against `glassChrome`/`slate900` in the real dark theme,
   not just structurally present in the widget tree (the test asserts a `DecoratedBox`
   with the right border color exists, not that it is visually legible).
