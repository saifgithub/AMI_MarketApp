## 0. What to attack hardest

1. **Is the reference-assembly definition of "version" right?** The version is a
   hash of the fully assembled prompt for a **fixed reference mandate**. That is a
   judgement, not a fact: it means two users on different mandates share a version
   (intended — they are running the same prompt generation) and it means a change
   to a *branch* only some mandates take will change the version only if the
   reference mandate takes that branch. The reference is
   `{plan: trader, risk_score: 3, single_name_cap_pct: 3.0}` on `MSFT` with a
   `{base_price: 100.0}` profile. **A template branch that only fires for, say, a
   halal mandate or `risk_score <= 2` is invisible to this hash.** I judged that
   acceptable because the version's job is to separate *code generations*, and a
   generation that changed a halal-only branch also changed the file. But if you
   can construct a prompt change that ships with an unchanged version, that is a
   MAJOR — it is the one failure mode that makes the column actively misleading.

2. **The gateway call site.** `prompt_version_for(audit_agent_id)` runs on every
   call. Cached after first use per agent, and the whole thing is wrapped so a
   failure yields `None` rather than raising — but I would check that the cache
   cannot serve a stale value across a hot reload, and that a `None` return never
   becomes the string `"None"` anywhere downstream.

3. **A deviation from my own filed scope, taken deliberately** (§3). The CR as
   filed said the version goes in each agent file's frontmatter. It does not, and
   I think the filing was self-contradictory.

## 1. Why this exists

Nothing recorded which prompt produced a stored turn. `llm_audit` keeps
`system_prompt` verbatim across 19 columns and says nothing about its generation;
`room_runs` has no prompt field at all.

So every epoch boundary in the CR143 audit was reconstructed **by hand from git
SHAs** — `7fc09420`, `258625a7`, `06098b4f`, `3f4d33d2` — a manual step with no
check on it. It produced a wrong published figure: an **18.4%** PM-reformatter
rate measured across a 30-day pool that straddled a prompt change, where the epoch
it was actually about is **0/18**. The same pooling made stance emission read 4.5%
because 1,682 of the pooled turns predated the envelope shipping at all. It also
cost four separate subagents time each, independently rediscovering that
`real_samples/*.prompt.txt` are pre-DEF228 captures.

And it matters this week: **DEF240, DEF241 and DEF243 all owe a post-promotion
re-measure**, and without this the only way to separate pre- from post-promotion
turns is timestamp-versus-deploy-time, done by hand — the exact step that already
produced one wrong number here.

## 2. What the version covers, and why not the base file

The base `.md` is **10–18% of what the model receives** (2,332 of 12,759 chars for
the PM before its transcript). A hash of the file alone would have been unchanged
by DEF236's format work and by DEF241's mandate-snapshot change — it would report
"same prompt" about a materially different one.

So `_assemble_reference_prompt` builds the real Room prompt via
`build_room_messages` and prepends `GROUNDING_DIRECTIVE`, covering: grounding
directive, base file, mandate overlay, role block, format constants, mandate
snapshot, Room block, safety floor, and the user turn.

Excluded on purpose: the user's actual mandate, the user overlay, holdings, the
transcript, the ticker profile. Those are a prompt's *input*, not its generation.

**Nothing touches the database.** `user_id=None` means no user overlay and no
journal block; a test fails if a session is ever opened.

## 3. The deviation, stated plainly

The CR as filed said (scope item 1) that the version belongs in each agent file's
**frontmatter**, "content-derived, not hand-maintained". Those two halves
contradict each other. A derived value cannot live in a hand-edited content file
unless something writes it there, and a generation step that rewrites
`content/agents/*.md` is a **new drift surface** — someone edits a prompt, forgets
to regenerate, and the frontmatter now asserts a version that is false. Worse than
none, by this CR's own argument against hand-written versions.

So the version is computed from the assembly and never stored in content. The
frontmatter keeps its four identity keys. The deviation is recorded in the CR doc
as a blockquote rather than silently absorbed.
