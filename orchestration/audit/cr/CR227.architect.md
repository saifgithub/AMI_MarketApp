## What and why

Saiful: *"we need to create a CR to enable trading with the alpaca account."* Clarified through
discussion into something narrower than a full brokerage-integration reversal: this is Alpaca's
own **paper** simulator, still simulated money — and the actual ask, in his own words, was
*"When placing an order, let the user select if it was for Ami sim, alpaca paper, or both."*

The trade ticket (`trade_ticket_sheet.dart`) gains a three-way destination selector — AMI Sim /
Alpaca Paper / Both — defaulting to AMI Sim (today's unchanged behavior) and visible only when
`alpacaLinkedProvider` reports a linked account, and hidden/forced to AMI-Sim-only on the
cover-a-short and sell-from-holding entry paths (their quantities are keyed to AMI's own
holdings, which don't translate to Alpaca's independent position sizes — CR227's stated
Non-goal).

## Decision-log amendment — landed first, its own commit, before any code (b2da0fd5)

D-004/D-069 read as an absolute: *"no brokerage integration ever,"* *"we never route an order,
never connect to an execution venue"* — no live/paper qualifier existed. **D-071**
(`docs/initial_specs/11_decisions/decision_log.md`) narrows this: AMI may route an order to a
linked brokerage account **only** when it is confirmed paper/simulated, checked by endpoint
(`baseUrl` resolving to a recognized Alpaca paper host), never by trusting a stored label. A
live/production account remains strictly forbidden from ever receiving an order — that half of
D-004's prohibition is explicitly restated as unchanged. `CLAUDE.md`'s decision-pointer table
("Endpoint of the journey" row) is updated to match. D-004's own cross-reference list now points
to D-071 alongside the existing D-069 pointer.

**Why I sequenced it this way:** the CR227 design doc calls out that the decision-log amendment
and the DEF145 guard-test rewrite should land as their own reviewable step before the order-call
code, "given how directly this crosses a previously locked decision" — so a reviewer (you) can
evaluate the policy change on its own commit before evaluating whether the implementation honors
it.

## DEF145's guard test — rewritten, not deleted (a04842cc)

`backend/tests/unit/test_def145_alpaca_stays_read_only.py` pins the backend's Alpaca posture by
two mechanisms: an exact AST-parsed allow-list of `httpx` calls `alpaca_service.py` may make
(`_ALLOWED_CALLS = {("exchange_code", "post")}` — the OAuth exchange only), and a corpus-wide grep
across `backend/app/` for `/v2/orders` or `/v2/positions/`. **Neither assertion changed** — CR227
adds **zero backend code path** to any Alpaca order endpoint, live or paper, because the design
is mobile-direct (see "Mobile places the order directly" below). What changed is the docstring
and assertion messages, which quoted the old absolute rule as their rationale; they now describe
the narrowed D-071 boundary and explain why the pin still holds unchanged under it. Rewriting
this file (rather than leaving it to quietly still pass under stale rationale, or deleting it) is
itself evidence the boundary was consciously re-examined, not eroded by omission.

## The load-bearing guarantee: the mandate floor cannot be bypassed by destination choice

This is the one finding I most want attacked, because if it is wrong the whole CR is wrong: **a
mandate violation must be refused on the Alpaca-only leg exactly as it is refused on the sim
leg**, or "uncoachable" (`check_mandate_compliance`) becomes trivially defeatable by picking
"Alpaca only" as the destination.

**Design:** "Alpaca only" and "Both" both call the EXISTING `POST /v1/sim/preview` endpoint
(`backend/app/api/sim.py:642-694`, unmodified by this CR — it already runs the identical
`check_mandate_compliance` pre-flight `/submit` runs, without persisting a `SimTradeRow`) before
any Alpaca order call. `mobile/lib/screens/sim/trade_ticket_sheet.dart`'s `_submitAlpacaOnly()`
(the "Alpaca only" path) and `_submit()`'s `TradeDestination.both` branch (the "Both" path) both
gate this way: `preview.accepted == false` (or a null preview, i.e. a network failure) leaves
`AlpacaClient.submitOrder()` entirely uncalled.

**Proven by mutation, not just by a green suite.** In the clean verification worktree (see
below), I changed `trade_ticket_sheet.dart:656` from `if (preview == null || !preview.accepted)`
to `if (false)` — i.e. simulated the gate being silently bypassed — and re-ran
`cr227_destination_routing_test.dart`. The test named exactly for this guarantee (*"a
mandate-blocking preview leaves the Alpaca order call unmade"*) failed immediately:

```
Expected: empty
  Actual: ['buy 1.0 AAPL']
a refused preview must leave the Alpaca order call entirely unmade — "uncoachable" is not
bypassed by picking a different destination
```

Reverted; suite green again; `git status --short` empty (worktree matches the committed SHA
byte-for-byte again). I would treat a passing suite alone as insufficient evidence for a claim
this load-bearing — the mutation is what proves the test would actually catch the regression it
exists to catch, not merely that it currently passes.

## Paper-vs-live enforcement: also proven by mutation

`mobile/lib/services/alpaca/alpaca_client.dart`'s new `isAlpacaPaperHost()` checks
`host.endsWith('.alpaca.markets') && host.contains('paper')` — a pattern check, not an equality
against the single default host, so a CR224 per-account paper override still passes while
`api.alpaca.markets` (live, no `paper` segment) fails. `AlpacaClient.submitOrder()` calls this
itself, independent of whatever the trade-ticket UI already checked — a second, structural
enforcement of the paper-only rule.

Mutation: dropped `&& host.contains('paper')`, leaving only the `.alpaca.markets` suffix check.
`alpaca_client_paper_only_test.dart` went from 9 passing to 7 passing / 2 failing — exactly the
two tests asserting a live host and a lookalike host are refused
(`the live/production host is refused`, `refuses against a stored live host, independent of any
UI check`). Reverted; back to 9/9.

## Mobile places the order directly — confirmed no backend path exists

Per the CR202 custody decision (Alpaca credentials are device-local only, never sent to or stored
by the AMI backend): `AlpacaClient.submitOrder()` is the sole new POST, calling
`$baseUrl/v2/orders` directly from the device using the same `AlpacaCredentialStore`-sourced
client CR224 already built. `git diff b2da0fd5^..30a3a6e3 -- backend/` touches exactly one
backend file, the DEF145 test rewrite above — **zero backend production code changed.** The
DEF145 corpus-grep test (unmodified) independently confirms no backend file references
`/v2/orders` or `/v2/positions/`.

## New mobile surface — `simPreview()` / `SimPreviewResult`

No new backend endpoint was needed — `POST /v1/sim/preview` already existed
(`backend/app/api/sim.py:642-694`) and already ran the exact compliance pre-flight this CR needed;
mobile previously had no client for it. Added: `ApiClient.simPreview()`
(`mobile/lib/services/api/api_client.dart`), `SimNotifier.preview()`
(`mobile/lib/state/sim_providers.dart`, stateless — touches neither `submitting` nor
`lastSubmit`, since it persists nothing and must not be confused with a real submit in the UI),
and `SimPreviewResult` (`mobile/lib/models/sim.dart`), parsed from the existing
`PreviewTradeResponse`/`ComplianceBlock` wire shape (`accepted`, `violations`, `blocked_by`,
`sharia_verdict` — the fields the gate decision needs; `fill_price`/`notional`/`cash_available`/
`held_quantity`/`price_source` exist on the wire but have no reader yet and are deliberately
left off rather than guessed at).

## Result surfacing

"Both" can legitimately fill on one leg and fail on the other (e.g. Alpaca rejects for
insufficient paper buying power while AMI's sim, with its own independent cash balance, accepts).
`_DestinationOutcome` (label/ok/message per destination) is rendered as a list in the ticket
rather than folded into the single existing snackbar, so a partial result is visible as partial.

## Non-goals, restated from the CR doc (unchanged, not attempted here)

No resting/limit/stop orders on the Alpaca leg (market/day only — AMI's own
LIMIT/STOP/STOP_LIMIT resting-order lifecycle has no Alpaca equivalent, and the destination
selector is hidden entirely whenever the ticket is in a non-market-order state via
`_destinationLocked`'s cover/sell gating — actually, to be precise: the selector's own gating is
on cover/sell only; a non-market AMI order type simply never reaches `_submitAlpacaOnly`/`both`
with an Alpaca call since `submitOrder()` itself is hard-coded `type: market`). No options. No
live/production Alpaca support, ever. No backend order-placement path (confirmed above).

## Backward compatibility with installed builds (the DEF294 question)

No backend response shape changed (CR227 adds zero backend production code), so an old client
parsing `/v1/sim/preview` or `/v1/sim/submit` responses is unaffected — those endpoints and their
payloads are byte-identical to before this CR. An old client simply never shows the new
destination selector (it doesn't know it exists), which is the ordinary "old client doesn't have
the new control yet" state, not a compatibility break.

## Known limits, stated rather than left to be found

- **No live device pass.** `NEEDS-DEVICE-CHECK` for the destination selector's actual on-screen
  layout/tap targets and for a real round-trip against Alpaca's live paper API (all testing here
  is against fakes — `_RecordingAlpacaClient`/`_FixedSim` — per this repo's established
  "subclass and override" test convention; no test in this repo mocks Dio's transport layer, and
  I followed that convention rather than introducing a new one).
- **`SimPreviewResult` only models the fields the gate decision needs** (`accepted`, `violations`,
  `blocked_by`, `sharia_verdict`). `fill_price`/`notional`/`cash_available`/`held_quantity`/
  `price_source` exist on `PreviewTradeResponse` but have no mobile reader — deliberately, since
  nothing in this CR's UI shows a pre-trade sizing preview, only a compliance gate. A future CR
  that wants to show "this would cost ~$X" would extend this model rather than needing a new one.
- **The paper-host pattern check (`host.contains('paper')`) is a heuristic on Alpaca's own naming
  convention**, not a call to an Alpaca API that definitively answers "is this a paper account."
  If Alpaca ever issues a paper host that doesn't contain the string "paper," or a live host that
  does, the check would be wrong in the unsafe direction (former) or overly restrictive (latter).
  I judged this acceptable because Alpaca's documented convention is exactly
  `paper-api.alpaca.markets` vs `api.alpaca.markets`, and CR224's per-account overrides were
  confirmed (prior CR) to still follow this pattern. **Worth attacking:** whether this heuristic
  is strong enough for a safety-relevant boundary, or whether Alpaca exposes an authoritative
  "account_type"/"is_paper" field on `GET /v2/account` this CR should have read instead of
  inferring from the hostname.
