## What and why

Drill 3 (CR004's A3, live Alpha `alpha-2026-09-25-4`): `docker restart ami_api_alpha` mid-Room-convene → row ended `status=cancelled`, `verdict=null`, `error_message="client disconnected mid-run"`, 12 credits charged, **no refund**. `_sweep_stuck_runs` / `MAX_AUTO_RETRIES` never fired because the row was never left `RUNNING`.

**Root cause, confirmed by reading the surrounding code (not assumed from the drill alone):**

1. `start_run()`'s own docstring is explicit: *"The run executes in a background asyncio.Task independent of the SSE connection — a client disconnect does not cancel the run."* Grepped the whole backend for `.cancel()` on this task or a caller of `RoomRunner.run()` other than `_pump()`/`_pump_backtest()`/`_respawn_run_from_row`'s own internal pump — **none exists**. So the `except (asyncio.CancelledError, GeneratorExit)` handler's own comment ("Client disconnect: the SSE consumer's `async for ev in run_iter` tears the iterator down via `aclose()`") describes a mechanism that, for THIS call path (the detached background task), cannot happen — nothing ever iterates that generator from an SSE consumer; only `_pump()` does, and `_pump()` is immune to client disconnects by design.
2. The ONE real, live source of `CancelledError`/`GeneratorExit` reaching this handler is the server's OWN shutdown: `docker restart` sends SIGTERM, uvicorn runs the ASGI lifespan shutdown, and when the event loop itself tears down, every still-pending task (the Room's `_pump` background task included) gets cancelled. The handler could not tell that apart from a (nonexistent today) genuine per-run cancellation, so it unconditionally marked the row `CANCELLED` with `error_message="client disconnected mid-run"` — a label that is provably false for the only path that reaches it, and (because `CANCELLED` is a terminal status, not `RUNNING`) permanently invisible to `_sweep_stuck_runs`, whose own docstring premise is "a run left in `status=running` means the server was restarted... while the run was in progress."

**The fix:**

- `RoomRunner.mark_shutting_down()` (new method) sets `self._shutting_down` (new instance flag, `__init__`-initialised `False`).
- `main.py`'s `lifespan()` shutdown phase (the `finally:` after `yield`) calls `get_room_runner().mark_shutting_down()` **before** cancelling its own tracked tick tasks — because that cancellation, and the loop teardown that follows this `finally` block on process exit, is exactly what cascades `CancelledError` into the Room's detached `_pump` tasks. Best-effort (wrapped in `try`/`except Exception: logger.exception(...)`) so a failure here can never block the rest of shutdown.
- `run()`'s `except (asyncio.CancelledError, GeneratorExit)` handler now branches: `self._shutting_down` → log `room_cancelled_shutdown` and re-raise WITHOUT touching the row (no status flip, no `error_message`, no `_persist_run` call) — leaving it exactly as `_sweep_stuck_runs` expects to find a genuinely-interrupted run, so the pre-existing retry-or-fail-with-refund contract fires on next boot. Anything else (today, nothing — kept as an inert defensive fallback in case a future caller ever does cancel this task directly) keeps the pre-fix CANCELLED/no-refund/`"client disconnected mid-run"` behaviour.
- **Second gap closed in the same pass:** `_sweep_stuck_runs`'s own retry-exhausted branch (`retry_count >= MAX_AUTO_RETRIES`) marked the row `failed` with **no refund** — the identical user-facing wrong, one hop later, for a run that dies twice. Now collects `(run_id, user_id, credit_cost)` for every such row inside the sweep's DB session, then — AFTER that session closes/commits — calls `refund()` for each (mirroring `_respawn_run_from_row`'s existing abandoned-snapshot refund shape: commit the row first, refund after, never nested inside the same open session). Best-effort, logged on failure, never blocks the sweep itself.

**Client-disconnect refund decision (per this CR's own instruction to read CR039 + decide, not silently pick one):** there is no genuine "client disconnected mid-run" case left to decide a policy for. CR039's `start_run()` explicitly decouples the SSE connection from the run's lifetime — the whole point of the detached background task is that a phone going to sleep or an LTE handoff must NOT interrupt a Room the user already paid for. So the non-shutdown branch of the handler is inert today; it is kept, unchanged, only so the `except` clause still means something if some future code path ever DOES call `.cancel()` on this task directly (e.g., a hypothetical "cancel my Room run" user action, which does not exist today). If that ever ships, its refund policy is a fresh, first-run design decision, not this one, since it would be a genuinely different question (the user actively chose to stop a run they were billed for) from either of the two cases this defect is about.

### MAJOR-1 — after an ordinary restart the credits stay taken

**Root cause, as diagnosed by the auditor:** `_sweep_stuck_runs` (`room_runner.py:4501-4599` this
round) claims `status == "running" AND started_at < now - room_dedup_running_minutes` (30 min,
`config.py:491`). It runs once, synchronously, in `RoomRunner.__init__`. A container restart comes
back in seconds — `started_at` is nowhere near 30 minutes old — so the row DEF425 round 1 leaves
RUNNING is invisible to the one sweep that will ever look at it, until some LATER boot happens to
land ≥30 minutes after the original `started_at`. On melehost that's the next promotion, which
could be hours or days away, or never. `_find_active_run` (`:4786-4813` this round) uses the same
30-minute window to decide a row is "active", so a re-convene of the same ticker attaches to the
dead run for that whole window and streams replayed events with no verdict.

**Fix chosen: mark the row, don't infer from age.**

1. New column `room_runs.interrupted_at` (nullable `DateTime(timezone=True)`), migration
   `def425a0interrupt1_room_runs_interrupted_at.py`, chained onto the actual single head
   `m111a0def416x417` (confirmed via `alembic heads` before writing the migration — DEF416 and
   DEF417 were already merged). `backend/app/db/models.py:707-750` (`RoomRunRow`) gets the mapped
   column, same nullable/no-default treatment `retry_count` uses for "row-only bookkeeping the
   domain object doesn't need to carry."
2. `room_runner.py`'s shutdown branch (`run()`'s `except (asyncio.CancelledError, GeneratorExit)`,
   the `if self._shutting_down:` arm) now does a small, targeted DB write — `row.interrupted_at =
   datetime.now(timezone.utc)` — directly on the row, the same way `_sweep_stuck_runs` already
   writes `row.retry_count` directly rather than routing through `_persist_run`/`RoomRun` (that
   Pydantic model has no `interrupted_at` field, deliberately not added — this is sweep-only
   bookkeeping, not a domain concept). Wrapped in its own `try/except Exception: logger.exception`
   so a DB hiccup here can never block the `raise` that must still propagate the
   CancelledError/GeneratorExit for the shutdown sequence to complete.
3. `_sweep_stuck_runs`'s query (`room_runner.py:4546-4553`) now selects
   `status == "running" AND (interrupted_at IS NOT NULL OR started_at < cutoff)` — an `or_()` union,
   not a replacement. A marked row is claimed at ANY age; an unmarked row still needs the 30-minute
   age rule, because a bare SIGKILL or an OOM-killer crash never reaches the shutdown branch at all
   and leaves no mark — age is the only signal that kind of stuck row can offer.
4. The sweep's retry branch (`room_runner.py:4557-4569`) now clears `row.interrupted_at = None` when
   it claims a marked row for retry. Without this, the retry keeps `status="running"` (by design —
   the row is "claimed for re-execution"), and the very next boot's sweep would immediately re-claim
   it AGAIN via the `interrupted_at IS NOT NULL` arm, double-retrying a run that is now legitimately
   back in flight. The retry-exhausted (`failed`) branch needs no such clearing — `failed` rows are
   never selected by `status == "running"` again regardless of the mark.
5. `_find_active_run` (`room_runner.py:4786-4813`) adds `.where(RoomRunRow.interrupted_at.is_(None))`
   — a marked row is never "active": no process is executing it, and it stays that way until the
   next boot's sweep claims it. This closes the second half of MAJOR-1 (the 30-minute lockout on
   re-convening the same ticker).

**Rejected alternative — `started_at < process_start`:** the auditor's round-1 note offered this as
an option; the CR brief instructed rejecting it and explaining why. `process_start` is correct ONLY
because today there is exactly one uvicorn worker, so "not executing at __init__ time" and "started
before this process existed" are the same fact. That stops being true the moment CR126 (Cloud Run,
multi-instance) ships: a fresh instance booting alongside a sibling that is still correctly mid-Room
would see that sibling's row as `started_at < process_start` (my own start time is always later than
its still-running peer's) and steal/retry a run nothing has abandoned. Marking the SPECIFIC row that
THIS process's OWN shutdown interrupted is instance-agnostic — it says nothing about any other
process's clock, so it stays correct whether there is one worker or ten.

### MINOR-1 — `_pump`'s `finally` journals a run that has not finished

**Root cause:** `run()` re-raises `CancelledError`/`GeneratorExit` on the shutdown path (both are
`BaseException` subclasses in this Python version, not `Exception`), so `_pump`'s `except Exception`
(`room_runner.py`, the `start_run()`-registered `_pump`, `try/except Exception/finally` block) never
catches it — the exception propagates straight through `async for ev in self.run(...)` to the
`finally`, which ran `on_complete` (`api/room.py:_finalise_to_journal` in production)
unconditionally. `_finalise_to_journal` reads `runner.get_run(run_id)` — the row DEF425 leaves
RUNNING — and journals it with the phrasing the auditor quoted from the runtime's own journal-entry
builder ("Room on TICKER — running ... without reaching a verdict"). ROOM_RUN journal entries carry
no dedupe key, so a subsequent successful retry's own real verdict entry lands ALONGSIDE this false
one; if retries are exhausted, this false "running" entry is left as the ONLY record of a run that
is actually `failed` and refunded.

**Fix:** `room_runner.py`, the `_pump` closure inside `start_run()` — the `finally` block's
`if on_complete is not None:` guard is now `if on_complete is not None and not self._shutting_down:`.
On the shutdown path this skips calling `on_complete` entirely; the eventual retry (which does its
own inline journal write in `_respawn_run_from_row`'s own `_pump`, unaffected by this flag since it
never registers the generic `on_complete` callback at all) or the sweep's retry-exhausted `failed`
branch is what writes the real, terminal-state journal entry. Scoped to exactly the call site the
auditor named (`start_run()`'s `_pump`) — the pre-existing, structurally identical `_pump_backtest`
closient (`room_runner.py:5049-5109` this round) has the same shape but is out of this defect's
scope (DEF425's own drill and the auditor's round-1 report are both about the live Room-convene path,
never backtests) and was left untouched.

### MAJOR-1 — while any response is still streaming, shutdown never reaches the mark

**Root cause, confirmed by reading uvicorn's own shutdown sequence and the code it constrains, not
just the auditor's drill:** uvicorn 0.47's server loop waits for in-flight connections to close
("Waiting for connections to close") BEFORE it ever runs the ASGI lifespan shutdown phase. `main.py`'s
`lifespan()` `finally:` — the block that calls `get_room_runner().mark_shutting_down()` before
cancelling its own tracked tasks (`main.py:504-526`) — is inside that lifespan shutdown phase, so it
cannot run until every open connection closes. Neither `backend/Dockerfile`'s `CMD` nor
`docker-compose.yml`'s `api-alpha` service set a bound on that wait: no `--timeout-graceful-shutdown`
on uvicorn, no explicit `stop_grace_period` on the service (Docker's own implicit default, 10s, was
the only limit). So with any Room/Brief/1-on-1 SSE stream open at SIGTERM, uvicorn waits past that
10s and Docker SIGKILLs it — the lifespan `finally:` never executes, `mark_shutting_down()` never
runs, and round 1+2's entire fix (leave the row RUNNING, stamp `interrupted_at`) never engages,
because the code path that does it is unreachable. This applies to EVERY running Room on the process
at that moment, not only the one being watched, since the flag and the mark are both process/row-wide.

**Fix chosen: bound uvicorn's wait, state the container's tolerance for it explicitly, pin the
relationship with a test.**

1. `backend/Dockerfile`'s `CMD` (line 112) now passes `--timeout-graceful-shutdown 5` to uvicorn.
   This is the ONLY uvicorn entrypoint found for the live api-alpha container — grepped the whole
   backend + root-level scripts for `uvicorn`. One other exists,
   `backend/scripts/supervisors/glm_sidecar.sh`, which runs a SECOND uvicorn on `:8001` inside the
   SAME container via `docker exec -d ... sh -c "exec uvicorn ..."` for the CR217 GLM benchmark arm;
   it is explicitly out of scope here — it is started/stopped manually by that script's own `kill
   $pid`, never receives the container's SIGTERM directly (its own `stop` case refuses to ever signal
   PID 1, the live `:8000` API), and is a benchmark tool, not the request-serving process DEF425 is
   about. Left untouched.
2. `docker-compose.yml`'s `api-alpha` service now sets `stop_grace_period: 15s` explicitly (it had no
   `stop_grace_period` key at all before this round, so Docker's undocumented-at-a-glance 10s default
   was the only number governing this, two files away from the Dockerfile flag it needs to exceed).
   15s leaves uvicorn's 5s bounded wait a 3x margin before Docker's SIGKILL, room for the ASGI
   lifespan shutdown itself (cancelling the lifespan's own tracked tasks, `main.py:520-526`) to run
   inside the remaining 10s after uvicorn's wait ends.
3. New test `backend/tests/unit/test_config_compose_parity.py::test_uvicorn_graceful_shutdown_timeout_is_below_stop_grace_period`,
   in the same file and style as the existing `test_inline_compose_defaults_match_settings` family
   (DEF260's third-direction parity checks) — parses the Dockerfile `CMD` line for
   `--timeout-graceful-shutdown` and the compose `api-alpha` block for `stop_grace_period` (falling
   back to Docker's own 10s default when compose sets none, which is a real, meaningful value here,
   not a parsing gap), and asserts the flag is present AND strictly below the grace period. A second
   test, `test_api_alpha_states_its_stop_grace_period_explicitly`, pins that the compose value itself
   must be a literal in the file, not an implicit default — the exact gap that let this MAJOR through
   two rounds.

**Why 5s / 15s and not tighter:** the auditor's own round-2 drill measured `--timeout-graceful-shutdown
5` closing the gap on a real `docker stop -t 10`. 5s is comfortably enough for uvicorn to finish
"waiting for connections to close" against typical Room/Brief/1-on-1 SSE payloads without becoming a
new source of slow-shutdown pain; 15s total keeps promotions (`/promote-to-alpha`'s own
`docker compose ... up -d --build`) from stalling meaningfully longer than today's implicit 10s.

### MINOR-1 — the respawn's own pump still journals a RUNNING row at shutdown

**Root cause:** round 2 applied the `not self._shutting_down` guard to `start_run()`'s `_pump`
(`room_runner.py`, the `on_complete` call inside that `_pump`'s `finally`) — but
`_respawn_run_from_row`'s `_pump` (`room_runner.py:4733-4784` this round, the retry's OWN pump,
structurally similar but a SEPARATE closure with no `on_complete` parameter at all) writes its
journal entry directly via `get_journal_store().append(...)` inside its own `finally`, with no
shutdown guard. A second SIGTERM landing mid-retry (auditor's drill C shape) still hits this
`finally` — `run()` re-raises `CancelledError`/`GeneratorExit` as a `BaseException`, uncaught by the
`except Exception` above it — and the row is still RUNNING, not finished, when it fires. Left
unguarded, this reproduces round 1's original drill-3 finding (a false "running ... without reaching
a verdict" journal entry, becoming the ONLY record if retries are then exhausted) through the retry
path instead of the first attempt.

**Fix:** `room_runner.py:4768`, inside `_respawn_run_from_row`'s `_pump`'s `finally` — added
`if self._shutting_down: return` immediately before the journal-write section (mirroring
`start_run()`'s `_pump` guard exactly, just applied to a direct write instead of an `on_complete`
call). On the shutdown path this skips the write entirely; the NEXT boot's retry (this same replay)
or the sweep's retry-exhausted `failed` branch writes the real, terminal-state entry once the run
actually finishes.

### MAJOR-1 (= DEF432 round 1 MAJOR-1, one shared root) — the respawn drops the real charge

**Root cause, as the auditor named it:** `_respawn_run_from_row` called
`self.run(...)` without `credit_cost` (`room_runner.py`, the respawn's `_pump`
closure). `_PendingRetry` had no field to carry it. So `run()` fell back to
`room_cost_for_plan(plan)` (base price only), and `_persist_run` overwrote
`row.credit_cost` with that lower figure — losing whatever CR090 live-data
surcharge the ORIGINAL `start_run()` had actually charged, before any refund
ever read the row. Every refund path that reads `row.credit_cost` afterwards
— this sweep's own retry-exhausted refund, CR039's failed-run refund, and
DEF432's outage refund — then gave back less than the user was actually
charged. Measured by the auditor: a Trader user charged base 8 + surcharge 4
= 12, respawned once, then refunded on retry-exhaustion, got back only 8.

**Fix:**

1. `_PendingRetry` (`room_runner.py`, ~:4257) gained a required `credit_cost:
   int` field.
2. `_sweep_stuck_runs` (~:4643) fills it from `row.credit_cost` at claim time,
   inside the same DB session that reads the row — the real figure, whatever
   it is (base alone, or base + surcharge).
3. `_respawn_run_from_row`'s `_pump` (~:4884) now passes
   `credit_cost=p.credit_cost` into its `self.run(...)` call. `run()` then
   never falls back to `room_cost_for_plan(plan)` for a respawned row, so
   `_persist_run` never overwrites the real charge, and `surcharge_charged`
   (the `live_data_notice` event) reports the real surcharge instead of 0.

Two pre-existing test call sites that construct `_PendingRetry` directly
(`test_retro_pm_floor_round2.py`, both under `_respawn_run_from_row`'s
MAJOR-1/MINOR-3 coverage) needed `credit_cost=8` added to match their seeded
rows' `credit_cost=8`, now that the field is required — mechanical, no
behaviour change to what those tests assert.

### MINOR-1 — the interrupted-at mark depends on uvicorn being PID 1

**Root cause, as the auditor named it:** the mark is written in `run()`'s
cancellation branch, reached only once something cancels the Room's `_pump`
task. The lifespan (`main.py`) only ever cancelled its OWN tracked tick
tasks; the Room's `_pump` tasks (bare `asyncio.create_task` calls at two
sites) were reached only by asyncio's own teardown cascade, itself reachable
only because uvicorn 0.47's `capture_signals` re-raises the captured SIGTERM
**inside the event loop** after `serve()` returns — a normal process dies
right there, before any teardown, UNLESS the exec-form Dockerfile `CMD` makes
uvicorn PID 1 (so the kernel drops the unhandled re-raised signal and lets
teardown proceed). Two changes that look harmless — compose `command:`
override, `init: true`, a shell-form entrypoint — would silently remove the
mark on every Room while every unit test stayed green, because those tests
call `mark_shutting_down()` and `task.cancel()` by hand.

**Fix, exactly as directed:**

1. `RoomRunner.__init__` gained `self._pump_tasks: set[asyncio.Task]`
   (~:4540) and a `_track_pump(task)` helper (~:4569) that adds the task and
   registers a done-callback (`task.add_done_callback(self._pump_tasks.discard)`)
   so the set only ever holds genuinely in-flight pumps.
2. Both `create_task(_pump())` call sites — `start_run`'s (~:5398) and the
   respawn's (~:4944) — now wrap the call: `self._track_pump(asyncio.create_task(_pump()))`.
3. New `async def cancel_pumps_for_shutdown(self, timeout: float)` (~:4578):
   cancels every tracked, not-yet-done task, then `asyncio.wait(tasks,
   timeout=timeout)`, logging `room_pump_cancel_timeout` if any are still
   pending after the bound (left `running`/unmarked — the pre-existing
   age-based sweep cutoff still claims it on a later boot).
4. `main.py`'s lifespan `finally` (~:531-549) now calls
   `await get_room_runner().cancel_pumps_for_shutdown(timeout=3.0)`
   immediately after `mark_shutting_down()` and before cancelling its own
   `tasks` list — best-effort, wrapped in `try/except Exception:
   logger.exception(...)`, same shape as the `mark_shutting_down()` call
   right above it. 3s bound: uvicorn's `--timeout-graceful-shutdown 5` (round
   3) has already elapsed by the time this runs, and Docker's
   `stop_grace_period: 15s` (round 3) leaves headroom after it.

The shutdown branch now stamps `interrupted_at` from this direct cancellation
— whatever the process's PID or entrypoint shape — rather than depending on
uvicorn happening to be PID 1.
