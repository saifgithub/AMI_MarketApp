## What and why

Drill 3 (CR004's A3, live Alpha `alpha-2026-09-25-4`): `docker restart ami_api_alpha` mid-Room-convene → row ended `status=cancelled`, `verdict=null`, `error_message="client disconnected mid-run"`, 12 credits charged, **no refund**. `_sweep_stuck_runs` / `MAX_AUTO_RETRIES` never fired because the row was never left `RUNNING`.

**Root cause, confirmed by reading the surrounding code (not assumed from the drill alone):**

1. `start_run()`'s own docstring is explicit: *"The run executes in a background asyncio.Task independent of the SSE connection — a client disconnect does not cancel the run."* Grepped the whole backend for `.cancel()` on this task or a caller of `RoomRunner.run()` other than `_pump()`/`_pump_backtest()`/`_respawn_run_from_row`'s own internal pump — **none exists**. So the `except (asyncio.CancelledError, GeneratorExit)` handler's own comment ("Client disconnect: the SSE consumer's `async for ev in run_iter` tears the iterator down via `aclose()`") describes a mechanism that, for THIS call path (the detached background task), cannot happen — nothing ever iterates that generator from an SSE consumer; only `_pump()` does, and `_pump()` is immune to client disconnects by design.
2. The ONE real, live source of `CancelledError`/`GeneratorExit` reaching this handler is the server's OWN shutdown: `docker restart` sends SIGTERM, uvicorn runs the ASGI lifespan shutdown, and when the event loop itself tears down, every still-pending task (the Room's `_pump` background task included) gets cancelled. The handler could not tell that apart from a (nonexistent today) genuine per-run cancellation, so it unconditionally marked the row `CANCELLED` with `error_message="client disconnected mid-run"` — a label that is provably false for the only path that reaches it, and (because `CANCELLED` is a terminal status, not `RUNNING`) permanently invisible to `_sweep_stuck_runs`, whose own docstring premise is "a run left in `status=running` means the server was restarted... while the run was in progress."

**The fix:**

- `RoomRunner.mark_shutting_down()` (new method) sets `self._shutting_down` (new instance flag, `__init__`-initialised `False`).
- `main.py`'s `lifespan()` shutdown phase (the `finally:` after `yield`) calls `get_room_runner().mark_shutting_down()` **before** cancelling its own tracked tick tasks — because that cancellation, and the loop teardown that follows this `finally` block on process exit, is exactly what cascades `CancelledError` into the Room's detached `_pump` tasks. Best-effort (wrapped in `try`/`except Exception: logger.exception(...)`) so a failure here can never block the rest of shutdown.
- `run()`'s `except (asyncio.CancelledError, GeneratorExit)` handler now branches: `self._shutting_down` → log `room_cancelled_shutdown` and re-raise WITHOUT touching the row (no status flip, no `error_message`, no `_persist_run` call) — leaving it exactly as `_sweep_stuck_runs` expects to find a genuinely-interrupted run, so the pre-existing retry-or-fail-with-refund contract fires on next boot. Anything else (today, nothing — kept as an inert defensive fallback in case a future caller ever does cancel this task directly) keeps the pre-fix CANCELLED/no-refund/`"client disconnected mid-run"` behaviour.
- **Second gap closed in the same pass:** `_sweep_stuck_runs`'s own retry-exhausted branch (`retry_count >= MAX_AUTO_RETRIES`) marked the row `failed` with **no refund** — the identical user-facing wrong, one hop later, for a run that dies twice. Now collects `(run_id, user_id, credit_cost)` for every such row inside the sweep's DB session, then — AFTER that session closes/commits — calls `refund()` for each (mirroring `_respawn_run_from_row`'s existing abandoned-snapshot refund shape: commit the row first, refund after, never nested inside the same open session). Best-effort, logged on failure, never blocks the sweep itself.

**Client-disconnect refund decision (per this CR's own instruction to read CR039 + decide, not silently pick one):** there is no genuine "client disconnected mid-run" case left to decide a policy for. CR039's `start_run()` explicitly decouples the SSE connection from the run's lifetime — the whole point of the detached background task is that a phone going to sleep or an LTE handoff must NOT interrupt a Room the user already paid for. So the non-shutdown branch of the handler is inert today; it is kept, unchanged, only so the `except` clause still means something if some future code path ever DOES call `.cancel()` on this task directly (e.g., a hypothetical "cancel my Room run" user action, which does not exist today). If that ever ships, its refund policy is a fresh, first-run design decision, not this one, since it would be a genuinely different question (the user actively chose to stop a run they were billed for) from either of the two cases this defect is about.

## Attack surface (please probe — re-drill on live Alpha when possible)

1. **Re-run CR004 A3 drill 3 exactly as originally reproduced** (`docker restart ami_api_alpha` mid-convene) once promoted. Expected: the row is left `RUNNING` through the restart, then either (a) respawned with the user's REAL portfolio snapshot within `room_dedup_running_minutes` of the next boot (RETRO-PM-FLOOR round 2's own bar — verify the respawned run's safety-floor inputs are real, not `run()`'s $100k/0%-drawdown defaults), or (b) if the snapshot can't be resolved, failed WITH a refund (`_respawn_run_from_row`'s existing abandoned-snapshot branch, untouched by this fix). Confirm credits net to the pre-charge balance in EITHER outcome, and confirm the mobile client's polling/reconnect UX handles a run that "disappears then reappears" across a restart reasonably (this fix does not add any push/notify hook for that transition — worth asking whether it should).
2. **Timing window:** `mark_shutting_down()` is called at the START of the `finally:` block, before `task.cancel()` on the tick tasks. Confirm this ordering genuinely precedes the cascade that reaches Room `_pump` tasks on the actual uvicorn/asyncio shutdown sequence used in production (SIGTERM → ASGI lifespan shutdown → loop teardown) — this was reasoned from uvicorn's documented behaviour and the existing `_nightly_audit_trim`-style tick cancellation already in this `finally:`, not measured against a live restart in this round.
3. **`_sweep_stuck_runs`'s new refund loop runs OUTSIDE the sweep's DB session, sequentially, per matched row** — for a fleet restart with MANY exhausted rows at once, this is N sequential `refund()` calls (each opening its own session + row lock), which could be slow at scale. Not a correctness concern at Alpha's scale, but worth flagging if this box ever accumulates a large backlog of exhausted rows.
4. **The "inert" non-shutdown branch** — confirm the audit agrees nothing today can reach it, and that keeping it (rather than deleting the whole CANCELLED/no-refund path) is the right call for forward-compatibility vs. dead-code-that-could-silently-diverge risk.
5. **Double-refund risk** — confirm a row can never be refunded twice: the shutdown-branch persists nothing (so `_sweep_stuck_runs` sees a clean `RUNNING` row exactly once), and the retry-exhausted refund only fires from `_sweep_stuck_runs` itself, which only ever transitions a given row `running → failed` once (a `failed` row is never re-selected by the `.where(RoomRunRow.status == "running")` query on a later boot).
