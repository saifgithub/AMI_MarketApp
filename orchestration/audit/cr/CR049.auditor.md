### Beyond the claims list — blocking synchronous I/O in async routes (MAJOR)

Read the scope-D security files (`turnstile.py`, `rate_limit.py`, `email_service.py`) — not
named in the 7 claims — and found a real defect:

- `turnstile.py::verify_turnstile` calls the **synchronous** `httpx.post` (not
  `httpx.AsyncClient`), invoked directly with no `await`/threadpool from three `async def`
  route handlers (`concierge_message`, `submit_contact`, `submit_data_request`).
- `email_service.py::send_email` — identical pattern, sync `httpx.post` to Resend
  (`timeout=15.0`), called directly from `submit_contact` (up to 2 sequential calls on the
  escalation path) and `submit_data_request`.
- `website_api/Dockerfile`'s `CMD` and `docker-compose.yml`'s `api-website` service both run
  plain `uvicorn ... ` with **no `--workers` flag** — single process, single event loop.
- `llm_client.py` gets this right elsewhere in the same codebase (`httpx.AsyncClient` +
  `await`) — this is an inconsistency, not unfamiliarity with the pattern.

**Consequence:** every blocking call runs directly on the event-loop thread of a single-worker
process, stalling the ENTIRE service — all other in-flight requests — for its duration. Worst
case on `/contact`'s escalation path: Turnstile (≤10s) + `send_contact_ack` (≤15s) +
`notify_team` (≤15s) ≈ **up to 40s of total blockage from one request**. Worse: Turnstile exists
to repel bot floods, and a bot flood against a Turnstile-gated endpoint is exactly the traffic
pattern that triggers many concurrent blocking verify calls — the bot-protection mechanism
becomes a self-inflicted DoS amplifier under the exact load it exists to defend against.

This matches a bug class this project's own governance has already flagged as an MVP
show-stopper elsewhere (a backend blocking-I/O concurrency bug) — real institutional weight
behind treating this seriously rather than as a nitpick.

**Recommended fix:** swap the sync `httpx.post` calls in both files for `httpx.AsyncClient`/
`await`, mirroring `llm_client.py`'s already-correct pattern — or, minimally, wrap the existing
sync calls in `asyncio.to_thread`/`run_in_threadpool`.

### Findings
