# DEF420 — audit lane (Standings screen restyle + adaptive layout)

**SCOPE:** def

**TIER: B.** Mobile-only, visual-only change to one screen behind the `AMI_GAMES` const-fold gate. No auth, billing, migration or compliance-perimeter change; no data/behaviour change (every provider read, l10n key set beyond the one addition, and the screen's rules — §6.1 no money, §11.2 desk disclosure, the `?? 0` dash class — are untouched and still covered by their original tests). A MAJOR finding raises it to Tier A.

**SHA:** `9e03b9fb` on branch `worktree-agent-a21c2392492cce4e5`, worktree of `main` at merge-base `92a7c6c0`. Review with `git diff 92a7c6c0..9e03b9fb -- mobile/ docs/defect/`.

**depends-on:** none. **Promoted:** no (mobile; ships in the next TestFlight/Play build after this verdict).

## What and why

Saiful, from a TestFlight +109 screenshot of the Game tab's Standings screen (CR109's field board): *"This screen is not aesthetically pleasing and in line with the rest of the app."*

**Root cause:** `GamesBoardScreen` (`games_board_screen.dart`) predates `AmiScreenHeader` (CR133/CR232) and was never migrated — it still wore a bare Material `AppBar` while every other pushed route in the app shares the same 64pt glass-chrome header. Its empty "not ranked yet" state set the heading in `AmiTypography.statBig` (42pt, the app's *number* type scale) rather than a heading style, which reads oversized and wraps at small widths / large text scale. The leaderboard row was a flat `Material`/`InkWell` with no per-entrant identity mark, and the YOU row's emphasis was a `slate800` tint — the same colour every OTHER row's own background already uses, so it read as barely distinguishable.

**Mid-review addition (Architect correction, relayed from Saiful):** *"really it should be adaptive to the different screen size surely?"* — the initial fix's overflow guard was a single 375dp/1.0–1.3x check, which is a floor, not a design target. Round 2 makes the layout genuinely width-derived rather than fixed, and — because no such convention existed anywhere in the app — adds the first shared width-class helper for other screens to adopt later.

## Changes (round 1 — restyle)

- **Header:** `AmiScreenHeader(title: l.gamesBoardTitle, titleColor: AmiColors.hexGreen, showBack: true)` replaces the bare `AppBar`. Matches the accent Games already uses elsewhere (`games_home_screen.dart`'s own header is `hexGreen`).
- **Empty ("not ranked yet") state:** moved from an ad hoc `_Panel` into `AccentCard` (the app's card component). Heading changed from `statBig` (42pt, wraps at small width/large scale) to `h3` (18pt, `maxLines: 1`) — a status is a heading, not a stat. Added a client-only "Next US close in …" line (`nextUsCloseEstimate()` + `_formatWait()`; 4pm ET arithmetic via UTC offset, weekend-skip, deliberately ignores holidays since the screen's own copy already says standings move "once per US close" — no backend call, per the brief).
- **Ranked state:** `_Panel` → `AccentCard`; headline switched from `statBig` to `statMid` (24pt) with an overflow guard.
- **Leaderboard row:** each entrant gained a 44pt `HexAvatar` (matching the app's existing agent-avatar-in-a-list-row size — `brief_history_screen.dart`, `lesson_beat_deck.dart` — not a new size invented for this screen), coloured amber for a desk (matches its DESK chip), cyan for the player's own row, and by return colour otherwise. Initials derived client-side from the handle (`_initials`), carrying no identity meaning beyond what the row's own text already states.
- **YOU row:** now a real `hexCyan` wash (12% alpha) + border, the same accent-card vocabulary the rest of the screen uses, instead of the old flat `slate800` tint.
- **Loading state:** `HexPulseLoader` (the app's shared loading motif) replaces the bare `CircularProgressIndicator`.
- **New l10n key:** `gamesBoardNextCloseIn` (`"Next US close in {countdown}"`), added to all three ARBs (`retranslate:[ar,ms]`) and regenerated via `flutter pub get`. No other key touched.
- Every existing rule and its test — §6.1 (no money), §11.2 (desk disclosure), the `?? 0` dash class, DEF343 tie-handling — is untouched; the original 9 tests in `games_board_screen_test.dart` pass unmodified against the restyle.

## Changes (round 2 — adaptive layout)

- **New shared helper:** `mobile/lib/theme/ami_window_size.dart` — `AmiWindowWidthClass` (compact <600dp / medium 600–840dp / expanded ≥840dp, Material 3's own window-size-class boundaries), `windowWidthClassOf(double)`, `AmiWindowSizeBuilder` (a `LayoutBuilder` wrapper resolving the class from `constraints.maxWidth`, following the same width-not-MediaQuery reasoning `AnchoredAdBanner`'s own doc comment gives), and `AmiContentWidthConstraint` (centres + caps content at `AmiBreakpoints.maxContentWidth` = 640dp, a no-op below the cap). **Checked first that nothing like this existed:** grepped `mobile/lib` for `maxContentWidth`/`WidthClass`/`isTablet`/breakpoint constants — nothing; the only adjacent precedent (`AnchoredAdBanner`) is a single-purpose `LayoutBuilder` for AdMob's own `AdSize` int and has no general width-class notion. This helper is deliberately screen-agnostic so it is reusable — **flagged here for an app-wide pass**, not wired into any other screen by this defect.
- **Standings screen:** the list body is now `AmiWindowSizeBuilder` → gutter padding of `AmiSpacing.m` (compact) or `AmiSpacing.l` (medium/expanded) → `AmiContentWidthConstraint`-wrapped content column (keyed `games_board_content_column` for the test suite). No new data/columns: the Architect's brief allowed showing extra columns "if present" on wider layouts, but `GameBoardRow` carries no rank-change/delta field, so there is nothing extra to surface without a new backend call, which the brief explicitly rules out — noted here rather than silently skipped.
- **Two real overflow bugs surfaced and fixed** by the breakpoint sweep (both pre-existing latent risk in the restyled layout, not something the original bare-AppBar screen had — the original used `statBig`/`Panel` sizes that happened not to trip this specific Row shape):
  1. `_YourStanding`'s ranked-state twr+label `Row` (`"+2.00%"` + `"% TWR"`) had neither child guarded — 44px overflow at 375dp/1.3x. Fixed: both wrapped in `Flexible`+ellipsis.
  2. The new "next US close" `Row` (round 1's own addition) had the same gap — up to 99px at 320dp/1.3x. Fixed the same way.
  3. **Structural fix, not just a squeeze:** `_BoardRow`'s trailing return percentage moved OFF the top line (it used to sit as a `Row` sibling after name+chips) onto its own line under the name. Rank(24) + avatar(44) + name + a chip + a percentage all sharing one `Row`'s width at 320dp/1.3x had no slack to give no matter how tightly each child was guarded — this is the actual fix, the `Flexible` guards above are the secondary one.

## Attack surface (please probe)

1. **`nextUsCloseEstimate()`'s arithmetic** (`games_board_screen.dart`) — the 20:30 UTC split-the-difference approximation between EST (20:00 UTC) and EDT (21:00 UTC) close times, and the weekend skip. It is explicitly NOT DST-aware (no timezone database dependency) — confirm the doc comment's claim that this is acceptable because it is advisory-only copy ("next US close in ~Xh"), never a scored deadline, and that nothing downstream treats it as authoritative.
2. **The new `AmiContentWidthConstraint`/`AmiWindowSizeBuilder` pair** being correct enough to become the app's reusable convention — this is infrastructure other screens may adopt without another design pass. Check the M3 boundary semantics (compact `< 600`, medium `600–840`, expanded `≥ 840`, all half-open at the right end) match what `windowWidthClassOf`'s unit test actually asserts, and that `AmiContentWidthConstraint` degrades to a true no-op (not just "visually similar") below its cap — the "fills the compact window" test only checks `> 300`, not exact equality to the unconstrained width; a tighter assertion may be worth demanding.
3. **The `_BoardRow` restructure** (return moved to its own line) — a real layout change beyond the minimum needed to fix the overflow. Confirm it doesn't regress readability/scanability of the leaderboard versus the old trailing-column layout, since that's a judgement call the Architect made rather than something Saiful specified.
4. **HexAvatar reuse at size 44** with initials derived from arbitrary desk/human handles (`_initials`) — check for a handle shape that produces something confusing or empty (e.g., all-symbol handles, single-character handles, very long unspaced handles the `Flexible` name ellipsizes around it).
5. **Semantics/Appium impact** — confirmed via grep that `games_board_screen.dart` carried zero `Semantics(identifier: …)` calls before this change (unlike `games_trade_ticket_screen.dart`, which has one and was not touched), so "preserve every existing semantics ID" was trivially satisfied. Worth an independent grep-confirmation rather than taking that at face value.
6. **The i18n boundary** — `gamesBoardNextCloseIn` was added to AR/MS ARBs as an EN placeholder with `retranslate:[ar,ms]`, per CLAUDE.md's "translation is not blocking, flag don't translate" rule; the per-key `@@x-ami-seeds` auto-translation sha map in AR/MS was deliberately left untouched (belongs to the i18n lane's tooling, not hand-edited here) — confirm that's the right boundary and the new key will actually get picked up by that lane's translation pass.
