## MAJOR 2 — Runbook step 3's "additive and safe" framing is materially wrong for the live system

`infra/CR124_HARDENING_RUNBOOK.md:15` states *"Everything before it [step 4] is additive and
safe to run against the live system."* Step 3 runs `ALTER USER postgres WITH PASSWORD
'${POSTGRES_PASSWORD}'` against the **currently-running, pre-CR124** `ami_postgres`/`ami_api_alpha`
containers. Confirmed via `git show 6ea166a6^:docker-compose.yml`: the OLD `api-alpha`'s
`DATABASE_URL` is `postgresql+psycopg2://postgres:postgres@postgres:5432/ami_trade` — the
password is a **hardcoded literal in the running container's env**, not read from `.env` at
runtime. It cannot pick up the new password without a restart (step 4).

Postgres does not kill already-open sessions on `ALTER USER … PASSWORD`, so existing pooled
connections keep working — but any **new** connection the old container opens after step 3
authenticates with a password Postgres no longer has, and fails. Checked the pool config
independently: `backend/app/db/session.py:62` — `create_engine(url, future=True,
connect_args=connect_args)` — no `pool_size`, `pool_recycle`, or `pool_pre_ping` set, so
SQLAlchemy defaults apply: `QueuePool`, `pool_size=5`, `max_overflow=10`, `pool_pre_ping=False`.
Overflow connections (anything past the 5 base) are created fresh under load and **closed** when
returned — so any traffic burst above 5 concurrent DB ops between step 3 and step 4 opens a new
connection with the stale hardcoded password and gets an auth failure, surfaced to whatever
request triggered it. `pool_pre_ping=False` means a connection that goes stale for any other
reason also isn't proactively caught — it fails on next use.

This is exactly the ordering question the audit brief asked to check. The SQL ordering itself is
correct (new password never used before it's set) — the defect is the runbook's blanket safety
claim for the window *before* step 4, on a host that is presently serving real Alpha traffic.
Saiful is the one executing this by hand (CLAUDE.md: "don't ask him to do code"); he will read
"safe" and not expect live errors in that window. Fix: reword step 3's framing to disclose the
overflow-connection risk, or move step 4 immediately after step 3 with no gap, rather than
treating them as independently safe.

## MAJOR 3 — non-root breaks yfinance's on-disk cache, silently, on every call, unflagged

Architect's §5 names exactly one non-root failure mode (`bug_attachments`, a WRITE path). There's
a second, unflagged one: yfinance's own SQLite cache directories.

`backend/Dockerfile:50-51` — `useradd --system --uid 1001 --gid ami --no-create-home ami`.
`--no-create-home` skips creating the directory but does **not** blank the passwd home-dir field
— Debian's `useradd` still records the default `/home/ami` (well-documented `useradd` behavior,
independent of container runtime). No `ENV HOME=` is set anywhere in the Dockerfile or compose,
so `$HOME` is unset for the `uvicorn` process (Docker doesn't synthesize one on `USER` switch —
only a login shell would). CPython's `os.path.expanduser("~")` falls back to
`pwd.getpwuid(os.getuid()).pw_dir` when `$HOME` is unset, landing on `/home/ami` — a directory
that doesn't exist, under `/home`, which is root-owned and not in the Dockerfile's
`chown -R ami:ami /data /app` (Dockerfile:53 — `/home` is untouched).

Traced the actual installed package (`yfinance==1.3.0`, matches `uv.lock`) directly:
`yfinance/cache.py:54` — `_TzDBManager._cache_dir = os.path.join(platformdirs.user_cache_dir(),
"py-yfinance")`, same pattern at `cache.py:249` (`_CookieDBManager`, used on **every** Yahoo
request for the crumb/cookie session — `store()`/`lookup()` called from
`yfinance/data.py:161,168`) and `cache.py:459` (`_ISINDBManager`). `platformdirs.user_cache_dir()`
with `XDG_CACHE_HOME` unset resolves to `~/.cache` → `/home/ami/.cache/py-yfinance`.

Read the failure path directly, not summarized: `_TzDBManager._initialise()`
(`cache.py:76-83`) tries `os.makedirs(cls._cache_dir)`, catches `OSError`, re-raises
`_TzCacheException`. That's caught one level up in `_TzCache.get_db()` (`cache.py:129-131`,
mirrored for Cookie at `cache.py:335-337`): logs via `get_yf_logger().info(...)` and sets
`self.dummy = True`, returning `None` — **not a crash**, confirmed. But `_TzDBManager._db` /
`_CookieDBManager._db` are only ever set on the *success* path — a failure never caches itself,
so `get_database()` re-enters `_initialise()` and re-attempts the failing `os.makedirs()` on
**every single call**, not once at cold start. `get_yf_logger()`
(`yfinance/utils.py:149-163`) is a plain `logging.getLogger('yfinance')` — a different stream
from the app's own `structlog` JSON pipeline (`app/core/logging.py:9-24`,
`logging.basicConfig(format="%(message)s", ...)` + structlog JSON renderer). It does propagate
to the root handler (so it does reach stdout / `docker logs`), but as an unstructured plain-text
line interleaved with the rest of the app's JSON log stream — inconsistent with, not filterable
by, whatever reads the structured stream.

Net effect: every yfinance call (market data is a core, constantly-hit feature) pays a failed
`makedirs` + exception + log call, and permanently loses the cookie/crumb cache that
`pyproject.toml:26-29`'s own comment says exists specifically to handle "Yahoo's rate-limit dance
(UA rotation, cookie/crumb session, exponential backoff)." Silent functional regression,
introduced specifically by N7, not tested, not disclosed. Given CLAUDE.md's explicit "degrade
loudly" priority (CR040) this is a MAJOR, not a nice-to-have — the fix is one line
(`ENV MPLCONFIGDIR`-style override via `yf.set_tz_cache_location()`/`set_cache_location()` at
app startup, or simplest: `mkdir -p /data/.cache && chown ami:ami /data/.cache` +
`ENV HOME=/data` in the Dockerfile, since `/data` is already chown'd).

## MINOR 1 — `REDISCLI_AUTH` wiring has zero regression coverage

Reasoned through and confirmed correct as shipped: Docker HEALTHCHECK CMD runs inside the
container's own process namespace and inherits the container's env, so
`docker-compose.yml:68-70`'s `REDISCLI_AUTH: ${REDIS_PASSWORD}` on the redis service *is*
visible to the `redis-cli ping` healthcheck probe (`docker-compose.yml:76`) — this part of the
design is right. But nothing tests for its presence: mutated the compose file (deleted the
`REDISCLI_AUTH` line + its two comment lines) and reran the CR124 + parity suite —
`20 passed`, unchanged. If this wiring is ever dropped by a future edit, Redis's healthcheck
starts failing `NOAUTH` forever, which blocks `api-alpha`'s `depends_on: condition:
service_healthy` — the whole stack fails to start. Low severity because the failure mode is loud
(nothing boots, impossible to miss) rather than a silent reopening of C3 — but the guard file's
own stated purpose is exactly "pin the hardening so a later edit cannot quietly undo it," and
this specific wiring, unlike every other CR124 property, has no assertion at all. One-line fix:
assert `"REDISCLI_AUTH" in redis_env` alongside the existing `test_redis_requires_a_password`.

## The central call — is "built, not applied" enough for COMPLETE on a security-hardening CR?

Independent of the 3 MAJORs above, this alone would bounce the round. The CR's acceptance
criteria are entirely live probes (psycopg2 connect must fail, `ss -ltn` must show loopback,
`/v1/health` must still 200, `docker inspect`/`whoami` must show non-root) and none can be run —
SSH to melehost is down (DEF224) and there is no Docker daemon on the Mac (confirmed: `docker
info` shows client-only, `Context: desktop-linux`, no server block). The C3 exposure this CR
exists to close — Postgres reachable as `postgres`/`postgres`, Redis unauthenticated, both from
any LAN device — is, by the architect's own words, **still live on melehost right now**.
Marking this COMPLETE would let the CR move to `done` in the register (BINDINGS: "a lane's
COMPLETE is what justifies moving that CR to done"), which would misrepresent the actual state of
production. This isn't "none applies" (PROTOCOL's exemption for when a real measurement doesn't
exist) — a real measurement applies and is simply blocked by an infra outage outside anyone's
control. Judgment: that gap alone would be legitimate grounds for AWAITING_FIXES even with zero
code findings, exactly as §7 of the submission itself anticipated. Once SSH is restored and the
runbook is run, round 2 should carry the 5-probe acceptance evidence from
`infra/CR124_HARDENING_RUNBOOK.md`'s own acceptance section as the real measurement — that's the
bar for COMPLETE here, not a second `yaml.safe_load` pass.
