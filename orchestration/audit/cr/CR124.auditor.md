## MAJOR — runbook step 3's "additive and safe" claim is wrong for the live system (round 1 finding, unaddressed)

`infra/CR124_HARDENING_RUNBOOK.md:15` (unchanged since round 1): *"Everything
before it [step 4] is additive and safe to run against the live system."*
Step 3 runs `ALTER USER postgres WITH PASSWORD` against the **still-running,
pre-CR124** stack. I independently confirmed both halves of why that's
false:

- **The old `api-alpha`'s password is a hardcoded literal, not read live.**
  `git show 6ea166a6^:docker-compose.yml | grep DATABASE_URL` →
  `postgresql+psycopg2://postgres:postgres@postgres:5432/ami_trade` — baked
  into the running container's env, unaffected by `.env` changes until a
  restart (step 4).
- **The connection pool has no ceiling that makes this safe.**
  `backend/app/db/session.py:62` — `create_engine(url, future=True,
  connect_args=connect_args)`, no `pool_size`/`pool_recycle`/`pool_pre_ping`
  — SQLAlchemy defaults apply: `QueuePool`, base `pool_size=5`,
  `max_overflow=10`, `pool_pre_ping=False`. Any traffic burst past 5
  concurrent DB ops in the window between step 3 and step 4 opens a fresh
  overflow connection with the now-stale hardcoded password and fails
  auth — surfaced to whatever real Alpha request triggered it.

The SQL ordering itself is correct (new password never used before it's
set); the defect is the blanket "safe" claim for the pre-step-4 window on a
host serving live traffic, and Saiful runs this by hand (CLAUDE.md: don't
ask him to do code) — he'll read "safe" and not expect live errors there.
Fix: disclose the overflow-connection risk in step 3's text, or collapse
steps 3–4 into one window with no gap.

## MAJOR — non-root breaks yfinance's on-disk cache silently, on every live market-data call (round 1 finding, unaddressed)

`backend/Dockerfile:51` (unchanged since round 1): `useradd --system --uid
1001 --gid ami --no-create-home ami`. `--no-create-home` skips creating the
directory but Debian's `useradd` still records `/home/ami` in passwd; no
`ENV HOME=` is set anywhere (confirmed: `grep -n "ENV HOME" backend/Dockerfile`
→ nothing), and `/home` is never `chown`'d (line 53 only touches
`/data /app`).

**Traced the actual installed package myself, not relayed** —
`yfinance==1.3.0` (matches `uv.lock:2537` exactly):

- `cache.py:54/249/459` — `_TzDBManager`, `_CookieDBManager`,
  `_ISINDBManager` all set `_cache_dir = os.path.join(platformdirs.user_cache_dir(),
  "py-yfinance")`, which resolves to `~/.cache` → `/home/ami/.cache/py-yfinance`
  when `$HOME` is unset (Python's `expanduser` falls back to the passwd
  entry) — a path under a root-owned, non-existent directory.
- `cache.py:57-59` — `get_database()`: `if cls._db is None:
  cls._initialise()`. `_initialise()` raises on `os.makedirs()` failure and
  **never sets `cls._db`** — confirmed by reading both methods directly.
  So every call re-triggers the same failing `makedirs()`, not just once at
  cold start.
- `cache.py:129-131` — the exception is caught, logged via
  `get_yf_logger().info(...)`, `self.dummy = True` — not a crash, confirmed.
  But `utils.py:149-163` shows `get_yf_logger()` is a bare
  `logging.getLogger('yfinance')`, a separate stream from
  `app/core/logging.py`'s structlog JSON pipeline (`logging.basicConfig`
  format `"%(message)s"` + `structlog.processors.JSONRenderer()`) —
  confirmed by reading both files. It reaches stdout/`docker logs`, but as
  an unstructured line that doesn't parse as JSON alongside the rest of the
  app's log stream.

`USE_REAL_MARKET_DATA=true` on melehost's `.env` (CLAUDE.md), so this isn't
a theoretical path — it's every live Yahoo quote fetch after the runbook
applies, degrading (not crashing) with a filesystem-permission retry and a
log-format inconsistency on each one. Not caught by the sqlite-tempfile unit
suite because it's a real-filesystem-permission interaction, not something
the test fixtures exercise. Fix: `ENV HOME=/home/ami` + create/chown that
directory in the Dockerfile alongside the existing `/data`/`/app` chown, or
point `yfinance`'s cache via `XDG_CACHE_HOME`/`set_tz_cache_location` at a
directory the non-root user actually owns.
