### MAJOR-1 — a push-notification tap still covers the chrome

CR232's whole purpose, in Saiful's words: *"the bottom menu, the ad, and the ticker tape
function should always be on every screen and page."* The root cause the CR identifies is
correct — pushes resolved to the root navigator, so pushed pages covered the shell.

**One live path was not converted.** A notification tap routes through
`DeepLinkDispatcher`, which pushes onto the **root** navigator:

```
push_notification_listener.dart:45-49
  _openedSub = service.notificationOpened().listen((link) {
    final navigator = appNavigatorKey.currentState;   // ROOT navigator
    if (navigator == null) return;
    DeepLinkDispatcher.dispatch(navigator, link);
  });

deep_link_dispatcher.dart:44-52
  static void _openHoldingDetail(NavigatorState navigator, ...) {
    ...
    navigator.push(
      MaterialPageRoute<void>(builder: (_) => TickerDetailScreen(ticker: ticker)),
    );
  }
```

`appNavigatorKey` is the root key (`app.dart:50`, defined `app_navigator_key.dart:8`), and
`TickerDetailScreen` is a full `Scaffold` page (`ticker_detail_screen.dart:37,126`). So a
user who taps a price-alert push lands on a full page **above** the shell: no bottom nav,
no ad slot, no ticker tape, and the back gesture as the only exit — which is the precise
state this CR exists to eliminate, and close to the "obscure exit" complaint that started it.

`git diff 4fb4f02f..2f867925 -- mobile/lib/services/notifications/deep_link_dispatcher.dart`
is **empty**: CR232 never touched this file. It is the one entry point the 60-push-site sweep
did not reach, because the navigator arrives as an injected parameter rather than from a
`BuildContext`.

This is exactly the risk the submission itself named in Attack surface 1 ("deep links or
notification taps that land a page on the root navigator and cover the chrome again"). It is
real, not hypothetical, and **no test covers it** — `grep -rl DeepLinkDispatcher mobile/test/`
returns nothing, and no test exercises `notificationOpened`.

Note the four reserved routes (`open_journal_entry`, `open_room_verdict`, `open_lesson`,
`open_game_close`) are `_stub` today but are wired to the same root navigator, so each
inherits the defect the moment its CR starts pushing.

**Fix is not a one-liner.** The per-tab keys (`home_shell.dart:84-85`,
`Map<AmiTab, GlobalKey<NavigatorState>> _navKeys`) are private to `_HomeShellState`, so the
dispatcher cannot reach them as written. The route out needs the active tab's navigator
exposed (or the dispatcher switching tab then pushing through that tab's key), plus a test
that asserts a dispatched deep link leaves the chrome mounted.

## Round 2 — auditor u66

**SHA audited:** `318fb6ac`, in a detached scratch worktree `CR232r2-u66` per DEF159. Worktree
verified clean after every probe was removed.

Both round-1 findings are genuinely fixed. I re-derived each independently rather than reading
the submission's own mutation transcript.

### MAJOR-1 — fixed, and the fix is better than the minimum

`grep -n 'appNavigatorKey\|rootNavigator' deep_link_dispatcher.dart` now returns **only doc
comments** — no root-navigator reference survives in any executable path. `dispatch` takes a
`WidgetRef`, switches `activeTabProvider` to the route's owning tab (DEF190's own mechanism) and
pushes on that tab's key from `homeShellNavKeysProvider`.

What makes it hold rather than merely move: **every failure mode returns a typed result instead
of falling back.**

- `navKeys == null` (shell not mounted) → `deferred`
- `navKeys[tab].currentState == null` (Navigator not attached this frame) → `deferred`
- route targets a tab this build does not render → `unknownRoute`

There is no branch that pushes anywhere on failure. The gated-tab check
(`!AmiTab.visible.contains(entry.tab)`) is a case I did not raise and the builder caught —
switching to a tab a flag-gated build does not render would be the same "landed somewhere the
user didn't ask for" failure in a different costume.

**The cold-start case is handled, which is where a naive fix would have dropped the link.** A tap
that *launches* the app can arrive before `HomeShell` publishes its keys (OneSignal's click
listener registers in `main()` before `runApp`). `_handleOpenedLink` queues the link and flushes
via `ref.listenManual`, **re-dispatching through the same path** so a second defer re-queues
correctly rather than duplicating the flush logic. The subscription is stored and cancelled in
`dispose`. Queued, not dropped, not root-pushed — CR040's direction.

The new test asserts the property that actually distinguishes the two states —
`find.descendant(of: HomeShell, matching: TickerDetailScreen)` — and the submission is right that
`find.byType` alone cannot tell them apart, because `IndexedStack` never unmounts sibling panes.

### The incidental bug they found is the most valuable thing in this round

`_HomeShellState.dispose()` originally called `ref.read(...)` directly, which throws `Bad state:
Cannot use "ref" after the widget was disposed` — `ConsumerStatefulElement.unmount()` invalidates
`ref` **before** `State.dispose()` runs. The uncaught exception aborted the rest of the
widget-tree unmount, breaking a sibling provider's `onDispose` (`telemetryProvider`'s flush-timer
cancel) and surfacing as **9 unrelated "Timer is still pending" failures** in a different test
file.

The fix — capture the `StateController` in `initState` while `ref` is valid, use that in
`dispose` — is correct, because a `StateController` is owned by the provider, not the widget, and
outlives it. The diagnosis is now written into `home_shell.dart:105-119` where the next person
to hit this shape will find it. That is a P-pattern candidate in its own right: *an exception in
`dispose()` does not fail where it is thrown.*
