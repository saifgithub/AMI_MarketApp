## MAJOR — a partial `PUT /v1/daily_challenge/reminder` silently clears the reminder hour

**Reproduced empirically, not inferred from reading.** Wrote a standalone
repro against the real endpoint + real DB session (not a unit of the
shipped test file):

```python
client.put("/v1/daily_challenge/reminder", json={"daily_reminder_hour": 8, "timezone": "Asia/Riyadh"})
client.put("/v1/daily_challenge/reminder", json={"timezone": "Asia/Kuala_Lumpur"})  # timezone-only update
# → DB row: daily_reminder_hour is now None. It was 8.
```

```
AssertionError: BUG: hour was silently cleared to None by a timezone-only PUT
```

**Root cause**, in `app/api/daily_challenge.py`'s `set_reminder_preference`:

```python
row.daily_reminder_hour = req.daily_reminder_hour   # ← unconditional
if req.timezone is not None:                        # ← guarded
    row.timezone = req.timezone
```

`ReminderPreference.daily_reminder_hour` defaults to `None` when the field
is **omitted** from the request body — Pydantic cannot distinguish "field
absent" from "field explicitly sent as `null`" on a plain `Optional[int] =
None` model. The handler treats both identically and writes `None`
straight to the column. `timezone` gets the opposite, correct treatment
(`if req.timezone is not None:` — only touch it when the caller actually
sent something) with the docstring explicitly promising *"Omit to leave
unchanged."* `daily_reminder_hour` makes no such promise and doesn't keep
it either, despite the model's own docstring establishing `null` as a
**meaningful, intentional** value ("null turns reminders off... so there
is no separate enabled flag to drift out of sync with the hour") — which
is exactly why "omitted" and "explicitly null" need to be distinguishable
here and currently aren't.

**Why this is a MAJOR, not a MINOR:** it's silent (200 OK, no error), it
reproduces on the single most plausible real-world call pattern for this
endpoint (a user updates their timezone — travel, relocation — without
touching their already-set hour), and it directly undoes the CR's own
stated purpose. §4 of the submission is a story about exactly this failure
shape: *"a feature that is on, green, and does nothing, with no error and
no user complaint"* — the write path CR095 built to fix that has a
narrower version of the same disease in it. The shipped test suite doesn't
catch it because `test_omitting_timezone_leaves_it_unchanged` tests the
omission of `timezone`, never the omission of `daily_reminder_hour` — the
asymmetry in the code is mirrored by an asymmetry in what got tested.

**Suggested fix** (not prescriptive): the model needs to distinguish unset
from explicit-null — either a sentinel (`daily_reminder_hour:
int | None | _UNSET = _UNSET`, matching whatever partial-update pattern
this project already uses elsewhere, if any) or `model_fields_set` /
`exclude_unset=True` on the incoming request, then only assign when
`"daily_reminder_hour" in req.model_fields_set`. Whichever shape, it needs
its own test in the same style as `test_omitting_timezone_leaves_it_unchanged`,
mirrored for the hour.

### MAJOR — a same-day timezone change causes a second reminder for the same day

**Reproduced empirically** (`backend/tests/unit/test_cr095_timezone_change_double_send_pin.py`):

```
user tz=UTC hour=10, email set.
tick 1 @ 2026-06-01T10:05Z  -> local 2026-06-01 10:05, reminded, source_ref="2026-06-01"
user changes tz -> "Pacific/Kiritimati" (UTC+14)   # e.g. via a future PUT /reminder call
tick 2 @ 2026-06-01T20:05Z  -> local 2026-06-02 10:05 (SAME real UTC day, 10h later),
                                hour reached again, no row exists for source_ref="2026-06-02"
                                -> sent again
```

```
$ .venv/bin/python -m pytest tests/unit/test_cr095_timezone_change_double_send_pin.py -v
1 passed
```

**Root cause**: `_already_reminded_today`'s dedupe key (`source_ref` =
`local_now.astimezone(user.timezone).date().isoformat()`) is recomputed
fresh from the user's *current* `timezone` column on every tick, with no
memory of what timezone produced the *previous* reminder's `source_ref`. A
large-enough forward offset change moves `local_date` to a value with no
existing `notifications` row, so `_already_reminded_today` correctly (by its
own narrow contract) answers "no" — but the true invariant CR095 promises
("at most once per day") is about the user's *calendar day*, and a mid-day
timezone edit is exactly the kind of ordinary user action (device-locale
resync, travel, a Settings screen) mobile is expected to wire up next.

**Why MAJOR not BLOCKER**: needs a real timezone value change between two
ticks — not the common steady-state case — but it needs no unusual
deployment topology, no restart, no concurrency; a single background task
running exactly as designed produces it from one ordinary user action.
Directly contradicts the CR's own acceptance line ("at most once per day")
and `daily_reminder.py`'s own docstring claim that the dedupe "makes the day
boundary the user's own, not UTC's" (true only while the user's timezone
column doesn't change between ticks — undocumented).

**Suggested fix** (not prescriptive): key the dedupe on something that
doesn't retroactively move when timezone changes — e.g. stamp
`source_ref` using the timezone *in effect when a reminder is sent* and, on
timezone WRITE, either (a) skip evaluating that user for the remainder of
the real day the change lands in, or (b) check for an existing
`daily_reminder` row within the trailing ~20h regardless of `source_ref`
before sending. Needs a test mirroring this pin, asserting the fixed
behaviour (`stats2["sent_email"] == 0`).

### MAJOR — two overlapping ticks double-send; no DB-level guard exists

**Reproduced empirically** (`backend/tests/unit/test_cr095_concurrent_ticks_double_send_pin.py`),
by widening the real TOCTOU window (a sleep inside the genuine
`_already_reminded_today`, not a fake) so two real, concurrent calls to
`send_due_reminders()` deterministically both observe "not yet reminded"
before either writes:

```
$ .venv/bin/python -m pytest tests/unit/test_cr095_concurrent_ticks_double_send_pin.py -v
1 passed
# both threads: sent_email=1 each: 2 emails, 2 NotificationRow rows,
# same user, same source_ref, zero errors
```

**Root cause**: `NotificationRow` (`app/db/models.py:528`) has no unique
constraint on `(user_id, type, source_ref)` — only 2 unrelated indexes
(`user_id, created_at` / `user_id, read_at`). `_already_reminded_today` is a
plain `SELECT`; `notify()`'s write is a plain `INSERT` with no
`ON CONFLICT`, no row lock, no serializable-isolation guard. The ONLY thing
preventing a double-send under concurrent execution is "in practice only
one process ever calls this" — an operational fact of today's melehost
topology (`container_name: ami_api_alpha`, no `--workers` flag in the
Dockerfile `CMD`, so one uvicorn process, one asyncio task, sequential
`while True: work; sleep`), not anything the code itself enforces.

`main.py::_daily_reminder_tick`'s docstring states this as an unconditional
property: *"this one is safe to run on a MUCH shorter interval without any
risk of a double-send"* — that claim is false in general; it happens to
hold only because of the current single-process deployment, which nothing
in this PROTOCOL/BINDINGS pair or the code guards against changing (a
`docker compose up --scale`, a future move to multiple workers for
throughput, or a promotion-restart window where the outgoing container's
in-flight `asyncio.to_thread(send_due_reminders)` hasn't finished when the
incoming container's work-first tick starts — `main.py`'s `lifespan`
`finally` cancels the asyncio task but cannot stop a synchronous function
already running in a threadpool thread).

**Why MAJOR not MINOR**: this project's own CLAUDE.md doctrine is explicit
that operational assumptions are not controls ("Prompt instructions are not
controls... make it structural" — the same principle applies to deployment
topology assumed-but-unenforced). A comment asserting "no risk" where the
actual guarantee is "no risk as long as nobody ever runs two of these" is
the kind of soft claim this repo's own failure-pattern doctrine flags.

**Suggested fix** (not prescriptive): a partial unique index on
`notifications(user_id, type, source_ref) WHERE type = 'daily_reminder'`
(mirrors the pattern CR136 M07 already used — `uq_journal_dedupe` — for
exactly this "prevent duplicate business-key rows" problem), with `notify()`
degrading a unique-violation to "already reminded" (not a hard 500) so a
losing racer sees a normal skip rather than an unhandled `IntegrityError`.
