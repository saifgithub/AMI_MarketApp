## 1. What broke, live

Found during CR136's first promotion to Alpha (`alpha-2026-08-04-1`). It took
the journal down for real users.

`init_schema()` called `Base.metadata.create_all(engine)` and only *afterwards*
checked `if "alembic_version" in inspector.get_table_names(): return`. That
guard protected the **stamp**, not the **create** above it.

On a fresh DB the pair is coherent. On an **existing** DB `create_all` still
fired and built exactly the tables the incoming CR had just added — correctly,
since it reads the same `Base.metadata` the migrations were autogenerated from
— then returned without stamping, because `alembic_version` was present.
Alembic was behind reality with no record of it.

Measured on Alpha 2026-08-04: the recreated container's first DB touch built
`price_history_daily` and `portfolio_value_snapshots`; `alembic_version` stayed
at `8a4ce4f8abc3`; `alembic upgrade head` reported
`Running upgrade 8a4ce4f8abc3 -> a9b0c1d20026` and raised
`psycopg2.errors.DuplicateTable: relation "price_history_daily" already exists`.

**The damage was not the table it failed on.** Alembic aborts the whole chain,
so `c2d3e4f50028` and `d3e4f5a60029` — which only ALTER `journal_entries`, a
table `create_all` will never touch because it already exists — never ran. The
promoted code maps `JournalEntryRow.dedupe_key`, the column was absent, and
every journal read on live Alpha failed with
`(psycopg2.errors.UndefinedColumn) column journal_entries.dedupe_key does not
exist`. 1203 journal rows were intact throughout; this was schema, not data.

Resolved by hand at the time (`alembic stamp b1c2d3e40027` then
`alembic upgrade head`, after verifying both created tables matched their
migrations column-for-column so the stamp was a fact rather than an
assumption). **The mechanism was left open** and recurs on every future CR that
adds a table.

## 2. What was changed, and why it is two changes

The row filed three candidates in preference order. **(a)** run migrations
before the app's first DB touch, **(b)** skip `create_all` when
`alembic_version` exists, **(c)** re-stamp to head after `create_all`.

On inspection (a) and (b) are not alternatives — they fix different halves of
the same outage, and shipping only one leaves the other live. (c) stays
rejected: it papers over a genuinely divergent schema.

**(b) — the wedge.** `session.py`: the `alembic_version` presence check moved
ABOVE `create_all`. On any DB carrying `alembic_version`, `init_schema` now
creates nothing; `create_all` reverts to what it is actually for, a fresh
sqlite tempfile.

One shape detail drove the implementation: `init_schema()` is called from ~10
store constructors (`auth_service.py:231`, `sim_engine.py:228`,
`watchlist_store.py:30`, `overlay_store.py:64`, `feedback_store.py:27`,
`price_alert_store.py:36`, `price_alert_evaluator.py:163`,
`notification_service.py:60`, …), **not once at boot** — "first DB touch" is
whatever request lands first. Without a guard, each call would pay an
`inspect()` plus a `MigrationContext` round trip for a question whose answer
cannot change while the engine lives. The short-circuit is keyed on the engine
OBJECT (`_schema_checked_for is engine`), so `reset_for_tests` — which disposes
and rebuilds the engine — re-arms it for free rather than needing its own reset
line.

**(a) — the window.** `/promote-to-alpha` step 5 now builds the image and runs
`docker compose run --rm --no-deps api-alpha alembic upgrade head` against the
live DB **while the OLD container is still serving**, swapping containers only
if that succeeds. Step 6 demoted from "run pending migrations" to "confirm
`alembic current` reports head".

Two things verified before writing that:

- `backend/Dockerfile:34` is `CMD ["uvicorn", …]` with **no `ENTRYPOINT`**, so
  `compose run … alembic upgrade head` actually overrides the command.
- `backend/alembic/env.py:22,31` imports `_resolve_url` from
  `app.db.session` and overrides `sqlalchemy.url` with it, so the one-shot
  container resolves the same DB URL from the same env as `compose exec` did.
  (`alembic.ini:91` holds only a placeholder sqlite path.)

Step 6's old note said the self-stamp made this *"a clean no-op on a fresh
container"* — true, and it read as though it covered the case it did not.
Rewritten with the outage described in place.

**Plus the diagnosis cost, which neither candidate addressed.**
`_report_if_behind_head` logs `db_schema_behind_head` with `current_revision`
and `head_revision` when the DB is behind the running code. It deliberately
never raises: a boot that refuses on a bad read would convert a reporting
problem into an outage. DEF215's outage was silent for as long as it took
someone to notice journal reads failing — old schema, new code, nothing
anywhere comparing the two.

## 5. Live / real measurement — partial, and this is the lane's weakest point

**What was measured:** Alpha's current revision, this session, over SSH:

```

→ d3e4f5a60029 (head)
```

So the 2026-08-04 hand-fix held, and Alpha is coherent today.

**What was NOT measured, stated plainly:**

1. **The new promotion ordering has never been run.** It is a documented
   procedure change in a markdown runbook; no test covers it and no promotion
   has happened since. `docker compose run --rm --no-deps api-alpha alembic
   upgrade head` is reasoned-through (CMD not ENTRYPOINT, env.py resolves the
   URL) but **unexercised against the real host**. Its first real execution is
   the next `/promote-to-alpha`.
2. **The fix is not on Alpha.** Everything above ran on the Mac against sqlite
   tempfiles. Alpha still runs the pre-fix `session.py`.
3. **The end-to-end assertion the row asked for does not exist.** The row wants
   *"a test that a non-fresh DB plus a table-adding migration ends at head"*.
   What ships instead is a test that `create_all` **does not fire** on a
   non-fresh DB — the cause rather than the outcome. Replaying the real
   migration chain on sqlite was not attempted (batch-mode ALTER differences
   make it a poor proxy for the Postgres path it would be standing in for), so
   the outcome-level claim rests on the causal one. **If you think that
   substitution is not good enough, that is a fair MAJOR.**

## 6. What I most want challenged

1. **The short-circuit changes `init_schema`'s contract.** It used to be
   idempotent-and-*restorative*: call it again after dropping a table and the
   table came back. It is now once-per-engine. `reset_for_tests` builds a new
   engine so the suite is unaffected (2341 passed), but if any code path
   anywhere relies on re-calling `init_schema()` to repair a schema, it is now
   a silent no-op. I grepped the callers and found none, but a grep is not a
   proof.
2. **Concurrency on `_schema_checked_for`.** Two threads entering
   `init_schema()` simultaneously can both pass the identity check. On the
   fresh path both call `create_all` (benign — `checkfirst=True`); on the
   non-fresh path both just log. I believe this is harmless rather than
   guarded. FastAPI runs sync deps in a threadpool, so it is reachable.
3. **`inspect(engine)` is now unguarded on the hot path.** Previously the
   inspect call lived inside the `try/except Exception: pass` around the stamp;
   it is now above it, so a DB that errors on introspection propagates out of
   `init_schema` instead of being swallowed. I believe that is correct
   (CR040 — a DB we cannot introspect should not boot quietly), but it is a
   behaviour change I made deliberately and did not test.
4. **Is `_report_if_behind_head` loud enough to count as a control?** It writes
   one ERROR line at first DB touch. CR038's rule is that an instruction is not
   a control; a log nobody reads is arguably the same class. The alternative —
   refusing to boot — I rejected as converting a reporting problem into an
   outage. That is a judgement call and I would take a challenge to it.
5. **Whether the promotion-runbook half belongs in this lane at all.** It is a
   markdown change with no automated verification, riding in the same commit as
   a tested source change. Splitting it out is defensible; I kept them together
   because shipping (b) without (a) leaves the outage window open and the pair
   only makes sense as one argument.
