# CR233 — audit lane (real Alpaca order types: limit/stop/stop_limit/bracket)

**SCOPE:** cr (mobile-only; no backend change)

**TIER: A.** This changes what gets sent to `POST /v2/orders` against a live-linked (paper) brokerage account, and what the trade ticket's destination lock permits. Same class of risk CR227 itself was routed to independent audit for.

**SHA:** see the commit this file ships with, same worktree branch — `git log --oneline -1 -- mobile/lib/services/alpaca/alpaca_client.dart mobile/lib/screens/sim/trade_ticket_sheet.dart`. Worktree branch, not yet merged to `main`.

**depends-on:** CR227 (`done`, market-only Alpaca order routing — this CR widens it), DEF419 (`open`, per-account mandate check — this CR's preview-sizing change composes with it but does not modify `toMandateSnapshotJson` or the account-snapshot wiring, per the dispatch brief's explicit instruction to keep this lane's edits confined). **Promoted:** no.

## What and why

Saiful, 2026-09-24: *"During trading, the 'destination' AMI, Alpaca, both, only appears when 'market' is selected. Everything else does not show it. Fix it please."*

CR227's round-1 audit found `AlpacaClient.submitOrder()` hard-coded `type: 'market'` regardless of what the ticket asked for — a LIMIT/STOP order routed to Alpaca was silently converted to an immediate market fill. The round-1 fix closed the silent-conversion hole by refusing every non-market order and hiding the destination picker for one. This CR replaces that refusal with the real capability: `submitOrder()` now builds market/limit/stop/stop_limit orders (plus an optional bracket) natively, and the destination lock no longer covers order type.

**The fix, mobile-only:**
- `alpaca_client.dart` gains `buildAlpacaOrderPayload()` (pure, builds the exact `POST /v2/orders` body per order type + optional bracket) and `validateAlpacaOrder()` (throws `AlpacaOrderRejected` — the same exception CR227 already used — before any network call, on an unrecognised type, a missing required price, or a wrong-side bracket per the DEF312/DEF377 rule).
- `submitOrder()` takes `limitPrice`/`triggerPrice`/`tif`/`bracket`, all optional; the old unconditional `orderType != market` refusal is gone, `orderType == unknown` still refuses.
- `trade_ticket_sheet.dart`'s `_destinationLocked` drops its order-type clause; cover-a-short/sell-from-holding stay locked (unrelated reasoning).
- The Alpaca-leg preview (`SimNotifier.preview()` → `ApiClient.simPreview()` → `POST /v1/sim/preview`) now sends the order's own `order_type`/`limit_price`/`trigger_price` instead of always `market`.
- CR230's order log (`detail`, free text, unchanged schema) carries order type/prices/TIF/bracket.
- `AlpacaOrder.isResting` (new) reads Alpaca's own order status so the result panel says "resting"/"accepted", never "filled", for an order that hasn't crossed the market.
- TIF: AMI's `gtd30`/`gtd90` → Alpaca's `gtc` (documented approximation — Alpaca has no N-day GTD on the simple orders endpoint).

Design note: `docs/forward_planning/CR233_alpaca_order_types/CR233_alpaca_order_types.md`. D-074 narrows D-071 accordingly (`docs/initial_specs/11_decisions/decision_log.md`).

## Known gap, disclosed not fixed (backend, out of scope for this mobile-only lane)

`preview_trade`'s handler (`backend/app/api/sim.py`) forwards `limit_price` to `SimEngine.preview()` but that engine method has **no `trigger_price` parameter at all** — a STOP/STOP_LIMIT Alpaca-leg preview still sizes cash sufficiency against the live mark, not the stop price, and `preview()` runs no bracket-validity check (`stop`/`target` aren't parameters on it either; only `submit_trade`'s path validates a bracket). Mobile sends `trigger_price` on the wire regardless (harmless today — no `extra="forbid"` on `SubmitTradeRequest`) so this is forwards-compatible, but the auditor should confirm nothing in the mobile code or copy claims this is currently honoured server-side. A backend follow-up CR is needed; flagged to the Architect for minting, not attempted in this worktree.

## Attack surface (please probe)

1. **Silent type conversion** — the exact CR227 round-1 MAJOR-1 shape, now on a wider surface. Confirm `buildAlpacaOrderPayload` never falls back to `type: 'market'` for a non-market `orderType`, and that `validateAlpacaOrder` genuinely runs before `_dio.post` in `submitOrder` (not just before some other check) — the fake-adapter tests assert zero calls on a validation failure; verify that holds under a mutation of the call order.
2. **Bracket side errors** — DEF312/DEF377 mirrored for Alpaca. Confirm the wrong-side check fires for BOTH buy and sell (stop_limit inverted-for-short case is tested; probe stop-only and target-only cases on the short side too, since the test suite's short-side coverage is thinner than the long side's).
3. **TIF mismatch vs AMI** — `gtd30`/`gtd90` → `gtc` is a documented non-equivalence. Confirm no copy anywhere (result panel, order log detail) claims the Alpaca leg expires with AMI's; confirm this is disclosed in the CR doc (it is) and judge whether the disclosure is strong enough for a feature that silently leaves an order resting indefinitely at Alpaca past when AMI's own mirror would have expired.
4. **Preview price basis** — confirm the STOP/STOP_LIMIT gap (mark-priced preview, not stop-priced) is genuinely a pre-existing/inherent backend limitation and not something this CR's mobile change could have closed by forwarding a field the backend already reads. Re-derive independently from `backend/app/services/sim_engine.py`'s `preview()` signature rather than taking the CR doc's word for it.
5. **Resting-vs-filled labelling** — `AlpacaOrder.isResting`'s status set (`new`/`accepted`/`pending_new`/`accepted_for_bidding`/`held`) is asserted from Alpaca's own documented order lifecycle, not from a live probe (no live Alpaca account in this worktree). Confirm the set is complete enough that a real resting order can't fall through to the "filled" message, and that a genuinely filled market order (whose response status is typically already `filled`) isn't misreported as resting.
6. **Order-log completeness** — confirm `_alpacaOrderLogDetail` is called with the same `limitPrice`/`triggerPrice`/`bracket` values that were actually sent to `submitOrder`, not independently recomputed (a second computation of the same facts is the DEF098 shape this project keeps naming).
7. **Destination-lock scope** — confirm the cover-a-short/sell-from-holding lock genuinely survived unchanged (two clauses, not the pre-CR233 three), and that no other code path implicitly depended on the removed clause (e.g., a resting-order-specific Alpaca warning that assumed the picker could never be visible for a non-market type).
