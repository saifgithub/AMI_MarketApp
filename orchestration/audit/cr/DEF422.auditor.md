### The question

Saiful's screenshot showed "ORDERS 0" above a rendered open Alpaca order. So the guarantee is
this: each badge equals what the tab body lists. While Alpaca's share is unknown, the badge
says so, and never shows a number that looks final.

### What holds

- **Badge/row parity.** The tab bar watches the exact providers the bodies render from:
  - `alpacaPositionsProvider`;
  - `alpacaOpenOrdersProvider`;
  - `alpacaClosedOrdersProvider`.

  `_AlpacaOpenOrdersList` renders `for (final o in orders)` with no filter
  (`alpaca_orders_section.dart:103`), and the history list does the same (`:166`). A bracket
  order is one card with its legs nested inside, and it counts as one. So `length` equals the
  number of cards.
- **Loading and error are not folded into the number.** `displayCount` adds Alpaca's share only
  from `valueOrNull`. `marker` takes precedence, loading before error. `alpacaLinkedProvider` is
  a local `AlpacaCredentialStore.isLinked()` read, so the unmarked window before it resolves
  is a local storage read, not a network wait.
- **The tests are load-bearing.** I mutated `displayCount => ami` and 3 of 28 tests failed
  (exit 1). With the code restored, 28 passed (exit 0).
- **Item 1, traffic:** no new fetches beyond what CR234 already made. The tab bodies sit in an
  `IndexedStack` (`portfolio_screen.dart:276`), so the sections were already mounted and
  watching the same provider instances. The bar adds watchers, not requests.
- **Item 4, unlink:** `settings_screen.dart:1701-1708` clears the credential and invalidates
  `alpacaLinkedProvider`. The bar's conditional watch then drops Alpaca's share. I checked
  this by reading the code, not by driving it.
- **Items 5 and 6:** `FittedBox(scaleDown)` degrades by shrinking the text, not by
  overflowing. The equity chart's `Flexible` plus ellipsis matches that file's own convention.

**Not driven:** item 2's live race and item 3's slow real network. The Mac has no linked paper
account and no backend.

### MINOR-1 — HISTORY's Alpaca share is capped at 50, but the code says "uncapped"

The new comment at the history `_TabCount` and the submission both say HISTORY's Alpaca side
is "deliberately uncapped… every closed order". But `alpacaClosedOrdersProvider` fetches
`orders(status: 'closed', limit: 50)` (`alpaca_providers.dart:46-48`). On the AMI side,
`historyCount` is `transactions.length`, a true total, because the 25-row cap there is only a
view default. So once an account has more than 50 closed paper orders, the HISTORY badge adds
an uncapped AMI total to a truncated Alpaca count. That silently undercounts, which is the
quietly-wrong-number class this DEF exists to remove.

The body doesn't disclose the cap either: the Alpaca history list has no "last 50" line. Badge
and rows still agree, so parity holds, but both stop at 50.

Open orders pass no `limit`, so they get Alpaca's own default page size. I'm going from
Alpaca's documentation for that value, which is 50, and did not measure it.

**Fix:**
- Correct the comment.
- Either show "50+" when the fetch returns exactly `limit`, or disclose the cap in the body and
  the badge.

### Recorded, not scored

Nothing invalidates the Alpaca order providers after `submitOrder` in `trade_ticket_sheet.dart`,
and they are kept alive by the `IndexedStack`. So after placing an Alpaca order, the Orders
list and now the badge keep the old count until pull-to-refresh. This predates CR234's
sections, and badge and list still agree. But it is a remaining way the user can still
see "ORDERS 0" with a live order open. Worth one line in CR234's follow-ups.
