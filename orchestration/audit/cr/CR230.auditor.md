## MAJOR-1 — the user's trade confirmation is gated on the logging round-trip

**The nominated guarantee is half-proven.** The submission's load-bearing claim is *"a failed log
call must never change the trade outcome,"* and for a **throwing** log call that is true and
properly pinned. I re-ran their mutation rather than trusting it: removing the `try { } catch (_)
{}` in `_reportOrderLog` gives 3 passed / 1 failed, the failure being
`the log call never gates the trade outcome — a throwing order_log call still shows the same
success banner as a working one`. That guard is real and load-bearing.

**But "failed" and "slow" are different failure modes, and only the first is covered.** A
`try/catch` swallows an exception; it does not bound a wait.

The call graph is unambiguous. `_placeAlpacaOrder` (`trade_ticket_sheet.dart:724, 739, 749, 759`)
does `await _reportOrderLog(...)` **before** the `return` in all four of its branches. Then
`_submitAlpacaOnly` does, in order:

```dart
final outcome = await _placeAlpacaOrder(typed, qty, TradeDestination.alpacaPaper);
if (!mounted) return;
HapticFeedback.mediumImpact();
setState(() => _destinationOutcomes = [outcome]);
if (outcome.ok) {
  Navigator.of(context).pop();
  ScaffoldMessenger.of(context).showSnackBar(...)   // the green success banner
}
```

So the haptic tick, the outcome row, the sheet dismissal and the success banner — the user's
entire confirmation — are all downstream of a logging HTTP call to AMI's own backend. The Alpaca
order has already been placed and accepted by then; only the *telling the user* is waiting.

`ApiClient`'s Dio config (`api_client.dart:346-347`) bounds it at `connectTimeout: 10s`,
`receiveTimeout: 30s`. So it cannot hang forever — it can hang for up to about half a minute.

**The consequence.** A degraded or unreachable `/v1/alpaca/order_log` — the backend down, the
tunnel flapping, a slow network — means a user whose paper order has *already executed at Alpaca*
sees an unchanged trade ticket with no haptic, no banner, and no outcome row for up to ~30
seconds. The natural response is to tap Buy again. This file already carries a fix for exactly
that user behaviour from a different cause: the `bug 9b3a6c2f` comment a few lines above explains
the previous snackbar was *"indistinguishable from the dark theme, leaving users unsure whether
the trade actually placed and tapping Buy again."* CR230 reintroduces that uncertainty through a
new door, and this one is reachable whenever AMI's own backend is having a bad minute.

**The docstrings state the right property and then don't hold it.** Three places say the report
runs *"after the outcome is already decided"* / *"the trade ticket's own success/failure banner is
already final by the time this runs."* That is true of the outcome **value** and false of its
**delivery**. The value is computed first; the user does not see it until the log call resolves.

**Evidence.** The ordering above is read directly from source and is not in dispute. I also
measured it, though I am explicit about the limits of that measurement: driving the real widget
with a 25s-delayed (not throwing) `alpacaReportOrderLog`, the outcome row was absent at T+3s —
after the Alpaca order had resolved — and present at T+29s, once the log call completed
(`logCalls=1` throughout, so this is one order, not a double-submit).

I burned several probe attempts at the widget level that observed the wrong surface (a popped
sheet, the selector chip, a torn-down tree), and one intermediate run produced a reading I could
not reconcile. I am reporting the source-level call graph as the finding's basis and the timing
run as corroboration, rather than the other way round.

**What would close it.** `unawaited(_reportOrderLog(...))` at the four call sites, plus a test
that fails without it — a slow (not throwing) fake log client, asserting the outcome is delivered
before it resolves. Note the CR doc's own original design said `unawaited`; the submission records
that it was changed to an awaited `try/catch` during implementation, to match
`_reportLinked`'s idiom. That idiom is right for the *swallow*; the `await` is what needs
dropping. `_reportLinked`'s own context differs — a link-state report is not sitting between a
user's executed trade and their confirmation of it.

## What I attacked that held

**1. Retention really is permanent, and the pin bites.** `alpaca_order_audit` is absent from
`trim_audit_tables()`'s model list (`audit.py:44-49`), so no sweep touches it. I verified the
pin catches a regression rather than merely passing: adding `(AlpacaOrderAuditRow,
"alpaca_order_audit")` to that list gives `1 failed, 10 passed`, the failure being
`TestRetentionPosture::test_a_row_older_than_the_audit_retention_window_survives_the_trim`.
Reverted, clean.

On the judgment call the submission explicitly raises — permanent vs. the 90-day track — I can
audit only that the code does what it claims, which it does, and that the reasoning is coherent,
which it is (`admin_audit`'s own docstring makes the same volume/forensic-value argument for the
same posture). Whether it matches what Saiful meant by *"keep a log of every interaction"* is his
call, not mine. Flagging it in the submission rather than letting it pass silently was correct.

**2. A client cannot log for another user, and cannot smuggle a `user_id`.** `log_order`
(`alpaca.py:117-137`) takes `user_id=current_user.id` from the authenticated session; the request
body has no `user_id` field and `AlpacaOrderLogIn` is `extra="forbid"`, so one cannot be added.
`_require_claimed` blocks anonymous users. Pinned by `TestAuthAndIsolation`'s two tests.

**3. The migration is genuinely single-head.** `cr230a0order0log` has `down_revision =
"e221i000009c"`, and it is the only file in the 73-revision tree descending from that revision —
no fork. Independently confirmed by DEF406's single-head test inside the green full suite.

**4. The DEF145 boundary is untouched and still passing.** CR230 adds no Alpaca HTTP call (the
new write goes to AMI's own DB), `alpaca_service.py` is not in the diff, and DEF145's 3 tests pass
at this SHA.

**5. The self-reported register drift is accurate in both directions.** I checked rather than
accepting the account: `git show d7d71755 --stat -- docs/forward_planning/cr_list.md` is empty, so
the commit genuinely did not regenerate the table — the gap was real and is described honestly.
At the audited HEAD, `test_registers_no_drift.py` + `test_p30_registers_name_things_that_exist.py`
give 10 passed. Surfacing this unprompted, when nothing at HEAD would have exposed it, is the
behaviour this handshake exists to encourage.

**6. One order writes exactly one log row.** Confirmed by direct measurement (`logCalls=1`),
matching the lane's own `hasLength(1)` assertion. An earlier reading of `2` in my probe was my
harness double-submitting — the lane's `_pump` already taps SUBMIT internally — not a defect.

## Note on scope and tier

The submission argues Tier B and closes on MINOR-only. MAJOR-1 promotes this to a second round
under the escalation-tiers binding, by the submission's own stated rule.

I considered whether MAJOR-1 is really a MINOR — nothing is lost, no data is wrong, and the
timeout bounds it at ~30s. I filed it as MAJOR because the harm is the one this repo has already
paid for once in this exact file (`bug 9b3a6c2f`): a user who cannot tell whether their order went
through, acting on that uncertainty with real money at the other end. A logging feature should not
be able to do that, and the fix is four `unawaited(...)` calls.

The scope question the submission raises — whether "every interaction" should include
`account()`/`positions()` reads — I would leave as built. Order placement is the state-changing
action; polling reads are volume without decision-relevant content, and the submission's reasoning
for excluding them is sound.

VERDICT: AWAITING_FIXES (round 1)
