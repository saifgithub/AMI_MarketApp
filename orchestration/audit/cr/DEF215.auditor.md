## §5.3 invites a MAJOR. I am declining it, on the merits

The submission says: the row asked for *"a test that a non-fresh DB plus a
table-adding migration ends at head"*; what ships asserts `create_all` **does
not fire** on a non-fresh DB — the cause rather than the outcome — and *"if you
think that substitution is not good enough, that is a fair MAJOR."*

It is good enough, and the reason is worth stating rather than waving through.
The outage was a four-link chain: (1) `create_all` builds table T on a
non-fresh DB → (2) `alembic upgrade head` re-CREATEs T and dies on
`DuplicateTable` → (3) Alembic aborts the chain so the later `journal_entries`
ALTERs never run → (4) the running code maps `dedupe_key` and every journal
read fails. The fix severs link 1, and the shipped test asserts link 1 is
severed. Links 2–4 are **Alembic's own documented behaviour** — an unblocked
chain runs to completion — and asserting them is testing the framework, which
this repo explicitly does not do. A test that replayed the chain on sqlite
would also be standing in for the Postgres path with batch-mode ALTER
semantics that differ, which the submission itself names as why it declined.

The residue that substitution leaves is *"does the real thing actually work on
the real host"*, and that is not a test-shape question. I answered it by
measurement instead — see below.

## The unexercised half, exercised

§5.1 is the honest disclosure that the whole `(a)` half is a markdown runbook
change that *"has never been run"* and whose first real execution would be the
next promotion. That is exactly the state where a reasoned-through procedure
quietly turns out to be wrong, so I ran its mechanism against melehost —
read-only, using `alembic current` in place of `alembic upgrade head`.
`env.py` mentions `init_schema`/`create_all` only in its docstring and calls
neither, so `current` cannot mutate anything; everything else about the
invocation is identical.

```
ssh melehost "cd ~/ami_trade && docker compose run --rm --no-deps api-alpha alembic current"
 Container ami-trade-local-api-alpha-run-1e13526d5ecb  Created
d3e4f5a60029 (head)
INFO  [alembic.runtime.migration] Context impl PostgresqlImpl.
EXIT=0
```

Five things that were arguments in §2 are now readings:

- **`container_name: ami_api_alpha` does not collide with `compose run`.** This
  was my sharpest objection to the step and it is dead: Compose ignored the
  pinned name and generated `ami-trade-local-api-alpha-run-1e13526d5ecb`. Had
  it applied the name, step 5 would have failed on every promotion forever.
- **It reaches the real database, not a fallback.** `Context impl
  PostgresqlImpl`. This was the failure mode I went looking for hardest,
  because `_resolve_url()` (`session.py:44-47`) returns a **sqlite path**
  whenever `database_url` is empty *or* still the `localhost` default — so a
  throwaway container that lost its env would have migrated a scratch sqlite
  file inside itself, exited 0, and told the runbook to go ahead and swap. That
  is precisely CR040's silent-success shape. It cannot happen here:
  `docker-compose.yml` sets `DATABASE_URL` as a **literal** in the `api-alpha`
  `environment:` block, pointing at `@postgres:5432`, which is not the
  `localhost` sentinel `_resolve_url` falls back on, and `compose run` applies
  the service's environment.
- **Exit code 0**, which is the signal step 5 branches on.
- **`--rm` cleaned up** — no leftover `api-alpha-run` container.
- **The live container was untouched**: `ami_api_alpha Up 10 hours (healthy)`
  before and after, same uptime. `compose run` publishes no ports without
  `--service-ports`, so it never contests `:8000` with the running container.

`d3e4f5a60029 (head)` also independently reproduces §5's own Alpha reading.

What remains genuinely unexercised is narrower than §5.1 claims: not the
procedure, but only the difference between `current` and `upgrade head` once
connected — i.e. Alembic's write path. Container, env, URL resolution, PATH,
`alembic.ini` discovery, network and exit-code propagation are all now
measured rather than reasoned.

## The new control is not dark on Alpha (DEF038 / DEF063 check)

`_report_if_behind_head` is only worth anything if it can find `alembic.ini` in
the real container, and `_alembic_config` locates it by walking
`Path(__file__).resolve().parent.parent.parent`. That is the exact shape of
bug this project has shipped twice. Ran the computation inside the live
container:

```
docker exec ami_api_alpha python -c "... Path(s.__file__).resolve().parent.parent.parent / 'alembic.ini'"
→ /app/alembic.ini
-rw-r--r-- 1 root root 5159 /app/alembic.ini        (present)
/app/alembic/versions/…                             (present)
```

`app/` is bind-mounted but `alembic.ini` and `alembic/` come from the image
(`Dockerfile:22-23`), and step 5 builds before it runs, so both are current.
The control will fire.

**Also checked because it would be silent and fatal:** `logger.warn` is called
*inside* `_report_if_behind_head`'s `except` handler, so if it did not exist
the handler itself would raise `AttributeError` straight out of `init_schema`
on the non-fresh path — every boot, on the deployed path, converting a
swallowed diagnostic into the outage the docstring promises never to cause.
`logger` is `structlog`'s `BoundLoggerLazyProxy`; `warn` resolves and calls
cleanly. Verified, not assumed.

## MINOR m1 — §6.2's "benign" is measurably not benign

§6.2 states that two threads entering `init_schema()` can both pass the
identity check, and that *"on the fresh path both call `create_all` (benign —
`checkfirst=True`)"*. `checkfirst` is not atomic: both threads inspect, both
see the table missing, both issue `CREATE TABLE`. Measured — two threads on a
barrier against a stripped sqlite DB:

```
thread exceptions      : ['OperationalError']
alembic_version rows   : ['e4f5a6b70030']   row count: 1  (>1 == corrupt)
tables built           : 35
get_current_revision() : e4f5a6b70030
```

So the **database ends coherent** — one `alembic_version` row, all 35 tables,
a revision Alembic can still read, and the double-stamp does not corrupt
anything, which was the failure I was actually hunting. But one of the two
threads **raised out of `init_schema()`**. The word "benign" is wrong; the
correct claim is "does not corrupt, but one caller eats an `OperationalError`".

MINOR, not MAJOR, and deliberately so:

- **Unreachable on the deployed path.** It is fresh-DB-only, and Alpha carries
  `alembic_version` (`d3e4f5a60029`, measured above), so `init_schema` never
  reaches `create_all` there at all.
- **Pre-existing, and this change strictly narrows it.** Before DEF215
  `create_all` ran on *every* one of the 13 `init_schema()` call sites, in every
  thread, for the life of the process. It now runs at most once per engine and
  only on a fresh database. The race window goes from permanent to first-boot.

Grading a change MAJOR for not fully closing a pre-existing race that it makes
strictly rarer would be the wrong call. What is worth correcting is the
submission's own confidence in it.

## MINOR m2 — nothing regression-protects the non-fresh memoisation

Mutation AUD-2 removes `_schema_checked_for = engine` from the non-fresh path
only, leaving the fix itself intact. **`4 passed` — survives.**

The shipped code is correct; this is a missing guard, not a defect. But it
guards something the submission argues for at length in §2: `init_schema()` is
called from **13** sites (I enumerated them; §2 says "~10"), so losing that one
line means every store constructor pays an `inspect()` plus a
`MigrationContext` round trip, and — the part that matters — a DB behind head
would emit `db_schema_behind_head` **13 times per process instead of once**.
The control introduced here specifically to be noticed becomes log spam, and
§6.4 already worries that a log nobody reads is not a control. The property is
cheap to pin: call `init_schema()` twice and assert one report.

## Checked and accepted

- **§6.1's contract change is real, and its risk is not.** Measured: after
  `DROP TABLE` + `init_schema()`, `table restored? False` — the function is
  genuinely no longer restorative. §6.1 says a grep is not a proof, so I
  enumerated all 13 call sites myself (`session.py:225`, plus 12 service/store
  constructors). Every one is a constructor-time "make sure the schema exists"
  call; none is a repair path, none re-calls to recover. The old contract has
  no consumer.
- **The engine-identity check is sound, including the trap it walks past.**
  `reset_for_tests` disposes, nulls `_engine`, then calls `init_schema()`, which
  builds a new `Engine` — so `is` differs and the guard re-arms with no reset
  line, exactly as claimed. Worth noting *why* this is safe rather than lucky:
  an `is` test against a dead object is normally a hazard, because CPython can
  allocate a new object at a freed address and produce a false positive.
  `_schema_checked_for` holds a **strong reference** to the old engine, so it
  cannot be freed, so its address cannot be reused. The thing that looks like a
  leak is what makes the identity check correct.
- **`_schema_checked_for = engine` is set AFTER the fresh-path work, not
  before** (`:207`), so a `create_all` that raises is not memoised as done and
  the next caller retries. The ordering that would have been a real bug is the
  right way round.
- **§6.3 accepted.** `inspect(engine)` is now outside the `try/except`, so a DB
  that cannot be introspected propagates instead of being swallowed. Deliberate
  and correct per CR040 — the alternative is booting quietly against a database
  we cannot read.
- **§6.4 accepted.** `_report_if_behind_head` is a diagnostic, and it is not
  carrying the safety load: the actual control is step 5's ordering — migrate
  while the old container serves, stop on failure, swap only on success. Refusing
  to boot on a failed *read* would convert a reporting problem into an outage,
  which is the reasoning given and it is right.
- **§6.5 accepted.** The runbook half and the source half are one argument;
  shipping (b) without (a) leaves the outage window open. Splitting them would
  have made the commit tidier and the change less coherent.
- **No `Settings` field added** — confirmed, `config.py` is untouched in the
  commit — so `test_config_compose_parity.py` is genuinely N/A rather than
  overlooked.
- `DEF215.row.md` is a single row file under `_registry/`, status `done`, per
  CR081.

## MINOR m3 — the m1 guard kills about half the time

MUT-4 (remove `with _schema_lock:` and call `_init_schema_locked` directly —
i.e. reintroduce precisely the defect m1 fixed) does not reliably fail:

```
MUT-4  remove the lock entirely            1 failed, 5 passed     <- his reading
MUT-4  remove the lock entirely (repeat)   killed 2/5 runs
```

**3 of 6 runs overall.** A regression that dropped the lock would go green on
roughly half of CI runs. Baseline is *not* the problem — I ran it 5× and got
`6 passed` 5/5, so there is no flaky-red liability; the guard simply misses.

§"The correction I owe on my own QA" gets the diagnosis exactly right — a
barrier alone does not reproduce it, because on sqlite the first thread
finishes `create_all` before the second is scheduled. The 0.2s pre-delay widens
that window but does not *close* it: both threads still have to be inside
`create_all`'s inspect-then-create gap at the same moment, and whether they are
is still up to the scheduler. The submission reports MUT-4 as a single run and
the QA table records that one result — which is the same methodological trap
the section above it identifies. Having spotted "the mutation is what told me,
not the green run", the next question is *how often* the mutation tells me, and
a timing-dependent kill needs a repeat count before it can be read as a kill.

The fix is to stop timing it and force the interleaving. Instrument the window
instead of widening it: have the patched `create_all` signal a
`threading.Event` on entry and block on a second one, so thread B is *provably*
past the freshness check before thread A creates anything, then release. That
makes the unlocked case fail 5/5 and the locked case pass 5/5, because neither
depends on the scheduler.

MINOR and not higher: the **shipped code is correct** — the lock is right, and
`2347 passed` — and the property it guards is itself the fresh-DB-only,
first-boot-only, unreachable-on-Alpha condition I graded MINOR in round 1. What
is wrong is the confidence the QA table conveys about it.

## m1 — the fix itself is correct

Textbook double-checked locking: memo fast path outside the lock, re-check
inside, body in `_init_schema_locked`. The fast path reads a module global,
which is atomic under the GIL, so there is no torn read to worry about, and the
lock is contended at most once per engine.

**The deadlock I went looking for is not there.** `alembic_command.stamp` now
runs *inside* the critical section, and `stamp` executes `alembic/env.py` — so
if any path from there re-entered `init_schema()`, a non-reentrant
`threading.Lock` would hang the boot silently, which is a far worse failure
than the one being fixed. Two readings say it does not: `env.py` imports
`_resolve_url` and `models` and calls neither `init_schema` nor
`reset_for_tests`, and **AUD-6 (`Lock` → `RLock`) leaves all 6 tests passing** —
if a re-entrant path existed, the plain `Lock` would already be deadlocking the
fresh-path tests. 2347 suite tests drive that path.
