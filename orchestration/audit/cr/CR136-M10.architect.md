## 1. Why this lane exists — and the case for returning it

**Scope note first, plainly:** Rev 4's named audit scope is M02 and M05 only
(`CR136_portfolio_health_metrics.md`, the "Risk class" section: *"Independent
audit remains warranted for the estimator module (M02) and rule engine (M05)
specifically"*). M10 is here on a risk argument raised by Saiful, not on Rev 4's
authority. If the argument below does not hold, **return it as misallocated
effort** — that is a correct verdict, not a failure of the lane.

The argument has four legs.

1. **M10 is the only module in CR136 whose output nothing ever corrects.**
   §3.8 is insert-if-absent *by design*: an existing `(portfolio_id, as_of)` row
   is **never updated** (`script:511-517`). M04/M05/M06/M07 recompute on every
   request; M09 re-renders; M03's tick re-runs daily. A wrong `total_value`
   written by M10 is wrong until someone hand-`DELETE`s it out of Postgres.
   Re-running the script cannot repair it — that is the same property that makes
   it safely idempotent.

2. **The module's one control is price-blind by construction, so it cannot see
   the failure that matters.** `terminal_mismatches` (`script:351-377`) compares
   the walk's holdings and cash against `sim_holdings` / `current_cash`. Both
   sides derive from the trade ledger; **neither involves a price.** The guard
   can print `terminal OK`, `main()` can return 0, and every valuation in the
   series can still be wrong.

   This is not a hypothetical. It is exactly what this module's own audit
   blocker did (`M10_backfill.md` §6b #7, fixed in `18cecc5f`): the price cache
   keyed by ticker alone served a truncated window to a later portfolio,
   **five days valued at the last execution price instead of the market close,
   `terminal OK`, exit 0, and permanent.** The class is proven live in this
   module, one round ago.

3. **A second instance of that same class is still open and ungated.** If Yahoo
   returns nothing for a held ticker — bad symbol, delisted name, rate limit,
   transient 5xx — `_YfinanceProvider` prints `!!` and returns `[]`
   (`script:150-155`; CR040-correct, it refuses the mock fallback). The walk
   then values that holding at **its last execution price for its entire
   history** (`script:326-329`), counts it in `stats["ledger_priced"]`, prints
   the count on the plan line — **and writes, and exits 0.** Nothing in the code
   gates on it. The only control is an operator reading the plan, and §3.10 of
   the module doc telling them to. CR038's rule is that an instruction is not a
   control; an operator protocol is the ops-facing version of the same sentence.

4. **These rows are what a user sees on day one.** M03's `tier2_blocks` reads
   rolling max drawdown and realised return off the `total_value` series, behind
   a 21-snapshot floor. Backfilled rows are precisely what clears that floor at
   go-live — so at launch the Tier-2 tiles are almost entirely this script's
   arithmetic, not the live tick's.

Grounding in the repo's recurring class: DEF210 (Dart enum never mirrored, a
coercion made one entry impersonate another) stayed dark ~10 weeks; DEF038 and
DEF063 each shipped dark for months for want of one `docker-compose.yml` line.
M10's failure shape is the same — nothing goes red — with one aggravation: it is
not repairable by redeploying, because the wrong rows are already written.

**The honest counter-argument, which the auditor should weigh:** the script has
**never been run against production data.** §3.10's protocol (deploy → dry-run
all → real-user spot-check → `--apply` → re-run → SQL sanity) is M11's work and
has not started. Nothing M10 can get wrong is live yet, and every failure above
is gated behind a human running four commands in order. If you judge that the
protocol, not the code, is the real control here — say so and bounce the lane
back to M11.

## 2. What the module is, and the decisions worth challenging

### 2.1 The pure core is the whole module; the DB and the network are seams

`events_from_trades` → `reconstruct_daily_values` → `terminal_mismatches` are
pure (no DB, no network), which is what the unit tests actually exercise.
`_run` is the DB-facing shell; `BackfillPriceProvider` is a `Protocol` with one
method, injected through `main(provider=…)`.

The walk mirrors the live engine deliberately: cash rounds to 2 dp after every
event (`script:259/273`), sells and closes clamp to what is held (DEF166), and
same-timestamp events are ordered by rank (buy-open 0, sell-open 1, buy-close 2)
so a close can never sell shares the walk has not bought yet. The claim being
mirrored is `sim_engine`'s `current_cash = round(…, 2)` — **at HEAD those are
lines 905 and 929**, not the `:891/:915` the module doc and the source comment
both cite (see §2.7c).

### 2.2 The price basis is a pin, and it is enforced structurally

`auto_adjust=False` (`script:138`). An adjusted series rewrites the past; ledger
share counts do not, so an adjusted basis misprices every pre-adjustment day the
moment a dividend or split lands. This is also why M01's `price_history_daily`
is **not** the valuation source (it stores the adjusted close in both columns) —
the seam register's last row.

`get_market_data_provider()` is refused outright: its `FallbackProvider` ends in
a deterministic mock walk, which would silently persist fabricated bars into a
table Tier-2 reads as realised history. §6 of the module doc asked for a **grep**
to prove that; a grep cannot tell an explanation from a call, and the module
docstring names the symbol deliberately in order to say why it is unused. The
real guard is an **AST test** walking every `Name`, `Attribute` and `ImportFrom`
(`test_the_script_never_reaches_for_the_falling_back_market_provider`). Same
substitution for §6's `predicted_vol_ann` grep — replaced by an assertion on
rows actually in the DB, which is strictly stronger.

### 2.3 The dry run really rolls back, and that cost the specified `IntegrityError` catch

§3.8 specified a belt-and-braces per-row `IntegrityError` catch counted as
`skipped_existing`. **It is not implemented, deliberately** (§6b #1). The obvious
implementation is `session.begin_nested()` per row, and under pysqlite a
`SAVEPOINT` implicitly commits the pending transaction — measured, not reasoned:
with `begin_nested()` in place a **DRY RUN wrote all ten rows** and the closing
`rollback()` did nothing. The dry run's promise is the more important property,
so the catch is gone; rows are added, flushed once per portfolio (`script:553`),
and a duplicate aborts the whole run loudly with nothing committed.
`test_a_dry_run_exercises_the_insert_path_and_then_writes_nothing` is what caught
that and is what keeps it caught. **The justification the doc gives for why the
remaining exposure is nil is factually wrong — see §2.7a.**

### 2.4 Insert-if-absent, never update — and what that buys and costs

Buys: a live row (real marks + a real F16 prediction) is never overwritten by a
reconstruction; a second `--apply` inserts 0; gaps left by an outage are filled.
Costs: permanence (§1.1), and the stated reason — *"a prior backfill's row is
byte-identical anyway, by determinism"* (`script:513-516`) — is not true. Yahoo
restates bars. A re-run months later would compute a different close for the same
historical day. The rows are never compared, so the behaviour is right; the
sentence justifying it is not.

### 2.5 Units — `drawdown_pct` on this table is a PERCENT, not a fraction

Worth stating explicitly given CR136's history with units. `drawdown_pct`
(`app/trading_math/portfolio.py:25-32`) returns `(start − value) / start * 100`
— a 0–100 percent, floored at 0 — and that is what M10 writes. It is **not** the
Tier-1 decimal-fraction convention, and it is **not** peak-to-trough: on
$10k→$15k→$12k this column stores `0.0` while the Tier-2 rolling-MDD tile,
computing peak-to-trough from `total_value`, reads `20.0`.
`test_the_drawdown_column_is_versus_starting_capital_not_peak_to_trough` pins
both numbers. M10 is this column's second writer, which is why the warning is
repeated in the module docstring rather than left in M03's.

### 2.6 F16 trio NULL on every backfilled row

`predicted_vol_ann`, `n_observations`, `engine_version` are all `None`
(`script:534-536`). No engine ran historically; a backcast σ back-dated onto
history would be fabricated auditability. `bias_z_stats` skips pairs whose prior
row has a null prediction, so backfilled rows are **structurally** excluded from
the bias z-series rather than excluded by convention.

### 2.7 Where the module doc and the code disagree

Code is truth; each disagreement is recorded here rather than quietly corrected.

**(a) The premise behind removing the `IntegrityError` catch is false — and the
reverse direction is a silent, permanent data loss nobody has written down.**

Both `M10_backfill.md` §6b #1 and the source comment (`script:549-552`) assert:
*"`uq_pvs_portfolio_asof`'s other writer is M03's tick, which only ever writes
TODAY, and today is excluded from the grid by construction."*

M03's tick does not write today. `portfolio_snapshot.py:107` sets
`as_of = resolve_day()` → `_default_trading_day()` →
`price_history.latest_trading_day()` (`price_history.py:485-502`), which returns
the **newest SPY date already stored in `price_history_daily`** — i.e. the last
*ingested* session. For most of any UTC day that is yesterday or earlier (the US
close is ~20:00–21:00 UTC and the row has to be written after it), and it is
yesterday-or-earlier for the whole of every weekend and every holiday. M10's grid
is `[d for d in trading_day_grid(provider, earliest) if d < today]`
(`script:442`). **So the tick's target day is normally INSIDE M10's grid, not
excluded from it.**

Two consequences, and the second is the one I want graded:

- *M03 → M10.* A tick landing between M10's `existing` SELECT (`script:501`) and
  its `session.flush()` (`script:553`) raises `IntegrityError` and aborts the
  whole run with nothing committed. Loud, and the safe direction — but the doc
  claims this exposure is "nil by construction", and it is not.
- *M10 → M03, the silent one.* If M10 writes the row for `latest_trading_day()`
  first, the tick then finds `exists` (`portfolio_snapshot.py:143-151`) and
  **skips that day permanently** — the tick only ever considers the single day
  `latest_trading_day()` returns and has no catch-up loop. That day's row is then
  a backfilled row: valued from Yahoo unadjusted closes instead of the live marks
  the tick would have used, with `predicted_vol_ann = None`. One F16 prediction
  is dropped out of the bias series, silently, every time `--apply` runs while
  `latest_trading_day() < today` — which is the normal case, not the edge case.
  §7's hand-off to M11 says the bias series *"begins at the first live-tick row
  with non-null `predicted_vol_ann`"*; that stays true, but the series acquires a
  hole M11 is not told to expect.

**I did not reproduce this in a run.** It is argued from file:line at
`c56e2c41`; I wrote no repro test and edited no source, because other agents are
reading this tree concurrently. Grade it on the reading, and bounce it if the
reading is wrong.

**(b) §3.4's "cached in-process per ticker"** was amended by §6b #7 to
`(ticker, start)` after the audit blocker. The code matches the amendment
(`script:127/130`); the §3.4 body still carries the superseded phrasing with a
pointer. Recorded, not a defect.

**(c) The doc's `sim_engine.py` line anchors have drifted.** §3.2 cites
`:891/:915` (cash rounding), `:893-916` (`_apply_sell_row`), `:394-403`
(`reset_portfolio`), `:920` (`evaluate_outcomes`), `:970` (`manual_close`).
Measured at `c56e2c41`: 905 / 929, `_apply_sell_row` at 907, `reset_portfolio`

**(d) §3.8's per-row `IntegrityError` catch and §6's two greps** are specified and
not implemented — both disclosed in §6b (#1, #2, #6) with reasons. Noted so the
acceptance checklist is not read as satisfied literally.

**(e) §3.10 has not been executed.** No dry run, no spot-check, no `--apply` has
ever been run against melehost. Measured this session: `curl -m 8
https://api-alpha.agenticmarketintel.ai/v1/health` → **`200`**, so the container
is serving; but `ssh -o ConnectTimeout=6 melehost` → **`connect to host
192.168.20.59 port 22: Operation timed out`** and `curl -m 5

## 5. What I would attack if I were the auditor

1. **`ledger_priced` gates nothing.** `stats["ledger_priced"]` is incremented
   (`script:329`), printed on the plan line (`script:558-560`) — and no branch
   reads it. A ticker Yahoo has no bars for is valued at its last execution price
   for its whole history, written, exit 0, permanent. The terminal guard cannot
   see it (§1.2). Compare with `mismatched`, which does drive exit 2. **If you
   find one thing in this lane, I expect it to be this** — it is the residue of
   the same class as the round-0 blocker, and the only thing standing between it
   and a production row is an operator reading stdout.
2. **The M03-tick collision, both directions** (§2.7a). The silent half —
   M10 pre-empting the tick's own day and permanently costing it one F16
   prediction — is the one I most want a second opinion on, because I derived it
   from `latest_trading_day()` without reproducing it.
3. **`--user-id` spot-check mode can print a series the full run will not
   write.** `earliest` is the minimum over the portfolios *in scope*
   (`script:424-433`), and every price series is fetched from it
   (`script:468`). Under `--user-id` that is the one user's own first event; in a
   full run it is the global minimum, so the series starts earlier and
   `_close_on_or_before` can carry a bar forward from *before* that user's first
   trade. For a portfolio whose ticker has no bar on the first grid day of its
   own range, the two modes diverge — one carries forward, the other falls to
   `ledger_priced`. §3.10 step 3's spot-check is meant to be the evidence for
   step 4's `--apply`; check whether it is evidence about the same numbers.
4. **The empty-grid path exits 0.** Total Yahoo failure ⇒ grid `[]` ⇒
   `trading-day grid: EMPTY — nothing can be valued this run` ⇒ under `--apply`,
   `committed.` ⇒ `return 0`. Loud on stdout, indistinguishable from success to
   anything reading the exit code. Is a run that valued nothing a success?
5. **`_close_on_or_before` returns `(0.0, False)` for "no bar", and the caller
   tests `close <= 0.0`** (`script:286/324`). A legitimately zero or negative
   close is indistinguishable from missing data. Immaterial for US equities;
   confirm it is immaterial rather than assume it.
6. **The exception path contradicts the docstring's exit-code promise.** The
   docstring says under `--apply` exit 2 "does NOT mean nothing was written —
   portfolios that passed the guard are committed". True for the terminal-guard
   path. **Not** true for the `except Exception: session.rollback(); raise` at
   `script:639-641` — one bad portfolio late in the loop discards every earlier
   portfolio's flushed rows. Decide whether that is the intended contract.
7. **`session.flush()` per portfolio, one `commit()` at the end** (`script:553`,
   `:633`). Confirm nothing in the loop can leave the session in a state where
   the final commit writes a partially-applied portfolio.
8. **Test-quality spot check:** `test_the_spot_check_mode_prints_the_whole_series`
   asserts `out.count("10000.00") >= len(_GRID)` — a count of a string, which
   would pass on a wrong series that happened to print that number. Contrast with
   `test_two_books_sharing_a_ticker_each_get_their_own_early_history`, which
   pins exact per-row values. Are there other assertions in this file that would
   survive a wrong number?
9. **Not re-file: DEF211 and DEF212 are deliberately deferred and do not live in
   this module.** DEF211 (zero-variance benchmark leg reaching an unguarded
   raise) is `portfolio_health.py`; DEF212 (one-sided breach-weight ceiling) is
   `portfolio_rules.py` + `portfolio_finding.py`. M10 imports neither. Verified
   by reading their row files this session.
