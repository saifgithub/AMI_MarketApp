### MAJOR-1 — Privacy v2.1 says the summary is not stored, but the preview-path summary is stored verbatim in `http_audit` for 90 days

Privacy v2.1, clause 3 (`website/privacy/index.html:212`, `legal/policies/privacy_policy.md:50`)
says the paper summary is sent with a Room/agent request and with an Alpaca order preview, and:
*"We do not store the summary as its own record; it is used for that request."* The DEF430 row
also says "(not persisted)".

`HTTPAuditMiddleware` captures every non-skipped request body. It redacts only
secret-shaped keys and the key `^alpaca$` (`backend/app/middleware/http_audit.py:94`). The Room
and 1-on-1 overlay rides under `alpaca`, so it is redacted. The DEF419 preview snapshot rides
under **`account`** (`mobile/lib/services/api/api_client.dart:1131`), so it is not. I drove a
real preview body through the real app with `TestClient`, then read the `HTTPAuditRow`:

```
_scrub_secret_fields(preview) -> {..., "account": {"kind": "alpaca_paper", "equity": 104321.5, "cash": 50000.0, "positions": [{"ticker": "NVDA", "qty": 12, "market_value": 2100.0}]}}
_scrub_secret_fields(room)    -> {..., "alpaca": "[REDACTED]"}
POST /v1/sim/preview -> status=401 rows=1 stored={"user_id": ..., "account": {"kind": "alpaca_paper", "equity": 104321.5, "cash": 50000.0, "positions": [{"ticker": "NVDA", "qty": 12, "market_value": 2100.0}]}}
```

The body is captured before the handler runs, so a 200 stores it the same way. `http_audit` is
kept 90 days (`AUDIT_RETENTION_DAYS = 90`, `services/audit.py:32`). Privacy discloses only "basic
request metadata (timestamps, IP address)" for request logs (`privacy/index.html:232`). The
gap predates this lane (DEF419 introduced `account`). But this lane published a policy sentence
it makes false, and this DEF's own acceptance is "policy matches behaviour". CR202's own comment at
`http_audit.py:87-93` names this exact outcome as the thing it prevents.

**Fix direction:** redact `account` on `/v1/sim/preview`. Either widen `_PRIVATE_FIELD_RE`, or add
a path-scoped key, so an unrelated `account` key elsewhere is not swept. Add a test that posts the
real `toMandateSnapshotJson` shape and asserts the stored row has no `equity`, `cash` or
`positions`. The alternative is to change the policy to say it is kept 90 days. That is a wording
decision for Saiful, not a code default.

### MAJOR-2 — the "one-time" notice repeats after the 90-day notifications trim

The notice is idempotent only through `uq_notifications_dedupe`, meaning the existence of the
earlier row. `trim_audit_tables()` deletes `notifications` rows older than 90 days
(`services/audit.py:7-9`, `:48-51`). The sweep runs on **every boot**
(`app/main.py` lifespan). So about 90 days after the first send, the next restart tells every
linked user again that "Privacy Policy updated (v2.1)". That repeats after every later trim,
forever. Probe (real `notify()`, real `trim_audit_tables()`, notice aged 91 days):

```
first=   {'eligible': 1, 'notified': 1, 'already_notified': 0, 'errors': 0}
trimmed= {..., 'notifications': 1, ...}
second=  {'eligible': 1, 'notified': 1, 'already_notified': 0, 'errors': 0}
```

The submission says "at most one policy_update row per user, ever … structurally, not just
empirically". That is true only within the retention window. A notice that re-announces a
policy change that didn't happen is user-facing and misleading.

**Fix direction:** make the once-only marker durable against the trim. Options: exempt
`policy_update` (or this `source_ref`) from `trim_audit_tables`, or record the send on
something not trimmed. A cutoff also works: only notify users with
`alpaca_linked_at < <DEF430 ship date>`, which also ends the every-boot sweep's reason to exist.
Add a test that trims and then re-sweeps.

### MINOR-1 — a live-linked user choosing ALPACA PAPER / BOTH is told the wrong reason

For a live host, `_fetchAlpacaSnapshot()` throws. Both callers (`trade_ticket_sheet.dart:790-800`,
`:966-973`) then show *"Couldn't read your Alpaca paper account — order not sent."* The account
was readable. The truth is that AMI only sends orders to paper accounts. Before this lane, the
user reached `submitOrder`'s explicit "refusing to place an order against a non-paper Alpaca
host". So this is a loud failure with a misleading cause (CR040's shape), and the new
`def419_per_account_test.dart` test pins the misleading text (`:663`). The destination picker is
still offered for a live link (`:1364`, gated on `alpacaLinkedProvider` only). **Fix
direction:** throw a distinct refusal from the paper gate and render "Your linked Alpaca account
is a live account; AMI only sends orders to paper accounts". Better still, hide or disable the
Alpaca destinations when `isLinkedToPaperAccount()` is false.

### MINOR-2 — the order log is not in the Privacy text

CR230's `alpaca_order_audit` stores symbol, side, qty, order type, prices, bracket, Alpaca order
id and status for every paper order and cancel. It is **excluded from the 90-day trim**, so it is
permanent (`db/models.py:2815-2830`). Privacy v2.1 describes routing (Terms §1) and the summary,
but not this log. Its "we record only that, and when, you linked an account" reads as the full
list. Graded MINOR because it covers paper activity the user initiated, and the DEF row scoped
the snapshot and routing. It is still a gap in the same policy paragraph, and permanent
retention is the part a reader would most want to know. **Fix direction:** one sentence in
clause 3 and in clause 9's retention list, same as MAJOR-1's wording decision.

### New findings

#### MAJOR-A — the preview response stores the paper account's cash and a position's quantity in `http_audit` for 90 days

`preview_trade` returns `cash_available=pv.cash_available` and
`held_quantity=pv.held_quantity` (`backend/app/api/sim.py:732-733`). On the snapshot path these
are the Alpaca paper account's own cash and position size (`sim_engine.py:2785-2786`, from
`sizing_cash = snap.cash` and the snapshot's holdings). The insufficient-cash refusal also
writes the cash into its text (`sim_engine.py:2765`). The middleware stores the response body
(`http_audit.py:256`). The scoped regex only matches the key `account`, so none of this is
redacted. Real app, real stored rows:

```
buy 1 NVDA   response_body= {..., "cash_available": 50000.0, "held_quantity": 0.0, "account_kind": "alpaca_paper", ...}
sell 5 MSFT  response_body= {..., "cash_available": 50000.0, "held_quantity": 12.0, "account_kind": "alpaca_paper", ...}
buy 500 NVDA violations= ['insufficient cash: need $73595.00, have $50000.00']
```

A concentration refusal also stores the percentage next to the notional
(`"position size 14109.3% exceeds single-name cap 150.0%"`, `notional: 14719000.0`). Equity
can be recovered from those two numbers.

**Failure scenario:** a linked user previews an order to their Alpaca paper account. For 90
days, `http_audit.response_body` holds their paper cash, the quantity they hold of that ticker,
and the account type. Privacy v2.1 clause 3 says "We do not store the summary as its own
record; it is used for that request." Cash and a position's quantity are fields of that summary.
This is the same sentence, the same route and the same data class as round-1 MAJOR-1. No test
covers it: mutation M9 (response scrub removed entirely) survives.

**Fix direction:** on `/v1/sim/preview`, when the request carried `account`, do not keep the
response body (store `[REDACTED]`, as `SCRUB_PATHS` does). Scrubbing single keys is weaker,
because the violation strings carry the numbers too. Add a test that reads the stored
`response_body` for a snapshot preview. The alternative is policy wording that admits a
90-day request log. That is Saiful's call, as in round 1.

#### MINOR-A — the scoped redaction matches the exact path only

`_PATH_SCOPED_PRIVATE_FIELDS.get(path)` (`http_audit.py:130`) is an exact dict lookup. A POST to
`/v1/sim/preview/` gets a 307 redirect, and the middleware stores the full snapshot before
redirecting:

```
SLASH STORED (307, 'account=x', '{..., "account": {"kind": "alpaca_paper", "equity": 104321.5, "cash": 50000.0, "positions": [{"ticker": "MSFT", "qty": 12, ...}]}, ...}')
```

The shipping client sends `/v1/sim/preview` without a trailing slash (`api_client.dart:1121`),
so today's app does not hit this. It becomes live if a client build, a proxy, or a later route
variant adds the slash. **Fix direction:** normalise the path before the lookup
(`path.rstrip("/")`), or redact `account` whenever `account.kind` is present.

#### MINOR-B — the new order-record sentence says three things the code does not do

The sentence: "When you send an order to your Alpaca paper account through AMI, we keep a record
of that order (...) so you and we can see what was sent; this record is kept for as long as your
account exists."

1. **More than sent orders are recorded.** `outcome` also takes `refused_client_side` (the
   order never left the phone), `rejected_by_alpaca`, a `network error`, and `cancelled`
   (`schemas/alpaca.py:110-112`; `trade_ticket_sheet.dart:1135,1146,1156`,
   `alpaca_orders_section.dart:248,259`). `detail` stores Alpaca's rejection text.
2. **"So you … can see" is not true.** Nothing reads `alpaca_order_audit`. The only code that
   touches it is the writer (`services/audit.py:250`). There is no route and no screen for the
   user. The in-app order list reads Alpaca directly.
3. **"For as long as your account exists" is not enforced, and one path breaks it.**
   `alpaca_order_audit.user_id` has no foreign key and no cascade (`db/models.py:2838`). An
   anonymous-to-existing-account merge deletes the anonymous `User` row
   (`merge_service.py:562`). It does not move these rows, so they stay under a user id that no
   longer exists. **Failure scenario:** a user links Alpaca while anonymous, places paper
   orders, then signs in to an existing account. Later they ask for deletion. Support deletes by
   their current user id, and the orphaned order rows survive. The record outlives the
   account, which is the opposite of what the sentence promises.

**Fix direction:** reword to "orders you send, cancel, or that are refused", drop "you and",
and either move the rows in `merge_service` or say the record is kept permanently. The
architect already flagged that deletion is a support process, not code. Part 3 is a concrete
case where that process would miss rows.
