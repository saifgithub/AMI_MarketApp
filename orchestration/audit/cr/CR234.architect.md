# CR234 — audit lane (Alpaca orders view: list/cancel/history + shared Alpaca identity)

**SCOPE:** cr (mobile-only for the identity/layout half; one narrow backend enum widening
for the cancel-outcome audit log)

**TIER: A.** `AlpacaClient.cancelOrder()` sends a `DELETE` against a live-linked (paper)
brokerage account — a write, same class of risk CR227/CR233 were routed to independent
audit for (D-071/D-074: a live account must stay read-only; paper writes are permitted
but must be structurally, not just conventionally, confined to a paper host).

**SHA:** worktree branch `worktree-agent-ae0ad9ca83ed14fb1`, based on `main`'s `1444baee`.
Review with `git diff 1444baee..HEAD`. Not yet merged to `main`, not pushed, no build bump.

**depends-on:** CR233 (`in_progress`, real Alpaca order types — this CR is its read/cancel
half), CR230 (`done`, the order-log audit table this CR's `cancelled` outcome extends),
CR202 (`done`, device-custody Alpaca account/positions — this CR's scope-addition half
reworks that section's rendering only, not its data flow). **Promoted:** no.

## What and why

Saiful, verbatim (2026-09-25, TestFlight +110): *"I am not seeing orders from alpaca in
the orders section after putting a limit buy."* Verified by the Architect before this
lane started: the order reached Alpaca and is resting there — the CR230 audit table shows
an ASML buy 10, `order_type=limit tif=gtc limit=1700.00 bracket_stop_loss=1619.15
bracket_take_profit=1946.42`, `alpaca_status=accepted`. CR233 gave `AlpacaClient` real
order types but never gave it a way to list or cancel one — this CR is that missing half.

**The fix:**
- `AlpacaClient.orders({status, limit, nested})` — `GET /v2/orders`; `nested: true`
  inlines a bracket's child legs under the parent.
- `AlpacaClient.cancelOrder(id)` — `DELETE /v2/orders/{id}`; re-checks `isAlpacaPaperHost`
  itself before any network call (same posture `submitOrder` already has), refuses on a
  non-paper host or unlinked device.
- `AlpacaOrder` gains `type`/`filledQty`/`limitPrice`/`stopPrice`/`timeInForce`/
  `submittedAt`/`legs`; new `isClosed`/`isCancellable` getters.
- Orders tab: `AlpacaOpenOrdersSection` — Alpaca's OPEN orders under AMI's own resting
  book, cancel action (confirm → DELETE → refresh both Alpaca providers → best-effort
  audit report, `outcome: cancelled`, backend enum widened to accept it).
- History tab: `AlpacaHistorySection` — Alpaca's CLOSED orders (last 50).
- CR040 throughout: an unreachable Alpaca surfaces a visible error row on both tabs,
  never an empty list.

**Scope addition, same session** — a TestFlight screenshot Saiful sent mid-review showed
the PRE-EXISTING (CR202) Alpaca account/positions section as a visibly inconsistent,
lesser design versus AMI's own: plain-text `'ALPACA PAPER'` header + green dot (no badge);
a `Container` with three `_AlpacaStat` columns where BUYING PWR ($362,137.57) wrapped onto
two lines; Alpaca positions as bare `Row`s of plain `Text` — no card, no chevron, no %
change, no stop indicator — against AMI's own `_ValueCard`/`_HoldingCard` treatment
(animated headline, LIVE pill, card positions with chevron/expand/stop chip). Saiful:
*"The alpaca section needs to be done along the same design as the rest, but with a clear
indicator for alpaca paper."*

**The scope-addition fix:**
- `PositionCard` (`widgets/sim/position_card.dart`) — extracted from `_HoldingCard`'s
  visual shell; every fact is now a primitive/widget-slot parameter. `_HoldingCard` (AMI)
  and the new `AlpacaPositionCard` both build on it.
- `ValueCard` (`widgets/sim/value_card.dart`) — extracted from `_ValueCard`'s shell;
  headline is a WIDGET slot (not a formatted string) specifically so AMI's
  `TweenAnimationBuilder` count-up plugs in with zero behavioural change; two stats
  layouts (`inline` = AMI's original 2-stat row, `columns` = Alpaca's original 3-stat
  block) rather than forcing one shape onto both.
- `AlpacaBadge`/`alpacaAccent`/`kAlpacaPaperLabel` (`widgets/alpaca/alpaca_badge.dart`) —
  the one identity every Alpaca surface uses, including the trade ticket's 9
  destination-label call sites (mechanically replaced, same literal string, no behaviour
  change).
- `AlpacaAccountCard`/`AlpacaPositionCard` (`widgets/alpaca/`) — build on the shells above;
  `AlpacaPositionCard`'s stop chip reads Alpaca's own open bracket orders
  (`alpacaOpenOrdersProvider`, matched by symbol), never invented.
- Tab-bar counts (`_PortfolioTabBar`) stay AMI-only, a documented decision (async Alpaca
  counts would otherwise show a number that changes shape mid-load — the "quietly wrong
  count" CR040 forbids).

Design note: `docs/forward_planning/CR234_alpaca_orders_view/CR234_alpaca_orders_view.md`.

## Attack surface (please probe)

1. **Cancel writes to a live account** — the exact CR227/CR233-class risk, now on a second
   write path. Confirm `cancelOrder()` genuinely checks `isAlpacaPaperHost` BEFORE
   `_dio.delete`, not merely before returning a friendly error after the call — the fake-
   adapter test asserts zero calls on refusal; verify that holds under a mutation of the
   check order (move the host check after the `_dio.delete` line and confirm a test fails).
2. **Cancel-outcome audit completeness** — confirm every `cancelOrder()` call site
   (`_AlpacaOrderCard._cancel` in `alpaca_orders_section.dart`) reports EXACTLY ONE audit
   row per attempt (success → `cancelled`, failure → `rejected_by_alpaca`), and that a
   throwing report call cannot surface to the user as a cancel failure (the report is
   `unawaited`/best-effort, same posture CR230 already established for submits — confirm
   this file's cancel path actually follows that pattern rather than `await`ing the report
   before showing the success snackbar).
3. **Race: cancel vs. a since-filled order** — `isCancellable` excludes `pending_cancel`
   and every closed status, but the UI's cancel button visibility is computed from the
   LAST FETCHED list, which can be stale by the time the user taps it. Confirm the
   catch-block on a 422/404 (Alpaca's own "already filled/cancelled" response) still
   refreshes both providers so the user sees the corrected state, not a UI that still
   shows a cancel button for an order that no longer exists.
4. **Identity-badge accent collision** — confirm `AmiColors.hexPurple` genuinely carries no
   conflicting meaning elsewhere ON THE PORTFOLIO SCREEN specifically (not just
   app-wide) — re-derive independently from `portfolio_screen.dart` rather than taking the
   CR doc's word that cyan/green/red/amber are the only accents in play there.
5. **AMI-rendering-unchanged claim** — verify by diff, not by trusting the "full suite
   passed" claim alone: confirm `git diff` on `_ValueCard`/`_HoldingCard` in
   `portfolio_screen.dart` shows ONLY the extraction (calling into `ValueCard`/
   `PositionCard`) and no incidental behavioural change (e.g., the P&L row's `Flexible`/
   `ellipsis` guards, the CR170 committed/available block, the CR189 stop/target distance
   lines) — these are load-bearing DEF/CR fixes from prior work and must survive the
   refactor verbatim.
6. **Overflow coverage genuinely representative** — the 320/375/430dp × 1.0x/1.3x matrix
   is asserted via `tester.takeException()` after a real `RenderFlex` layout pass, not a
   golden image — confirm this is a meaningful guard (i.e. that the PRE-fix code actually
   throws under `pumpWidget` at these sizes, which the mutation check above already
   establishes for `PositionCard`) and probe whether `AlpacaAccountCard`'s `FittedBox`
   headline could still clip unreadably small at 320dp×1.3x even though it does not
   overflow (a passing exception-check does not guarantee legible text size).
7. **Tab-count decision** — confirm the inline documentation at the `_PortfolioTabBar`
   call site actually matches what ships (AMI-only counts), and that no other surface in
   the app (push notifications, a badge elsewhere) implies a combined count that this
   change would now contradict.
8. **DEF145 guard robustness** — confirm the reworded schema comment (removing the literal
   `/v2/orders` string) doesn't just dodge THIS iteration of the grep-based guard while
   leaving the underlying invariant (backend never talks to Alpaca's order endpoints)
   equally true — re-derive that the backend genuinely has no code path to Alpaca's REST
   API for orders, independent of the comment wording.
