## What and why

CR228's Step 1 pilot (30-ticker paired A/B, `risk_score` 1 vs 5, everything else identical, fresh
users to bypass `resolve_mandate`'s override-ignoring gotcha) measured a real but far-too-narrow
risk-appetite effect: approve rate 3.4% (R1) vs 24.1% (R5), McNemar p=0.031 — both far below the
Street's 60.0% Buy-or-better on the same sample. The pilot's own before/after analysis attributed
the effect to `DEFAULT_RISK_TIER_CAPS` (`trading_math/sizing.py:22`) via CR197's option-generation
mechanism (the PM approves more because a wider debate spread hands it a bigger menu of sizes, not
because its own judgement changed — the PM prompt is byte-identical across risk tiers, verified in
the pilot). Saiful's sequencing for the fix (2026-09-22): widen the cap table first, then the PM
prompt (Step 3), then a structural graded-vote threshold (Step 4).

This submission is Step 2 only: widen the cap table, and widen `_derive_risk_score` per Saiful's
explicit input selection (`max_drawdown_pct`, `horizon`, `primary_goal`; `compliance` excluded).

## Change 1 — `DEFAULT_RISK_TIER_CAPS` widened, five distinct values

`trading_math/sizing.py:22` (line number pre-change) was
`{1: 1.5, 2: 1.5, 3: 3.0, 4: 4.5, 5: 4.5}` — five risk-slider positions, three enforced single-name
caps (tier 1≡2, tier 4≡5 collapsed). Now `{1: 1.0, 2: 2.0, 3: 3.0, 4: 4.0, 5: 5.0}` — five distinct,
evenly-spaced values. Tier 3 (the default/no-onboarding-yet fallback) is unchanged at 3.0%, so
`test_resolved_sector_cap_matches_default_risk_tier_preset`'s pinned expectation for a bare mandate
needed no update.

**Why the ceiling is 5.0 and not higher.** `DEFAULT_MAX_OPEN_RISK_FRACTION_OF_DRAWDOWN`
(`trading_math/risk_limits.py`, deliberately left unchanged — see "Scope discipline" below) couples
the single-name cap to `DIVERSIFICATION_FLOOR`'s "≥30 names reachable" invariant via
`_names_reachable` (`test_cr129_risk_limits_from_risk_tolerance.py`). I computed the reachable count
at each candidate tier-5 ceiling before picking one: 5.0% still clears the floor (30 names reachable,
exactly at the floor); 5.1% breaks it (29). Verified by mutation below.

## Change 2 — `_derive_risk_score` widened beyond the three scenario answers

`services/concierge_engine.py:456` (pre-change) used only `risk_components_partial`'s three fields
(`drawdown_response`, `regret_asymmetry`, `concentration_tolerance` — Q3-Q5). Now also reads
`max_drawdown_pct` (Q6), `horizon` (Q2), and `primary_goal` (Q1) from `session.answers` when
present, applying each as a bounded nudge (±0.5 per input, divided by however many of the three are
available) around the unchanged scenario-derived base. `compliance` (Q7) was explicitly excluded —
Saiful's selection, not an oversight.

**The backwards-causality fix.** `q6_text` (line 100) uses the risk score to *suggest* a drawdown
percentage to the user — that direction is unavoidable, since Q6 IS the question that produces
`max_drawdown_pct`, so `session.answers` has no value for it yet at that call site (verified,
`test_cr228_q6_suggestion_uses_scenario_only_base`). But the **readback** score (computed after Q6
*and* Q7 are both answered, `_build_readback_summary` → `_derive_risk_score`) previously never read
the user's actual Q6 answer at all — a user offered "50% sounds like a fit" who explicitly picks "No
cap" saw that override respected for `max_drawdown_pct` itself, but their implied risk preference
never fed back into `risk_score`. It now does (`test_cr228_disagreeing_drawdown_answer_nudges_the_score_at_readback`).

**Why the nudge is bounded, not a replacement formula.** The three Q3-Q5 scenario answers are the
most deliberate risk-preference measurement the interview has (specific loss/regret/concentration
scenarios, not a single tap). I did not want three maximally-aggressive-signalling new inputs
(short horizon, learning-to-trade goal, no drawdown cap) to be able to override three
maximally-conservative scenario answers on their own —
`test_cr228_scenario_answers_remain_the_dominant_signal` pins exactly that: the most aggressive
values on all three new inputs, against the most conservative scenario answers (which alone
resolve to risk_score=1), reach at most 2, not 5.

## The finding I most want attacked

**Does the tier-5 single-name cap ceiling (5.0%) genuinely preserve
`DIVERSIFICATION_FLOOR` for every `max_drawdown_pct` value, or only for `base_mandate`'s 30%?**
`resolved_max_open_risk_pct` scales the open-risk budget as `fraction * max_drawdown_pct` — a user
with `max_drawdown_pct=10` (the most conservative Q6 answer, `Literal[10,20,30,50,100]`) has budget
`0.50 * 10 = 5.0pts` at tier 5, and `_names_reachable` at the new 5.0% cap would be
`floor(5.0 / (5.0*10/100)) = 10` — **below the 30-name floor.** I did not add a test pinning this
cross-product (tier x `max_drawdown_pct`), and `test_cr129_risk_limits_from_risk_tolerance.py`'s
existing parametrisation only exercises `base_mandate.max_drawdown_pct=30`. **I believe this is a
pre-existing gap, not one this commit introduces** — the OLD table (tier-5 cap 4.5%) has the exact
same arithmetic problem at `max_drawdown_pct=10` (`floor(5.0/(4.5*10/100))=11`, still below 30) —
but I have not verified that claim against the actual guard code path (only against the formula by
hand), and I did not go looking for it before this CR touched the same table. Attack this: is
`DIVERSIFICATION_FLOOR` actually enforced anywhere at runtime for a low-`max_drawdown_pct` /
high-`risk_score` mandate, or does the guard test's single fixed `max_drawdown_pct=30` mean the
floor has silently never been checked for the users most likely to violate it?

## What changed and why

`_vote_pm_samples` (`services/room_runner.py:6640`) is the CR197 mechanical aggregator that picks
one verdict from N independent CIO reads when `pm_self_consistency_samples > 1` (production
default 5, CR214). Before this round, APPROVE needed a flat strict majority (`n // 2 + 1`)
regardless of the mandate's risk_score, and any tie fell to PASS uniformly
(`room_runner.py:6634` in the original CR228 plan doc's line numbering — the exact "structural
bias toward not trading that no risk setting adjusts" the plan named as reason #5 for the drought).

New `_approve_vote_threshold(risk_score, n)` grades that bar:

- risk_score ≤2: `majority + 1` — a clean super-majority, not just "more APPROVEs than PASSes."
- risk_score 3: `majority` — unchanged, byte-for-byte the original arithmetic.
- risk_score ≥4: `majority - 1` — a near-tie is enough, directly fixing the asymmetry.
- Clamped to `[1, n]` in all cases.

`_vote_pm_samples` takes a new `risk_score: int = 3` parameter — the default reproduces the
pre-CR228 behaviour exactly, so every existing caller (both pre-existing test files below) is
unaffected without being touched. The one production call site
(`room_runner.py:~5533`) passes `risk_score=ctx.mandate.risk_score` — the same mandate the run is
for.

**Why this is different in kind from Step 3.** Step 3's PM prompt line is, by its own README
section, "a hypothesis, not an assumed fix" — CLAUDE.md's "prompt instructions are not controls"
means it needs an ablation to be credited with any effect at all. Step 4 is the structural
counterpart: it is the vote-counting arithmetic itself, so it holds regardless of how well any
model complies with anything upstream of it. It only engages once
`pm_self_consistency_samples > 1` — at the production default of 5, the three tiers are 4/5
(conservative), 3/5 (neutral), 2/5 (aggressive): distinct and monotonic, verified never to
collapse to the same number at that specific n (see tests below), which is the n that actually
ships.

**Scope discipline kept:** `_PM_ACTION_SYNONYMS` (unchanged, `room_runner.py:1980`) collapses
every raw model action string down to exactly `{APPROVE, PASS}` before it ever reaches
`_vote_pm_samples` (MODIFY also maps to APPROVE at the synonym layer; REJECT/WAIT/HOLD/NO all map
to PASS). So in every real call, `_vote_pm_samples`'s `parsed` list only ever contains those two
actions. I did not assume that invariant silently, though — the graded-threshold branch only
engages `if set(actions) <= {APPROVE, PASS}`; anything else (there is currently no path that
produces it) falls through to the original `Counter`-based plurality-with-tie-to-PASS logic,
completely untouched. `DEF059`'s "an uncertain path must never mint a confident buy" is preserved
at every tier: even the aggressive bar still requires the approve side to be at least equal to the
threshold, never automatically win a flat tie below it (n=4, `risk_score>=4` needs 2, a genuine
2-2 split has approve_votes=2 which meets it — that specific case is called out and pinned
explicitly in the tests, not glossed over, because it's the one place "ties now sometimes go
APPROVE" is real and worth your attention).
