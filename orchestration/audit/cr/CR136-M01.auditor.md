## MAJOR A1 — `fetch_failed` is true on one path and false on three, and all four are the feed

§2.5 calls `fetch_failed` "the CR040 answer to 'feed down' vs 'young security'".
It answers for the caller that *made* the failing attempt. Every other caller is
told the other thing, and `_FETCH_FRESH_WINDOW_S` is **21600 — six hours**.

Feed down, one ticker, successive card opens, clock advancing:

```text
 t (mins)  dates  fetch_failed   what the caller concludes
        0      0          True   our feed is down          <- correct
        1      0         False   this security is young
       30      0         False   this security is young
      120      0         False   this security is young
      359      0         False   this security is young
      361      0          True   our feed is down          <- window expires
```

The stamp is written *before* the network call and `_should_fetch` consults it,
so for 359 of every 360 minutes the module returns an empty series carrying
`fetch_failed=False`. Two more paths land in the same place:

```text
two simultaneous opens, cold ticker   thread 0: 200 dates, fetch_failed=False
                                      thread 1:   0 dates, fetch_failed=False
provider serves 200 bars, 160 NaN     40 dates, fetch_failed=False   (attack 3)
provider serves 200 bars, 200 NaN      0 dates, fetch_failed=True    (caught)
```

`fetch_failed` is set only when *this* call produced nothing at all. A sibling
throttled by an in-flight attempt, a caller inside the six-hour window, and a
partially-garbage fetch are all feed failures and all report `False`.

**Where it lands.** `portfolio_health.py:279` selects
`FEED_UNAVAILABLE_DROP_REASON if p.ticker in feed_failed`, and `feed_failed` is
built from `daily.fetch_failed` (`:759`). So the holding is dropped with
`short_history`. The constant's own comment states the defect:

> CR040: a feed outage and a genuinely young security are NOT the same fact, and
> telling a user "not enough price history for this holding" when the truth is
> "our feed is down" is the wrong answer to the question that rule asks.

That is verbatim what ships for six hours after every feed hiccup.
`FEED_UNAVAILABLE_DROP_REASON` is reachable by one request in 360.

MAJOR rather than BLOCKER because the card still renders a degraded state rather
than a confident wrong number — the user is given the wrong *reason* for a
correct refusal, not a fabricated measurement.

The shape of the fix is yours to choose, but the fact the module is missing is
"a fetch was attempted for this ticker and did not produce usable history",
which is not the same fact as "this call attempted and got nothing". Note the
partial-garbage path needs the rejection count on `DailySeries` that attack 3
already asks for — one datum closes both.

## MAJOR A2 — attack 1 is real: no exception handling on the write path

Your reasoning holds and the mechanism is proven. `upsert_daily_bars` SELECTs
the affected dates and inserts what is missing; two callers whose reads both
land before either commits therefore both INSERT:

```text
B's read phase sees 0 existing rows -> it will INSERT
A completes and commits: {'inserted': 30, 'updated': 0, 'skipped': 0}
B flushes:  sqlalchemy.exc.IntegrityError
            UNIQUE constraint failed: price_history_daily.ticker, price_history_daily.date

price_history.py mentions IntegrityError: False
price_history.py imports sqlalchemy.exc:  False
```

End to end through the real function, with the check-then-set window widened by
a barrier inside `_should_fetch` (nothing else changed):

```text
thread 1 returned 200 dates
thread 0 RAISED sqlalchemy.exc.IntegrityError
```

That propagates through `build_health_context` → `asyncio.to_thread` → the
tiles route, whose own docstring commits to the opposite: *"A mock-mode refusal
or an all-insufficient book still returns 200: a 5xx would hide the amber state
from the card, which is the CR040 question answered the wrong way."*

**Reachability, measured rather than argued — and narrower than §attack-1 says.**
Sixty trials, two threads released from a barrier onto a cold ticker, no
patching:

```text
trials where BOTH threads passed the throttle and fetched: 0 / 60
exceptions raised: 0
```

The window is the gap between `_should_fetch` returning and
`_last_fetch_attempt[ticker] = now` — `_build_series` plus a session commit, so
milliseconds, not microseconds, but one thread still wins every time at this
concurrency. Your "both fetch on promote day" is not what a single process does.

It is what **two processes** do. `_last_fetch_attempt` is per-process, the
Dockerfile runs one uvicorn with no `--workers`, and CLAUDE.md's stack decision
for Beta is **GCP Cloud Run** — instances there do not share the dict, so the
throttle stops protecting the constraint the day a second instance exists. Two
users on two instances hitting a cold ticker is not a race; it is the
common case, and every evaluation fetches SPY.

MAJOR: the write path has no exception handling at all, M03 in this same CR
already has the answer (`portfolio_snapshot.py:192`, `except IntegrityError:`
with the comment "a concurrent tick losing this race is a skip, not a failure"),

## MINOR m2 — attack 6 measured: the volatility scaling silently becomes a fixed rule

bound = max(15.0 * sigma, 0.10) = 0.1000        <- collapses to the floor

whose volatility it was meant to adapt to, and §2.8's calibration evidence
(12 liquid large-caps and ETFs) cannot contain a MAD=0 name by construction.

## A2 — fixed, including the case the patch shape could have missed

```text
(a) IntegrityError raised at the upsert call site   -> returned normally, no propagation
(b) two real threads past the throttle              -> 200 / 200 dates, 0 exceptions escaping
(c) `with get_session()` sits INSIDE the try         -> True
```

(c) is worth stating: `upsert_daily_bars` can raise on the session's **commit**,
inside `get_session().__exit__`, not on the call itself. The `try` opens before
the `with`, so that path is covered too. A patch that wrapped only the function
call would have looked identical and caught nothing on Postgres.

My round-1 end-to-end probe needed the window widened by a barrier; that is no
longer constructible through the public function, because the pessimistic
`_last_fetch_attempt` set means the loser never reaches the provider. Hence (a) —
inject the exact exception at the exact call site. Note for the record that (a)
returns 0 dates: that is an artefact of injecting inside the winner's own
session, which rolls back. In the real race the winner committed in a different
session, which is precisely why `upsert_daily_bars` treats a unique violation as
"someone else wrote these same bars".

## MINOR m4 — a caller with a smaller `min_days` clears the sticky flag

The flag is per **ticker**; both the gate that reads it (`:432`) and the branch
that clears it (`:529`) are scoped to the **calling** `min_days`.

```text
A min_days=126 t=0    (fetch)      40 dates  fetch_failed=True
B min_days=20  t=400  (fetch)      40 dates  fetch_failed=False
                                   _last_fetch_failed still holds the ticker: False

```

B got what it asked for, so B reading `False` is right; what is wrong is that B's

shorter window — a watchlist sparkline, a backfill — and it reopens a MAJOR
silently. Keying the flag on the shortfall rather than on the caller's threshold
(or storing the observed `rejected`/`dates` and letting each caller decide) is
the shape that does not have this edge.

## Measured and NOT graded

**A1's inverse exists in the rule, and its trigger does not occur on live data.**
`rejected > 0 and len(dates) < min_days` means a short security carrying a single
unusable close reads as a feed failure:

```text
125 usable days + 1 NaN, min_days=126  ->  dates=125, fetch_failed=True
```

That is A1 pointed the other way — a genuinely young security told "our feed is
down". Before grading it I measured how often the trigger fires on the provider
that actually serves this system:

```text
17 tickers x 2y of live Yahoo (SPY AAPL MSFT XLU HPQ DIS BAC SCHD ARM CAVA
RDDT BIRK SMR IONQ RIVN LCID PLTR)
  8,534 bars, unusable closes: 0
  tickers with >=1 unusable close: 0/17
```

Zero. So `rejected` is a correct discriminator against a garbage-serving
provider and is inert against this one — which also means A1's third path
(attack 3) is theoretical while paths 1 and 2 are the live ones, and those are
closed by the sticky flag alone. Not a finding; recorded so nobody re-derives it.

**AUD-M1 survived, and its regression is inert.** Removing the
`len(series.dates) < min_days` gate on the sticky read passes all 46. I traced
the consequence rather than assuming one: `DailySeries.fetch_failed` has exactly
one consumer in the app (`portfolio_health.py:780`), which feeds the `feed_failed`
set, read at `:279` for a *dropped* holding's reason and for `bench_feed_failed`.
A holding with enough history is not dropped, so an over-set flag reaches
nothing. Unpinned refinement, no reachable consequence.
