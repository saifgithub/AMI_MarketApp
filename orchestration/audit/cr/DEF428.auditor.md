# DEF428 — auditor verdicts (onboarding Q6 typed drawdown answers)

## Round 1 — auditor u66

**SHA audited:** `6a66be08` (the architect's follow-up on top of the merge `cc70d55f`). Diff
reviewed as `b5de455c..6a66be08`. Audited in a detached scratch worktree `DEF428-u66` per
DEF159. Probes ran from that worktree and were removed afterwards. The worktree was verified
clean before the suite ran.

**Tier A.** The submission says it becomes Tier A if a MAJOR is found, and one is.

### The question this lane has to answer

The goal is: a number the user types at Q6 becomes the drawdown limit they actually trade under.
If it can't, the user is told so. It must never silently become 30%. The lane's tests stop at
`session.answers`. None of them follows the value to the place it becomes a mandate. So I drove
it there.

### MAJOR-1 — accepted off-grid values fail at claim and fall back to 30% silently

`Mandate.max_drawdown_pct` is `Literal[10, 20, 30, 50, 100]` (`app/schemas/mandate.py:203`).
This lane made `_parse_drawdown_pct` accept any value in `(0, 100]`. Both places that persist
the interview call `Mandate.model_validate(session_to_mandate_dict(...))` with no guard:
- the claim (`app/api/auth.py:94`, `_bind_onboarding_session`);
- the restart confirm (`app/api/onboarding.py:147-150`).

I drove this for real. `process_answer` ran at Q6, then a magic-link claim went through the
real `auth` router with the DEF060 harness:

```
typed='20%'   stored_answer=20    claim_status=200                    mandate_dd=20
typed='45%'   stored_answer=45    claim_status=RAISED ValidationError  mandate_dd=None
typed='5%'    stored_answer=5     claim_status=RAISED ValidationError  mandate_dd=None
typed='12.5%' stored_answer=12.5  claim_status=RAISED ValidationError  mandate_dd=None
typed='40%'   stored_answer=40    claim_status=RAISED ValidationError  mandate_dd=None   (chip; pre-existing, see below)
```

The retry makes it worse. `_bind_onboarding_session` saves `claimed_user_id` *before* it
validates. So the second call hits the idempotency early-return and never tries again:

```
RETRY first=ValidationError second=ok (returned) stored=None effective_dd=30 claimed=True
```

In practice:
1. A user types "45%".
2. The readback shows "Max drawdown 45%", and the user confirms it.
3. The claim returns a 500.
4. From then on the user trades under `get_or_default`'s **30%**.

Nothing tells them. This is the outcome DEF428 was filed to remove, now reached through a crash.
Before this lane, the same input gave a silent 30% with no crash. After it, the user gets a
crash, then still the silent 30%.

**Fix direction (the architect's call):** the parser's accepted set must be a subset of the
schema's Literal, or the Literal must widen. Widening touches `risk_limits`, the PATCH
validator and the DEF062 422 test, and I don't recommend doing it inside a Tier-B defect. If an
off-grid number is typed (5, 45, 12.5), don't snap it quietly to a chip. Re-ask and name the
choices the product actually supports, since snapping is a fabrication too. Either way, a
test has to drive every accepted Q6 value through `session_to_mandate_dict` →
`Mandate.model_validate`. That makes "parser output ⊆ schema" a property, not a hope.
Separately, `_bind_onboarding_session` should not mark the session claimed until the mandate
has persisted. Otherwise any future validation failure is also permanent and silent.

### MINOR-1 — the "does not advance" guarantee is client-trusted

The architect asked for this in attack-surface item 2. `submit_answer`
(`app/api/onboarding.py:71-99`) passes `req.step` straight to `process_answer`. It never
compares that to `session.current_step`. A client stuck on Q6 can post `step=Q7_CONSTRAINTS`
and move forward. `max_drawdown_pct` is then absent, and `_build_readback_summary`'s
`.get("max_drawdown_pct", 30)` shows and stores 30. The shipped mobile client posts the step it
was given, so this needs a misbehaving client. It isn't reachable in normal use. It is still
the same fabricated default, and the re-ask can't stop it.

### Recorded, not scored — the "40%" chip was never persistable

`Q6_CHIPS` offers "40%" and `_DRAWDOWN_PCT_TO_TIER` maps 40. The mandate Literal has no 40.
Tapping the chip fails at claim in exactly the way MAJOR-1 describes. This predates the lane:
before it, `"40" in t` → 40 did the same. Most likely it arrived with DEF418's five-tier
widening.

This lane's `test_def428_chip_values_still_all_parse_and_advance` asserts that 40 parses and
advances. So it certifies a chip that can't be saved. If MAJOR-1 is fixed with the subset
property, that fix covers this too. If it's fixed any other way, this needs its own DEF.

### The other attack-surface questions

1. **First number wins** ("between 20% and 30%" → 20): I agree. Taking the lower, stricter bound
   of a range is conservative. Probes: "10-15%" → 10; "10,000%" → `None`; "-10%" → `None`;
   "$10,000" → re-ask; "5k" → re-ask. A nit: "1,5%", with a comma as the decimal point, reads as 5.
3. **Rounding to one decimal place:** this is moot while the Literal holds. `12.5` can't be
   persisted at all (MAJOR-1).
4. **`_DRAWDOWN_PCT_TO_TIER.get(dd, 3)` for an off-grid value:** also moot under MAJOR-1. If the
   parser's output stays inside the Literal, every value has a tier.
