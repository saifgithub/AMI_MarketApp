### Two independent live end-to-end scripts — not the coder's tests, my own from scratch

1. **My own single-merge scenario**, deliberately using different numbers than any fixture in the
   test file (orphan: `floor_manager` plan, balance 77, spent-down from a purchase; adopter: an
   existing `trial_trader` with 42 banked credits) — ran through the real `AuthService` +
   `MergeService().execute(...)` + `credit_service.balance_for(...)`, no mocks. Confirmed: adopter
   ends up `floor_manager` (higher wins) with balance `119` (77+42, summed); the orphan row is
   gone; `revenuecat_events`/`subscription_events` correctly re-keyed (0 remaining on the orphan);
   and critically, a **post-merge `balance_for()` read still returns 119**, not a wiped-back-down
   single-plan allowance — the mid-month-wipe guard genuinely holds under a scenario I built
   myself, not the shipped fixture.
2. **My own 2-hop chain-merge scenario — a scenario with ZERO test coverage in the shipped suite.**
   Created three real users A/B/C. Merged A→B (A deleted), then merged B→C (B deleted) — so C is
   now two merges removed from A's original identity. Sent a live webhook `RENEWAL` for **A's**
   original `app_user_id` (twice-orphaned) through the real `/v1/webhooks/revenuecat` endpoint with
   the RC secret unset (alias transfer offline, exercising only the backend safety net). It
   resolved with **200, not 404**, and the grant landed correctly on **C** (`plan == "trader"`).
   This independently proves the bounded chain-follow (`_follow_merge_alias`, 5-hop cap with cycle
   protection) genuinely works for the scenario it was explicitly written to handle — a case the
   coder's own 11-test file never exercises.

### Three mutation-tested claims, all caught cleanly

1. **Conflict-rule inversion** — hardcoded `final_plan = source_plan` (always take the orphan's
   plan, ignoring rank). `test_adopter_higher_plan_is_kept_never_downgraded` caught it immediately
   (`floor_manager` adopter incorrectly downgraded to `trader`) — this is the exact "wrong conflict
   rule silently gives or takes a paid entitlement" risk the architect named explicitly.
2. **Period re-stamp removed** (`credits_period_start`/`credits_plan_at_grant` left untouched after
   the carry) — `test_trader_orphan_into_floor_pass_adopter_carries_plan_and_sums_credits` caught
   it (`credits_plan_at_grant` stayed `None`), confirming the re-stamp is load-bearing against a
   later `_ensure_period()` drift-detection silently re-granting (wiping) the carried sum.
3. Reverted both; final suite re-confirmed 1212/1212 clean.
