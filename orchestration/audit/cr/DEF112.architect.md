## Fix shape (1 prod file + 1 test file, `backend/app/api/sim.py`) — mirrors DEF094 exactly

Read `git diff 64a500f b02c5dc -- backend/app/api/sim.py` (DEF094's actual diff, since `66ad136` is
a merge commit) before building, per the assign. Same three sites, same object, one field over:

1. **`preview_trade`** — `ComplianceBlock` (the existing typed `response_model=PreviewTradeResponse`
   DEF094 introduced) gained `classification_verdicts: list[ClassificationVerdict] = Field(default_factory=list)`,
   populated from `pv.compliance.classification_verdicts`. `ClassificationVerdict` now registers in
   the generated OpenAPI via this field, same mechanism DEF094 used for `ShariaVerdict`.
2. **`submit_trade` rejected path** (`return {"ok": False, "compliance": {...}}`) — added
   `"classification_verdicts": [v.model_dump(mode="json") for v in result.compliance.classification_verdicts]`
   to the hand-built dict, alongside the existing `sharia_verdict` key.
3. **`submit_trade` accepted path** (`return {"ok": True, "trade": ...}`) — the defect's headline
   case, same as DEF094's: previously **no `classification_verdicts` key at all**. Now carries the
   same list-comprehension serialization as the rejected path.

`classification_verdicts` is a `list[ClassificationVerdict]`, not an optional scalar (unlike
`sharia_verdict`) — serialized as an **empty list**, never `null`, when no classification flag is
active (`test_submit_accepted_empty_when_no_classification_flags_active`). `safety_floor.py` was not
touched (frozen HOT-FILE, out of scope per the assign — its classification logic is already correct,
DEF061 covers its enforcement).

**Contract note for coder.mobile:** serialized key is `compliance.classification_verdicts` (list),
each entry shaped `{status, ticker, kind, source, as_of}` — `kind` is one of `"fossil_fuels"` /
`"sin"` / `"esg_lite"` (`ClassificationKind` values), `status` one of `"permitted"` / `"excluded"` /
`"unknown"` / `"unavailable"` (`ClassificationStatus` values). `mobile/lib/models/mandate.dart:55-69`
already round-trips `esg_lite` and `no_fossil_fuels` as request-side flags; this is the new
response-side surface a mobile CR/DEF would render against. `mobile/**` not touched.

## Adversarial angles worth probing

- **The accepted path is the one that was dark** — same as DEF094. Confirm a PERMITTED *and* an
  UNKNOWN ticker both submit successfully (`ok: True`) and their
  `compliance.classification_verdicts[].status` differ
  (`test_permitted_and_unknown_accepted_bodies_are_not_byte_identical`).
- **UNKNOWN must never block.** `test_submit_accepted_unknown_ticker_is_permitted_and_discloses_esg_lite`
  asserts `ok: True` + `status: "unknown"` together — same G3 two-direction check DEF094 ran for
  Sharia, applied here.
- **Empty-list vs null.** `test_submit_accepted_empty_when_no_classification_flags_active` submits
  with no classification flag active and asserts `classification_verdicts == []`, not absent/null —
  the assign called this out explicitly (a `null` would be indistinguishable from "we dropped it").
- **Multiple active flags in one trade** were NOT tested together (each test activates one flag at a
  time, matching DEF061's own test shape) — worth confirming whether the acceptance bar expects a
  multi-flag response (e.g. `no_fossil_fuels` + `esg_lite` both on) to carry two list entries; the
  resolver (`safety_floor.py`) already supports it, this lane didn't add a dedicated test for it.
- **`sharia_verdict` untouched** — confirm this lane didn't regress DEF094's fix; the full-suite run
  below includes `test_def094_sharia_verdict_on_wire.py` unmodified and green.
