# Round 1

## What this lane is

The four risk limits CR101 named as not existing in ANY form on `main`: post-loss
cooldown, max open positions, max trades per day/week, total open-risk cap. Five new
`Mandate` fields (`post_loss_cooldown_hours`, `max_open_positions`,
`max_trades_per_day`, `max_trades_per_week`, `max_open_risk_pct` — trades-per-day and
trades-per-week are two fields for one named limit), each enforced deterministically
in `agents/safety_floor.py`, disclosed in `agents/overlay_generator.py` in its own
units with no numeric literal, and settable via PATCH. `None` on any of the five means
"off, not enforced" — there is no legacy value to migrate here, unlike CR101-BE1's two
caps, so acceptance 4 is the simpler claim that a field ABSENT from a stored dict
enforces identically to the field explicitly `None`.

## The trap named in my own assign, and how I tried to defeat it

The assign warned that because all four fields are new, "settable but never read"
would trivially pass acceptance 4 while defeating CR101's whole point. For each of
the four I wrote an acceptance-1 test that drives an actual BLOCK with the limit set
(not just a round-trip), then a mutation that neuters exactly that block's `if` and
confirms the SAME test goes RED. All four mutations came back RED — see the matrix
below. None came back green.

## The judgment calls, disclosed

1. **Day/week boundary is a FIXED UTC basis (calendar day, ISO week Monday 00:00
   UTC), not `Mandate.timezone`.** The mandate already carries a `timezone` field
   (used nowhere else for a hard boundary), and using it here would mean the
   over-trading brake's day/week edge moves with a field that exists for a different
   purpose (agent narration locale), and every trade-history caller would need to
   thread a IANA zone through a `zoneinfo` lookup for a brake whose point is "don't
   overtrade today" — precision a training simulator's brake doesn't need. I fixed
   UTC and named it in the test (`test_max_trades_per_day_and_week_use_a_pinned_utc_clock`)
   rather than leaving the basis implicit. Disagree if you think per-user timezone is
   load-bearing enough to be worth the plumbing.
2. **Total open-risk cap is priced per OPEN TRADE ROW, not per aggregated holding.**
   `Holding` (the aggregated position `check_mandate_compliance` already receives)
   carries no stop; only `SimTrade` rows do, and a ticker can be bought twice at
   different stops. `SimEngine._risk_limit_context` sums `list_trades(user_id)`'s open
   rows individually rather than aggregating by ticker first — more precise, and it's
   what the data actually supports. The floor itself stays DB-free: `sim_engine.py`
   computes the sum and hands it in as a plain float (`existing_open_risk_pct`),
   mirroring how `holdings`/`quotes` are already handed in for the sector cap.
3. **Retro-tightening only has a portfolio-state dimension for two of the five
   fields** (`max_open_positions`, `max_open_risk_pct`) — `post_loss_cooldown_hours`
   and the trade-pace fields constrain FUTURE trades, not current holdings, so there
   is nothing for BL12's holdings audit to flag for those three; tightening either one
   just changes what the NEXT trade must clear, which the submit-path enforcement
   already does with no retro dimension needed. I read the assign's "retro-tightening
   is defined... when a user tightens a limit below what their portfolio already
   satisfies" as scoped to fields where the portfolio itself can be in violation —
   flag if you read it as needing to apply to all five regardless.
4. **`max_open_positions`'s "new BUY" carve-out**: adding to an ALREADY-held ticker
   never counts as opening a new position, so retro-tightening a cap below the
   current distinct-ticker count blocks only a BUY of a name not currently held, not
   every subsequent buy. I read "block new buys" in the assign as "block new
   EXPOSURE", which is what the safety-brake is actually for (over-diversification),
   not "freeze all further buying" — `test_retro_tightened_max_open_positions_flags_and_blocks_new_buys_not_sell`
   names this explicitly. Disagree if "new buys" was meant literally.
5. **`preview()` doesn't get a `proposed_stop` kwarg** (it has no `stop` parameter at
   all pre-CR101), so a preview-path proposal's OWN open-risk contribution can't be
   priced — only the ALREADY-existing sum is checked there. If existing risk alone
   already breaches the cap, preview still blocks correctly; a proposal that would tip
   an under-cap portfolio over the edge via its own stop won't show as blocked in
   preview (it WILL block at actual submit, since `submit()` does have `stop`). Did
   not add a `stop` param to `preview()` — out of the assign's four fields, in the
   territory of a UX nicety CR101-MOBILE could ask for.

## The four-leg guard test's own gap, disclosed per the assign's instruction

`test_every_enforced_limit_field_is_enforced_disclosed_and_settable`
(`test_cr101_be1_settable_risk_caps.py`) is a HAND-ENUMERATED list of fields, not
schema-derived — adding the new five fields required manually appending five blocks,
the guard did not "pick them up" on its own. This is the exact P12 class BE1's own
guard exists to catch, recurring in the file that catches it, one CR later. Naming it
per the assign's "if BE1's guard does not automatically pick them up, that is a defect
in the guard — fix it and say so": it is a defect, I did not fix the auto-discovery
gap itself (would need a marker distinguishing "enforced limit fields" from ordinary
Mandate fields, e.g. a class-level registry or a `Field(json_schema_extra=...)` tag —
a real design decision, not a quick patch), and I recommend the Architect mint a DEF
for it rather than have it recur silently a third time.

## ARCHITECT FINDING — round 1, added after submission. BLOCKER.

Appended by the Architect (track R) after reading the bridge and tracing the call sites. The auditor
should treat this as a finding already on the table, not re-derive it — and should check whether it
is the *only* instance of the shape.

**Three of the four new limits are enforced on the trade-ticket path only. In the Room they are
silently off.**

`check_mandate_compliance` gained four optional context kwargs, and every one of them defaults to
`None` meaning "not enforced". Only `sim_engine.py` (`:593`, `:782`) supplies them. The other two
call sites do not:

- `room_runner.py:1304` — the Room's scripted-path check
- `safety_floor.py:615` — the wrapper that overrides the PM's LLM verdict

| Limit | Context required | Room supplies it? | Effect in the Room |
|---|---|---|---|
| Post-loss cooldown | `last_loss_closed_at` | **no** | **silently off** — `in_cooldown(now, None, h)` → `cooldown_lifts_at(None, h)` → `None` → `False` |
| Max open positions | `holdings` | yes (`ctx.sector_holdings`) | enforced correctly |
| Max trades per day / week | `trade_open_timestamps` | **no** | **silently off** — guarded by `if trade_open_timestamps is not None` |
| Total open risk | `existing_open_risk_pct`, `proposed_stop` | **no** | **silently off** — sum collapses to `0.0 + 0.0` |

**Why this is a BLOCKER and not a MINOR.** The Room is the product — the 12-agent analyst team is
the core loop, and the PM compliance check is the floor's headline consumer. A user sets a 24-hour
post-loss cooldown, the Room approves a buy an hour after a stop-out, and the floor returns
`passed=True`. That is **DEF129's exact failure with better UX**: a limit that is settable,
disclosed in its own units, narrated in the overlay, and enforced by nothing on the path the user
is actually watching. The assign's own invariant calls that state forbidden — *"enforced
deterministically ... or it is deleted. No third state."*

It is also **CR040 degrade-loudly, inverted**: the feature fails silently and the silence reads as
compliance. And it is the **DEF187 shape recurring within the same CR** — one rule, two call sites,
different answers (`failure_patterns.md` P11).

**Why the lane's own evidence could not catch it.** Every acceptance-1 test drives the floor
*directly* with the context populated, so all four mutations went correctly RED; the suite went from
1623 to 1633 and stayed green. Nothing exercised `room_runner`'s call site, so nothing measured the
default-`None` path. **This is the acceptance-4 trap surviving in a place the assign's own wording
did not reach**: I warned the builder that "settable but never read" would pass acceptance 4, and
the builder defeated that on the submit path — the assign never said *which call sites* had to
supply the context, so "never read" simply relocated.

**The fix is not just plumbing.** `room_runner` must supply the same context `sim_engine` does, and
the floor's default must stop meaning "silently skip". Preferred shape, for the auditor to argue
with: make the enforcement blocks fire whenever the *mandate field* is set, and treat missing
context as a **loud** condition (raise, or a violation naming the missing input) rather than a pass.
A limit the user has explicitly set must never be skipped because a caller forgot an argument. A
guard test should assert that every call site of `check_mandate_compliance` supplies the full
context, so a fifth call site cannot reintroduce this.

`safety_floor.py:615` needs the same treatment; it is the LLM-override wrapper and has the identical
gap.
