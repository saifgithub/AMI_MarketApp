### MAJOR-1 — the "zero HTTP calls on refusal" assertion for a live-host cancel is vacuous

`cr234_alpaca_orders_test.dart:241-258`, *"refuses against a stored live host"*, does this:

```dart
expect(() => client.cancelOrder('ord_123'), throwsA(isA<AlpacaOrderRejected>()), ...);  // not awaited
expect(adapter.calls, isEmpty, reason: 'the paper-host check must run before any HTTP call');
```

The first `expect` on an async call registers a pending matcher and returns at once. The second
line then runs synchronously, before `cancelOrder` has passed its first `await` (the credential
read). So `calls` is always empty at that instant, whatever the method goes on to do.

**Mutation, mine:** moved the paper-host check to *after* `_dio.delete`, so the DELETE is sent to
the live host and the refusal is thrown afterwards. Result: `+14: All tests passed!`. This is
exactly the mutation attack surface §1 asked for. The lane says it is pinned. It is not.

The code is correct today. But this test is the only structural guard behind a locked decision
(D-071: *"a live/production account stays strictly read-only"*) on a brokerage write. A
regression that sends a DELETE to a live Alpaca account would ship green. (The equivalent
`submitOrder` test is not vacuous. I moved that host check after a POST and 3 tests failed.)

**Fix:** `await expectLater(client.cancelOrder('ord_123'), throwsA(isA<AlpacaOrderRejected>()))`,
then assert `adapter.calls` is empty. Re-run the post-DELETE mutation to confirm the test now
goes red.

### MINOR-1 — the lost-race refresh (attack surface §3) has no test

The catch block does refresh both providers after a 422/404 (`:264-265`). Deleting those two
lines leaves `cr234_alpaca_orders_section_test.dart` green (`+11`). The code is correct, but the
refresh is unguarded, even though the lane lists "the lost-race path" as covered.

### MINOR-2 — a refused cancel (live host) fails silently in the UI

`cancelOrder` throws `AlpacaOrderRejected` for a non-paper host, but `_cancel` catches only
`AlpacaException` (`:244-268`), and the two are unrelated types (`alpaca_client.dart:74,83`). The
refusal escapes `onPressed` as an unhandled async error: no snackbar and no audit row. The Orders
list does not hide Cancel for a live-linked account (`if (!closed && order.isCancellable)`). So
a user who linked a live account sees Cancel buttons that do nothing when tapped. Safety holds,
because nothing is sent. This is a silent failure (CR040). **Fix:** catch `AlpacaOrderRejected`
and show its message, or hide Cancel when the linked host is not paper.

### MINOR-3 — `hexPurple` already means two other things on the portfolio screen (attack surface §4)

- It is in the sector-allocation palette (`portfolio_screen.dart:1153`), so an AMI sector slice
  can be purple.
- It is AMI's own `RestingOrderState.unknown` colour (`resting_orders_section.dart:92`), in the
  AMI resting-order book directly above `AlpacaOpenOrdersSection` on the same tab.

The badge text disambiguates, so this is MINOR. A purple chip on an AMI order still reads as
"Alpaca" at a glance.

### Verdict

The feature is built right: cancel is structurally paper-only, the backend stays out of Alpaca's
order API, and each attempt is audited once. But the one test offered as proof that a live
account can never receive a DELETE asserts nothing. I moved the check after the DELETE and the
suite stayed green. For a Tier-A write behind a locked decision, that guard has to be real.
