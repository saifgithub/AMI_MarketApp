### Finding 1 — MAJOR (test-coverage gap on the CR's single most safety-critical value; delivered code independently verified correct)

`test_held_user_shows_weight_matching_sim` asserts `f"{expected_weight:.1f}%" in block` — a
**substring search against the whole rendered block**, not against the specific
`"You currently hold {held_weight:.1f}% of {ticker}"` sentence it exists to verify (the exact
sentence-shape that failed in the real SCHD incident). `_build_sim_holdings_block` computes the
discussed ticker's weight **twice**, independently, from the same underlying values: once inside
the per-position listing loop (`weight = mkt_value / total * 100`, rendered as `"SYM ×qty (X% of
portfolio, ...)"`), and again after the loop specifically for the discussed ticker (`held_weight =
(held_qty * marks.get(ticker_u)) / total * 100`, rendered as the "You currently hold X%" sentence).

I mutated **only** the second computation (×1.5) and re-ran the test — **it still passed**. Debug
output confirmed why: the block correctly showed `"AAPL ×5 (7.4% of portfolio, ...)"` (the
untouched per-position line) alongside the now-wrong `"You currently hold 11.2% of AAPL"` (my
mutated line) — and the test's substring check against `"7.4%"` was satisfied by the *first*,
unrelated occurrence, never inspecting the second. A real regression in the "You currently hold"
sentence's formula — the literal replacement for the exact statement that caused the production
incident — would ship silently.

**Not a functional defect today**: both formulas read the same `agg`/`marks`/`total` values, so
they are mathematically guaranteed identical under the current implementation (confirmed by direct
read — `held_qty` and `qty` both come from the same `agg[sym]` entry, `marks.get(ticker_u)` and
`marks.get(sym)` are the same dict lookup when `sym == ticker_u`). The shipped code is correct. The
gap is specifically that the regression guard for this exact class of failure is not independent
of the number it happens to share a value with today — a future edit to either formula (rounding,
a fee adjustment, a display-only tweak) could silently desync the two without any test noticing.

**Recommendation** (not blocking this round, since the delivered behaviour is correct): tighten the
assertion to `assert f"You currently hold {expected_weight:.1f}%" in block` so it can only be
satisfied by the specific sentence it claims to verify.

### Finding 2 — MINOR (zero test coverage for the sim-vs-Alpaca precedence claim; delivered code independently verified correct)

`_compose_portfolio_block` — the function that implements adversarial focus #2's entire claim
("the Alpaca text is a labelled overlay below the sim block, not a competing portfolio") — has
**zero references anywhere in `test_cr055_room_holdings.py`**. No test ever passes a non-`None`
`alpaca_snap` into it. I verified the function's actual behaviour myself by direct invocation (sim
block emitted first, the Alpaca text correctly wrapped under the "informational overlay only — NOT
AMI's portfolio of record" label, and a `None` input returns the sim block byte-unchanged) — so this
is not a live defect, but it means a future regression in this exact precedence logic (e.g.
accidentally emitting Alpaca as a second `"YOUR PORTFOLIO"`-style block, or dropping the disclaimer)
would not be caught by CI. Lower severity than Finding 1 because it only affects the minority of
users who have linked an Alpaca paper account, not the always-present sim block every user sees.

Also noted in passing: the per-position `unrealised` P&L figure has no independent test assertion
either — same class of gap, cosmetic stakes (display-only, not decision-critical), folded into this
finding rather than filed separately.
