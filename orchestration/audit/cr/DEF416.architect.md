# DEF416 — audit lane (users.apple_id / users.google_id unique-constraint race)

**SCOPE:** def

**TIER: A.** Touches the auth path (`auth_service.py`'s Apple/Google sign-in) and adds a migration to `users`, the identity table every other feature depends on.

**SHA:** `b51147f2` on branch `worktree-agent-ac342e6958d9a958f`, worktree of `main` at merge-base `abd76ee8`. Review with `git diff abd76ee8..b51147f2`.

**depends-on:** none. **Promoted:** no. `/promote-to-alpha` still owed — see Attack Surface §1, the auditor should count existing duplicates on melehost **before** that promotion runs.

## What and why

Filed during CR231's stabilisation-programme sweep (`docs/defect/_registry/DEF416.row.md`, architect, 2026-09-24). `backend/app/db/models.py:113-115` declared `apple_id`, `google_id` and `hms_unionid` as plain nullable `String` columns — no `unique=True`, no index. `auth_service.py`'s `sign_in_with_apple` (~:590-668, pre-fix) and `sign_in_with_google` (~:691-760, pre-fix) both do the ordinary check-then-insert shape: SELECT `User` by the provider `sub`; on a miss, build and INSERT a fresh row.

Under one writer this is correct. Under two concurrent first-time sign-ins presenting the same OIDC `sub`, both reads land before either commit, both branches decide "no existing user," and — because there was no constraint — **both INSERTs succeeded, silently**. No `IntegrityError`, nothing to catch. Two `User` rows for one identity, diverging from that point (separate credit balance, journal, trial window).

Same failure class as ISS001 (`docs/dilemmas/ISS001_DB_INSERT_RACE/` — **still unresolved**, three submissions in, no verdict, field kept open 2026-08-16 for a 4th contributor per `ISS001_STATE.md`) and DEF401 (`docs/defect/_registry/DEF401.row.md`) — `failure_patterns.md` P15. This defect does not wait on ISS001's eventual verdict about the *general* mechanism for the other 20+ P15 sites; it reuses DEF401's already-shipped, already-audited shape for this one pair of sites. It is a strictly worse instance than DEF401's own (`uq_verdict_outcomes_room_run`) or the rest of P15's open sites: those at least have a constraint to violate and raise on. `apple_id`/`google_id` had nothing to catch at all — the ISS001 brief's own 2026-08-15 correction (§3.1, rows 3-4) is what first surfaced that fact, after the original inventory had assumed a constraint that didn't exist.

## The fix

1. **Migration `def416a0oidc0uq`** (`backend/alembic/versions/def416a0oidc0uq_users_oidc_unique.py`), chained onto the verified single current head `cr230a0order0log` (confirmed via `alembic.script.ScriptDirectory.get_heads()`, not by eyeballing `down_revision` pointers). Adds three partial unique indexes — `uq_users_apple_id`, `uq_users_google_id`, `uq_users_hms_unionid` — each `WHERE <col> IS NOT NULL`, spelled identically for `sqlite_where`/`postgresql_where` (same convention as `uq_journal_dedupe`/`uq_reputation_event_dedup`). On Postgres only, `upgrade()` runs a pre-check (`GROUP BY ... HAVING COUNT(*) > 1` per column) and raises `RuntimeError` naming every conflicting value and row id if duplicates already exist — it never deletes or merges rows. SQLite skips the pre-check: a fresh test DB is built by `Base.metadata.create_all()` and stamped straight to head, so it never replays this migration's `upgrade()` at all (same reasoning `8c5b1a70f4d2`'s docstring gives for its own Postgres-only branch).
2. **`models.py` mirror**: `User.__table_args__` (new — the class had none before) gets the same three `Index(unique=True, sqlite_where=..., postgresql_where=...)` declarations, so `create_all()` gives the unit suite the identical constraint.
3. **`auth_service.py`**: both sign-in functions' fresh-insert branch now runs `s.add(row)`/`s.flush()` inside `s.begin_nested()`; a caught `IntegrityError` re-SELECTs by the column that fired and calls the same `_attach_apple_sub`/`_attach_google_sub` closure the "found an existing row" branch already used (extracted from what was previously inline `else:` logic, byte-identical behaviour). This is DEF401's exact shape (`verdict_outcomes.py:286-312`) — SAVEPOINT insert, catch, re-SELECT, hand off to found-row path, return the winner. No new mechanism invented.
4. `test_p15_check_then_insert_guard.py`'s `_UNREVIEWED` pin: `sign_in_with_apple`/`sign_in_with_google` removed (now guarded — the AST scanner's `_integrity_guarded_spans` sees the `try/except IntegrityError` wrapping the `.add()` call). `_claim_or_create`/`ensure_anonymous` deliberately left pinned — CR191's remaining scope, not this defect's.

Design note with full reasoning, operator remedy, and per-test rationale: `docs/defect/DEF416_oidc_unique.md`.

## Mutation evidence

Reverted `with s.begin_nested():` to a bare `s.add(row); s.flush()` in the Apple path (scratch edit, not committed) — `test_apple_sign_in_race_lands_one_user_row_both_callers_agree` failed, but not with the expected assertion: it raised `sqlalchemy.exc.PendingRollbackError: This Session's transaction has been rolled back due to a previous exception during flush`. That's a stronger kill than a plain assertion failure — it demonstrates *why* the SAVEPOINT is load-bearing rather than cosmetic: without it, `get_session()`'s commit-on-exit/rollback-on-exception session (`backend/app/db/session.py:101-113`) is poisoned by the failed INSERT, and the recovery branch's own re-SELECT can't run at all. Reverted; full `test_def416_oidc_unique_race.py` green again (6/6).

## Attack surface (please probe)

1. **Pre-existing duplicates on Alpha's live DB.** The migration's pre-check only fires on Postgres and only at migration time. **Before `/promote-to-alpha` runs this migration, count actual `apple_id`/`google_id`/`hms_unionid` duplicates on melehost, read-only**: `SELECT apple_id, COUNT(*) FROM users WHERE apple_id IS NOT NULL GROUP BY apple_id HAVING COUNT(*) > 1;` (and the same for `google_id`, `hms_unionid`). If any group is found, the migration will refuse and list them — but confirming ahead of time avoids a failed promotion attempt and gives Saiful the operator-remedy path (`docs/defect/DEF416_oidc_unique.md` § Operator remedy) before it blocks a deploy in the moment.
2. **Partial-index semantics, Postgres vs SQLite.** I asserted `WHERE ... IS NOT NULL` is spelled identically on both dialects and is "not load-bearing" (NULLs already don't collide in a plain unique index on either). Please verify that claim directly rather than trusting the docstring — `test_multiple_users_with_null_apple_id_do_not_collide` proves it on SQLite (the only dialect the unit suite runs against); nothing in this branch proves it on real Postgres. If you have Postgres access (melehost, read-only, off a throwaway table) a two-row NULL-vs-NULL insert would close that gap definitively.
3. **Race handling — does the recovery path actually preserve every side effect the found-row branch performs?** I extracted `_attach_apple_sub`/`_attach_google_sub` from the pre-existing `else:` branch so both paths are byte-identical, but please check the BL2 device re-key logic (`_rekey_devices_to`, `adopted_from`) that runs *before* the insert attempt — lines 626-631 / 747-752 in the current file — for the specific case where `row is None` initially (no existing row was found), the insert races and loses, AND `user_id` pointed at a **different** anonymous row than either the winner's row or the loser's own attempted insert. Does the loser's re-key-eligibility get evaluated against the *pre-race* `row=None` state (so `adopted_from` stays `None` and the pre-claim anon's devices are never re-keyed to the winner), and if so, is that a gap this defect should also close or an acceptable narrowing (the loser signs into the correct account; only the *device* re-key is what might be missed on this specific interleaving)?
4. **Is six tests enough coverage for a Tier-A auth-path change?** I did not write a test for the interaction between this fix and the existing BL2 adoption/email-fallback logic under a lost race (e.g., race occurs on the email-fallback branch rather than the fresh-insert branch — that branch was already guarded implicitly because it UPDATEs an already-found row rather than inserting, so it shouldn't be reachable, but worth an independent look at whether that reasoning holds).
5. **`hms_unionid` — dead code risk of the reverse kind.** Nothing writes this column yet (no Huawei flow). The constraint is inert today by construction, which is intentional (closing the gap before the flow exists rather than after), but confirm there's no migration-ordering hazard for whenever CR-Huawei-AppGallery actually lands and starts writing it — should be none, since this is a plain additive constraint, but worth a second look given DEF278's own history of subtle migration-ordering mistakes.
