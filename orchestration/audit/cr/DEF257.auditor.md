## MINOR 1 — the M5 table row and the test it cites don't describe the same mutation, and one of the two is a real survivor

The "bound was an accident" section (prose) describes M5 as *"widen the
accepted decorations to `-`, `>`, `#`"*. The "Mutation harness, 4 of 4 killed"
table describes M5 as *"allow unlimited emphasis characters"*. These are two
different code changes. I built both and ran each in isolation:

```
Mutation A — _EMPHASIS = r"[*_>#-]{0,2}\s*"  (matches the PROSE description)
  -> test_the_decoration_boundary_is_a_decision FAILS, exactly as claimed.

Mutation B — _EMPHASIS = r"[*_]{0,}\s*"      (matches the TABLE description,
                                                literally: unbounded repetition)
  -> 16/16 PASS. A true survivor — nothing in this file, or in the other three
     stance-envelope test files (test_cr106_stance_envelope.py,
     test_def241_def243_debator_arithmetic_and_stance.py,
     test_def247_displaced_stance_envelope.py — grepped all four for `***`
     and for `emphasis`/`EMPHASIS`, zero hits outside this file), exercises
     3+ repeated emphasis characters.
```

So the table's row is testing Mutation A under a description that reads like
Mutation B. The real M5 (decoration-character widening) genuinely is killed;
the repetition-count bound (`{0,2}`) is genuinely unpinned.

**Why this doesn't block:** `_EMPHASIS` appears twice in the assembled pattern
(once before the optional bracket, once after), so the *effective* current
cap on consecutive emphasis characters is not 2, it's 4 — confirmed by testing
the real, unmutated code directly:

```
2 asterisks -> stripped   3 asterisks -> stripped   4 asterisks -> stripped
5 asterisks -> LEAK       6 asterisks -> LEAK
```

`***STANCE: …***` (bold+italic — the one plausible next drift, since it's
standard markdown and arguably *more* natural for a model reaching for
emphasis than plain bold) is already handled correctly today. Nothing
realistic exceeds 3. So the prose's own "one or two" self-description
undersells what the code does, and the survivor mutation (B) only matters for
inputs with 5+ consecutive `*`/`_`, which no real turn has ever produced. A
real gap in what's pinned, not a live risk — flagged so the table gets
corrected (either fix the M5 description to match Mutation A, or add a
genuine test for the repetition bound if 4/4 is meant to include it).
