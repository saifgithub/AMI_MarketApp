**Fix:** add the 15 keys to `mobile/lib/l10n/app_ar.arb` and
`mobile/lib/l10n/app_ms.arb`, regen, parity test green.

## MAJOR M2 — migration `deep_link` column is `sa.JSON()`; the model is `JsonB()`; claim (e) is false

`backend/alembic/versions/8a4ce4f8abc3_notifications_price_alerts.py:34`:

```python
sa.Column("deep_link", sa.JSON(), nullable=False, server_default=sa.text("'{}'")),
```

`backend/app/db/models.py` (NotificationRow): `deep_link: Mapped[dict] =
mapped_column(JsonB(), ...)`. House convention, verified against every sibling
migration carrying JSON columns (`d8a3e9f40004`, `a3b4c5d60017`, `b2d3e4f50021`,
`c9f0a1b20022`): all import `JsonB` from `app.db.base` and use it in DDL. This
migration is the lone outlier. On Postgres (Alpha at promotion) the column is
created `json` while the model renders/binds `jsonb` — runtime-compatible
today (no bind processors on `JsonB`, no index on the column), but permanent
model-vs-DDL drift on a brand-new table and a spurious alter diff on every
future `--autogenerate`. The submission's claim (e) — "both new tables use the
portable `Uuid`/`JsonB` TypeDecorators from `app/db/base.py`, not raw Postgres
types" — is false for `deep_link`, and it was presented as verified. (`sa.Uuid()`
for the id/user_id columns is fine: precedent exists in `a1c2e3f40020`,
`b2d3e4f50021`, `d5f2a3b00009`.) Nothing has been promoted yet, so the fix is
free now and a second migration later.

**Fix:** `from app.db.base import JsonB`, `sa.Column("deep_link", JsonB(), ...)`.
