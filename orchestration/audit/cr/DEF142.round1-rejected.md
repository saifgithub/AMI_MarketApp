## BLOCKER (Part B / CR108) — the wrap never happens, and the test that proves it cannot fail

Three separate facts, each measured, each independent of font metrics.

### 1. The label never wraps. Not for any of the 13 labels.

`FittedBox` lays its child out with **unbounded** constraints. `softWrap` and `maxLines: 2` cannot
break a line that has infinite width available, so `track_hex_button.dart:76-84` — a `FittedBox`
wrapping a `Text` — produces a **one-line paragraph in every case**. The width constant CR108 added
(`flatTopHexWidthFractionAtTwoLineLabel`) is applied to the `SizedBox` **around** the `FittedBox`,
never to the text that is supposed to wrap inside it.

Measured by pumping the real widget at the lane's own 143.2×124 fixture and reading
`RenderParagraph.size`: **`paraH = 14.0` for all 13 labels** — one line height, every one. The
two-line branch is dead code at every geometry, not just this one.

### 2. So the labels are still being shrunk — and five of them are now SMALLER than before the fix.

With the paragraph laid out at its full one-line intrinsic width and the `FittedBox` constrained to
the label box, `BoxFit.scaleDown` scales the whole thing down. That is precisely the shrink CR108
was filed to eliminate. Comparing painted width to paragraph width at the lane's fixture, before
(`8bb00594`) vs after (`846e92cd`):

| Label | before | after | |
|---|---|---|---|
| ISLAMIC FINANCE | 5.64px | **5.47px** | **worse — and this is CR108's named target** |
| ASSET CLASSES | 6.51px | **6.31px** | worse |
| FUNDAMENTALS | 7.05px | **6.84px** | worse |
| NEWS & MACRO | 7.05px | **6.84px** | worse |
| FOUNDATIONS | 7.70px | **7.46px** | worse |
| EVALUATION | 8.00px | 8.20px | better |
| TECHNICAL / SENTIMENT / ECONOMICS | 8.00px | 9.11px | better |
| RISK / EDGE / QUANT / ETHICS | 8.00px | 10.00px | better (never scaled) |

**Read these as relative, not absolute.** `flutter_test` uses a fixed-width test font, so the
absolute pixel values are not a device claim. The before/after comparison is valid because both
sides are measured under the same font. The mechanism — raise the base 8px→10px (text 25% wider)
and narrow the box 103.7→96.8 (7% narrower), while the wrap that was supposed to absorb the extra
width never engages — is font-independent, and it is why the long labels got worse.

The four short labels that never scaled at all (RISK, EDGE, QUANT, ETHICS) do get the full base
raise. So the change is not worthless; it is a base-size raise that helps the labels which were
never the problem and hurts the five that were.

### 3. The guard cannot fail. That is the more important half.

`track_hex_button_test.dart:65` reads the FittedBox scale as
`paragraph.getTransformTo(null).getMaxScaleOnAxis()`. **That returns 1.000 for every label**, while
the painted rect proves real scaling is happening (e.g. `ISLAMIC FINANCE`: paragraph 177.0px,
painted 96.8px). `RenderFittedBox`'s paint-time scale is not visible through this transform walk.

So `_renderedLabelFontSize` computes `10.0 * textScale * 1.0` — a constant — and all 26 size
assertions reduce to `expect(10.0, greaterThanOrEqualTo(10.0))`. **They cannot fail.**

Confirmed by mutation, which is how this was found: setting `needsTwoLines = false` — deleting the
entire feature — leaves **all 27 tests green**. The hand-off's headline claim ("all 13 render
≥10.0px at 1.0×") is an artifact of the broken measurement, not a property of the widget.

The lane's comment at `track_hex_button_test.dart:54-59` reasons carefully about *why* reading
`Text.style.fontSize` would be wrong and then substitutes a different metric that is also blind.
The reasoning is right; the replacement was never itself validated against a known-scaled case.

**`getRect(finder).width / RenderParagraph.size.width` is the metric that works** — it goes through
`localToGlobal`, which does apply the paint transform. That, plus asserting `paraH` is two line
heights for the labels that are supposed to wrap, is the guard this needs.

### Why the builder's own count was also off

The hand-off says "exactly 3 of 13 wrap (NEWS & MACRO, ASSET CLASSES, ISLAMIC FINANCE)". Measured,
**9 of 13** exceed the one-line box at this fixture. The three named are simply the widest. Nothing
depends on the count — none of the nine actually wrap — but it indicates the claim was reasoned
from the three labels the row discusses rather than measured across the set.

## Part A (DEF142 / HexAvatar) — sound, and its guard bites

Kept separate because none of the above touches it.

- **Diff scope re-verified:** `git diff 8bb00594..846e92cd --stat` = 10 files, +483/−64.
  `portfolio_screen.dart` and all three `app_*.arb` files untouched, as the assign fenced them
  against the concurrent CR120 lane. The fence held.
- **Suite re-measured by me in the lane's worktree:** `flutter test -r compact` → **306 passed**,
  0 failed (base 266, so +40 are this lane's). `flutter analyze --no-fatal-infos` → 5 issues, all
  pre-existing and named in the assign verbatim, exit 0.
- **The census reproduces.** I re-derived it rather than trusting it: ten distinct `HexAvatar`
  sizes across `mobile/lib` — 20, 28, 32, 44, 48, 56, 72, 110, 120, 160. At `size * 0.16` exactly
  **one** site renders below 4.0px (`lesson_tile.dart` at size 20 → **3.2px**); the next size up,
  28, renders **4.48px**. The floor sits strictly between the broken site and every working one.
- **The 4.0px floor exists because the builder caught an error in my assign.** My table rounded
  4.48px to "4.5px", which reads as *clearing* a 4.5px floor when it is 0.02px **under** one —
  CR107's proposed floor would have culled every 28pt site along with the one real problem. The
  builder set 4.0px and said why instead of absorbing it. Score that as a strength.
- **One benign error in the builder's justification.** It says it checked "the four 28pt sites";
  there are **five** — it omits `room_transcript_rows.dart:231`. I checked the fifth: it passes
  `label: ''` and prints the abbreviation in an adjacent `Text`, with a comment already citing
  DEF142. It takes no in-hex label under any floor. Count wrong, conclusion unaffected.
- **The contrast check extends the existing one rather than forking it.** The new case lives in
  `room_board_test.dart`'s existing non-vacuous contrast group; the WCAG helpers were hoisted to
  file scope so both cases share one implementation. This is the DEF098 shape handled correctly.
- **Mutation, run by me: RED.** Setting `_minHexAvatarLabelFontSize` to 0.0 — deleting the floor —
  turns `hex_avatar_test.dart` **2 RED of 9**. Part A's guard bites.

### Part A gaps that stand

- **No device check.** All of it is widget-test measurement. The gate is `independent` precisely
  because this wants Saiful's eye on a phone.
- **`combInkFor` was read, not reused** — a one-line identity in `room_board.dart`; `HexAvatar`
  uses `effectiveColor` directly. Same value today, silent divergence if a family colour ever needs
  lifting. A latent DEF098 instance, named by the builder unprompted.
- **The contrast assertion reads `Text.style.color` and `BoxDecoration.color`, not pixels.** Worth
  asking whether a rendered-colour check is available, given what style-level assertions just cost
  us in Part B.

## Disposition

**Part B goes back for round 2.** Two things must change together, and neither is cosmetic: bound
the text so `softWrap`/`maxLines: 2` can actually break a line, and replace the scale metric with
one that observes the paint transform (`getRect` vs `RenderParagraph.size`), plus a `paraH`
assertion so a silently-unwrapped label is a failure. A single unbreakable long word
(`FUNDAMENTALS`, 12 chars) still cannot wrap and must fall back to scaling — that case needs
deciding, not assuming.

**Part A is ready** and would pass a gate today. It is on the same branch, so it does not ship
separately without a split.

**Nothing here reaches `main`,** so no shipped build is affected. CR107 stays HELD — it was waiting
on this pass as its control, and the control is not yet valid.

**Integration hazard, unchanged:** this branch was cut before CR120's handshake files landed, so
`git diff main..lane/DEF142.coder.mobile` shows `CR120.architect.md` and `CR120.coder.mobile.md`
as deletions. They are absences, not deletions. CR120 has since integrated at `72a6d804`; merging
`main` into the lane resolves it.
