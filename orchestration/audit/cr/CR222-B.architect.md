## What the feature promises the user

Portfolio Health §F3 gains a block, **"The same money, held passively"**: what a mandate-matched
passive instrument would have returned on the SAME cash, on the SAME dates, had it received every
deposit the user's own book received and never been traded. Two measures — money-weighted (IRR,
timing kept) and time-weighted (TWR, timing removed) — both sides, both differences, in
percentage points, with no interpretation attached (CR131's honesty rules: no grade, no warning,
no verdict, one shape whether the user is ahead or behind). The promise that matters most for a
halal user: the twin is their OWN mandate's passive instrument, never a silent substitution of an
unscreened index fund. Machine states (`twin_unmapped`, `twin_history`, `twin_short_window`,
`twin_no_capital`) replace numbers whenever the counterfactual cannot be honestly measured —
degrade loudly, never a fabricated close.

### (a) Ordinary mandate — 90-day NAV spine, `open` at day 0 ($10,000), `restart` at day 40
($6,000 fresh stake), SPY drifting 0.05%/day

Rendered §F3 block:

```
**The same money, held passively**
Comparison holding: SPY, annual expense ratio 0.0945%. Bought with the same cash on the same
dates as this book's own deposits, and never traded.
Money-weighted (the deposits' own timing kept): this book -99.23% a year against SPY's -99.25%,
a difference of 0.02 percentage points.
Time-weighted over the same window (the deposits' timing removed, not annualised): this book
5.42% against SPY's 4.50%, a difference of 0.92 percentage points.
Measured over 90 market days on the shared date grid. Method: internal rate of return over the
deposit schedule, and the chain-linked time-weighted return over the same points.
```

`validate_sections` → `None` (passes).

**Hand-checked arithmetic** (independent of the module's own functions — built the cash-flow
schedule and TWR chain by hand from the same NAV rows):

- Cash-flow schedule the IRR should see: `-$10,000` on day 0, `-$6,000` on day 40 (the restart is
  a deposit, per the CR's own construction), `+$6,178.9642...` (the terminal NAV) on day 89.
  Hand-built `CashFlow` list fed through the module's own `irr()` in isolation (not through
  `build_passive_twin`) returned `-0.9922695762338087` — matches the block's `user_irr` to the
  last bit. The number reads oddly negative only because ACT/365 annualises a schedule whose
  LAST deposit (the $6,000 restart) sits 50 days from the terminal date at a small dollar gain —
  bisection on the annual rate over a short window inflates/deflates fast; this is the solver
  behaving correctly on a short, restart-heavy schedule, not a bug (see the twin's own IRR moving
  in lockstep with it, -99.25%, which is the same artifact acting on the same schedule shape).
- Time-weighted return, chain-linked and split at the `restart` (the module's documented
  behaviour — a capital event that isn't the first row splits the chain): segment 1 (day 0 →
  day 39, pre-restart) = `navs[39]/navs[0] - 1 = 0.023668744728650104`; segment 2 (day 40 →
  day 89, post-restart) = `navs[89]/navs[40] - 1 = 0.02982736719206036`. Chain-linked:
  `(1.023668744728650104)(1.02982736719206036) - 1 = 0.05420208826070705` — matches `user_twr`
  (0.05420163404 in the printed block after rounding for display; the renderer's own `_pct(...,
  2)` rounds to "5.42%", consistent) to full precision against the module's own unrounded
  `_returns_for` output.
- Median holding period (behaviour block, same fixture): 12 closed round trips, each held exactly
  3 calendar days by construction → `median([3]*12) = 3.0`, matches.
- Turnover: 12 buys, quantity 10 @ $100 = $1,000 notional each, no sells (self-closed via
  won/lost status) → `avg_side_notional = (12,000 + 0)/2 = 6,000`; `turnover_pct = 6000/10000*100
  = 60.0`; `window_days = (2026-09-25 − 2026-01-05).days = 263`;
  `annualised = 60.0 * 365.25/263 = 83.33` (rounded) — both match the computed block exactly.
- Disposition: win pattern `i%3 != 0` over `i in range(12)` → 8 wins, 4 losses, matching
  `realised_gains_count=8`, `realised_losses_count=4` exactly; every position is self-closed
  (no lot left open anywhere in the account), so `paper_gains_count=paper_losses_count=0` and
  `PGR=PLR=8/(8+0)=4/(4+0)=1.0` — 100%/100%, matching the rendered block.

## Bug found and fixed: `unregistered_number` on the CR222 §4 attention-trade sentence

Not a slice-B bug in isolation — it lives in `_f3_behaviour` (CR222 §4, slice D), but it broke
**this lane's own probe** the first time §F3 rendered with BOTH B and D on together (the flip
Saiful asked for turns both on at once, so this is exactly the combination that matters). Filing
it here because the fix is in a shared file (`portfolio_health_constants.py`) both lanes read
from, and I found it while probing B; see CR222-D for the D-side detail of the same fix.

**The bug:** `_f3_behaviour` (`portfolio_finding.py:686`) writes fixed prose — "within 5 trading
days of a 10%-or-larger price move ... within 1 day of a Room convene" — from the module-level
constants in `behaviour_diagnostics.py`
(`ATTENTION_MOVE_LOOKBACK_TRADING_DAYS=5`, `ATTENTION_MOVE_THRESHOLD_PCT=10.0`,
`ATTENTION_CONVENE_LOOKBACK_CALENDAR_DAYS=1`), but `build_allowlist` never registered "5" as a
number the Finding may contain. The renderer's own literal "5" tokenizes
(`tokenize_numbers`) exactly like a data-driven number, and the validator has no way to tell a
structural constant from a datum — that distinction is what `VALIDATOR_FIXED_RAW` /
`VALIDATOR_FIXED_PCT` exist for (`portfolio_health_constants.py:285-304`), and "5" was missing
from both.

**Why the permanent test suite never caught it:** `test_cr222_behaviour_diagnostics.py::
test_behaviour_block_passes_validator_ready_shape` passes today, but only by accident — its
hand-built fixture happens to set `disposition.realised_gains_count = 5`, which the generic
per-field registration (`portfolio_finding.py:1024-1028`, RAW scale) coincidentally puts "5" in
the allow-list for an unrelated reason. Change that fixture's count to anything else and the same
test would fail with the identical `unregistered_number` on token `'5'` my probe hit. Confirmed
by direct reproduction:

`"1"` and `"10"` (PCT) were already covered by `VALIDATOR_FIXED_RAW`/`VALIDATOR_FIXED_PCT` for

that happened to hold, which is the same shape of luck as the "5" one, just not yet exhausted.

**Impact if shipped unfixed:** `POST /v1/portfolio/health/{user_id}/finding` would raise
internally (`build_finding` returns `(None, "unregistered_number")`,
`portfolio_finding.py:1583`) for ANY training user with both `PORTFOLIO_PASSIVE_TWIN_ENABLED`

## Attack surface

- **Can the twin ever silently be SPY for a halal user?** No — structurally, not just by
  observed behaviour. `map_twin_instrument` (`passive_twin.py:234`) branches `if halal:` into its
  own `return` (the halal ticker, or `None`) and the `return TwinInstrument(default_ticker...)`
  at the bottom is OUTSIDE that `if` block — there is no fallthrough path from the halal arm to
  the default-ticker return; Python's control flow makes it unreachable, not merely untested.
  Verified by direct read of the function plus case (b) above (both configured and unconfigured
  halal paths probed against a fixture where SPY prices exist and would produce a plausible-
  looking number if the fallback fired).
- **Are cash flows dated correctly?** Verified by hand in case (a): the `restart` deposit lands
  as a `-$6,000` flow on day 40 in the IRR schedule (matching the TWR chain-split at the same
  date), reconstructed independently from the raw NAV rows rather than by re-reading the
  module's own `_flows_for` output. The module's own `test_a_restart_deposit_lands_in_both_
  series_on_the_same_date` / `test_the_restart_deposit_is_the_restart_rows_own_nav`
  (`test_cr222_passive_twin.py:153,178`) cover this from the unit side; this round adds an
  independent hand-computation on a different (larger, more realistic) fixture.
- **Toll symmetry, given C stays off:** confirmed the rendered twin block carries no
  `cost_treatment` key under this flip (`training_toll_enabled=False` throughout every probe
  case) — `_with_cost_treatment` (`passive_twin.py:311`) only adds the key when
  `_twin_toll_charged()` reads true, and the block dict is otherwise identical to what slice B
  alone would have produced before slice C's toll-symmetry code landed in the same file
  (`test_twin_output_is_byte_identical_to_slice_b_with_the_toll_off`,
  `test_cr222_training_toll.py:797`, already green).
- **Advice-adjacent language:** scanned all four rendered blocks above plus the permanent
  suite's `test_the_twin_block_carries_no_grade_no_warning_no_verdict`
  (`test_cr222_passive_twin.py:499`) for grade/warning/verdict/advisory language
  ("underperform", "outperform", "you should", "beat the market", imperative "buy"/"sell", etc.)

  should do about them.
- **Expense-ratio double-scaling** (the class of bug DEF212 named): `build_allowlist` registers
  the expense ratio at its OWN percent scale (`already_percent=True`) rather than through the
  generic ×100 sweep, specifically because 0.0945 at the generic sweep's scale would register

  this round beyond confirming the existing test (`test_the_expense_ratio_renders_at_its_own_
  precision_and_validates`) is real and green.
- **Not independently re-driven this round:** the IRR bisection's numerical behaviour at the
  bracket extremes (`_IRR_LOW=-0.9999`, `_IRR_HIGH=1e6`) — case (a)'s schedule produced a
  plausible-looking but visually startling ~-99% figure (explained above as an ACT/365
