# Round 1

## The headline: one assign instruction was not followed literally — read this before the acceptance table

Item 3 of "what to build" rules: *"Remove [`SINGLE_NAME_ABSOLUTE_CAP_PCT`] as an enforced
ceiling... If you conclude on the code that removing it opens a real hole, stop and disclose — do
not quietly keep both."* I did not remove it. I am disclosing, not quietly keeping both.

**What I measured, before deciding anything.** I first implemented the literal instruction: made
the deterministic floor's `single_name_cap_pct(mandate)` fall back to `risk_tier_cap(risk_score)`
when unset (matching the assign's framing that this "is what the PM actually clamps to"). Full
suite: **43 tests failed**, all in `sim.submit()`-adjacent files that never touch the Room —
`test_sim_engine.py`, `test_cost_basis_lots.py`, `test_mandate_audit.py`, `test_def110_backfill.py`,
`test_def110_outcome_liquidates.py`, `test_def112_classification_verdicts_on_wire.py`,
`test_sim_reputation.py`, most of `test_cr026_sector_allocation.py`'s enforcement tests. Every
failure was the SAME shape: a direct trade sized 3-45% of portfolio, previously accepted, now
rejected with `"position size X% exceeds single-name cap 3.0%"` (a risk_score=3 mandate).

**Why.** Two enforcement paths for a single-name cap exist on `main`, and they measure
differently:

1. **The Room path.** `room_runner._risk_tier_size_ceiling` pre-clamps the PM's proposed size to
   `risk_tier_cap(risk_score)` (~1.5-4.5%) BEFORE the trade ever reaches
   `safety_floor.check_mandate_compliance`. The floor's own check then compares against its
   constant — but the proposal is already under it, so the floor's number never binds here. This
   is exactly what the assign's own "can essentially never fire on the Room path" describes.
2. **The direct trade-ticket path.** `sim.submit()` calls `check_mandate_compliance` with NO prior
   size clamp (confirmed in DEF153's own docstring: *"The app's trade ticket submits market
   orders, so this is the path a user actually takes"*). Its ONLY historical single-name gate was
   the floor's own constant — `SINGLE_NAME_CAP_PCT = SINGLE_NAME_ABSOLUTE_CAP_PCT = 50.0` — not
   `risk_tier_cap`.

So "what the PM actually clamps to" is true on the Room path and FALSE on the direct-submit path.
Defaulting the floor's fallback to `risk_tier_cap` instead of 50% would have silently tightened
every existing user's direct-submit cap ~11x on deploy — the exact failure acceptance 4 says is
"the one failure nobody would notice," now caught by the very suite acceptance 4 asks me to keep
green. I reverted to the literal instruction, confirmed RED, then landed on the disclosed
compromise below rather than pick a side unilaterally.

**What I shipped instead:** `safety_floor.single_name_cap_pct(mandate)` — an explicit
`single_name_cap_pct` override always wins (satisfies "settable"); UNSET, it falls back to
`SINGLE_NAME_ABSOLUTE_CAP_PCT` (50%) — the EXACT value this specific floor enforced pre-CR101,
migration-safe. `overlay_generator._max_position_pct`, `room_runner._risk_tier_size_ceiling`, and
`room_prompts`'s researcher-cap note all keep falling back to `risk_tier_cap` — ALSO unchanged from
`main`. Once a user explicitly PATCHes `single_name_cap_pct`, every one of these sites reads that
SAME value, so shown == enforced holds for them prospectively (CR046 C-a, extended). For a user who
has NOT set an override, the pre-existing 50%-floor vs. risk-tier-preset-overlay split survives
unchanged — not fixed by this lane, flagged in the hand-off for a DEF.

**What I want the auditor to attack:** is 50% actually the right migration-safe default, or should
this lane instead have TIGHTENED the direct-submit path to `risk_tier_cap` as a deliberate defect
fix bundled in, with the 43 tests corrected to the new, tighter, intended behaviour instead of
preserved? I judged that a scope decision above a `coder.api` lane (it changes real enforcement for
every existing user, not just adds a write path), which is why I preserved the status quo and
disclosed rather than silently choosing. Disagree if you think the assign's "remove it" instruction
already settled this and I should have gone the other way.

## The judgment calls, disclosed

1. **Units: both new fields are percentage points (0-100), matching `max_drawdown_pct`'s
   convention** (`sector_cap_pct=40.0` means 40%), not the fraction (0.0-1.0) `sector_allocation.py`
   computes internally. `sector_concentration_cap(mandate)` does the `/100` conversion at the
   boundary; nothing outside that function sees percentage-point sector values.
2. **Coalesce-at-read, not validate-at-construction.** I considered a `model_validator(mode="after")`
   that bakes in the preset default the first time a `Mandate` is constructed. Rejected: the test
   suite constructs `conservative_mandate`/`aggressive_mandate` fixtures via
   `base_mandate.model_copy(update={"risk_score": ...})`, which does NOT run validators — a baked
   default would freeze `base_mandate`'s risk_score=3 preset onto every fixture derived from it via
   `model_copy`, silently breaking `test_position_sizing.py` and several `test_overlay_generator.py`
   assertions that rely on the preset tracking `risk_score`/`concentration_tolerance` live. Both
   `sector_cap_pct` and `single_name_cap_pct` stay `None` until an explicit PATCH; every resolver
   coalesces to the preset AT THE CALL SITE, every time. This is also what makes the migration
   proof (acceptance 4) hold for a `model_copy`-derived mandate, not just a freshly-validated one.
3. **`SINGLE_NAME_ABSOLUTE_CAP_PCT` was NOT removed** — see the headline. Still exported from
   `trading_math/sizing.py`, still used by `risk_debator_sizes`'s narrative bound AND (new,
   disclosed) as `safety_floor.single_name_cap_pct`'s unset-fallback.
4. **`drawdown_response`/`regret_asymmetry` untouched**, per the fence — still feed
   `_derive_risk_score()` in `concierge_engine.py`, nothing here changes that path.
5. **Resolver centralisation.** Added `trading_math.sizing.resolved_single_name_cap_pct` /
   `resolved_sector_cap_pct` — pure functions, override-or-preset — so
   `overlay_generator._max_position_pct`, `room_runner._risk_tier_size_ceiling`,
   `room_prompts`'s researcher-cap note, and `safety_floor.single_name_cap_pct` /
   `sector_allocation.sector_concentration_cap` all read ONE computation each, not five
   independent re-derivations (the CR046/DEF153 lesson, applied prophylactically before a sixth
   site could drift).
