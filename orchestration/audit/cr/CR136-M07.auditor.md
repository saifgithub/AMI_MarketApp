### The part that is not in the submission: neither counter ever advances again

`daily_used` counts journal **rows**. The write always collides, so no row is
ever created, so the counter is frozen. I drove the same book past the cap:

```text
after POST 1 + delete:                                   generations=1
POST 2: 200 created=False daily_used=1 cap=2 trial_used=1 generations=2
POST 3: 200 created=False daily_used=1 cap=2 trial_used=1 generations=3
POST 4: 200 created=False daily_used=1 cap=2 trial_used=1 generations=4
POST 5: 200 created=False daily_used=1 cap=2 trial_used=1 generations=5
POST 6: 429  ← the RATE LIMITER, not the gate
```

**Generation ran five times against a daily cap of two**, and `trial_findings_used`
froze at 1 of 7 alongside it. The only thing that stopped it is
`portfolio_health_finding_rate_limit`, whose own comment says it is explicitly
*not* the spend control:

> "it brackets scripted hammering of the route itself, which the daily cap alone
> would still let build context on every hit" — `rate_limit.py:251-252`

So for any user who deletes today's Finding and regenerates, the bound is
5/min for the rest of the UTC day — roughly 7,200 generations, each a billed LLM
call on the enabled path, because `llm_render_sections` runs *before*
`append_unique`. That is §1.2's "gate too open ⇒ unbilled LLM calls, discovered
on an invoice", reached by an ordinary user through `journal_screen.dart:170-186`
with its undo snackbar. No attacker, no concurrency, no double-tap needed — a
delete and a regenerate.

The irony is worth stating because it is the design's own logic turned against
it: §2.3 deliberately counts soft-deleted rows so that deleting a Finding does
**not** refund the budget. That decision is right. The collision defeats it by
guaranteeing there is no row to count.

## MINOR m1 — §5.3, the daily cap resets with the book, and that is a question for Saiful, not a fix for you

Confirmed: `daily_used` filters on `reference_id == portfolio_id`,
`reset_portfolio` (`sim_engine.py:399-417`) deletes the row and `ensure_portfolio`
mints a fresh `uuid4()`. Trial counters survive because they are per-user, which
is correct and which your docstring explains well.

I am **not** grading this as a defect: it matches Rev 4's "per portfolio per day",
you tested it as intended, and the cost to the user is their entire simulated
book. But taken with B1 it is the second independent path by which the thing §5.3
calls "the only limiter on an entitled user" does not limit, and once B1 is fixed
it is the only one left. That makes it a pricing decision rather than an
engineering one, and it should go to Saiful in those terms: *the daily cap is
per-book, and a book is free to destroy and recreate.*

Related and not separately graded — §5.7: the limiter is an in-process
`OrderedDict` singleton. Alpha is one container today, so 5/min is 5/min. On two
replicas it is 10/min, and it is the only bound on B1's loop until B1 is fixed.
Worth a line in the module doc rather than a change.

## MINOR m2 — §5.4, the unbounded fetch

`portfolio_health_stats` (`journal_store.py:340-381`) selects **every** Portfolio
Health row the user has ever had, with no `COUNT` and no date bound on the trial
leg, and counts in Python — on every gate evaluation, which is both routes. It is
bounded today by cap × days only because the cap works; B1 is a live
demonstration that "bounded by the cap" is an assumption, not a property. A
`COUNT` plus a `min(created_at)` is owed, and the trial leg wants the same date
bound the daily leg already has.

## MINOR m3 — the `_as_utc` hazard is documented in five lines and pinned by nothing

MUT-G reverts `_as_utc(now).astimezone(...)` to the bare `astimezone()` the
comment warns against, and all 34 tests pass. The comment is right about the
hazard — a naive datetime is reinterpreted as local system time, offsetting the
UTC day boundary by the container's timezone.

Downgraded to MINOR after checking the call site rather than stopping at the
mutation: `evaluate_gate` does `now = now or datetime.now(timezone.utc)`
(`health_gate.py:88`), so the only caller always passes an aware value and the
guard is defensive against a caller that does not exist yet. It is still a
five-line comment describing a defect nothing would catch, and one test passing a
naive `now` closes it.
