# CR136 spec pack — development-ready tightening (auditor lane, 2026-08-02)

Written at Saiful's direction between r1 and r2. **Lane discipline:** this file
lives in the audit lane so r2 independence survives — the architect lifts it
into the CR doc wholesale; nothing here is merged by the auditor. It closes
MAJOR M1 and MINORS m2–m5 by proposal, and adds the three things the CR lacks

Every pinned number below carries its derivation so the choice is re-derivable

## 1. Sufficiency contract (closes M1)

All thresholds in **trading days** (returns count, not bars: 65 bars → 64
returns). One floor per metric, stated here, code reads them from one
`SUFFICIENCY` constant block — never scattered literals.

| Metric | Min observations | Rationale (derivation) | `standard_error` |
|---|---|---|---|
| Portfolio volatility σₚ | **T ≥ 126** | SE(σ̂) = σ/√(2T): at 126 obs, 20%/√252 = **1.26pp**; at the 251 the 1y fetch yields, 0.89pp. 126 = 6 trading months — first day a user has a defensible number. | `σ/√(2T)` Gaussian; doc carries the fat-tail caveat (κ≈30 ⇒ ~1.9× wider; still ≪ any mean-term SE) |
| Beta + R² | **T ≥ 126** (same aligned window) | Inherits the Σ window; regression needs the same sample. | OLS: `σ_ε / √(Σ(x−x̄)²)` |
| Diversification ratio DR² | inherits Σ sufficiency | Same matrix, same window. | **null by decision** — delta-method SE for a ratio of quadratic forms is not defensible at our T; documented, not computed |
| Risk contribution | inherits Σ sufficiency | Same matrix. Plus the Σ conditioning rule below. | null (same decision) |
| HHI / effective-N (weight concentration) | **none** — pure accounting of today's weights | No estimation involved; `basis: "weights"`. | null always |
| Benchmark volatility (context metric, §5) | T ≥ 126 | Same formula as σₚ on the benchmark leg. | `σ/√(2T)` |
| Tier-2 realised max drawdown | **≥ 2 snapshots** | Descriptive statistic, no inferential claim — but `window_days` is mandatory and comparisons across different windows forbidden. | null always (descriptive) |

**Σ conditioning rule:** LW shrinkage is applied at every T/N, but
`sufficient` additionally requires **T/N ≥ 5** (e.g., 25 holdings need 126 obs
→ 5.04 ✓; 40 holdings need the 1y window). Ledoit–Wolf (2004) validates
shrinkage well below this; 5 is the conservative retail-book floor.

**Short-history holding rule (recent IPO etc.):** a holding with < T_min
observations is **dropped from Σ**, weights renormalised over the remainder,
and the metric is marked `partial: true` with `dropped_holdings: [...]`.
If dropped weight exceeds **20% of invested value**, the whole Tier-1 block
returns `sufficient: false` — a Σ that ignores a fifth of the book is not the
user's portfolio.

**R² companion flag (not a sufficiency condition):** `R² < 0.20` sets
`low_explanatory_power: true` on the beta block. Beta still ships — with the
flag, and the Finding's copy must say what it means.

## 2. Estimator pins (closes m4, m5)

- **Weight convention (m5):** `w` spans **total portfolio value, cash
  included as a zero-vol row**. The user is shown the risk of their whole
  book as displayed in the app; the invested-only alternative inflates every
  number for cash-heavy users and contradicts the tile copy. Verified in r1:
  Euler identity holds exactly with a cash row (Σ contributions = 1.000000,
  cash = 0.0000). Risk-contribution percentages are computed against σₚ of
  the total book and additionally reported per invested sleeve in the
  detailed section (labelled, never mixed).
- **Benchmark:** one series, `SPY` (adjusted close — dividends included,
  avoids the ^GSPC price-only inconsistency), date-aligned by inner join on
  candle timestamps; misaligned or short → beta block `sufficient: false`,
  never silently re-gridded (defect 7).
- **Ledoit–Wolf (m4):** hand-roll the closed form — **2004 =
  constant-correlation target**, stated by citation; identity target is the
  2003 paper and is not what we ship. Intensity clamped to [0,1]; the shrunk
  matrix is PSD by convexity (convex combination of PSD matrices) — one line
  in the doc closes the non-PSD worry. `numpy` is **declared explicitly** in
  `backend/pyproject.toml` (it currently arrives only transitively via
  yfinance — a removal there would silently break the engine; degrade-loudly
  applies to dependencies too).
- **Annualisation:** √252 applied only to trading-day series; the snapshot
  job writes trading days only (gate on candle timestamps, per scope 3a).

## 3. Uncertainty contract — corrected schema (closes m2)

```json
{
  "metric": "portfolio_volatility",
  "value": null,
  "standard_error": null,
  "n_observations": 0,
  "window_days": 0,
  "sufficient": false,
  "partial": false,
  "dropped_holdings": [],
  "low_explanatory_power": null,
  "basis": "holdings",
  "engine_version": "cr136.v1"
}
```

Hard rules:

- `sufficient: false` ⇒ `value` and `standard_error` are **null**. Never
  `0.0` — a zero is a number an agent can narrate; null is not (this is what
  makes serialisation-boundary enforcement structural, attack surface 6).
- `partial: true` ⇒ `dropped_holdings` non-empty, and every surface (API
  consumer, Room context, Finding, journal payload) carries both.
- `engine_version` on every block — old journal entries stay interpretable
  after the estimator changes.

## 4. LLM / CR137 prompt contract

"Agents narrate, never compute" is only real if the context handed to the LLM
is pre-digested. Structural rules, in enforcement order:

1. **Strip before assembly.** The context builder drops any metric block with
   `sufficient: false` *before* prompt construction. The model never sees the
   number, the null, or the metric name — there is nothing to narrate.
2. **Comparisons are precomputed, not derived.** Agents are forbidden from
   arithmetic, so any comparison the product wants stated must be a metric in
   the API. Ship one context metric: **benchmark volatility** (same window,
   same estimator). "23% vs the market's 15%" is then a citation, not a
   computation. No ratios beyond this — if a comparison isn't in the payload,
   it isn't said.
3. **Prompt skeleton (system side, verbatim slots):**

   ```
   You are the AMI analyst team filing a Portfolio Health finding.
   You may only cite numbers present in PORTFOLIO_CONTEXT below.
   Never compute, estimate, extrapolate, or compare beyond what is present.
   Never make return predictions or performance claims.
   Volatility, beta, diversification and risk contribution are estimates
   over the stated window — always keep the window attached.
   If a metric is absent, the data was insufficient — do not mention it.
   PORTFOLIO_CONTEXT: {stripped_metric_blocks}
   FINDING_SECTIONS: {section_specs}   # §5 templates + triggered rules §6
   ```

4. **Output is structured, not free prose:** the model returns the Finding as
   sectioned JSON matching §5's templates; the renderer (not the model) owns
   number formatting. Template placeholders are filled from the same stripped
   context — the model selects and orders, the deterministic layer
   interpolates. This is the CR046 discipline applied to prose.

## 5. The Finding — presentation plan

The user-facing artefact is a **critical financial analysis of the whole
portfolio**, filed like a report from their analyst team. Five mandatory
sections; required items per section below. Brand voice: numbers over
adjectives; every number traceable to a metric id in the payload.

**§5.1 Headlines** (3–5 one-liners, each = one number + its plain meaning)
- Required items: portfolio volatility with benchmark volatility alongside;
  top risk contributor as "X% of risk vs Y% of money"; effective independent
  bets (DR²) next to raw holding count; realised max drawdown **with its
  window**; beta with R² flag if set.
- Rules: no adjectives of judgement ("dangerous", "healthy"); a headline with
  a `partial` metric carries the partial marker.

**§5.2 Executive summary** (4–8 sentences, descriptive only)
- Required: risk posture sentence (σₚ vs benchmark); diversification sentence
  (DR² vs holding count — copy must honour the m3 caveat: "effective
  independent bets", never a literal bet count promise); concentration
  sentence (top contributor); window + sufficiency disclosure sentence.
- Forbidden: advice verbs (recommendations live in §5.5 only), any
  mean-return or performance claim, any number not in context.

**§5.3 Detailed math analysis** (one block per metric)
- Required per block: value, `standard_error` where defined, `n_observations`,
  `window_days`, estimator name + citation (Markowitz; Ledoit–Wolf 2004;
  Choueifaty & Coignard; CAPM), one-line "what this measures", data-quality
  notes (`partial`, `dropped_holdings`, `low_explanatory_power`).
- Also required once per section: the shrinkage disclosure line ("covariance
  estimated with Ledoit–Wolf shrinkage for a short sample") and the
  gross-of-fees line (no fee/slippage deduction exists in the sim — Rev 2
  review found this; disclose wherever performance-adjacent numbers appear).
- This section is what the app's lessons cross-reference (CR054 M11/M12) —
  same metric names, same formulas.

**§5.4 Conclusion** (2–4 sentences)
- Ties the three threads: risk level, diversification quality, concentration.
- Must restate the window and any sufficiency limits. **No new numbers** —
  every figure cited already appeared above.

**§5.5 Actionable recommendations** (deterministic rule engine, §6)
- Required per recommendation: the trigger values shown ("because NVDA is 62%
  of your risk at 30% of your money"), the `based_on` metric ids, and a
  severity band. One to three recommendations per Finding; none triggered ⇒
  the section says so plainly (never manufactures a suggestion).

Presentation surfaces: the Portfolio Health card (already scoped, item 6 of
the CR) carries §5.1 headlines + entry point; the full Finding is a detail
view. Any `sufficient: false` block renders the explicit "not enough data
yet" state — never a blank, a zero, or a number.

## 6. Recommendation rule engine (deterministic — the LLM never invents advice)

Rules fire on the stripped metric context; templates are fixed strings with
value slots. Initial rule set (thresholds pinned here, tunable in one
constant block):

| Rule | Trigger | Template (slots in braces) |
|---|---|---|
| R1 concentration | top contributor risk_share ≥ 40% | "{ticker} is {risk_share}% of your portfolio's risk at {weight}% of its value. Trimming it reduces total risk more per dollar than any other single change." |
| R2 correlated cluster | DR² < 2.0 and holdings ≥ 8 | "You hold {n} positions but only {dr2} effective independent bets — they move together. Adding {count} positions in the same sectors will not change this; a genuinely different exposure will." |
| R3 beta band | β ≥ 1.3 with R² ≥ 0.2 | "Your portfolio amplifies the market: β = {beta}. A 10% market move has historically meant ~{beta×10}% for this book over the window." |
| R4 cash drag (vol) | cash weight ≥ 40% | "{cash}% in cash dilutes every risk number above. These metrics describe a smaller invested sleeve than your total book suggests." |
| R5 data limits | any `partial: true` | "Metrics exclude {dropped} (insufficient history). Treat the numbers as describing {covered}% of your invested value." |

LLM role: select ordering and phrasing within the triggered templates only.
Thresholds live in code with known-answer tests (fire/no-fire at boundaries).

## 7. Journal storage plan

Every generated Finding is persisted to the user's journal — the app already
has the machinery (`journal_entries` table, `JournalStore.append`, schema
enum `EntryType` validated at the schema layer over a plain String column, so
**no migration needed** for a new value).

- New `EntryType.PORTFOLIO_HEALTH_ANALYSIS = "portfolio_health_analysis"`.
- `title`: "Portfolio Health — {as_of date}"; `ticker: null`;
  `agents_involved`: the CR137 roster when the Room narrates it, empty list
  for the deterministic-only Finding; `tags`: `["portfolio_health",
  "cr136"]`.
- `payload`: the **full stripped metric context** (every block with
  uncertainty fields + `engine_version`), the triggered rule ids with their
  slot values, and the five rendered sections as markdown. Storing the
  context verbatim means the entry is self-explaining forever — no
  re-computation, no dependence on later engine versions.
- **Idempotency:** at most one entry per `(portfolio_id, as_of)`; re-runs
  same-day update nothing (finding generation keys off the same trading-day
  snapshot discipline as scope item 2). Keyed to `portfolio_id` and **never
  spans a reset** — same rule as the value snapshots (a wiped account does
  not inherit the old account's findings).
- Surfacing: entry appears in the existing journal timeline; opening it
  renders the stored sections, not a live re-generation. User annotation
  reuses the existing `/note` endpoint untouched.

## 8. Cohesion map

```
holdings + market data ──► metrics engine (this CR, deterministic)
     │                         │ uncertainty contract on every block
     │                         ▼
     │                   GET /v1/portfolio/health/{user_id}
     │                         │
     │            context builder (strip insufficient, §4.1)
     │                         │
     │        ┌────────────────┼─────────────────┐
     │        ▼                 ▼                 ▼
     │   Health card      CR137 Room         Finding renderer
     │   (headlines)      (narrate only,     (5 sections from
     │                    prompt contract)    templates §5–6)
     │                                          │
     │                                          ▼
     │                              journal_entries row (§7)
     ▼
portfolio_value_snapshots (Tier 2, trading-day gated)
```

- **Versioning:** `engine_version` in every metric block, journal payload,
  and Finding — estimator changes never make old artefacts ambiguous.
- **Degrade-loudly matrix:** mock market-data mode → engine refuses entirely
  (CR040); partial history → `partial` + disclosure everywhere; insufficient
  → null + strip + "not enough data yet"; benchmark misalignment → beta block
  insufficient, never re-gridded.
- **Sequencing unchanged:** CR136 engine first, CR137 Room consumes it; the
  Finding renderer works with or without the Room (deterministic templates
  stand alone — the Room adds debate, never numbers).
