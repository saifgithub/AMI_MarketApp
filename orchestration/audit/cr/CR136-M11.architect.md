## 1. Why this lane exists — and the case for returning it

**Scope first, honestly.** Rev 4's named audit scope is **M02 and M05 only**
(the two math-critical modules). Every other CR136 lane, this one included, is a
risk-based extension raised by Saiful. If the argument below does not hold,
**return this lane as misallocated effort** — I would rather spend the round on
a module users touch.

The argument is that **M11 is the module that decides whether the other ten
audits mean anything at ship time.** Three concrete things:

1. **The live cross-check is the only evidence that will ever exist that the
   shipped engine's arithmetic is right on real data.** M02's COMPLETE was
   granted against checked-in fixture literals. Fixtures prove the engine
   matches its fixtures; by construction they cannot prove the fixtures
   describe the arithmetic an independent reader would do, and they say nothing
   about the live book. `cr136_live_crosscheck.py` is the one artefact that
   closes both gaps — and it is scheduled to run **exactly once**, at
   promotion, with nobody double-checking its verdict. A harness that prints
   `PASS` when it should not is a false all-clear on the whole estimator stack.
2. **The cold-start ordering constraint decides whether Tier 2 ever starts.**
   `run_portfolio_snapshot_tick` resolves `as_of` from `latest_trading_day()` =
   `max(date)` over SPY rows in `price_history_daily`, mock-source rows excluded
   in real mode (`price_history.py:485-502`). On a fresh Alpha DB that is
   `None`, so the tick writes nothing on **every** run until a health evaluation
   of a book *that holds something* warms the table — and M10's backfill does
   not, because it fetches through its own unadjusted provider. Get the order
   wrong and the F16 bias series, which is Tier 1's entire validation layer,
   silently never accumulates while the app looks fine.
3. **The checklist is the only record of what has and has not been verified.**
   Phases 2, 3, 4.1 and 4.5 are all deferred (Mac off LAN, no devices). What
   gets shipped on is this file's ticks.

**And the silence argument, which is the one that decides it.** This repo's
recurring failure class is a defect that is dark for weeks because nothing goes
red: DEF210 ~10 weeks, DEF038 and DEF063 each dark for *months* for want of one
`docker-compose.yml` line. Every failure mode above is in that class. Worse:
§3.4.2 below is a live instance of it **inside the ship gate itself** — the
harness prints `PASS — every published metric agrees to 2 dp.` and exits 0 in
states where it compared three of the five level metrics to nothing at all. A
gate that can pass without checking manufactures exactly the darkness this
project keeps paying for, at the single moment everyone is most inclined to
believe it.

**The counter-argument, stated fairly.** M11 changes no app behaviour. Its
script never runs in production, never runs in CI, and has never run at all —
the Mac has been off the LAN for the whole build. A defect here cannot reach a
user directly; it can only fail to *catch* one. An auditor who thinks the right
allocation is the code users touch should say so and bounce this lane, and I
would accept that reading.

## 2. What the module is, and the decisions worth challenging

### 2.1 The harness is independent of the arithmetic, deliberately dependent on the hygiene

`cr136_live_crosscheck.py` re-implements EWMA covariance, σₚ, β, R², TE, DR² and
Euler risk shares in numpy from Rev 4's formulas and **imports nothing from
`app.trading_math`** — the code under test. λ, √252 and the 504-return cap are
retyped as literals (`:83-87`) rather than imported, because the constants
module re-exports from `trading_math`; if a constant moves, the script failing
IS the signal.

The one deliberate dependency is the **data-hygiene** filter: `_load_closes`
imports `_MOCK_SOURCE` from `app.services.price_history` and skips mock rows
when `settings.use_real_market_data` (`:123-140`), mirroring the engine's
`_load_rows` (`price_history.py:171-175`). That was M11's own adversarial pass
(`a4265fd5`) — before it, the harness recomputed from bars the engine correctly
refused and would have reported a FAIL against an engine that was right. **This
asymmetry is the design decision worth challenging**: arithmetic independent,
hygiene mirrored. I think it is right — a hygiene difference makes the
comparison a different question, not a stricter one — but it is a judgement
call and it is the seam where the "independent" claim is weakest.

### 2.2 The weights identity between the harness and the engine

The harness does not recompute position values; it takes the holding set,
`invested_weight`, `covered_invested_value`, `total_value` and `cash_fraction`
from the payload and rebuilds the LEVEL vector as
`invested_weights × (covered_invested / covered_total)` (`:331-335`). The engine
builds `w_level = p.value / covered_total` (`portfolio_health.py:370-373`) from
`v_weights = p.value / covered_invested`. The two are the same number by
identity, so the harness is checking the **covariance and the derived
functionals**, not the weighting. Stated plainly because it bounds what a PASS
means.

### 2.3 R0 stays the deliberate SHARE/LEVEL exception — and M11 is why its sector half is now tested

R0 is the one deliberate exception to the seam register's SHARE/LEVEL rule:
total-value weights, because the trade gate's own denominator is
`position_pct(market_value, portfolio_value)` (`portfolio_rules.py:222-233`).
M05's lane led with the single-name half of that. M11's adversarial pass found
the **sector** half had never been cross-checked against
`allocate_by_sector` + `sector_concentration_cap`, and added the two tests
(`a4265fd5`) that QA-A and QA-B below exercise. Same rule, same justification,
same failure class, one column over.

### 3.4 What I would attack if I were the auditor

1. **The harness has ZERO automated coverage, and its one structural property is
   protected by prose.** Measured: `grep -rln "cr136_live_crosscheck" backend/tests/`
   returns **nothing**. Not one test imports it, references it, or parses it.
   The docstring says *"must not import `app.trading_math`"* and M11 §5 says
   *"acceptance greps enforce"* — **there is no such grep**, not in
   `promotion_checklist.md`, not in any test. CR038's rule is that prompt
   instructions are not controls; a docstring instruction is the same object.
   DEF141 is this repo's own precedent (five audit pins stranded off the
   collection path, none had run since the hour it was written) and
   `test_cr136_dart_parity.py` — M09's round-2 fix, a *backend* test that reads
   a source file to enforce a cross-boundary contract — is the pattern that
   would close it in about twenty lines. **If you find one thing in this lane, I
   expect it to be this.**
2. **`PASS` is printed for metrics that were never compared.**
   `cr136_live_crosscheck.py:391-404`: `unchecked` rows (`api is None`) are
   printed and then **excluded from the exit code**. `failures` only counts rows
   where `api is not None`. Concretely: `beta`, `r_squared` and `tracking_error`
   are all gated on `benchmark_usable`, a state the engine explicitly models
   (`INSUFFICIENT_BENCHMARK_MISALIGNED`, `portfolio_health.py:427-431`). On such
   a book the script compares σₚ and the risk shares, skips three of five level
   metrics, and prints `PASS — every published metric agrees to 2 dp.` and
   returns 0. The same happens on any payload **key rename** — `r_squared` is
   read off `blocks["beta"]["r_squared"]` (`:357`) with no schema pin between
   the harness and M07. That is DEF210's shape one layer further out, sitting in
   the ship gate. Is "published" doing enough work in that sentence for a
   `PASS` to mean what a reader will take it to mean?
3. **`_joined_returns`'s docstring claims it mirrors M04's join order. It does
   the opposite.** Harness (`:143-167`): per-ticker trim to the newest 505
   dates FIRST, then intersect, then trim. Engine `_join`
   (`portfolio_health.py:302-307`): intersect the **full** date sets, trim
   **once** at the end. For dense series the two coincide, which is why nothing
   has surfaced; for a sparse or gappy series they do not. The usual
   consequence is a window-count mismatch → `exit 2`, whose message reads
   *"Re-run after the history warmer has caught up, or investigate M01's join"*
   — i.e. the operator is sent to the wrong place. In the corner where the
   counts coincide but the date sets differ, it is a spurious `exit 1`
   attributed to the engine. Grade the comment as much as the code: a comment
   asserting a mirror that is not one is worse than no comment.
4. **The live checklist is stale at HEAD, and nothing makes that visible.**
   Phase 0.1 pins `a4265fd5 / 2240 passed`; HEAD is `c56e2c41 / 2269 passed`
   (§3.2). Phase 1.4 ("Both lanes read `VERDICT: COMPLETE`") is still `☐` even
   though both now do — `CR136-M02.auditor.md:7` **COMPLETE (round 1)** and
   `CR136-M05.auditor.md:191` **COMPLETE (round 2)**. Checklist 1.1 says
   "26 scripts + README index"; the directory holds **27** `.py` files + the
   README. None of these is dangerous on its own. The question is whether a
   ship gate whose evidence silently ages is a gate at all, and whether Phase 0
   needs a "re-measure at the actual ship SHA" instruction rather than a
   recorded number.
5. **The `_today_utc` clamp — check the boundary, not the intent.**
   `test_cr136_health_gate.py` now uses `max(now + offset, day_start)`. That is
   correct only because `portfolio_health_stats` counts with
   `_as_utc(r.created_at) >= day_start` — **inclusive**
   (`journal_store.py:377-381`). Flip that to `>` and the fixture that was fixed
   for flakiness becomes flaky again in the other direction. Worth confirming
   the two are coupled deliberately.
6. **The mock-source mirror's `real_mode` resolution.** The harness reads
   `bool(settings.use_real_market_data)` at `:123`; `latest_trading_day` reads
   it the same way (`price_history.py:494`), but `_load_rows` takes `real_mode`
   as a **passed argument** (`price_history.py:171`). Confirm every caller
   derives it identically, or the harness and the engine can disagree about
   which rows exist while both believe they agree.
7. **The deferred half.** Phases 2, 3, 4.1 and 4.5 are `☐` and unrunnable from

## A1 — the ship gate compared a strict subset and still exited 0

Confirmed exactly as reported. `unchecked` rows were printed and then dropped
from the exit code, and the verdict sentence was unconditional.

**Fix** (`cr136_live_crosscheck.py`):

- an unpublished metric now **fails the run** unless it is named in a new
  `--allow-unchecked` flag. The waiver names metrics; it is not a blanket
  "allow any subset", so the operator states which absences they expect and the
  gate still fails on any other.
- `checked: N` became `compared: N of M`, and both PASS sentences now carry the
  count: `PASS — all 7 metrics published and agreeing to 2 dp`, or, when a
  waiver is used, `PASS — all 4 of 7 metrics agree; 3 expected-unpublished and
  waived by --allow-unchecked: [...]`.
- a metric named in `--allow-unchecked` that turns out to BE published is
  printed as a stale allowance, so a waiver cannot quietly outlive its reason.
- the FAIL message names the two readings the operator has to choose between:
  the engine withheld the metric (a real finding) or the payload renamed a
  field this harness reads (schema drift with no pin — DEF210's shape).

**The test the submission argued could not exist.** §4 said this deliverable
"has no test that can be made to fail". `backend/tests/unit/test_cr136_live_crosscheck_gate.py`
— 6 tests — stubs `_fetch_health` and `_load_closes` and drives `main()`, which
is the auditor's own probe made permanent. The control payload is built from
the **harness's own helpers** over the same stubbed closes, so it genuinely
agrees; a gate that simply failed on everything would satisfy every negative
test and prove nothing.

Covered: the reachable benchmark-drop route, the renamed-field route, the
waiver, the full-payload control, a real numeric disagreement, and an
independence guard reading the harness's import list.

**Mutation results** — 3 mutations, all killed, and one of them corrected a
weak test:

| # | Mutation | Result |
|---|---|---|
| MUT-1 | `surprises = []` (restore the exact defect) | **2 failed** |
| MUT-2 | `surprises = list(unchecked)` (waiver ignored) | **1 failed** |
| MUT-3 | print the FAIL, `return 0` | **1 failed** |

MUT-1 killed only **one** test on first run. The renamed-field test was passing
for the wrong reason: replacing the whole `beta` block also replaced its value,
so the run failed on a numeric disagreement and never exercised the rename. It
now mutates the field name in place on an otherwise-agreeing payload —
`beta_block["rsq"] = beta_block.pop("r_squared")` — and MUT-1 kills two. Worth
recording, because a test that passes for the wrong reason is exactly what A1
was.

**Checklist 2.9's existing reading stands.** That run printed `checked: 9,
FAILED: 0` with no `not checked` line — nothing was unchecked, so the old gate's
verdict was sound for that book. Under the new gate the same run reads
`compared: 9 of 9` / `PASS — all 9 metrics published and agreeing to 2 dp`. The
fix does not retroactively weaken the evidence already recorded; it makes the
next run's exit code mean what 2.9 always assumed it meant.
