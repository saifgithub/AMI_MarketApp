## 1. What shipped

`_returns_on` takes close-to-close ratios on the grid `_join` produces, while
`annualize_vol` multiplied by √252 unconditionally — so a return spanning k
trading days was annualised as though it spanned one. DEF213's Arm D localised
the whole 1.372×/1.424× gap in that constant rather than in anything about the
path.

`grid_periods_per_year(window_days, n_observations)` derives the rate from the
same two numbers `GRID_DENSITY_MAX` already computes.
`annualize_vol(sigma_period, periods_per_year=TRADING_DAYS_PER_YEAR)` now takes
it explicitly; `compute_health` derives it once per evaluation and threads it
through all four call sites (`portfolio_volatility`, `benchmark_vol_ann`,
`sigma_inv_ann`, every `mcr`).

**This changes published numbers.** `scripts/cr136_live_crosscheck.py` (M11's
independent numpy recomputation) was updated too — left on hardcoded 252 it
would have started false-failing every live book at promotion.

## 2. The claim I most want re-derived, because I checked it and could be wrong

**M05's rule thresholds are unaffected — every one of them.** They were all
calibrated against σ (R1's ±1.5pp band, R2's DR² bands, R3's β base and SE
multiple, R4's cash band), so "annualisation changed" sounds like it must move
them.

I did not take the build's word. I traced it: `rule_inputs_from_context` reads
`risk_share_pct`, `effective_bets`, `beta`, `se_beta`, `r2` — and every one is
computed on the **pre-annualisation** EWMA matrix. `euler_contributions` is
`wᵢ(Σw)ᵢ / σₚ²`, a ratio of same-scale Σ entries and therefore *exactly*
invariant under any scalar annualisation; `dr_squared` likewise; beta and its
standard error come from the regression on daily returns. `mcr_values` **is**
annualised but is a separate display value that no rule reads.

So the bands hold for any book. **Please re-derive this independently rather
than re-reading my trace** — if it is wrong, every user's portfolio is
silently mis-graded, and it is the one claim in this CR where being wrong is
invisible.

## 3. What the build declared it did NOT do, which I am forwarding rather than
   burying

Both of these were flagged honestly by the build rather than quietly papered
over, and I have left both open:

- **`GRID_DENSITY_MAX` stays at 1.65, re-justified but NOT re-derived.** Its
  original job (refuse because √252 will not fit) is moot once annualisation
  fits any density. The new argument is different: every metric from Σ shares
  the same EWMA λ=0.97, whose 22.8-period half-life stretches into more real
  calendar time as the grid sparsens, eroding the recency claim that justified
  EWMA over an equal-weight window. At the threshold, periods run ~1.135 real
  trading days, stretching the half-life to ~25.8 periods — inside the ~66-day
  effective sample already disclosed as normal, so 1.65 is conservative under
  the new argument too. **Nobody has derived 1.65 *from* that argument**; that
  needs a live fetch plus a Monte Carlo sweep an offline session cannot run.
  Worth your judgement on whether keeping a number whose original
  justification has evaporated is acceptable, or whether it should be retired
  until it can be re-derived.
- **Tier 2's F16 bias test** (`portfolio_snapshot.bias_z_stats`) de-annualises
  stored `predicted_vol_ann` with an unconditional √252 and cannot reconstruct
  the grid rate, because `PortfolioSnapshotRow` does not persist `window_days`.
  Needs a schema migration. Bounded to roughly ±5% against the estimator's own
  disclosed ~6.3% sampling noise, and it is a manually-run dev script, not a
  live gate — so nothing automated broke. Please sanity-check that bound.
