## MAJOR A1 — the runbook's spot-check cannot validate what the full run writes

§5.3 raises this and it is real. Proven from source, not inferred:

```python
:405   if user_id is not None:
:406       query = query.where(SimPortfolioRow.user_id == user_id)
:407   portfolios = session.execute(query).scalars().all()
...
:423   earliest: date | None = None
:424   for p_row in portfolios:              # <- the FILTERED set
:432       first = _first_event_date(events)
:433       if first is not None and (earliest is None or first < earliest):
:433           earliest = first
...
:468       prices[ticker] = provider.unadjusted_daily(ticker, earliest)
```

`earliest` is the minimum first-event date over the portfolios **this run
selected**. `--user-id` narrows the set, which moves `earliest` later, which
shortens the price window, which changes what `_close_on_or_before` can carry
forward. Days that the full run values from a real prior close fall back to
`last_event_price` in the spot-check.

Measured on two books where the second holds a ticker whose bars stop before its
own first trade:

```text
spot-check  --user-id B   planned 5  inserted 5  ledger_priced 5  terminal OK   exit 0
            printed total_value 10000.00 on every day   (the 100.00 execution price)

full run    --apply        wrote for the SAME five days
            total_value 11000.00                        (carried from the 200.00 close)
```

Both runs print `terminal OK`. Both exit 0. Nothing names the difference.

**Why MAJOR.** This is not a hypothetical ordering: `promotion_checklist.md`
row 2.8's acceptance sequence is *dry-run all → real-user spot-check with
`--user-id` → `--apply`*, and it was executed that way on 2026-08-06 with the
spot-check recorded as evidence (*"22 rows, trading days only … cash/invested
reallocation coherent, terminal matched"*). The step that exists to catch a bad
backfill reads a different valuation from the one that ships, and reports
success either way. A verification step that verifies something else is the
CR040 question answered wrong: the operator ends up believing the numbers were
checked.

The shipped test `test_two_books_sharing_a_ticker_each_get_their_own_early_history`
pins the run-global-earliest design deliberately (`:671-675`: *"one window per
ticker per run, taken from the RUN-GLOBAL earliest event date"*). The design is
fine; what is missing is that the window is a property of the **run**, so a
filtered run is a different question. Either fetch from the unfiltered earliest
regardless of `--user-id`, or make a filtered run say so in its output.

## MINOR m1 — an empty grid under `--apply` exits 0 and prints `committed.`

§5.4, reproduced:

```text
CR136 M10 portfolio-snapshot backfill — APPLY
trading-day grid: EMPTY — nothing can be valued this run
user 3ebdcc65-…  days none  planned 0  inserted 0  ...  terminal OK
  rows inserted           : 0
committed.
EXIT_CODE = 0    ROWS_WRITTEN = 0
```

The grid is empty when `price_history_daily` holds no SPY rows — the cold-start
state M11 §1.2 is entirely about, and one this project has actually been in.

I considered MAJOR and rejected it, deliberately and against my own instinct to
be consistent with M11's A1. The difference is that **nothing false is printed**:
`rows inserted : 0` is quantitative, unmissable and true, and `committed.`
accurately describes an empty transaction. M11's gate asserted *"every published
metric agrees"* when it had compared four of seven. Here the exit code is the
only misleading channel, the documented contract is *"0 clean; 2 terminal-guard
failure"*, and an empty grid genuinely is clean under it. No unattended consumer
keys on this exit code today. Worth a distinct exit code anyway.

## MINOR m2 — the blocker's own regression test does not catch the blocker

QA-C re-keys the price cache `(ticker, start)` → `ticker`:

```text
QA-C  key = (ticker, start) -> key = ticker      1 failed, 25 passed
      kills: test_the_price_cache_is_keyed_by_ticker_and_start
      SURVIVES: test_two_books_sharing_a_ticker_each_get_their_own_early_history
```

The surviving test's own docstring presents it as *"the audit's blocker, with the
REAL provider"* and argues `FakeProvider` cannot catch it. It cannot catch the
re-key either, and for a structural reason: every ticker is fetched from the
run-global `earliest` (`:466-468`), so within a single run there is exactly one
`start` per ticker and the key's second component never varies. The cache-key
test is the only guard, and it is the unit test the narrative treats as the
weaker of the two.

## MINOR m3 — two silences the plan cannot distinguish

- `ledger_priced` gates nothing. Six occurrences: one init, one increment, four
  inside f-strings. No branch, no return, no exit code reads it — while
  `mismatched` does (`:619`, `:638 return 2 if mismatched else 0`). My A1 probe
  printed `ledger_priced 5` alongside `terminal OK` and returned 0. A book valued
  entirely off stale execution prices is reported as a clean backfill.
- `_close_on_or_before` returns `(0.0, False)` for "no bar at all" (`:286`) and
  the caller branches on `close <= 0.0` (`:324`). A stored close of exactly zero,
  a negative close and "no data" are the same event on that path. Given m3's
  first half, the plan cannot tell an operator which one happened.
