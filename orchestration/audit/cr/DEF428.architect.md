# DEF428 — audit lane (onboarding Q6 typed drawdown answers silently became 30%)

**SCOPE:** def

**TIER: B.** Backend-only, single-file behaviour change confined to the anonymous onboarding
interview's Q6 answer parsing (`concierge_engine.py`). No auth, billing, migration or
compliance-perimeter change. Raises to Tier A if a MAJOR is found — the risk this defect
actually carries is a silently-wrong risk mandate reaching `_derive_risk_score` and the
compliance floor downstream, which is why it is filed at all despite the small diff.

**SHA:** base `b5de455c` on `main`; lane commit(s) to be captured at commit time on this
worktree's branch. Review with `git diff b5de455c..<lane-sha> -- backend/app/services/concierge_engine.py backend/tests/unit/test_concierge_engine.py docs/defect/`.

**depends-on:** DEF418 (found by U68 auditing that lane's round 1 — see
`orchestration/audit/cr/DEF418.auditor.md`, "Recorded, not scored" section). **Promoted:** no
(backend; ships via `/promote-to-alpha` after this verdict).

## What and why

U68, auditing DEF418 (Q6's five-tier suggestion widening), flagged but deliberately did not
score a pre-existing, unrelated bug in the same function: `_parse_drawdown_pct` matched only
the six chip substrings ("10"…"50", "no cap") and fell back to a bare `30` for anything else.
Q6 is the interview's one free-text numeric question ("What's the largest temporary loss you
could stomach…") — a user who typed "5%", "45%", "83", or "12.5%" instead of tapping a chip got
a **30%** drawdown mandate with nothing disclosed, indistinguishable from someone who
deliberately chose 30%. That mandate value feeds `_derive_risk_score`'s nudge table
(`_DRAWDOWN_PCT_TO_TIER`) and the readback the user is asked to confirm — a wrong number that
looks like a normal answer is worse than an obviously-broken one, because nothing prompts the
user to look twice.

**Root cause:** `_parse_drawdown_pct` was written keyword-first (does the text contain "50"?
"40"? …) against a fixed six-value set, with a catch-all default rather than a real parse. It
predates free-text ever reaching this function in practice — the six chips normally cover it —
so the free-text path was effectively untested against anything but the exact chip strings.

## Fix

`backend/app/services/concierge_engine.py`:

- **`_parse_drawdown_pct(text: str) -> float | None`** (was `-> int`, implicit default `30`):
  now a real parse. `"no cap"` / `"no limit"` / `"uncapped"` → `100` (unchanged from before).
  Otherwise a regex (`-?\d+(?:\.\d+)?\s*(?:%|percent)?`) pulls the first explicit number,
  optionally signed (so `"-10%"` is rejected, not silently abs'd) and optionally decimal,
  with or without a `%`/`percent` suffix. A result outside `(0, 100]` or no match at all →
  `None`. A whole number returns `int`; a fractional one rounds to 1 decimal place (`"12.5%"`
  → `12.5`) rather than either truncating or inventing more precision than was typed.
- **`process_answer`**: Q6 is special-cased before `_record_answer` runs — if
  `_parse_drawdown_pct` returns `None`, the function returns immediately with
  `next_step == ConversationStep.Q6_MAX_DRAWDOWN` (i.e. **does not advance**) and a new
  clarifying message (`_q6_clarify_text()`, same `Q6_CHIPS`), and `session.answers` is left
  untouched — `max_drawdown_pct` is never written for an unparseable answer. A parseable
  answer behaves exactly as before (records the value, advances to Q7).

This is the interview's **first re-ask** of any kind. There was no existing "unparseable
answer" precedent to follow in this state machine — every other `_classify_*` function
(`_classify_goal`, `_classify_horizon`, `_classify_drawdown_response`, `_classify_regret`,
`_classify_concentration`, `_parse_constraints`) has a keyword-based "safe default" and the
state machine always advances via `_NEXT_STEP`. Those defaults are defensible because the
underlying signal is a preference classification with no single objectively-wrong answer;
Q6 is different because it is the one place the interview asks for, and the user supplies,
an exact number that becomes a stored mandate figure — a wrong guess there isn't an
approximation, it's a fabrication. `process_answer`'s signature and every other caller
(`app/api/onboarding.py::submit_answer`) are unchanged — it already forwards whatever
`next_step`/`message` it's given generically, so no API-layer change was needed for the
re-ask to work.

DEF418's five-tier suggestion table (`{1:10, 2:20, 3:30, 4:40, 5:50}`), `Q6_CHIPS`, and
`_DRAWDOWN_PCT_TO_TIER` are untouched and re-verified passing.

## Attack surface (please probe)

1. **The regex's number-extraction order** (`re.search`, first match wins) — a string with
   two numbers ("between 20% and 30%, say 25") takes the FIRST one (20), not an average or the
   last. Confirm that's the right call versus, say, refusing when more than one plausible
   percentage appears — the brief says "parse any explicit percentage 1–100 the user types
   exactly," which this reads as "the one they led with," but that's a judgement call worth a
   second look.
2. **`session.answers` never getting `max_drawdown_pct` on repeated unparseable answers** — if
   a client somehow calls `confirm_readback` or otherwise reaches `_build_readback_summary`
   while still stuck on Q6 (shouldn't be reachable via the normal flow, since `next_step` never
   left `Q6_MAX_DRAWDOWN`), the summary's `session.answers.get("max_drawdown_pct", 30)` default
   is untouched — same "30 if truly absent" fallback as before this fix, at a point in the flow
   that should be unreachable. Worth confirming the API layer genuinely cannot skip ahead.
3. **Decimal rounding to 1 place** (`round(pct, 1)`) — confirm this is the "documented rounding"
   the brief accepted rather than an arbitrary choice; no spec pins a specific decimal count for
   `max_drawdown_pct` elsewhere in the schema.
4. **`_DRAWDOWN_PCT_TO_TIER.get(dd, 3)`** — a parsed non-chip value like `45` or `12.5` now
   reaches this dict, misses (it only has the six chip keys), and falls back to the neutral
   nudge tier 3. That's pre-existing behaviour (DEF418 didn't touch it, this lane doesn't
   either) but is now reachable by more inputs than before, since free-text values are honoured
   rather than being forced through a chip value first — confirm tier-3-neutral is the intended
   nudge for an off-grid percentage rather than, say, interpolating between the two nearest
   chip tiers.

## Architect follow-up before submission (commit on `main` after merge `cc70d55f`)

The worker's parser read the first number anywhere in the answer, so "I could lose $10,000"
became a 10% mandate and "5k" became 5%. That is the same silent-wrong-value class DEF428
fixes. `_parse_drawdown_pct` now accepts a number only if it is marked "%"/"percent" or is
the entire answer. A range ("10-15%", "10 to 15 percent") takes its lower, stricter bound,
matching the existing "between 20% and 30%" → 20. Anything else re-asks. The re-ask copy
changed from "I didn't catch a number there", which is wrong after "$10,000", to
"I need that as a percentage of your portfolio".

New test: `test_def428_money_and_loose_numbers_are_not_read_as_a_percentage`. With the
`fullmatch` fallback mutated back to `re.search`, 1 test fails; with the fix, 38 pass.
`test_concierge_engine.py` plus 4 onboarding files: 50 passed, exit 0.
