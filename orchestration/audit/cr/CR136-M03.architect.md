## 1. Why this lane exists — and when to return it

**Scope note first.** Rev 4's named audit scope is M02 and M05 only (Risk class:
*"Independent audit remains warranted for the estimator module (M02) and rule
engine (M05) specifically"*). M03 is here on a risk argument raised by Saiful,
not on Rev 4's authority. **If the argument below does not hold, return this
lane as misallocated effort** — that is a legitimate verdict and I would rather
have it than a courtesy pass.

The argument is not that M03's arithmetic is hard. It is that **M03 is the only
module in CR136 whose failures are invisible by construction**, and this repo's
recurring failure class is precisely a defect that stays dark because nothing
goes red (DEF210: ~10 weeks; DEF038 and DEF063: months each, both for want of
one line of config forwarding).

Four concrete shapes, all silent:

1. **It writes to a table nobody reads yet.** A wrong row is not a wrong screen
   today; it is a wrong screen in 21 trading days, when the tile finally turns
   on. Between now and then the corrupt state and the correct state are
   indistinguishable to every observer.
2. **It is a background task with no caller.** Nothing invokes it, so nothing
   can fail to invoke it visibly. Verified: **no test anywhere asserts the
   `asyncio.create_task(_portfolio_snapshot_tick())` registration exists**
   (`grep -rn "create_task\|_portfolio_snapshot_tick" backend/tests/unit/` hits
   only unrelated files and M03's own import of the tick function). Deleting one
   line in `main.py` turns the entire Tier-2 half of CR136 off with a green
   suite. That is the DEF063 shape exactly, and this repo already has the
   counter-pattern for it — `test_cr055_room_holdings.py:250`
   `test_runner_injects_portfolio_snapshot_at_every_call_site` greps source for
   the wiring.
3. **Its liveness is hostage to an undeclared cross-module dependency.**
   `latest_trading_day()` (price_history.py:485) is `max(date)` over SPY rows in
   `price_history_daily`. The only writer of that table is
   `portfolio_health._gather_inputs` (portfolio_health.py:752), guarded by
   `if tickers:` — **an empty book fetches nothing**. So an Alpha where no user
   holds anything never warms the table, `latest_trading_day()` stays `None`,
   and the tick writes zero rows forever while logging one warning an hour.
   `get_benchmark_series` exists (price_history.py:471) and has **no caller in
   `backend/app`**. M11 recorded the ordering in a promotion checklist; per
   CR038 a checklist is not a control.
4. **It is the validator of everything else.** F16's whole point is that
   `predicted_vol_ann` written down at prediction time makes M02/M04 auditable
   later. If M03 stores the wrong number, or scores it against the wrong
   denominator, the audit trail for the two modules Rev 4 *did* scope silently
   certifies whatever it is fed.

The honest counter-argument, which the auditor should weigh: the module is small

## 2. What the module is, and the decisions worth challenging

### 2.1 One row per (portfolio, trading day), keyed to `portfolio_id`

`run_portfolio_snapshot_tick` (portfolio_snapshot.py:85) resolves the day from
the benchmark's own candle grid, sweeps `SimPortfolioRow`, and writes at most
one row per portfolio per day. Idempotency is check-before-insert with the
unique constraint `uq_pvs_portfolio_asof` as the DB backstop.

Keying to `portfolio_id` rather than `user_id` is what makes a series
structurally unable to span a reset: `reset_portfolio` is destroy-and-recreate
and the replacement gets a fresh UUID. `SimPortfolioRow.user_id` is
`unique=True` (models.py:341), so the one-portfolio-per-user assumption the tick
relies on (it captures marks by `user_id` while writing under `portfolio_id`) is
enforced by the schema, not by convention. Worth confirming you agree that
holds.

**Deliberate, and challengeable:** pre-reset history is destroyed, explicitly,
in `reset_portfolio` — not merely left to the FK cascade, because sqlite does
not enforce FK pragmas and the test DB would otherwise disagree with production
about what a reset destroys.

### 2.2 The two drawdowns are structurally separated

`drawdown_pct` (stored column) is the sim's vs-STARTING-CAPITAL number;
`realised_max_drawdown` (Tier-2 block) is peak-to-trough over stored
`total_value`. $10k → $15k → $12k reads **0.0** and **20.0**. The guard is not a
comment: T9 builds the points with `drawdown_pct = 99.0` as a sentinel and
asserts 99.0 appears in no Tier-2 output field. Nothing in `tier2_blocks` or
`bias_z_stats` reads the field.

### 2.3 Rolling, never expanding (Rev 4 F10)

`window = points[-TIER2_MDD_WINDOW_SNAPSHOTS:]`. An expanding maximum is a
monotone ratchet — a user who has taken a 40% drawdown can never move the number
again, so the metric they are being taught to manage is one their behaviour
cannot change. Floor is 21 snapshots (Rev 4: the old "≥2" floor was vacuous);
below it `sufficient: false`, `value: null`, never `0.0`.

### 2.4 Units — verified end-to-end, three layers

Tier-2 `realised_*` are **already percent**, and that is honoured at every layer
I could read: `max_drawdown_pct` returns positive percent (returns.py:41–57) and
`realised_return` is `(v[-1]/v[0] − 1) × 100`;
`METRIC_VALUE_UNIT` marks both `UNIT_PERCENT`
(portfolio_health_constants.py:212–213); `kMetricValueUnit` marks both
`HealthMetricUnit.percent` (portfolio_health.dart:48–49); `health_card.dart:404`
carries the comment *"Already a percentage on the wire (M03 §3.5) — never scaled
again."* `predicted_vol_ann` is the opposite pin — a **decimal fraction**,
because `bias_z_stats` divides a fraction return by it and the units cancel only
that way. M04 hands it over as `float(block["value"])` of
`portfolio_volatility`, which `METRIC_VALUE_UNIT` marks `UNIT_FRACTION`. So the
M06 round-0 "1969.00%" class is not reachable through this seam as built —
**but nothing automated enforces it**, and that is the point of QA-A/QA-D below
only indirectly. Attack it.

### 2.5 Doc↔code disagreements — the code is the truth

Recorded rather than fixed, because the code is right and the doc is stale:

- **Module doc §3.4 defines `PredictedVol` in `portfolio_snapshot.py` with a
  field `sigma_ann`.** As shipped the class is **M04's**
  (`portfolio_health.py:100`) and the field is **`predicted_vol_ann`**. M03
  imports nothing from it and duck-types `predicted.predicted_vol_ann` at row
  construction. The seam register pins the *function* signature, not the field
  name, so nothing across that boundary is checked — see §3.3.5.
- **Module doc §3.4 says the default trading-day source is `market_data.py`.**
  It is `app.services.price_history.latest_trading_day` (price_history.py:485).
- **`_tier2_block` emits `insufficient_cause`**, which is not in the seam
  register's contract-1 field list. M04's blocks carry it too, so it is a
  CR-wide contract extension the register never recorded. The register claims to
  override the module docs; it does not override the code, and here the code
  moved.
- **Module doc §3.5 pins `sufficient` for `realised_return` as "≥ 2 points".**
  Shipped: `len(window) >= 2 and values[0] > 0.0` — a stricter, correct guard (a
  zero denominator has no return).

### 2.6 Snapshots are written on mock prices; Tier 1 refuses them

Deliberate and asymmetric, and the decision I most want challenged.
`build_health_context` **refuses outright** in mock mode (portfolio_health.py:799)
— CR040 answered correctly. `run_portfolio_snapshot_tick` **writes the row
anyway**, stamping `source`, on the argument that the sim's realised value is
the sim's realised value regardless of where the price came from. The
consequence: `tier2_blocks` and `bias_z_stats` **never read `source`**, so a
252-row window mixing `mock_walk` and `yahoo` rows is presented as realised
history with no marker at all. Ask whether that is the CR040 question answered
the wrong way one layer down.

Compounding it: `SimEngine._aggregate_source_from_quotes` (sim_engine.py:308)
returns `"mock_walk"` for an **empty** quote dict, so a cash-only book in
real-data mode is stamped `mock_walk`. Provenance on those rows is wrong in the
pessimistic direction.

### 3.3 What I would attack if I were the auditor

Ranked. The first two are the ones I actually expect to survive.

1. **The Tier-2 blocks never reach the wire — M03's read half is dead code
   today.** `compute_health`'s returned `blocks` (portfolio_health.py:670–692)
   contains no `realised_max_drawdown` / `realised_return`; `_health_envelope`
   wraps that context unmodified (portfolio.py:119); the Finding route passes
   `metric_blocks=list(context["blocks"].values())` (portfolio.py:200).
   `grep -rn --include="*.py" "tier2_blocks\|equity_curve" backend/` finds
   **zero non-test callers**. Downstream, `portfolio_finding.py:296` renders the
   Rev 4 §F1 headline *"rolling-window max drawdown with window (Tier 2, when
   sufficient)"* — which Rev 4 marks **Required** — from a block that can never
   arrive; `health_card.dart:401` branches on presence and its own comment says
   *"until M07/M03 wire the realised blocks through, its absence is a silent
   absent tile"*. M03's doc §4 assigns the serving to M07, and **M07's doc never
   mentions Tier 2 at all** (`grep -n "tier2\|Tier 2\|realised" M07_api_gating.md`
   → no hits), so no module owns the seam. The failure is time-delayed and
   perfectly disguised: for the first 21 trading days it is indistinguishable
   from "not enough data yet", and after that it just stays off. Is this M03's
   to fix, M07's, or a spec hole — and does the CR ship with a Rev 4 "Required"
   §F1 element unreachable?
2. **`bias_z_stats` assumes adjacent points are one trading day apart, and never
   checks.** It iterates `zip(points, points[1:])` and never reads `as_of`
   (portfolio_snapshot.py:329). The tick only ever writes `latest_trading_day()`
   and **never backfills a missed day**, so any outage or deploy spanning more
   than one trading day leaves a hole; the hole's k-day return is then divided by
   a one-day vol, and each such z is inflated ~√k. A correctly calibrated engine
   would read OUT OF BAND on the F16 acceptance test, and the tempting "fix"
   is to inflate σ. Silent in both directions. Gaps are the expected case here,
   not the exotic one.
3. **The tick's liveness has no guard.** Two independent single points of
   silence: (a) no test asserts the `create_task` registration in `main.py`
   (§1.2); (b) `latest_trading_day()` depends on SPY rows that only a health
   evaluation of a **non-empty** book writes (§1.3). Either one alone means zero
   Tier-2 history, indefinitely, with a green suite.
4. **The "the value row is always written" invariant does not hold as claimed.**
   The `try/except Exception` around the vol provider covers only
   `resolve_vol(user_id)` (portfolio_snapshot.py:158–165). The attribute reads
   `predicted.predicted_vol_ann` / `.n_observations` / `.engine_version` happen
   later, inside the insert block, under the **outer** per-portfolio handler. So
   a `PredictedVol` whose field M04 renames raises `AttributeError` there and
   **no value row is written at all** — the exact outcome the docstring and the
   commit message say can never happen ("realised history is never hostage to
   the vol engine"). T4 only exercises a *raising* provider, never a malformed
   *return*. Nothing type-checks that seam (§2.5).
5. **`except IntegrityError: skipped += 1`** (portfolio_snapshot.py:192) counts
   *every* integrity error as "already had today's row" — a Postgres FK
   violation from a portfolio reset landing mid-sweep, a NOT NULL, anything. The
   stats dict is this job's only production observability, and it would read
   `skipped_existing` while writing nothing. On sqlite (no FK pragma) the same
   race inserts an orphan row instead.
6. **`insufficient_cause` is always `"short_window"`.** When
   `max_drawdown_pct` returns `None` for a non-positive value in the series
   (returns.py:47), sufficiency flips false but the cause still says the window
   was short. A wiped book — the case where max drawdown matters most — is
   reported to the user as "not enough data yet".
7. **`n_observations` counts snapshots, not returns, on both Tier-2 blocks.**
   Right for the MDD floor (Rev 4 counts snapshots) but for `realised_return`
   there is exactly one return over the window, and Tier-1 blocks count returns.
   `health_card.dart` renders `mdd.nObservations` into the user-facing
   "not enough data" note — is it the number the copy claims?
8. **`backend/scripts/cr136_bias_test.py` has no test at all.** Its
   verdict-suppression rule (`n < 252` ⇒ "band does not apply yet") *is* the F16
   honesty control and is asserted nowhere. It is also the artefact M11's
   promotion checklist runs live.
9. **Lifecycle/concurrency (protocol's stateful-construct clause).** The tick is
   a process-lifetime `asyncio` task calling a blocking sweep via `to_thread`,
   opening a session per portfolio. Two api replicas, or a slow sweep overlapping
   its own next interval, both resolve to the unique constraint — which returns
   the mislabel in item 5. Also confirm `settings.portfolio_snapshot_interval_seconds`
   is read once per loop (it is, main.py:164) and that an exception inside the
   sweep cannot exit the `while True`.
