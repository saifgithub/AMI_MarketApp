### MAJOR-2 (foreign #2 — REAL). A soft-deleted journal entry is resurrected by the retry's append fallback

`update_by_reference`'s docstring promises "a user who deleted their Room's journal entry
gets no entry resurrected by a later CIO retry" (`journal_store.py:339-341`) and returns

fresh entry (`room_runner.py:7142-7148`), collapsing "never existed" (should not happen)
and "the user deleted it" (a real, reachable state) into one branch. User data-agency
defect, directly contradicting the primitive's own documented guarantee. Real, verified.

### MAJOR-3 (foreign #3 — REAL). Mobile never parses `cio_retry_available` / `cio_retried` from GET payloads — the retry offer dies on the reconnect path

`RoomRunSnapshot.fromJson` (`mobile/lib/models/room.dart:195-221`) omits both keys (and
`refunded`), and `_recoverViaPolling`'s final `copyWith` (`room_providers.dart:625-633`)
sets no cio flags — so after a dropped-socket recovery (the 90 s polling path) an eligible
run renders `done` with `cioRetryAvailable == false` and the button never appears. The
backend computes the flags on GET and list (`api/room.py:431,537`) — a delivered surface
with no consumer. The architect disclosed "RoomRunSnapshot not extended" as out of the
brief's scope, but the polling-recovery path is IN the live-session scope and loses the
offer exactly where outages cluster (flaky networks), and the 4 h eligibility window
implies come-back-later is an intended flow. MAJOR — the feature's core promise ("offer
the option to the customer") is undeliverable except to a user watching live when the
`done` event arrives.

### MAJOR-A. An exception after a successful outage refund triggers a second refund (credit mint)

`room_runner.py:6740-6771`. Round 1 added 3 things inside the `else:` of the outage refund's
try/except: the suffix `model_copy`, `_build_cio_context_snapshot(ctx, profile)` and
`_persist_run(run)`. That `else:` is inside `run()`'s outer `try` (`:6470`). So any exception
there reaches `except Exception` at `:6915`. That handler sets the run to FAILED and refunds
`run.credit_cost` a second time (CR039, `:6924`). Before CR237 this branch only held a
`logger.info` (`9cf6b71b`), so the problem is new in this lane.

Measured on a real `start_run`, in both P5 and P5b:

```
ledger rows: credits_spent 8 'room:AAPL'
             credits_refunded 8 'room_outage_no_verdict:<id>'
             credits_refunded 8 'room_failed:<id>'
spent=8 refunded=16 net=-8   balance 150 -> 158
status=failed  refund_recorded=True  events: [('error', ...)]   (the verdict event is never sent)
```

The user gains one Room's cost. The verdict they were owed becomes an `error`, and the run is
FAILED, so no retry is offered. What triggers it: any fault in that window. A DB error on the
second write is one. A profile value that Postgres JSONB rejects when the snapshot persists is
another. `_persist_run` does not swallow errors (`:5036`). The snapshot is the first time the full
`profile` dict is written to JSONB. I did not show that any specific value (for example NaN) is
reachable on Alpha. The mint follows from the code structure, and P5 and P5b measure it.

Fix direction (the architect chooses): the CR039 refund in `except Exception` should skip when
`run.refund_recorded` is already True. That guard is structural and covers every future line in
the `else:`. Or wrap the post-refund bookkeeping in its own try/except that logs. Pin it with a
test in the shape of P5b.

### New findings (all MINOR)

**MINOR-1. The codec's "refuse, don't coerce" contract has two holes: `pd.NaT` and `(str, Enum)`.**
`cio_snapshot_codec.py:44` returns any `str` subclass as-is, so a str-Enum goes through
`json.dumps` as its value and comes back as a plain `str`, with a different `format()`. `:56` checks
`isinstance(value, datetime)`, which `pd.NaT` satisfies. It encodes as `"NaT"` and fails only on
decode (B5: the snapshot is stored, every retry raises, and the run stays eligible for the window).
Neither type is reachable in today's profile (see "Real-profile reach"). Fix direction: exact-type
checks (`type(value) is datetime` / `date` / `str`), and refuse `Enum` before the `str` branch.
Pin both in the codec tests.

**MINOR-2. A fault between the retry's persist and its verdict stream leaves the client told "failed"
and the Journal stale.** The success branch persists at `room_runner.py:7259`, banks at `:7271`
outside any `try`, updates the Journal in a `try`, and streams at `:7303`. I made
`bank_verdict_outcome` raise on the retry and drove the real route (C1). Result:
`events=[agent_done, error, done]`, error text "The Chief Investment Officer couldn't be asked
again — something failed on our side…". But `done` carried `cio_retried: true`, the row holds
APPROVE, and the Journal entry is still the outage one (`journal_summary_has_APPROVE=False`). So
the client's copy is false and the Journal diverges from the row for good. It is not reachable today,
because `bank_verdict_outcome` swallows its own exceptions (`verdict_outcomes.py`, `except Exception`
at the body's end). Only a raise while its arguments are evaluated (`_reference_close`,
`getattr(mandate.horizon…)`) would get there. Fix direction: make the bank call non-fatal, the way
`run()`'s bookkeeping is.

**MINOR-3. Mutation survivors: codec strictness and the snapshot's strict-JSON check are unpinned.**
N3, N5, N6 and N8 survive (see the table). The one that matters for Postgres is N5: removing
`json.dumps(snapshot, allow_nan=False)` (`room_runner.py:4368`). The docstring (`:4356-4358`) says
this line is what refuses a non-finite trader level. `JsonB` (`app/db/base.py:23-32`) sets no
serializer, so SQLAlchemy's default `json.dumps` would write a bare `NaN`, which Postgres's JSON
grammar rejects. Both persist attempts would then fail, and the row would land in the under-report
state above. I did not measure this on Postgres (there is none on the Mac), and I have not shown a
NaN trader level is reachable. It needs one test with a NaN `trader_entry`. N6 (numpy branch
removed, so `np.int64` / `np.bool_` would be refused and the retry offer lost) and N3 (lookup by
class name, not identity) need one codec test each. N8 (the snapshot's inner `except` narrowed to
`TypeError`) is covered by the same NaN test.

**MINOR-4. The encoded snapshot ships on every GET and list payload.** `RoomRun.cio_context_snapshot`
(`schemas/room.py:289`) goes out through `response_model=RoomRun` (`api/room.py:422`, `:544`). The
client never reads it, because the retry reads the row server-side. Measured on a synthetic but
realistic run (B6: the mock profile plus `DividendGrowth`/`BuybackPrice` plus 10 headlines with
~600-char summaries): snapshot **12,420 bytes** (headlines 8,720) out of a **17,171-byte** `RoomRun`,
against 5,138 bytes without it. So about 72% of that run's payload is unused. It is present only
while a run is an eligible outage PASS, since success clears it. It also puts the internal
`__cr237__` tags on the public wire. Nothing sensitive is in it: the portfolio block is rebuilt fresh
on retry and is not in the snapshot, and the rest is the user's own run's fact sheet. The architect
disclosed this under "Not in this round". I record it as MINOR so it is tracked. Fix direction:
`Field(exclude=True)`, or drop it in the two routes.

"Not in this round", the rest: I agree the detached pump is unneeded, since ordering closes MINOR-1.
