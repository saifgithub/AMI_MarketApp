### MAJOR-1 (foreign #1 — REAL). A successful retry wipes `sheet_state` / `reference_price` / `next_convene_delta` off the persisted verdict

`run()` stamps all three onto every completed run's verdict post-loop
(`room_runner.py:6638-6643`) — including the original outage PASS, so the persisted row
carries them. `retry_cio_step` replaces `run.verdict` with `_run_cio_step`'s fresh verdict
and persists it (`:7112`) WITHOUT re-stamping — despite computing `ctx.next_convene_delta`
itself (`:7037-7039`) and using `_reference_close(profile)` for banking (`:7129`). The
next convene's `_room_delta_context` reads exactly these fields (`:5787-5793`) → the delta
line silently degrades to absence on the run after a retry, and the verdict card loses the
stamped fields the outage verdict carried. Silent data regression on the verdict path —
Tier A. Real, verified line by line.

### MAJOR-2 (foreign #2 — REAL). A soft-deleted journal entry is resurrected by the retry's append fallback

`update_by_reference`'s docstring promises "a user who deleted their Room's journal entry
gets no entry resurrected by a later CIO retry" (`journal_store.py:339-341`) and returns
`None` for soft-deleted rows. Its only caller treats `None` as "missing" and appends a
fresh entry (`room_runner.py:7142-7148`), collapsing "never existed" (should not happen)
and "the user deleted it" (a real, reachable state) into one branch. User data-agency
defect, directly contradicting the primitive's own documented guarantee. Real, verified.

### MAJOR-3 (foreign #3 — REAL). Mobile never parses `cio_retry_available` / `cio_retried` from GET payloads — the retry offer dies on the reconnect path

`RoomRunSnapshot.fromJson` (`mobile/lib/models/room.dart:195-221`) omits both keys (and
`refunded`), and `_recoverViaPolling`'s final `copyWith` (`room_providers.dart:625-633`)
sets no cio flags — so after a dropped-socket recovery (the 90 s polling path) an eligible
run renders `done` with `cioRetryAvailable == false` and the button never appears. The
backend computes the flags on GET and list (`api/room.py:431,537`) — a delivered surface
with no consumer. The architect disclosed "RoomRunSnapshot not extended" as out of the
brief's scope, but the polling-recovery path is IN the live-session scope and loses the
offer exactly where outages cluster (flaky networks), and the 4 h eligibility window
implies come-back-later is an intended flow. MAJOR — the feature's core promise ("offer
the option to the customer") is undeliverable except to a user watching live when the
`done` event arrives.

### MINOR-1 (foreign #4 — real, downgraded to MINOR). No `live` guard on the retry

`retry_cio_step` computes `live = gateway.has_real_provider()` at retry time
(`room_runner.py:7043-7044`); a False there routes `_run_cio_step` through the scripted
`_assemble_verdict` branch (`:4784-4785`), persisting/banking/journaling a canned APPROVE
as the CIO's real verdict. Reachable only if the provider registration is removed and the
process restarted inside the 4 h window — on Alpha the vLLM provider is registered, and in
that misconfigured state fresh rooms would run scripted too, so this is the app's
sanctioned mock mode rather than a CR237-specific hole. Still, the honest shape is a
refusal ("the CIO is unavailable — try later"), since the retry exists precisely because a
non-live answer was not acceptable the first time. MINOR.

### MAJOR-A. An exception after a successful outage refund triggers a second refund (credit mint)

`room_runner.py:6740-6771`. Round 1 added 3 things inside the `else:` of the outage refund's
try/except: the suffix `model_copy`, `_build_cio_context_snapshot(ctx, profile)` and
`_persist_run(run)`. That `else:` is inside `run()`'s outer `try` (`:6470`). So any exception
there reaches `except Exception` at `:6915`. That handler sets the run to FAILED and refunds
`run.credit_cost` a second time (CR039, `:6924`). Before CR237 this branch only held a
`logger.info` (`9cf6b71b`), so the problem is new in this lane.

Measured on a real `start_run`, in both P5 and P5b:

```
ledger rows: credits_spent 8 'room:AAPL'
             credits_refunded 8 'room_outage_no_verdict:<id>'
             credits_refunded 8 'room_failed:<id>'
spent=8 refunded=16 net=-8   balance 150 -> 158
status=failed  refund_recorded=True  events: [('error', ...)]   (the verdict event is never sent)
```

The user gains one Room's cost. The verdict they were owed becomes an `error`, and the run is
FAILED, so no retry is offered. What triggers it: any fault in that window. A DB error on the
second write is one. A profile value that Postgres JSONB rejects when the snapshot persists is
another. `_persist_run` does not swallow errors (`:5036`). The snapshot is the first time the full
`profile` dict is written to JSONB. I did not show that any specific value (for example NaN) is
reachable on Alpha. The mint follows from the code structure, and P5 and P5b measure it.

Fix direction (the architect chooses): the CR039 refund in `except Exception` should skip when
`run.refund_recorded` is already True. That guard is structural and covers every future line in
the `else:`. Or wrap the post-refund bookkeeping in its own try/except that logs. Pin it with a
test in the shape of P5b.

### MAJOR-B. A retry crashes for any run whose original Room had 2 or more live news headlines

`room_runner.py:4360` stores the whole `profile` in `cio_context_snapshot`. When news is LIVE,
`profile["news_headlines"]` holds `LiveHeadline` NamedTuples (`room_runner.py:1599`). JSONB stores
them as arrays, so they come back as lists. The retry's CIO prompt then renders them:

```
room_runner.py:7115 retry_cio_step -> :4562 _run_cio_step -> :7843 _draw_pm_candidates
-> :7980 _stream_pm_response -> room_prompts.py:1678 build_room_messages
-> :2923 _format_profile -> :3498 _catalyst_line -> news_context.py:433 format_headline
AttributeError: 'list' object has no attribute 'title'
```

In P6 the snapshot's headline type was `list`. The row stays the outage PASS and stays eligible.
The retry route has no handler around the generator (`api/room.py:475-521`), so the SSE body
aborts with no `error` event and no `done` event. The button stays on offer for the 4-hour
window, and every tap crashes the same way. This is a silent failure on the feature's main path
(CR040). It hits every paid-tier run with live news, including the `live+4` runs DEF432's probes
were built on. The CIO prompt renders `news_headlines[1:]`, so a feed with exactly one headline
does not crash. I know that from reading the code; I did not measure it. The suite misses this
because no CR237 test gives `run()` a LIVE `news_feed`. The docstring at `:4348-4351` says the
profile is "already JSON-safe". That is only true of `field_state`, not the whole dict.

Fix direction: serialise the snapshot's profile to JSON-native values, and rebuild the typed values
in `_rebuild_ctx_from_snapshot`. Or store the formatted headline strings. Pin it with a retry test
that has a LIVE news feed.

### MINOR-1. The retry is tied to the client connection, and its verdict event goes out before it is persisted

`retry_cio_step` runs inside the SSE response (`api/room.py:475`), not as a detached pump like
`run()`. `_run_cio_step` yields `verdict` (`:4923`) before the retry's success branch persists it
(`:7167-7175`). A disconnect at that yield leaves the verdict unpersisted. In P7 the client saw
APPROVE, the row stayed the outage PASS, and the run was still eligible, so the user could
re-roll the CIO. The window is one chunk send, and no credits move. A drop anywhere earlier in
the retry just wastes the CIO call. That is acceptable, but it should be written down.

### MINOR-2. A still-down retry streams a verdict that differs from the one it persists

### Abuse paths (goal check)

- **Repeat retries:** a still-down retry stays eligible and moves no credits (P2). Once a retry
  succeeds, the snapshot is cleared and the verdict is no longer outage-shaped, so the next retry
  is refused (P1).
- **Retry after a successful CIO:** refused, on the same runner and on a fresh one (P1).
- **Retry across a restart:** refused after success (P1, fresh runner). The mid-retry restart
  case is covered by the submission's `test_restart_mid_retry…`, which B3 kills.
- **Concurrent retries:** refused within one process (P2). Across two processes, both run (P3).
  Credits are unaffected and the topology is single-process today.
- **Free Room without an outage:** not reachable. `cio_context_snapshot` has one writer
  (`:6760`), inside the successful outage-refund branch and gated on `is_llm_outage_verdict`.
  Eligibility requires the server-set `overridden_from_llm` flag plus the sentinel prefix.
- **Double refund:** reachable through MAJOR-A.
