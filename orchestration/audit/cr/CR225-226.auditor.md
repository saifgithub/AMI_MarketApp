### What must hold, and whether it does

- **Real unit ids only on a production build. Holds.** `AdMobConfig.resolve` downgrades
  `mode=live` to Google's test units on any channel other than `production`
  (`admob_config.dart:185-205`). Only `build_testflight.sh:157-160` and `build_playstore.sh:157-160`
  set the channel. It becomes `production` only with `--production` or `RELEASE_CHANNEL=production`,
  which is the same definition the RevenueCat test-key refusal and the games gate already use, so it
  cannot be split from them. `install_iphone.sh` never forwards the define (grepped), and no other
  script, CI file or doc sets it. **Mutation, mine:** gate disabled, 3 failed.
- **Consent before the first request, for every format. Holds in the code.** `requestFill` awaits
  `_ensureReady()` (UMP `gatherConsent`, then `configureAndInitialize`) before any load, and the
  banner goes through the same `requestFill` (`admob_ads_service.dart:66,121-146`). Concurrent
  first requests share one memoised future.
- **Paid tiers see no banner. Holds.** The banner passes the same plan gate as the other six
  placements; its frequency-cap carve-out comes after that gate (`ads_providers.dart:118-130`).
  **Mutation, mine:** banner exempted from the plan gate, 5 failed.
- **Age treatment is never misdeclared as child-directed. Holds, by read.** `AdAgeTreatment.none`
  maps to `TagForChildDirectedTreatment.unspecified` for both fields
  (`admob_real_sdk.dart:63-78`). In `google_mobile_ads-9.0.0`, `TagForChildDirectedTreatment` and
  `TagForUnderAgeOfConsent` share the codes `yes=1 / no=0 / unspecified=-1`
  (`request_configuration.dart`), so reusing one tag for both fields is exact.
- **Full mobile suite at +111:** `01:52 +1688: All tests passed!`, EXIT=0. The lane's six files:
  68 passed.

### MINOR-1 — the banner requests with the NATIVE ad unit id, so AdMob can never fill it (latent)

`case AdFormat.banner:` loads with `adUnitId: _setup.nativeAdUnitId`
(`admob_ads_service.dart:83-91`). That holds in both modes: in test mode it is Google's
native-advanced test unit (`…/3986624511` iOS, `…/2247696110` Android, `admob_config.dart:132-135`).
AdMob ad units are format-bound, and Google publishes separate banner test units. A banner load
against a native unit should fail with AdMob's format-mismatch error, and then fall back to house
fill every time.

The lane calls this *"under-serves rather than over-serves"*. My reading is that it never serves.
I have not measured it: there is no device, console or test device in the audit sandbox. It is
latent, because no build sets `ADMOB_MODE`. And when it happens it is silent, since `debugPrint`
is a no-op in release. **Fix before `ADMOB_MODE` is ever set:** add a banner unit-id define (with
the banner test ids in `_testSetup`), and a test asserting a banner request carries the banner id.

### MINOR-2 — the two consent-perimeter behaviours this CR made reachable have no guard

- **Banner consent gating is untested.** The *"consent gates every load"* tests use only
  `walletAndPlan` and `journalEmptyState` (`admob_ads_service_test.dart:154-200`). **Mutation,
  mine:** banners skip `_ensureReady()`, and the service plus banner tests stay green (`+24`). The
  code is correct today. A regression would request banners before UMP consent, on every page.
- **The `_tagFor` age remap is untested.** **Mutation, mine:** `none` mapped to `yes`, and
  `test/services/` plus the structural test stay green (`+205`). It is correct by read, as above.
  An untested line is what decides whether the app declares itself child-directed.

**Fix:** a banner case in the consent-gate group, and `_tagFor` made `@visibleForTesting` with a
three-row test.
