# DEF439 — auditor verdicts (only Alpaca PAPER accounts can be linked, D-075)

## Round 1 — auditor u66

**SHA audited:** `9085bea3` (main, the DEF439 merge). It contains fix `92f18b70` and test
`7cf861cd` on base `981307b5`. I audited in a detached scratch worktree, `ami_wt/DEF439-u66a`,

**Tier A.** A linked account can receive market orders (D-071). If a live account were
admitted wrongly, real orders could be routed to it.

### The questions this lane has to answer

1. Is it impossible to link a **live** Alpaca account through every entry path? The paths are
   the API key, OAuth, relink, and a credential stored before this fix.
2. Can any order or cancel route to a live account? The places to check are the trade ticket,
   the Orders section and the client.
3. How is "paper" decided, and can that decision fail open? Cases: a network error, a 404, an
   unknown value, a stale flag.
4. Is the backend also on the order path, which would make a client-only check bypassable?

### How "paper" is decided

Paper is decided **by the host only**. `isAlpacaPaperHost` (`alpaca_client.dart:69-72`) returns
true when the host ends with `.alpaca.markets` and contains `paper`. The key prefix is only a
courtesy check (`_isLiveKeyId`, `alpaca_connect_screen.dart:279-280`). No stored label or
cached "is paper" flag exists: every reader re-derives the answer from `creds.baseUrl`
(`isLinkedToPaperAccount`, `:395-398`). The in-memory `_cached` credential in
`AlpacaCredentialStore` is cleared by `clear()`, which the Relink path calls, so it cannot hold
a stale paper verdict.

Fail-closed probes. Each input went through `isAlpacaPaperHost` and Dart's `Uri` in a
throwaway test inside the worktree, which I deleted afterwards:

```
false | api.alpaca.markets                                  (live)
false | paper@api.alpaca.markets                            (userinfo)
false | paper-api.alpaca.markets@api.alpaca.markets         (userinfo)
false | api.alpaca.markets#.paper.alpaca.markets            (fragment)
false | api.alpaca.markets?h=.paper.alpaca.markets          (query)
false | api.alpaca.markets/.paper.alpaca.markets            (path)
false | api.alpaca.markets\@paper-api.alpaca.markets        (backslash)
false | paper-api.alpaca.markets.evil.com / paperalpaca.markets / "not a url" / ""
true  | api.alpaca.markets:443@paper-api.alpaca.markets     -> request host paper-api (consistent)
true  | PAPER-API.ALPACA.MARKETS                            (lowercased)
EXIT=0
```

The predicate and the request both parse with Dart `Uri`, so the host that is checked is the
host that gets called. An unparseable URL gives an empty host, which returns false. On the
API-key path, a network error, a 404 or any non-2xx makes `validate()` throw, and nothing is
saved (`alpaca_connect_screen.dart:309-310`). On the OAuth path, a `DioException` makes
`validateOAuthToken` throw before `save()`.

### Q2: orders and cancels never reach a live host. MET, and strong

- `submitOrder` checks the host at `alpaca_client.dart:492` and `cancelOrder` at `:544`. Both
  checks are unchanged from before this lane and are independent of the UI. I mutated each one,
  and each mutation was caught (table below).
- The trade ticket's destination picker is gated on `alpacaLinkedProvider`
  (`trade_ticket_sheet.dart:1397`). The preview fetch re-checks at `:779` before
  `account()`/`positions()` run.
- The Orders section is gated through `_AlpacaGate` on `alpacaLinkedProvider`
  (`alpaca_orders_section.dart:48-53`). The Portfolio account, positions and tab counts are
  gated as well (`portfolio_screen.dart:521-526, 2031-2050`). I found no reader of `account()`,
  `positions()` or `orders()` that skips the gate.
- If a non-paper credential was stored before this fix, `alpacaLinkedProvider` now reads it as
  **not linked**. The picker, the Orders section, the Portfolio card and the Room snapshot all
  go dark for it, and the user sees an amber Relink prompt.

### Q4: backend. There is no order path, so nothing can be bypassed there

`backend/app/api/alpaca.py` has three routes. `/link` exchanges the OAuth code; the token is
not stored. `/link_state` takes a boolean and `/order_log` takes a report. `alpaca_service.py`
makes exactly one outbound call, `httpx.post(settings.alpaca_oauth_token_url)` (`:91`), for the
token exchange. The backend never calls `/v2/orders`, so paper-only is enforced where the
orders are actually sent, on the device. A modified client holding the user's own keys is the
user acting on their own account and is outside AMI's routing. **Not a gap.**

### MAJOR-1: the OAuth gate rests on a false premise. Alpaca's authorize URL does have `env=paper`, and a default token also covers the user's live account

The lane's docstrings and D-075 claim two things. First, that Alpaca's `/oauth/authorize`
"documents no `env=paper` selector". Second, that "a token minted against a live account is
rejected by the paper host with a 401". See `alpaca_client.dart:357-367`,
`alpaca_connect_screen.dart:35-41` and `:607-611`, and `decision_log.md:695-697`. The lane
states the first claim as research ("Alpaca gives no other hook").

Alpaca's own OAuth guide (`docs.alpaca.markets/docs/using-oauth2-and-trading-api`, fetched
2026-09-25) says the opposite. In its authorize-parameter table:

> `env` | Optional | If provided, must be one of `live` or `paper`. If not specified, the user
> will be prompted to authorized both a live and a paper account.

It also says:

> A single Alpaca OAuth token may authorize access to either: One live account, One paper
> account, [or] One live account and one paper account.

`buildAuthUrl` (`alpaca_connect_screen.dart:103-114`) sends no `env`, so the consent screen
asks for **both** accounts, with scope `account:write trading`. The token that comes back is
valid on the paper host, so `validateOAuthToken`'s `GET paper-api/v2/account` returns 200 and
the token is saved. That token also carries trading authority over the user's **live** account.
The gate cannot refuse the default case it was written for. The 401 that the lane tests treat as
"a live-account token" (`def439_alpaca_oauth_paper_validate_test.dart:86`) only happens for an
`env=live`-only grant, and AMI's URL never requests that.

- **Goal 2 still holds.** The OAuth save stores the default paper host
  (`alpaca_connect_screen.dart:615-619`, no `baseUrl`), and `submitOrder`/`cancelOrder` refuse
  any non-paper host. So AMI's code does not route this token to a live venue.
- **Goal 1 fails on this path.** A credential with live-account write authority can be linked.
  The relink detector cannot see it, because the host is paper. The disclosure
  (`app_en.arb` `alpacaConnectDisclosure`: "a live account cannot be linked") and D-075 would
  both be false the day OAuth is enabled.
- **Reachability today: dormant.** `_clientId` is
  `String.fromEnvironment('ALPACA_CLIENT_ID')` (`:63`). No build script in the repo passes that
  define: grep found hits only in backend, docs and `docker-compose.yml`. The file itself says
  enabling OAuth is "a config change". That is exactly what makes a dormant gate with a false
  premise dangerous, so doubt resolves toward MAJOR.

**Fix.**
1. Add `'env': 'paper'` to `buildAuthUrl`'s `queryParameters`, and pin it with a unit test on
   `buildAuthUrl`. It is a pure top-level function, so it can be tested.
2. Keep `validateOAuthToken` as the second layer, but correct its docstring, the file docstring,
   D-075 and the `:86` test name to match what Alpaca actually documents.
3. My mutation M6 shows that deleting the `validateOAuthToken` call from `_exchangeCode`
   survives: the OAuth tab cannot render without the compile-time client id. Either extract the
   exchange→validate→save sequence into a testable function, or say plainly in the lane that
   the ordering is unpinned.

### MINOR-1: `AlpacaClient.validate()` (API key) has no direct test; making it fail open survives

M8 swallows the `DioException` in `validate()`, and all 170 targeted tests pass. The widget
tests override `validate` (`_RecordingAlpacaClient`), and grep finds no test that drives the
real method. The lane calls this the "structural gate" (gate 3), but host restriction is the
real control. Even with a fail-open `validate()`, a live pair would be stored against a paper
host and would get 401 on every call, never a live order. So this is a test gap, not a live
path. Pin it: a 401 from `validate()` must throw with `isAuthFailure`. Relatedly, M16 stores a
live `baseUrl` after a successful validation and also survives. The provider re-check catches
that downstream, but no test asserts that the host which was validated is the host that gets
saved.

### MINOR-2: the Portfolio relink prompt is unpinned

M15 deletes `if (storedNonPaper) return const _AlpacaRelinkPrompt();`

the Settings row. The submission names both surfaces as wired. Without the prompt, a pre-fix

### MINOR-3: the submission says the Orders cancel copy is "untouched", but the diff changed it and it is still English-only

The submission says the CR234 r2 MINOR-4 raw string is "untouched by this fix (out of scope)",
and that `alpaca_orders_section.dart` changed only "to keep compiling/passing". The diff

and MS users still get an English clause inside a translated sentence, which was half of
MINOR-4's complaint. Move it to an ARB key with `retranslate:[ar,ms]`, and correct the
submission's description.

### Things I checked that hold

  prefix tests themselves, and the host gates are independent of it.
- No `mobile/lib` code reads `AlpacaCredentialStore` for a "linked" decision without going
  through `isLinkedToPaperAccount`. `alpacaStoredNonPaperProvider` and `AlpacaSnapshotCache`

### Summary

The trading guarantee, that no order routes to a live account, is **MET and strongly pinned**:
host-based, fail-closed, and every write guard is mutation-killed. The linking guarantee is met
on the API-key path and for stale credentials. It is **not** met on the OAuth path, whose
premise contradicts Alpaca's own documentation (MAJOR-1). That path is dormant today, and the
fix is one query parameter plus a pin. Three MINOR test and copy gaps.
