## MINOR-1 — an unrecognised order state vanishes from every bucket, silently

`ticker_orders` (`ticker_interest.py:104-111`) buckets resting orders with an `if/elif/elif`
over state string literals and **no `else`**:

```python
if state == "filled":            ...
elif state in _PENDING_STATES:            # working, triggered, filling
elif state in _TERMINAL_NOT_FILLED_STATES: # cancelled, expired, rejected
```

An order whose state matches none of the three falls through all of them and is added to
nothing. It does not raise, does not log, and does not appear in any column — it simply is not
counted, while the row it belonged to still renders as a complete picture of that ticker.

**The current vocabulary is exactly right — I checked by running, not reading.** `SimRestingOrderRow`'s
docstring (`models.py:2238`) declares **seven states**, and the lane's two tuples plus the
`filled` literal cover precisely those seven. Writing one order in each of the seven documented
states:

```
7 real states written; buckets total = 7      ← nothing falls through today
```

So this is **latent, not live**. Credit where due: getting all seven right, partitioned
correctly, is the substance of the claim and it holds.

**But the failure mode is invisible when it arrives.** Writing three orders where two carry
plausible future states (`partially_filled`, `pending_cancel`):

```
3 resting orders written; buckets total = 1
filled=0 pending=1 not_filled=0
ORDERS SILENTLY DROPPED: 2
```

Two orders vanished. No error, no log, no zero — the ticker's row just quietly understates. This
is P2/DEF135's mirror: a total that silently undercounts still reads as a true total, and an
admin making a decision from "AAPL: 12 filled, 3 pending, 1 not filled" has no way to know four
more orders existed. It is also the house rule — *an entry without an enforcing check is not
done*. The seven-state coverage is correct and nothing enforces that it stays correct; there is
no test tying these tuples to the model's declared vocabulary.

**This is the fragility the lane nominated.** Its own submission says: *"a manual Python
`if/elif` over `SimRestingOrderRow.state` string literals — the kind of logic that silently
degrades if a state name is mistyped or a bucket is left out."* That reading was right. What the
mutation it ran proves is that the buckets split correctly *today*; it does not catch a state
being added, because no test knows how many states there are supposed to be.

**What would close it.** Either is fine, plus a test that fails without it:
1. An `else` that makes the unknown state loud — count it in an `other` bucket that the UI shows,
   or log a warning naming the state. Degrade loudly (CR040) rather than dropping.
2. A guard test asserting the union of `{"filled"} | _PENDING_STATES | _TERMINAL_NOT_FILLED_STATES`
   equals the seven states the model documents, so adding an eighth fails the suite until it is
   bucketed. This is the "enforcing check" the house rule asks for, and it is three lines.

(2) is the stronger one: it fails at the moment the vocabulary changes, rather than waiting for
someone to notice a total looked low.

## MINOR-2 (NEW, introduced by the round-2 fix) — the `other` bucket is excluded from the ranking key, so an unrecognised-only ticker is truncated out of the response

`ticker_interest.py:130-134`:

```python
ranked = sorted(
    by_ticker.items(),
    key=lambda kv: kv[1]["filled"] + kv[1]["pending"] + kv[1]["not_filled"],
    reverse=True,
)[:limit]
```

`other` is absent from the sum. A ticker whose orders are all unrecognised therefore ranks with
key **0** — below every ticker with a single recognised order — and `[:limit]` drops it.

**Measured, not reasoned.** 24 tickers with 1 `working` order each, plus `GHOST` with **50**
unrecognised orders, plus `QUIET` with **1** recognised order, `limit=25`:

```
limit=25, returned 25
GHOST (50 unrecognised) in view: False
QUIET (1 recognised)   in view: True
GHOST row: None
```

This is not ordinary low-volume truncation. `other` contributes exactly zero to the rank, so the
loudest possible signal — a ticker generating fifty orders in a state nobody recognises — sorts
strictly below the quietest recognised one and leaves the response entirely.

**Why this is the round-1 defect displaced one level, not a new concern.** MINOR-1 was: *a state
outside the documented set is counted nowhere, and an admin reading the totals cannot tell.* The
fix makes the count exist in `by_ticker`. But the admin reads the API response, not the dict —
and for the ticker most likely to expose a vocabulary drift, the response omits the row. The
CR040 intent the fix's own comment states ("it shows up as a nonzero `other` column, not as a
silently-low total") holds only for a ticker that *also* has enough recognised orders to survive
the cut.

**Severity MINOR, same as round 1, and for the same reason:** unreachable today. The guard test
means an 8th state cannot enter `RestingOrderState` without failing the suite, so `other` is
provably 0 in production right now. This is the second line of defence — the one that exists
precisely for the case where the first is bypassed (a raw DB write, a migration, a state written
by an older deployed version). Both round-1 rationales apply unchanged.

**Suggested fix** — one line, include `other` in the key:

```python
key=lambda kv: kv[1]["filled"] + kv[1]["pending"] + kv[1]["not_filled"] + kv[1]["other"],
```

A ticker with unrecognised orders then ranks by its true volume and stays visible. Worth a test
pinning it, in the shape of the probe above: a ticker whose orders are all unrecognised must
appear in the response when its volume would otherwise place it in view.

If instead the intent is that `other` should *never* influence ranking, then say so and surface
the total another way — a top-level `"unrecognised_total"` in the response would do it, and
would be visible regardless of truncation. Either is fine; the current state is the one that
isn't, because the bucket exists but cannot always be seen.
