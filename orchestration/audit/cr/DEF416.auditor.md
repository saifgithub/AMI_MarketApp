### MINOR-1 — the recovery guards a branch the route never takes; the route's own race gives HTTP 500

`POST /v1/auth/apple` and `/google` always pass `user_id=current_user.id` (`api/auth.py:228-233`).
`get_current_user` loads a live `users` row or returns 401. So in `sign_in_with_apple` the lookup
by `user_id` always finds the caller's anonymous row, and control takes the `else:
_attach_apple_sub(row)` UPDATE branch. The new `begin_nested()` / `IntegrityError` recovery sits on
the INSERT branch, and the INSERT branch runs only when that row does not exist.

The lane's race tests pass `user_id=uuid4()`, an id with no row
(`test_def416_oidc_unique_race.py:138,177`). They exercise only the branch the route cannot reach.

I drove the route's real shape on Postgres through the real `AuthService`: two existing anonymous
rows claiming the same `sub`, both reading before either commits.

```
PROBE apple_anon_race:  A -> IntegrityError (UniqueViolation "uq_users_apple_id")  | B -> signed in | rows with sub = 1
PROBE apple_anon_race  retry by A -> B's account (adopted_from = A), rows with sub = 1
PROBE google_anon_race: A -> IntegrityError (UniqueViolation "users_email_key")    | B -> signed in | rows with sub = 1
PROBE google_anon_race retry by A -> B's account (adopted_from = A)
```

And the lane's own shape, on real Postgres blocking (B waits on A's uncommitted key):

```
PROBE apple_insert_race:  A and B -> the same id, rows with sub = 1
PROBE google_insert_race: A and B -> the same id, rows with sub = 1
```

**Consequence.** The fork is closed. A duplicate account can no longer be created on any path.
But the submission's claim that "the loser signs into the winner's account instead of raising"
does not hold for any request a user can send. On the route, the loser gets an unhandled
`IntegrityError` at commit, which surfaces as HTTP 500. The route only maps `ValueError`
(`api/auth.py:234-235`).

It fails loudly and recovers on retry, as measured above. It needs the same Apple or Google
account signing in for the first time on two devices within a few milliseconds of each other.
There is no data loss and no silent state. Hence MINOR.

(On Google, `users_email_key` already rejected this race wherever the token carried an email.
The new `google_id` index covers email-less tokens.)

**Fix:** after `_attach_apple_sub(row)` / `_attach_google_sub(row)` on the found-row branch, flush
inside `s.begin_nested()`. On `IntegrityError`, re-select by the sub, re-key devices from
`user_id` and set `adopted_from = user_id`. That is the same shape as the sequential "row found
by sub" path. Add a race test whose callers hold *existing* anonymous rows.

**Attack surface §3 (device re-key on a lost INSERT race):** it only arises on the unreachable
branch. On the reachable branch, a retry re-keys and adopts correctly (`adopted_from = A` above).
Not scored.

**Attack surface §4 (email-fallback branch):** it updates an already-found row. It can still
violate the index, because a unique index is violated by an UPDATE as well as an INSERT. That is
the same mechanism, and the same retry recovery, as MINOR-1. Folded into MINOR-1.

**Attack surface §5 (`hms_unionid`):** the constraint is additive and nothing writes the column
yet. Its migration ordering is covered by the round trip above. No finding.

### Verdict

The invariant this defect exists for, one identity to one account, is now a database
constraint. It is live, holds 0 duplicates across 52 linked rows, and I verified it on real
Postgres, including the migration's refusal to run over existing duplicates and the round trip
through the DEF416/DEF417 merge. The race recovery is real but covers a branch the route never
takes. The branch users do take fails with a loud, retryable 500 rather than signing the loser
in. That is a MINOR, and it does not force another round.
