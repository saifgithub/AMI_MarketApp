## The admin auth gate — attacked, held

`get_admin` (`admin.py:80`) fails closed in both directions: 503 when neither auth path is
configured, 403 when configured and nothing verifies. There is no "allow when unset" branch.

**The static bearer path — 12 adversarial inputs, only the exact secret admits.**

| input | result |
|---|---|
| no headers / empty bearer / wrong secret | refuse |
| **correct secret** (incl. lowercase `bearer` scheme) | **admit** — `static_bearer` |
| secret without the `Bearer ` prefix | refuse |
| secret with trailing extra (`…extra`) | refuse |
| truncated secret (last char dropped) | refuse |
| CF JWT present while CF is disabled | refuse |
| forged CF JWT + no / wrong bearer | refuse |

Comparison is `hmac.compare_digest` (`cf_access.py`), so it is timing-safe rather than `==`.

**The CF Access path — the never-exercised one — survives the standard JWT attacks.** This is
the part I judged worth the most effort, because nobody has ever run it end-to-end (the CF
dashboard step is still outstanding), so a flaw here would have shipped unnoticed. Against a
synthetic CF keypair with the verifier wired to it:

| forgery | result |
|---|---|
| `alg=none`, correct iss/aud/email | **REJECTED** — "header missing kid/alg" |
| **HS256 hand-crafted using the RSA public key as the HMAC secret** (the classic RS256→HS256 confusion bypass) | **REJECTED** — jose refuses an asymmetric key as an HMAC secret |
| RS256 signed by a different RSA key | REJECTED — signature verification failed |
| right key, wrong audience | REJECTED — aud not in accepted audiences |
| right key, wrong issuer | REJECTED — iss not in accepted issuers |
| right key, expired | REJECTED — token expired |
| **properly signed, correct iss/aud** | admitted (correct — see below) |

I flagged `algorithms=[alg]` in `oidc_verifier.py:96` as a concern on reading it — taking the
algorithm from an attacker-controlled header is the textbook setup for algorithm confusion. I
then tested it rather than filing it: it is **not exploitable here**, because the key is
converted with `jwk.construct(...).to_pem()` and python-jose refuses to use an asymmetric PEM as
an HMAC secret. Worth recording that the safety comes from the library boundary, not from an
explicit algorithm allow-list in our code — a future library swap would want re-checking. Not a
finding today; the behaviour is correct and proven.

Issuer, audience and JWKS URI are all constructed correctly
(`https://<team>/cdn-cgi/access/certs`, issuer = team domain, audience = the AUD tag), and both
`iss` and `aud` are checked by explicit membership after decode.

**Half-configuration degrades loudly (CR040), as claimed.** `_cached_verifier()` logs
`cf_access_half_configured` and leaves the CF path *disabled* rather than accepting or rejecting
everything. Pinned by `test_half_configured_disables_cf_path`.

**One design property worth stating plainly, which is not a defect.** There is no in-app admin
email allowlist — `grep` for one across `backend/app/` returns nothing. Any validly signed CF
token for the configured AUD becomes an admin, with `email` recorded as the operator. That is
deliberate and correctly documented (`cf_access.py:5`: the JWT is issued to a request that
"passed the edge policy"), and it is the normal CF Access posture. It does mean **the Cloudflare
dashboard policy is the entire gate on *who***, so that outstanding manual setup carries the
whole authorization decision. The submission already flags the setup as outstanding; I am noting
where the trust actually sits, not asking for a change.

## Every admin write is gated and audited — enumerated, not sampled

I enumerated every route across the five admin modules rather than spot-checking:

```
13 write routes (POST/PATCH/DELETE):  all gate=Y
11 of 13 record an admin_audit row
```

The two without an audit row are `/messages/preview` and `/preview` — POST by HTTP verb,
read-only in fact. I verified that rather than assuming it from the name: neither body contains
`session.add`, `commit`, `update`, `insert`, `delete`, or `notify()`; each returns a count. So
"every admin *write* leaves an `admin_audit` row naming the operator" holds with no exceptions.

`test_cr200_admin_audit.py`'s negative case (`test_failed_write_leaves_no_audit_row`) is the
right test to have written — it proves the audit row is transactional with the write it
describes rather than emitted unconditionally.

## Closing note

This is a month-old shipped feature meeting an auditor for the first time, and it came back
clean. The auth gate is the part that mattered and it is well built: it reuses the existing OIDC
verifier rather than hand-rolling JWT checks, compares the static secret in constant time, fails
closed when unconfigured, and degrades loudly when half-configured. I could not construct a
credential that admits when it should not.

The one thing I would want a future reader to know, recorded here rather than as a finding:
**authorization for the console rests entirely on the Cloudflare Access policy**, because the app
verifies that a token is authentic but never that its bearer is on a list. That is the intended
design and it is documented — but it means the outstanding CF dashboard step is not merely the
last integration chore, it is where the actual access-control decision gets made.
