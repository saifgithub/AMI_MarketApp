## MAJOR A1 — the ship gate prints PASS and exits 0 having compared a strict subset

§3.4.2, confirmed end to end, and it is the finding.

`cr136_live_crosscheck.py:391-404`. `unchecked` rows (`api is None`) are printed
and then **excluded from the exit code**; `failures` counts only rows where
`api is not None`. The verdict sentence is unconditional.

I stubbed `_load_closes` and `_fetch_health` and drove `main()`:

```text
control: honest payload                    exit=0  checked: 7  FAILED: 0
                                           PASS — every published metric agrees to 2 dp.

(ii) benchmark unusable                    exit=0  checked: 4  FAILED: 0
     beta / r_squared / TE unpublished     PASS — every published metric agrees to 2 dp.

(iii) M07 renames r_squared -> rsq         exit=0  not checked: ['r_squared']
      nothing else changes                 PASS — every published metric agrees to 2 dp.

(iv) control: sigma_p 0.1pp wrong          exit=1  FAILED: 1
```

(iv) is the control that matters: when the harness *does* compare, it works.
The defect is entirely in what it declines to compare and still calls a PASS.

**Checklist row 2.9's acceptance criterion is literally the exit code** — *"exits
**0**"*. The `checked: N` line and the `not checked: [...]` line are printed, but
they are prose; the exit code is the control, and it cannot distinguish
"compared everything" from "compared four of seven". CR038's rule in this repo
is that an instruction is not a control. This is that rule applied to a gate.

**Reachability — and a correction to the submission's own mechanism.** §3.4.2
cites `INSUFFICIENT_BENCHMARK_MISALIGNED`. That cause covers three states
(`portfolio_health.py:426-430`), and two of them self-correct:

- benchmark absent from the table → the harness's `missing` check fires first →
  `exit 2`. Safe.
- joint window shorter than `T_MIN` → the harness joins the same short window →
  `t_obs != api_t` → `exit 2` with the window-mismatch message. Safe.
- **`bench_clean` false — a bad print in stored SPY.** The engine drops the
  benchmark but keeps `dates = _join(survivor_tickers)`; the harness's join over
  `[*tickers, SPY]` yields the same dates whenever SPY covers them, which it
  normally does. `t_obs` matches, the harness proceeds, three of five level
  metrics come back `None`, and it prints PASS. **This is the reachable route.**

And (iii) needs no unusual book at all. `r_squared` is read off
`blocks["beta"]["r_squared"]` (`:357`) with no schema pin between the harness and
M07, and M07 owns that payload in a different lane. Same shape as DEF210, one
layer further out, sitting in the ship gate.

MAJOR, not BLOCKER: nothing wrong reaches a user. What it reaches is the
operator, at the single moment they are most inclined to believe it — which is
the "dark for weeks because nothing went red" class §1 correctly names as this
repo's recurring failure.

Smallest fix: `unchecked` non-empty ⇒ non-zero exit, or an explicit
`--allow-unchecked` that names them. The verdict sentence should say what N was.

## MINOR m2 — `_joined_returns`'s docstring asserts a mirror that is inverted

§3.4.3, confirmed and measured.

Harness (`:143-167`): per-ticker trim to the newest 505 dates **first**, then
intersect, then trim. Engine `_join` (`portfolio_health.py:302-307`): intersect
the **full** date sets, trim **once** at the end. The docstring says the harness
mirrors M04's order "because doing it in the other order silently yields a
different window" — it is doing the other order.

A book with one holding on a sparser calendar than the rest (A: 780 weekdays;
B: every other weekday over the same span):

```text
engine  _join   -> 390 dates, 389 returns   [2023-08-07..2026-07-30]
harness _joined -> 252 dates, 251 returns   [2024-08-27..2026-07-30]
payload n_observations = 389, harness computes 251  ->  MISMATCH -> exit 2
```

35% of the window, and the operator is sent to *"investigate M01's join"* — a
correct module.

Not graded higher because the degradation is reliably loud. The harness's
intersection is a subset of the engine's by construction (pre-trimming can only
remove candidate dates), so its count is always ≤ the engine's and the window
check fires before any number is compared. I tried to construct the worse
corner — equal counts, different date sets, spurious `exit 1` blaming the engine
— and could not; a subset that still holds 505 dates necessarily reaches
further back, so the counts diverge first.

Grade the comment as hard as the code, as §3.4.3 asks: it is affirmatively
wrong about the thing it exists to explain.

## MINOR m4 — "agrees to 2 dp" is the right tolerance for the render and the wrong one for §1.1's claim

Mine, not on the attack list.

`_TOL = 0.005` is **absolute**, in the rendered unit. Checked against the card,
that is defensible everywhere: `portfolio_volatility` renders at 1 dp
(`health_card.dart:365`), `beta` at 2 dp (`:381`), `r_squared` as a 0-dp percent
(`:384`), `effective_bets` at 1 dp (`:393`), risk shares as 0-dp percents
(`risk_money_bars.dart:92`); tracking error is not rendered in `mobile/` at all.
The tolerance is at most half a rendered ULP for every one of them. As a
*rendering* check it is exactly right, and `_pp`'s docstring says so precisely.

§1.1 makes a different and larger claim: this is *"the only evidence that will
ever exist that the shipped engine's **arithmetic** is right on real data."*
Against the numbers the gate actually recorded on 2026-08-05:

```text
metric                      live value    ±0.005 as a relative band
portfolio_volatility (pp)      2.7571        0.18%
beta                           0.0415       12.05%
r_squared                      0.0487       10.27%
tracking_error (pp)           14.3196        0.03%
effective_bets                 1.9023        0.26%
```

β and R² were certified to ±12% and ±10%. Not because the tolerance is wrong,
but because the **book selection** drove them toward zero: 87.2% cash, so
β ≈ invested_fraction × sleeve β. The runbook's selection criteria
(`cr136_live_crosscheck.py:40-45`) pin holdings and history length and say
nothing about cash weight, and the one run performed landed in the regime where
two of the five level metrics carry the least information.

Fix is one line of runbook (prefer a book with a low cash fraction, or add a
relative floor to the tolerance for near-zero metrics) or one sentence of §1.1.
Same class as M04 r4's m1: the number is fine, the claim resting on it is a size
larger than the measurement.
