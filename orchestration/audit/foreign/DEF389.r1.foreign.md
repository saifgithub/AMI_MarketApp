## Findings

### [blocking] The logging half of the fix covers two of the Room's three LLM exception handlers; `room_pm_reformat_failed` still logs a blank error for bare transport timeouts
`backend/app/services/room_runner.py:5579`
>         logger.warning("room_pm_reformat_failed", error=str(exc)[:200])

The DEF389 defect has two halves: unreachable guard (fixed) and blank error field
because `str(httpx.ReadTimeout()) == ""` (claimed fixed at "both log sites"). There
are three LLM exception handlers in the Room call path — `room_agent_llm_failed`
(`room_runner.py:5038`, fixed), `room_pm_llm_failed` (`room_runner.py:5473`, fixed),
and this one on the DEF058 reformat recovery call, which still uses the bare
`str(exc)[:200]`. The reformat call runs under the same 90s `asyncio.wait_for`
(`room_runner.py:5559`) against the same provider, so an empty-`str()` exception
there (ReadTimeout, ConnectTimeout, PoolTimeout — all stringify to "") still
produces `error=""` and falls through to the same fail-safe PASS with the failure
unnamed. Worse, the pinning test locks the gap in:

`backend/tests/unit/test_def389_transport_timeout.py` (from the diff)
>     assert src.count("(str(exc) or repr(exc))[:200]") == 2

— so any future attempt to fix the third site fails this test until the test is
also touched. Impact is narrower than pre-fix (with transport 180s > guard 90s a
ReadTimeout can rarely reach the handler before the `wait_for` cancels), but the
defect row states "both log sites now use `(str(exc) or repr(exc))`" — that claim
is factually incomplete; there are three.

### [question] The timeout-ordering invariant is only established for the vLLM provider; every fallback provider still carries a 60s transport under the 90s guard
`backend/app/services/llm_gateway.py:402`
>             timeout=60.0,

`backend/app/services/llm_gateway.py:567`
>         timeout_seconds: float = 60.0,

`AnthropicProvider` keeps its hardcoded 60s, and the `kimi`/`deepseek`/`qwen`/
`gemini` registrations (llm_gateway.py:920, 948, 963, 980) pass no
`timeout_seconds`, taking the same 60.0 default. `_active_provider_name()`
(llm_gateway.py:1003-1020) prefers vllm, so on Alpha — where `VLLM_BASE_URL` is
set — the fix holds. But if vLLM is unregistered (env dropped, the DEF038 class
this very commit cites) or `LLM_FORCE_PROVIDER` selects another provider (a
documented manual knob), the Room's 90s guard is again shadowed by a 60s transport
and DEF389 reproduces verbatim on the fallback path, including the blank
`room_pm_llm_failed error=""` (the repr fallback helps naming, but the guard is
dead again). The lane question — "nothing else in the call path re-introduces an
inner limit shorter than the guard" — is answered only for the primary provider.
Someone who knows whether Alpha can ever run with vLLM absent while
`ANTHROPIC_API_KEY` is present should disposition this.

### [noted] The settings validator's lower bound permits re-creating the inversion by config
`backend/app/core/config.py:127`
>     vllm_request_timeout_s: float = Field(default=180.0, ge=30.0, le=900.0)

`ge=30.0` accepts any value from 30s up — including 60.0, the exact value that
caused the defect. The ordering is enforced only by
`test_transport_budget_exceeds_the_orchestration_budget`, which asserts whatever
env the test process loaded, at test time; nothing at boot refuses a
`VLLM_REQUEST_TIMEOUT_S` ≤ 90. Given the commit itself invokes CR040 ("prompt
instructions are not controls; make it structural"), a `ge=` bound below
`_AGENT_LLM_TIMEOUT_S` is a config-shaped hole in the very guard being added.
Minor because the shipped default and compose default are both 180.

### [noted] The commit's mental model of the 180s budget overstates what an httpx scalar timeout bounds on a stream
`backend/app/services/llm_gateway.py:592`
>         self._client = httpx.AsyncClient(

with `timeout=timeout_seconds` (line 595). A scalar httpx timeout sets the
connect/read/write/pool budgets, and on a streaming response the read timeout
applies per socket read, not to total response wall-time — a completion dribbling
one token every 179s never trips the 180s transport. In practice this is harmless
here (the 90s `wait_for` remains the binding total-time limit, which is exactly
the ordering DEF389 wants), but the config comment's framing of 180s as "the
HTTP read timeout for a vLLM completion ... the TRANSPORT budget" will mislead the
next person reasoning about end-to-end budgets.

## What checked out

- Ordering on the primary path is correct: `VLLMProvider` now receives
  `timeout_seconds=settings.vllm_request_timeout_s` (llm_gateway.py:886), default
  180.0 > `_AGENT_LLM_TIMEOUT_S = 90.0` (room_runner.py:3233), and the setting is
  forwarded in `docker-compose.yml`'s `api-alpha` block with the same 180 default.
- All three Room `asyncio.wait_for` guards (agent text, PM stream, PM reformat)
  use the same 90s `agent_timeout_s`; the CR214 five-sample fan-out
  (room_runner.py:4518-4526) issues concurrent `_stream_pm_response` calls each
  under its own 90s guard, so the transport budget per draw (180s) clears the
  measured 45.9s worst case with the claimed margin.
- The premise test (`str(httpx.ReadTimeout("")) == ""`) is asserted, not assumed,
  and the `(str(exc) or repr(exc))` expression does name the exception type.
