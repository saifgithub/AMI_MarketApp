## Why this is coder.api, not coder.room

DEF098 is the **class**, not an instance. Its parity guard spans **three prompt surfaces** — the Room
(`_format_profile`, coder.room), the **1-on-1 chat blocks** (`agent_runner.py` / `social_context.py` /
`build_*_context_block`, coder.api), and **Concierge** (`concierge_prompts.py`, coder.api). Two of the
three surfaces, plus the one cross-path fix it carries (the 1-on-1 next-earnings drop), are coder.api
territory, and coder.room may not edit them. The Room *instances* of the class (DEF095, DEF096) are already
a separate coder.room batch; this lane builds the guard **over** them and fixes the api-side hole.

## The finding (measured, in the spec — do not re-derive)

Live ticker data has **two renderers that have never been reconciled**, and the drift goes both ways —
proof neither is authoritative:

- **Room `_format_profile` drops** the social trio (`mention_trend` / `influencer_take` / `pattern`) — the
  DEF096 instance, fixed in the coder.room batch this lane depends on.
- **The 1-on-1 fundamentals path drops next-earnings date + consensus EPS** — computed in
  `room_runner.py` from `get_market_data_provider().earnings()`, but `agent_runner.py:187-216` injects
  live-data / news / social / technicals / journal and never earnings.

Nothing links a computed field to the block that must render it. The precedent that already solved this
shape for a different resource is
[`backend/tests/unit/test_config_compose_parity.py`](../../../backend/tests/unit/test_config_compose_parity.py)
(a config value defined in `settings` but not forwarded in `docker-compose.yml` shipped a feature dark
twice — DEF038/DEF063). This is that test's prompt-data analogue.

## Build (§Proposed fix — you decide the exact shape)

1. **A prompt-data parity test** modelled on `test_config_compose_parity.py`. For each live source
   (`fundamentals`, `technicals`, `news`, `social`, `earnings`, `journal`), enumerate the fields its
   **fetcher/formatter actually produces** (read the pipeline output — NOT a hand-kept list, per
   §Guard-on-the-guard, or the check rots exactly like the thing it guards).
2. Assert each produced field is **either** rendered in the block on **every surface the consuming agent
   reads** (the Room `_format_profile` *and* the matching 1-on-1 block) **or** listed in an explicit
   `INTENTIONALLY_OMITTED` registry with a one-line reason. The test fails the build on a computed field
   that is neither rendered nor declared.
3. **Fix the one real api-side instance:** render next-earnings date + consensus EPS in the 1-on-1
   fundamentals block so it reaches parity with the Room.

**Declare the by-design omissions** the sweep found (so the registry records deliberate, not accidental):
- Concierge `_format_journal` drops `summary`/`user_note`/`tags`/`agents_involved`/`created_at` —
  intentional (Concierge *routes* to an entry, does not analyse it).
- Room researchers' journal (`format_journal_entry`) drops `summary`/`user_note` — **decide deliberately**:
  DEF054/055 frame it as a decision-*lookback* and the reasoning lives in those fields, so this one is
  arguable. Either render them or declare the omission with the reason — do not leave it accidental.

**Stronger option if you judge it worth the refactor (not required):** collapse the two renderers to one
field registry both paths derive from, so drift is impossible rather than merely detected. The parity test
is the minimum; the single source of truth is the cure.

## Guard-on-the-guard (mandatory)

The registry must enumerate from the fetcher's output, not a static list. Prove it: a test that adds a new
field to a fetcher's output and shows the parity test goes RED until the field is rendered-or-declared. If
the guard passes when a freshly-produced field is dropped, the guard is theatre.
