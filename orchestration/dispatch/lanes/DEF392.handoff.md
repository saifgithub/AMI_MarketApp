## Defect

The transport-vs-guard timeout ordering invariant (DEF389) was enforced for the
vLLM provider only, and only at test time.

(a) `OpenAICompatibleProvider.__init__` defaulted `timeout_seconds` to a magic
    `60.0`. Only the vLLM registration passed a value; kimi / deepseek / qwen /
    gemini passed nothing and therefore sat at 60s — INSIDE the 180s
    `room_agent_timeout_s` guard. Same DEF389 failure mode, four providers over.
(b) `Settings` had no cross-field validator, so
    `ROOM_AGENT_TIMEOUT_S=800 VLLM_REQUEST_TIMEOUT_S=45` booted happily with the
    ordering inverted — the guard can never fire, and the Room falls back to the
    DEF059 fail-safe PASS.

## Plan

1. `llm_gateway.py`: module-level `_TRANSPORT_TIMEOUT_MARGIN_S`; default
   `timeout_seconds: float | None = None` on `OpenAICompatibleProvider`
   (and `VLLMProvider`, which forwards it), resolved at construction to
   `settings.room_agent_timeout_s + _TRANSPORT_TIMEOUT_MARGIN_S`. No new Settings
   field, so `test_config_compose_parity.py` is untouched.
2. `config.py`: `@model_validator(mode="after")` raising when
   `vllm_request_timeout_s <= room_agent_timeout_s`.
3. New `tests/unit/test_def392_transport_ordering.py` (4 assertions).
