# DEF382 — hand-off (coder.local · AT:R75 · lane/DEF382.coder.local)

DEFECT: replace the `tutorial_coach_mark` package. Ruled by the CEO 2026-09-01.
The reason was measured and is not re-litigated here: interacting with a
first-run coach-mark tour destroyed the app's iOS accessibility tree
permanently (`page_source` 13 KB → 1.5 KB, all nav identifiers gone, same
process, app foreground, no crash).

## What was built

**NEW `mobile/lib/features/tour/ami_tour_overlay.dart`** (356 lines) — our own
overlay primitive, the whole replacement surface:

* `AmiTourController` — exactly `next()` and `skip()`. Nothing else. That is
  all `TourCard` ever used, so nothing else exists.
* `AmiTourStep` — replaces `TargetFocus`: `identify`, `target` (GlobalKey),
  `shape` (`AmiTourShape.rect` / `.roundedRect`), `radius`, `paddingFocus`,
  `align` (`AmiTourAlign.top` / `.bottom`), `absoluteTop`, and
  `builder(context, controller)`.
  `absoluteTop` is the replacement for the old
  `ContentAlign.custom` + `CustomTargetContentPosition(top: 180)`, used by the
  Journal's list step, whose target fills the screen so neither `top` nor
  `bottom` fits.
* `showAmiTour(context, steps, {barrierColor, barrierOpacity, onFinish})` —
  replaces `TutorialCoachMark(...).show(context:)`. Inserts one `OverlayEntry`
  into the root overlay; on finish AND on skip it calls
  `entry.remove()` guarded by `entry.mounted`. `onFinish` fires on the finish
  path only, never on skip — every screen's completion toast depends on that
  distinction.
* Rendering: full-screen barrier (black, alpha 0.88) painted in a `saveLayer`
  with the target rect erased via `BlendMode.clear`, so the hole is a real
  hole, not a lighter patch. The card is `Positioned` above/below the target
  per `align` (clamped to stay on screen) or pinned at `absoluteTop`.
* `Scrollable.ensureVisible(ctx, 350ms, alignment: tooltipAbove ? 0.85 : 0.15)`
  is preserved verbatim from `floor_screen._runFloorTour` and now applies to
  every tour — but only when the target is actually inside a `Scrollable`
  (`Scrollable.maybeOf`), which is why `YOU` (whose bar is not scrollable)
  keeps its old no-scroll behaviour.
* A step whose target has vanished is stepped over rather than shown as a
  full-screen dim with nothing to point at.
* The barrier absorbs every tap: nothing under the tour is reachable until
  Skip or Next, which is what the first-run flow and the harness both assume.

**`tour_card.dart`** — two lines: the package import swapped for
`ami_tour_overlay.dart` (import re-sort required by `directives_ordering`) and
`final AmiTourController controller;`. Both `MergeSemantics` +
`Semantics(identifier: TourIds.skip / TourIds.next)` wrappers and the whole
widget shape below them are untouched (`git diff` on that file is 2 changed
lines).

**Five step files** (`floor_tour`, `portfolio_tour`, `lessons_tour`,
`journal_tour`, `you_tour`) — type migration only. Verified mechanically: for
every step, `(identify, key, shape, radius, paddingFocus, align, top-offset)`
was extracted from the HEAD version and compared against the new one. Four
files MATCH exactly; `journal_tour`'s third step differs only in that
`align: custom` became `align: bottom` + `absoluteTop: 180`, because the new
type has no `custom` — the 180 offset is preserved and `bottom` reproduces the
old `beforeFocus` scroll alignment for a custom-aligned step.

**Five screens** (`floor`, `portfolio`, `lessons`, `journal`, `you`) — now call
`showAmiTour(...)`. Each screen's own pre-tour logic is untouched: the
`TourIntroSheet` gate and its `start != true || !mounted` check on Floor, the
`ref.listen` + `hasSeen`/`markSeen` + `mounted` gates on the other four, the
GlobalKeys passed in, and the completion toast/SnackBar in `onFinish`. The
per-screen `beforeFocus` lambdas are gone because that behaviour moved into the
primitive.

**`mobile/pubspec.yaml`** — `tutorial_coach_mark: ^1.3.3` removed.
**`mobile/pubspec.lock`** — its 8 lock stanza removed (expected).

`grep -rn "tutorial_coach_mark" mobile/lib mobile/test` → **no matches** (exit 1).

## Tests

* `test/qa/tour_ids_test.dart` — changed ONLY in that `_FakeController` now
  `implements AmiTourController` (and drops the `previous()` override the new
  interface does not have) plus the import. All assertions unchanged.
* `test/features/tour/you_tour_journal_test.dart` — same kind of change:
  `_NoopController implements AmiTourController`, `List<AmiTourStep>`,
  `step.builder(ctx, ...)` for `step.contents!.first.builder!`, and
  `journal.target` for `journal.keyTarget`. Assertions unchanged.
* `test/features/tour/nav_change_test.dart` — untouched; it never referenced
  the package.
* **NEW `test/features/tour/ami_tour_overlay_test.dart`** (8 tests): the overlay
  inserts on show; `skip()` ends the tour and the `AmiTourOverlay` is GONE from
  the tree (and the screen underneath is tappable again); `next()` advances
  exactly one step and leaves no card behind; finishing the last step removes
  the entry too; `onFinish` fires on finish and NOT on skip; both `TourIds.skip`
  and `TourIds.next` render; a real `TourCard` hosted in the overlay is walked
  end-to-end by tapping `ami.tour.next` through DONE to dismissal; a step whose
  target is gone is stepped over. The entry-removal assertions are the point of
  the file — a leaked entry is this defect's own shape.

## Could not do / deliberately not claimed

* **No device-level acceptance.** No iOS simulator, no Appium, no device run —
  out of scope for this lane by instruction. The acceptance for DEF382 is a
  measured accessibility tree (page_source size + nav identifier count) across
  every tour × every dismissal path, on device. NOTHING in this lane proves the
  tree survives; it proves the replacement exists, behaves, removes its entry,
  and passes the existing suite. That measurement is the architect's next step.
* Two facts about the new overlay are widget-test-only and therefore NOT
  equivalent to that measurement: the barrier's `BlendMode.clear` cutout is
  asserted nowhere visually (no pixel test), and semantics survival through
  overlay insertion/removal is argued from the fact that our overlay adds plain
  widgets and removes its entry, not measured on a `UIAccessibilityElement` tree.
