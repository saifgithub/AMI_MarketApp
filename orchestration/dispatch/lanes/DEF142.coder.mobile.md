## Part A — HexAvatar (DEF142)

1. **Canvas-interior treatment, every call site.** Interior `slate900` (was the solid
   family fill), border stays family-coloured (unchanged), label ink is the family colour
   itself — no global ink, matching CR106's comb wholesale. `hex_avatar.dart:158-176`.
2. **Contrast computed in a test, extending the existing one.** `room_board_test.dart`'s
   non-vacuous contrast test (`amiCanvasContrastFloor` pin) gets a new `testWidgets` case
   in the same group, pumping `HexAvatar` itself per family and asserting the rendered
   `Text.style.color` and the interior `Container`'s `BoxDecoration.color`. The WCAG
   luminance/ratio helpers were hoisted from that test's closure to file scope so the new
   case shares them rather than duplicating the math (DEF098's class is two checks of one
   rule — this stays one file, two assertions). **Why here and not a new file:** the
   assign is explicit that a second contrast test over the same palette is exactly what
   DEF098 named.
3. **Font floor derived from the census, not from CR107's guess.** Set at **4.0px** —
   measured strictly between the 20pt site's 3.2px and every other census size's 4.48px
   and up, not at CR107's proposed 4.5px. Reason: `28 * 0.16 = 4.48`, inside float-rounding
   distance of 4.5 — a 4.5px floor would have silently culled the four 28pt sites
   (`room_screen.dart` x3, `lesson_reader_screen.dart:278`) along with the one site that's
   actually the problem. Verified those four sites don't need the in-hex label anyway:
   all four already print the agent's abbreviation in adjacent 11pt/body `Text` next to
   the hex, so nothing is lost either way — but the floor itself is picked to not force
   that question.
4. **Below the floor, no label — not a shrunken one.** `showLabel = label.isNotEmpty &&
   fontSize >= 4.0`; below it the `Container`'s child is `null`. `hex_avatar_test.dart`
   iterates all ten distinct census sizes and asserts the render for each, naming
   `lesson_tile.dart`'s size-20 site (3.2px) as the real site that hits the branch, plus
   a same-file test that an empty label never renders `Text` either.

## Part B — TrackHexButton (CR108)

1. **Wrap, don't shrink.** `track_hex_button.dart` now measures the label with a
   `TextPainter` at the raised 10px base against the one-line box
   (`flatTopHexWidthFractionAtLabel`, 0.724 x W). If it fits, one line, unchanged box. If
   not, `maxLines: 2`, `softWrap: true`, box narrows to the new
   `flatTopHexWidthFractionAtTwoLineLabel` (0.676 x W) — the width at the wrapped block's
   top line (~y=0.176 when centred on the existing y=0.224), a named constant added
   beside `flatTopHexWidthFractionAtLabel` in `hex_clipper.dart` so a future y-position
   change moves both together.
2. **`0.40` (`honeycombHexWidthFraction`) untouched.** `honeycomb_layout_test` still
   green — ran as part of the full suite below, not spot-checked alone.
3. **Measured off the rendered widget, per acceptance #6/#7.** `track_hex_button_test.dart`
   pumps all 13 shipped `honeycombTrackLabel` values inside a 143.2 x 124pt hex (the
   census value `honeycomb_layout_test.dart` itself uses for a typical device column) and
   reads the actual `FittedBox` paint-transform scale off the render tree via
   `RenderParagraph.getTransformTo(null)` — **not** `Text.style.fontSize`, which always
   reads back as the unscaled 10px base since `FittedBox` scales visually at paint time
   without rewriting the style. Result: all 13 render **>=10.0px at 1.0x** and **>=10.5px
   at 1.15x**; `ISLAMIC FINANCE` specifically never drops below its 10px base at either
   scale (it was 8.4px, below its OLD 8px base, before this fix). Confirmed exactly 3 of
   13 wrap (`NEWS & MACRO`, `ASSET CLASSES`, `ISLAMIC FINANCE`) — matches the row's
   prediction; the other ten stay one line at the higher cap.
4. **`honeycombTrackLabel` gap flagged, not fixed** — hardcoded English, no ARB coverage.
   `app_*.arb` files belong to the live CR120 lane this round; wrapping behaviour for
   longer AR/MS translations stays untested by definition.

### 1. The mechanism, fixed

`track_hex_button.dart`'s two-line branch no longer puts `FittedBox` around the `Text`.
It now gives the `Text` its width from a plain `SizedBox` only (no `FittedBox` in that
branch at all), so `softWrap`/`maxLines: 2` has a real boundary to break against.
`FittedBox` is kept, but only in the single-line branch — that half of the mechanism
already worked before CR108 (that's the pre-CR108 `8bb00594` baseline's own single-line
scale-down), so it wasn't rebuilt, just isolated to where it belongs.

Whether a label wraps is now **confirmed, not assumed**: after the single-line natural
width says a label is a wrap candidate, a second `TextPainter` pass lays it out at
`maxLines: 2` against the two-line box and checks `computeLineMetrics()` — wrap is only
taken if it produces more than one line and every line's width fits the box. If not
(see the unbreakable-word case below), the label falls back to the single-line
`FittedBox` path instead of silently rendering something that doesn't fit.

### 2. The unbreakable-word case — measured, and the stated premise didn't hold

The assign named `FUNDAMENTALS` (12 characters, no space) as unable to wrap and
required an explicit decision for it. Measured against the real render tree at the
lane's fixture, **that premise is false**: Flutter's default text layout breaks an
unbreakable "word" at the character level as a last resort when `maxLines` allows a
further line and there's no whitespace break (UAX#14 fallback) — confirmed directly by
walking caret offsets per character (`FUNDAMENT` / `ALS`, an 8/4 mid-word split).
`FUNDAMENTALS` therefore wraps like any other long label and meets the floor at full
size (`geometricScale` 1.00, not scaled down at all) — it never reaches the
single-line-scale-down fallback. That fallback path is still real code and still
load-bearing; since none of the 13 shipped labels are long enough (even as one word) to
need it, `track_hex_button_test.dart` proves it with a synthetic 36-character word
(`SUPERCALIFRAGILISTICEXPIALIDOCIOUSXX`) and asserts it takes the fallback
(`geometricScale` 0.24, one line, not two) rather than silently overflowing.
This correction is stated plainly in `CR108.row.md` and in this hand-off rather than
building the fallback path silently around a premise that turned out not to apply.

### 3. The metric, replaced and validated before being trusted

Round 1's `paragraph.getTransformTo(null).getMaxScaleOnAxis()` does not observe
`RenderFittedBox`'s paint-time scale. `track_hex_button_test.dart` now reproduces that
directly (not just cites it): a dedicated harness pumps a `Text` inside a `FittedBox`
forced to a known 0.5x scale and shows the old metric reads `1.000` on it while the new
one — `tester.getRect(finder).width / RenderParagraph.size.width`, which goes through
`localToGlobal` and does apply the paint transform — reads back `0.5` within 0.02.
That validation runs *before* any of the real-widget assertions, per the round-2
instruction not to substitute an unvalidated metric for another.

A `paraH` assertion (`RenderParagraph.size.height` compared against a same-harness
single-line reference — `find` a genuinely single-line label like `RISK` through the
*same* `_measure` helper, not a bare standalone `TextPainter`; the ambient
`MaterialApp`/`Scaffold` `DefaultTextStyle` merges in a `height` value a bare
`TextPainter` never sees, so a bare-painter reference silently mismatched the real
render by 40% until caught and fixed) makes a silently-unwrapped label a visible
failure — exactly the round-1 case the old metric couldn't catch.
