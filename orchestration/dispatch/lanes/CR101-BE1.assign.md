## What and why

Saiful, 2026-07-29, on being unable to find risk settings in the app: *"we had a CR related to 4
additional risk parameter to be set for the customer. I cant see it in the settings page."*
Correct — **CR101 was never built.** Settings sends exactly three keys today (`settings_screen.dart:56,59,62`):
`risk_score`, `max_drawdown_pct`, `compliance`.

The governing rule is Saiful's own amendment: *"a risk setting that a user cannot change violates
the user's rights… they should be able to set whatever they like."* Testable invariant — a Mandate
field feeding an enforced limit is **(a) enforced, (b) disclosed in its own units, (c) disclosed in
the agent overlay, (d) settable** — or it is **deleted**. No third state.

**This lane is the two caps that already exist and are already enforced.** The four that do not
exist at all (post-loss cooldown, max open positions, max trades per day/week, total-open-risk cap)
are **CR101-BE2** — not this lane. Do not build them here.

## Measured state — verified on `main` at `73a25c7f`, so you do not have to re-derive it

**Cap 1 — sector cap. Enforced, shown, NOT settable.**
`risk_components.concentration_tolerance: int 1-5` → `_TOLERANCE_TO_CAP`
(`services/sector_allocation.py:61`) `{1:0.25, 2:0.30, 3:0.40, 4:0.50, 5:0.60}` → enforced at
`agents/safety_floor.py:293` via `_sector_cap_breach(..., cap=_sector_concentration_cap(mandate))`,
and the resulting % is **already displayed to the user** on the allocation donut
(`api/portfolio.py:60`). Its sole write path is `_classify_concentration`
(`services/concierge_engine.py:278`), a keyword match on onboarding free text. Settings never sends
the key and onboarding cannot re-run, so **in practice every user sits at tolerance 3 = 40%.**

**Cap 2 — single-name cap. There are TWO, ~11x apart.**
- `risk_tier_cap(risk_score)` (`trading_math/sizing.py:29`), table `{1:1.5, 2:1.5, 3:3.0, 4:4.5, 5:4.5}` — this is what the PM actually clamps to.
- `SINGLE_NAME_ABSOLUTE_CAP_PCT = 50.0` (`trading_math/sizing.py:26`) — the floor's backstop, which given the clamp above **can essentially never fire on the Room path**.

**The three `risk_components` are NOT what an earlier version of the CR row claimed.** I corrected
that row today; read the correction before you touch them. `drawdown_response` and
`regret_asymmetry` feed `_derive_risk_score()` (`concierge_engine.py:409-415`, called at `:222` and
`:424`): `base = round((drawdown_response + concentration_tolerance) / 2)`,
`max(1, min(5, base + regret_asymmetry))`. They set the user's **initial `risk_score`**, which is
enforced. **Deleting them would silently change how every new user's opening risk score is
computed.** They are write-once derivation inputs, not dead code.

## What to build

1. **THE BLOCKER, FIRST — `MandateStore.patch` is a shallow merge.**
   `services/mandate_store.py:91-113` merges top-level keys and has one hand-written `compliance`
   special case. So `PATCH {"risk_components": {"concentration_tolerance": 4}}` **replaces the whole
   object**, the required siblings vanish, and DEF062's re-validation returns **422**. Generalise to
   a recursive merge for nested BaseModel fields. **DEF062's re-validation through the full `Mandate`
   schema must survive** — it exists because `model_copy(update=...)` skips validation and
   `max_drawdown_pct` feeds a raw numeric comparison in the safety floor. Do not weaken it.
2. **Sector cap becomes an explicit, settable field.** Store the limit, not the ordinal:
   add `sector_cap_pct` and demote `_TOLERANCE_TO_CAP` from storage semantics to a **preset table**.
   That is what makes CR046's shown-equals-enforced trivially true here: the donut already shows a
   number, and after this the shown number IS the stored number.
3. **Single-name cap becomes ONE explicit, settable field.** Add `single_name_cap_pct`, defaulting
   from `DEFAULT_RISK_TIER_CAPS[risk_score]`, which likewise demotes to a **preset table**.
   **Architect's ruling on the ambiguity, so you do not have to guess:** the settable field is the
   one that actually binds today — the risk-tier clamp. `SINGLE_NAME_ABSOLUTE_CAP_PCT` fails the
   invariant on three of four legs (not settable, not disclosed, not in the overlay) and it
   contradicts the CR's own L3 decision that there is **no ceiling, only loud disclosure**. Remove it
   as an enforced ceiling and keep its value only if it is useful as the preset table's maximum. If
   you conclude on the code that removing it opens a real hole, **stop and disclose — do not
   quietly keep both.**
4. **Both new fields reach the agent overlay.** `agents/overlay_generator.py` currently interpolates
   `risk_score` and `max_drawdown_pct` at 12+ sites and **zero** sector/concentration references.
   The overlay must carry both caps in their own units.
   **Interpolate the constant, never a literal** — `safety_floor.py:30-35` explains why: a bare
   "50%" in prose can drift from the enforced value. Shares the no-numeric-cap-literal-in-agent-copy
   constraint with **CR105** item 2, which gets more load-bearing once caps are per-user.
