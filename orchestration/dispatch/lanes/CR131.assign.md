# CR131 — the Day Trader outcome comparison

KIND: code

## What and why

Read `docs/forward_planning/CR131_day_trader_outcome_instrumentation/README.md` in full.

CR129 lets a user switch off their guardrails. This lane is what makes that a lesson instead of a
faster way to lose. Compute the user's own numbers from `sim_trades` and place them beside the
published baselines.

## Build

The metric set in the CR doc: trade frequency active-vs-before, realised P&L, win rate and average
win/loss, **turnover** (so the Barber–Odean comparison is like-for-like), and position on the
Taiwan survival curve. Reuse **CR051**'s aggregation path; do not build a second one.

## The three rules that decide whether this ships

1. **Never extrapolate a thin sample.** A user three days in has no annualisable return — return
   *"too early to compare"* and say why. Standing project rule: never present an estimate as a
   measurement. A chart annualising four trades would break it spectacularly.
2. **No moralising.** Numbers, not warnings. The 11.4-vs-18.5 gap outperforms any copy we could
   write, and a lecture lets the reader dismiss the data along with it.
3. **It must work for the user who is WINNING** — honestly, including that <1% sustain it. Do not
   bury a good result; contextualise it.

## Fences

- **Do NOT touch `mobile/`** — the surface is a separate lane once this API exists.
- **READ DEF166 BEFORE TRUSTING P&L.** Clamped closes stamp `realised_pnl` on the full quantity —
  it is open and it corrupts precisely the number this lane reports. If you cannot compute P&L
  correctly around it, **say so and ship the frequency/turnover metrics without P&L** rather than
  reporting a number you know is wrong.
- Baselines are US/Taiwan retail equity data — carry that provenance in the payload.

## Acceptance

1. Each metric computed from real `sim_trades` rows, tested against a fixture portfolio.
2. **Thin-sample refusal is tested**: a 3-trade history returns the too-early signal, not a number.
3. Active-vs-before windows split on the CR129 preset-switch journal event, proven by a test.
4. A winning day trader gets an honest, contextualised result — tested, not asserted.
5. DEF166's effect on P&L is either correctly handled (say how) or explicitly excluded (say so).
6. Mutations: remove the thin-sample guard → acceptance 2 RED. Report honestly, **including GREEN**.
7. Full backend suite green, repo root, baseline = CR129-BE's post-merge count. Never `pytest -x`.
