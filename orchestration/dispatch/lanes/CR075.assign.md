## Context (diagnosis verified by the Architect against current code — build on it)

CR069 shipped a **sourced** Sharia allowlist (`sharia_universe.py`): the `halal` mandate flag enforces
the SPUS-published S&P 500 Sharia Industry Exclusions constituents (AAOIFI, three-state resolve via the
parent index), degrading loudly to `UNAVAILABLE` when the source is unreachable/stale. **But the universe
lives only in process memory.** `ShariaUniverseProvider._cache` is built on first use and re-fetched no
more often than every `_REFETCH_INTERVAL_S = 900.0` s (`sharia_universe.py:82`); `default_halal_universe()`
**may block on two 15 s httpx round-trips on the request path** (`_default_fetcher` :289), which is exactly
why `default_halal_universe_async()` has to `asyncio.to_thread` it (:406). Consequences (verified): network
on the first halal trade after any restart; each container re-downloads; two workers can hold two different
as-of dates; **and a source outage of any length ⇒ `_paused()` ⇒ every halal trade blocked** — DEF093's
blast radius, triggered by a bad minute on a host we don't control, when yesterday's list was fine.

**The fix: persist the universe, refresh it daily in the background, resolve every request from the stored
row.** This buys a long runway before the pause fires, and the stored `fetched_at` becomes the freshness
signal the parent-index mirror never publishes (a frozen mirror is otherwise invisible).

## Build

1. **Storage — a new table (coder.api schema owner + Alembic migration).** One row per successful fetch:
   `standard`, `source_url`, `parent_source_url`, `as_of` (the file's date, nullable — parent list has none),
   `fetched_at` (**our** UTC stamp — the missing freshness signal), the compliant set, the parent set (two
   lists of a few hundred tickers — JSON/text columns are fine, "size is a non-issue"). **Append-only is the
   natural fit** for the CR's defensibility argument ("which companies did AMI treat as compliant on a given
   day → a row answers it"); the read is "latest row for the standard by `fetched_at`". You own the exact
   shape — **state your latest-vs-history + any retention decision in the hand-off** (open question in §What).
   Migration `down_revision = a1c2e3f40020`.

2. **Refresh — `_sharia_universe_refresh()` background task, in the EXISTING pattern (no new dependency, no
   new mechanism).** Mirror `_league_roll_tick()` (`main.py:71`): a `while True` loop that does the network
   fetch (reuse `fetch_compliant_universe` + `fetch_parent_index`), stamps `fetched_at`, writes a row; a tick
   that finds a **fresh** row already stored does nothing (idempotent — restarts can't miss a boundary, same
   reasoning as the league roll). Register it in `lifespan`'s `tasks` list (:99-102). SPUS publishes daily, so
   a daily-ish interval is right; **the fetch happens HERE, off the request path — never in the reader.**

3. **Read path — resolve from the stored row.** `ShariaUniverseProvider` (or its accessors) reads the latest
   row instead of fetching: **no network, no `asyncio.to_thread` for a socket, no first-request stall.** The
   in-process cache becomes a plain read-through of the row (a cheap local DB read), not the source of truth.
   `default_halal_universe()` / `default_halal_universe_async()` / `get_sharia_universe_provider()` keep their
   **exact current signatures** — the four callers above are untouched. The `HalalUniverse` frozenset +
   `resolve()` three-state contract stays **byte-identical** so `safety_floor` / `sim_engine` / `room_runner`
   don't change.

4. **Staleness — unchanged in spirit (constraint 3 / CR040), but measured against the recorded date.** Serve
   the held list while it is inside its window; past the window, pause loudly (`UNAVAILABLE`) exactly as now.
   `sharia_staleness_days` is 7 today, measured against `as_of`. **Open decision (state it, don't inherit):**
   whether a *held* list should be servable for a longer window than a *fetched* one — a held list ageing is
   a different risk than a fetch being stale. Pick a value, name it, justify it in the hand-off.

5. **Seeding — first boot, empty table, unreachable source ⇒ still `UNAVAILABLE`, and that is the ONLY path
   that produces it.** Correct behaviour; a guard must prove it.

6. **Refresh-failure visibility — degrade loudly on the REFRESHER, not the reader.** A refresh that fails N
   days running while the held list is still in-window is invisible to the user (they keep trading on a valid
   list) but **must be visible to us** — a rising log/metric on consecutive refresh failures. This is CR040
   applied to the refresher. (Don't make the reader loud for this — the reader is legitimately serving a good
   held list; the loudness belongs on the thing that's silently failing to update.)

## Tests

New `backend/tests/unit/test_cr075_sharia_persistence.py` (RED-first — the guards must fail before the fix),
one per acceptance criterion:
- **A1** Fresh row stored ⇒ resolve performs **no** network fetch. (Inject a fetcher that raises if called;
  seed a fresh row; assert `resolve()` works and the fetcher was **never** invoked.)
- **A2** Source made unreachable + held row **inside** its window ⇒ trades resolve normally against the held
  list, and the `as_of` surfaced is the **held** date (not `UNAVAILABLE`).
- **A3** Held row aged **past** its window ⇒ pauses loudly (`ShariaStatus.UNAVAILABLE`), exactly as today.
- **A4** `fetched_at` **advances** on a refresh where `as_of` does **not** — proving the parent-mirror
  freshness signal exists even though the file never says so.
- **A5** Two providers reading the **same** row resolve a given ticker **identically** (one universe, one date).
- **A6** First boot / empty table + unreachable source ⇒ `UNAVAILABLE` (seed path), and no other path does.
- Refresh-failure visibility: a repeated refresh failure while in-window logs the loud refresher signal (not
  a reader pause).
