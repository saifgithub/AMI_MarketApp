Track U returned **`AWAITING_FIXES` (round 1)**. Everything the round-1 hand-off asked to be verified

MAJOR was found independently, outside your claims list:**

**1. MAJOR — blocking synchronous HTTP inside `async def` routes.**
`website_api/app/services/turnstile.py` and `website_api/app/services/email_service.py` make
**synchronous** HTTP calls, and they are invoked directly from `async def` route handlers on a
**single-worker** process. Every such call parks the event loop for the duration of a network
round-trip, so one slow upstream stalls *every* concurrent request. Under a bot flood — which is
precisely the traffic Turnstile exists to absorb — this is self-inflicted DoS amplification.

This is the **same class** already flagged as an MVP show-stopper in **CR036**. Second occurrence,
so per CLAUDE.md it earns a **guard, not just a fix**: add a check that fails the build if a
`website_api` service makes a sync HTTP call reachable from an `async def` route.

Fix direction (yours to design, but two options and the tradeoff):
- **Make the calls async** (`httpx.AsyncClient`) — correct, and the routes are already `async def`.
- **Or make the route handlers sync `def`** — FastAPI then runs them in a threadpool and the loop is
  never blocked. This is exactly what the *backend* does for the same pattern
  (`backend/app/api/auth.py:130` `def magic_link_start` → blocking `smtplib`), which is why the
  backend is **not** affected. Cheaper, but caps concurrency at the threadpool size.

Prefer the async client unless you find a reason it doesn't hold. **Say which you chose and why.**

**2. MINOR — one genuine "the AI" in visitor-facing copy.**
`website/ami-trade/sad-to-see-you-go/index.html:71` says "the AI trading-education app". User-facing
copy names **AMI** (CLAUDE.md, behaviour-critical). The round-1 hand-off claimed a naming grep that

- `llm_client.py` gets this right elsewhere in the same codebase (`httpx.AsyncClient` +

**Consequence:** every blocking call runs directly on the event-loop thread of a single-worker
process, stalling the ENTIRE service — all other in-flight requests — for its duration. Worst
case on `/contact`'s escalation path: Turnstile (≤10s) + `send_contact_ack` (≤15s) +

pattern that triggers many concurrent blocking verify calls — the bot-protection mechanism
becomes a self-inflicted DoS amplifier under the exact load it exists to defend against.

This matches a bug class this project's own governance has already flagged as an MVP
show-stopper elsewhere (a backend blocking-I/O concurrency bug) — real institutional weight
behind treating this seriously rather than as a nitpick.

**Recommended fix:** swap the sync `httpx.post` calls in both files for `httpx.AsyncClient`/
`await`, mirroring `llm_client.py`'s already-correct pattern — or, minimally, wrap the existing
sync calls in `asyncio.to_thread`/`run_in_threadpool`.
