### The migration failure — resolved, but it WILL recur

`alembic upgrade head` died: `DuplicateTable: relation "badges" already exists`, on
`d1e2f3a40023 → d4e5f6a70024` (badges/streak_freezes, CR091/CR092/CR094).

Cause: the new container boots → `init_schema()` runs `create_all()` → creates the new tables from
the new models → then the migration tries to create them again. The protocol claims this was fixed
post-AT:R13; **the fix only covers a FRESH DB** (`init_schema` self-stamps after `create_all`). An
*existing* DB gaining new models hits it every time.

Resolved by `alembic stamp d4e5f6a70024` **after measuring that the live schema matched the
migration exactly** — 7/7 columns on `badges`, 5/5 on `streak_freezes`, same types, nullability,
the `false` server_default, both indexes, both unique constraints. Verified after: pointer reads
`d4e5f6a70024`, `upgrade head` is a clean no-op (exit 0). Saiful chose the stamp from three options.

**⚠️ Stamping was only safe because the schemas happened to match.** If a future migration does
something `create_all()` cannot — a backfill, a rename, a data change — stamping past it silently
skips real work. **This deserves a DEF; I offered to file it and Saiful has not answered.** File it.
