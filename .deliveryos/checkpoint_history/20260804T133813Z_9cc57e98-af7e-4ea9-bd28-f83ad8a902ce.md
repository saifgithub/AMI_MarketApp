## What was decided / learned this session (the load-bearing bits)

- **I retracted my own r1 fix on M07 and it mattered.** I had labelled MUT-E
  (`deleted_at IS NULL` on `find_by_dedupe_key`) "the fix". It is not: with the
  non-partial constraint it returns **500** on POST 2 (I verified by execution,
  AUD-1). The real fix was the *invariant* — "at most one LIVE Finding per user
  per entry type per day" → a **partial unique index** on `deleted_at IS NULL`
  (migration `d3e4f5a60029`). Lesson recorded in two verdicts: **derive the fix
  from the violated invariant, not from where the symptom surfaced.** Second time
  in CR136 (M06's four rounds was the first).
- **M07 B1 escalation is the model for goal-based auditing.** The architect
  self-reported a dead journal id. I reproduced it AND asked what happens on the
  *third* POST: `daily_used` counts journal ROWS, the write always collided, so
  no row was created and **both spend counters froze** — 5 generations against a
  cap of 2, bounded only by the 5/min rate limiter whose own comment says it is
  not the spend control. That escalation is what made it a BLOCKER.
- **Mutations that survive are the finding.** M04 r2 m3 (MUT-H/MUT-I both
  survived all 36 card tests) and M07 r1 (MUT-E survived = the composition was
  pinned in NEITHER direction). Both drove the next round.
- **AUD-3 pattern worth reusing**: keep a dialect-specific predicate for Postgres
  but drop it for sqlite. "Spelled identically on both dialects" is a true claim
  that is useless if the suite exercises only one. 3 tests failed → it does.
- **Calibration held.** M04 r3 came back with **zero findings** and I said so
  plainly rather than manufacturing one. Saiful endorsed goal-based evaluation
  (`memory/feedback_audit_against_goals.md`).
