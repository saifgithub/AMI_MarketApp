**5. THE OOM chain (most recent, most important not to re-litigate):**
   - Probe 1: OOM-killed exit 137 at step 200/400. I wrongly blamed `cutoff_len=5120` (memory
     pressure) and reverted to 4096. **This revert was WRONG** — training was healthy (25.4
     s/step, faster than run 1's 28.2s; loss 0.40→0.22; token acc 0.89→0.93).
   - Probe 2 (with `prediction_loss_only=True` added, cutoff restored to 5120): OOM-killed AGAIN
     at step 200. This proved the real cause: **TRL's own `compute_metrics` reports
     `mean_token_accuracy`, which needs logits, which silently overrides
     `prediction_loss_only` back to False.** Setting that flag did nothing.
   - Root cause: HF Trainer accumulates eval LOGITS across all 47 val batches for
     `compute_metrics`. Vocab=131,072 → ~2GB/sequence in fp32 → ~100GB accumulated at
     `eval_steps=200`. Run 1 never hit this because its val targets were short (331-char
     median); run 2's val carries recipe-10 reports.
   - **Fix: `eval_strategy="no"` — in-training eval disabled entirely**, not just the logits
     flag. This is ALSO the methodologically correct call independent of the OOM: run 1 hit a
     great eval loss (0.2384) and still couldn't produce the deliverable, because val.jsonl is
     drawn from the same generators as train (decorrelated in examples, identical in SHAPE —
     P27). What decides run 2 is `eval_surfaces.py` free-generation, not held-out loss.
     Held-out loss is still measured once, after merge, via `eval/quick_eval.py`.
   - **cutoff_len is back at 5,120 and should STAY there** — it was never the problem across all
     three probes. Do not revert it a third time without new evidence.
   - Probe 3 launched with eval off: `docker run -d --name ami_probe ... --probe 400`, config/
     train_lora.py already synced to alpha-spark.
