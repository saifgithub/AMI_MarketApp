## What was decided this session

1. **Reframe from "too conservative" to "too narrow to differentiate."** Saiful,
   2026-09-22: risk appetite (and other settings) may be too narrow; higher risk
   appetite should recommend more, and the highest tier should recommend more
   than the market/Street. Risk-score derivation should use all the app's
   parameters, not just three.

2. **Code audit found the dial has no approval-propensity mechanism**, only a
   sizing mechanism:
   - `DEFAULT_RISK_TIER_CAPS = {1:1.5, 2:1.5, 3:3.0, 4:4.5, 5:4.5}`
     (`backend/app/trading_math/sizing.py:22`) — 5 slider positions, 3 distinct caps.
   - `_portfolio_manager_block` (`backend/app/agents/overlay_generator.py:883`) —
     the ONE agent that decides APPROVE/PASS — has no risk branch, only
     `Consider risk_score={n} and current drawdown` (:900), directionless.
   - `_derive_risk_score` (`backend/app/services/concierge_engine.py:455`) uses
     only 3 of 7 onboarding answers (`drawdown_response`, `regret_asymmetry`,
     `concentration_tolerance`). `max_drawdown_pct` causality is BACKWARDS
     (risk_score suggests it via `q6_text`, user's answer never feeds back).
     `risk_quotes` (3 verbatim user sentences) is written/journalled but read by
     ZERO prompts, despite being user-editable in Settings (CR220).
   - `primary_goal`, `horizon` collected, barely/never branched on for risk.

3. **CR197's ablation (`docs/forward_planning/CR197_risk_debate_effectiveness/REPORT.md`)
   reframes the fix**: the PM PASSes for want of option generation, not courage —
   "the debate hands the PM a middle-sized alternative it does not construct on
   its own; without it the PM sees only the Trader's raw take-it-or-leave-it
   proposal, and leaves it." This means widening the cap table IS the approval
   fix, not just a sizing fix. Corroborating: `pm_option_ladder_enabled`
   (`backend/app/core/config.py:802`, currently OFF) measured +4.8pp
   (16.3%→21.1%) over the same 136 convenes.

4. **Baseline is partly contaminated by infrastructure**: `backend/app/core/config.py:138`
   records ~7% of PM calls being killed at the old 90s timeout → DEF059 fail-safe
   PASS. Timeout is now 180s (verified deployed: `ROOM_AGENT_TIMEOUT_S=180.0` on
   `ami_api_alpha`, checked 2026-09-22). Any pilot/experiment MUST exclude
   `overridden_from_llm=true` records or bake the old outage rate into the number.

5. **Sequencing Saiful chose** (explicit): "We will end up doing all 3. Start
   with widening the cap. Then the prompt and then the structural change." So:
   Step 2 = widen cap table (+ widen `_derive_risk_score` inputs: `max_drawdown_pct`,
   `horizon`, `primary_goal`). Step 3 = PM prompt risk branch. Step 4 = graded
   `approve_votes` (0-5) threshold by risk tier.

6. **Ran Step 1 pilot on Alpha** (melehost, `ami_api_alpha` container) —
   2 arms × 30 tickers, risk_score 1 vs 5, same tickers (paired), via
   `backend/scripts/room_benchmark.py --mandate-json ... --fresh-user`.
   `--fresh-user` is MANDATORY: `resolve_mandate` (`backend/app/services/mandate_store.py:292`)
   ignores `mandate_override` when the user already has a stored mandate — without
   fresh users both arms silently run identically. Verified pre-flight (both the
   cap resolution AND the exact overlay text) before spending GPU time.

## Step 1 RESULT — already committed, do not re-run

**Contradicted my own prediction.** I expected no approve-rate difference (PM
prompt unchanged) and only a size difference. Measured (n=29 judged pairs,
FAILSAFE/floor-override excluded):

| | R1 | R5 | delta |
|---|---|---|---|
| approve rate | 3.4% (1/29) | 24.1% (7/29) | **+20.7pp** |
| mean approve_votes (0-5) | 0.31 | 1.24 | **+0.93** |
| mean size_pct on APPROVE | 1.00% | 4.50% | — |

6 verdict flips, all PASS→APPROVE, zero reverse. McNemar exact **p=0.031**
(significant at n=29). Both arms remain far below the Street's 60.0% on this
sample (per-ticker consensus in `docs/forward_planning/CR035_room_benchmark/results/consensus.jsonl`).

**Mechanism** (verified, not guessed): the PM prompt itself is 987 chars in BOTH
arms, differing by one digit. The effect runs through the Trader/risk-debate
SIZING ladder — R1 compresses proposals to a narrow band near 1.5%, R5 spreads
the same debate across a band up to 4.5%, handing the PM a bigger/more-separated
menu of sizes. This is CR197's option-generation lever firing across the
risk_score axis with NO prompt change. Full writeup + data + scorer:
`docs/forward_planning/CR228_risk_appetite_differentiation/README.md` (section
"Step 1 result"), `results/runs_cr228-r{1,5}-20260922.jsonl`,
`results/pilot_scored_2026-09-22.txt`, `score_pilot.py` (reusable — takes two
runs_*.jsonl paths, does the paired McNemar comparison, excludes FAILSAFE).

**Implication for Step 2**: widening the cap table is now a MEASURED
differentiation fix, not just reasoned-about. Steps 3-4 should be scoped and
measured as ADDITIONS on top of this baseline (since a real, if too-narrow,
spread already exists without them) — not as the first source of any spread.
