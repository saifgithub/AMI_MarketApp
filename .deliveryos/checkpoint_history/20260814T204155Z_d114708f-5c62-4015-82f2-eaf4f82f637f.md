# Bugs found + fixed this session (all in qa/appium/, all MINE from CR162, all verified live
# on the device before AND after the fix)

## Fix 1 — `labelled_only` silently no-op on Android
`helpers/locators.py::interactive_elements()` — the `labelled_only` kwarg was implemented
inside the iOS NSPredicate branch only; the Android branch (`clickable(true)` UiSelector)
ignored it completely and returned every clickable node regardless. Introduced in commit
`82a54433` (my own CR162 perf commit). Consequence: `helpers/onboarding.py::_live_chip`
picks the bottom-most labelled candidate and documents BY NAME that this filter excludes the
unlabelled send-arrow beside the text input — on Android it didn't, the arrow sits below the
chip row, and the Concierge onboarding walk spent its entire 120s budget tapping send on an
empty field. Verified via `diag_candidates.py` (in scratchpad, not committed) before/after:
before fix, `labelled_only=True` returned 5 candidates (same as False); after, 3 (correctly
excluding the EditText + send arrow at y=626, keeping only the 3 labelled chips at y=514).
FIX: added `_android_label()` helper reading `content-desc` OR `.text`, client-side filter
after the Android UiSelector query. Docstring rewritten to explain WHY the mechanisms differ
per-platform (iOS: no "any label" predicate exists in UiSelector; Android: attribute reads
are cheap enough that per-candidate filtering is fine, unlike WebDriverAgent).

## Fix 2 — Android text locators never searched `content-desc`
`_all_by_text()` / `_all_by_text_contains()` in `helpers/locators.py` used ONLY
`UiSelector().text("...")`. Flutter's Android engine maps `Semantics(label:)` to
`AccessibilityNodeInfo.setContentDescription()`, NOT `setText()` — a canvas-painting Flutter
app has essentially no native TextViews, so almost every user-visible string lives in
`content-desc`. This bug is CR080-ORIGINAL, not CR162 — traced via
`git log -L /def _all_by_text/,.../:qa/appium/helpers/locators.py`, present since commit
`edbef146` (CR080's original harness) and just carried forward unchanged through my CR162
rewrite. Measured live: tree contained `content-desc='FLOOR'` while
`exists_text(driver,'FLOOR')` returned `False`. This made `test_bottom_nav_text_resolves` AND
`ensure_onboarded`'s early-return probe (`wait_visible_text(driver, "FLOOR", timeout_s=5)`)
both unsatisfiable on Android — meaning **every prior "landed on Floor" check in CR080's
history could never actually have confirmed that text-based landing on Android**, only the
identifier-based checks (which didn't exist before CR162) could have. This needs more
investigation eventually re: how CR080's suite reported passes historically — NOT resolved
this session, flagging for later, did not chase it further.
FIX: `_all_by_text`/`_all_by_text_contains` now query BOTH `description("...")` (tried first,
the common case) and `text("...")` on Android, sharing one retry ladder via new
`_find_any_with_retry()` helper (so a miss doesn't pay the backoff twice).

## Fix 3 — retry backoff nested inside `wait_visible_*`'s own deadline
`wait_visible_text`/`wait_visible_id` poll in a loop with their own `timeout_s` deadline, but
called the underlying lookup with `retry=True` (the default) — so each "attempt" inside the
poll loop ALSO ran its own ~5.4s backoff ladder internally. Measured: a miss cost 7.65s
against a `timeout_s=2` budget (vs 0.37s with `retry=False`). This is what made the whole
Android run feel painfully slow — Saiful flagged this directly mid-session ("the phone is not
slow... your commands to test it is very slow") and he was right, this was 100% my harness,
not the device.
FIX: both `wait_visible_text` and `wait_visible_id` now call the lookup with `retry=False`
inside their own poll loop — the wait function owns the deadline, the lookup just does one
attempt per poll tick.

## App defect fixed — HexButton double-announces its label (DEF249-class, 3rd occurrence)
`mobile/lib/widgets/hex/hex_button.dart` — `Semantics(label: label, child: <...Text(label)...>)`
wraps a subtree whose Text renders the identical string; Semantics merges its own label with
merged descendants', producing a doubled announcement. Measured live on device:
`content-desc='CONVENE THE ROOM\nCONVENE THE ROOM'` on the Floor screen's primary CTA. Same
exact pattern as DEF249 (bottom nav gave "FLOOR\nFLOOR", Concierge chips same) — this is the
**third occurrence**, so per `failure_patterns.md`'s "second occurrence gets a guard" rule I
added a proper guard rather than just a spot-fix.
FIX: removed the redundant `label: label` from the outer `Semantics(...)` in
`hex_button.dart` (~line 106) — the child Text already supplies it via merge.
NEW TEST: `mobile/test/widgets/hex_button_semantics_test.dart` (created this session) — 5
cases: label announced exactly once, button+enabled flags survive, disabled state still
readable, tap not swallowed, visible Text renders once. **Mutation-verified**: manually
reintroduced `label: label` into a backup copy of the source, re-ran the test suite, confirmed
it fails with the correct diagnostic message ("HexButton announces its label 2 times..."),
then restored the real fix. This is the same mutation-check rigor CR163's `mutation_guard.sh`
uses for the crawler — applied here by hand since this is a single widget test file.

This fix breaks the "3 failures due to duplicated label" cluster in the phase1 run:
`test_floor_renders_convene_cta`, `test_convene_sheet_navbar`,
`test_convene_sheet_scroll_overflow` — all should now find "CONVENE THE ROOM" by exact text.
NOT YET RE-VERIFIED against the device after this particular fix — see Open Items.
