**DEF209 — OneSignal push, OPEN, in-progress diagnosis.**
- Found live, immediately after promoting CR027: `send_notification.py` run inside
  the container against a real (CR035-synthetic, non-human — safe to use per
  `feedback_user_report_exclusions` memory, `last_app_version='room-benchmark'`)
  Alpha user got a genuine OneSignal 403.
- Root cause #1 (fixed, confirmed real): `notification_service.py` sent
  `Authorization: Basic {rest_key}` — the legacy v1 scheme. The configured key is
  the current `os_v2_app_…` format (113 chars), which OneSignal's own API
  reference (`documentation.onesignal.com/reference/create-message`, fetched live)
  requires as `Authorization: Key {rest_key}`. Fixed in
  `backend/app/services/notification_service.py` (one word) +
  `backend/tests/unit/test_notification_service.py`'s pinned assertion. Filed as
  **DEF209** (row: `docs/defect/_registry/DEF209.row.md`), committed, redeployed,
  full backend suite green (1947 passed after this + the CR084 test fix).
- Root cause #2 (NOT yet fixed — this is the open thread): after the scheme fix
  and redeploy, the exact same 403 still occurs. Raw diagnostic call from inside
  the live container with the corrected header reproduces it identically. Per
  OneSignal's own docs (fetched live), an `os_v2_app_…` key has send-permission by
  default, so this isn't a scheme/permission-shape problem — narrowed to: (a) an
  IP allowlist on the key blocking melehost's egress IP, (b) the key having been
  rotated/revoked since being pasted into `infra/alpha.env`, or (c) an app_id/key
  mismatch (multiple OneSignal apps).
- **Saiful just reported he successfully sent a push via the OneSignal dashboard
  UI itself.** I explained why this narrows things further rather than resolving
  it: the dashboard authenticates via his logged-in web session, NOT the REST API
  key — so it confirms the app itself is healthy and (if he received it on a
  device) that client-side device registration works, but it does **not**
  validate the REST key credential path our backend code actually uses. This
  makes the REST key itself (options a/b/c above) even more likely to be the
  actual fault, not a broader account/app problem.
