- **Background-notification timing trap** (documented in toolkit README,
  commit `08109cbb`): a `bash ... & ` launched via `run_in_background: true`
  fires its "completed" notification when the OUTER call detaches the INNER
  `&` process, NOT when that process itself finishes. Hit this repeatedly
  live this session on both 5-min full-Room draws and ~20s single-agent
  replays. ALWAYS verify via `ps -p <pid>` (capture `$!` at launch) or the
  real output file — never trust the notification text alone. The reliable
  pattern used throughout: `while ps -p <pid> > /dev/null 2>&1; do sleep 5;
  done` wrapped in its OWN `run_in_background: true` call, which DOES give a
  trustworthy completion notification since the wait loop only exits when
  the real process dies.

  always `[{"role":"user","content":"Convene on X."}]`. The REAL task text,
