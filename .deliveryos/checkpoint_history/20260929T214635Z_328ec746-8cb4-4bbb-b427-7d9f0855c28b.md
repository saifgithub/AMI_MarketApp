4. **Scoped the Cloud Run Jobs migration (§10 Option 2) from actual code**, not guessed —
   dispatched a research subagent to read `room_runner.py`, `room.py`, `infra/gcp/*.tf`, and the
   mobile polling path. Findings written into CR245 §10 (commit `c600ffa8`), the load-bearing
   one:
   - **Persistence is already process-independent**: `RoomRunRow` (Postgres) is written
     incrementally by `_checkpoint_run`/`_persist_run` after each of the 12 agents
     (`room_runner.py:5091-5153`), and `GET /v1/room/{run_id}` (`room.py:422-439`) already reads
     it via plain DB read — no in-memory dependency. **A Cloud Run Job calling the same `run()`
     path against shared Postgres would already produce a row the existing endpoint can serve,
     unmodified, from a different process.** No Redis anywhere in the Room path (confirmed by
     grep).
   - **The real seam**: live SSE streaming (`room.py:311-371`) reads from
     `_active_queues: dict[UUID, asyncio.Queue]`, a plain in-memory attribute on the
     process-global `RoomRunner` singleton (`room_runner.py:5339`). If a Job runs in a separate
     container from the API service serving SSE, `subscribe()` silently returns nothing — not an
     error — which collides with this repo's own CR040 "degrade loudly" rule. Same issue for
     `_retrying_runs`/`_pending_retry`/`_pump_tasks` (other in-memory-only state).
   - `_sweep_stuck_runs()` already has a **recorded, rejected** design alternative for exactly
     this multi-instance case (DEF425.architect.md round 2) — flagged as unfinished work
     independent of the Jobs question.
   - **Mobile's `_recoverViaPolling()`** (`room_providers.dart:591-659`) can reconstruct full
     final state via polling but only reacts to terminal status; live per-phase/per-token
     events are SSE-only. 90s polling cap is itself shorter than the ~5min observed run.
   - **Zero Cloud Run Jobs resources exist in Terraform today** — only one
     `google_cloud_run_v2_service.api` (`cloud_run.tf:5`). Confirmed the `timeout=300s` line
     sits under a stale comment ("~90s + buffer") — doc-drift, independently noted under
     Option 1 too.
   - **Explicitly still no engineering-effort estimate** — the scoping narrows *what* changes
     (RoomRunner's in-memory state + new Terraform), not *how long*. Saiful asked "did we
     estimate the amount of work?" — answer given was no, and offered to break it into 6 pieces
     (Terraform, dispatch redesign, cross-process live-SSE replacement, stuck-run-sweep fix,
     mobile polling-cap fix, testing/rollout) if he wants that written up — **not done yet,
     he hasn't asked for it explicitly**.

5. **Answered two architecture questions verbally (not written into any CR, correctly — these
   were "explain," not "record a finding"):**
   - "did we have 3 dockers or should we have 1?" → melehost (Alpha) actually runs **5**
     containers (`postgres`, `redis`, `api-alpha`, `api-website`, `cloudflared` — confirmed via
     `docker-compose.yml` service keys, corrected an earlier mis-grep that only found 3). Cloud
     Run Terraform has only **1** service defined; Postgres/Redis on Cloud Run would be managed
     services (Supabase/Memorystore), not sibling containers — so "3 vs 1" doesn't map cleanly
     onto Cloud Run.
   - "could all of them be grouped into 1 docker?" → answered no, with reasons: Postgres/Redis
     are maintained upstream images (bundling = losing upstream patching), independent
     lifecycle/restart-without-DB-downtime, independent resource budgets, and this is exactly
     the "one service = one VM" model that §11 flags as a *risk* in Cloudways/Elestio, not
     something to emulate ourselves. Also ties to melehost's own proven C3 security finding
     (Compose networking mistakes) — more tangled container boundaries make that class of
     mistake easier, not harder.
