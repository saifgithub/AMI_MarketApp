**The CR's own design had a hole, found by checking it was still actionable before building (this
is the pattern worth repeating on the next 2-3 CRs too — verify the spec against current reality
before implementing it as written):** re-reading the counters mid-session gave 1,064,911 queries —
**fewer** than the 59,681,175 recorded 3 days earlier in the CR doc — because the vLLM process had
restarted. Δqueries = −58,616,264. The CR's acceptance criterion #2 (`Δhits/Δqueries` between two
samples) returns a negative/nonsensical rate across that boundary; a naive `max(0,...)` clamp would
read as a total cache collapse — a well-formed 200 with plausible numbers, harder to catch than an
unreachable host. Fixed in the design itself: `_rate_between()` detects any counter descent and
returns `status="reset", rate=None` rather than a number. Storing counters RAW (never as a
pre-computed rate) is what makes the reset detectable at all — documented as now load-bearing for a
second, unanticipated reason. 3 distinct not-a-measurement statuses, all `rate=None`: `reset`,
`no_queries_in_window`, `insufficient_samples`. 18 tests, mutation-proven 3/3 (removing the reset
check, making an idle window report `0.0`, making absent counters parse as zero — each reds exactly
the tests written for it).
