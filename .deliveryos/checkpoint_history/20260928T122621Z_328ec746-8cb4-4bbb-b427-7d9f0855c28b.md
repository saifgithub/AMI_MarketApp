3. **CR245 §9**: floated a 3-environment strategy (Alpha/Beta/Prod, same Terraform module,
   scaling 1,000→1,000,000 users) — exploratory only, not decided.
4. **CR245 §10 — the big finding this session**: Convene the Room is a ~5-minute single SSE
   connection. Cloud Run's `timeout=300s` (currently configured in `infra/gcp/cloud_run.tf`)
   is ALREADY shorter than that — a live bug independent of everything else. Three platform
   options recorded, NONE chosen:
   - **Option 1**: Cloud Run as-is (raise timeout, tune `concurrency` down from 80) — has
     the connection-holding/billing problem Saiful flagged (80-way concurrency on a thin
     2vCPU/2GiB instance, billed for idle-waiting time).
   - **Option 2**: Cloud Run + async job/poll instead of held-open SSE — mostly-existing
     groundwork already in the codebase (push-notification stub in `room.py`
     `_finalise_to_journal` — `TODO B1: fire APNs push notification here`; mobile's
     `open_room_verdict` deep-link route, also stubbed; working poll fallback via
     `GET /v1/room/{run_id}`). BUT: real unresolved risk — `start_run()` launches Room
     execution via bare `asyncio.create_task()` (`room_runner.py:5984` area), and Cloud
     Run's default request-based billing throttles CPU to near-zero once the triggering
     HTTP response returns — a documented Cloud Run failure pattern, not yet mitigated. Real
     fix is Cloud Run Jobs (separate GCP primitive, run-to-completion, no live connection
     needed) — a genuine backend re-architecture, not a config change.
   - **Option 3**: VPS (same execution model as Alpha/melehost today, no throttling risk at
     all) — CR006-confirmed pricing $15-23/mo (Contabo/OVHcloud). Real tradeoff: security/ops
     burden becomes fully self-managed. Grounded in a REAL proven incident, not hypothetical
     — `docs/governance/security_review_2026-07-29.md` finding C3 (Critical): Docker Compose
     on melehost bypasses `ufw`, published Postgres (superuser, default password) and Redis
     (no auth) on `0.0.0.0`, proven live-exploitable from an ordinary LAN device, read all 30
     tables. Required CR123/CR124 to remediate.
5. **CR245 §11** (this turn, just before savepoint): researched managed-VPS options that
   handle security/backups/updates, per Saiful's direct ask. Four candidates:
   - **Raw VPS** (Contabo/OVHcloud) — confirmed price, zero managed security (same as #3
     above).
   - **Netcup Managed Private Server** — RULED OUT. Confirmed from their own FAQ: "provided
     without root or sudo access" — incompatible with Docker/Compose, which needs
     root-equivalent access.
   - **Cloudways** — confirmed (from Cloudways' own pages): automated OS security patching,
     managed firewall, Imunify360 (real-time threat/malicious-IP detection), automated
     backups, SSL, retains SSH access for custom Python. GAP: not verified whether it can
     host this app's actual multi-container Docker Compose stack (Postgres + Redis +
     FastAPI together) — their platform is built around single-app-per-server hosting. A
     pricing-page fetch attempt this session returned corrupted binary content, not real
     data — price NOT re-verified.
   - **Elestio** — confirmed (from Elestio's own pages): automated updates, daily backups,
     TLS, CI/CD deploy from GitHub/GitLab/Docker registries (not just their pre-built app
     catalog). Pricing hourly, "starts at $11/mo" (smallest single-service tier, not an
     all-in multi-service price). GAP: their standard model is "one service = one VM" (full
     isolation per service) — unclear if this maps cleanly onto a 3-service stack
     (FastAPI+Postgres+Redis) as one unit, or would need splitting into 3 separate VMs.
