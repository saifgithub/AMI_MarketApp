## 6. The finding worth carrying forward

**Writing "revert-proof QA" from reasoning about the code, rather than from actually running the
revert, produced three wrong claims out of four in one lane.** The pattern that got past me twice in
one file: a defect fix composed of two overlapping gates (or a fix + a non-vacuity companion test)
can leave the NAMED test permanently green while an incidental OTHER test is the one that actually
notices regressions — so the QA table's attribution was confidently wrong even though *something*
in the file did fail under mutation. The auditor's method — apply the mutation to real source, run,
revert, read the actual failing test name — is not optional rigor, it's the only way this class of
error is catchable. Going forward: before writing a "reverting X turns test Y red" claim, actually do
it and paste the real test name from the output, never infer it from what the test's docstring says
it's for.
